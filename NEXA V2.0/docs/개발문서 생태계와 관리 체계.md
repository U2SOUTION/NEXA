# SW 개발 문서 생태계 와 관리 체계

## **[확장판] 소프트웨어 개발 문서 관리 체계 (11대 분류)**

| 폴더 번호 | 문서명 (영문)                    | 핵심 목적 (Objective)                   | 주요 포함 항목                                                  | 관련 소스 및 근거                       |
| :-------- | :------------------------------- | :-------------------------------------- | :-------------------------------------------------------------- | :-------------------------------------- |
| **01**    | **BRD** (사업 전략)              | 비즈니스 가치와 수익 모델 정의          | 비전, 타겟 시장, **수익 모델(BM)**, 비용 및 예산                | 프로젝트의 최상위 나침반                |
| **02**    | **Legal & Policy** (법무/정책)   | 법적 규제 준수 및 서비스 이용 약관 관리 | **개인정보 처리방침**, 이용약관, PG사 연동 조건                 | BRD의 리스크 항목에서 독립 분리         |
| **03**    | **MVP Plan** (실험 계획)         | 가설 검증을 위한 최소 기능 정의         | 핵심 가설, **필수 구현(In-Scope)**, **구현 제외(Out-of-Scope)** | 오버엔지니어링 방지 및 빠른 검증        |
| **04**    | **Decision Log** (의사결정/회고) | 프로젝트 주요 분기점 및 실험 결과 기록  | 피벗 판단 기준, **기술 선택 이유(Why)**, 장애 회고 기록         | MVP 실험 결과 및 TDD의 결정 근거 기록   |
| **05**    | **PRD** (기획서)                 | 제품의 구체적인 동작 규칙 정의          | 유저 스토리, **기능/비기능 요구사항**, **예외 케이스**          | 개발/디자인/QA의 공통 설계도            |
| **06**    | **Analytics Spec** (데이터 분석) | 비즈니스 지표 측정을 위한 추적 설계     | 이벤트 태그(GA4/Mixpanel) 명세, 트리거 조건, 속성값             | PRD의 성공 지표(KPI)를 기술적으로 구현  |
| **07**    | **UI/UX Spec** (디자인)          | 화면 설계 및 인터랙션 정의              | 디자인 시스템, **유저 플로우**, **데이터 매핑**                 | 기획과 개발 사이의 시각적 연결          |
| **08**    | **TDD** (기술 설계)              | 시스템 아키텍처 및 데이터 흐름 설계     | **DB 스키마**, **API 명세**, 시스템 아키텍처                    | 코드 구현 전 기술적 무결성 확보         |
| **09**    | **Admin & Ops** (운영 매뉴얼)    | 내부 관리자용 시스템 조작 및 운영 지침  | 어드민 페이지 사용법, **CS 처리 절차**, 수동 DB 조작 가이드     | TDD의 배포/운영 환경 항목에서 독립 분리 |
| **10**    | **QA Test Case** (검증)          | 출시 전 기능 및 보안 결함 확인          | **해피 패스(정상)**, **새드 패스(예외)**, 버그 추적 리포트      | 예기치 못한 크래시 및 보안 구멍 방지    |
| **11**    | **User Guide** (공개 문서)       | 최종 사용자를 위한 제품 설명 및 지원    | 가입 가이드, **자주 묻는 질문(FAQ)**, **업데이트 이력**         | CS 답변 시간 단축 및 유저 신뢰 구축     |

### **정확한 분류를 위한 가이드라인**

1.  **리스크 관리의 분리 (02번)**: 기존에는 BRD의 일부였으나, 개인정보 보호법이나 이용약관은 출시 직전에 매우 중요해지므로 별도 폴더로 관리하여 법적 분쟁을 예방해야 합니다.
2.  **데이터 분석의 독립 (06번)**: 단순히 "성공 지표를 보겠다"는 계획(PRD)과 "어떤 버튼 클릭 시 어떤 값을 보낸다"는 분석 명세는 다릅니다. 이를 분리해야 개발자가 정확한 이벤트 로그를 심을 수 있습니다.
3.  **운영 지침의 체계화 (09번)**: TDD가 개발을 위한 것이라면, 운영 매뉴얼은 출시 후 관리를 위한 것입니다. 특히 1인 개발 시 나중에 "이 데이터를 어떻게 수정했었지?"라며 헤매는 시간을 줄여줍니다.
4.  **히스토리의 기록 (04번)**: MVP 실험이 실패했거나 기술 스택을 변경했을 때, 그 **'이유(Why)'**를 별도로 기록해두면 나중에 똑같은 시행착오를 반복하는 것을 막을 수 있습니다.

### **💡 절충안의 핵심 규칙 (Naming Convention)**

1.  **Prefix (분류 번호) 필수**: `01_`부터 `11_`까지 번호를 맨 앞에 붙입니다. 이는 다른 에디터 탐색기에서도 **사업 → 기획 → 개발 → 검증** 순으로 문서가 정렬되도록 강제하여 "개발 11대 문서 생태계"의 흐름을 지켜줍니다.
2.  **Middle (직관적 이름)**: 한글이나 영문으로 문서 내용을 명확히 적습니다. (예: `결제프로세스`, `시스템아키텍처`)
3.  **Suffix (버전 vs 날짜)**:
    - **버전(`v1.0`)**: 문서의 **완성도와 상태**가 중요할 때 사용합니다. 특히 디자인이나 기획서처럼 개발자가 참고해야 할 '최종본' 개념이 강한 문서에 적합합니다.
    - **날짜(`240610`)**: 문서의 **발생 시점과 히스토리**가 중요할 때 사용합니다. 실험 결과나 결정 기록처럼 "그때 왜 그랬는지"에 대한 맥락이 필요한 문서에 적합합니다.
4.  **아카이브 활용**: 만약 탐색기가 너무 지저분해지면, 구버전 파일들은 폴더 내에 `_Archive` 폴더를 만들어 옮기고, 최상위에는 항상 **최신 버전 하나**만 남겨두는 것이 오버엔지니어링을 방지하는 좋은 방법입니다.

이 절충안을 사용하면 옵시디언 외부의 탐색기에서도 **논리적인 순서**로 정렬되면서도, 파일명만 보고도 해당 문서가 **어떤 단계의 어떤 정보**인지 즉시 파악할 수 있습니다.

## **🏢 BRD vs 📱 PRD 한눈에 비교하기**

| 구분 [1, 2]    | BRD (Business) - 사업관점                            | PRD (Product) - 제품 기능관점                           |
| -------------- | ---------------------------------------------------- | ------------------------------------------------------- |
| **쉽게 말해?** | **"이 사업으로 어떻게 돈 벌 것인가?"**               | **"유저에게 어떤 기능을 제공할 것인가?"**               |
| **핵심 질문**  | **Why & Who** (왜 만들고, 누가 돈을 내는가)          | **What & How** (무엇을 만들고, 유저는 어떻게 쓰는가)    |
| **주요 독자**  | 투자자, 경영진, 사업 담당자 (비즈니스 조직)          | 개발자, 디자이너, QA 엔지니어 (제품 메이커)             |
| **핵심 내용**  | 시장 분석, 경쟁사 요금제, 수익 모델, 예산, 매출 목표 | 유저 시나리오, 기능 리스트, 예외 처리 규칙, 데이터 매핑 |

## **01. BRD (비즈니스 요구사항 정의서) 상세 세부 항목**

장기 프로젝트의 최상위 나침반이자, PRD의 부모 문서가 되는 **BRD(Business Requirements Document, 비즈니스 요구사항 정의서)**의 세부 항목을 테이블로 정리해 드립니다.

BRD는 기술이나 화면 기능이 아니라, **"이 프로젝트가 왜 사업적으로 가치가 있는가? 어떻게 돈을 벌고 시장에서 살아남을 것인가?"**를 정의하는 비즈니스 전략서입니다. 1인 개발이라도 이 문서가 단단해야 개발 도중 흔들리지 않고 '수익을 내는 제품'을 만들 수 있습니다.

| 항목 분류 [2, 3]          | 세부 항목명 (영문명)                      | 설명                                                                       | 1인 개발자를 위한 현실적인 작성 팁                                  |
| ------------------------- | ----------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| **1. 프로젝트 개요**      | 비즈니스 배경 (Background)                | 이 프로젝트를 시작하게 된 시장의 기회나 문제 상황을 기술합니다.            | "기존 앱들은 A 기능이 비싸서 유저들이 불편해함" 등 시장의 틈새 기술 |
|                           | 비전 및 목표 (Vision & Goals)             | 이 서비스가 궁극적으로 도달하고자 하는 최종 모습을 정의합니다.             | 예: "출시 6개월 내 틈새시장 점유율 10% 달성"                        |
| **2. 시장 및 타겟 분석**  | 타겟 시장 (Target Market / TAM)           | 제품이 진입할 실제 시장의 규모와 특성을 정의합니다.                        | 전체 시장 크기보다 내가 당장 침투 가능한 유저 규모 분석             |
|                           | 경쟁사 분석 (Competitor Analysis)         | 직접적/간접적 경쟁 서비스들의 장단점과 요금을 분석합니다.                  | 경쟁사 대비 **내 서비스만의 확실한 차별점(USP)** 1가지 명시         |
| **3. 비즈니스 모델**      | 수익 모델 (Monetization / BM)             | 이 서비스를 통해 **어떻게 돈을 벌 것인지** 구조를 정의합니다.              | 구독형(SaaS), 광고, 건당 수수료, 인앱 결제 등 구체적 설정           |
|                           | 비용 및 예산 (Cost & Budget)              | 개발 및 운영(서버비, 외부 API 비용, 마케팅비)에 가용 가능한 예산입니다.    | 혼자 개발 시 시간(기회비용)과 월 고정 인프라 비용 한도 설정         |
| **4. 핵심 비즈니스 요구** | 킬러 기능 정의 (Core Capabilities)        | 비즈니스 목표 달성을 위해 **제품이 반드시 해결해야 하는 핵심 가치**입니다. | PRD의 요구사항으로 이어지는 가장 중요한 비즈니스 규칙               |
|                           | 사용자 범위 (User Scope)                  | 시스템을 이용할 비즈니스 주체들을 정의합니다.                              | 예: 일반 사용자, 판매자, 시스템 관리자 등 권한 그룹 분리            |
| **5. 성공 지표 & 리스크** | 비즈니스 성공 지표 (Business Metrics)     | 서비스가 사업적으로 성공했는지 평가할 재무적/수치적 지표입니다.            | 매출액, 유료 전환율, 월간 활성 사용자 수(MAU) 등                    |
|                           | 제약 사항 및 리스크 (Risks & Constraints) | 법적 규제, 저작권, 기술적 한계 등 사업적 위험 요소를 파악합니다.           | 예: 전자상거래법 준수 여부, 개인정보 보호법(PG사 연동 조건) 등      |
| **6. 실행 로드맵**        | 단계별 로드맵 (Phase Roadmap)             | MVP → 정식 출시 → 확장 등 **사업 단계(Phase)**별 목표, 기간, 핵심 산출물을 정의합니다. | Phase 1(MVP 검증 4주) → Phase 2(유료화) → Phase 3(기능 확장)처럼 3단계만 먼저 작성 |
|                           | 단계별 성공 기준 (Phase Exit Criteria)    | 각 Phase를 종료하고 다음 단계로 넘어가기 위한 **최소 달성 조건**을 명시합니다. | MVP Phase는 03번 문서의 Go/No-Go 기준과 동일하게 유지 — BRD·MVP 중복 방지 |

---

### **💡 BRD 작성 가이드**

- **PRD와의 명확한 차이**:
  - **BRD**: "결제 대행사(PG)를 붙여서 월 9,900원의 **구독 모델로 수익을 창출**한다." (비즈니스 요구)
  - **PRD**: "마이페이지에 '구독하기' 버튼이 있고, 클릭 시 Toss Payments 모달이 열리며 결제 성공 시 DB의 멤버십 등급이 업데이트된다." (기능 요구)
- **1인 개발자의 흔들림 방지**: 혼자 장기 개발을 하다 보면 기능 구현(코딩)의 재미에 빠져 **"내가 이걸 왜 만들고 있었지? 돈은 어떻게 벌지?"**를 놓치기 쉽습니다. 개발 도중 방향성이 헷갈릴 때마다 이 BRD를 열어보고 브레이크를 잡아야 오버엔지니어링을 막을 수 있습니다.

## **03. MVP (최소 기능 제품 검증 계획서) 상세 세부 항목**

| 항목 분류 [2, 3, 4] | 세부 항목명 (영문명)                        | 설명                                                                                                          | 1인 개발자를 위한 현실적인 작성 팁                            |
| ------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| **1. 가설 정의**    | 핵심 비즈니스 가설 (Core Hypothesis)        | "사용자들은 **[문제]**를 겪고 있으며, **[핵심 기능]**을 주면 **[행동]**할 것이다"를 정의합니다.               | BRD의 비전 중 가장 본질적인 핵심 가치 딱 1가지만 추출         |
|                     | 대안적 가설 (Alternative Hypothesis)        | 핵심 가설이 틀렸을 때 검증할 **Plan B 가설**을 미리 정의합니다.                                               | 예: "유료 전환 대신 광고 수익 모델이 더 빠르게 검증될 수 있다" — 피벗 시 방향 전환 비용 절감 |
| **2. 범위 제한**    | 필수 구현 기능 (In-Scope)                   | 가설 검증을 위해 **'이게 없으면 서비스가 성립 안 됨'** 수준의 핵심 기능입니다.                                | PRD의 기능 목록 중 80%를 과감히 버리고 최소한만 선택          |
| (가장 중요)         | 구현 제외 기능 (Out-of-Scope)               | 이번 MVP 검증 단계에서는 **절대 개발하지 않고 미룰** 기능들입니다.                                            | 예: 회원탈퇴, 비밀번호 변경, 화려한 마이페이지 등은 모두 제외 |
| **3. 수동 운영**    | 인간 자동화 계획 (Concierge / Wizard of Oz) | 복잡한 백엔드 로직이나 매칭 알고리즘을 코딩하는 대신, **내가 직접 수동으로 처리할 영역**입니다.               | 예: 알림톡 자동 발송 코딩 대신, 내가 직접 카카오톡 수동 발송  |
| **4. 검증 및 평가** | 최소 성공 기준 (Success Criteria)           | 이 실험이 성공했는지 판단할 **최소한의 정량적 기준**입니다.                                                   | 예: "랜딩 페이지 방문자 중 이메일 구독율 10% 이상"            |
|                     | 피드백 수집 채널                            | 사용자의 진짜 목소리와 불편함을 들을 창구입니다.                                                              | 구글 폼, 카카오톡 오픈프로필 링크 등 아주 간단하게 배치       |
| **5. 의사 결정**    | 피벗/지속 판단 기준 (Go / No-Go Criterion)  | MVP 출시 후 결과 데이터를 보고 **다음 단계(정식 개발)로 갈지, 아이디어를 엎을지(Pivot)** 결정하는 기준입니다. | "가설이 틀렸다면 코드를 더 짜지 않고 비즈니스 방향을 바꾼다"  |

### **💡 MVP 문서 활용법**

- **오버엔지니어링(Over-engineering) 방어막**: 혼자 장기 개발을 하다 보면 이것도 넣고 싶고 저것도 넣고 싶어서 출시가 1년 뒤로 밀리기 일쑤입니다. MVP 문서는 나 자신에게 **"지금 이 기능 안 만들어도 가설 검증할 수 있잖아?"**라고 브레이크를 걸어주는 역할을 합니다.
- **TDD와의 연결**: MVP 문서에서 정의된 `In-Scope(필수 구현 기능)`만 가지고 **TDD**를 작성해야 개발 속도가 상상을 초월하게 빨라집니다.

## **04. Decision Log (의사결정/회고) 상세 세부 항목**

MVP 실험 결과, 기술 스택 변경, 장애 대응 등 **"왜(Why) 그렇게 결정했는가?"**를 기록하는 문서입니다. TDD의 기술 선택 근거와 PRD의 방향 전환 이력을 한곳에서 추적할 수 있습니다.

| 항목 분류              | 세부 항목명 (영문명)                        | 설명                                                                                      | 1인 개발자를 위한 현실적인 작성 팁                               |
| ---------------------- | ------------------------------------------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **1. 결정 기록**       | 결정 요약 (Decision Summary)                | 무엇을, 언제, 누가(본인) 결정했는지 한 줄로 요약합니다.                                   | "2026-06-10: Next.js App Router로 전환"처럼 날짜·결론을 앞에 배치 |
|                        | 배경 및 맥락 (Context)                      | 결정이 필요했던 상황, 당시 제약(시간·예산·기술)을 기술합니다.                             | "MVP 2주차, Pages Router에서 라우팅 버그 반복" 등 구체적 상황    |
|                        | 검토한 대안 (Alternatives Considered)       | 선택하지 않은 옵션과 각각의 장단점을 나열합니다.                                          | "A: Remix — 학습 곡선 높음 / B: Next.js — 팀(본인) 숙련도 높음"  |
|                        | 최종 선택 및 이유 (Decision & Rationale)    | **최종 선택**과 **Why**를 명확히 적습니다.                                                | TDD 기술 스택 항목과 상호 링크 — 6개월 뒤 본인도 납득할 근거     |
|                        | 비용 영향도 (Cost Impact)                   | 결정에 따른 **금전·시간·기회비용** 변화(절감/증가)를 정량·정성으로 기록합니다.            | "호스팅 $20→$80/월, 개발 2주 단축" — BRD 예산·Phase Roadmap과 대조 |
| **2. 실험·피벗 기록**  | MVP 실험 결과 (Experiment Result)           | MVP(03번) 가설 검증 결과, 정량·정성 데이터를 기록합니다.                                  | "이메일 구독율 4% — 목표 10% 미달 → 피벗 검토"                   |
|                        | 피벗/지속 판단 (Go / No-Go / Pivot)         | 실험 결과에 따른 다음 행동(정식 개발·피벗·중단)과 판단 근거입니다.                        | MVP의 Go/No-Go 기준과 1:1 대응 — 감정이 아닌 데이터 기반 기록     |
| **3. 기술·아키텍처**   | 기술 스택 변경 (Tech Stack Change)          | 프레임워크, DB, 호스팅, 라이브러리 교체 시 이유와 마이그레이션 계획을 기록합니다.         | Decision Log → TDD(08번) 업데이트 순서로 연동                    |
|                        | 아키텍처 분기 (Architecture Fork)           | 모노레포 분리, 마이크로서비스 전환 등 구조적 결정을 문서화합니다.                         | 폴더 구조 변경 전·후 다이어그램을 첨부하면 회고 시 유용           |
| **4. 장애·회고**       | 장애 회고 (Incident Postmortem)             | 장애 발생 시각, 영향 범위, 근본 원인, 재발 방지 조치를 기록합니다.                        | "유저 DB 30분 다운 — 원인: 마이그레이션 미적용" 형식으로 간결히   |
|                        | 프로젝트 회고 (Retrospective)               | 스프린트·마일스톤 종료 시 잘한 점, 개선점, 다음 액션을 정리합니다.                      | 1인 개발은 분기(3개월)마다 30분 회고만 해도 충분                 |
| **5. 상태 추적**       | 결정 상태 (Status)                          | **Active(유효)**, **Superseded(대체됨)**, **Deprecated(폐기)** 중 현재 상태를 표시합니다. | 구 결정은 삭제하지 말고 Superseded로 표시 — 히스토리 보존        |
|                        | 관련 문서 링크 (Related Docs)               | 연관 BRD, PRD, TDD, MVP 문서 링크를 연결합니다.                                           | 옵시디언 `[[wikilink]]` 또는 파일 경로로 상호 참조               |

### **💡 Decision Log 활용법**

- **TDD와의 분리**: TDD는 "현재 시스템이 어떻게 동작하는가(What)"이고, Decision Log는 "왜 이렇게 설계했는가(Why)"입니다. 기술 스택 변경 시 Decision Log에 Why를 먼저 쓰고 TDD를 갱신하세요.
- **반복 실수 방지**: 6개월 전에 버렸던 기술을 다시 도입하려 할 때, 당시 기록을 열어보면 같은 시행착오를 막을 수 있습니다.

## **05. PRD (제품 요구사항 정의서) 세부 항목**

PRD는 **제품 전체의 방향성과 모든 기능**을 정의하고, MVP 문서는 **빠른 검증을 위한 핵심 기능과 실험 지표**에 집중합니다.
개발, 디자인, 마케팅 팀이 하나의 목표를 바라볼 수 있도록 상세하게 작성합니다.

| 항목 분류        | 세부 항목명                      | 설명                                                     |
| ---------------- | -------------------------------- | -------------------------------------------------------- |
| **기본 정보**    | 문서 개요 (Overview)             | 제품명, 버전, 작성자, 작성일, 최근 변경 이력 관리        |
| **배경 및 목표** | 제품 목적 (Purpose)              | 이 제품(기능)을 **왜(Why)** 만들어야 하는지 배경 기술    |
|                  | 목표 및 비전 (Goals)             | 제품이 달성하고자 하는 궁극적인 비즈니스 목표            |
| **고객 정의**    | 타겟 유저 (User Persona)         | 제품을 사용할 핵심 사용자 층 및 페르소나 정의            |
|                  | 사용자 스토리 (User Story)       | 유저 관점에서 요구하는 기능 (예: "~로서 ~를 하고 싶다")  |
| **요구사항**     | 기능 요구사항 (Functional)       | 제품이 반드시 수행해야 하는 기능 목록 및 상세 설명       |
|                  | 비기능 요구사항 (Non-functional) | 보안, 성능 속도, 지원 환경(OS, 브라우저) 등 기술 스펙    |
|                  | 예외 케이스 (Exception Case)     | 네트워크 오류, 잘못된 입력 등 예외 상황 시 대응 플로우   |
|                  | 데이터 요구사항 요약 (Data Requirements) | 기능 구현에 필요한 **입력·출력·저장 데이터**의 종류, 출처, 보관 기간을 요약합니다. TDD DB 스키마(08번)·UI/UX 데이터 매핑(07번) 작성 전 1차 정리용 — 필드명은 여기서 확정하지 않아도 됨 |
| **제약 및 일정** | 마일스톤 (Milestone)             | 디자인, 개발, QA, 배포 등 타임라인 및 마감일             |
|                  | 제약 사항 (Constraints)          | 예산, 인력, 법적 규제 등 개발 시 고려해야 할 제한 요소   |
| **성공 지표**    | 핵심 성과 지표 (KPI)             | 제품 출시 후 성공 여부를 판단할 데이터 지표 (예: 리텐션) |

## **06. Analytics Spec (데이터 분석) 상세 세부 항목**

PRD의 성공 지표(KPI)를 **"어떤 버튼 클릭 시 어떤 값을 보내는가"** 수준으로 기술하는 문서입니다. 개발자가 이벤트 로그를 정확히 심고, 마케팅·사업 담당자가 동일한 지표 정의를 공유할 수 있습니다.

| 항목 분류                | 세부 항목명 (영문명)                      | 설명                                                                                    | 1인 개발자를 위한 현실적인 작성 팁                                    |
| ------------------------ | ----------------------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| **1. 분석 목표**         | KPI 매핑 (KPI Mapping)                    | PRD·BRD의 비즈니스 지표를 측정 가능한 이벤트·속성으로 변환합니다.                     | "유료 전환율" → `subscription_completed` 이벤트 1개로 시작          |
|                          | 측정 도구 (Analytics Stack)               | GA4, Mixpanel, Amplitude, PostHog 등 사용할 분석 도구와 계정·프로젝트 ID를 명시합니다.  | MVP 단계는 GA4 무료 + 1개 커스텀 이벤트만으로도 충분                |
| **2. 이벤트 명세**       | 이벤트 이름 (Event Name)                  | 스네이크 케이스 등 팀 규칙에 맞는 이벤트 식별자를 정의합니다.                           | 예: `signup_completed`, `payment_failed` — PRD 기능명과 대응          |
|                          | 트리거 조건 (Trigger Condition)           | 이벤트가 **언제** 발화되는지(버튼 클릭, API 성공, 페이지 뷰 등)를 정의합니다.           | "결제 API 200 응답 후"처럼 개발자가 코드에 바로 옮길 수 있게 작성     |
|                          | 이벤트 속성 (Event Properties)            | 이벤트와 함께 전송할 key-value(플랜 종류, 금액, 오류 코드 등)를 정의합니다.           | PII(이메일 전체)는 보내지 말고 `user_id` 해시 또는 익명 ID 사용     |
| **3. 유저·세션**         | 유저 식별 (User Identification)           | 로그인 전·후 유저 ID 연결 방식, 익명 ID와 회원 ID 병합 규칙을 정의합니다.               | Legal(02번) 개인정보 처리방침과 수집 범위 일치 필수                   |
|                          | 세션·페이지뷰 (Session / Pageview)        | SPA 라우팅 시 페이지뷰 정의, 세션 타임아웃 등 기본 추적 규칙을 명시합니다.            | Next.js App Router는 `pathname` 변경 시 수동 page_view 호출 여부 결정 |
| **4. 퍼널·대시보드**     | 전환 퍼널 (Conversion Funnel)             | 가입 → 온보딩 → 결제 등 단계별 이벤트 순서와 이탈 지점을 정의합니다.                   | MVP 성공 기준(03번)과 동일한 퍼널 1개만 먼저 설계                    |
|                          | 대시보드·리포트 (Dashboard Spec)          | 주간·월간 확인할 차트, 세그먼트(신규/복귀 유저)를 정의합니다.                         | 1인 개발은 GA4 기본 리포트 3개(유입·전환·이탈)로 시작                 |
| **5. 품질·거버넌스**     | 이벤트 네이밍 규칙 (Naming Convention)    | 신규 이벤트 추가 시 따를 prefix·버전 규칙을 정의합니다.                                 | `06_Analytics_유저행동추적_v1.0.md` — PRD 버전과 연동                 |
|                          | QA·검증 (Analytics QA)                    | 이벤트가 의도대로 수집되는지 확인하는 체크리스트(디버그 뷰, 샘플 로그)를 포함합니다.  | QA Test Case(10번)에 "이벤트 발화 확인" 시나리오 1~2개 추가           |
|                          | 데이터 보존·삭제 (Retention & Deletion)   | 로그 보관 기간, 회원 탈퇴 시 분석 데이터 삭제·익명화 정책을 명시합니다.                 | Legal(02번) 개인정보 파기 정책과 동일하게 유지                        |
|                          | 데이터 소유자 및 검증 주기 (Owner & Audit Cycle) | 각 KPI·이벤트의 **담당자(Owner)**와 정기 검증 주기(주간/월간)를 정의합니다.          | 1인 개발은 본인이 Owner, 검증은 "배포 후 1주일 내 GA4 디버그 뷰 확인"으로 단순화 |

### **💡 Analytics Spec 작성 가이드**

- **PRD와의 연결**: PRD "핵심 성과 지표(KPI)" 표의 각 행마다 최소 1개 이벤트 또는 속성을 매핑하세요. KPI만 있고 이벤트가 없으면 출시 후 "숫자를 못 본다"는 상황이 반복됩니다.
- **개발 우선순위**: MVP In-Scope 기능에 해당하는 이벤트만 먼저 구현하고, 나머지는 v1.1 Analytics Spec으로 미룹니다.

## **07. UI/UX Spec (디자인 명세서) 상세 세부 항목**

기획(PRD)과 개발(TDD) 사이를 유기적으로 연결해 주는 **UI/UX Spec (디자인 명세서/화면 설계서) 로서** 눈에 보이는 화면의 형태뿐만 아니라 **"유저가 버튼을 눌렀을 때 화면이 어떻게 반응하고 이동하는가?"**라는 시각적 기능과 흐름을 정의하는 문서입니다. 1인 개발 시에는 **피그마(Figma) 파일 안에 페이지를 나누거나 캔버스 내부에 텍스트로 적어두는 방식**으로 관리하면 가장 효율적입니다.

| 항목 분류                  | 세부 항목명 (영문명)                       | 설명                                                                                     | 혼자 개발할 때의 핵심 팁 (Figma 활용)                                                                        |
| -------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **1. 디자인 시스템**       | 글로벌 스타일 (Global Styles)              | 서비스 전체에 공통으로 사용할 컬러(Palette)와 타이포그래피(Font) 규칙입니다.             | 피그마의 **Variables(변수)**나 **Local Styles**로 등록하여 코드의 Tailwind/CSS 변수와 일치시킵니다.          |
|                            | UI 컴포넌트 라이브러리 (Component Library) | 버튼, 입력창(Input), 모달(Modal), 카드 등 반복 사용되는 UI 요소의 집합입니다.            | 피그마 **Component(기포넌트)** 기능을 활용해 `Default`, `Hover`, `Focus`, `Disabled` 상태를 미리 만듭니다.   |
| **2. 사용자 흐름**         | 와이어프레임 (Wireframe)                   | 시각적 디자인 요소(색상, 이미지)를 배제하고 화면의 레이아웃과 정보 배치만 설계합니다.    | 펜으로 종이에 그리거나 피그마 플러그인을 활용해 빠르게 구조만 잡습니다.                                      |
|                            | 유저 플로우 (User Flow / IA)               | 사용자가 목표를 달성하기 위해 이동하는 화면 간의 전체적인 경로(지도)입니다.              | 피그마 캔버스 위에 각 화면을 배치하고 화살표(Connector)로 연결해 정보 구조(IA)를 한눈에 봅니다.              |
| **3. 화면별 상세 명세**    | 인터랙션 명세 (Interaction Spec)           | 특정 버튼이나 영역을 클릭/스크롤/스와이프했을 때 일어나는 애니메이션과 반응입니다.       | 피그마의 **Prototype** 기능을 연결해 앱의 실제 구동 느낌을 미리 테스트해 봅니다.                             |
| (가장 중요)                | 콘텐츠 & 데이터 매핑 (Data Mapping)        | 화면의 각 요소에 어떤 실제 데이터(텍스트, 이미지)가 노출되어야 하는지 정의합니다.        | "여기는 DB의 `user.profile_img`가 들어가고, 비어있으면 기본 아바타 노출"과 같은 규칙을 화면 옆에 메모합니다. |
| **4. 예외 및 반응형 처리** | 상태별 UI 명세 (State Spec)                | 로딩 중(Loading), 데이터 없음(Empty), 에러(Error) 발생 시 유저에게 보일 화면입니다.      | 개발할 때 가장 빼먹기 쉬운 부분입니다. 빈 화면과 로딩 스피너 디자인을 반드시 미리 정의합니다.                |
|                            | 반응형/디바이스 대응 (Responsive Design)   | 데스크톱, 태블릿, 모바일 등 화면 크기 변화에 따라 레이아웃이 어떻게 변하는지 정의합니다. | 피그마의 **Auto Layout** 기능을 적극 활용하여 창 크기가 줄어들 때의 정렬 규칙을 세웁니다.                    |

### **💡 UI/UX Spec 실무 적용 가이드**

- **기획(PRD)과의 연결**: PRD에 적힌 사용자 스토리(예: "유저는 비밀번호 찾기를 할 수 있다") 마다 대응하는 피그마 화면 프레임을 만드세요.
- **개발(TDD)과의 연결**: 피그마 컴포넌트의 이름(예: `Button/Primary/Large`)을 나중에 작성할 React 컴포넌트 파일명이나 Props 구조와 똑같이 맞추면 TDD를 쓸 때나 코딩할 때 뇌 손실을 엄청나게 줄일 수 있습니다.

## **08. TDD (Technical Design Document) 기술 설계 문서**

| 항목 분류 [1]                | 세부 항목명 (영문명)                     | 설명                                                                             | 핵심 포함 내용 예시                                       |

|                              | 시스템 요구사항 (Requirements)           | 개발 관점에서 만족해야 하는 성능 및 기술적 목표를 정의합니다.                    | "첫 페이지 로딩 1.5초 이내", "SSR 필수 적용" 등           |
| **2. 아키텍처 및 기술 스택** | 시스템 아키텍처 (System Architecture)    | 인프라, 백엔드, 프런트엔드의 전체적인 구조와 연결 방식을 정의합니다.             | 인프라 구조도, 클라이언트-서버 구조도                     |
|                              | 기술 스택 및 라이브러리 (Tech Stack)     | 사용할 언어, 프레임워크, 주요 라이브러리와 **선택 이유**를 명시합니다.           | Next.js, Tailwind CSS, Zod, Zustand 등을 고른 이유        |
|                              | 디렉토리/파일 구조 (Directory Structure) | 프로젝트의 폴더 구조와 컴포넌트 배치 규칙을 사전에 정의합니다.                   | `src/features`, `src/components` 등 디렉토리 트리         |

|                              | 데이터 유효성 검증 (Zod Schema)          | 클라이언트와 서버 사이에서 교환되는 데이터의 무결성 검증 규칙입니다.             | `userSchema = z.object({ email: z.string().email() })`    |
|                              | 상태 관리 전략 (State Management)        | 전역 상태(Global), 지역 상태(Local), 서버 상태(Server)의 관리 주체를 정의합니다. | Zustand 클라이언트 상태, TanStack Query 서버 캐싱 분리    |
| **4. 데이터 흐름 & 로직**    | 데이터 흐름도 (Data Flow Diagram)        | 유저의 행동(Input)부터 DB 저장(Output)까지 데이터가 거쳐 가는 경로입니다.        | Client Form ➔ API Route (Zod 검증) ➔ DB 저장 흐름         |
|                              | 핵심 비즈니스 로직 (Core Logic)          | 알고리즘, 가중치 계산, 복잡한 비즈니스 규칙의 구현 방법을 기술합니다.            | 장바구니 할인율 계산 공식, 포인트 차감 순서 규칙          |

|                              | 데이터 보호 (Data Protection)            | 전송(TLS), 저장(암호화), PII 마스킹, API Rate Limit 등 민감 데이터 처리 규칙입니다. | Legal(02번) 개인정보 항목과 수집·보관 범위 1:1 대응         |

### **💡 TDD 작성 팁**

1. **"왜(Why)"를 꼭 적으세요:** 기술 스택이나 폴더 구조를 적을 때, 6개월 뒤의 내가 다시 봐도 납득할 수 있도록 **"A 라이브러리 대신 B를 선택한 이유"**를 한 줄이라도 적어두어야 나중에 흔들리지 않습니다.
2. **처음부터 다 채우지 마세요:** 장기 프로젝트라면 1번(개요)부터 6번(타스크)까지 틀만 만들어 둔 뒤, **당장 개발할 MVP 기능 분량만큼만 2~5번의 세부 내용을 채우고 개발에 착수**하는 것이 지치지 않는 비결입니다.

## **10. QA Test Case (테스트 케이스) 상세 세부 항목**

| 항목 분류 [1, 2]        | 세부 항목명 (영문명)           | 설명                                                                     | 1인 개발자의 현실적인 관리 팁                                                  |
| ----------------------- | ------------------------------ | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| **1. 기본 정보**        | ID / 모듈명 (Test ID / Module) | 테스트 케이스의 고유 번호와 해당 기능이 속한 대분류입니다.               | 예: `AUTH-001` (회원가입), `PAY-003` (결제 취소)                               |
|                         | 테스트 목적 (Description)      | 해당 케이스가 **'무엇을 검증하기 위한 시험인가'** 정의합니다.            | 예: "비밀번호 자릿수 미달 시 가입 차단 검증"                                   |
|                         | 회귀 테스트 대상 여부 (Regression Flag) | 배포·핫픽스 후 **반복 실행해야 하는 핵심 시나리오**인지 표시합니다.       | **Y**: 결제·로그인·핵심 퍼널 / **N**: 1회성 신기능 — 릴리스마다 Y만 돌리면 충분 |
| **2. 사전 조건 & 환경** | 사전 조건 (Pre-requisites)     | 테스트를 진행하기 위해 **시스템이 미리 갖춰야 할 상태**입니다.           | 예: "이미 로그아웃된 상태여야 함", "장바구니에 상품이 있어야 함"               |
|                         | 테스트 환경 (Environment)      | 테스트를 진행한 기기, 브라우저, 운영체제 정보입니다.                     | 혼자 할 때는 `Chrome(데스크톱)`, `Safari(iOS)` 정도로 축소 가능                |
| **3. 테스트 시나리오**  | 테스트 절차 (Test Steps)       | 유저가 실제로 행동하는 순서를 **1, 2, 3 단계**로 상세히 적습니다.        | 예: 1. 회원가입 페이지 접속 2. 이메일 입력 3. 비밀번호 4자리 입력 후 제출 클릭 |
| (가장 중요)             | 예상 결과 (Expected Result)    | 기획(PRD)과 디자인에 정의된 **정상적인 시스템의 반응**입니다.            | 예: "‘비밀번호는 8자 이상이어야 합니다’라는 에러 메시지가 출력된다."           |
| **4. 결과 기록**        | 실제 결과 (Actual Result)      | 테스트를 직접 수행했을 때 화면에 나타난 실제 현상입니다.                 | 정상 작동 시 "예상 결과와 동일", 버그 발생 시 현상 기술                        |
|                         | 통과 여부 (Status)             | 최종 검증 결과 상태를 표시합니다.                                        | **Pass(통과)**, **Fail(실패)**, **Block(진행 불가)**                           |
| **5. 버그 추적**        | 결함 링크 (Defect / Bug Link)  | 테스트가 Fail 되었을 때, 고쳐야 할 버그 내용(코드 위치 등)을 연결합니다. | 1인 개발 시에는 해당 행에 바로 코멘트나 Todo 태스크 연결                       |

### **💡 QA Test Case 작성 노하우 (Happy vs Sad)**

테스트 케이스를 작성할 때는 머릿속으로 두 가지만 기억하고 항목을 쪼개면 됩니다.

1. **해피 패스 (Happy Path - 정상 케이스)**
   - 유저가 기획자가 의도한 대로 올바르게 값을 입력하고 스무스하게 성공하는 경로 (예: 양식에 맞게 다 쓰고 가입 성공)
2. **새드 패스 (Sad Path - 예외/실패 케이스)**
   - 유저가 잘못된 값을 넣거나 시스템 오류가 나는 경로 (예: 중복 이메일 입력, 글자수 미달, 결제 중 네트워크 끊김 등)

**특히 '새드 패스'를 잘 적어두어야 나중에 앱이 커졌을 때 예기치 못한 크래시(Crash)나 보안 구멍을 막을 수 있습니다.** Zod 스키마로 1차 검증한 에러 메시지가 화면에 예쁘게 잘 뜨는지 확인하는 용도로 이 QA 시나리오를 활용하시면 됩니다.

## 옵시디언 중심의 관리 툴

옵시디언에서 **Frontmatter(YAML)**를 데이터베이스처럼 활용할 때, 모든 내용을 일일이 수기할 필요는 없습니다. 옵시디언의 생태계를 활용하면 **반자동**에서 **완전자동**까지 수준별로 관리가 가능합니다.

우리가 앞서 정의한 **BRD, MVP, PRD 등 11대 문서 체계**를 옵시디언에서 어떻게 자동화하여 관리할 수 있는지 그 방법을 정리해 드립니다.

### **1. 반자동 방식: 템플릿(Templates) 활용**

옵시디언의 기본 기능인 **'Templates'**나 커뮤니티 플러그인인 **'Templater'**를 사용하는 방식입니다.

- **작동 방식**: 새 문서를 만들 때 미리 정의된 서식을 불러옵니다.
- **자동화 요소**: 문서 생성 시점의 **날짜(Date)**, **제목(Title)** 등을 자동으로 입력해 줍니다.
- **예시**: `05_PRD` 템플릿을 실행하면 문서 최상단에 아래 내용이 자동으로 생성됩니다.
  ```yaml
  ---
  category: "05_PRD"
  created: 2026-06-10
  version: 1.0
  status: "Draft"
  ---
  ```
  이후 `status`나 `version` 같은 가변적인 정보만 필요할 때 수정하면 됩니다.

### **2. UI 기반 관리: 프로퍼티(Properties) 기능**

최신 옵시디언 버전에는 YAML을 텍스트로 치지 않고 메뉴 버튼처럼 관리할 수 있는 **'Properties'** 기능이 내장되어 있습니다.

- **작동 방식**: 소스 코드(---)를 직접 건드리지 않고, 화면 상단에 나타나는 입력창에서 값을 선택합니다.
- **자동화 요소**: 'Category' 항목을 **'목록(List)'** 타입으로 설정해두면, 미리 입력해둔 11개 카테고리(01_BRD, 02_Legal 등) 중 하나를 클릭만으로 선택할 수 있습니다.

### **3. 완전자동 방식: 플러그인 조합**

고급 플러그인을 사용하면 문서 생성부터 분류까지 완전히 자동화할 수 있습니다.

- **QuickAdd**: 버튼 하나로 "새 PRD 만들기"를 실행하면, 자동으로 날짜를 채우고, 폴더를 지정된 곳(`05_Planning_PRD`)에 생성하며 YAML 값까지 세팅해 줍니다.
- **Metadata Menu**: 특정 폴더에 있는 문서들의 YAML 속성값을 관리자 화면처럼 한눈에 보고 일괄 수정할 수 있게 해줍니다. 예를 들어 여러 PRD의 상태를 한꺼번에 'Published'로 바꿀 때 유용합니다.
- **Linter**: 문서를 저장할 때마다 설정된 규칙에 따라 날짜 정보를 최신화하거나, 누락된 YAML 필드를 자동으로 추가해 줍니다.

---

### **💡 우리 체계에 적용하는 팁**

별도의 앱과 DB를 구축하기 전 단계라면, 옵시디언에서 다음과 같이 가이드를 잡는 것이 가장 효율적입니다.

1.  **입력은 반자동**: `Templater`를 통해 문서 종류별(BRD, TDD 등)로 기본 YAML 구조를 만듭니다.
2.  **관리는 데이터 뷰(Dataview)**: `Dataview` 플러그인을 설치하면, 수기로 적은 YAML 데이터를 모아 자동으로 **표(Table)**를 만들어 줍니다. 이를 통해 별도의 앱 없이도 "현재 진행 중인 프로젝트 리스트"나 "최근 수정된 기술 설계서" 목록을 볼 수 있습니다.
3.  **파일명 간소화**: YAML에 `category: 05_PRD`가 들어가 있다면, 실제 파일명은 날짜를 빼고 `결제_프로세스.md`라고만 지어도 검색과 정렬에 전혀 문제가 없습니다.

**참고**: 위에서 언급한 플러그인(Templater, QuickAdd, Metadata Menu, Dataview) 정보는 옵시디언 커뮤니티의 일반적인 활용 사례로, 제공된 소스 문서에는 포함되어 있지 않으므로 별도의 확인이 필요할 수 있습니다. 하지만 소스에서 강조하는 **'11대 문서 생태계'의 체계적인 관리**를 구현하는 데 가장 최적화된 도구들입니다.

---

### **💡 옵시디언 활용을 위한 최종 조언**

1. **결정의 근거 연결**: **TDD(08)**의 기술 스택·보안 설계 항목 옆에는 항상 해당 결정을 내린 **Decision Log(04)** 문서 링크를 YAML `related_decision` 또는 `[[wikilink]]`로 연결합니다.
2. **실패에서 배움 연결**: **QA(10)**에서 자주 발생하는 **'새드 패스'** 케이스는 `faq_candidate: true` 같은 Properties 플래그로 표시하고, 정기적으로 **User Guide(11)**의 **FAQ** 섹션 후보군으로 검토·이관하는 프로세스를 둡니다.
3. **파일명 간소화 유지**: 앞서 논의한 대로 **Prefix(01~11)**만 파일명에 유지하고, 버전·날짜·상태·링크 등 상세 정보는 **Properties(YAML)**에 맡겨 탐색기 가독성을 높입니다.
