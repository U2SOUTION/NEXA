# SW 개발 문서 생태계 와 관리 체계

## **[확장판] 소프트웨어 개발 문서 관리 체계 (11 대 분류)**

| 폴더 번호 | 문서명 (영문)                    | 핵심 목적 (Objective)                   | 주요 포함 항목                                                  | 관련 소스 및 근거                       |
| :-------- | :------------------------------- | :-------------------------------------- | :-------------------------------------------------------------- | :-------------------------------------- |
| **01**    | **BRD** (사업 전략)              | 비즈니스 가치와 수익 모델 정의          | 비전, 타겟 시장, **수익 모델 (BM)**, 비용 및 예산                | 프로젝트의 최상위 나침반                |
| **02**    | **Legal & Policy** (법무/정책)   | 법적 규제 준수 및 서비스 이용 약관 관리 | **개인정보 처리방침**, 이용약관, PG 사 연동 조건                 | BRD 의 리스크 항목에서 독립 분리         |
| **03**    | **MVP Plan** (실험 계획)         | 가설 검증을 위한 최소 기능 정의         | 핵심 가설, **필수 구현 (In-Scope)**, **구현 제외 (Out-of-Scope)** | 오버엔지니어링 방지 및 빠른 검증        |
| **04**    | **Decision Log** (의사결정/회고) | 프로젝트 주요 분기점 및 실험 결과 기록  | 피벗 판단 기준, **기술 선택 이유 (Why)**, 장애 회고 기록         | MVP 실험 결과 및 TDD 의 결정 근거 기록   |
| **05**    | **PRD** (기획서)                 | 제품의 구체적인 동작 규칙 정의          | 유저 스토리, **기능/비기능 요구사항**, **예외 케이스**          | 개발/디자인/QA 의 공통 설계도            |
| **06**    | **Analytics Spec** (데이터 분석) | 비즈니스 지표 측정을 위한 추적 설계     | 이벤트 태그 (GA4/Mixpanel) 명세, 트리거 조건, 속성값             | PRD 의 성공 지표 (KPI) 를 기술적으로 구현  |
| **07**    | **UI/UX Spec** (디자인)          | 화면 설계 및 인터랙션 정의              | 디자인 시스템, **유저 플로우**, **데이터 매핑**                 | 기획과 개발 사이의 시각적 연결          |
| **08**    | **TDD** (기술 설계)              | 시스템 아키텍처 및 데이터 흐름 설계     | **DB 스키마**, **API 명세**, 시스템 아키텍처                    | 코드 구현 전 기술적 무결성 확보         |
| **09**    | **Admin & Ops** (운영 매뉴얼)    | 내부 관리자용 시스템 조작 및 운영 지침  | 어드민 페이지 사용법, **CS 처리 절차**, 수동 DB 조작 가이드     | TDD 의 배포/운영 환경 항목에서 독립 분리 |
| **10**    | **QA Test Case** (검증)          | 출시 전 기능 및 보안 결함 확인          | **해피 패스 (정상)**, **새드 패스 (예외)**, 버그 추적 리포트      | 예기치 못한 크래시 및 보안 구멍 방지    |
| **11**    | **User Guide** (공개 문서)       | 최종 사용자를 위한 제품 설명 및 지원    | 가입 가이드, **자주 묻는 질문 (FAQ)**, **업데이트 이력**         | CS 답변 시간 단축 및 유저 신뢰 구축     |

### **정확한 분류를 위한 가이드라인**

1. **리스크 관리의 분리 (02 번)**: 기존에는 BRD 의 일부였으나, 개인정보 보호법이나 이용약관은 출시 직전에 매우 중요해지므로 별도 폴더로 관리하여 법적 분쟁을 예방해야 합니다.
2. **데이터 분석의 독립 (06 번)**: 단순히 " 성공 지표를 보겠다 " 는 계획 (PRD) 과 " 어떤 버튼 클릭 시 어떤 값을 보낸다 " 는 분석 명세는 다릅니다. 이를 분리해야 개발자가 정확한 이벤트 로그를 심을 수 있습니다.
3. **운영 지침의 체계화 (09 번)**: TDD 가 개발을 위한 것이라면, 운영 매뉴얼은 출시 후 관리를 위한 것입니다. 특히 1 인 개발 시 나중에 " 이 데이터를 어떻게 수정했었지?" 라며 헤매는 시간을 줄여줍니다.
4. **히스토리의 기록 (04 번)**: MVP 실험이 실패했거나 기술 스택을 변경했을 때, 그 **' 이유 (Why)'**를 별도로 기록해두면 나중에 똑같은 시행착오를 반복하는 것을 막을 수 있습니다.

### **💡 절충안의 핵심 규칙 (Naming Convention)**

1. **Prefix (분류 번호) 필수**: `01_` 부터 `11_` 까지 번호를 맨 앞에 붙입니다. 이는 다른 에디터 탐색기에서도 **사업 → 기획 → 개발 → 검증** 순으로 문서가 정렬되도록 강제하여 " 개발 11 대 문서 생태계 " 의 흐름을 지켜줍니다.
2. **Middle (직관적 이름)**: 한글이나 영문으로 문서 내용을 명확히 적습니다. (예: `결제프로세스`, `시스템아키텍처`)
3. **Suffix (버전 vs 날짜)**:
    - **버전 (`v1.0`)**: 문서의 **완성도와 상태**가 중요할 때 사용합니다. 특히 디자인이나 기획서처럼 개발자가 참고해야 할 ' 최종본 ' 개념이 강한 문서에 적합합니다.
    - **날짜 (`240610`)**: 문서의 **발생 시점과 히스토리**가 중요할 때 사용합니다. 실험 결과나 결정 기록처럼 " 그때 왜 그랬는지 " 에 대한 맥락이 필요한 문서에 적합합니다.
4. **아카이브 활용**: 만약 탐색기가 너무 지저분해지면, 구버전 파일들은 폴더 내에 `_Archive` 폴더를 만들어 옮기고, 최상위에는 항상 **최신 버전 하나**만 남겨두는 것이 오버엔지니어링을 방지하는 좋은 방법입니다.

이 절충안을 사용하면 옵시디언 외부의 탐색기에서도 **논리적인 순서**로 정렬되면서도, 파일명만 보고도 해당 문서가 **어떤 단계의 어떤 정보**인지 즉시 파악할 수 있습니다.

## **🏢 BRD vs 📱 PRD 한눈에 비교하기**

| 구분 [1, 2]    | BRD (Business) - 사업관점                            | PRD (Product) - 제품 기능관점                           |
| -------------- | ---------------------------------------------------- | ------------------------------------------------------- |
| **쉽게 말해?** | **" 이 사업으로 어떻게 돈 벌 것인가?"**               | **" 유저에게 어떤 기능을 제공할 것인가?"**               |
| **핵심 질문**  | **Why & Who** (왜 만들고, 누가 돈을 내는가)          | **What & How** (무엇을 만들고, 유저는 어떻게 쓰는가)    |
| **주요 독자**  | 투자자, 경영진, 사업 담당자 (비즈니스 조직)          | 개발자, 디자이너, QA 엔지니어 (제품 메이커)             |
| **핵심 내용**  | 시장 분석, 경쟁사 요금제, 수익 모델, 예산, 매출 목표 | 유저 시나리오, 기능 리스트, 예외 처리 규칙, 데이터 매핑 |

## **01. BRD (비즈니스 요구사항 정의서) 상세 세부 항목**

장기 프로젝트의 최상위 나침반이자, PRD 의 부모 문서가 되는 **BRD(Business Requirements Document, 비즈니스 요구사항 정의서)**의 세부 항목을 테이블로 정리해 드립니다.

BRD 는 기술이나 화면 기능이 아니라, **" 이 프로젝트가 왜 사업적으로 가치가 있는가? 어떻게 돈을 벌고 시장에서 살아남을 것인가?"**를 정의하는 비즈니스 전략서입니다. 1 인 개발이라도 이 문서가 단단해야 개발 도중 흔들리지 않고 ' 수익을 내는 제품 ' 을 만들 수 있습니다.

| 항목 분류 [2, 3]          | 세부 항목명 (영문명)                      | 설명                                                                       | 1 인 개발자를 위한 현실적인 작성 팁                                  |
| ------------------------- | ----------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| **1. 프로젝트 개요**      | 비즈니스 배경 (Background)                | 이 프로젝트를 시작하게 된 시장의 기회나 문제 상황을 기술합니다.            | " 기존 앱들은 A 기능이 비싸서 유저들이 불편해함 " 등 시장의 틈새 기술 |
|                           | 비전 및 목표 (Vision & Goals)             | 이 서비스가 궁극적으로 도달하고자 하는 최종 모습을 정의합니다.             | 예: " 출시 6 개월 내 틈새시장 점유율 10% 달성 "                        |
| **2. 시장 및 타겟 분석**  | 타겟 시장 (Target Market / TAM)           | 제품이 진입할 실제 시장의 규모와 특성을 정의합니다.                        | 전체 시장 크기보다 내가 당장 침투 가능한 유저 규모 분석             |
|                           | 경쟁사 분석 (Competitor Analysis)         | 직접적/간접적 경쟁 서비스들의 장단점과 요금을 분석합니다.                  | 경쟁사 대비 **내 서비스만의 확실한 차별점 (USP)** 1 가지 명시         |
| **3. 비즈니스 모델**      | 수익 모델 (Monetization / BM)             | 이 서비스를 통해 **어떻게 돈을 벌 것인지** 구조를 정의합니다.              | 구독형 (SaaS), 광고, 건당 수수료, 인앱 결제 등 구체적 설정           |
|                           | 비용 및 예산 (Cost & Budget)              | 개발 및 운영 (서버비, 외부 API 비용, 마케팅비) 에 가용 가능한 예산입니다.    | 혼자 개발 시 시간 (기회비용) 과 월 고정 인프라 비용 한도 설정         |
| **4. 핵심 비즈니스 요구** | 킬러 기능 정의 (Core Capabilities)        | 비즈니스 목표 달성을 위해 **제품이 반드시 해결해야 하는 핵심 가치**입니다. | PRD 의 요구사항으로 이어지는 가장 중요한 비즈니스 규칙               |
|                           | 사용자 범위 (User Scope)                  | 시스템을 이용할 비즈니스 주체들을 정의합니다.                              | 예: 일반 사용자, 판매자, 시스템 관리자 등 권한 그룹 분리            |
| **5. 성공 지표 & 리스크** | 비즈니스 성공 지표 (Business Metrics)     | 서비스가 사업적으로 성공했는지 평가할 재무적/수치적 지표입니다.            | 매출액, 유료 전환율, 월간 활성 사용자 수 (MAU) 등                    |
|                           | 제약 사항 및 리스크 (Risks & Constraints) | 법적 규제, 저작권, 기술적 한계 등 사업적 위험 요소를 파악합니다.           | 예: 전자상거래법 준수 여부, 개인정보 보호법 (PG 사 연동 조건) 등      |
| **6. 실행 로드맵**        | 단계별 로드맵 (Phase Roadmap)             | MVP → 정식 출시 → 확장 등 **사업 단계 (Phase)**별 목표, 기간, 핵심 산출물을 정의합니다. | Phase 1(MVP 검증 4 주) → Phase 2(유료화) → Phase 3(기능 확장) 처럼 3 단계만 먼저 작성 |
|                           | 단계별 성공 기준 (Phase Exit Criteria)    | 각 Phase 를 종료하고 다음 단계로 넘어가기 위한 **최소 달성 조건**을 명시합니다. | MVP Phase 는 03 번 문서의 Go/No-Go 기준과 동일하게 유지 — BRD·MVP 중복 방지 |

### **💡 BRD 작성 가이드**

- **PRD 와의 명확한 차이**:
  - **BRD**: " 결제 대행사 (PG) 를 붙여서 월 9,900 원의 **구독 모델로 수익을 창출**한다." (비즈니스 요구)
  - **PRD**: " 마이페이지에 ' 구독하기 ' 버튼이 있고, 클릭 시 Toss Payments 모달이 열리며 결제 성공 시 DB 의 멤버십 등급이 업데이트된다." (기능 요구)

## **03. MVP (최소 기능 제품 검증 계획서) 상세 세부 항목**

| 항목 분류 [2, 3, 4] | 세부 항목명 (영문명)                        | 설명                                                                                                          | 1 인 개발자를 위한 현실적인 작성 팁                            |
| ------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| **1. 가설 정의**    | 핵심 비즈니스 가설 (Core Hypothesis)        | " 사용자들은 **[문제]**를 겪고 있으며, **[핵심 기능]**을 주면 **[행동]**할 것이다 " 를 정의합니다.               | BRD 의 비전 중 가장 본질적인 핵심 가치 딱 1 가지만 추출         |
|                     | 대안적 가설 (Alternative Hypothesis)        | 핵심 가설이 틀렸을 때 검증할 **Plan B 가설**을 미리 정의합니다.                                               | 예: " 유료 전환 대신 광고 수익 모델이 더 빠르게 검증될 수 있다 " — 피벗 시 방향 전환 비용 절감 |
| **2. 범위 제한**    | 필수 구현 기능 (In-Scope)                   | 가설 검증을 위해 **' 이게 없으면 서비스가 성립 안 됨 '** 수준의 핵심 기능입니다.                                | PRD 의 기능 목록 중 80% 를 과감히 버리고 최소한만 선택          |
| (가장 중요)         | 구현 제외 기능 (Out-of-Scope)               | 이번 MVP 검증 단계에서는 **절대 개발하지 않고 미룰** 기능들입니다.                                            | 예: 회원탈퇴, 비밀번호 변경, 화려한 마이페이지 등은 모두 제외 |
| **3. 수동 운영**    | 인간 자동화 계획 (Concierge / Wizard of Oz) | 복잡한 백엔드 로직이나 매칭 알고리즘을 코딩하는 대신, **내가 직접 수동으로 처리할 영역**입니다.               | 예: 알림톡 자동 발송 코딩 대신, 내가 직접 카카오톡 수동 발송  |
| **4. 검증 및 평가** | 최소 성공 기준 (Success Criteria)           | 이 실험이 성공했는지 판단할 **최소한의 정량적 기준**입니다.                                                   | 예: " 랜딩 페이지 방문자 중 이메일 구독율 10% 이상 "            |
|                     | 피드백 수집 채널                            | 사용자의 진짜 목소리와 불편함을 들을 창구입니다.                                                              | 구글 폼, 카카오톡 오픈프로필 링크 등 아주 간단하게 배치       |
| **5. 의사 결정**    | 피벗/지속 판단 기준 (Go / No-Go Criterion)  | MVP 출시 후 결과 데이터를 보고 **다음 단계 (정식 개발) 로 갈지, 아이디어를 엎을지 (Pivot)** 결정하는 기준입니다. | " 가설이 틀렸다면 코드를 더 짜지 않고 비즈니스 방향을 바꾼다 "  |

### **💡 MVP 문서 활용법**

- **오버엔지니어링 (Over-engineering) 방어막**: 혼자 장기 개발을 하다 보면 이것도 넣고 싶고 저것도 넣고 싶어서 출시가 1 년 뒤로 밀리기 일쑤입니다. MVP 문서는 나 자신에게 **" 지금 이 기능 안 만들어도 가설 검증할 수 있잖아?"**라고 브레이크를 걸어주는 역할을 합니다.
- **TDD 와의 연결**: MVP 문서에서 정의된 `In-Scope(필수 구현 기능)` 만 가지고 **TDD**를 작성해야 개발 속도가 상상을 초월하게 빨라집니다.

## **04. Decision Log (의사결정/회고) 상세 세부 항목**

MVP 실험 결과, 기술 스택 변경, 장애 대응 등 **" 왜 (Why) 그렇게 결정했는가?"**를 기록하는 문서입니다. TDD 의 기술 선택 근거와 PRD 의 방향 전환 이력을 한곳에서 추적할 수 있습니다.

| 항목 분류              | 세부 항목명 (영문명)                        | 설명                                                                                      | 1 인 개발자를 위한 현실적인 작성 팁                               |
| ---------------------- | ------------------------------------------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| **1. 결정 기록**       | 결정 요약 (Decision Summary)                | 무엇을, 언제, 누가 (본인) 결정했는지 한 줄로 요약합니다.                                   | "2026-06-10: Next.js App Router 로 전환 " 처럼 날짜·결론을 앞에 배치 |
|                        | 배경 및 맥락 (Context)                      | 결정이 필요했던 상황, 당시 제약 (시간·예산·기술) 을 기술합니다.                             | "MVP 2 주차, Pages Router 에서 라우팅 버그 반복 " 등 구체적 상황    |
|                        | 검토한 대안 (Alternatives Considered)       | 선택하지 않은 옵션과 각각의 장단점을 나열합니다.                                          | "A: Remix — 학습 곡선 높음 / B: Next.js — 팀 (본인) 숙련도 높음 "  |
|                        | 최종 선택 및 이유 (Decision & Rationale)    | **최종 선택**과 **Why**를 명확히 적습니다.                                                | TDD 기술 스택 항목과 상호 링크 — 6 개월 뒤 본인도 납득할 근거     |
|                        | 비용 영향도 (Cost Impact)                   | 결정에 따른 **금전·시간·기회비용** 변화 (절감/증가) 를 정량·정성으로 기록합니다.            | " 호스팅 $20→$80/월, 개발 2 주 단축 " — BRD 예산·Phase Roadmap 과 대조 |
| **2. 실험·피벗 기록**  | MVP 실험 결과 (Experiment Result)           | MVP(03 번) 가설 검증 결과, 정량·정성 데이터를 기록합니다.                                  | " 이메일 구독율 4% — 목표 10% 미달 → 피벗 검토 "                   |
|                        | 피벗/지속 판단 (Go / No-Go / Pivot)         | 실험 결과에 따른 다음 행동 (정식 개발·피벗·중단) 과 판단 근거입니다.                        | MVP 의 Go/No-Go 기준과 1:1 대응 — 감정이 아닌 데이터 기반 기록     |
| **3. 기술·아키텍처**   | 기술 스택 변경 (Tech Stack Change)          | 프레임워크, DB, 호스팅, 라이브러리 교체 시 이유와 마이그레이션 계획을 기록합니다.         | Decision Log → TDD(08 번) 업데이트 순서로 연동                    |
|                        | 아키텍처 분기 (Architecture Fork)           | 모노레포 분리, 마이크로서비스 전환 등 구조적 결정을 문서화합니다.                         | 폴더 구조 변경 전·후 다이어그램을 첨부하면 회고 시 유용           |
| **4. 장애·회고**       | 장애 회고 (Incident Postmortem)             | 장애 발생 시각, 영향 범위, 근본 원인, 재발 방지 조치를 기록합니다.                        | " 유저 DB 30 분 다운 — 원인: 마이그레이션 미적용 " 형식으로 간결히   |
|                        | 프로젝트 회고 (Retrospective)               | 스프린트·마일스톤 종료 시 잘한 점, 개선점, 다음 액션을 정리합니다.                      | 1 인 개발은 분기 (3 개월) 마다 30 분 회고만 해도 충분                 |
| **5. 상태 추적**       | 결정 상태 (Status)                          | **Active(유효)**, **Superseded(대체됨)**, **Deprecated(폐기)** 중 현재 상태를 표시합니다. | 구 결정은 삭제하지 말고 Superseded 로 표시 — 히스토리 보존        |
|                        | 관련 문서 링크 (Related Docs)               | 연관 BRD, PRD, TDD, MVP 문서 링크를 연결합니다.                                           | 본문 **경로 링크**(그래프) · YAML **`doc_id` 만**(목록) — Wikilink 금지 |

### **💡 Decision Log 활용법**

- **TDD 와의 분리**: TDD 는 " 현재 시스템이 어떻게 동작하는가 (What)" 이고, Decision Log 는 " 왜 이렇게 설계했는가 (Why)" 입니다. 기술 스택 변경 시 Decision Log 에 Why 를 먼저 쓰고 TDD 를 갱신하세요.
- **반복 실수 방지**: 6 개월 전에 버렸던 기술을 다시 도입하려 할 때, 당시 기록을 열어보면 같은 시행착오를 막을 수 있습니다.

## **05. PRD (제품 요구사항 정의서) 세부 항목**

PRD 는 **제품 전체의 방향성과 모든 기능**을 정의하고, MVP 문서는 **빠른 검증을 위한 핵심 기능과 실험 지표**에 집중합니다.
개발, 디자인, 마케팅 팀이 하나의 목표를 바라볼 수 있도록 상세하게 작성합니다.

| 항목 분류        | 세부 항목명                      | 설명                                                     |
| ---------------- | -------------------------------- | -------------------------------------------------------- |
| **기본 정보**    | 문서 개요 (Overview)             | 제품명, 버전, 작성자, 작성일, 최근 변경 이력 관리        |
| **배경 및 목표** | 제품 목적 (Purpose)              | 이 제품 (기능) 을 **왜 (Why)** 만들어야 하는지 배경 기술    |
|                  | 목표 및 비전 (Goals)             | 제품이 달성하고자 하는 궁극적인 비즈니스 목표            |
| **고객 정의**    | 타겟 유저 (User Persona)         | 제품을 사용할 핵심 사용자 층 및 페르소나 정의            |
|                  | 사용자 스토리 (User Story)       | 유저 관점에서 요구하는 기능 (예: "~로서 ~를 하고 싶다 ")  |
| **요구사항**     | 기능 요구사항 (Functional)       | 제품이 반드시 수행해야 하는 기능 목록 및 상세 설명       |
|                  | 비기능 요구사항 (Non-functional) | 보안, 성능 속도, 지원 환경 (OS, 브라우저) 등 기술 스펙    |
|                  | 예외 케이스 (Exception Case)     | 네트워크 오류, 잘못된 입력 등 예외 상황 시 대응 플로우   |
|                  | 데이터 요구사항 요약 (Data Requirements) | 기능 구현에 필요한 **입력·출력·저장 데이터**의 종류, 출처, 보관 기간을 요약합니다. TDD DB 스키마 (08 번)·UI/UX 데이터 매핑 (07 번) 작성 전 1 차 정리용 — 필드명은 여기서 확정하지 않아도 됨 |
| **제약 및 일정** | 마일스톤 (Milestone)             | 디자인, 개발, QA, 배포 등 타임라인 및 마감일             |
|                  | 제약 사항 (Constraints)          | 예산, 인력, 법적 규제 등 개발 시 고려해야 할 제한 요소   |
| **성공 지표**    | 핵심 성과 지표 (KPI)             | 제품 출시 후 성공 여부를 판단할 데이터 지표 (예: 리텐션) |

## **06. Analytics Spec (데이터 분석) 상세 세부 항목**

PRD 의 성공 지표 (KPI) 를 **" 어떤 버튼 클릭 시 어떤 값을 보내는가 "** 수준으로 기술하는 문서입니다. 개발자가 이벤트 로그를 정확히 심고, 마케팅·사업 담당자가 동일한 지표 정의를 공유할 수 있습니다.

| 항목 분류                | 세부 항목명 (영문명)                      | 설명                                                                                    | 1 인 개발자를 위한 현실적인 작성 팁                                    |
| ------------------------ | ----------------------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| **1. 분석 목표**         | KPI 매핑 (KPI Mapping)                    | PRD·BRD 의 비즈니스 지표를 측정 가능한 이벤트·속성으로 변환합니다.                     | " 유료 전환율 " → `subscription_completed` 이벤트 1 개로 시작          |
|                          | 측정 도구 (Analytics Stack)               | GA4, Mixpanel, Amplitude, PostHog 등 사용할 분석 도구와 계정·프로젝트 ID 를 명시합니다.  | MVP 단계는 GA4 무료 + 1 개 커스텀 이벤트만으로도 충분                |
| **2. 이벤트 명세**       | 이벤트 이름 (Event Name)                  | 스네이크 케이스 등 팀 규칙에 맞는 이벤트 식별자를 정의합니다.                           | 예: `signup_completed`, `payment_failed` — PRD 기능명과 대응          |
|                          | 트리거 조건 (Trigger Condition)           | 이벤트가 **언제** 발화되는지 (버튼 클릭, API 성공, 페이지 뷰 등) 를 정의합니다.           | " 결제 API 200 응답 후 " 처럼 개발자가 코드에 바로 옮길 수 있게 작성     |
|                          | 이벤트 속성 (Event Properties)            | 이벤트와 함께 전송할 key-value(플랜 종류, 금액, 오류 코드 등) 를 정의합니다.           | PII(이메일 전체) 는 보내지 말고 `user_id` 해시 또는 익명 ID 사용     |
| **3. 유저·세션**         | 유저 식별 (User Identification)           | 로그인 전·후 유저 ID 연결 방식, 익명 ID 와 회원 ID 병합 규칙을 정의합니다.               | Legal(02 번) 개인정보 처리방침과 수집 범위 일치 필수                   |
|                          | 세션·페이지뷰 (Session / Pageview)        | SPA 라우팅 시 페이지뷰 정의, 세션 타임아웃 등 기본 추적 규칙을 명시합니다.            | Next.js App Router 는 `pathname` 변경 시 수동 page_view 호출 여부 결정 |
| **4. 퍼널·대시보드**     | 전환 퍼널 (Conversion Funnel)             | 가입 → 온보딩 → 결제 등 단계별 이벤트 순서와 이탈 지점을 정의합니다.                   | MVP 성공 기준 (03 번) 과 동일한 퍼널 1 개만 먼저 설계                    |
|                          | 대시보드·리포트 (Dashboard Spec)          | 주간·월간 확인할 차트, 세그먼트 (신규/복귀 유저) 를 정의합니다.                         | 1 인 개발은 GA4 기본 리포트 3 개 (유입·전환·이탈) 로 시작                 |
| **5. 품질·거버넌스**     | 이벤트 네이밍 규칙 (Naming Convention)    | 신규 이벤트 추가 시 따를 prefix·버전 규칙을 정의합니다.                                 | `06_Analytics_유저행동추적_v1.0.md` — PRD 버전과 연동                 |
|                          | QA·검증 (Analytics QA)                    | 이벤트가 의도대로 수집되는지 확인하는 체크리스트 (디버그 뷰, 샘플 로그) 를 포함합니다.  | QA Test Case(10 번) 에 " 이벤트 발화 확인 " 시나리오 1~2 개 추가           |
|                          | 데이터 보존·삭제 (Retention & Deletion)   | 로그 보관 기간, 회원 탈퇴 시 분석 데이터 삭제·익명화 정책을 명시합니다.                 | Legal(02 번) 개인정보 파기 정책과 동일하게 유지                        |
|                          | 데이터 소유자 및 검증 주기 (Owner & Audit Cycle) | 각 KPI·이벤트의 **담당자 (Owner)**와 정기 검증 주기 (주간/월간) 를 정의합니다.          | 1 인 개발은 본인이 Owner, 검증은 " 배포 후 1 주일 내 GA4 디버그 뷰 확인 " 으로 단순화 |

### **💡 Analytics Spec 작성 가이드**

- **PRD 와의 연결**: PRD " 핵심 성과 지표 (KPI)" 표의 각 행마다 최소 1 개 이벤트 또는 속성을 매핑하세요. KPI 만 있고 이벤트가 없으면 출시 후 " 숫자를 못 본다 " 는 상황이 반복됩니다.
- **개발 우선순위**: MVP In-Scope 기능에 해당하는 이벤트만 먼저 구현하고, 나머지는 v1.1 Analytics Spec 으로 미룹니다.

## **07. UI/UX Spec (디자인 명세서) 상세 세부 항목**

기획 (PRD) 과 개발 (TDD) 사이를 유기적으로 연결해 주는 **UI/UX Spec (디자인 명세서/화면 설계서) 로서** 눈에 보이는 화면의 형태뿐만 아니라 **" 유저가 버튼을 눌렀을 때 화면이 어떻게 반응하고 이동하는가?"**라는 시각적 기능과 흐름을 정의하는 문서입니다. 1 인 개발 시에는 **피그마 (Figma) 파일 안에 페이지를 나누거나 캔버스 내부에 텍스트로 적어두는 방식**으로 관리하면 가장 효율적입니다.

| 항목 분류                  | 세부 항목명 (영문명)                       | 설명                                                                                     | 혼자 개발할 때의 핵심 팁 (Figma 활용)                                                                        |
| -------------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **1. 디자인 시스템**       | 글로벌 스타일 (Global Styles)              | 서비스 전체에 공통으로 사용할 컬러 (Palette) 와 타이포그래피 (Font) 규칙입니다.             | 피그마의 **Variables(변수)**나 **Local Styles**로 등록하여 코드의 Tailwind/CSS 변수와 일치시킵니다.          |
|                            | UI 컴포넌트 라이브러리 (Component Library) | 버튼, 입력창 (Input), 모달 (Modal), 카드 등 반복 사용되는 UI 요소의 집합입니다.            | 피그마 **Component(기포넌트)** 기능을 활용해 `Default`, `Hover`, `Focus`, `Disabled` 상태를 미리 만듭니다.   |
| **2. 사용자 흐름**         | 와이어프레임 (Wireframe)                   | 시각적 디자인 요소 (색상, 이미지) 를 배제하고 화면의 레이아웃과 정보 배치만 설계합니다.    | 펜으로 종이에 그리거나 피그마 플러그인을 활용해 빠르게 구조만 잡습니다.                                      |
|                            | 유저 플로우 (User Flow / IA)               | 사용자가 목표를 달성하기 위해 이동하는 화면 간의 전체적인 경로 (지도) 입니다.              | 피그마 캔버스 위에 각 화면을 배치하고 화살표 (Connector) 로 연결해 정보 구조 (IA) 를 한눈에 봅니다.              |
| **3. 화면별 상세 명세**    | 인터랙션 명세 (Interaction Spec)           | 특정 버튼이나 영역을 클릭/스크롤/스와이프했을 때 일어나는 애니메이션과 반응입니다.       | 피그마의 **Prototype** 기능을 연결해 앱의 실제 구동 느낌을 미리 테스트해 봅니다.                             |
| (가장 중요)                | 콘텐츠 & 데이터 매핑 (Data Mapping)        | 화면의 각 요소에 어떤 실제 데이터 (텍스트, 이미지) 가 노출되어야 하는지 정의합니다.        | " 여기는 DB 의 `user.profile_img` 가 들어가고, 비어있으면 기본 아바타 노출 " 과 같은 규칙을 화면 옆에 메모합니다. |
| **4. 예외 및 반응형 처리** | 상태별 UI 명세 (State Spec)                | 로딩 중 (Loading), 데이터 없음 (Empty), 에러 (Error) 발생 시 유저에게 보일 화면입니다.      | 개발할 때 가장 빼먹기 쉬운 부분입니다. 빈 화면과 로딩 스피너 디자인을 반드시 미리 정의합니다.                |
|                            | 반응형/디바이스 대응 (Responsive Design)   | 데스크톱, 태블릿, 모바일 등 화면 크기 변화에 따라 레이아웃이 어떻게 변하는지 정의합니다. | 피그마의 **Auto Layout** 기능을 적극 활용하여 창 크기가 줄어들 때의 정렬 규칙을 세웁니다.                    |

### **💡 UI/UX Spec 실무 적용 가이드**

- **기획 (PRD) 과의 연결**: PRD 에 적힌 사용자 스토리 (예: " 유저는 비밀번호 찾기를 할 수 있다 ") 마다 대응하는 피그마 화면 프레임을 만드세요.
- **개발 (TDD) 과의 연결**: 피그마 컴포넌트의 이름 (예: `Button/Primary/Large`) 을 나중에 작성할 React 컴포넌트 파일명이나 Props 구조와 똑같이 맞추면 TDD 를 쓸 때나 코딩할 때 뇌 손실을 엄청나게 줄일 수 있습니다.

## **08. TDD (Technical Design Document) 기술 설계 문서**

| 항목 분류 [1]                | 세부 항목명 (영문명)                     | 설명                                                                             | 핵심 포함 내용 예시                                       |
| ---------------------------- | ---------------------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------------- |
| **1. 기본 정보 & 개요**      | 문서 개요 (Overview)                     | 이 기술 설계 문서가 해결하고자 하는 개발 목표를 서술합니다.                      | 배경, 연관된 PRD 링크, 관련 기능 범위                     |
|                              | 시스템 요구사항 (Requirements)           | 개발 관점에서 만족해야 하는 성능 및 기술적 목표를 정의합니다.                    | " 첫 페이지 로딩 1.5 초 이내 ", "SSR 필수 적용 " 등           |
| **2. 아키텍처 및 기술 스택** | 시스템 아키텍처 (System Architecture)    | 인프라, 백엔드, 프런트엔드의 전체적인 구조와 연결 방식을 정의합니다.             | 인프라 구조도, 클라이언트 - 서버 구조도                     |
|                              | 기술 스택 및 라이브러리 (Tech Stack)     | 사용할 언어, 프레임워크, 주요 라이브러리와 **선택 이유**를 명시합니다.           | Next.js, Tailwind CSS, Zod, Zustand 등을 고른 이유        |
|                              | 디렉토리/파일 구조 (Directory Structure) | 프로젝트의 폴더 구조와 컴포넌트 배치 규칙을 사전에 정의합니다.                   | `src/features`, `src/components` 등 디렉토리 트리         |
| **3. 데이터 모델링**         | 데이터베이스 스키마 (DB Schema)          | 테이블 구조, 필드 타입, 테이블 간의 관계 (1:N, N:M) 를 정의합니다.                 | ERD(엔티티 관계도), PostgreSQL 테이블 명세                |
|                              | 데이터 유효성 검증 (Zod Schema)          | 클라이언트와 서버 사이에서 교환되는 데이터의 무결성 검증 규칙입니다.             | `userSchema = z.object({ email: z.string().email() })`    |
|                              | 상태 관리 전략 (State Management)        | 전역 상태 (Global), 지역 상태 (Local), 서버 상태 (Server) 의 관리 주체를 정의합니다. | Zustand 클라이언트 상태, TanStack Query 서버 캐싱 분리    |
| **4. 데이터 흐름 & 로직**    | 데이터 흐름도 (Data Flow Diagram)        | 유저의 행동 (Input) 부터 DB 저장 (Output) 까지 데이터가 거쳐 가는 경로입니다.        | Client Form ➔ API Route (Zod 검증) ➔ DB 저장 흐름         |
|                              | 핵심 비즈니스 로직 (Core Logic)          | 알고리즘, 가중치 계산, 복잡한 비즈니스 규칙의 구현 방법을 기술합니다.            | 장바구니 할인율 계산 공식, 포인트 차감 순서 규칙          |
|                              | 에러 핸들링 & 로그 (Error & Logging)     | 예외 상황이 발생했을 때 시스템이 어떻게 반응하고 기록할지 정의합니다.            | 글로벌 에러 바운더리 배치, Sentry 에러 로깅 포인트        |
| **5. 인터페이스 명세**       | API 엔드포인트 명세 (API Specification)  | 프런트엔드와 백엔드가 주고받을 API 의 주소, 메서드, 데이터 구조입니다.            | REST API (POST /api/auth/register), Request/Response Body |

### **💡 TDD 작성 팁**

1. **" 왜 (Why)" 를 꼭 적으세요:** 기술 스택이나 폴더 구조를 적을 때, 6 개월 뒤의 내가 다시 봐도 납득할 수 있도록 **"A 라이브러리 대신 B 를 선택한 이유 "**를 한 줄이라도 적어두어야 나중에 흔들리지 않습니다.
2. **처음부터 다 채우지 마세요:** 장기 프로젝트라면 1 번 (개요) 부터 6 번 (타스크) 까지 틀만 만들어 둔 뒤, **당장 개발할 MVP 기능 분량만큼만 2~5 번의 세부 내용을 채우고 개발에 착수**하는 것이 지치지 않는 비결입니다.

### **💡 QA Test Case 작성 노하우 (Happy vs Sad)**

테스트 케이스를 작성할 때는 머릿속으로 두 가지만 기억하고 항목을 쪼개면 됩니다.

1. **해피 패스 (Happy Path - 정상 케이스)**
   - 유저가 기획자가 의도한 대로 올바르게 값을 입력하고 스무스하게 성공하는 경로 (예: 양식에 맞게 다 쓰고 가입 성공)
2. **새드 패스 (Sad Path - 예외/실패 케이스)**
   - 유저가 잘못된 값을 넣거나 시스템 오류가 나는 경로 (예: 중복 이메일 입력, 글자수 미달, 결제 중 네트워크 끊김 등)

**특히 ' 새드 패스 ' 를 잘 적어두어야 나중에 앱이 커졌을 때 예기치 못한 크래시 (Crash) 나 보안 구멍을 막을 수 있습니다.** Zod 스키마로 1 차 검증한 에러 메시지가 화면에 예쁘게 잘 뜨는지 확인하는 용도로 이 QA 시나리오를 활용하시면 됩니다.

## 옵시디언 중심의 관리 툴

옵시디언에서 **Frontmatter(YAML)**는 메타·관계 ID 용, **본문 경로 링크**는 그래프·가독성용으로 **역할을 분리**합니다.
**Wikilink(`[[...]]`) 는 사용하지 않습니다.** YAML 과 본문을 이중 작성하지 않습니다.

### **설치 플러그인 (공식 계획)**

| 플러그인 | 역할 |
| :------- | :--- |
| **[Linter](https://github.com/plume-app/obsidian-linter)** | 저장 시 YAML 필수 키 보정, `updated` 갱신, Wikilink·금지 패턴 검출 |
| **[Dataview](https://github.com/blacksmithgu/obsidian-dataview)** | `doc_id` 중복·누락 감시, 분류별 목록·관계 대시보드 |

옵시디언 기본 **Properties**·**Templates**는 보조로 사용합니다. (커뮤니티 Templater·QuickAdd 등은 당분간 필수 아님.)

---

### **Frontmatter 스키마 (초안 · SSOT)**

#### 공통 규칙

- **확정 문서**(`01_BRD`~`11_UserGuide`, `_inbox` 제외): **필수 키 7 개** + **용어 키 2 개**(값은 빈 배열 허용) 를 갖습니다.
- **`doc_id`**: `{접두}-{순번}` 형태의 **불변 식별자**. 파일명·폴더가 바뀌어도 유지합니다.
- **README·인덱스 (MOC)**: `doc_id` 생략. `category`·`title` 만으로 충분.
- **YAML ↔ 본문 역할 분리** (이중 작성 금지):
  - **YAML**: 메타데이터 + 관계 **`doc_id` 만** + **용어 배열** `terms_*` (Dataview·개념 검색)
  - **본문**: **경로 링크만** (옵시디언 그래프·GitHub·VS Code 가독성)

#### `doc_id` 부여 규칙

| 항목 | 규칙 |
| :--- | :--- |
| **형식** | `{접두}-{NNN}` — 접두 3~4 자 + 하이픈 + 3 자리 순번 (예: `PRD-001`, `TDD-042`) |
| **접두** | 11 대 분류별 고정 코드 (아래 표). 요건류 통칭 예시로 `REQ-001` (= PRD·MVP 등 **요구 문서**) 도 허용 |
| **불변** | 파일 리네임·승격 시 `doc_id` 는 **변경하지 않음**. 대체 정본은 구 문서 `status: archived` + 본문 링크로 연결 |
| **유일** | vault 전체에서 **중복 불가** — Dataview 로 감시 |

| category | doc_id 접두 예 |
| :------- | :------------- |
| `01_BRD` | `BRD-` |
| `02_Legal` | `LEG-` |
| `03_MVP` | `MVP-` |
| `04_Decision` | `DEC-` |
| `05_PRD` | `PRD-` · `REQ-` |
| `06_Analytics` | `ANA-` |
| `07_UIUX` | `UIX-` |
| `08_TDD` | `TDD-` |
| `09_Admin` | `ADM-` |
| `10_QA` | `QA-` |
| `11_UserGuide` | `UG-` |

**발급·조회 SSOT:** 전체 확정 문서 77 건의 `doc_id`·`title`·관계는 **[doc_id_레지스트리.md](./doc_id_레지스트리.md)** 에 있으며, 각 본문 frontmatter YAML 은 **레지스트리 표를 기준**으로 채웁니다. 신규 승격 시 레지스트리에 한 줄 추가 → 동일 `doc_id` 를 frontmatter 에 기입합니다.

#### 필수 · 권장 키 (단순화)

| 키 | 타입 | 필수 | 설명 |
| :--- | :--- | :---: | :--- |
| `doc_id` | string | ● | `PRD-001` · `REQ-001` 등 불변 고유 키 |
| `title` | string | ● | 한글 제목 |
| `category` | string | ● | `01_BRD` … `11_UserGuide` (폴더·11 대 분류 추적) |
| `domain` | string | ● | `NEXIA` · `NEXAOS` · `LangGraph` · `U2BEE` 등 (`Nexaon` 은 모듈명 — frontmatter `domain` 값 아님) |
| `status` | string | ● | `draft` · `review` · `published` · `archived` (4 종) |
| `created` | date | ● | `YYYY-MM-DD` |
| `updated` | date | ● | Linter 로 저장 시 자동 갱신 권장 |

#### 용어 배열 (`terms_standard` · `terms_nexa`)

업계 기술 스택 용어와 NEXA 내부 시스템 용어를 **개념 색인**으로 분리합니다. (법규·약관 용어는 **포함하지 않음** — `02_Legal` 은 별도.)
**사람이 읽는 정의 SSOT:** [NEXA V2.0 용어집 (TDD-060)](./08_TDD/NEXAOS/08_TDD_NEXAOS_용어집_v1.0.md).

| 키 | 타입 | 키 존재 | 값 채우기 | 설명 |
| :--- | :--- | :---: | :---: | :--- |
| `terms_standard` | list | ● | ○ | **업계·기술 스택** 용어 (MQTT, LangGraph, Yjs, REST, React Flow …) |
| `terms_nexa` | list | ● | ○ | **NEXA 내부** 용어 (NEXIA, Twinex, Omnix, `domainKey`, NEXA-CELL …) |

**운영 규칙**

1. **키는 전 확정 문서에 포함** — 값을 모르면 `terms_standard: []` · `terms_nexa: []` 로 둡니다. (승격 직후에도 OK)
2. **값은 점진 채움** — 허브 문서 (TDD-001, TDD-010, BRD-001 등) → 자주 여는 문서 순. 한 번에 77 건 필수 아님.
3. **수량 가이드** — 문서당 **3~12 개 권장**, 느슨한 상한 **~20 개**. 헷갈리는 개념만 넣습니다.
4. **`domain` 과 중복 최소화** — `domain: NEXIA` 는 이미 있으므로 `terms_nexa` 에는 **하위 모듈·탭·스토어** 위주.
5. **관계 키와 분리** — `parent_doc` / `implements_doc` 는 문서 ID, `terms_*` 는 검색·학습용 키워드.

#### `tags` (옵시디언 태그 패널 · 파생)

| 키 | 타입 | 필수 | 설명 |
| :--- | :--- | :---: | :--- |
| `tags` | list | ○ | **파생 필드** — `terms_standard` · `terms_nexa` 및 `category` · `domain` 에서 `scripts/sync_terms_to_tags.py` 가 생성. **수동 편집 금지** |

**태그 접두 (중첩 태그)**

| 접두 | 출처 | 예 |
| :--- | :--- | :--- |
| `doc/cat/` | `category` | `doc/cat/08-tdd` |
| `doc/domain/` | `domain` (소문자) | `doc/domain/nexia` |
| `std/` | `terms_standard` | `std/langgraph` |
| `nexa/` | `terms_nexa` | `nexa/Omnix` |

재생성: `python scripts/sync_terms_to_tags.py` · dry-run: `--check`

**표기**

| 필드 | 예시 |
| :--- | :--- |
| `terms_standard` | `"mqtt"`, `"websocket"`, `"next-js"` (항목마다 **쌍따옴표**) |
| `terms_nexa` | `"NEXIA"`, `"Twinex"`, `"NEXA-CELL"`, `"FileDropZone"` |

**YAML 배열 표기**

- 형태: **`terms_standard: []`** (빈 배열) · **`terms_standard: ["mqtt", "rest"]`** (대괄호 + **쌍따옴표**)
- **각 항목은 반드시 `"..."` 로 감쌉니다.** (`file-upload` 처럼 하이픈·대문자 혼합 시 따옴표 없으면 YAML 파서·Linter 오류 가능)
- `- 항목` 블록 형태는 사용하지 않습니다. (`[]` + 쌍따옴표만)

**빈 배열 의미:** `[]` = 아직 미작성 또는 해당 없음 (초기에는 구분하지 않음). Dataview 로 “값이 비어 있는 문서” 목록을 만들어 천천히 채웁니다.

> **폐기·대체 문서:** 구 `superseded` 는 `status: archived` 로 통합. 대체 정본 연결은 **본문 경로 링크**로만 표기.

#### 관계 타입 (YAML 키 · 3 개 통폐합)

YAML 에는 **`doc_id` 문자열만** 적습니다. 경로·파일명은 YAML 에 넣지 않습니다.

| YAML 키 | 타입 | 의미 | 구 키 |
| :------ | :--- | :--- | :---- |
| `parent_doc` | string | 상위 기획·요건 문서 (BRD·MVP·상위 PRD) | `derives_from` |
| `implements_doc` | string | 내가 구현·상세화해야 하는 대상 (PRD·MVP 등) | `implements` |
| `see_also` | list | 횡단 참고 (`doc_id` 배열) | `see_also` |

- **TDD → PRD:** `implements_doc: PRD-012`
- **PRD → BRD:** `parent_doc: BRD-001`
- **Decision(04) 연결:** `parent_doc` 또는 `see_also` 에 `DEC-003` — Why 상세는 본문 링크
- **구현 역참조·대체 관계:** YAML 키를 늘리지 않음. 필요 시 `see_also` 또는 **본문 `## 관련 문서`**만 사용

> **README(MOC):** 목록·발견용 outgoing **경로 링크**만 많아도 됨. 관계 `doc_id` 는 확정 본문에만 둡니다.

#### 확정 문서 예시 (TDD)

```yaml
tags: ["doc/cat/08-tdd", "doc/domain/nexia", "std/file-upload", "std/multipart", "std/rest", "nexa/NEXIA", "nexa/FileDropZone", "nexa/NexiaLeftNav", "nexa/files"]
```

### **경로 링크 단일 규칙 (Wikilink 금지)**

| 규칙 | 내용 |
| :--- | :--- |
| **1. Wikilink 금지** | `[[파일명]]` · `[[경로\|별칭]]` 사용하지 않음. Linter 로 검출·제거 권장 |
| **2. 본문만 링크** | 관계의 **시각·그래프 연결**은 본문 `[표시 텍스트](상대경로/파일.md)` 만. YAML 에 경로 넣지 않음 |
| **3. 상대 경로** | **현재 파일** 기준 (`./` · `../`). 확장자 `.md` 필수 |
| **4. 표시 텍스트** | 한글 `title` 권장. 필요 시 `doc_id` 병기 — 예: `드롭존 첨부 (PRD-012)` |
| **5. 링크 대상** | **확정 정본** 파일. `_inbox` 는 `status: draft` 일 때만 |
| **6. 관련 문서 섹션** | 본문 하단 `## 관련 문서` — **그래프용 유일한 링크 허브** (README 제외) |

**본문 예시** (YAML `doc_id: PRD-005` · 구현 TDD 는 TDD 문서의 `implements_doc` 에만):

```markdown
## 관련 문서

| 관계 | 문서 |
| :--- | :--- |
| 구현 TDD | [드롭존 · 첨부 파일 구조 (TDD-013)](../../08_TDD/NEXIA/08_TDD_NEXIA_드롭존첨부파일구조.md) |
| 연관 PRD | [files.source_metadata 추출 (PRD-013)](./05_PRD_NEXIA_파일메타데이터AI추출.md) |
| 상위 BRD | [NEXA 사업 마스터 플랜 (BRD-001)](../../01_BRD/01_BRD_NEXA_사업마스터플랜.md) |
```

**금지 예시**

- `[[08_TDD_NEXIA_드롭존첨부파일구조]]` (Wikilink)
- `[TDD](08_TDD_NEXIA_드롭존첨부파일구조)` (`.md` 없음)
- YAML `implements_doc` 에 `08_TDD/NEXIA/....md` 경로 기재 (경로는 본문 전용)

### **Linter · Dataview 운용**

**Linter (권장 설정 방향)**

- 저장 시 `updated` 를 당일 날짜로 갱신
- 확정 폴더 문서에 `doc_id`·`title`·`category`·`domain`·`status` 누락 시 경고
- `terms_standard` · `terms_nexa` **키 누락** 시 경고 (값 `[]` 허용)
- 정규식으로 `\[\[[^\]]+\]\]` 포함 시 경고 (Wikilink)

**Dataview**

- [부록](#부록--dataview-감시-쿼리) 쿼리로 `doc_id` **중복·누락** 감시
- `parent_doc` · `implements_doc` 로 상하위 체인 목록 조회 (파일 경로 변환은 하지 않음 — `doc_id` 조인만)
- `terms_*` 로 **업계 스택·내부 모듈** 기준 문서 클러스터 조회

**Properties (내장)**

- `category` · `status` · `domain` 을 List 타입으로 등록해 드롭다운 선택
- `terms_standard` · `terms_nexa` 도 **List** 타입으로 등록 (빈 목록부터 추가 가능)

### **💡 옵시디언 활용을 위한 최종 조언**

1. **결정 (04) 연결**: TDD 변경 Why 는 YAML `see_also: ["DEC-003"]` 또는 `parent_doc` + 본문 `## 관련 문서` 경로 링크로만 연결합니다.
2. **승격 시 체크**: `_inbox` → `NN_` 폴더 이동 시 **불변 `doc_id` 발급** · 필수 키 7 개 · `terms_standard: []` · `terms_nexa: []` · 본문 `## 관련 문서` 에 경로 링크 ≥1.
3. **용어 채우기**: 승격 직후 terms 는 비워도 됨. 허브·자주 보는 문서부터 3~12 개씩 추가.
4. **이중 작성 금지**: YAML 에 경로를 적었다면 본문에 같은 관계를 반복하지 않아도 됨 — 역할이 다름 (ID vs 그래프).
5. **그래프 해석**: Graph view 에서 `path:README` 필터로 MOC 를 숨기면 본문 경로 링크 관계만 보입니다.

```dataview
TABLE length(rows) AS "중복 건수", rows.file.link AS "파일 목록"
FROM "01_BRD" OR "02_Legal" OR "03_MVP" OR "04_Decision" OR "05_PRD" OR "06_Analytics" OR "07_UIUX" OR "08_TDD" OR "09_Admin" OR "10_QA" OR "11_UserGuide"
WHERE doc_id
GROUP BY doc_id
WHERE length(rows) > 1
SORT length(rows) DESC
```
