# 2026-06-12 WHY CHAIN

> " 우리 시스템의 와이 체인은 단순한 에러 로그 추적이 아니다.
> 거절 (`Reject`) 이라는 하나의 현상 뒤에 숨겨진 인과관계를 [SHACL ➡️ OWL ➡️ Redis ➡️ Zod ➡️ 비즈니스 목적] 으로 이어지는 5 단계 기술 사슬 (5 Whys) 로 추적하여 설명하는 무결성 아키텍처다."
' Why Chain(왜 - 체인) 기법 ' 은 문제의 근본 원인을 찾기 위해 " 왜?" 라는 질문을 꼬리를 물고 반복하는 원인 분석 방법론 (5 Whys) 입니다.

이를 데이터 패브릭 (Data Fabric) 및 온톨로지 (Ontology) 와 연결하면, 데이터 세계에서 발생하는 복잡한 오류의 원인을 추적하고 데이터 간의 인과관계를 지도처럼 시각화하는 강력한 도구가 됩니다.

## 🔗 1. 온톨로지 (Ontology) 와의 연결: Why Chain 의 ' 관계 ' 를 컴퓨터에게 학습시키기

온톨로지는 데이터 간의 개념과 상호 관계를 컴퓨터가 이해할 수 있는 형태 (인과관계, 종속관계 등) 로 정의한 지식 그래프의 기초입니다.

- 인과관계의 데이터화: Why Chain 이 " 원인 A ➡️ 결과 B ➡️ 결과 C" 라는 인간의 논리적 사슬을 만든다면, 온톨로지는 이를 `[원인 A] -> isCauseOf -> [결과 B]` 구조의 데이터 (트리플) 로 명확히 정의합니다.
- 지식의 자산화: Why Chain 을 통해 밝혀낸 장애 원인이나 비즈니스 로직을 온톨로지에 등록하면, 컴퓨터가 자동으로 " 왜 이 데이터가 생성되었는가?" 에 대한 맥락을 이해할 수 있습니다.

## 🌐 2. 데이터 패브릭 (Data Fabric) 과의 연결: Why Chain 의 ' 추적 경로 ' 를 자동화하기

데이터 패브릭은 사방에 흩어진 데이터를 하나의 거대한 직물 (Fabric) 처럼 촘촘하게 연결하여 관리하는 아키텍처입니다. 여기에는 데이터의 계보 (Lineage) 와 메타데이터가 핵심 역할을 합니다. [1, 2, 3]

- 데이터 리니지 (Lineage) 가 곧 Why Chain: 데이터 패브릭 환경에서 " 이 매출 데이터는 왜 오차가 발생했는가?" 라는 질문을 던지면, 시스템은 데이터의 이동 경로를 거꾸로 추적 (Data Lineage) 합니다. 이것이 바로 데이터 세계의 'Why Chain' 입니다.
- AI 기반의 원인 분석: 데이터 패브릭에 구현된 온톨로지 덕분에, 시스템은 " 왜?" 라는 질문을 받을 때마다 수많은 데이터 소스를 스스로 체인처럼 엮어 나가며 근본적인 데이터 오염 소스 (Root Cause) 를 실시간으로 찾아냅니다.

## 💡 한 눈에 보는 요약 시나리오

> "A 매장의 5 월 매출 데이터가 갑자기 누락되었다. 왜?"

1. Why Chain (인간의 분석): 데이터가 안 들어옴 ➡️ API 전송이 실패함 ➡️ 소스 서버 점검이 있었음 ➡️ 공지가 누락됨 (근본 원인).
2. 온톨로지 (관계 정의): `[서버 점검]` 은 `[API 실패]` 의 원인이고, `[API 실패]` 는 `[데이터 누락]` 을 유발한다는 ' 인과관계 법칙 ' 을 미리 정의해 둠.
3. 데이터 패브릭 (실제 추적): 이 법칙과 데이터 계보 (Lineage) 를 바탕으로, 시스템이 전사 데이터 네트워크를 스스로 종단하여 "4 단계 전 소스 서버 시스템의 점검 공지 누락이 원인 " 임을 자동으로 찾아내 사용자에게 보고함.

## 1. Why chain 은 왜 하필 '5 가지 ' 일까요?

인류의 품질 관리 역사에서 수많은 실험을 거친 결과, 대부분의 복잡한 시스템 장애나 비즈니스 문제는 5 번 정도 깊이 파고들었을 때 비로소 겉치레를 벗겨내고 ' 근본적인 원인 (Root Cause)' 에 도달한다는 통계적 결론을 얻었기 때문입니다.

- 1~2 번째 Why: 눈에 보이는 ' 현상 ' 이나 단순한 시스템 에러를 짚어냅니다.
- 3~4 번째 Why: 에러를 유발한 구체적인 ' 기술적 결함이나 파이프라인의 구멍 ' 을 찾아냅니다.
- 5 번째 Why: 시스템 전체를 지탱하는 ' 아키텍처의 철학, 정책, 설계의 본질 ' 이라는 진짜 정답에 도달합니다.

## 2. NEXA 아키텍처로 보는 '5 가지 와이 체인 ' 실전 매칭

사용자가 화면에서 " 이 데이터 제안이 왜 거절 (`Reject`) 되었는가?" 라는 하나의 현상을 마주했을 때, NEXA 데이터 패브릭 내부에서 작동하는 5 가지 기술적 와이 체인 (5 Whys) 의 구조입니다.

- 현상: 시스템이 최종 데이터베이스 (`Neo4j`) 적재를 거절 (`Reject`) 하고 롤백시켰다.
- 1st Why (현상 분석): 왜 거절되었는가?
    
    - ➡️ [SHACL 레이어] 가 최종 승격 (`promoted`) 직전 단계에서 검증 위반 (`Violation`) 을 발생시켰기 때문에.
    
- 2nd Why (인과 구조 추적): 왜 SHACL 검증을 통과하지 못했는가?
    
    - ➡️ [OWL 온톨로지 레이어] 의 비즈니스 규칙과 장비 간 관계성 (도메인 키) 조건이 불일치했기 때문에.
    
- 3rd Why (데이터 원천 추적): 왜 데이터 관계성이 꼬인 채 유입되었는가?
    
    - ➡️ [event bus / Redis] 에 적재되어 있던 `TICK(Live Feed)` 패킷 내부에 필수 정보가 누락되어 있었기 때문에.
    
- 4th Why (입구 파이프라인 저격): 왜 필수 정보가 누락된 데이터가 버퍼까지 들어왔는가?
    
    - ➡️ 앞단의 [validate · staging / Zod] 검증 단계에서 5W1H(HEXAGON) 패킷 구조의 헤더 결함을 걸러내고 `[TDD-023]` 거부 로직을 발동시켰기 때문에.
    
- 5th Why (근본적인 비즈니스 목적 - Root Cause 🌟): 왜 이렇게 복잡하고 깐깐한 양방향 방어벽 체인을 구축했는가?
    
    - ➡️ 생성형 AI(랭그래프) 의 블랙박스 환각 현상으로부터 시스템의 단일 진실 공급원 (SSOT) 을 철저히 보호하고, 인간에게 완벽하게 설명 가능한 데이터 패브릭을 구현하기 위한 제품의 최상위 비전 때문에.

## 관련 사전 개념

> 온톨로지는 ' 설계도 (규칙)' 이고, 데이터 패브릭은 그 설계도를 포함해 건물을 짓고 관리하는 ' 전체 건설 시스템 (아키텍처)' 입니다.

## 🧱 1. 온톨로지 (Ontology): " 데이터의 의미와 관계를 정의하는 명세서 "

온톨로지는 데이터 패브릭의 핵심 부품이자 기술적 수단입니다.

- 본질: 컴퓨터가 데이터의 뜻을 이해할 수 있도록 단어와 단어 사이의 관계 (인과, 상속, 포함 등) 를 규정한 지식 모델링 체계입니다.
- 역할: "A 는 B 의 원인이다 ", " 고객은 상품을 구매한다 " 처럼 데이터의 ‘맥락과 규칙’을 제공합니다.
- 특징: 데이터가 실제로 어디에 저장되어 있는지 (클라우드, 로컬 서버 등) 는 관심이 없으며, 오직 데이터의 의미적 연결에만 집중합니다. [1]

## 🌐 2. 데이터 패브릭 (Data Fabric): " 전사 데이터를 하나로 엮는 거대한 아키텍처 " [2]

데이터 패브릭은 온톨로지를 활용하는 종합 데이터 관리 환경 (플랫폼) 입니다.

- 본질: 분산된 수많은 데이터 소스 (DB, 클라우드, API 등) 를 하나의 촘촘한 직물 (Fabric) 처럼 가상으로 연결하는 종합 아키텍처입니다.
- 역할: 사용자가 데이터가 어디에 있든 상관없이 실시간으로 찾고, 분석하고, 거버넌스를 적용할 수 있게 통제합니다.
- 특징: 파이프라인 구축, 보안, 메타데이터 관리, 실제 데이터 접근 제어 등 데이터 비즈니스의 전 과정을 아우르는 거대한 인프라 개념입니다. [3]

## 🤝 결론: 둘은 어떤 관계인가요?

" 데이터 패브릭이 더 똑똑하게 작동하기 위해 온톨로지를 채택합니다."

과거의 데이터 통합 기술은 사람이 일일이 코딩해야 했습니다. 하지만 데이터 패브릭은 온톨로지 (지식 그래프) 를 내장하고 있어서, 시스템 스스로 데이터의 의미를 해석하고 AI 를 통해 " 이 데이터와 저 데이터는 이런 관계구나!" 라며 알아서 데이터를 연결합니다.

개념 구분이 명확해지셨나요? 이를 바탕으로 앞서 말씀드린 Why Chain(원인 추적) 기법을 어느 쪽에 더 중점을 두고 깊게 살펴보고 싶으신가요?



네, 완벽하게 간파하셨습니다!

데이터 패브릭은 프론트엔드의 특정 기술 문법이나 컴포넌트 단위가 아니라, 기업의 모든 데이터 인프라를 관통하는 ' 종합 시스템 아키텍처 (구조)' 를 의미합니다. 리액트는 그 거대한 빙산의 일각인 'UI 화면 ' 일 뿐입니다.

전체 시스템 관점에서 데이터 패브릭이 어떻게 구성되고 작동하는지 5 가지 핵심 레이어 (구조) 로 명확하게 짚어드리겠습니다.

## 🌐 데이터 패브릭의 5 대 아키텍처 레이어 (전반적 구조)

데이터 패브릭은 소스 데이터부터 사용자 화면까지 아래와 같은 층 (Layer) 이 촘촘하게 엮인 구조입니다.

```unset
[ 5. 소비 레이어 ]      ◀ 리액트(React) UI / BI 대시보드 / AI 모델
        ▲
[ 4. 오케스트레이션 ]   ◀ 데이터 파이프라인 자동 제어 (Airflow, Kubeflow)
        ▲
[ 3. 지식 그래프 ]     ◀ 온톨로지(Ontology) / 시맨틱 메타데이터 (Neo4j)
        ▲
[ 2. 가상화 레이어 ]    ◀ 데이터를 옮기지 않고 연결하는 가상 SQL (Trino, Denodo)
        ▲
[ 1. 데이터 소스 ]     ◀ 사방에 흩어진 원본 DB (MySQL, Oracle, AWS S3)
```

## ① 1 층: 데이터 소스 레이어 (Data Sources)

- 구조: 온프레미스 서버, AWS/Azure 클라우드, NoSQL, API 등 기업 내 모든 원본 데이터 저장소입니다.
- 특징: 데이터 패브릭은 이 데이터들을 한 곳으로 강제로 쑤셔 넣지 (Migration) 않습니다. 그냥 둔 채로 연결합니다. [1]

## ② 2 층: 데이터 가상화 레이어 (Data Virtualization)

- 구조: Trino(구 Presto) 나 Denodo 같은 분산 쿼리 엔진이 위치합니다.
- 특징: 서로 다른 저장소에 있는 데이터들을 마치 하나의 데이터베이스에 있는 것처럼 가상으로 묶어줍니다. 사용자가 SQL 을 날리면 가상화 엔진이 각 DB 에서 데이터를 실시간으로 긁어옵니다.

## ③ 3 층: 시맨틱 메타데이터 & 온톨로지 레이어 (Knowledge Graph)

- 구조: Graph DB(예: Neo4j) 나 시맨틱 웹 기술 (RDF/OWL) 이 핵심 구동축입니다.
- 특징: 여기서 온톨로지가 쓰입니다. 데이터 패브릭의 ' 두뇌 ' 역할을 하며, "A 데이터와 B 데이터는 사실 같은 뜻이며, 서로 인과관계가 있다 " 는 메타데이터 (데이터의 데이터) 지도를 스스로 그립니다.

## ④ 4 층: 오케스트레이션 및 거버넌스 레이어 (Data Ops)

- 구조: Apache Airflow, Kubeflow 등과 보안/권한 통제 솔루션이 작동합니다.
- 특징: 데이터가 안전하게 흘러가도록 길을 닦고, 데이터의 계보 (Lineage) 를 실시간으로 기록하여 Why Chain(원인 추적) 이 가능하도록 이력을 남깁니다.

## ⑤ 5 층: 데이터 소비 레이어 (Data Consumption)

- 구조: 최종 사용자가 만나는 화면으로, 여기서 리액트 (React) 가 등장합니다.
- 특징: 데이터 분석가나 경영진이 리액트로 만든 대시보드를 보며 " 어라? 3 층 온톨로지 맵을 보니 이 데이터의 원인이 저기였네?" 하고 인사이트를 얻거나 데이터를 조회하는 창구입니다.

## 🔑 결론: 데이터 패브릭의 본질

따라서 데이터 패브릭을 구축한다는 것은 " 데이터가 어디에 있든 사용자는 신경 쓰지 않고, 시스템이 온톨로지 (뇌) 를 기반으로 알아서 데이터를 찾고 엮어서 실시간으로 배달해 주는 유기적인 교통 시스템을 만드는 것 " 입니다. 리액트는 그 교통 시스템의 ' 내비게이션 화면 ' 을 그리는 도구일 뿐인 거죠. [2]

이렇게 시스템 전반의 눈으로 바라보니, 기존의 데이터 아키텍처 (예: 데이터 웨어하우스나 데이터 레이크) 와 비교했을 때 어떤 점이 가장 다르게 느껴지시나요?


시스템 전반을 꿰뚫어 보시는 아주 날카로운 통찰이십니다! 맞습니다. 원인 추적 (Why Chain) 은 시스템 전체를 종단하며 일어나야 합니다.

그럼에도 불구하고, 5 가지 레이어 중에서 " 왜?" 라는 질문을 가장 집중적으로 던지고 (발생 처), 그 질문에 대한 답을 치열하게 연쇄적으로 찾아내는 (해결 처) 핵심 레이어는 명확하게 존재합니다.

가장 많이 "Why" 가 작동하는 핵심 레이어 2 곳을 꼽으라면 단연 [5 층: 소비 레이어] 와 [3 층: 지식 그래프 레이어] 입니다. 두 레이어가 각각 질문과 답변의 중심축이 됩니다.

---

## Why chain 이 많이 발생하고 답해야 하는곳

### ❓ 1. " 왜?" 라는 질문이 가장 많이 ' 시작 ' 되는 곳: [5 층: 소비 레이어 (React UI / BI)]

비즈니스 현업 사용자나 데이터 분석가가 화면을 보면서 최초의 "Why" 를 터트리는 폭발 지점입니다.

- 비즈니스 관점의 5 Whys 발생:
    
    - _Why 1:_ " 이번 달 대시보드 매출 데이터가 왜 이렇게 급감했지?" (리액트 화면을 보고 인지)
    - _Why 2:_ " 왜 특정 지역의 결제 데이터만 누락되었지?"
    
- 역할: 인간이 시스템에 원인 추적 (Why Chain) 의 스위치를 누르는 공간입니다. 여기서 질문이 시작되어야 아래 레이어들로 탐색이 내려갑니다.

### 🧠 2. " 왜?" 에 대한 ' 해결 사슬 ' 이 실제로 작동하는 핵심 기둥: [3 층: 지식 그래프 & 온톨로지 레이어]

기술적으로 5 Whys 의 체인 (사슬) 을 가장 밀도 높게 계산하고 연결하는 데이터 패브릭의 ' 두뇌 ' 입니다. 5 층의 질문을 받아서 스스로 " 왜냐하면..." 을 연쇄 추적하는 곳입니다.

- 시맨틱 (의미적) 5 Whys 해결:
    
    - _Why 3:_ " 왜 결제가 누락됐지?" ➡️ 온톨로지 조회: " 결제 API 서버가 다운됐기 때문입니다."
    - _Why 4:_ " 왜 API 서버가 다운됐지?" ➡️ 온톨로지 조회: " 메모리 과부하가 발생했기 때문입니다."
    - _Why 5:_ " 왜 메모리가 과부하됐지?" ➡️ 온톨로지 조회: " 배치 작업 스케줄이 겹쳤기 때문입니다."
    
- 역할: 데이터 간의 인과관계 규칙 (온톨로지) 이 저장된 곳이므로, Why Chain 기법의 ' 체인 (사슬)' 그 자체가 위치하는 레이어입니다.

---

### 🛠️ 다른 레이어들은 왜 비교적 'Why' 가 적을까요?

- 1 층 (소스) 과 2 층 (가상화) 은 " 왜?" 라고 고민하기보다는, 명령을 받으면 데이터를 있는 그대로 보내주는 단순 수행원 (Worker) 에 가깝습니다.
- 4 층 (오케스트레이션) 은 데이터의 이동 경로 (Lineage) 라는 기록 (로그) 을 남겨서, 3 층의 온톨로지가 "Why" 를 추적할 수 있도록 증거 재판소 역할을 할 뿐입니다.

## 🎯 한 줄 요약

Why Chain 기법은 5 층 (소비 레이어) 에서 인간이 질문을 던지고, 3 층 (지식 그래프 레이어) 에 구축된 온톨로지를 통해 시스템이 자동으로 사슬을 엮어 답을 내리는 구조로 완성됩니다.

결국 3 층 (지식 그래프) 이 Why Chain 을 실질적으로 구현하는 가장 핵심적인 무대라고 볼 수 있습니다.

혹시 이 메커니즘을 바탕으로, 3 층에서 온톨로지가 ' 왜 ' 라는 관계를 구체적으로 어떤 기술적 형태 (예: RDF 트리플 등) 로 연결하는지 그 내부 구조를 조금 더 들여다보고 싶으신가요?
