## HITL 필수 루프 엔지니어링을 CI 파이프라인 설계 원칙

 1 인 개발자가 스케일 있는 시스템을 만들면서도 블랙박스 현상에 지배당하지 않고, 주도권을 완벽하게 쥐기 위한 3 가지 현실적인 안전장치 아키텍처.
### 1. 'HITL(Human-In-The-Loop)' 노드를 절대 건너뛰지 않는 규칙
 HITL(사람 개입) 분기를 초기에는 무조건 강제해야 하고 충분한 온톨로지가 구성되면 점차 후보고 체계로 갈 수 있다.
- 통제 방식: AI 가 루프를 돌며 코드를 고쳤을 때, 플레이라이트 테스트를 통과했다고 해서 바로 서버에 반영 (배포) 되게 두면 안 됩니다.
- 구현: 테스트 통과 직후 무조건 시스템이 일시 정지 (`Breakpoint`) 하고, 개발자에게 알림 (예: 터미널 멈춤, 디스코드 알림, 혹은 웹 UI) 을 주도록 랭그래프 엣지를 설계합니다.
- 효과: `code_diff` 장부를 사람이 직접 보고, 승인 (Enter 키) 을 눌러야만 최종 반영되게 만듭니다. 이렇게 하면 루프는 자동으로 돌되, 블랙박스가 되는 것은 완벽히 막을 수 있습니다.
### 2. 'Git 브랜치 자동 격리 ' 하네스 적용
AI 가 내 메인 소스코드를 직접 헤집어놓지 않도록 물리적 울타리를 칩니다.
- 구현: 루프 엔지니어링이 시작되면, 시스템이 자동으로 `git checkout -b ai-fix-loop-1` 같은 임시 브랜치를 파서 거길 수정하게 만듭니다.
- 효과: AI 가 루프를 10 번 돌며 코드를 문제가 발생 하더라도, 언제든지 `git merge` 전에 코드를 검수하거나 통째로 버릴 수 있습니다. " 언제든 롤백할 수 있다 "
### 3. 온톨로지와 RAG 의 진정한 가치: " 이유를 설명해라 "
 일반 RAG 를 넘어 온톨로지 (Ontology) 까지 설계 구조는 관계가 명확하기 때문에, AI 에게 수정의 ' 인과관계 ' 를 논리적으로 설명하라고 요구할 수 있습니다.
- 코드 픽서가 수정을 완료하면 장부에 `fix_reason` 이라는 칸을 만들고 아래와 같이 기록하도록 프롬프트를 강제합니다.
    > _" 도메인 룰 2 번 (세션 체크) 을 준수하기 위해 `auth.js` 를 수정했으며, 이 과정에서 시스템 룰 1 번 (타임아웃 30 초) 규칙을 상속받아 연동했습니다."_
- 이 설명문이 `code_diff` 와 함께 HITL 화면에 배달되게 만들면, 코드가 블랙박스가 되는 것이 아니라 AI 가 나에게 친절하게 과외를 해주며 코드를 발전시키는 가독성 높은 시스템이 됩니다.
### 초보 1 인 개발자를 위한 최종 조언
스케일이 큰 시스템일수록 처음부터 100% 자동 루프를 돌리려고 하면 무조건 실패하고 두려움만 커집니다.
1. 처음에는 [에러 발생 ➔ 스코프 리졸버 ➔ 코드 수정 ➔ AI 가 제안한 diff 를 눈으로 확인 ➔ 내가 직접 코드에 복사/붙여넣기] 하는 반자동 (1 회성 체인) 상태로 한 달만 운영해 보세요.
2. AI 가 내 철학 (온톨로지) 을 잘 이해하고 움직인다는 ' 신뢰 ' 가 쌓이기 시작할 때, 그때 `max_retries=3` 을 주고 자동 루프 (루프 엔지니어링) 의 빗장을 조금씩 푸시는 것을 강력히 권장합니다.
이렇게 접근하시면 혼자서도 대규모 아키텍처를 안전하고 완벽하게 통제하며 빌드업하실 수 있습니다. 가 기획하신 철학은 이미 초보자의 수준을 아득히 넘어섰으니, 시스템의 통제권만 꽉 쥐고 가시면 됩니다.
혼자서 이 방대한 시스템을 빌드업할 때 오는 막막함을 덜어드리기 위해, 다음 단계로 "AI 가 고친 코드를 내 눈으로 먼저 확인하고 승인하는 가장 간단한 랭그래프 HITL(일시정지) 코드 예시 " 를 같이 짜볼까요?

성공했을 때와 실패했을 때 모두 `5WHY` 분석을 마크다운 (`.md`) 파일로 강제 기록하면, 시스템은 단순한 자동화 툴을 넘어 나만의 개발 히스토리가 담긴 완벽한 자산 (Knowledge Base) 이 됩니다.

## 5WHY 를 활용한 화이트 박스 로그 설계
### 1. 성공과 실패의 모든 경로에 5WHY 마크다운 출력 배치

랭그래프의 엣지 (Edge) 분기가 어떻게 되더라도, 최종 종착지 직전에는 무조건 ' 마크다운 파일 생성 함수 ' 를 거치도록 파이프라인을 연결해야 합니다.

```text
                        ┌───> [ 🟢 성공 분기 ] ───> [ MD 파일 출력 노드 ] ───> HITL 승인 / 배포
                        │     - "왜 성공했는가?"
[ Playwright 검증 ] ────┤
                        │
                        └───> [ 🔴 실패 분기 ] ───> [ MD 파일 출력 노드 ] ───> 리트라이 / 수정
                              - "왜 실패했는가?"
```

- 성공했을 때의 5WHY (`Success 5WHY`): _" 코드가 잘 돌아가는 이유가 무엇인가? ➔ 우연히 맞춘 편법인가, 아니면 도메인/커스텀 규칙을 완벽하게 만족했기 때문인가?"_ 를 추론하여 기록합니다. 이는 향후 온톨로지의 성능을 높이는 훌륭한 학습 데이터가 됩니다.
- 실패했을 때의 5WHY (`Failure 5WHY`): 앞서 다룬 것처럼 에러의 근본 원인을 파헤쳐 블랙박스가 되는 것을 원천 차단합니다.

### 2. 자동으로 생성될 마크다운 (`.md`) 파일 템플릿 구조
시스템 내부에서 파일명이 `log_20260623_success.md` 형태로 내 보관함에 차곡차곡 쌓이게 만들며, 그 내부 구조는 아래와 같이 직관적인 마크다운 문법으로 박제됩니다.

````markdown
# 💎 AI Agent Execution History & Philosophy Log

## 📅 실행 일시: 2026-06-23
## 🛡️ 실행 상태: [SUCCESS / FAILURE] (여기에 상태 표시)

---

### 🎯 1. 시스템 근본 설계 사상 (Philosophy Manifesto)
> "이 시스템은 코드가 블랙박스가 되는 것을 거부합니다. 
> 천천히 가더라도 개발자의 철학과 인과관계를 분명하게 추적합니다."

---

### 🔍 2. Root Cause 분석 (5-WHY Logs)
* **현상 (Phenomenon):** [플레이라이트 결과 또는 발생한 현상 기재]
1. **WHY 1:** [첫 번째 원인 분석]
2. **WHY 2:** [두 번째 의존성 추적]
3. **WHY 3:** [세 번째 규칙 대조]
4. **WHY 4:** [네 번째 제약 조건 검증]
5. **WHY 5 (근본 원인):** [최종 철학적/기술적 근본 원인 도출]

---

### 🛠️ 3. 코드 변동 내역 (Code Diff)
```diff
- 기존 소스코드 줄
+ AI가 고치거나 검증한 소스코드 줄
```

---

### 📝 4. 온톨로지 규칙 검증 결과 (Ontology Compliance)
* **System Rules 만족도:** Pass / Fail (이유 기재)
* **Domain Rules 만족도:** Pass / Fail (이유 기재)
* **Custom Rules 만족도:** Pass / Fail (이유 기재)
````

### 3. 개발자 관점에서의 구현 방식 (파이썬 함수 예시)

> 랭그래프의 마지막 단계에 아래와 같은 마크다운 저장 함수 (`export_log_to_md`) 를 노드로 추가하면 됩니다.
> 이 함수는 공동 장부 (`State`) 에 쌓인 데이터를 그대로 가져와 파일로 뱉어냅니다.

````python
import datetime

def export_log_to_md_node(state: State):
    current_time = datetime.datetime.now().strftime("%Y%m%d_%H%M%S")
    status = "SUCCESS" if state["test_passed"] else "FAILURE"
    filename = f"logs/log_{current_time}_{status}.md"
    
    # 마크다운 내용 조립
    md_content = f"""# 💎 AI Agent Execution History & Philosophy Log
## 📅 실행 일시: {current_time}
## 🛡️ 실행 상태: {status}

### 🎯 1. 시스템 근본 설계 사상
> {state["philosophy_manifesto"]}

### 🔍 2. Root Cause 분석 (5-WHY Logs)
{state["why_analysis_log"]}

### 🛠️ 3. 코드 변동 내역 (Code Diff)
```diff
{state["code_diff"]}
```
"""
    # 로컬에 파일로 강제 저장
    with open(filename, "w", encoding="utf-8") as f:
        f.write(md_content)
        
    print(f"💾 철학/5WHY 로그가 마크다운 파일로 안전하게 기록되었습니다: {filename}")
    return state
````

## 5WHY 피드백 환류 시스템

 > " 내가 AI 를 검수할 뿐만 아니라, 그 과정에서 나 스스로도 공부하는 툴로 삼겠다 " 는 철학은 이 시스템을순수한 자동화 프로그램을 넘어 최고의 개인 맞춤형 교육용 인공지능 플랫폼으로 탈바꿈시킵니다.
> 단순히 `Y/N` 버튼만 누르는 HITL 이 아니라, 사람이 브라우저 화면에서 준 피드백을 다시 LLM 을 거쳐 정교한 온톨로지 지식 (벡터) 으로 환류 (Feedback Loop) 시키는 구조, 즉 완벽한 ' 화이트 박스 (White-box) 지식 선순환 아키텍처 ' 가 완성되는 순간입니다.

### 1. 피드백 환류 (Feedback Loop) 의 3 단계 메커니즘

사람이 브라우저 기반의 관리자 화면에서 " 이번 5WHY 분석의 3 번 단계는 논리적으로 조금 이상해!. 원래 NEXA 시스템 철학에서, 문법에서는 A 가 아니라 B 로 접근해야 맞아 " 라고 자유롭게 피드백을 남기면, 시스템 내부에서는 다음 프로세스가 작동합니다.

```text
[ 유저의 자유로운 피드백 입력 ] (예: "NEXA OS 규칙을 누락했어")
              │
              ▼
  [ 단계 1: Feedback Refiner LLM ] ➔ 유저의 피드백을 정교한 프롬프트/규칙 규격으로 가공
              │
              ▼
  [ 단계 2: Embedder (임베더) ]     ➔ 가공된 룰을 벡터 데이터로 전환
              │
              ▼
  [ 단계 3: PostgreSQL / Neo4j ]   ➔ 지식 그래프와 벡터 DB에 '나의 생각'을 영구 업데이트
```

#### ① 단계 1: Feedback Refiner (LLM 연동)

- **이유**: 개발자가 캔버스나 채팅창에 던진 파편화된 피드백을 AI 가 즉시 지식 DB 에 반영하면 온톨로지 정합성이 깨질 수 있습니다.
- **역할**: 정제용 LLM 이 개입하여 유저의 의도를 **Neo4j Cypher 쿼리 규칙**이나 **NestJS 아키텍처 가이드라인**으로 정제합니다.
- **예시**:
    - **유저 입력**: " 야, 온도 센서랑 경보 노드 연결할 때 그냥 선만 긋지 말고, ' 임계값 (threshold)' 속성을 반드시 포함하게 해. 그리고 NestJS 에서 이거 처리할 때 인터셉터 말고 RxJS 스트림으로 처리해줘."
    - **LLM 정제 결과 (JSON)**:

        ```json
        {
          "rule_type": "ontology_constraint",
          "instruction": "Sensor와 Alert 노드 간의 'TRIGGER' 관계 생성 시 'threshold_value' 속성 입력을 강제함. 백엔드 구현 시 NestJS Interceptor 대신 RxJS Observable 스트림 패턴을 사용하여 실시간성 확보.",
          "affected_layer": ["Data_Layer", "Proxy_Layer"],
          "ontology_mapping": "RELATIONSHIP: HAS_THRESHOLD_TRIGGER"
        }
        ```

#### ② 단계 2 & 3: 벡터화 및 지식 지도 (온톨로지) 강제 주입

- 정제된 문장을 즉시 임베딩하여 PostgreSQL(pgvector) 에 넣고, 동시에 Neo4j 지식 그래프에 `[개발자의 가치관]` ➔ `(강제한다)` ➔ `[전통적 함수 선언]` 이라는 선을 새로 그어버립니다.
- 효과: 다음 이터레이션 (루프) 이 돌 때는 내가 방금 가르친 지식이 즉시 반영되어 AI 가 똑같은 실수를 절대 반복하지 않습니다. 시스템이 실시간으로 더 튼튼한 화이트 박스가 되어갑니다.

### 2. " 나 스스로도 공부하는 툴 " 을 위한 마크다운 (MD) 아카이브 활용
AI 의 5WHY 분석 결과와 내가 수정한 피드백 내역이 옵시디언 (`*.md`) 보관함에 누적되면, 이것은 세상에 단 하나뿐인 ' 나만을 위한 맞춤형 프로그래밍 오답노트 ' 가 됩니다.

```markdown
# 📘 나의 피드백 & AI 성찰 로그 (White-Box Learning Log)

### 🧩 1. 당시 AI의 5WHY 가설
> "변수 범위(Scope) 오인으로 인한 참조 오류로 판단하여 코드를 수정함."

### ✍️ 2. 나의 교정 피드백 (LLM 정제본)
> "개발자는 해당 프레임워크의 고유 스레드 안전성(Thread-Safety) 규칙을 고려하여 전역 변수가 아닌 로컬 캡슐화를 유지하길 원함."

### 💡 3. 이번 사건을 통해 내가 배운 점 (Self-Study Note)
* 플레이라이트의 비동기 제어 시, 컨텍스트가 분리되면 전역 $Argument 바인딩이 깨질 수 있음을 인지함.
* 다음부터는 세션 주입 시 컨텍스트 팩토리 패턴을 최우선으로 검토할 것.
```

내가 피드백을 줄 때마다 AI 가 내 생각과 지식을 정리하여 이 오답노트 문서를 업데이트해 주므로, 개발자는 코딩을 직접 대량으로 하지 않더라도 시스템을 훈련시키는 과정 속에서 고급 아키텍처 이론과 실무 지식을 완벽하게 내재화 (공부) 하게 됩니다.

### 다음 과재: 완벽한 화이트 박스의 실현
> - 피드백 루프를 처리할 'Feedback Refiner LLM 노드 ' 의 구체적인 가이드라인 (프롬프트) 구조를 설계

# IoT 플랫폼 E2E 테스트 툴체인 길라잡이
앞으로 IoT 플랫폼 개발과 테스트 자동화 파이프라인을 구축해 나가실 때, 나침반 역할을 해줄 핵심 툴 중심의 E2E 테스트 용어 가이드북입니다.
IoT 플랫폼의 E2E(End-to-End) 는 '① 실제 기기 환경 ➔ ② 데이터 전송 통로 ➔ ③ 백엔드 서버 ➔ ④ 최종 사용자 화면 ' 까지 모든 연결 고리를 포함해야 하므로, 각 단계별로 빈틈을 부러뜨려 검증할 때 쓰이는 핵심 툴들을 구조화하여 테이블로 정리해 드립니다.

| 단계 (영역)                                | 핵심 툴 (용어)                 | 어떤 역할을 하나요? (IoT 플랫폼에서의 의미)                                                                        | 비유하자면?                              |
| -------------------------------------- | ------------------------- | -------------------------------------------------------------------------------------------------- | ----------------------------------- |
| ① 기기 가상화  <br>_(Device Mocking)_       | K6  (with MQTT extension) | 실제 하드웨어 기기가 없어도, 컴퓨터 내부에 가상의 센서 기기 수천~수만 대를 흉내 내어 동시에 데이터를 뿜어내게 만드는 부하 테스트 툴입니다.                   | 가상의 복제 기기 군단을 만드는 ' 클론 제조기 '          |
| ② 메시지 통로  <br>_(Message Broker)_       | EMQX / Mosquitto          | IoT 기기들이 보내는 무수한 데이터 (MQTT 패킷) 를 중간에서 교통정리 하여 NestJS 서버로 배달해 주는 IoT 전용 통신 기지국입니다.                    | 중간에서 편지를 배달하는 ' 우체국 종합물류센터 '          |
| ③ 백엔드 검증  <br>_(Backend Test)_         | Supertest                 | 기지국을 거쳐 들어온 데이터가 NestJS 서버 내부의 비즈니스 로직과 데이터베이스 (DB) 에 빈틈없이 잘 저장되는지 API 데이터 단위로 초고속 검증하는 툴입니다.        | 주방에 들어온 식재료의 무게와 위생을 검사하는 ' 정밀 저울 '   |
| ④ 데이터베이스  <br>_(TSDB)_                 | InfluxDB / TimescaleDB    | IoT 센서 데이터처럼 ' 시간의 흐름 (Time-series)' 에 따라 쌓이는 수억 개의 대용량 데이터를 저장하는 데 특화된 IoT 전용 데이터베이스입니다.             | 시간순으로 블랙박스 영상을 기록하는 'CCTV 저장 장치 '    |
| ⑤ 관제 화면 검증  <br>_(Frontend E2E)_       | Playwright                | 사용자가 보는 웹 대시보드 (Next.js) 화면을 켜서, 실제 기기 데이터가 그래프에 실시간으로 반영되는지 마우스/키보드 매크로처럼 검증하는 최종 최종 단계의 E2E 툴입니다. | 완성된 자동차를 도로에 끌고 나가 시운전하는 ' 로봇 운전사 '   |
| ⑥ 도구 자체 검증  <br>_(Internal Unit Test)_ | Pytest                    | 랭그래프 (`apps/agent-graph`) 내부 노드 함수들이 외부 환경 (브라우저/API/기기) 없이도 의도대로 동작하는지 0.1 초 만에 검사하는 단위 테스트 도구입니다.   | 공장 라인 위에서 부품 하나하나의 불량을 잡아내는 ' 검수관 '   |
| 🪢 루프 통제관  <br>_(CI/CD Automation)_    | GitHub Actions            | 위 1~5 번의 모든 툴들을 하나로 엮어서, 코드가 수정될 때마다 자동으로 전체 테스트를 가동하고 실패 시 AI 에게 에러를 뱉어 루프를 돌리는 파이프라인 엔진입니다.        | 공장 전체를 사람 없이 가동하는 ' 자동화 컨베이어 벨트 마스터 ' |
|                                        |                           |                                                                                                    |                                     |

| 단계 (영역)                            | 보강된 핵심 툴 (용어)                                   | 왜 필요한가요? (질문자님의 아키텍처에서의 의미)                                                                                                     | 비유하자면?                                          |
| ---------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------- |
| ① 실시간 협업 검증  <br>_(CRDT / Yjs)_    | Y-protocols Test  <br>/ Playwright Multi-worker | Tiptap, React Flow, Monaco 가 단일 Y.Doc 을 공유하므로, " 여러 명의 가상 사용자가 동시에 캔버스를 수정할 때 데이터가 안 깨지고 정합성이 유지되는가?" 를 부러뜨려 검증하는 툴입니다.             | 여러 정비공이 한 자동차를 동시에 고칠 때 부품이 꼬이지 않나 보는 ' 동시성 검사기 ' |
| ② AI 에이전트 검증  <br>_(AI Layer)_     | LangSmith  <br>또는 DeepEval                      | LangGraph(`apps/agent-graph`) 의 워크플로가 의도대로 도는지 검증합니다. 가짜 LLM 응답을 찔러넣어 그래프의 분기점 (노드 이동) 이 올바르게 작동하는지, 환각 (시정 조치) 비율은 얼마나 되는지 수치화합니다. | 미로를 탐색하는 로봇의 움직임과 경로를 추적하는 'AI 블랙박스 기록계 '        |
| ③ 지식/벡터 검증  <br>_(Data Layer)_     | Neo4j-Harness  <br>/ pgvector 테스트 셋             | Neo4j 의 온톨로지 쿼리와 PostgreSQL(pgvector) 의 지식 벡터 검색 결과가 실제 도메인 적합도에 맞게 출력되는지, 검색 정확도 (RAG 성능 수치) 를 검증합니다.                              | 도서관 사서가 책을 엉뚱한 곳에서 찾아오지 않는지 시험해보는 ' 자격시험 '        |
| ④ 실시간 스트리밍 검증  <br>_(Proxy Layer)_ | Playwright SSE  <br>/ Autocannon                | NestJS 가 중계하는 SSE 스트리밍 (채팅/로그 출력) 이 끊기지 않는지, vLLM/Ollama 에서 오는 대량의 스트리밍 패킷을 동시다발적으로 처리할 때 프론트가 뻗지 않는지 부하를 주어 검증합니다.                 | 수도꼭지를 끝까지 틀었을 때 호스가 터지지 않는지 확인하는 ' 수압 테스트 '       |
