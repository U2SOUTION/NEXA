# 시스템 - 음성학습 툴 로직 Flow 와 기술 스택 (Tech Stack)

펌웨어 전체를 다시 굽지 않고, 음성 모델 파일만 바꿔 끼우는 구조입니다. 목소리는 서버에서 배우고, 로터는 완성된 파일을 받아서 실행합니다. 파일을 내려 받아 다시 읽는 구간은 짧게 끝나는 것이 목표이고, 그 시간이 몇 초인지는 현장 무선을 재보고 적습니다. 학습 버튼부터 모델이 나오기까지는 그보다 깁니다.

Rotor 의 평소 조종 링크는 **ESP-NOW** 입니다. 모델 다운로드는 그 링크에 싣지 않고, 조종을 쉬고 있을 때만 Wi-Fi 로 받습니다.

## 1. 시스템 아키텍처 및 기술 스택 (Tech Stack)

| 레이어 | 기술 스택 / 라이브러리 | 주요 역할 |
| :--- | :--- | :--- |
| **프론트엔드 (Web UI)** | Vue.js / React / Svelte, **Web Audio API**. 작업대 최초 주입만 **Web Serial API** (`esptool-js`) | 키워드 표, 음성 녹음 (16 kHz, Mono), 학습 시작, 적용 상태 표시 |
| **백엔드 (Node.js)** | Express / NestJS, Multer, 작업 큐, 필요하면 Python `child_process` | 녹음 보관, 학습 작업을 하나씩 돌리기, 완성된 `.tflite` 와 체크섬 서빙 |
| **학습 엔진 (AI)** | **Python**, **TensorFlow / Keras**, Librosa | 기기와 같은 MFCC, 가벼운 CNN 학습, **INT8 TFLite** 로 변환 |
| **임베디드 (ESP32-S3)** | **ESP-IDF**, PSRAM 있는 모듈, **TFLite Micro**, LittleFS | 정비 구간에만 모델 수신. 청취 중에만 추론. 실패하면 펌웨어 기본 모델 |

### 1.1 통신은 두 갈래로 둡니다

평소 조종은 ESP-NOW (목표 지연 10 ms 안쪽) 또는 CAN 입니다. 이쪽에는 키워드 ID 만 타고, 음성과 모델 파일은 타지 않습니다. 현장 중계가 필요하면 그 조종은 플랫폼 문서대로 로컬 서버가 맡습니다.

음성 모델은 로컬 서버가 아니라 **외부 웹 플랫폼**에서 받습니다. 녹음과 학습이 끝난 `.tflite` 가 거기에 있기 때문입니다. 로터가 무장 해제이고 `LISTEN_OFF` 인 정비 구간일 때만 Wi-Fi 로 플랫폼의 모델 API 를 당겨 옵니다. 받기가 끝나면 Wi-Fi 는 접고, 조종은 다시 ESP-NOW 입니다. 홈 공유기에 상시로 붙어 있으면서 조종 전파와 무전기를 나누어 쓰지 않습니다. 브라우저가 로터에게 직접 " 가져가라 " 고 HTTP 를 보내지도 않습니다. 플랫폼에 준비됨만 표시되고, 로터가 정비 구간에 당겨 갑니다. 플랫폼에 붙지 못하면 받기를 그만두고, 지금 들어 있는 모델이 없으면 공장 기본 모델을 유지합니다.

## 2. 전체 흐름

### Phase 1 — 베이스 펌웨어를 처음 넣을 때

밀봉된 로터를 쓸 때마다 하는 일은 아닙니다. 작업대에서 빈 보드에 공용 펌웨어를 한 번 넣는 절차입니다.

1. ESP32-S3 를 PC 에 USB 로 연결하고, 브라우저에서 기기 연결을 누릅니다 (Web Serial).
2. 서버에 미리 빌드해 둔 베이스 펌웨어를 받아 `esptool-js` 로 넣습니다. 이 이미지 안에 **기본 음성 모델 10 어** 가 들어 있습니다. Left / Right / Center, Up / Down, Go / Stop / Home / Pause / Cancel 입니다. 서버 파일만 믿고 기본 모델을 빼지 않습니다.
3. LittleFS 모델 칸을 포맷해 둡니다. 나중에 커스텀 `.tflite` 가 여기 앉습니다.

와이파이 비밀번호나 서버 IP 를 NVS 에 박아 두고 상시 접속하지 않습니다. 정비 모드에서 외부 웹 플랫폼에 그 자리에서만 붙습니다.

### Phase 2 — 목소리 모으기, 배우기

이 표는 **장비 하나** 기준입니다. 로터를 다른 장비에 페어링하면 그 장비의 표로 바뀝니다. 목소리는 로터에 남는 모델이고, " 이 말을 들으면 무슨 동작을 할지 " 는 장비 프로필입니다.

1. 기본어 10 개의 말과 ID 는 고정입니다. 코어는 Left / Right / Center (ID `1`~`3`) 이고, 나머지는 Up / Down / Go / Stop / Home / Pause / Cancel (ID `4`~`10`) 입니다. 이 10 어와 ID 구간은 Rotor 의 `VOICE_KEYWORD_DEFAULT` 와 같고, `11`~`15` 도 그쪽 예약과 같습니다. 목록을 못 읽었을 때 다시 켜는 것은 그중 코어 3 어뿐입니다. 이 장비에서 안 쓰는 기본어는 표에서 지우는 대신 **끕니다.** 끈 말은 인식 후보에서 빠져서, 안 쓰는 말이 확률을 가져가지 않습니다. 다시 켤 수 있게 행은 남습니다. Stop 은 말로 하는 정지이고, 빨간 버섯 스위치의 비상 정지를 대신하지 않습니다.
2. 커스텀은 공장 모델에 없는 말을 쓰고 싶을 때만 둡니다. `[+ 키워드 추가]` 로 늘리고, ID 는 `16`~`35` 입니다. 칸 수는 **20 − 지금 켜 둔 기본어 수** 입니다. 기본 10 어를 모두 끄면 커스텀 20 칸을 다 씁니다. 10 어를 모두 켜면 커스텀은 10 칸입니다. 예: " 왼쪽 ", " 치즈 ". ID `11`~`15` 는 나중에 기본어를 더할 자리라 비워 둡니다.
3. 커스텀 칸마다 웹에서 녹음합니다. Web Audio API 가 `16 kHz, 16-bit, Mono` 로 맞춥니다. 한 클립은 1 초 안쪽입니다. 5 번만 받아도 화면 데모는 보이지만, 내 목소리에 맞추려면 **칸마다 8~15 번**이 출발점입니다. 여러 사람이나 양봉장 소음까지 커버하려면 더 받습니다.
4. 서버는 그 녹음에 표준 무음·소음·다른 말 (거절 클래스) 을 섞습니다. 이번 장비에서 **켜 둔** 기본어 음성만 같이 넣습니다. 끈 기본어는 모델 클래스에 넣지 않습니다.
5. 학습이 끝나면 INT8 `.tflite`, 체크섬, 라벨 표가 나옵니다. 분류 출력은 연속 인덱스 `0` 부터라 `keyword_id` 와 같지 않습니다. 라벨 표가 인덱스를 ID 로 바꿉니다. 예를 들면 `class 0 → keyword_id 1`, `class 3 → keyword_id 16` 입니다. 거절 클래스는 ID 가 없어서 `0x2B` 로 나가지 않습니다.
6. 발행 전에, 가능하면 **로터 본체 마이크**로 칸마다 몇 번 말해 봅니다. 학습 마이크는 PC 이고 현장 마이크는 INMP441 이라, 서버에서 잘 맞던 칸도 로터에서는 놓칠 수 있습니다. 놓치는 칸만 다시 녹음해서 같은 작업을 한 번 더 돌립니다.

글자만 NVS 에 넣어서는 새 발음이 생기지 않습니다. 새 발음은 이 커스텀 모델이 있을 때만 알아듣습니다. 커스텀을 배우지 않으면, 그 장비 표에서 켜 둔 기본어만 페어링됩니다.

### Phase 3 — 모델만 내려받기

1. 웹에서 적용을 누르면 서버는 그 로터용 `custom.tflite`, 체크섬, 라벨 표를 준비합니다. 동작 매핑 JSON 은 **장비** 쪽으로 가고, 로터로는 모델과 라벨만 갑니다.
2. 로터는 조종을 쉬고 `LISTEN_OFF` 인 동안 외부 웹 플랫폼의 `GET /api/rotors/:id/model.tflite` 를 당겨 옵니다.
3. LittleFS 에 임시 이름으로 받은 뒤, 크기와 체크섬이 맞으면 `custom.tflite` 로 바꿉니다. 반쪽 파일은 올리지 않습니다.
4. 맞으면 인터프리터를 새로 붙여 PSRAM 으로 읽습니다. 재부팅 없이 갈아끼우는 것이 목표입니다. 붙이다가 실패하거나 서명이 틀리면 그 파일은 버리고, **펌웨어 안의 기본 모델**로 돌아갑니다. 청취를 다시 열기 전에는 `LISTEN_OFF` 입니다.
5. 다음 페어링에서 장비는 `VoiceKeywordList` 를 보냅니다. 켤 기본어는 `count` 에 넣지 않고 `enabledDefault` (`uint16`, bit0 = ID 1 … bit9 = ID 10) 에만 싣습니다. `count` 와 `item[]` 은 커스텀만입니다. 필드 정의는 Rotor 문서의 구조체와 같습니다. 로터 NVS 에는 그 `deviceID` 벌만 둡니다. 목록을 못 읽으면 코어 3 어 Left / Right / Center 만 나갑니다. 커스텀이 0 칸인 것도 정상입니다.

## 3. 구현할 때 챙길 것

**LittleFS 칸.** `partitions.csv` 에 모델용 파티션을 1MB~2MB 정도 잡아 둡니다. 파일 자체는 보통 그보다 작습니다 (수십~수백 KB 를 기대하고, 학습 결과로 확정합니다). 칸은 여유 공간입니다.

**MFCC 숫자는 서버와 기기가 같습니다.** 시작값은 16 kHz, 창 25 ms, 홉 10 ms, 멜 밴드 40, 클립 1 초입니다. Librosa 기본값에 맡기지 않습니다. 이 숫자 중 하나를 바꾸면 학습 스크립트와 펌웨어를 같이 바꿉니다. 여기가 어긋나면 서버 정확도는 로터에서 재현되지 않습니다.

**파일에서 모델 읽기.** 배열로 펌웨어에 박지 않고, 커스텀 파일이 검증된 뒤에만 이렇게 올립니다.

```cpp
// 체크섬이 맞는 custom.tflite 만 연다. 실패하면 펌웨어 기본 모델로 남긴다.
File modelFile = LittleFS.open("/custom.tflite", "r");
size_t modelSize = modelFile.size();
uint8_t* modelBuffer = (uint8_t*)ps_malloc(modelSize);
modelFile.read(modelBuffer, modelSize);
modelFile.close();

model = tflite::GetModel(modelBuffer);
// AllocateTensors 가 실패하면 modelBuffer 를 버리고 기본 인터프리터를 유지한다.
```

추론은 가장 높은 점수를 바로 채택하지 않습니다. 거절 클래스가 이기거나 `VOICE_CONFIDENCE_MIN` 을 못 넘기면 `0x2B` 를 보내지 않습니다. 청취가 꺼져 있으면 이 인터프리터도 돌리지 않습니다.

**INT8 만 배포합니다.** Float32 파일은 로터에 내리지 않습니다. 정수로 줄이면 파일이 작아지고, ESP32-S3 의 벡터 명령을 타는 커널이면 추론도 가벼워집니다. 레이어는 Depthwise Separable 처럼 TFLite Micro 가 지원하는 것만 씁니다. 몇 밀리초인지는 보드에서 재봅니다.

## 4. 디폴트와 커스텀

- **그냥 쓰는 사람.** 공장 모델 안에서 이 장비에 필요한 기본어만 켭니다. 나머지는 꺼 둡니다. 커스텀 녹음은 없습니다.
- **내 말, 내 단어를 쓰고 싶은 사람.** 끈 기본어가 비운 칸까지 포함해, 켠 기본어와 합쳐 20 칸 안에서 녹음하고 서버가 커스텀 `.tflite` 를 만듭니다. 기본어가 하나도 필요 없으면 커스텀 20 칸만으로 모델을 만듭니다. 학습이 실패하거나 파일을 못 받으면 코어 3 어만 남습니다.

```text
storage/
├── defaults/
│   └── corpus/                         # 기본어 학습용 음성. 폴백 모델은 펌웨어 안
└── rotors/
    └── rotor_<controller_id>/
        ├── custom.tflite               # 검증된 뒤에만 이 이름
        ├── model.sha256
        └── audio_dataset/
            ├── kw_16/                  # "왼쪽" 같은 커스텀 칸
            └── background/             # 무음, 소음, 다른 말
equipment/
└── <deviceID>/
    └── voice-map.json                  # 장비 동작 매핑. 로터로 안 보냄
```

목소리 파일은 그 사용자 것만 보관하고, 학습이 끝난 뒤 얼마나 둘지는 따로 정합니다. 모델 다운로드 API 는 그 로터 인증이 있을 때만 엽니다.

## 5. 파이썬 학습

웹에서 **나만의 모델 학습 시작** 을 누르면 Node 가 녹음을 저장하고 작업을 큐에 넣습니다. 개발 중에는 `child_process` 로 바로 파이썬을 붙여도 됩니다. 여러 대가 동시에 누르면 한 번에 하나씩 돌립니다. 웹 요청 안에서 학습을 끝내지 않습니다.

1. **특징.** 위 MFCC 숫자로 1 초 클립을 같은 크기의 특징 맵으로 만듭니다. 원본 WAV 를 로터에 넣지 않습니다.
2. **모델.** 1D/2D CNN 또는 Depthwise Separable 2~3 단의 작은 분류기입니다. 클래스마다 내 녹음과 함께 무음·소음·다른 말을 넣습니다. 안 그러면 아무 소리나 키워드로 찍습니다.
3. **변환.** Float32 로 배운 뒤 INT8 로 양자화해 `.tflite` 를 만듭니다. 같이 만드는 라벨 표는 클래스 인덱스에서 `keyword_id` 로 가는 표입니다. 클래스 번호를 ID 로 쓰지 않습니다.

## 6. 무선으로 넣는 순서

범용 모드나 커스텀 모드나, 로터 입장에서 파일 받는 동작은 같습니다. 커스텀 파일이 검증되지 않으면 공장 모델을 계속 씁니다.

1. 서버는 `custom.tflite` + 체크섬 + 라벨을 로터 폴더에, `voice-map.json` 은 장비 폴더에 둡니다.
2. 로터가 정비 구간에 외부 웹 플랫폼에서 모델과 라벨을 당겨 LittleFS 에 안전하게 바꿉니다.
3. 로드에 성공하면 그 모델로 듣습니다. 추론이 낸 클래스 인덱스를 라벨 표로 `keyword_id` 로 바꾼 뒤, 그 ID 가 장비의 활성 목록에 있을 때만 보냅니다. `voice-map.json` 의 동작 이름은 장비가 읽습니다.

## 7. 키워드 매핑 표

로터는 알아들은 **키워드 ID** 만 ESP-NOW/CAN 의 `0x2B` 로 던지는 입력 장치로 둡니다. 동작을 고르는 표는 웹에 두고, 저장은 장비 프로필로 갑니다.

표는 장비 하나를 연 상태에서 행을 추가, 수정, 삭제합니다.

| 키워드 | ID | 장비 동작 | 상태 | 관리 |
| :--- | ---: | :--- | :--- | :--- |
| **Left** | 1 | 장비가 정함. 말은 고정 | 켤 수 있음 | 동작 수정, 끄기/켜기 |
| **Right** | 2 | 장비가 정함. 말은 고정 | 켤 수 있음 | 동작 수정, 끄기/켜기 |
| **Center** | 3 | 장비가 정함. 말은 고정 | 켤 수 있음 | 동작 수정, 끄기/켜기 |
| **Up** | 4 | 장비가 정함. 말은 고정 | 이 장비에서 끔 | 동작 수정, 끄기/켜기 |
| **Down** | 5 | 장비가 정함. 말은 고정 | 이 장비에서 끔 | 동작 수정, 끄기/켜기 |
| **Go** | 6 | 장비가 정함. 말은 고정 | 이 장비에서 끔 | 동작 수정, 끄기/켜기 |
| **Stop** | 7 | 장비가 정함. 말은 고정. 비상 정지 아님 | 이 장비에서 끔 | 동작 수정, 끄기/켜기 |
| **Home** | 8 | 장비가 정함. 말은 고정 | 이 장비에서 끔 | 동작 수정, 끄기/켜기 |
| **Pause** | 9 | 장비가 정함. 말은 고정 | 이 장비에서 끔 | 동작 수정, 끄기/켜기 |
| **Cancel** | 10 | 장비가 정함. 말은 고정 | 이 장비에서 끔 | 동작 수정, 끄기/켜기 |
| **왼쪽** | 16 | 좌회전 미세 보정 | 학습 필요 | 녹음/학습, 삭제 |

- 기본 10 행은 말과 ID 를 바꾸거나 표에서 없애지 않습니다. 이 장비에서 끄면 인식 후보에서 빠지고, 그 칸 수만큼 커스텀을 더 넣을 수 있습니다. 행은 남아 다시 켤 수 있고, 다시 켜면 커스텀 여유가 줄어듭니다. ID `11`~`15` 는 나중에 기본어를 늘릴 자리라 비워 둡니다.
- 커스텀 행은 기본 10 어에 없는 말만 적습니다. **녹음/학습** 으로 그 칸의 목소리를 받습니다. 추가 버튼은 켠 기본어와 커스텀의 합이 20 이 되면 닫힙니다. 기본어를 모두 끈 장비는 커스텀만 20 개까지 둡니다.
- 목록을 읽지 못하면 Left / Right / Center 만 다시 켜집니다.
- 인식률 칸은 시험 녹음이나, 장비가 올려 준 최근 점수를 보여 주기 위한 것입니다. 조종 패킷에 점수를 실어 보내지는 않습니다. `0x2B` 에 confidence 를 넣으려면 Rotor 문서 쪽 패킷을 그때 늘립니다.

`voice-map.json` 은 대략 이런 모양입니다. `action` 은 장비 안의 동작 이름이고, 로터가 보내는 패킷이 아닙니다.

```json
{
  "deviceID": 4097,
  "version": 104,
  "modelRev": "custom-104",
  "mappings": [
    {
      "keyword_id": 1,
      "keyword_text": "Left",
      "is_custom": false,
      "enabled": true,
      "action": "STEER_LEFT"
    },
    {
      "keyword_id": 7,
      "keyword_text": "Stop",
      "is_custom": false,
      "enabled": false,
      "action": "HALT"
    },
    {
      "keyword_id": 16,
      "keyword_text": "왼쪽",
      "is_custom": true,
      "action": "NUDGE_LEFT"
    }
  ]
}
```

`modelRev` 는 로터에 올라간 OTA `.tflite` 버전과 같은 값이고, `version` 은 동작 매핑만 바꿀 때 따로 올라가는 표 개정입니다.

`keyword_id: 16` 이 맞으면 로터는 `0x2B` 에 16 만 실어 보냅니다. 청취가 켜져 있고, 그 `deviceID` 의 화이트리스트와 confidence 를 통과할 때만입니다. 100 Hz 코어 스트림과는 섞지 않습니다. " 왼쪽이면 좌회전 " 은 장비가 `action` 을 보고 합니다.

```text
[장비 표에서 "왼쪽" 추가]
        │
        ▼
[브라우저 녹음]  칸마다 8~15회, 16 kHz
        │
        ▼
[서버 큐]  기본어 음성 + 내 녹음 + 무음/소음  →  INT8 custom.tflite
        │
        ▼
[로터 마이크로 확인]  놓치는 칸만 다시 녹음
        │
        ▼
[정비 구간]  LISTEN_OFF, Wi-Fi 로 외부 웹에서 모델만 수신
             체크섬 실패·플랫폼 단절 → 펌웨어 기본 모델
        │
        ▼
[페어링]  장비가 VoiceKeywordList 를 보내고
          로터는 ID 만 0x2B 로 돌려 보냄
```

말 한마디의 뜻은 장비 표에서 고치고, 로터는 그 말을 몇 번인지 알려 주는 쪽으로 두면 됩니다. 펌웨어를 매번 다시 굽지 않아도, 새 발음은 모델 파일로, 장비마다 다른 동작은 매핑 파일로 나뉩니다.




## 장기플랜 : 진정한 음성 지원을 위한 로드맵

### 현제 NEXA Rotor 의 음성 위치

| 항목 | 현재 스펙 | 한계 |
|---|---|---|
| 마이크 | INMP441 (본체) + `VOICE_EXT_MIC` (유선 플러그인) | 무선 스트리밍 없음 |
| 인식 | 키워드 스팟팅 (화이트리스트 ID) | 자연어/문장 인식 불가 |
| 출력 | 키워드 ID 만 송신, TTS 없음 | 피드백은 LED/진동/피에조 |
| 노이즈 | `VOICE_NOISE_GATE_DB`, `STEREO_BF` (빔포밍) | AEC/노이즈 캔슬링 미흡 |
| 서버 | 외부 웹 플랫폼 (모델 OTA) | 로컬 서버에서 STT/TTS 처리 없음 |

### 진정한 음성 지원을 위한 3 단계

#### 1 단계: 무선 스트리밍 마이크
- **현재**: Rotor 마이크는 I2S(INMP441), 오디오 스트림 미송신 (문서 원칙).
- **필요**: Rotor 가 오디오를 **Wi-Fi/ESP-NOW 스트림**으로 로컬 서버에 전송. 또는 별도 무선 마이크 모듈.
- **충돌**: 문서의 “오디오 스트림 미송신” 원칙과 정면 충돌. → 원칙 변경 또는 별도 오디오 채널 필요.

#### 2 단계: 노이즈 제거 (AEC + NS)
- **현재**: `VOICE_NOISE_GATE_DB`, `STEREO_BF` (빔포밍).
- **필요**: AEC (에코 캔슬링), NS (노이즈 서프레션), AGC (자동 게인). ESP32-S3 에서는 연산 부담 → 로컬 서버 또는 클라우드에서 처리.
- **현실**: ESP32-S3 에서 실시간 AEC 는 가능하지만 품질 한계. 로컬 서버 (라즈베리 파이/PC) 에서 처리가 현실적.

#### 3 단계: TTS (Text-to-Speech)
- **현재**: TTS 없음. 피드백은 LED/진동/피에조.
- **필요**: 로컬 서버에서 TTS 생성 → 오디오 스트림으로 Rotor 스피커 (또는 PC 스피커) 출력.
- **Rotor 하드웨어**: 스피커/앰프 미장착. TTS 출력은 PC 스피커 또는 별도 오디오 모듈 필요.

### 현실적 로드맵

| 단계 | 기간 | 내용 | Rotor 변경 |
|---|---|---|---|
| **1 (현재)** | 완료 | 키워드 스팟팅 + PTT 트리거 | 없음 (문서 원칙 유지) |
| **2 (단기)** | 3~6 개월 | PC 마이크 + 호스트 STT → 키보드 타이핑 | Rotor = PTT 트리거만 |
| **3 (중기)** | 6~12 개월 | Wi-Fi 오디오 스트림 + 로컬 서버 AEC/NS + STT | 오디오 스트림 채널 추가 (문서 원칙 변경) |
| **4 (장기)** | 12 개월 + | 로컬 TTS + 스피커 출력 + 양방향 음성 | Rotor 하드웨어 (스피커) 추가 |

### 핵심 제약

1. **오디오 스트림 미송신 원칙** — 1 단계에서 깨야 함. ESP-NOW 대역폭 부족 → Wi-Fi 별도 채널 필요.
2. **ESP32-S3 연산 한계** — AEC/NS/STT/TTS 모두 로컬 서버로 오프로드.
3. **Rotor 하드웨어** — 스피커/앰프 미장착. TTS 출력은 PC/별도 모듈.
4. **배터리** — 무선 스트리밍 + Wi-Fi 상시 접속 = 전력 소모↑. 배터리 용량 재검토.

### 한 줄 결론

> **진정한 음성 지원은 Rotor 단독으로는 불가능합니다.**
> Rotor 는 **PTT 트리거 + 키워드 ID 송신**에 한정하고,
> **무선 오디오 스트림 + 로컬 서버 AEC/NS/STT + TTS** 를 별도 계층으로 추가해야 합니다.
> 이는 Rotor 문서의 “오디오 스트림 미송신” 원칙을 깨는 **대규모 아키텍처 변경**이므로, 단계적으로 접근하는 것이 현실적입니다.
