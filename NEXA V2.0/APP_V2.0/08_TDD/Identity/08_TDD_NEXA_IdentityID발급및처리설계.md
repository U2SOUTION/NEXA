# NEXA-OS 의 지식 기반 기초인 Identity ID 발급 처리 설계

**Identity ID(영혼 ID)**의 발급과 관리는 단순히 글자를 대조하는 수준을 넘어, **형식·절차의 결정론적 규칙 + 통계적으로 유일한 난수 ID**와 **인공지능 기반의 유연한 맥락 해석 (Probabilistic)**이 결합된 **' 하이브리드 방식 '**으로 이루어집니다.

> 어떤 원리를 통해 " 실제 의미 " 와 " 지능 " 이 협력하여 ID 를 관리하는지 그 핵심 메커니즘.

**문서 범위:** 본 문서는 **외부에 직접 노출되는 고객 대면용 자료가 아니다.** 내부 저장소에서 구현·운영·거버넌스 근거로 쓰는 **기획·설계 SSOT**이다. **근간 기획문서**와 `identity_id` **역주입 대상 문서**도 **비공개 지식 자산**(팀 리포·내부 위키 등) 을 전제로 하며, 공개 채널에 실을 내용은 **별도 편집·승인 경로**를 둔다.

**상호 참조 (SoT 계층):**

- **Knowledge OS 운영·API·크롤러·감사·신뢰도·불변 토큰 큐:** [`08_TDD_Knowledge_지식운영체제_API운영정책`](../Knowledge/08_TDD_Knowledge_지식운영체제_API운영정책.md) — 본 문서는 **영혼 원장 (`nexa_identities`)**에 특화한다. **용어 CRUD, `nexa_knowledge_vectors` UPSERT, 문서 `anchor_id` 동기화, `nexa_knowledge_audit_logs`, STUCK/ASK 임계값** 등의 **계약·흐름**은 위 문서 및 DDL 명세를 따른다. 상위 경계 요약은 동일 문서 **§0-A**를 본다.
- **Capability ID(`nexa.*` 네임스페이스):** [`08_TDD_NEXA_CapabilityID체계_발급및Tier접근권한`](./08_TDD_NEXA_CapabilityID체계_발급및Tier접근권한.md) — **기능 자격·액션 계층**이다. **`domain_tags`(메인 메뉴·플랫폼 도메인 레지스트리)** 와는 **별도 축**이며, 자동 1:1 매핑을 전제로 하지 않는다.

## 1. 하이브리드 발급 체계: 뼈대는 ' 코드 ', 근육은 'AI'

시스템의 주소인 ID 자체는 무결해야 하므로 발급 과정에서 역할을 철저히 분리합니다.

- **ID 발급 (함수/코드로 처리):** **SSOT 는 DB**이다. 서버 API(또는 Node.js 발급 서비스) 가 **단일 트랜잭션으로 `nexa_identities` 에 mint**한 뒤, 그 결과로만 문서·크롤러가 `identity_id` 를 **역주입 (동기화)**한다.
- **Identity ID(영혼 ID) 와 그 메타데이터에 대한 진실의 단일 원천 (SSOT) 은 데이터베이스 (DB)** 이다.
- **표기 길이 정책 (고정):** `identity_id` **총 6 자** — **접두 1 자 + `-` + NanoID 본문 4 자** (예: `K-a3F9`). 본문은 **NanoID 4 자**만 사용한다. **목적:** **내부** 기획·스펙 문서와 주석에 자주 넣어도 **가독성을 해치지 않도록 최대한 짧게** 유지한다.
- **규모 전제:** 플랫폼에서 관리하는 영혼 원장은 **총 1 만 건 전후**를 예상한다. (정책 변경 시 NanoID 자릿수·알파벳만 키우면 되며, 그때는 DDL·마이그레이션으로 대응한다.)
- **사전 중복 검사:** NanoID **4 자**만으로는 공간이 유한하므로 **이론적 충돌 (재추첨)** 가능성이 있다. 따라서 mint 직전 **DB 에서 동일 `identity_id` 존재 여부를 조회**하고, 이미 있으면 **NanoID 만 재생성 후 재시도**한다. **발급 자체 빈도가 매우 낮으므로** 이 사전 검사·재시도는 **운영 부담이 크지 않다**고 본다.
- DB 의 **`identity_id`**에 **전역 UNIQUE**·**PK**(단일 키) 를 걸어 기계적 중복을 차단한다. 지식 OS 에서 **같은 영혼 ID 는 도메인·프로젝트와 무관하게 하나의 본체만 존재한다**.
- **의미 부여 및 분류 (AI 담당):** 발급된 ID 에 대해 **인공지능 (Zenith Indicator)**이 문서 내용을 읽고 가장 적절한 **도메인, 계층 (Breadcrumb), 태그, 요약**을 추출하여 DB 속성값으로 제안합니다. 즉, " 이 글자가 무엇을 의미하는지 " 를 AI 가 해석하여 지능적 자산으로 등록하는 것입니다.

## 2. 언어적 라우팅 (Linguistic Routing) 을 통한 의미의 좌표화

사용자가 한국어로 입력한 내용이 어떻게 특정 Identity ID 와 연결되는지는 **' 언어적 라우팅 '** 엔진이 결정합니다.

- **의미의 좌표화 (Semantic Vectorizing):** 사용자의 입력이나 엣지 센서의 데이터를 단순 키워드가 아니라 육하원칙 (5W1H) 이 담긴 다차원 좌표로 변환합니다.
- **중의성 해소 (Disambiguation):** 예를 들어 'CORE' 라는 단어가 유입되었을 때, AI 는 현재의 **HEXAGON 컨텍스트**(Where, What 등) 를 분석하여 이것이 ' 주권 (Where.CORE)' 을 의미하는지 ' 펌웨어 (Base-Core)' 를 의미하는지 판별하여 정확한 ID 에 매핑합니다.

## 3. 아톰화 (Atomization) 와 지능적 족보

날것의 데이터를 AI 가 즉시 이해할 수 있는 **' 아톰 (Atom)'** 단위로 정제하는 과정이 핵심입니다.

- **의미의 추출:** 마이크로 센티널이 보낸 비식별 요약본을 바탕으로 인디케이터가 **코일 밸런서 (6-Coils)** 가중치를 필터로 사용하여 사건의 동기 (Why) 를 도출하고 최종 아톰으로 박제합니다.
- **인과 사슬 (Why Chain) 결합:** 모든 Identity 는 생성 시점의 **사실 (SNT) → 판단 (IND)** 사슬과 강하게 결합되어 그 유래를 증명하며, 이는 단순한 기록을 넘어 시스템의 ' 사유 방식 ' 을 보관하는 과정이 됩니다.

## 4. 인간 중심의 가드레일 (ASK → WILL)

# Identity ID 중복은 어떻게 막을 수 있나?

내용의 중복 문제를 해결하고 동일한 **Identity ID(영혼 ID)**로 수렴시키기 위한 구체적인 로직은 **' 언어적 정규화 '**, **' 벡터 유사도 검색 '**, 그리고 **' 문맥 기반 중의성 해소 '**가 결합된 3 단계 검증 파이프라인을 통해 실현됩니다.

단순히 글자를 비교하는 것이 아니라, 해당 내용의 **의미적 본질 (Semantic Essence)**을 추출하여 기존 원장과 대조하는 것이 핵심입니다.

## 1. 1 단계: 영문 IR 및 5W1H 토큰 정규화 (Linguistic Normalization)

내용 중복을 잡기 위한 첫 번째 단계는 서로 다른 표현을 하나의 표준화된 언어로 변환하는 것입니다.

- **표준화:** 한국어로 작성된 서로 다른 문장 (예: " 배터리 절약 로직 ", " 전력 소모 최적화 알고리즘 ") 을 시스템 표준인 **영문 IR(Intermediate Representation)**인 `Power Saving Logic` 으로 변환합니다.
- **토큰화:** 해당 내용을 **HEXAGON(5W1H) 6 축 정수 토큰**으로 변환합니다. 예를 들어, ' 공간 (Where)', ' 의도 (What)' 등의 토큰값이 일치하는지 1ms 내에 먼저 필터링하여 검색 범위를 90% 이상 줄입니다 (Pruning).

## 2. 2 단계: 하이브리드 벡터 검색 및 점수 산출 (Semantic Matching)

정규화된 뼈대를 바탕으로 DB(`nexa_knowledge_vectors`) 내의 기존 지식들과 의미적 거리를 계산합니다.

- **유사도 검색:** `pgvector` 와 `nomic-embed-text` 모델을 사용하여, 새로 입력된 내용과 가장 유사한 기존 Identity ID 후보군을 추출합니다.
- **복합 점수 식 (Scoring Formula):** 다음과 같은 가중치 합산 방식을 적용하여 중복 여부를 판별합니다:
  $$Final Score = (어휘 일치도 \times 0.35) + (벡터 유사도 \times 0.35) + (HEXAGON 문맥 일치도 \times 0.30)$$
- **문맥 대조:** 단순히 뜻이 비슷한 것을 넘어, 해당 개념이 사용된 **Where(스코프)**나 **Why(인과관계)** 토큰이 일치하는지 대조하여 중의성을 해소합니다.

## 3. 3 단계: 정책 분기 및 사용자 승인 (ASK -> WILL)

계산된 점수에 따라 시스템은 세 가지 경로 중 하나를 선택합니다.

- **자동 연결 (High Confidence):** 유사도가 임계값 (예: 95 점) 이상인 경우, 새로운 ID 를 발급하지 않고 기존 ID 에 대한 **' 재등장 (Mention)'**으로 기록하여 지능적 족보를 연결합니다.
- **병합 제안 (Ambiguous):** 유사도가 중간 범위 (예: 70~95 점) 인 경우, 시스템은 **STUCK** 상태를 선언하고 **넥슈 (NEXU) 의 Jitter(떨림)** 연출과 함께 " 기존 `K-a3F9` 와 동일한 개념인가요?" 처럼 **6 자 `identity_id`** 로 **ASK(승인 대기)** 요청을 보냅니다.
- **신규 발급 (Unique):** 기존 지식들과의 유사도가 현저히 낮은 경우에만 새로운 Identity ID 를 원자적으로 발급합니다.

## 4. 4 단계: 지능적 족보 (Why Chain) 박제

결정된 사항은 단순 기록이 아닌 **인과 사슬**로 저장됩니다.

- **언급 (Mention) 관리:** 동일한 Identity ID 가 여러 문서에 재등장할 경우, 각 문서의 **`anchor_id`**와 연결하여 " 어느 영혼이 어느 문서들의 어느 지점에 뿌리 내리고 있는지 " 를 `nexa_knowledge_references` 테이블에 누적 기록합니다.
- **진화 이력 추적:** 만약 유사한 내용이 발견되어 기존 ID 로 통합되었다면, 그 판단 근거 (추론 로직) 를 `why_chain` 에 저장하여 나중에 시스템이 왜 중복으로 판단했는지 역추적할 수 있게 합니다.

**요약하자면**, 이 로직은 **" 언어로 내용을 깎아내고 (정규화), 숫자로 거리를 재며 (벡터), 문맥으로 확정 (HEXAGON)"**하는 과정을 통해 내용 중복을 원천적으로 차단하고 시스템의 지능적 일관성을 유지합니다.

> 결론적으로, AI 성능이 낮더라도 " 입력은 규격화 (IR) 하고, 발급은 코드가 담당하며, 판단은 수식 (Scoring) 으로 검증하고, 모호할 땐 사람에게 묻는 (ASK)" 다층 구조를 통해 시스템의 일관성을 유지할 수 있습니다.

# Identity ID 의 권위

AI 가 의미를 해석하고 ID 를 제안하더라도, 최종적인 권위는 인간에게 있습니다.

- **신뢰도 기반 승인:** AI 가 제안한 분류나 연결의 **신뢰도 점수 (Confidence Score)**가 임계값 (95 점) 미만일 경우, 시스템은 **STUCK** 상태를 선언하고 **ASK(승인 대기)** 펄스를 발생시켜 사용자의 최종 승인을 기다립니다.
- **무손실 박제:** 사용자가 승인한 의지 (WILL) 는 미래 페르소나 학습의 핵심 근거가 되어 시스템의 ' 지혜 ' 로 승격됩니다.

**결론적으로**, Identity ID 는 단순한 ' 글자 매칭 ' 이 아니라, **AI 가 맥락을 해석하여 좌표를 찍고 사람이 그 의미를 확정하는 " 지능형 오케스트레이션 " 의 결과물**입니다. 이를 통해 NEXA-OS 는 데이터가 방대해져도 길을 잃지 않고 250 만 광년의 데이터 우주를 항해할 수 있는 ' 지능적 지도 ' 를 유지하게 됩니다.

## 1. `nexa_identities` 테이블의 설계 목적 및 위상

- **역할:** 시스템 내 모든 객체 (지식, 장치, 실행 패킷 등) 의 불변하는 정체성과 탄생 이유 (Why) 를 기록하는 **영혼의 지문**입니다.
- **발급 규칙:** 서버 API 가 `K`(지식), `P`(프로토콜), `F`(기능) 등 **접두 1 자**와 **NanoID 4 자**를 하이픈으로 결합해 **총 6 자** `identity_id` 를 원자적으로 발급합니다. (형식: `{접두}-{4자}`) 발급 직전 **사전 중복 검사·충돌 시 재추첨**은 상단 §1 정책과 동일합니다.
- **발급 경계:** 아무 문서에서나 생성되지 않고, `nature_tag` 가 `RULE` 또는 `INTENT` 인 **NEXA-OS 근간 기획문서**에서만 추출·정의하는 것을 **현재 SSOT 의도**로 둔다. 실제 **어디서 mint 가 허용되는지**는 **mint API·역할·허용 `anchor_id`/경로 목록** 등 **애플리케이션·운영 정책**이 게이트이다. `**tenant_id`·`mint_surface` 만으로\*\* 발급이 자동 허용되는 것은 아니다 (§2-B-1~3 표).
- **전역 원장 (지식 OS 커널):** `identity_id` 는 **도메인 (Nexion·패널·오케스트레이션 등) 과 무관하게 동일한 문자열이 동일한 본체**를 가리킨다. **프로젝트 (`project_id`) 는 Identity 의 소속이 아니라**, 문서·지식 행·멤버십·실행 패킷 등 **주변 자원의 RLS·쿼터 구획**에만 건다. 예: `nexa_knowledge_*` 의 행은 `project_id` 로 격리되어도, 그 안의 `mention → identity_id` 참조는 **전역 원장의 같은 `K-…`** 를 가리킨다.

**Knowledge OS 용어·정의와의 관계:** `nexa_knowledge_definitions` 등 **용어 (terms)** 행은 Knowledge OS 의 검색·RAG·CRUD 단위이고, **`identity_id` 는 그 위에 올라가는 전역 영혼 식별자**다. 구현 패턴 (권장): 정의 행에 `identity_id` 를 기록하고, 벡터는 **`term_id` → `nexa_knowledge_vectors`**(§2-1). **불변 토큰·승인 큐**(`change_requests` 등, ARCH §4.4) 와 Identity **mint 이후 코어 불변**은 **같은 거버넌스 정신**을 공유하나, **테이블·큐는 구현에서 통합하거나 분리**할 수 있다 — Identity 코어 변경은 본 문서 **불변성 절·「운영자」정제 툴**로만 예외 허용.

**`domain_tags` 와 Capability:** **`domain_tags`**는 **메인 메뉴·플랫폼 도메인 레지스트리**의 승인된 ID 배열이다. **Capability ID 문자열**(`nexa.platform.…`) 과 **동일 개념이 아니다.** 필요한 연결은 제품 정책에 따라 별도 매핑·추천 로직으로 둔다 (ARCH §0-A, Capability SSOT).

## 2. 예상 필드 구성 (`nexa_identities`)

본 절은 `**nexa_identities` 한 테이블**의 컬럼을 **역할별로 표를 나누어** 정리한다. **UUID·6 자 FK·주체 참조 등 ID 성격이 같은 열은 §2-B-1 한 표에 모았다.\*\*

- **§2-B-1 식별·ID·맥락·승계:** 전역 PK `identity_id`·`id_prefix`, 테넌트·표면, 근거 `anchor_id`·`source_span`, 승계 `superseded_by_id`·`replaced_by_id`, 승인·주체 UUID.
- **§2-B-2 분류·정의·축:** `nature_tag`, `status`, 지문·해시·HEXAGON·`why_chain`·`identity_aliases`·**`domain_tags`**(메인 메뉴·플랫폼 도메인).
- **§2-B-3 시간·가변 메타:** mint·승인 시각, 행 생성·갱신, `metadata`.

**임베딩 벡터**는 본 테이블에 두지 않고 `**nexa_knowledge_vectors`\*\* 에 둔다 (§2-1).

**기본 키:** `**identity_id` 단일 PK**, 플랫폼 (지식 OS) **전역 UNIQUE\*\*. 테넌트별로 다른 `K-…` 표기를 허용하지 않는다.

### §2.0 보강·승계·분류 필드 개요

아래는 **중복 방지 파이프라인**(정규화 → Pruning → 벡터·ASK), **족보 연속성**, **플랫폼 내비게이션**을 `nexa_identities` 안에서 지원한다 (상세는 §2-B-1·§2-B-2 표).

1. **`content_fact`:** AI·정규화 파이프라인이 만든 **English IR 한 줄**. 해시 (`definition_fingerprint`) 보다 앞단에서 **사람·규칙이 읽고 대조**하기 위한 텍스트 지문.
2. **HEXAGON 6 축 스냅샷 (`hexagon_*`):** mint 시점의 **5W1H 정수 토큰**을 컬럼으로 고정해 **복합 인덱스·Pruning**에 쓴다. (내부적으로 UCL/헤더 스냅샷 역할과 동일하며, 용어집의 **HEXAGON** 명칭에 맞춘다.)
3. **`identity_aliases`:** 같은 영혼을 가리키는 **다국어·표현 변형**을 JSONB 로 둔다. 중의성 해소 시 **근거·가중치**로 사용; 출처·승인 메타를 두어 **AI 의 무단 별칭 난립**을 제한한다.
4. **`superseded_by_id` / `replaced_by_id`:** 병합 수렴 vs 정책적 ID 교체를 **서로 다른 포인터**로 나누어 Traceability 를 유지한다 (상세는 §2-B-1 표).
5. **`domain_tags`:** **메인 메뉴·플랫폼 도메인 레지스트리**와 짝을 지은 **복수 태그**. 메뉴·레지스트리 변경 시 **정제 툴**로 재매핑 (하단 §「운영자」·§2).

## 3. 요약: 지능이 박제되는 과정

사용자가 넥사 OS 의 근간 기획문서에서 새로운 개념을 정의하면 다음과 같은 족보가 형성됩니다.

1. **`project_logs`**가 발급되어 " 이 개념은 무엇이다 " 라는 **의미 매칭:**이 생깁니다.
2. **`identity_id`**에 의해 이 영혼은 특정 **가문 (프로젝트)**의 자산으로 등록됩니다.
3. **`superseded_by_id`**를 통해 이 영혼이 **어느 층위 (예: 커널)**에서 탄생했는지 기록됩니다.
4. 마지막으로 **`anchor_id`**가 문서의 특정 지점에 **정책 분기:**을 내려, 영혼이 실제 자산 (파일) 에 박제되어 연주될 수 있는 **B. 아이디의 족보 (4 대 식별자)**를 갖게 됩니다.

이렇게 구성된 족보는 사후에 사고가 발생하거나 데이터의 유래를 찾을 때 **[실행 (EFF) → 판단 (IND) → 사실 (SNT) → 기획 문서 (anchor_id)]**로 역추적 하여 감사·분쟁에 쓸 수 있는 근거가 됩니다.

  6. 의미론적 잠금 (Meaning Lock) 적용: Re-pointing 작업 중에는 해당 ID 들에 대한 추가적인 수정이나 참조 생성이 일어나지 않도록 논리적 잠금 상태를 유지해야 정합성 오류를 막을 수 있음

## 2. 4 대 식별자 체계의 서사적 정립

시스템의 무결성을 증명하는 4 가지 핵심 키의 역할이 비유와 함께 명확히 정의되었습니다.

- **OS 내 어느 표면·계열** 두 명령이 정면으로 충돌할 때 시스템이 **허용 값은 SSOT·마이그레이션으로 고정** 상태로 전이되고 **정본 코어의 보호:**에서 연결을 직접 조정하는 복구 흐름이 구체화되었습니다.
