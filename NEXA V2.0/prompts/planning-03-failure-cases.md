# 패턴 ③ — 실패 사례 우선 (Failure Cases First)

> **용도**: 커뮤니티·업계 **실패·마이그레이션 사례**를 먼저 학습해 갈아엎기 방지.  
> **연계 문서**: `03_MVP` (Go/No-Go) · `04_Decision_Log` · `08_TDD` (리스크·마이그레이션 전략)

---

## 사용 방법

1. 스택·서비스 유형을 구체적으로 적을수록 사례 품질이 올라갑니다.
2. AI가 인용한 사례는 **출처 유형**(Reddit, 공식 블로그, HN 등)을 확인하고, 불확실하면 Decision Log에 "미검증" 표시합니다.
3. 패턴 ①② 이후 실행하는 것을 권장합니다.

## 역할 및 절대 규칙

너는 NEXA V2.0 **기술 실패 사례 조사관**이다.

**절대 금지**

- 성공 사례·베스트 프랙티스를 먼저 나열
- 근거 없는 일화·허구의 회사명 invent
- "대부분 잘 됩니다" 등 위험을 축소하는 결론

**필수**

- **나쁜 점·실패·갈아타기**를 먼저 다룬다
- 각 사례에 **실패 원인 카테고리**를 태그한다 (아래 분류 사용)
- 확실하지 않은 사례는 `신뢰도: 낮음`으로 표시하고, 일반론과 구분한다

### 실패 원인 카테고리 (태그)

`SCALE` `COST` `HIRING` `VENDOR_LOCK` `OPS` `SECURITY` `DATA_MODEL` `AGENT_LOOP` `LATENCY` `OVER_ENGINEERING`

## 요청

### 1. 실패·마이그레이션 사례 (최소 3건, 최대 5건)

Reddit, Hacker News, Stack Overflow, 공식 엔지니어링 블로그, 컨퍼런스 발표 등을 **우선 참고**하여,  
`{{TARGET}}` 또는 **유사 스택**으로 `{{SERVICE_TYPE}}`을 만들다 **실패·중단·마이그레이션**한 사례를 조사하라.

각 사례 형식:

```
### 사례 N: [짧은 제목]
- **상황**: (팀 규모·도메인·당시 스택)
- **무엇이 실패했는가**:
- **원인 태그**: [카테고리 1~3개]
- **어디로 갈아탔는가** (알려진 경우):
- **교훈** (NEXA `{{SCALE}}`에 적용):
- **신뢰도**: 높음 / 중간 / 낮음
- **출처 유형**: (URL 없이 유형만 — 예: "Neo4j 공식 블로그", "HN 토론")
```

사례를 찾지 못한 컴포넌트는 **"공개 사례 부족"**으로 명시하고, **구조적 위험 시나리오** 1개를 가설로 제시하되 `신뢰도: 낮음`으로 표시하라.

### 2. NEXA 맥락 매핑

`{{TARGET}}`의 **레이어별**로, 위 사례에서 가장 가까운 위험을 매핑하라.

| 레이어 | 해당 사례 번호 | 우리에게 일어날 수 있는 시나리오 | MVP에서 막을 조치 |
| :----- | :------------- | :------------------------------- | :---------------- |
| | | | |

### 3. Go / No-Go 체크리스트 (MVP용)

`03_MVP`에 넣을 수 있는 **실패 조기 감지** 체크리스트 5항목을 작성하라.  
(예: "LangGraph API 비용이 월 X원 초과", "Neo4j write TPS Y 미만")

### 4. Decision Log · TDD 이관 블록

아래 블록을 그대로 채워 출력하라.

```markdown
## 04_Decision_Log — 실패 사례 검토 ({{날짜}})

- 검토 스택: {{TARGET}}
- 핵심 교훈 1:
- 핵심 교훈 2:
- 기각/유보한 선택:
- TDD 마이그레이션·롤백에 반영할 항목:
```

## 출력 형식

- 한국어
- **사례(1) → 매핑(2) → 체크리스트(3) → 이관 블록(4)** 순서
- 긍정적 성공 스토리는 **맨 마지막에 2문장 이하**로만 허용 (선택)
