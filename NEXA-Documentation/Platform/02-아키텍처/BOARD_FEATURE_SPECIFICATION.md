# 넥사보드 기능 명세서

**작성일**: 2024년  
**목적**: 넥사보드의 핵심 기능 및 확장 기능 정의  
**최초 기획 의도**: 내부 협업 중심 - 여러 사람이 여러 장비를 이용하여 각각의 권한 UI를 통해 협업

---

## 0. 기획 의도 및 원칙

### 0.1 최초 기획 의도

- **내부 협업 중심**: 여러 사람이 여러 장비를 이용하여 각각의 권한 UI를 통해 협업
- **외부 오픈**: 보안 이슈로 매우 신중하게 검토 필요 (먼 미래)
- **확장성**: 내부적으로도 충분히 확장 통합이 가능한 구조 설계

### 0.2 설계 원칙

- **최소한의 정보 요구**: 초기 등록 시 최소한의 정보만 요구 (선등록 → 자동처리 → 이후 수정)
- **자동화 우선**: 가능한 한 자동으로 처리하여 사용자 부담 최소화
- **확장성 고려**: 미래 확장을 고려한 구조 설계
- **보안 우선**: 내부 협업 중심이므로 보안을 최우선으로 고려

### 0.3 통신 아키텍처

**MQTT 선택의 주요 계기:**

- **토픽 권한 기능**: MQTT의 토픽 기반 권한 관리 기능이 웹소켓 통신에서 MQTT로 결정하게 된 중요한 계기
  - 토픽별 세밀한 접근 제어 가능
  - 디바이스/사용자별 구독/발행 권한 관리
  - 보안 및 협업 시나리오에 적합

**MQTT 선택의 주요 계기:**

- **토픽 권한 기능**: MQTT의 토픽 기반 권한 관리 기능이 웹소켓 통신에서 MQTT로 결정하게 된 중요한 계기
  - 토픽별 세밀한 접근 제어 가능
  - 디바이스/사용자별 구독/발행 권한 관리
  - 보안 및 협업 시나리오에 적합

**엣지 디바이스 ↔ 플랫폼 통신:**

- **프로토콜**: MQTT 기반
- **초기 구축**: Node.js 서버에서 웹소켓 포트를 이용하여 MQTT 우회 구축
  - 웹소켓 포트를 통해 MQTT 브로커 기능 구현
  - 호스팅 제약사항 우회
- **향후 업그레이드**: 호스팅 업그레이드 후 정식 MQTT 포트 적용
  - 표준 MQTT 포트 (1883: TCP, 8883: TLS/SSL)
  - 전용 MQTT 브로커 운영

**협업 통신:**

- **프로토콜**: WebSocket 기반
- **용도**: 여러 사용자 간 실시간 협업
  - 실시간 메시지 교환
  - 상태 동기화
  - 알림 전달

**통신 계층 구조:**

```
엣지 디바이스 ←→ [MQTT] ←→ 플랫폼 서버
                              ↕
                         [WebSocket]
                              ↕
                         협업 사용자들
```

## 1. 핵심 기능 (Core Features)

### 1.1 기기 등록 (Device Registration)

**기능 설명:**

- 사용자가 보유한 IoT 기기를 시스템에 등록
- 넥사 시스템에서 생산한 기기 또는 API 규격에 맞춰 개발한 기기 지원

**초기 등록 정보 (최소 요구):**

- 모델 번호 (필수)
- API 키 발급 (자동 또는 수동)

**자동 처리되는 정보:**

- MAC 주소 (기기에서 자동 전송)
- 하드웨어 버전 (모델 번호 기반 자동 조회)
- 펌웨어 버전 (기기에서 자동 전송)
- 기기 타입 (모델 번호 기반 자동 조회)
- 기본 센서 정보 (모델 번호 기반 자동 조회)

**이후 수정 가능한 정보:**

- 기기 이름 (사용자 지정)
- 연결 타입 (WiFi, Ethernet, Bluetooth, Serial)
- 연결 설정 (WiFi SSID, 비밀번호 등)
- 위치 정보
- 설명

**등록 프로세스:**

1. 사용자가 모델 번호 입력
2. 시스템이 모델 번호 기반으로 하드웨어 정보 자동 조회
3. API 키 발급 (자동 또는 수동)
4. 기기가 서버 모드로 작동하여 플랫폼으로 정보 전달
5. 플랫폼에서 API 키 발급 및 등록 완료
6. 이후 사용자가 필요에 따라 정보 수정

**자동 디바이스 발견 (Auto Discovery):**

- 기기가 초기 서버 모드로 작동
- 플랫폼으로 기기 정보 전달
- 플랫폼에서 API 키 발급
- 등록 완료 후 일반 모드로 전환

**데이터베이스 테이블:**

- `devices_iot` (기본 정보)
- `devices_firmware` (펌웨어 버전 관리)
- `devices_models` (모델 정보 - 하드웨어 정보 자동 조회용)

**통신 프로토콜:**

- **MQTT 기반 통신**: 엣지 디바이스와 플랫폼 간 통신은 MQTT 프로토콜 사용
- **초기 구축**: Node.js 서버에서 웹소켓 포트를 이용하여 MQTT 우회 구축
- **향후 업그레이드**: 호스팅 업그레이드 후 정식 MQTT 포트(1883/8883) 적용하여 운영

**관련 기능:**

- 자동 디바이스 발견 (서버 모드 → 플랫폼 전달 → API 발급)
- MAC 주소 기반 중복 등록 방지
- API 키 발급 및 관리
- MQTT 토픽 및 설정 관리

### 1.2 보드에 기기 연결 (Device-Board Connection)

**기능 설명:**

- 보드를 생성한 후 등록된 기기를 보드에 연결
- **N-N 관계**: 하나의 보드에 여러 기기 연결 가능, 하나의 기기를 여러 보드에 연결 가능
- 확장성을 고려한 다대다 관계 설계

**연결 정보:**

- 보드 ID
- 기기 ID
- 연결 설정 (JSON)
- 표시 순서
- 활성화 여부

**데이터베이스 테이블:**

- `board_devices` (보드-기기 연결, N-N 관계)

**관련 기능:**

- 기기 상태 모니터링 (온라인/오프라인)
- 연결 해제
- 연결 설정 변경
- 보드별 기기 목록 조회
- 기기별 연결된 보드 목록 조회

### 1.3 패널 자동 호환성 검색 (Panel Auto-Compatibility)

**기능 설명:**

- 보드에 기기를 연결하면 호환되는 모든 패널이 자동으로 리스트에 표시
- 패널은 기기의 센서 타입, 기능에 따라 자동 필터링

**패널 카탈로그 (panel_catalog) 개념:**

- **패널 카탈로그**: 패널의 종합 정보 저장소
- 패널의 모든 정보를 담는 통합 저장소 (타입, 메타데이터, 호환성 등)
- 패널의 기본 정보 (이름, 설명, 아이콘, 카테고리)
- 패널 타입 정의 (패널의 속성 중 하나)
- 패널이 요구하는 센서 타입 및 기능 정의
- 호환성 규칙 정의
- 패널 인스턴스 생성 시 카탈로그 정보를 기반으로 생성

**패널 개발 및 배치 프로세스:**

1. **패널 개발**: 개발자가 실제 패널을 컴포넌트/모듈로 개발
2. **카탈로그 등록**: 개발된 패널을 `panel_catalog` 테이블에 등록 (모든 패널 정보 종합)
3. **사용자 선택**: 사용자가 `panel_catalog`에서 검색하거나 선택
4. **창에 배치**: 선택한 패널을 `board_windows`의 창에 배치하여 `board_panels`에 저장 (패널 인스턴스 생성)

**패널 인스턴스 (panel_instances) 개념:**

- **패널 인스턴스**: 보드에 실제로 배치된 패널
- 패널 카탈로그 정보를 기반으로 생성
- **창 구조와의 관계**: `board_windows` 테이블에 정의된 창(Window) 안에 배치됨
  - `pane_id` 컬럼이 `board_windows`의 창을 참조하여 어떤 창에 속하는지 지정
  - 창 구조(`board_windows`)는 컨테이너 역할, 패널 인스턴스(`board_panels`)는 내용물 역할
- **패널 배치 정보**: 그리드 위치(`grid_x`, `grid_y`, `grid_w`, `grid_h`)로 창 내부에서의 위치와 크기 정의
- 패널별 개별 설정 정보 포함 (`config` JSON 필드)
- `board_panels` 테이블에 저장됨

**창 구조 vs 패널 인스턴스 구분:**

- **`board_windows` (창 구조)**: 화면을 어떻게 분할할지, 각 창의 크기는 얼마인지 정의 (컨테이너)
- **`board_panels` (패널 인스턴스)**: 각 창 안에 어떤 패널을 어디에 배치할지 정의 (내용물)

**호환성 규칙:**

- 패널이 요구하는 센서 타입과 기기의 센서 타입 매칭
- 패널이 요구하는 기능과 기기의 기능 매칭
- 패널 카테고리별 필터링 (데이터 보기, 제어, 알림 등)

**데이터베이스 테이블:**

- `panel_catalog` (패널 카탈로그 - 패널 정보 종합)
- `panel_compatibility` (패널 호환성 매핑 - 패널-기기/센서 호환성)
- `board_windows` (창 구조 - 화면 분할/병합 구조 정의)
- `board_panels` (패널 인스턴스 - 보드에 배치된 실제 패널)
- `devices_sensors` (기기 센서 정보)

**관련 기능:**

- 패널 호환성 검사 API
- 패널 추천 시스템
- 사용자 정의 패널 등록 (내부 협업용)

### 1.4 패널 기능 (Panel Features)

**기능 설명:**

- 넥사에서 제공하는 다양한 패널 타입
- 사용자도 패널 개발 및 등록 가능 (미정)

**패널 카테고리:**

#### 데이터 보기 패널

- 텍스트 디스플레이
- **테이블 뷰** (데이터를 테이블 형태로 표시)
- 게이지
- 차트 (라인, 바, 파이 등)
- 상태 표시기
- 로그 뷰어
- 이미지 뷰어
- **데이터 분석 패널** (AI 기반 지능적 분석)

**확장 계획:**

- 다양한 데이터 시각화 패널 추가 예정
- 패널 개발에 많은 비중을 둘 계획

#### 제어 패널

- 버튼 제어
- 스위치 제어
- 슬라이더 제어
- **조이스틱 제어** (가상 조이스틱)
- **실물 조이스틱 연결 패널** (실제 조이스틱 하드웨어와 연결)
- 명령어 입력
- 색상 선택

**확장 계획:**

- 다양한 제어 인터페이스 패널 추가 예정
- 코딩 익숙해지면 이 부분에 많은 비중을 둘 계획

#### 설정 패널

- 기기 설정
- 센서 보정
- 알림 규칙 설정

#### 알림 패널

- 알림 센터
- 알림 규칙 편집기
- 자동화 규칙 편집기

**데이터베이스 테이블:**

- `panel_catalog` (패널 카탈로그 - 패널 정보 종합)
- `board_panels` (패널 인스턴스 - 보드에 배치된 실제 패널)
- 패널 설정은 `board_panels.config` JSON 필드에 저장

## 2. 확장 기능 (Extended Features)

### 2.1 넥사보드 독립 기능 개발 접근 페이지

**기능 설명:**

- 넥사보드와 독립된 별도의 기능/프로그램 개발 접근 페이지 제공
- API 기반 개발 지원
- 개발자 도구 및 문서 제공

**제공 기능:**

- RESTful API 엔드포인트
- **WebSocket 실시간 통신** (초기 구현 필요)
- **API 키 관리** (초기 구현 필요)
- 개발자 대시보드
- API 문서 (Swagger/OpenAPI)
- SDK 제공 (JavaScript, Python 등)

**통신 아키텍처:**

- **엣지 디바이스 ↔ 플랫폼**: MQTT 기반 통신
  - **MQTT 선택 이유**: 토픽 기반 권한 관리 기능이 핵심 계기
    - 토픽별 세밀한 접근 제어
    - 디바이스/사용자별 구독/발행 권한 관리
    - 보안 및 협업 시나리오에 적합
  - 초기: Node.js 서버에서 웹소켓 포트를 이용하여 MQTT 우회 구축
  - 향후: 호스팅 업그레이드 후 정식 MQTT 포트(1883/8883) 적용
- **협업 통신**: WebSocket 기반 실시간 메시지 교환
  - 여러 사용자 간 협업 시 WebSocket으로 메시지 주고받기
  - 실시간 상태 동기화 및 알림

**구현 우선순위:**

- **초기 구현 필요**: API 키 관리, WebSocket 실시간 통신
- 내부 협업을 위한 기본 인프라

**데이터베이스 테이블:**

- `api_keys` (API 키 관리)
- `api_usage_logs` (API 사용 로그)
- `developer_apps` (개발자 앱 등록 - 내부 협업용)

### 2.2 온라인 IoT 기기 펌웨어 업데이트 (OTA - Over-The-Air)

**기능 설명:**

- 플랫폼에서 IoT 기기의 펌웨어를 원격으로 업데이트
- 버전 관리 및 롤백 지원

**업데이트 프로세스:**

1. 펌웨어 파일 업로드
2. 펌웨어 검증 (해시 확인)
3. 대상 기기 선택
4. 업데이트 스케줄링 (즉시 또는 예약)
5. 업데이트 진행 상황 모니터링
6. 업데이트 완료 확인
7. 롤백 옵션 제공

**업데이트 모드:**

- **수동 업데이트** (권장): 사용자가 직접 확인 후 업데이트 실행
- **자동 업데이트** (선택): 위험 부담 고려하여 신중하게 구현
  - 안전 장치: 백업, 롤백, 단계적 배포
  - 모니터링: 업데이트 실패 시 자동 롤백

**데이터베이스 테이블:**

- `devices_firmware` (펌웨어 버전 관리)
- `firmware_updates` (업데이트 이력)
- `firmware_files` (펌웨어 파일 저장)

### 2.3 플랫폼 AI 연동 개인화 (AI Personalization)

**기능 설명:**

- AI를 활용한 사용자 개인화 기능

**AI 기능:**

- 사용 패턴 분석
- 자동화 규칙 추천
- 이상 징후 감지 (Anomaly Detection)

- 에너지 사용 최적화
- 사용자 행동 예측
- 데이터 분석 패널에서 지능적 분석 제공

**데이터베이스 테이블:**

## 3. 추가 아이디어 (Additional Ideas)

### 3.1 기기 그룹 관리 (Device Groups)

**기능 설명:**

- 여러 기기를 그룹으로 묶어 일괄 관리
- 그룹 단위 제어 및 모니터링

**보드 메뉴 관리 vs 기기 그룹:**

- **보드 메뉴 관리**: 보드와 그룹의 계층 구조 관리 (트리 구조)
- **기기 그룹**: 여러 기기를 논리적으로 묶어 일괄 제어/모니터링
- **관계**: 하나의 보드에 여러 패널을 배치하는 것과 유사하게, 하나의 보드에 여러 기기 그룹을 배치할 수 있음
- **차이점**: 보드 메뉴는 보드/그룹의 구조 관리, 기기 그룹은 기기들의 논리적 그룹핑

**사용 사례:**

- 같은 공간의 모든 조명을 하나의 그룹으로 관리
- 층별/구역별 기기 그룹화
- 시간대별 그룹 제어
- 하나의 보드에 여러 패널을 배치하는 것처럼, 하나의 보드에 여러 기기 그룹을 배치

**데이터베이스 테이블:**

- `devices_groups` (기기 그룹)
- `device_group_members` (그룹 멤버)

---

### 3.2 시나리오/시퀀스 관리 (Scenarios/Sequences)

**기능 설명:**

- 여러 기기와 패널을 연동한 복잡한 시나리오 생성
- 시간 기반 또는 이벤트 기반 시퀀스 실행

**구현 방식 고려사항:**

- **옵션 1: 패널에 기능 추가**
  - 장점: 패널 내에서 직접 연결 가능
  - 단점: 모든 패널이 이 기능에 대응해야 하므로 패널 구성 복잡도 증가
- **옵션 2: 별도 페이지 구현** (권장)
  - 장점: 패널 구성 복잡도 유지, 전용 UI로 더 직관적
  - 단점: 패널과 별도로 관리 필요

**초기 아이디어:**

- 서로 연결해주는 패널을 넣어서 패널 간 연결
- 하지만 모든 패널이 이러한 기능에 대응해야 하므로 복잡도 증가

**사용 사례:**

- "출근 모드": 조명 켜기, 온도 조절, 뉴스 읽기
- "잠자기 모드": 조명 끄기, 온도 낮추기, 알림 음소거
- "파티 모드": 조명 색상 변경, 음악 재생, 온도 조절

**데이터베이스 테이블:**

- `scenarios` (시나리오)
- `scenario_steps` (시나리오 단계)
- `scenario_triggers` (시나리오 트리거)

**구현 방식:**

### 3.4 사용자 권한 및 공유 (User Permissions & Sharing)

**기능 설명:**

- 여러 사용자가 같은 보드/기기를 공유
- 역할 기반 권한 관리

**구현 순서:**

1. 사용자 등록 및 관리 기능 먼저 구현
2. 이후 보드에 사용자 연결
3. 권한 레벨 설정

**권한 레벨:**

- 소유자 (Owner): 모든 권한
- 관리자 (Admin): 설정 변경, 기기 추가/제거
- 편집자 (Editor): 패널 추가/수정, 제어
- 뷰어 (Viewer): 읽기 전용

**핵심 기능:**

- 내부 협업의 핵심 기능
- 여러 사람이 여러 장비를 이용하여 각각의 권한 UI를 통해 협업

**데이터베이스 테이블:**

- `users` (사용자 정보)
- `shares_boards` (보드 공유)
- `shares_devices` (기기 공유)
- `user_roles` (사용자 역할)

### 3.5 백업 및 복원 (Backup & Restore)

**기능 설명:**

- 보드 설정, 패널 구성, 자동화 규칙 백업
- 백업 파일로 복원

**기능:**

- **자동 백업** (기본 제공): 서버 여유에 따라 몇 주~몇 달 자동 보관
- 수동 백업 (선택적)
- 선택적 복원 (보드별, 기기별)
- 백업 파일 다운로드/업로드

**백업 정책:**

- 자동 백업: 서버 여유에 따라 자동으로 보관
- 보관 기간: 몇 주에서 몇 달 (서버 용량 고려)
- 사용자 부담 최소화: 별도 설정 없이 자동으로 처리

**데이터베이스 테이블:**

- `backups` (백업 이력)
- `backup_files` (백업 파일 정보)
