## ✨ NEXA-Platform: 스키마 아키텍처 설계 가이드

지금까지 구축한 **Formulator(배합기)** 체계는 데이터의 흐름을 요리에 비유하여 논리적 복잡성을 직관적으로 해결하려는 시도입니다. 이를 바탕으로 시스템의 근간이 되는 스키마 설계 가이드 문서를 정리해 드립니다.

### ✨ 1. 전체 파일 구조 및 주요 역할

| 폴더        | 파일명                 | 역할 및 책임                                                       |
| ----------- | ---------------------- | ------------------------------------------------------------------ |
| **common**  | `metadata.ts`          | 객체의 생애주기 관리 (ID, 생성일, 수정일, 소유자 등)               |
|             | `taxonomy.ts`          | 시스템 구성 요소의 계층적 분류 (Group, Type 등)                    |
| **modules** | `formulator.ts`        | 핵심 연산 단위. 입력 성분(Ingredients)을 받아 결과(Results)를 배합 |
|             | `connection.ts`        | 데이터의 혈관. 출력 단자와 입력 단자를 잇는 논리적 통로            |
|             | `blueprint.ts`         | 시스템 전체 설계도. 모든 포뮬레이터와 커넥션의 집합체              |
| **recipes** | `math/logic/filter.ts` | 포뮬레이터의 구체적인 동작 원리(Settings)를 정의하는 조리법        |
|             | `gateway.ts`           | 물리적 하드웨어(I/O)와 논리 세계를 잇는 인터페이스 규격            |
| **engine**  | `runtime.ts`           | 실행 중인 엔진의 상태 데이터(CPU, 메모리, 현재 설계도) 규격        |
| **storage** | `repository.ts`        | 설계도 파일의 물리적 저장 정보(파일 경로, 해시, 백업) 규격         |

### ✨ 2. 설계 목적 및 주요 포인트

-   **목적:** 하드웨어 제어 로직을 모듈화하여, 복잡한 프로그래밍 없이도 **'조립식 배합'**이 가능한 환경을 제공함
-   **유연한 설정 (Settings):** `z.record(z.string(), z.any())`를 사용하여 각 레시피마다 다른 설정 인자를 유연하게 수용하면서도, 하위 스키마를 통해 엄격한 검증을 병행함
-   **물리-논리 분리:** `Gateway` 스키마를 통해 하드웨어 핀 번호와 비즈니스 로직을 분리하여, 장치가 바뀌어도 설계도(Blueprint)를 그대로 재사용 가능함
-   **가시성 보장 (Display):** 모든 핵심 스키마에 `display` 객체를 포함하여, 데이터만으로도 UI(노드 에디터)를 완벽하게 렌더링할 수 있도록 설계함

### ✨ 3. 앞으로의 실제 적용 가이드 (Implementation Roadmap)

스키마가 완성되었으므로, 이를 활용하여 시스템을 구동할 **Service 레이어** 구현 시 다음 원칙을 준수합니다.

-   **엄격한 타입 추론:** 모든 서비스 함수는 Zod의 `z.infer<T>`를 통해 생성된 타입을 사용하여 런타임 에러를 방지함
-   **순수 함수 기반 Evaluator:** `recipes`에 정의된 연산 로직은 외부 상태에 의존하지 않는 순수 함수로 구현하여 테스트 용이성을 확보함
-   **비동기 흐름 제어:** `connection.ts`를 해석할 때는 데이터의 선후 관계(Dependency Graph)를 파악하여 순차적으로 연산이 일어나도록 설계함
-   **영속성 관리:** `storage/repository.ts` 규격에 따라 설계도를 JSON 형태로 직렬화하여 로컬 또는 클라우드에 안전하게 보관함

### **NEXA NODE** Property Editor:

D3.js 를 기반 노드를 캔버스에 배치하고 각 노드에 패널을 부여하고 라인 구성으로 데이터 흐름을 구성 할 수 있으며 `포물레이터` 노드를 중간에 배치하여 각 노드간의 데이터를 연산을 통해 재구성 할 수 있다.<br>
패널은 단순히 화면의 일부가 아니라, 사용자의 의도를 데이터로 변환하는 인터페이스입니다. <br>

-   프로젝트 생성 -> 장비구성 -> 노드 배치 (옵션 : 실제 또는 가상으로 실레이션)
-   노드를 클릭 했을때 가용한 포뮬레이터 노드가 활성화 되며 캔버스에 배치
-   페널노드에 입출력 포인트가 활성화 되고 페널노드(래시피) <-> 포물레이터 <-> 패널노드(디스플레이) 의 라인 관계를 형성
-   관계 라인을 형성하고 포플레이터를 셋팅하면 실시간 디스플레이 노드에 반영
-   레시피(노드:패널)에 맞는 포물레이터 settings (예: SCALER 선택 시 min/max 입력칸 표시)를 하면 불가, 부적절, 적합 등의 피드백
-   데이터(실제값,입력값,자동렌던값) 값에 따라 결과 실시간 디스플레이 반영

## ✨ NEXA Node 시각화 및 개발 우선순위 정립

제공해주신 **NEXA Node**의 개념은 단순한 데이터 흐름을 넘어, 사용자가 시각적으로 로직을 '조립'하고 실시간으로 '결과'를 확인하는 **대화형 환경**을 지향하고 있습니다. 특히 D3.js 기반의 캔버스와 포뮬레이터를 통한 데이터 재구성은 시스템의 핵심 가치입니다.

이를 바탕으로, 사용자가 화면에서 노드를 배치하고 피드백을 받는 과정을 최우선으로 하는 **UI/UX 중심의 개발 순서**를 제립해 드립니다.

#### ✨ 1단계: 패널 및 디스플레이 규격 확정 (UI Foundation)

사용자가 캔버스에서 보는 모든 것은 스키마에 정의되어 있어야 합니다. 패널이 "사용자의 의도를 데이터로 변환하는 인터페이스"가 되기 위한 기초 작업을 완료합니다.

-   **`panel.ts` 최종 설계:** 노드의 위치(), 크기, 최소화 상태뿐만 아니라 해당 패널이 어떤 `formulatorId`와 연결되어 있는지 정의합니다.
-   **`display.ts` 보완:** 각 노드가 캔버스에서 가질 아이콘, 테마 색상, 단위 표시(Unit) 규격을 확정하여 시각적 직관성을 높입니다.

#### ✨ 2단계: 컴포넌트 라이브러리 및 브릿지 설계 (Bridge Layer)

정적인 스키마 파일을 읽어와서 동적인 UI 컴포넌트로 변환하는 단계입니다.

-   **Taxonomy 기반 메뉴 생성:** `taxonomy.ts`를 스캔하여 MATH, LOGIC 등 카테고리별 포뮬레이터 목록을 UI 사이드바에 자동으로 나열합니다.
-   **Property Editor(속성 편집기) 동적 생성:** 사용자가 노드를 클릭하면 `recipes/*.ts` 스키마를 분석하여 해당 레시피에 필요한 입력창(Input, Slider, Checkbox 등)을 자동으로 렌더링합니다.

#### ✨ 3단계: 이벤트 핸들링 및 관계 형성 (Interaction)

D3.js 캔버스 위에서 사용자의 행동을 `blueprint.ts` 데이터로 치환하는 단계입니다.

-   **Connection 로직 구현:** 마우스 드래그로 두 노드를 이을 때, `connection.ts` 규격에 맞는 소켓(Source/Target) 데이터를 생성하고 유효성(데이터 타입 일치 여부)을 검증합니다.
-   **실시간 피드백 시스템:** `settings` 입력 시 "적합/부적합" 상태를 판별하여 노드의 테두리 색상을 바꾸거나 경고 아이콘을 표시하는 시각적 피드백을 구현합니다.

#### ✨ 4단계: 가상 시뮬레이션 및 엔진 가동 (Execution)

설계된 로직에 가상의 데이터를 흘려보내 실시간으로 결과를 확인하는 단계입니다.

-   **Virtual Gateway 주입:** 실제 장비 없이도 가상의 입력값(Mock Data)을 넣어 노드 사이의 데이터 흐름을 시각화합니다.
-   **Evaluator 가동:** 완성된 `blueprint` 데이터를 `evaluator.ts`에 주입하여, 연산 결과가 디스플레이 노드에 실시간으로 반영되는지 확인합니다.

#### ✨ 5단계: 작성된 로직을 저장 및 재사용

설계된 로직을 넥사보드에 배치하여 데이터를 확인하고 제어할 있도록 하거나 EPR 등에도 재사용 가능 하도록 한다.

-   로직 작성자는 배치된 '`Logic Panel` 페널의 편집 버튼을 누르면 NEXA NODE 에 진입하여 바로 수정 할 수 있습니다.

## ✨ 패널의 이원화: 데이터 수집과 가공 결과의 분리 설계

패널을 **순수 패널(Raw/Source Panel)**과 **가공 패널(Result/Logic Panel)**로 이원화하는 것은 매우 전략적인 접근입니다. 이는 데이터의 '발생'과 '활용'을 분리하여, 최종 가공된 결과물을 넥사보드뿐만 아니라 ERP 등 외부 시스템에서도 독립적으로 재사용할 수 있는 **모듈형 데이터 구조**를 가능하게 합니다.

### ✨ 1. 패널의 이원화 정의 및 분류

| 분류          | 명칭                   | 주요 역할                                                                                 | 재사용성                                                                                      |
| ------------- | ---------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| **순수 패널** | **Raw/Source Panel**   | 하드웨어(센서)나 외부 API에서 들어오는 가공되지 않은 원시 데이터를 시각화하고 제어합니다. | 특정 하드웨어에 종속적이며, 주로 '재료' 역할을 수행합니다.                                    |
| **가공 패널** | **Result/Logic Panel** | 포뮬레이터를 통해 연산, 필터링, 논리 판단이 완료된 '정제된 결과물'을 시각화합니다.        | 하드웨어와 무관한 '지표' 데이터이므로 넥사보드, ERP, 모바일 앱 등에서 즉시 재사용 가능합니다. |

---

### ✨ 3. 데이터 흐름 및 재사용 시나리오

1. **데이터 발생 (Raw Panel):** 14번 핀의 온도 센서 데이터를 `Raw Panel`이 실시간으로 표시합니다.
2. **논리 요리 (Formulator):** '온도 스케일러'와 '비교기'를 통해 "정상 범위 여부(Boolean)"를 계산합니다.
3. **결과 확정 (Result Panel):** 가공된 "정상 여부" 데이터를 `Result Panel`에 바인딩합니다.
4. **외부 재사용:** ERP 시스템은 넥사보드의 복잡한 로직을 몰라도, `Result Panel`의 `exportKey`만 호출하여 "현재 공정 상태: 정상"이라는 결과값만 가져갑니다.

## ✨ NEXA-Platform: 스키마 아키텍처 및 시스템 구축 통합 가이드

지금까지 논의된 모든 기술적 사양과 비즈니스 로직을 하나로 통합한 마스터 가이드입니다. 이 문서는 설계의 '요리' 철학을 유지하면서도, 실제 **NEXA NODE** 에디터 구현과 외부 시스템(ERP) 연동까지 고려한 탄탄한 구조를 지향합니다.

### ✨ 1. 시스템 파일 구조 및 핵심 도메인

| 도메인                  | 폴더 및 파일          | 역할 및 책임                                                                               |
| ----------------------- | --------------------- | ------------------------------------------------------------------------------------------ |
| **기초 자재 (Base)**    | `common/`             | 모든 데이터의 신분증(`metadata`), 언어 규격(`taxonomy`), 시각적 상태(`display`) 정의       |
| **핵심 모듈 (Core)**    | `modules/`            | 요리사(`formulator`), 혈관(`connection`), 주방 설계도(`blueprint`), 조리대(`panel`)        |
| **조리법 (Recipe)**     | `recipes/`            | 실제 데이터를 가공하는 수학(`math`), 논리(`logic`), 정제(`filter`), 입출력(`gateway`) 규격 |
| **관제/저장 (Control)** | `engine/`, `storage/` | 실시간 엔진 가동 상태(`runtime`) 및 설계도 영속성 관리(`repository`)                       |

---

### ✨ 2. NEXA NODE: 시각적 배합 시스템의 핵심 설계

단순한 데이터 연결을 넘어 **"사용자의 의도를 가치 있는 정보로 치환"**하는 에디터의 핵심 포인트입니다.

-   **D3.js 기반 캔버스:** 노드 간의 복잡한 상관관계를 유동적인 라인으로 시각화하여 데이터 흐름을 한눈에 파악합니다.
-   **지능형 Property Editor:** 노드를 선택할 때마다 해당 레시피(`recipes/*.ts`)를 해석하여 필요한 입력 컨트롤을 즉시 생성합니다.
-   **실시간 피드백 루프:** 사용자가 값을 입력하는 순간, `display.ts`의 `FeedbackStatus`를 통해 **적합/부적합** 여부를 시각적으로 즉시 알립니다.

---

### ✨ 3. 패널의 이원화 전략: 생산과 소비의 분리

NEXA-Platform의 가장 강력한 특징인 **데이터 재사용성**을 위한 설계입니다.

| 분류          | 명칭             | 원천 데이터           | 외부 연동 (ERP 등)            |
| ------------- | ---------------- | --------------------- | ----------------------------- |
| **순수 패널** | **Raw Panel**    | 하드웨어 핀, 원시 API | 불가 (내부 장치 종속적)       |
| **가공 패널** | **Result Panel** | 포뮬레이터 연산 결과  | **적극 권장 (JSON/API 매핑)** |

> **시나리오:** 공장의 '모터 진동 센서(Raw)'가 100개를 발생시키면, '평균 필터(Formulator)'가 이를 요리하여 '기계 이상 징후(Result)'라는 단 하나의 고급 정보로 만듭니다. ERP는 복잡한 센서값 대신 이 '이상 징후' 패널만 구독합니다.

---

### ✨ 4. 단계별 구축 로드맵 (Implementation Roadmap)

혼선 없는 진행을 위해 작업의 순서를 **의존성 기반**으로 재정리했습니다.

#### **[P0] 시각적 뼈대 완성 (UI Foundation)**

-   **작업:** `panel.ts`와 `display.ts` 최종 통합.
-   **목표:** 캔버스 위에 Raw 노드와 Result 노드를 시각적으로 구분하여 배치할 수 있는 데이터 규격 완성.

#### **[P1] 동적 에디터 및 브릿지 구축 (Bridge Layer)**

-   **작업:** `taxonomy.ts`를 읽어 메뉴를 생성하고, `recipes/` 스키마를 읽어 속성 편집기를 자동 생성하는 로직 구현.
-   **목표:** 코딩 없이 스키마 추가만으로 새로운 기능의 노드를 에디터에 추가할 수 있는 구조 확보.

#### **[P2] 인터렉션 및 무결성 검증 (Interaction)**

-   **작업:** 드래그 앤 드롭 연결 로직 및 타입 체킹 시스템 구축.
-   **목표:** "숫자 데이터"를 "불리언 입력단"에 연결할 때 발생하는 오류를 에디터 수준에서 차단.

#### **[P3] 실시간 엔진 및 시뮬레이션 (Execution)**

-   **작업:** `evaluator.ts` 개발 및 가상 가이트웨이 주입.
-   **목표:** 캔버스에서 값을 바꿨을 때 최종 Result 패널에 수치가 실시간으로 변하는 '살아있는 로직' 구현.

#### **[P4] 영속성 및 외부 확장 (Storage & API)**

-   **작업:** `repository.ts` 기반 저장소 구축 및 ERP 연동용 API Endpoint 생성.
-   **목표:** 완성된 로직을 저장하고, 권한이 있는 외부 시스템에 가공된 데이터를 공급.

---

### ✨ 5. 향후 확장 시나리오 검토 포인트

-   **자동 렌더링(Auto-Layout):** 수백 개의 노드가 배치될 경우를 대비한 자동 정렬 알고리즘.
-   **버전 관리(Versioning):** 로직 수정 시 이전 버전으로 되돌릴 수 있는 스냅샷 기능.
-   **권한 전파(Permission):** 특정 Result 패널만 특정 사용자에게 노출하는 세부 보안 정책.
