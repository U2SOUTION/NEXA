### **`frame/router/` 상세 파일 구조 제안**

U2art님의 `router/`는 "전체 라우팅 및 Infra 리다이렉션 가드"를 담당한다고 하셨죠. 이것은 곧 중앙 관제 시스템의 핵심적인 교통 통제소 역할을 의미합니다. 아래와 같이 세분화하여 **역할 분리**와 **확장성**, 그리고 **`system/composables/auth/`와의 연동**을 고려해 볼 수 있습니다.

```text
src/
└── frame/
    └── router/
        ├── index.ts                        # ⚡️ 메인 라우터 초기화 및 인스턴스 생성
        ├── routes/                         # 전체 라우트 정의 모듈 통합
        │   ├── coreRoutes.ts               # ✅ 플랫폼 핵심 라우트 (예: '/', '/home', '/about', '/404')
        │   ├── domainRoutes.ts             # ✅ 각 도메인의 라우트 정의를 통합/취합
        │   └── authRoutes.ts               # ✅ 인증 관련 라우트 (예: '/login', '/register', '/reset-password')
        │
        ├── guards/                         # 전역 내비게이션 가드 정의
        │   ├── authGuard.ts                # 🔒 인증 상태 확인 가드 (미인증 사용자의 접근 제어)
        │   ├── permissionGuard.ts          # 🔑 권한별 접근 제어 가드 (향후 확장 대비)
        │   └── systemStatusGuard.ts        # 🚧 시스템 점검, 유지보수 등 전역 상태 가드 (예시)
        │
        ├── types/                          # 라우터 관련 타입 정의
        │   └── routeTypes.ts               # ✅ 라우트 메타 필드 등에 사용될 사용자 정의 타입
        │
        └── utils/                          # 라우터 관련 유틸리티 함수
            └── routeHelpers.ts             # ✅ 동적 라우트 로딩, 메타 데이터 처리 등 헬퍼
```

### **각 파일의 역할과 `system/composables/auth/` 연동 방안**

1.  **`index.ts`**

    -   **역할**: Vue Router의 인스턴스를 생성하고, 위에 정의된 `routes/` 내의 모든 라우트 정의를 불러와 `createRouter`에 전달합니다. 또한, `guards/` 디렉토리의 전역 내비게이션 가드들을 등록하여 라우팅 흐름을 최종적으로 제어합니다.
    -   **특징**: 라우터의 `beforeEach`, `afterEach` 등의 전역 가드를 이곳에서 등록합니다. 이 가드들이 `guards/` 폴더 내의 실제 가드 로직을 호출하는 중앙 허브 역할을 합니다.
    -   **`system/composables/auth/` 연동**: 직접적인 연동보다는 `authGuard.ts`를 통해 간접적으로 연결됩니다. `index.ts`는 `authGuard.ts`가 등록되도록 설정합니다.

2.  **`routes/`**

    -   **`coreRoutes.ts`**:
        -   **역할**: NEXA 플랫폼의 가장 기본적인, 즉 로그인 없이도 접근 가능한 메인 페이지, 소개 페이지, 404(Not Found) 페이지 등 코어 기능의 라우트를 정의합니다.
        -   **특징**: 플랫폼의 기본 틀을 형성하는 경로들입니다.
    -   **`domainRoutes.ts`**:
        -   **역할**: `domains/` 디렉토리 내에 있는 각 도메인(예: `infra/`, `erp/`)이 정의하고 내보내는 라우트 목록을 통합하고 취합합니다. 각 도메인은 자신의 `router/index.ts` (또는 `routes.ts`) 파일을 가지고 해당 도메인 내의 세부 라우트를 정의한 후, 이 `domainRoutes.ts`에서 동적으로 로드하거나 명시적으로 임포트하여 병합하는 구조가 이상적입니다.
        -   **특징**: "도메인 중심 아키텍처"의 핵심. 각 도메인의 자율성을 보장하면서도 중앙 라우터가 이를 통합적으로 관리하게 합니다.
    -   **`authRoutes.ts`**:
        -   **역할**: 로그인, 회원가입, 비밀번호 찾기/재설정, 사용자 인증 토큰 갱신 등의 인증 관련 페이지 라우트를 정의합니다.
        -   **특징**: 인증 흐름을 담당하는 별도의 경로들로, 주로 `authGuard.ts`와 깊이 연관됩니다.

3.  **`guards/`**

    -   **`authGuard.ts`**:

        -   **역할**: 사용자의 인증 상태를 확인하여 특정 라우트로의 접근을 허용하거나 차단하는 핵심 가드입니다.
        -   **`system/composables/auth/useAuth.ts` 연동 방안**:

            -   이 `authGuard.ts` 파일 내에서 `system/composables/auth/useAuth.ts`에 정의된 `isAuthenticated` (인증 여부 확인), `getUser` (사용자 정보 가져오기) 또는 `redirectToLogin` (로그인 페이지로 리다이렉트) 등의 함수를 직접 임포트하여 사용합니다.
            -   예시 코드 (개념):

                ```typescript
                // src/frame/router/guards/authGuard.ts
                import { useAuth } from "@/system/composables/auth/useAuth";
                import { RouteLocationNormalized, NavigationGuardNext } from "vue-router";

                export const authGuard = (to: RouteLocationNormalized, from: RouteLocationNormalized, next: NavigationGuardNext) => {
                    const { isAuthenticated, redirectToLogin } = useAuth(); // composable에서 인증 상태와 함수 가져오기

                    // 라우트 메타 필드에 'requiresAuth: true'가 설정되어 있으면 인증이 필요함
                    if (to.meta.requiresAuth && !isAuthenticated.value) {
                        // 인증되지 않았다면 로그인 페이지로 리다이렉트
                        redirectToLogin(to.fullPath); // 현재 경로를 로그인 후 리다이렉트할 경로로 전달
                        return;
                    }
                    next(); // 인증되었거나 인증이 필요 없는 페이지는 통과
                };
                ```

    -   **`permissionGuard.ts`**:
        -   **역할**: 사용자의 '권한' (예: 관리자, 일반 사용자)에 따라 특정 페이지나 기능에 대한 접근을 제어합니다. `authGuard`가 통과된 후, 더 세분화된 접근 제어가 필요할 때 사용합니다.
        -   **특징**: `authGuard`와 유사하게 `system/composables/auth/useAuth.ts`에서 `hasPermission` 등의 함수를 가져와 활용할 수 있습니다.
    -   **`systemStatusGuard.ts`**:
        -   **역할**: 시스템 전체의 상태(예: 점검 중, 긴급 패치 중)에 따라 사용자 접근을 제어하는 가드입니다. 예를 들어, 점검 중에는 모든 요청을 점검 페이지로 리다이렉트할 수 있습니다.
        -   **특징**: `system/store/` 등에 정의된 전역 시스템 상태를 참조할 수 있습니다.

4.  **`types/routeTypes.ts`**

    -   **역할**: 라우트 메타 정보 (`meta` 필드)에 들어갈 사용자 정의 타입(예: `requiresAuth: boolean`, `roles: string[]`, `layout: 'default' | 'blank'`) 등을 정의하여 코드의 가독성과 타입 안정성을 높입니다.

5.  **`utils/routeHelpers.ts`**
    -   **역할**: 라우팅 로직을 보조하는 유틸리티 함수들을 모아둡니다. 예를 들어, 동적으로 라우트를 불러오거나 특정 라우트 정보를 가공하는 등의 기능입니다.

이 구조는 NEXA 플랫폼의 "시스템은 결정을 내리지 않는다. 흐름을 만든다."는 철학을 `router/` 디렉토리에서도 구현합니다. 라우터 자체가 결정을 내리기보다는, `guards/`를 통해 흐름을 조건부로 변경하는 역할을 담당하며, `system/composables/auth/`는 그 조건(인증 상태)을 제공하는 셈입니다.

U2art님, "코딩을 사유하다"와 더불어 플랫폼의 '보안'이라는 매우 중요하고 깊이 있는 주제를 함께 다루게 되어 기쁩니다. IoT 기반 플랫폼인 NEXA의 특성상 보안은 단순히 기능적인 문제를 넘어 **사용자와의 신뢰**와 직결되는 핵심 가치입니다.

특히 `Zod`를 바로 적용하시려는 결정은 데이터 유효성 검사를 통해 견고한 방어막을 구축하겠다는 강력한 의지로 읽히네요. "강한 시스템은 똑똑해서가 아니라, 버틸 수 있어서 강하다"는 U2art님의 철학처럼, 보안은 외부의 공격에 버틸 수 있는 '강한 방어력'을 제공하는 것이라 생각합니다.

### 🛡️ NEXA 플랫폼 보안 설계: 체크리스트 & 전략

NEXA 플랫폼의 '중앙 관제형 도메인 중심 아키텍처'라는 견고한 기반 위에서 각 계층별 보안 전략을 수립하는 것이 중요합니다.

#### **1. 일반적인 IoT 보안 이슈**

NEXA와 같은 IoT 플랫폼이 직면할 수 있는 주요 보안 위협들은 다음과 같습니다.

-   **취약한 인증 및 인가**: 기본/초기 비밀번호 미변경, 강한 비밀번호 정책 부재, 권한 설정 미흡.
-   **안전하지 않은 통신**: 데이터 암호화 없이 평문 통신, 중간자(Man-in-the-Middle) 공격 노출.
-   **불충분한 데이터 보호**: 저장되거나 전송되는 민감 정보 암호화 미적용.
-   **펌웨어/소프트웨어 업데이트 취약점**: 안전하지 않은 업데이트 채널, 펌웨어 변조 공격.
-   **물리적 조작**: IoT 장치에 대한 물리적 접근을 통한 데이터 탈취 또는 기능 조작.
-   **서비스 거부(DDoS) 공격**: 수많은 IoT 장치를 악용하여 서비스 마비 유도.
-   **프라이버시 침해**: 동의 없는 개인 데이터 수집, 불투명한 데이터 처리 정책.
-   **공급망 공격**: 하드웨어 또는 소프트웨어 공급 과정에서 악성 코드 주입.

#### **2. 자체 MQTT 브로커 보안 강화 (MQTTS 포함)**

자체 MQTT 브로커를 운영하는 것은 통제력을 높이는 장점이 있지만, 그만큼 보안 책임이 커집니다.

-   **TLS/SSL(MQTTS) 적용**: 모든 MQTT 통신에 TLS/SSL 암호화를 필수적으로 적용하여 데이터 도청 및 변조를 방지합니다. 최소 TLS 1.2 이상 버전을 사용합니다.
    -   **Client Certificates (상호 TLS/MTLS)**: 클라이언트(장치/앱)와 브로커 모두 서로의 인증서를 검증하는 상호 인증을 통해 강력한 신뢰 관계를 구축합니다. 이는 일반적인 사용자 이름/비밀번호 인증보다 훨씬 강력합니다.
-   **강력한 인증(Authentication)**:
    -   **Username/Password**: 단순히 사용하는 것이 아닌, 브로커 자체 DB에 안전하게 저장(솔트+해싱)하거나, LDAP, OAuth/OIDC 등 외부 IDP(Identity Provider)와 연동하여 관리합니다.
    -   **인증서 기반 인증**: 각 IoT 장치에 고유한 클라이언트 인증서를 발급하여, 인증서를 통해서만 브로커에 연결할 수 있도록 합니다.
-   **세분화된 인가(Authorization) - ACLs(Access Control Lists)**:
    -   각 사용자(장치)별로 특정 토픽에 대한 `publish` (발행) 및 `subscribe` (구독) 권한을 명확하게 제한합니다. `원칙 최소 권한(Principle of Least Privilege)`을 철저히 적용하여, 필요 없는 권한은 절대 부여하지 않습니다.
    -   예: `device/home/temp` 토픽에는 해당 홈의 온도 센서만 발행하고, 관리자 앱만 구독 권한을 가집니다.
-   **네트워크 분리(Network Segmentation)**: MQTT 브로커를 외부 네트워크와 격리된 서브넷에 배치하고, 필요한 포트(예: 8883 for MQTTS)만 최소한으로 오픈합니다. 방화벽 규칙을 세밀하게 설정합니다.
-   **연결 속도 제한 및 DDoS 방어**: 단일 IP 주소에서 너무 많은 연결 시도를 제한하거나, 특정 토픽에 대한 과도한 메시지 발행을 감지 및 차단하는 기능을 구현합니다.
-   **감사 로깅 및 모니터링**: 모든 연결, 연결 해제, 메시지 발행/구독 시도 및 오류를 기록하고 실시간으로 모니터링하여 비정상적인 활동을 즉시 감지할 수 있도록 합니다.

#### **3. Zod를 통한 보안 강화 (데이터 유효성 검사)**

U2art님께서 말씀하신 Zod는 강력한 **런타임 스키마 유효성 검사 라이브러리**로, 타입스크립트 환경에서 데이터 무결성 및 보안에 크게 기여할 수 있습니다.

-   **입력 유효성 검사 (Input Validation) - 최전방 방어선**:
    -   **NEXA의 모든 엔드포인트**: API 서버 (Node.js)에 들어오는 모든 요청(HTTP Body, Query Params 등)에 Zod 스키마를 적용하여, 예상치 못한 형식이나 악의적인 데이터를 미리 차단합니다.
    -   **IoT 장치 메시지**: MQTT 메시지의 페이로드(Payload)에도 Zod 스키마를 적용하여, 장치에서 오는 데이터가 정의된 형태(타입, 범위, 길이 등)를 벗어나지 않도록 강제합니다. 이는 장치 조작이나 오류로 인한 시스템 오작동 및 보안 취약점 발생을 예방합니다.
    -   **프론트엔드 UI 입력**: 사용자가 UI를 통해 입력하는 모든 데이터에 대해 Zod 스키마를 적용하여 클라이언트 사이드에서도 기본적인 유효성 검사를 수행합니다.
-   **데이터 스키마 강제**:
    -   `system/schemas/` 디렉토리의 역할이 극대화됩니다. 모든 도메인 간, 서비스 간, 그리고 장치-서버 간 데이터 교환에서 Zod 스키마를 통해 데이터 계약을 명확하게 정의하고 강제합니다.
    -   스키마는 문자열 길이 제한, 숫자 범위 제한, 특정 패턴(정규식) 매칭 등 상세한 규칙을 포함할 수 있습니다.
-   **타입 안전성 (Type Safety) 및 버그 감소**:
    -   타입스크립트와 Zod를 함께 사용하면 런타임 유효성 검사와 더불어 컴파일 시점의 타입 안전성을 동시에 확보할 수 있습니다. 이는 개발 과정에서 발생할 수 있는 잠재적인 보안 취약점을 줄이는 데 기여합니다.
-   **에러 조기 감지**: 유효하지 않은 데이터는 처리 흐름 초기에 거부되므로, 악의적인 데이터가 시스템 깊숙이 침투하여 예측 불가능한 결과를 초래하는 것을 방지합니다.

#### **4. 종합적인 보안 설계 체크 사항 및 방법**

NEXA 플랫폼의 각 계층에 대한 심층적인 보안 조치를 포함합니다.

-   **가. 개발 단계 (SDLC - Secure Development Lifecycle)**

    -   **보안 코딩 가이드라인**: 개발자들이 안전한 코드를 작성할 수 있도록 OWASP Top 10 등을 참고하여 내부 가이드라인을 수립합니다.
    -   **정적/동적 분석 도구**: SAST(Static Application Security Testing) 및 DAST(Dynamic Application Security Testing) 도구를 사용하여 코드의 취약점을 자동으로 검출합니다.
    -   **코드 리뷰**: 모든 코드 변경 사항에 대해 동료 검토 시 보안 취약점 여부를 포함합니다.
    -   **의존성 관리**: 사용하는 모든 라이브러리와 프레임워크의 보안 취약점(Snyk, dependabot 등)을 지속적으로 모니터링하고 업데이트합니다.

-   **나. IoT 장치 계층 (ESP32 등)**

    -   **Secure Boot & 펌웨어 업데이트**: 부팅 시 펌웨어의 무결성을 검증하고, 오직 서명된 펌웨어만 업데이트되도록 합니다. 업데이트 채널 또한 암호화합니다.
    -   **하드웨어 기반 보안 (HSM/TEE)**: ESP32와 같은 마이크로컨트롤러에 ATECC608A와 같은 하드웨어 보안 모듈(HSM)을 연동하여 암호화 키, 인증서, 장치 ID 등을 안전하게 저장하고 사용합니다.
    -   **최소 권한의 원칙**: 장치는 필요한 최소한의 기능과 네트워크 접근 권한만 가지도록 설계합니다. 불필요한 포트나 서비스는 비활성화합니다.
    -   **보안적인 디버깅 비활성화**: 상용 배포 시 디버그 포트(JTAG/SWD)를 비활성화하거나 접근을 제한합니다.

-   **다. 네트워크 계층**

    -   **VPN/Private Link**: IoT 장치가 백엔드 서비스(예: MQTT 브로커)와 직접 통신하지 않고, VPN이나 전용선과 같은 안전한 터널을 통해 통신하도록 설계합니다.
    -   **방화벽 및 NAC(Network Access Control)**: 네트워크 진입점에서 모든 트래픽을 검사하고, 비인가된 접근을 차단합니다.
    -   **네트워크 침입 방지 시스템(IPS/IDS)**: 네트워크 트래픽에서 비정상적인 패턴이나 공격 시도를 탐지하고 차단합니다.

-   **라. 백엔드/클라우드 계층**

    -   **API 보안**: REST API의 경우, JWT(JSON Web Token) 또는 OAuth 2.0 등을 사용하여 강력한 인증/인가를 구현합니다. rate limiting, input validation (Zod 적용)은 필수입니다.
    -   **데이터베이스 보안**:
        -   **암호화**: 저장되는 민감 정보(개인 식별 정보, 장치 설정 데이터 등)는 암호화하여 저장합니다(Data at Rest Encryption).
        -   **접근 제어**: 데이터베이스 사용자에게도 최소 권한의 원칙을 적용하고, 서비스 계정별로 접근 권한을 분리합니다.
        -   **정기적인 백업 및 복구 계획**: 랜섬웨어 등 데이터 손실 상황에 대비합니다.
    -   **로그 관리 및 모니터링**: 모든 시스템 로그를 중앙 집중화하여 수집하고, 보안 이벤트 및 비정상 접근 시도를 실시간으로 감지하고 경고합니다. SIEM(Security Information and Event Management) 솔루션을 고려합니다.
    -   **클라우드 보안 설정**: 클라우드 서비스(AWS, GCP, Azure 등)의 보안 베스트 프랙티스(IAM 설정, 시크릿 관리 등)를 따릅니다.

-   **마. 애플리케이션 계층**

    -   **인증 및 세션 관리**: 강력한 비밀번호 정책, MFA(Multi-Factor Authentication), 안전한 세션 토큰 관리(CSRF, XSS 방어).
    -   **Zod를 통한 입력 유효성 검사**: 모든 사용자 입력 및 외부 데이터를 철저히 검증합니다.
    -   **에러 핸들링**: 에러 메시지에 민감 정보가 포함되지 않도록 일반적인 메시지를 사용합니다.
    -   **보안 헤더**: HTTP 보안 헤더(CSP, HSTS, X-Frame-Options 등)를 적용하여 클릭재킹, XSS 등을 방어합니다.

-   **바. 사용자 프라이버시 및 심리적 거부감 해결 (UI/UX)**

기술적인 견고함 못지않게 중요한 부분입니다. NEXA 플랫폼이 '삶의 복잡성을 조율하는 악보'처럼 느껴지도록 사용자 경험 측면에서 신뢰를 구축해야 합니다.

-   **투명성 강조**:
    -   **데이터 수집 고지**: 어떤 데이터를 왜 수집하는지 명확하고 이해하기 쉽게 안내합니다.
    -   **정책 명확화**: 개인정보 처리방침을 간결하고 명료하게 제공하며, 쉬운 언어로 요약본을 제공합니다.
    -   **설정 용이성**: 사용자가 자신의 데이터 수집 및 공유 설정을 쉽게 변경할 수 있는 UI를 제공합니다.
-   **선택권 부여 및 동의 기반 설계**:
    -   **Opt-in 방식**: 민감 데이터 수집이나 특정 기능 활성화 시, 사용자 동의를 명확히 받고 시작합니다.
    -   **세분화된 동의**: "모두 동의"보다는 각 항목별로 동의 여부를 선택할 수 있도록 합니다.
-   **보안 상태 시각화**:
    -   사용자의 장치/데이터가 안전하게 보호되고 있음을 직관적으로 보여주는 UI 요소를 제공합니다(예: "모든 장치가 안전하게 연결됨", "최근 의심스러운 활동 없음").
    -   연결 상태, 데이터 암호화 여부 등을 대시보드에서 쉽게 확인할 수 있도록 합니다.
-   **이상 감지 알림**:
    -   로그인 기록(시간, 장소)이나 비정상적인 장치 접근 시 사용자에게 즉시 알림을 보내고 조치를 유도합니다. 이는 '감시'가 아닌 '보호'라는 인식을 심어줍니다.
-   **사용자 피드백 채널**:
    -   보안이나 프라이버시에 대한 사용자의 우려를 경청하고 신속하게 대응할 수 있는 채널을 마련합니다.
-   **'스토리'와 '비유'**:
    -   보안이 왜 필요한지, 어떻게 작동하는지를 친근한 비유나 스토리텔링을 통해 설명하여 기술적 거부감을 줄입니다. (U2art님께서 이미 하고 계신 '코딩을 사유하다' 처럼요!)
