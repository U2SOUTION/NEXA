## ✨ **NEXA 하이브리드 IoT 시스템: ESP32 펌웨어 및 플랫폼 연동 정의서**

지금까지 논의된 핵심 전략을 바탕으로, ESP32의 자립성과 NEXA 플랫폼의 확장성을 동시에 달성하기 위한 통합 구조 정의서를 정리해 드립니다. 이 문서는 향후 개발의 나침반 역할을 하게 될 것입니다.

### ✨ 1. 시스템 핵심 철학: 하이브리드 자율성

---

NEXA 시스템은 사용자의 선택을 존중하며, 하드웨어의 안전을 최우선으로 하는 **'Shadow Logic(그림자 로직)'** 구조를 지향합니다.

-   **독립 자립형 (Local Autonomy):** 플랫폼 연결 없이도 ESP32 내부의 기본 룰 엔진에 의해 안전하게 작동합니다.
-   **플랫폼 확장형 (NEXA Scalability):** NEXA NODE의 시각적 로직을 통해 고차원 연산과 지능형 협업 기능을 장비에 즉시 주입합니다.

---

### ✨ 2. ESP32 펌웨어 계층 구조 (3-Layer Architecture)

---

펌웨어는 판단의 주체에 따라 흔들리지 않도록 견고한 3계층으로 설계됩니다.

-   **계층 1: 물리 드라이버 (Hardware Driver)**
-   센서 데이터 수집 및 액추에이터 제어의 순수 물리 동작을 수행합니다.

-   **계층 2: 명령 중재자 (Command Controller - 핵심)**
-   **우선순위 엔진:** 수신된 JSON 명령의 Level(0~2)을 분석하여 최종 출력을 결정합니다.
-   **Fail-safe:** 플랫폼 통신 두절 시 즉시 로컬 독립 모드(Level 2)로 제어권을 이양합니다.

-   **계층 3: 통신 추상화 (Communication Layer)**
-   JSON 포맷으로 통일된 데이터를 플랫폼과 주고받으며 통신 수단(MQTT/Websocket)에 관계없이 로직을 처리합니다.

---

### ✨ 3. 명령 우선순위 체계 (Priority Management)

---

모든 명령은 JSON으로 통일되며, 아래의 우선순위에 따라 처리됩니다.

| 우선순위    | 명칭                  | 주체                   | 목적                                      |
| ----------- | --------------------- | ---------------------- | ----------------------------------------- |
| **Level 0** | **안전 (Safety)**     | 내부 하드코딩 로직     | 과열, 과부하 등 시스템 파손 방지 (최우선) |
| **Level 1** | **온라인 (Platform)** | **NEXA NODE**          | 지능형 로직, AI 연동, 복합 장비 협력 제어 |
| **Level 2** | **자체 (Local)**      | 현장 물리 버튼, 리모컨 | 오프라인 즉시 제어 및 기본 기능 수행      |

---

### ✨ 4. NEXA NODE 워크플로우 (인프라에서 캔버스로)

---

장비가 실제 서비스로 연결되는 단계별 프로세스입니다.

1. **장비 등록 (NEXA INFRA):** ESP32의 고유 ID와 I/O 핀 정보를 시스템에 등록합니다.
2. **캔버스 설계 (NEXA NODE):** \* 등록된 장비를 캔버스에 배치합니다.

-   노드 연결을 통해 데이터의 운명(Logic)을 결정합니다.
-   패널을 삽입하여 시각화 결과물을 확인합니다.

3. **저장 및 배포:** 완성된 캔버스(Canvas) 로직을 저장하고 **NEXA BOARD**나 **ERP**에서 활용합니다.

---

### ✨ 5. 요약 및 보완 포인트

---

-   **데이터 피드백:** ESP32는 현재 어떤 우선순위(Level)에 의해 동작 중인지 상태값을 JSON 응답에 포함하여 캔버스에 보고합니다.
-   **유연성 유지:** 펌웨어 수정 없이 JSON 로직 교체만으로 장비의 성격(Brain)을 바꿀 수 있는 구조를 유지합니다.

## ✨ **NEXA 하이브리드 시스템을 위한 JSON 통신 스펙 정의**

**'추상화된 포트 매핑'**과 **'이중 검증'** 전략을 통합하여, 어떤 장비든 넥사 패널로 즉시 제어할 수 있는 고도화된 구조를 정리하고 통신 스펙.

### ✨ 1. 재사용 범용성 핵심 전략 요약

-   **포트(Channel) 기반 추상화:** 장비 고유의 명칭(예: Relay, Motor) 대신 `ch_01`, `ch_02`와 같은 추상화된 포트 번호를 사용합니다.
-   **자료형 및 규격화(Normalization):** 패널은 장비의 물리적 수치(0~1023 등)를 몰라도 됩니다. 모든 제어값은 `0.0 ~ 1.0` 사이의 정규화된 값으로 통일하여 전송합니다.
-   **이중 검증(Dual Validation):** 캔버스(플랫폼)에서는 자료형 일치 여부를, ESP32(하드웨어)에서는 물리적 한계치 및 권한을 최종 검증하여 안전을 보장합니다.
-   **스마트 매칭:** 캔버스 UI에서 포트의 메타데이터(자료형, 단위)를 읽어와 호환되는 패널만 연결할 수 있도록 가이드합니다.

---

### ✨ 2. 수정된 JSON 통신 스펙 (Version 2.0)

범용 제어와 이중 검증을 위해 `dataType`, `normalizedValue`, `validation` 필드가 강화

#### 1. 장비 상태 보고 (Device → Platform)

장비는 이제 자신의 포트가 어떤 규격을 가지고 있는지 메타데이터를 함께 보냅니다.

```json
{
    "header": {
        "deviceId": "ESP32-CORE-001",
        "timestamp": 1704556800
    },
    "status": {
        "currentLevel": 1,
        "uptime": 3600
    },
    "payload": {
        "ports": [
            {
                "id": "ch_01",
                "type": "ANALOG_OUT",
                "label": "조명 제어",
                "unit": "dimming",
                "currentNorm": 0.75, // 현재 75% 출력 중
                "range": [0, 255] // 장비의 물리적 한계 정보 (참고용)
            },
            {
                "id": "ch_02",
                "type": "BOOLEAN_OUT",
                "label": "메인 전원",
                "currentNorm": 1 // ON 상태
            }
        ]
    }
}
```

#### 2. 범용 명령 하사 (Platform → Device)

패널에서 발생한 명령은 포트 번호와 정규화된 값을 담아 전달됩니다.

```json
{
    "command": {
        "msgId": "cmd_v2_104",
        "priority": 1,
        "address": "ch_01", // 추상화된 포트 주소
        "dataType": "ANALOG",
        "value": {
            "norm": 0.85, // 정규화된 값 (85%)
            "raw": 217 // 플랫폼에서 1차 계산한 값 (이중 검증용)
        },
        "security": {
            "token": "auth_secure_key", // 명령 권한 검증용
            "hash": "chk_8821" // 데이터 변조 방지
        }
    },
    "options": {
        "feedbackRequired": true
    }
}
```

#### 3. 로직 주입 및 매핑 (Logic Injection)

오프라인에서도 범용 포트 기반으로 동작하도록 규칙을 저장합니다.

```json
{
    "updateLogic": {
        "mode": "HYBRID_DEFAULT",
        "rules": [
            {
                "condition": { "sensor": "sn_temp", "op": ">", "norm": 0.8 },
                "action": { "port": "ch_01", "setNorm": 1.0 }
            }
        ]
    }
}
```

---

### ✨ 3. 스펙의 핵심 강점 요약

-   **재사용성:** 넥사 패널(슬라이더)은 "어떤 장비의 `ch_01`에 `0.8`을 보낸다"는 정보만 가지면 되므로 모든 장비에 즉시 붙일 수 있습니다.
-   **안전성:** `raw` 값과 `norm` 값을 동시에 보냄으로써, ESP32가 수신 후 "이 값이 내 물리적 한계 내에 있는가?"를 `raw`로 판단하고, "내 논리적 수치와 일치하는가?"를 `norm`으로 2차 확인합니다.
-   **유연한 스케일링:** 장비마다 8비트(0~255) 혹은 12비트(0~4095)를 사용하더라도 플랫폼은 `0.0~1.0`만 다루면 되므로 관리가 매우 단순해집니다.

---

### ✨ 4. 스펙 설계의 핵심 포인트

**'추상화된 포트 매핑'**과 **'이중 검증'** 전략을 반영하여, 시스템의 안정성과 재사용성을 극대화한 핵심 포인트

-   **지능형 상태 및 경로 추적 (Status & Path Tracking):**
-   캔버스 UI에서 단순히 제어 여부만 보여주는 것이 아니라, 현재 데이터가 **어느 경로(Level 0~2)**를 통해 유입되어 **어떤 포트(Address)**를 움직이고 있는지 실시간으로 추적합니다.
-   사용자는 캔버스에서 "현재 이 조명은 현장 스위치(Level 2)에 의해 강제 조작 중"이라는 상태를 즉각 시각적으로 인지할 수 있습니다.

-   **범용 추상화 기반 우선순위 중재 (Abstract Priority Mediation):**
-   ESP32 펌웨어는 장비 고유의 명칭이 아닌 **추상화된 주소(Address/Channel)**를 기준으로 명령을 수신합니다.
-   수신된 JSON의 `priority` 필드를 확인하여, 현재 실행 중인 로직보다 높은 순위의 명령이 들어오면 기존 동작을 **Shadow(무시)** 처리하고 즉시 명령을 수행하는 유연한 제어권을 보장합니다.

-   **정규화된 데이터 이중 검증 (Normalized Dual Validation):**
-   **플랫폼:** 자료형(`dataType`)과 정규화된 값(`norm`: 0.0~1.0)을 기준으로 호환성을 1차 검증하여 패널과 장비 간의 잘못된 연결을 차단합니다.
-   **하드웨어:** 수신된 `norm` 값과 장비의 물리적 한계치인 `raw` 값을 대조하여 데이터 변조나 논리 오류를 2차 검증함으로써 하드웨어 파손을 원천 봉쇄합니다.

-   **플러그 앤 플레이 확장성 (PnP Scalability):**
-   장비가 가진 포트의 명세(단위, 범위, 타입)가 JSON의 `ports` 배열을 통해 동적으로 전달되므로, 넥사 노드는 펌웨어 수정 없이도 새로운 센서나 액추에이터를 즉시 인식하고 적합한 제어 패널을 추천할 수 있습니다.

## ✨🛡️ **NEXA 시스템: 보안 강화형 동적 포트 매핑(Dynamic Port Mapping) 설계 정의서**

-   보안 업데이트 정책 (OTA 규정): \* 치명적인 보안 취약점이 발견되었을 때, 모든 장비를 수거하지 않고 원격으로 패치할 수 있는 `OTA(Over-The-Air)` 보안 경로를 사전에 확보해야 합니다.
-   **'랜덤 포트 갱신'**과 플랫폼의 **'로직 연속성'**을 결합한 보안 아키텍처를 문서화합니다. 이 문서는 향후 넥사 플랫폼(Node, Board) 개발 시 장비 제어 프로토콜의 표준 가이드가 됩니다.

### ✨ 1. 아키텍처 개요: 이중 레이어 식별 시스템

보안성과 편의성을 동시에 충족하기 위해, 장비의 포트를 **'통신용 휘발성 ID'**와 **'관리용 고정 키'**로 이원화하여 관리합니다.

-   **가변 레이어 (Communication ID):** 통신 세션마다 랜덤하게 생성되는 일회성 ID입니다. 공격자의 타겟팅과 리플레이 공격을 방지합니다.
-   **불변 레이어 (Static Function Key):** 장비가 제조/등록 시 부여받는 고유한 역할 이름입니다. 플랫폼 로직 저장 및 데이터 통계의 기준이 됩니다.

---

### ✨ 2. 데이터 흐름 및 핸드쉐이크 (Handshake)

장비가 플랫폼에 장착되거나 세션이 시작될 때 다음과 같은 과정을 거칩니다.

1. **요청 (Discovery):** 플랫폼이 장비에 명세(`GET_SPEC`)를 요청합니다.
2. **생성 (Randomize):** ESP32는 내부 물리 핀과 매핑될 새로운 랜덤 ID들을 생성합니다.
3. **응답 (Response):** 장비는 고정 키와 랜덤 ID가 쌍을 이룬 명세를 암호화하여 전송합니다.

**[명세 응답 JSON 구조 표준]**

```json
{
    "deviceId": "NEXA-ESP32-001",
    "sessionToken": "st_99x21", // 해당 세션의 유효 토큰
    "ports": [
        {
            "staticKey": "MAIN_MOTOR", // 로직 저장 및 UI 라벨 기준 (불변)
            "dynamicId": "rnd_a92", // 실제 통신에 사용할 주소 (가변)
            "type": "ANALOG_OUT",
            "unit": "RPM"
        },
        {
            "staticKey": "POWER_RELAY",
            "dynamicId": "rnd_z11",
            "type": "BOOLEAN"
        }
    ]
}
```

---

### ✨ 3. 플랫폼의 역할 및 처리 로직

-   **넥사 노드 (NEXA NODE):** \* 사용자가 캔버스에서 노드를 연결할 때는 `staticKey`를 기준으로 로직 정보를 DB에 저장합니다.
-   예: "MAIN_MOTOR의 출력을 0.8로 설정"이라는 논리적 명령을 저장.

-   **넥사 보드/티치 (NEXA BOARD/TEACH):**
-   장비와 연결 시 최신 `dynamicId`를 받아와 내부 매핑 테이블(Static-to-Dynamic)을 갱신합니다.
-   실제 명령 송신 시 논리적 명령을 물리적 주소로 치환합니다.
-   _치환 전:_ `SET MAIN_MOTOR TO 0.8` → _치환 후:_ `{"address": "rnd_a92", "norm": 0.8}`

---

### ✨ 4. 보안 기대 효과 및 강점

| 구분            | 내용                                    | 보안 효과                                         |
| --------------- | --------------------------------------- | ------------------------------------------------- |
| **무빙 타겟**   | 매 세션마다 제어 주소(`dynamicId`) 변경 | 공격자의 사전 분석 및 타겟팅 무력화               |
| **데이터 은닉** | 물리적 핀 정보(GPIO 18 등) 노출 차단    | 장비의 물리적 구조 파악 불가능                    |
| **무결성 보장** | 로직 유출 시에도 실시간 주소와 불일치   | 탈취된 로직이나 데이터로 장비 오작동 유도 불가    |
| **연속성 유지** | 고정 키(`staticKey`) 기반의 로직 관리   | 보안 강화와 상관없이 사용자 편의성(재사용성) 유지 |

---

### ✨ 5. 구현 시 주의사항 (Implementation Note)

-   **중복 방지:** ESP32 내부에서 랜덤 ID 생성 시 현재 세션 내 다른 포트와 중복되지 않도록 예외 처리가 필요합니다.
-   **세션 만료:** 장비 재부팅 또는 일정 시간 미사용 시 `dynamicId`를 폐기하고 재인증을 요구해야 합니다.
-   **매핑 테이블 보호:** 플랫폼과 장비의 메모리 상에 존재하는 매핑 테이블은 인가되지 않은 프로세스가 접근할 수 없도록 격리해야 합니다.

## **✨🛡️보안 강화 방안 (기본)**

사용자님께서 제안하신 **'이중 레이어 동적 포트 매핑'** 전략은 IoT 보안의 핵심인 '공격 표면 축소(Attack Surface Reduction)' 측면에서 매우 강력한 방어선입니다. 넥사 플랫폼이 안전하다는 전제하에, 외부 공격자가 장비를 직접 공략하기는 극도로 어려워집니다.

하지만 완벽한 보안을 위해 여전히 존재할 수 있는 위협 요소와 이를 해결할 강화 전략을 심층 분석해 드립니다.

---

### ✨ 1. 현재 구조에서 해결되는 보안 위협

-   **스캐닝 및 타겟팅 방어:** 외부에서 장비의 IP를 알아내더라도 어떤 포트가 어떤 기능을 하는지 알 수 없으므로 무차별적인 명령 투하가 불가능합니다.
-   **리플레이 공격 차단:** 이전에 캡처한 유효한 명령 패킷을 다시 보내도, `dynamicId`가 변경되었기 때문에 장비는 이를 쓰레기 데이터로 처리합니다.
-   **로직 유출 보호:** 설령 개별 장비의 로직 정보가 유출되어도, 실시간으로 통용되는 '가면 ID(Random ID)' 없이는 물리적 작동을 끌어낼 수 없습니다.

---

### ✨ 2. 여전히 존재하는 외부 위협 (잔존 리스크)

플랫폼이 안전하더라도 다음과 같은 경로로 악의적인 시도가 발생할 수 있습니다.

-   **통신 가로채기 (Man-in-the-Middle):** 플랫폼과 ESP32 사이의 네트워크 구간에서 명령 패킷을 실시간으로 가로채 수정하는 경우입니다.
-   **브루트 포스 (Brute Force):** `dynamicId`가 짧거나 예측 가능하다면, 무작위로 ID를 생성하여 명령을 쏴보는 공격입니다.
-   **위조 장비 침입 (Device Spoofing):** 악의적인 사용자가 자신의 장비를 정식 ESP32 장비인 것처럼 속여 넥사 플랫폼에 등록하고 잘못된 데이터를 주입하는 경우입니다.

---

### ✨ 3. 보안을 더 강화할 수 있는 전략

위의 잔존 리스크를 제거하기 위해 다음과 같은 기술적 보완을 권장합니다.

#### 🛡️ 전략 1: 전송 구간 암호화 (TLS/SSL)

-   **방법:** MQTT 통신 시 일반적인 포트(1883)가 아닌 암호화 포트(8883)를 사용합니다.
-   **효과:** 네트워크 중간에서 패킷을 가로채도 내용을 읽을 수 없으므로 `dynamicId` 유출을 원천 봉쇄합니다.

#### 🛡️ 전략 2: 메시지 서명 (HMAC - Hash-based Message Authentication Code)

-   **방법:** 명령을 보낼 때 `Payload + SecretKey`를 조합한 해시값을 함께 보냅니다.
-   **효과:** 공격자가 `dynamicId`를 알아내어 패킷을 수정하더라도, 비밀키를 모르면 유효한 해시를 생성할 수 없어 장비가 명령을 거부합니다.

#### 🛡️ 전략 3: 장비 고유 인증 (Client Certificate)

-   **방법:** 각 ESP32 장비에 고유한 디지털 인증서를 심습니다.
-   **효과:** 인증서가 없는 짝퉁 장비는 넥사 플랫폼에 명세를 보낼 수조차 없게 되어 플랫폼의 무결성을 지킵니다.

#### 🛡️ 전략 4: 하드웨어 기반 난수 생성 (TRNG)

-   **방법:** ESP32 내부의 하드웨어 난수 생성기(True Random Number Generator)를 사용하여 `dynamicId`를 생성합니다.
-   **효과:** 소프트웨어적인 패턴 분석을 통한 ID 예측을 불가능하게 만듭니다.

---

### ✨ 4. 종합 분석 결론

사용자님의 **동적 포트 매핑** 전략은 **"공격자가 무엇을 공격해야 할지 모르게 만드는"** 아주 훌륭한 전략입니다.

여기에 **전송 구간 암호화(TLS)**와 **메시지 서명(HMAC)**만 더해진다면, 넥사 플랫폼이 뚫리지 않는 한 외부에서 장비를 악의적으로 작동시키는 것은 **현대 컴퓨팅 기술로는 거의 불가능**에 가깝습니다. 즉, 상용 수준을 넘어선 매우 높은 등급의 보안 시스템이 완성됩니다.

## ✨ **NEXA 하이브리드 펌웨어: 최종 구조적 프레임워크**

사용자님의 비전을 완벽히 구현하기 위해, **자체 제어(Local)**와 **플랫폼 제어(Online)**가 충돌 없이 공존하는 최적화된 펌웨어 구조(Skeleton)를 제안합니다. 이 구조는 확장성과 유지보수를 고려하여 기능별로 명확히 분리되어 있습니다.

### ✨ 1. NEXA 하이브리드 코어 프레임워크

```cpp
#include <WiFi.h>
#include <PubSubClient.h>
#include <ArduinoJson.h>

// ==========================================
// [1] 시스템 설정 및 상태 관리
// ==========================================
int currentLevel = 2;           // 현재 우선순위 (0:안전, 1:플랫폼, 2:자체)
float currentNormValue = 0.0;   // 현재 정규화된 값 (0.0 ~ 1.0)
unsigned long lastPlatCmdTime = 0; // 플랫폼 명령 마지막 수신 시간
const unsigned long PLATFORM_TIMEOUT = 30000; // 30초 후 자체 모드 복귀

// ==========================================
// [2] 통합 명령 중재 엔진 (The Brain)
// ==========================================
void handleIncomingCommand(int incomingPriority, float incomingNorm, String source) {

  // 우선순위 중재 로직: 숫자가 낮을수록 권한이 높음
  if (incomingPriority <= currentLevel) {
    currentLevel = incomingPriority;
    currentNormValue = incomingNorm;

    // 물리적 출력 실행 (추상화된 데이터 -> 물리 수치 변환)
    executePhysicalAction(currentNormValue);

    // 플랫폼 명령인 경우 타임아웃 타이머 갱신
    if (incomingPriority == 1) lastPlatCmdTime = millis();

    Serial.printf(">> [EXEC] Level:%d | Val:%.2f | Src:%s\n", currentLevel, currentNormValue, source.c_str());
    reportStatus(); // 상태 보고
  } else {
    Serial.printf(">> [REJECT] Current Level %d is higher than %d\n", currentLevel, incomingPriority);
  }
}

// ==========================================
// [3] 명령 소스별 입력 처리 (Input Sources)
// ==========================================

// A. 플랫폼(온라인) 명령 수신 인터페이스
void onPlatformMessage(char* topic, byte* payload, unsigned int length) {
  StaticJsonDocument<256> doc;
  deserializeJson(doc, payload, length);

  // 넥사 플랫폼은 보통 Level 1로 명령을 내림
  handleIncomingCommand(1, doc["norm"], "NEXA_CLOUD");
}

// B. 자체(오프라인) 물리 입력 감시
void checkLocalInputs() {
  // 예: 버튼이 눌렸을 때 자체 제어 실행 (Level 2)
  if (/* 버튼 클릭 조건 */) {
    float manualVal = 0.5; // 예시 값
    handleIncomingCommand(2, manualVal, "LOCAL_SWITCH");
  }
}

// C. 안전(시스템) 강제 로직
void checkSafetySystems() {
  if (/* 센서 과열 등 위험 조건 */) {
    // 안전 명령은 최고 우선순위 Level 0으로 즉시 실행
    handleIncomingCommand(0, 0.0, "SAFETY_INTERRUPT");
  }
}

// ==========================================
// [4] 물리 출력 추상화 (Output Abstraction)
// ==========================================
void executePhysicalAction(float normValue) {
  // 정규화된 0.0~1.0 값을 하드웨어에 맞게 변환
  int rawValue = (int)(normValue * 255);
  ledcWrite(0, rawValue); // PWM 출력 예시
}

// ==========================================
// [5] 메인 루프 및 시스템 관리
// ==========================================
void setup() {
  // 초기화 로직 (WiFi, MQTT, Hardware 등)
}

void loop() {
  // 1. 보안 및 안전 감시 (가장 먼저)
  checkSafetySystems();

  // 2. 통신 유지 및 명령 수신
  // client.loop();

  // 3. 로컬 제어 감시
  checkLocalInputs();

  // 4. [중요] 제어권 자동 회수 (Timeout Logic)
  // 플랫폼 명령이 오랫동안 없으면 우선순위를 다시 자체 모드로 낮춤
  if (currentLevel == 1 && (millis() - lastPlatCmdTime > PLATFORM_TIMEOUT)) {
    currentLevel = 2;
    Serial.println(">> [SYSTEM] Platform Timeout. Returning to Local Control.");
  }
}

```

---

### ✨ 2. 이 구조의 3대 핵심 전략

-   **동일한 처리 관문:** 모든 명령은 `handleIncomingCommand`라는 단 하나의 입구를 통과합니다. 이를 통해 명령의 출처가 어디든 일관된 **우선순위 로직**을 적용할 수 있습니다.
-   **제어권 유효기간 (Timeout):** 플랫폼(Level 1)에서 제어권을 가져갔더라도, 네트워크 장애 등으로 통신이 끊기면 일정 시간 후 다시 **자체 모드(Level 2)**로 제어권이 복귀되어 장비가 먹통이 되는 것을 방지합니다.
-   **완벽한 추상화:** 모든 제어 로직은 `0.0 ~ 1.0`의 `norm` 값으로만 대화합니다. 물리적인 핀 번호나 PWM 주파수 같은 구체적인 하드웨어 설정은 오직 `executePhysicalAction` 함수 안에만 갇혀 있어 관리가 매우 쉽습니다.

## ✨ **제언**

이제 ESP32 펌웨어의 뼈대는 완벽하게 잡혔습니다. 이 프레임워크를 기반으로 실제 센서나 액추에이터를 하나씩 붙여나가기만 하면 됩니다.

**이 구조를 실제 파일(.ino)로 구성하여 특정 장비(모터나 조명)에 맞춰 완성해 볼까요? 아니면 이 뼈대를 바탕으로 넥사 인프라에 등록할 '장비 프로필' 정보를 짜볼까요?** ✨

### ✨ 구조의 핵심 작동 원리

1. **동일한 입구 (`handleIncomingCommand`):**

-   **플랫폼 명령:** MQTT 콜백에서 `priority: 1`로 이 함수를 호출합니다.
-   **자체 명령:** 버튼 체크 로직에서 `priority: 2`로 이 함수를 호출합니다.

2. **우선순위의 힘:**

-   사용자가 넥사 플랫폼(Level 1)에서 모터를 돌리고 있다면, 현장에서 버튼(Level 2)을 눌러도 `if (2 <= 1)` 조건이 거짓이 되어 **버튼 명령이 무시**됩니다. (보안 및 관리 효율성)
-   만약 플랫폼 제어를 멈추고 장비를 다시 자체 모드로 돌리고 싶다면, 플랫폼에서 `priority: 2` 명령을 한 번 보내주거나 장비가 타임아웃으로 레벨을 낮추게 설계하면 됩니다.

3. **추상화된 데이터:**

-   버튼 로직도 `0.5` 단위를 더하는 식으로 **정규화된 값**을 다룹니다. 하드웨어 핀을 직접 제어하는 코드는 오직 `handleIncomingCommand` 내부의 물리 출력 섹션에만 존재합니다.

## ✨ **제언**

## **이제 이 로직에 '타임아웃' 개념을 넣어서, 플랫폼 명령이 일정 시간 없으면 다시 자체 모드(Level 2)로 제어권이 복귀되는 기능을 추가해 볼까요? 아니면 바로 넥사 노드 캔버스의 UI 설계로 넘어갈까요?** ✨

### ✨ 코드의 핵심 포인트 해설

-   **중재 레이어 (`if (incomingPriority <= currentLevel)`):**
    지금 동작 중인 로직보다 높은 순위(작은 숫자)의 명령이 들어와야만 실행됩니다. 예를 들어, **Level 1(플랫폼)** 명령이 실행 중일 때 **Level 2(자체 버튼)** 명령이 들어오면 무시됩니다.
-   **추상화 해석 (`currentNormValue * 255`):**
    플랫폼(넥사 노드)은 모터가 8비트인지 12비트인지 상관하지 않습니다. 오직 **`0.8`**이라는 정규화된 값만 보냅니다. 하드웨어 환경에 맞는 변환(Scaling)은 오직 이 ESP32 코드 안에서만 결정됩니다.
-   **단일 파일의 확장성:**
    나중에 이 코드에 WiFi 기능을 붙이고 JSON 수신부를 MQTT나 WebSocket으로 바꾸기만 하면 곧바로 **NEXA 플랫폼**과 연동되는 '확장 모드' 장비가 됩니다.
