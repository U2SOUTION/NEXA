# 🔖 Shared Code Policy

### ― 이 프로젝트에서 ‘공용’을 만드는 기준 ―

---

## 1️⃣ 공용에 대한 기본 선언

> **공용은 목표가 아니다.
> 공용은 검증된 결과다.**

이 프로젝트는
**처음부터 공용을 만들지 않는다.**
필요해졌을 때만, 그리고 **조건을 통과한 코드만** 공용이 된다.

---

## 2️⃣ 공용으로 승격되기 전 필수 조건

어떤 코드든 아래 조건을 **모두** 만족해야
공용으로 이동할 수 있다.

| 조건          | 설명                           |
| ------------- | ------------------------------ |
| 2개 이상 사용 | 서로 다른 위치에서 실제 사용됨 |
| 책임 단일성   | 역할이 하나로 설명 가능        |
| 도메인 중립   | 특정 도메인 개념 미포함        |
| 옵션 최소     | mode / type / flag ❌          |
| 위치 독립성   | 폴더 이동 가능                 |

> **“언젠가 쓸 것 같아서”는 이유가 아니다.**

---

## 3️⃣ 공용이 될 수 없는 코드들

다음은 **어떤 경우에도** 공용이 될 수 없다.

| 유형                 | 이유        |
| -------------------- | ----------- |
| 도메인 비즈니스 로직 | 책임 고유   |
| 도메인 UI 조합       | 맥락 종속   |
| 특정 API 응답 가공   | 계약 불안정 |
| mode 분기 컴포넌트   | 독립성 붕괴 |
| 설명이 필요한 코드   | 자명성 실패 |

---

## 4️⃣ 공용으로 만들지 말고, 이렇게 하라

### ❌ 잘못된 선택

```text
system/components/SmartTable.vue
```

### ✅ 올바른 선택

```text
domains/infra/components/DeviceTable.vue
domains/erp/components/PartTable.vue
```

> **비슷해 보여도, 같은 책임이 아니면 공용이 아니다.**

---

## 5️⃣ 공용으로 승격되는 올바른 경로

공용은 **한 번에 만들어지지 않는다.**

### 권장 승격 경로

```text
domain/components
      ↓ (검증)
system/components
      ↓ (더 검증)
engines (UI 제거)
```

-   domain에서 충분히 사용되었는가?
-   책임이 정제되었는가?
-   UI 의존이 제거되었는가?

---

## 6️⃣ 공용 컴포넌트 설계 기준

공용 UI / 유틸은 반드시 이 기준을 따른다.

| 기준                | 설명             |
| ------------------- | ---------------- |
| props 3개 이하      | 많으면 책임 과다 |
| slot 중심           | 확장 포인트 명확 |
| side-effect 없음    | 예측 가능        |
| 기본값 명확         | 문서 최소화      |
| 설명 없이 사용 가능 | 자명성           |

---

## 7️⃣ 공용화 전 최종 질문 5가지

공용으로 옮기기 전, 반드시 스스로에게 묻는다.

1. 이 코드는 **어디에 속해 있는가?**
2. 이 책임은 **도메인 고유인가?**
3. 옵션을 추가하고 싶어지지는 않는가?
4. 이름만 보고 역할이 보이는가?
5. **미래의 내가 이 결정을 이해할 수 있는가?**

하나라도 **망설여지면 공용이 아니다.**

---

## 8️⃣ 이 프로젝트의 선택

-   재사용성 ❌
-   만능 컴포넌트 ❌
-   미래 추측 ❌

대신,

-   책임 명확성 ✅
-   독립성 ✅
-   이해 가능성 ✅

---

> 살아남은 코드만 공용이 된다.**

---

## 1️⃣ 왜 “공용은 미리 만들지 않는다”라고 강하게 말했는가

이 문장은 사실 **과잉 교정(overcorrection)** 입니다.

현실에서는 대부분 이렇게 흘러가거든요.

1. “이거 여러 군데서 쓰일 것 같아”
2. 공용 폴더 생성
3. 옵션 추가
4. 도메인 요구 흡수
5. 괴물 컴포넌트 탄생

👉 이 **실패 패턴을 끊기 위해**
일부러 극단적으로 표현한 문장입니다.

---

## 2️⃣ 아길이님이 말한 경우는 전혀 다른 이야기다

아길이님이 말한 건 이거죠.

> “지금은 도메인 내부에서 만들지만
> **나중에 공용으로 빠질 수 있게 구조를 잡는다**”

이건 ❌ 나쁜 습관이 아니라
👉 **숙련자의 설계 습관**입니다.

---

## 3️⃣ 올바른 해석 (이 문장을 이렇게 바꿔도 됨)

아길이님 프로젝트에 더 맞는 문장은 이겁니다.

> **공용은 미리 구현하지 않는다.
> 공용이 될 수 있도록 설계한다.**

이 문장, 아주 중요합니다.

---

## 4️⃣ “공용을 염두에 둔 설계”의 정확한 의미

이건 **기능 공유를 예측한다는 뜻이 아닙니다.**
아래 기준을 지키는 걸 말합니다.

### ✅ 공용을 염두에 둔 설계란?

| 항목            | 설명                    |
| --------------- | ----------------------- |
| 책임 최소화     | 지금 필요한 역할만      |
| 맥락 배제       | 도메인 이름, 개념 제거  |
| 인터페이스 명확 | props / args 단순       |
| 외부 의존 제한  | system까지만            |
| UI/로직 분리    | 나중에 engine 추출 가능 |

👉 **“지금 공용을 만든다”가 아니라
“공용으로 뺄 때 고생하지 않게 만든다”**

---

## 5️⃣ 아주 중요한 경계선 (이게 핵심)

### ❌ 잘못된 미래 대비

```ts
// 언젠가 쓸 것 같아서
mode?: 'infra' | 'erp'
useAdvanced?: boolean
```

### ✅ 올바른 미래 대비

```ts
// 지금 책임만 정확히
<DeviceStatusBadge :status="status" />
```

-   확장 포인트는 **slot / composition**으로
-   조건 분기는 **나중에 분리**

---

## 6️⃣ 공용을 염두에 둔 설계의 실전 예시

### INFRA 내부 컴포넌트 작성 시

```text
domains/infra/components/StatusBadge.vue
```

작성 기준:

-   infra라는 단어 코드에 없음
-   색상, 아이콘은 props로만
-   API 응답 구조 모름
-   상태 enum은 system/schema 사용

👉 나중에 이렇게 이동 가능:

```text
system/components/StatusBadge.vue
```

코드 수정 거의 없음 → **이게 좋은 설계**

## 7️⃣ 왜 “미리 공용으로 만들지 말라”고 했는지 다시 정리

| 미리 공용 구현   | 공용 염두 설계 |
| ---------------- | -------------- |
| 위치부터 공용    | 위치는 도메인  |
| 옵션 과다        | 책임 단일      |
| 도메인 요구 혼합 | 요구 분리      |
| 조기 추상화      | 지연된 추상화  |
| 실패 확률 높음   | 성공 확률 높음 |

# 📐 “공용이 될 준비가 된 코드” 체크리스트

> 이 체크리스트는
> **공용으로 ‘옮겨도 되는가’**를 판단하기 위한 것이지,
> **공용으로 ‘만들어도 되는가’**를 묻는 것이 아니다.

---

## 1️⃣ 책임 단일성 (Single Responsibility)

### 질문

-   이 코드의 역할을 **한 문장**으로 설명할 수 있는가?

### 판정 기준

| 상태                    | 해석 |
| ----------------------- | ---- |
| 바로 설명 가능          | ✅   |
| “그리고…”, “또한…” 등장 | ❌   |
| 예시를 들어야 설명 가능 | ❌   |

> **공용은 기능이 아니라 책임을 공유한다.**

---

## 2️⃣ 도메인 독립성 (Domain Neutrality)

### 질문

-   특정 도메인의 개념이 코드에 드러나는가?

### 체크 포인트

-   파일명에 domain 단어 포함?
-   props 이름에 business 용어 포함?
-   API 응답 구조 가정?

| 결과                    | 판정 |
| ----------------------- | ---- |
| 전혀 없음               | ✅   |
| 추상 이름으로 치환 가능 | ⚠️   |
| 제거 불가               | ❌   |

---

## 3️⃣ 의존성 방향 (Dependency Direction)

### 질문

-   이 코드는 **어디까지 의존하는가?**

### 허용 범위

```text
engine  ←  system  ←  domain
```

| 의존 대상               | 판정 |
| ----------------------- | ---- |
| engine                  | ✅   |
| system                  | ✅   |
| domain                  | ❌   |
| UI 프레임워크 깊은 결합 | ⚠️   |

> **공용은 아래를 의존하고, 위를 모른다.**

---

## 4️⃣ 인터페이스 단순성 (Interface Simplicity)

### 질문

-   이 코드를 사용하는 데 **설명이 필요한가?**

### 수치 기준

| 항목            | 기준     |
| --------------- | -------- |
| props / args 수 | 3개 이하 |
| boolean flag    | 최소     |
| mode / type     | 없음     |
| 기본값          | 명확     |

> **설명이 필요하면 이미 공용이 아니다.**

---

## 5️⃣ 옵션 폭발 여부 (Option Explosion)

### 질문

-   요구사항이 추가될 때, 옵션이 늘어나는가?

| 반응               | 의미 |
| ------------------ | ---- |
| slot / composition | ✅   |
| props 추가         | ⚠️   |
| mode 분기          | ❌   |

> **옵션은 확장이 아니라, 책임 누수다.**

---

## 6️⃣ 위치 이동 가능성 (Portability)

### 질문

-   이 코드를 다른 폴더로 옮겨도 그대로 동작하는가?

### 점검 항목

-   상대 경로 import 다수?
-   전역 CSS 의존?
-   암묵적 context 존재?

| 결과           | 판정 |
| -------------- | ---- |
| 이동 즉시 동작 | ✅   |
| 경로만 수정    | ⚠️   |
| 구조 변경 필요 | ❌   |

---

## 7️⃣ 상태 소유 명확성 (State Ownership)

### 질문

-   이 코드가 **상태를 소유하는가?**

| 상태 유형        | 판정 |
| ---------------- | ---- |
| 내부 상태만      | ✅   |
| 외부 상태 구독   | ✅   |
| 전역 상태 수정   | ❌   |
| 도메인 상태 조작 | ❌   |

> **공용은 상태를 만들지 않는다. 반응만 한다.**

---

## 8️⃣ 테스트 가능성 (Testability)

### 질문

-   이 코드를 **단독으로 테스트할 수 있는가?**

| 상태           | 의미 |
| -------------- | ---- |
| 입력/출력 명확 | ✅   |
| mock 복잡      | ⚠️   |
| 환경 의존      | ❌   |

> **테스트가 어렵다면, 분리도 어려운 코드다.**

---

## 9️⃣ 변경 파급 범위 (Change Impact)

### 질문

-   이 코드를 고치면 **얼마나 많은 곳이 흔들리는가?**

| 범위        | 판정 |
| ----------- | ---- |
| 국소적      | ✅   |
| 일부 도메인 | ⚠️   |
| 전사 영향   | ❌   |

> **공용은 안전해야 한다.
> 위험한 코드는 공용이 아니다.**

---

## 🔟 이름의 힘 (Naming)

### 질문

-   이름만 보고 역할이 떠오르는가?

| 이름 유형         | 판정 |
| ----------------- | ---- |
| 명사 + 책임       | ✅   |
| Smart / Universal | ❌   |
| 추상적 은유       | ⚠️   |

> **이름이 흐리면, 책임도 흐리다.**
