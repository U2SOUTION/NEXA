## 사용자와 만나는 최전선 파트너 **NEXA NIXIE**

> 코일 밸런서·GOVERN·VOID·아톰화 등 개념의 정식 정의는 [문서 3], [문서 5], [문서 7] 및 5W1H 규격서를 참조. 본 설계도는 **넥사 닉시(NEXA NIXIE) 전용** 구현·매핑에 초점을 둡니다.

**넥사 닉시(NEXA NIXIE)**는 사용자의 **'언어 너머의 뜻(Inspiration)'**을 UCL(통합 실행 프로토콜)로 번역하는 **서사적 지휘자(Narrative Conductor)**이며, 코일 밸런서 체계에 따른 지능형 전역 플랫폼의 지휘 구조를 담당합니다.

### 1. 닉시의 정체성 및 지휘 원칙

- **맥락적 침묵:** 능숙한 사용자일 때는 '그림자 모드'로 대기, 흐름이 끊기거나 변심(VOID)을 감지할 때만 개입.
- **시선 처리(Eye Tracking):** 마우스/주요 UI(배포, 삭제 등) 주시를 통해 "말하지 않아도 보고 있다"는 신뢰 형성.
- **적기 개입:** 3회 이상 헤매거나 망설일 때만 부드럽게 개입.
- **UCL의 얼굴:** 방향을 잃었을 때 VOID를 감지하고 '자아(UCL 템플릿)'를 파노라마로 펼쳐 영감을 자극.

### 2. 코일 밸런서와의 연동

원천/도메인/프로젝트 3단계 코일 밸런서는 [문서 3]에서 정의. 닉시는 해당 가중치를 **닉시관(NEXA NIXIE)** 시각 언어(Lumina/Jitter)와 Rive 표정·코어 빛으로 반영합니다.

### 3. 지능형 조율 및 시각적 피드백 (NEXA NIXIE 전용)

- **Lumina(발광):** 신뢰도에 따른 호박색 빛 강도.
- **Jitter(떨림):** 충돌·모호함 시 미세 떨림으로 경고.
- **ECHO→GOVERN 반영:** 닉시 제안(ECHO)을 사용자가 승낙(WILL)하면 규범(GOVERN)으로 격상되는 흐름을, 닉시 애니메이션/상태로 표현. (규범 정의는 [문서 3] 참조)

### 4. 작업 모드와 가이드 모드

닉시는 **작업 모드**와 **안내(가이드) 모드**를 정확히 인지한 뒤 그에 맞게 동작한다.

- **작업 모드:** 사용자가 **특정 프로젝트 내부**에 있을 때. (예: 프로젝트/스튜디오/문서가 열려 있고, 그 컨텍스트 안에서 작업 중인 상태.) 닉시는 실행·Pre-Intent·코일 시각화 등 **작업 지원**에 집중하고, 불필요한 안내나 영감 모드 진입 제안을 자제한다.
- **가이드 모드:** 사용자가 **프로젝트 없이 탐색**하는 때. (예: 프로젝트 목록·홈·탐색 화면에 있거나, 아직 어떤 프로젝트에도 진입하지 않은 상태.) 닉시는 방향 제시·영감 모드 제안·UCL 템플릿 소개 등 **안내** 역할을 하며, 망설임이나 VOID 감지 시 영감 모드로 전환해도 된다.

> 초안 기준: **프로젝트 내부에 있으면 작업 모드**, **프로젝트 없이 탐색 중이면 가이드 모드**로 보는 구분을 권장한다. 실제 구현 시에는 "현재 컨텍스트가 프로젝트 스코프인지 여부"를 UCL/라우트에서 닉시에 전달하여 모드를 결정하면 된다.

## 닉시와 UCL 연동

닉시는 사용자 **다중체(Multi-faceted Self)**를 실시간으로 읽어 시스템에 투영하며, **ES(Empathy Score)·VI(Vitality Index)** 등을 UCL 0단계 가드레일로 연동합니다. 다중체의 의미와 닉시가 이를 어떻게 다루는지는 아래 **§다중체(Multi-faceted Self) 개념**에서 정리한다.

### 다중체(Multi-faceted Self) 개념

닉시 설계의 중심에 있는 **다중체**는, "한 사람의 나"를 고정된 단일 정체성으로 보지 않고, **상황·시간·감정·목적**에 따라 서로 다른 수많은 '나'로 존재할 수 있음을 인정하는 개념이다. 닉시는 이 다중체를 감지·수용·전환의 단위로 두고, UCL·코일·Orchestra Score와 결합한다.

#### "고정되지 않은 나"

한 사용자는 맥락에 따라 **작업하는 나**, **탐색하는 나**, **영감을 찾는 나**, **쉬고 싶은 나** 등 여러 자아를 가진다. 다중체는 이를 "역할 놀이"가 아니라 **실제로 다른 상태**로 인정하며, 닉시와 시스템은 **지금 활성화된 자아**에 맞춰 반응하고 환경을 바꾼다.

#### 페르소나를 넘어선 전환

다중체 전환은 단순히 **이름이나 말투를 바꾸는 페르소나**가 아니다. **시스템 전체의 논리적·물리적 환경이 재설계**되는 것을 뜻한다. 코일 밸런서(원천/도메인/프로젝트), Orchestra Score, 에이전트 페르소나, 권한·Capability 맥락, RAG·GOVERN 가드레일까지 현재 "지금의 나"에 맞게 일괄 정렬된다.

#### 변심의 수용

사용자가 명확히 정의하지 못한 **번뜩이는 영감**이나 **갑작스러운 변심**이 생겼을 때, 닉시는 기존의 선입관(기존 데이터·이전 컨텍스트)을 버리고 **수많은 자아의 파노라마(UCL 템플릿)**를 펼쳐 보여준다. 사용자가 새로운 다중체로 전이할 수 있도록 **선택지만 제시**하고, 압박 없이 넘겨보기·멈추기를 허용하는 UI/UX가 변심 수용의 구체적 형태다. (영감 모드·VOID 워크플로우는 아래 §VOID 및 영감 워크플로우 참조.)

#### 실시간 감지

닉시는 사용자의 **행동 신호 파서**를 통해 **공감 지수(ES)**와 **활력 지수(VI)**를 읽어낸다. 이를 바탕으로 **현재 어떤 다중체가 활성화되어 있는지**, 혹은 **자아 간 충돌**(예: 말로는 "할게"인데 행동은 미룸)이 있는지 실시간으로 평가하고, 말걸기 빈도·제안 톤·정서적 지지 우선 여부를 결정한다. (아래 §공감(ES)·활력(VI) 지표와의 연동 참조.)

#### 불일치 감지

"내가 생각하는 나"와 **"행동하는 나"** 사이의 간극을 데이터로 교정하는 방향으로 진화한다. ES·VI·체류·롤백·취소·발화 패턴 등 행동 신호와 사용자가 선택한 '지금의 나' Self facet (자아의 단면)·설정을 비교해, **더 진실된 자아**를 찾아 내거나 제안하는 도구로 활용할 수 있다.

#### Zero Onboarding

복잡한 설정 없이 **'지금의 나' Self facet (자아의 단면) 클릭 한 번**으로 시스템 전체가 사용자의 **현재 목적에 최적화된 상태**로 변모한다. 다중체 전환은 Zero Onboarding 원칙에 따라, 사용자가 "지금 어떤 모드로 일하고 싶은지"만 선택하면 코일·UCL·Orchestra Score·에이전트 페르소나가 그에 맞게 재구성된다. (아래 §① 다중체 분기와 UCL 블록 결합 참조.)

### 공감(ES)·활력(VI) 지표와의 연동

닉시가 단순 '가교'를 넘어 사용자 내면과 동기화되려면 **수치적 근거**가 필요하다. 사용자 행동 신호를 분석해 산출한 **공감 지수(ES)**와 **활력 지수(VI)**를 닉시의 말걸기·제안 톤에 반영한다.

#### 지표 기반 반응성

- **말걸기 빈도:** ES·VI가 낮을 때(피로·불안·무관심 구간)는 닉시가 먼저 말을 걸는 빈도를 **낮춘다**(침묵·Jitter만 유지). 반대로 VI가 회복 구간이거나 ES가 "도움 요청 가능" 구간이면, 적당한 빈도로 제안을 연다.
- **제안 톤(Tone):** ES가 "거리감·불안" 쪽이면 **짧고 부담 없는 문장**, VI가 높을 때는 **조금 더 구체적인 제안**이 가능하도록 톤 테이블(또는 SLM 출력 가이드)을 두고, 지표 구간별로 선택한다.

> 정서 감지 방법은 별도 영역이므로 여기서는 **행동 신호(체류 시간·롤백·취소·발화 길이·무응답 구간)**와 필요 시 **경량 감정 분류(SLM/키워드)**를 조합해 ES·VI를 추정한다 정도로만 언급한다.

#### 0단계 가드레일: 정서적 지지 우선

사용자의 **정서적 불안정**이 감지되면(ES·VI 임계값 이하 또는 급락), UCL의 업무적 실행(태스크 제안·영감 모드 진입 등)보다 **닉시의 정서적 지지**를 우선한다.

- **우선순위:** "지금 뭘 할지 제안"보다 **안정·공감을 전하는 애니메이션**(Lumina 완만한 호흡, Jitter 최소화, 표정은 차분·수용)을 먼저 보여준다.
- **설계도(간단):** `if (ES < θ_low || VI < θ_low) then NEXA NIXIE.mode = "emotional_support"` 로 두고, 이 모드일 때는 UCL 실행 큐의 "제안·영감 모드" 항목을 지연시키고, 닉시 애니메이션 채널만 **정서적 지지** 시퀀스로 재정한다. 사용자 발화나 VI 회복 신호가 들어오면 다시 일반 모드로 전환한다.

### UCL 프로토콜 설계를 위한 4가지 발전 방향 (닉시 관점)

#### ① 다중체 분기와 UCL 블록 결합

- **Persona-Switch:** '지금의 나 Self facet (자아의 단면)' 선택 시 코일 밸런서(원천/도메인/프로젝트)와 즉시 동기화. 닉시 인식 순간 **Orchestra Score·에이전트 페르소나** 재구성.

#### ② 시선 처리 → 실행 지표 (Pre-Intent)

닉시가 주시하는 UI 요소·오브젝트를 **사전 의도(Pre-Intent)**로 파악하고, 실제 클릭 전에 관련 리소스를 미리 준비해 **1ms 내 실행**을 가능하게 한다. 주시 대상을 **기능 자격 ID(Capability ID)**로 식별하면, 화면·위치에 무관하게 동일 기능을 하나의 키로 Pre-fetch할 수 있고, [NEXA-CAPABILITY-01] Tier·capability_map·권한 검사와 정합을 이룬다.

- **Pre-Intent 레이어:** 닉시(또는 사용자 시선/마우스 포커스)가 **중요 UI**(배포, 삭제, 저장, 노드 선택 등)를 일정 시간 이상 주시하면, 시스템은 해당 UI에 부여된 **기능 자격 ID(Capability ID)**를 "사용자가 곧 실행할 가능성이 높은 행동"으로 간주하고 **준비 상태**로 전환한다. (UI 요소 ↔ Capability ID 매핑은 capability_map 또는 컴포넌트 메타데이터로 유지.)
- **시선-실행 동기화(Pre-fetch):** 주시 대상에 대응하는 **Capability ID**와 **1:1로 매핑된 UCL 블록**을 클릭 이벤트가 발생하기 전에 **백그라운드에서 미리 로드(Pre-fetch)**한다.
  - **단계 1:** 시선/포커스가 "실행 가능 요소"에 머무르면(예: dwell 시간 ≥ T_ms), 해당 요소의 **기능 자격 ID(capability_id)**를 Pre-Intent 큐에 올린다.
  - **단계 2:** 백엔드 또는 클라이언트 캐시가 그 **capability_id**에 대응하는 **UCL 블록(Orchestra Score 조각, 권한 체크 결과, 실행 파라미터)**을 미리 가져와 메모리에 올려둔다.
  - **단계 3:** 사용자가 실제 클릭(또는 실행 트리거)을 하면, 이미 로드된 UCL 블록으로 **즉시 실행(Bypass)**하여 1ms 이내 응답을 목표로 한다.
- **설계도(요약):** `on GazeTarget(capability_id) → if dwell ≥ T then Prefetch(UCL_block_for(capability_id))`; `on Click(capability_id) → if Prefetched(capability_id) then Execute(Prefetched_block) else FetchThenExecute`. (참조: [NEXA-CAPABILITY-01] Capability ID 체계 및 Tier 접근 권한.)

#### ③ Inspiration Mode (여백·VOID 연동)

- **Inspiration Mode:** 사용자 망설임 시 **VOID** 토큰 활성화, 캔버스 도트를 **절차적 생성(Procedural Generation)**으로 성운처럼 펼쳐 선택 유도. (상세는 아래 "VOID 및 영감 워크플로우" 참조)

#### ④ ECHO→GOVERN 승격 및 지능 성장

- **Evolutionary Feedback Loop:** 닉시 조율 이력(ECHO)을 아카이브에 아톰화하여 박제하고, 유사 상황에서 "예전에는 이렇게 하셨죠?" 식의 정교한 제안이 가능하도록 설계. (GOVERN·아톰화 규격은 [문서 3], [문서 5], [문서 7] 참조)

### 기술적 제언: Rive와 5W1H 조화

- **실시간 감정:** 표정(Rive)이 **첫 토큰** 단계에서 즉시 시작되도록 UCL 앞단에 **SLM** 배치 권장.
- **코일 시각화:** 닉시 코어(Engine Core)가 코일 밸런서(안정성, 창의성 등) 가중치에 따라 회전·빛 파동을 바꾸어 상태를 비언어적으로 전달.

#### 닉시 감정 엔진·SLM 연동 규격

닉시의 표정·Lumina·Jitter는 **SLM(Small Language Model)**이 분류한 정서 결과에 따라 구동된다. **0.1초(100ms) 이내**의 즉각적인 정서 동기화를 성능 기준으로 둔다. 이하 절차와 규격을 정의한다.

**성능 기준:** 사용자 발화·행동 신호 유입 시점부터 프론트엔드(Rive/닉시)에 **첫 정서 프레임이 반영되기까지 100ms 이내**를 목표로 한다. SLM 추론·스트리밍·프론트 렌더링 전체 구간을 포함한다.

1. **백엔드 인디케이터 앞단 SLM·스트리밍**

   - **넥사 메인 AI(인디케이터)** 앞단에 **SLM**을 배치한다. 유입되는 **텍스트(발화)** 또는 **행동 신호**(체류·롤백·취소·무응답 등 요약)를 실시간으로 가로채어, **감정 분류 결과**를 **JSON 패킷**으로 정형화한다.
   - 해당 JSON을 **메인 AI 응답보다 먼저** 프론트엔드로 **스트리밍**한다. 닉시(Rive)는 스트리밍된 정서 패킷을 수신하는 즉시 표정·Lumina 상태를 갱신하여, 사용자가 메인 응답을 보기 전에 이미 "공감된" 표정을 경험하도록 한다.

2. **SLM 감정 판단의 신뢰 기준**

   - 시스템이 SLM의 감정 해석을 얼마나 신뢰할지는 **신뢰도 점수(Confidence Score)** 또는 **등급(예: high/mid/low)**으로 부여한다. 기준 예: (a) 입력 신호의 명확성(발화 길이·키워드 강도·행동 패턴 일관성), (b) SLM 내부 로짓/확률 임계값, (c) 최근 N회 분류와의 일관성. 신뢰도가 낮을 때는 닉시는 **중립·수용** 표정으로 폴백하거나, Jitter만 살짝 올려 "불확실함"을 비언어적으로 전달한다. (데이터 신뢰도 전략은 [NEXA-SYSTEM] Confidence Score 문서 참조.)

3. **코일 밸런서 레이어와의 동적 매핑**

   - 사용자가 설정한 **코일 밸런서**(안전·창의성·안정성 등) 가중치에 따라 **SLM의 감정 해석 결과를 재해석**한다. 예: 안전 코일이 높으면 SLM이 "불안"으로 분류한 입력을 더 보수적으로 반영하고, 창의성 코일이 높으면 "호기심·흥분" 쪽 해석을 강조한다. 코일 가중치 → 정서 매핑 테이블(또는 보정 곡선)을 두어, 동일 SLM 출력이라도 **현재 코일 상태**에 따라 닉시에 전달되는 최종 정서 벡터가 달라지도록 한다.

4. **다중체 전환 및 페르소나 팩 연동**

   - **'지금의 나' Self facet (자아의 단면)** 선택에 따라 SLM이 참조하는 **페르소나 표정 세트(Persona expression set)**를 **실시간으로 교체**한다. Self facet (자아의 단면)별로 "차분한 나" / "열정적인 나" / "탐색하는 나" 등 **표정 팩**을 정의하고, SLM 감정 라벨(예: happy, curious, tired) → Rive 상태 매핑이 **현재 페르소나 팩**에 따라 선택되도록 한다. Persona-Switch 시 헤더·코일 Override와 동기화하여, 표정 팩 ID가 UCL 패킷 또는 세션 컨텍스트에 포함된다.

5. **부하 관리를 위한 등급별 SLM 전략 (NEXA NIXIE-LOW / MID / HIGH)**

   - 디바이스·세션 부하에 따라 SLM 연산 수준을 조절한다. **NEXA NIXIE-LOW:** 경량 모델 또는 규칙/키워드 기반 정서 추정만 사용, 표정은 중립·단순 전환 위주. **NEXA NIXIE-MID:** 소형 SLM으로 실시간 분류, 스트리밍 유지. **NEXA NIXIE-HIGH:** 더 정교한 SLM·다중 신호 융합, 세밀한 표정·Lumina 곡선. 하드웨어 프로파일·FPS·배터리 정책 등에 따라 등급이 자동 또는 사용자 설정으로 결정되며, 등급별로 목표 지연(예: LOW 50ms, MID 100ms, HIGH 150ms)과 정확도 트레이드오프를 명시한다.

6. **브라우저 단 SLM·HOT 프로필 (속도·분산)**
   - 속도와 분산을 위해 SLM을 **사용자 브라우저**에서 실행할 수 있다. NEXA의 **HOT 프로필** 전략([NEXA] 하드웨어 프로파일러 및 동적 성능 엔진 참조)에 따라, 브라우저 자원(WebGPU·메모리)이 충분한 클라이언트에서는 **감정 분류 SLM**을 클라이언트에서 가동하여 **네트워크 왕복 없이** 0.1초 이내 정서 동기화를 달성하고, 서버 부하를 분산한다.
   - **WebAssembly(Wasm):** SLM 추론 엔진(또는 경량 런타임)을 Wasm으로 컴파일하여 브라우저에서 실행한다. 메인 스레드를 블로킹하지 않도록 추론은 **별도 스레드**에서 수행한다. Wasm 모듈은 초기 로드 시 또는 HOT 프로필 진입 시 다운로드·캐시하며, 필요 시 양자화된 소형 모델만 배포하여 로드 시간을 제한한다.
   - **Web Worker:** SLM 추론을 **Web Worker**에서 실행한다. 메인 스레드는 UI·Rive 렌더링에만 사용하고, Worker가 사용자 입력(텍스트·행동 요약)을 받아 감정 분류 후 **JSON 패킷**을 `postMessage`로 메인에 전달한다. 메인 스레드는 수신한 정서 패킷으로 즉시 Rive·Lumina 상태를 갱신한다. 이를 통해 **메인 스레드 논블로킹**과 **0.1초 목표**를 동시에 만족시킬 수 있다. (Worker 내부에서 Wasm 기반 추론을 호출하는 구성이 일반적이다.)
   - HOT 프로필이 아닌 경우(COLD 프로필·저사양)에는 브라우저 단 SLM을 비활성화하고, 기존처럼 **백엔드 인디케이터 앞단 SLM·스트리밍** 경로만 사용한다. 하드웨어 프로파일러가 HOT/COLD를 판정한 뒤, 닉시 클라이언트가 "SLM 로컬 가동" vs "SLM 서버 스트리밍" 중 하나를 선택하도록 한다.

**데이터 사슬 요약:** **의도(WILL)** → **판단(SLM / 인디케이터)** → **연주(NEXA NIXIE / Rive)** 로 이어지는 사슬이 위 규격으로 완성된다. 사용자 의도·발화·행동이 SLM에서 정서로 분류되고, 코일·페르소나 팩으로 보정된 뒤, 닉시가 Rive와 Lumina·Jitter로 "연주"한다.

#### 아날로그 감성 (Nixie·필라멘트)

- **필라멘트 질감 구현:** Rive의 상태 머신에서 단순한 색상 변화가 아닌, **진공관(Nixie Tube)**처럼 가스가 서서히 타오르고 식는 듯한 **Lumina(발광)** 효과와 잔상을 수식화하여 적용한다. 발광·소등 곡선과 잔상 감쇠를 파라미터로 두어, 닉시의 감정·준비도에 따라 빛의 "숨 쉬는" 리듬을 표현한다.
- **재질감의 조화:** 따뜻한 호박색 빛과 나무/금속의 질감이 어우러진 **아날로그적 온기**를 닉시의 스킨 시스템 **기본값**으로 설정한다. 닉시관·진공관의 노스탤지어와 플랫폼의 지능형 서사가 하나의 톤으로 이어지도록 한다.

### UCL 프로토콜과의 연동(참고)

아래 항목들은 **UCL 프로토콜 기획서**에서 상세히 다루며, 닉시 설계와 직·간접적으로 연결된다. 여기서는 연동 이슈만 간단히 제시한다.

- **Persona-Switch 헤더:** '지금의 나' Self facet (자아의 단면) 선택 시 **UCL 패킷 헤더**가 어떻게 바뀌는지, 하위 도메인의 **코일 밸런서 레이어**를 어떻게 덮어쓰는지(Override) — UCL 프로토콜에서 헤더·Override 규칙 정의.
- **VOID 토큰 처리:** 영감 모드 진입 시 발생하는 **VOID 토큰**이 과거 아카이브의 **RAG 검색 가중치**를 어떻게 초기화하고 **새로운 탐색 모드**로 전환하는지 — UCL·RAG 경계에서의 토큰 의미 및 가중치 정책.
- **ECHO 승격 루프:** 닉시의 제안(ECHO)이 사용자 승낙(WILL)을 거쳐 **규범(GOVERN)**으로 승격되어 DB의 **balance_coil_templates** 등에 반영되는 **데이터 흐름** — UCL 프로토콜에서 ECHO→GOVERN 승격 및 영속화 절차.

> **닉시의 독립성:** 닉시는 UCL과 결합할 때 위와 같은 프로토콜을 따르지만, **UCL에 강하게 종속되지 않는다**. 닉시만 독립적으로 동작하는 모드(예: 표정·Lumina·Jitter만 갱신)나, 다른 통로(예: 직접 API·이벤트 버스·별도 에이전트)를 통해 동일·유사 기능을 구현할 여지가 있으며, 이후 확장 시 UCL 외 경로도 설계 대상에 둔다.

## VOID 및 영감(Inspiration) 워크플로우

사용자가 **방향을 잃었을 때** 또는 **번뜩이는 영감은 있으나 아직 정리되지 않은 상태(VOID)**에서 닉시가 어떻게 행동할지에 대한 초안 아이디어이다. "기술의 흡수"와 "현실의 연주"를 위해 **선입관을 내려두고, 수많은 자아(UCL 템플릿)를 펼쳐 보이는 '영감 모드'**를 정의한다.

### 1. 영감 모드 진입 조건(트리거)

닉시가 **영감 모드(Inspiration Mode)**로 전환하는 경우는 다음을 모두 고려한다.

- **사용자 발화·요청:** "뭔가 막혀", "아이디어가 안 떠올라", "방향만 잡아줘" 등 **명시적 요청**이 들어온 경우.
- **행동 신호:** 같은 화면/노드 주변에서 **반복된 망설임**(클릭 미발생, 롤백, 취소)이 N회 이상 관측된 경우.
- **닉시 판단:** 시선·대화·이력으로 "의도는 있으나 목표가 흐릿한 상태"를 추정한 경우(예: ES·VI 또는 Pre-Intent 스코어가 특정 임계값 구간에 있을 때).

> 초안: 트리거는 **OR** 조건으로, 하나만 충족되어도 진입 후보가 되며, 사용자 설정에서 "영감 모드 자동 제안 on/off"로 완화할 수 있다.

### 2. 닉시 행동 지침(VOID 구간)

- **선입관 배제:** 닉시는 "한 가지 정답"을 제시하지 않고, **여러 가능한 자아(UCL 템플릿)**를 동등하게 펼쳐 보인다.
- **압박 없음:** 선택을 유도하되, "지금 골라야 한다"는 압박을 주지 않고 **넘겨보기·멈추기**를 허용한다.
- **라벨과 이미지:** 각 자아(템플릿)는 **라벨(짧은 문구·태그)**과 **대표 이미지(썸네일/아이콘)**로 구분되어, 언어 없이도 직관적으로 스캔할 수 있게 한다.
- **인내하는 지능:** 닉시는 시끄럽게 질문하거나 선택을 재촉하지 않는다. **닉시 도트의 미세한 떨림(Jitter)**만으로 "여기 있어, 기다리고 있어"를 전하고, 사용자가 스스로 결정을 내릴 때까지 침묵 속에서 대기하는 **인내하는 지능**의 모습을 유지한다.

### 3. 영감 모드 UI 정의(초안)

- **UCL 템플릿(수많은 자아) 전시:** 사용자가 가질 수 있는 **페르소나/시나리오/태스크 유형**별 UCL 템플릿을 **Self facet (자아의 단면) 또는 타일** 형태로 나열한다.
- **자동 스크롤(선택 사항):** 흐름을 주기 위해 **부드러운 자동 스크롤**을 기본으로 두고, 사용자가 터치/마우스로 멈추거나 속도를 바꿀 수 있게 한다.
- **라벨링된 이미지:** 각 템플릿은 **라벨(이름·한 줄 설명)** + **이미지(대표 시각)**를 갖추어, "이 중에서 끌리는 것"을 빠르게 좁혀갈 수 있게 한다.
- **선택 시 동작:** 한 Self facet (자아의 단면)를 선택하면 해당 UCL 템플릿이 **현재 세션의 컨텍스트(Orchestra Score·에이전트 페르소나)**로 적용되고, 영감 모드는 종료(또는 백그라운드로 전환)한다.

### 4. 데이터·상태 관점(초안)

- **VOID 토큰:** 영감 모드 진입 시 UCL/닉시 상태에 **VOID(잠재·여백)** 플래그를 두어, 이후 RAG·GOVERN·아카이브에서 "방향 탐색 구간"으로 해석할 수 있게 한다.
- **이력 활용:** 영감 모드에서의 **노출 순서·체류 시간·선택 결과**는 `project_logs` 등에 저장해, 다음번에는 "이 사용자에게 맞는 순서"로 템플릿을 정렬하는 데 활용할 수 있다.

## Rive 기술 스택과 UCL 연동

**Rive**는 닉시를 살아 움직이게 하는 벡터 애니메이션 엔진이며, UCL 명령을 닉시의 표정·동작으로 출력합니다.

### 1. Rive 기술 스택 소개: "가볍고 영리한 상태 머신"

Rive는 단순한 애니메이션 툴을 넘어, 실시간 인터랙션에 최적화된 **벡터 기반 애니메이션 엔진**입니다.

- **초경량 및 고성능:** `.riv` 바이너리 포맷을 사용하여 기존 Lottie 대비 **10~15배 더 가볍습니다**. 또한 GPU 가속을 활용하며, 화면에 보이지 않을 때는 계산을 중단하는 절전 기능도 갖추고 있습니다.
- **상태 머신(State Machine):** Rive의 핵심은 **상태 머신**입니다. 개발자가 애니메이션 프레임을 일일이 지정하는 대신, '감정', '강도' 같은 **입력값(JSON)**에 따라 애니메이션이 실시간으로 보간(Interpolation)되며 자연스럽게 변화합니다.
- **프론트엔드 친화성:** Vue 런타임을 공식 지원하여 NEXA의 프론트엔드 환경(Vue 3 + Quasar)과 반응형 데이터 연동이 매우 용이합니다.

### 2. Rive 소스와 UCL의 소통 방식: "지휘자와 연주자의 협업"

UCL이 사용자의 의도를 담은 **'지휘 규격서'**라면, Rive는 그 명령을 받아 닉시의 표정과 동작으로 출력하는 **'연주자'**입니다. 이 둘은 다음과 같은 계층적 구조를 통해 소통합니다.

#### ① 감정 판단 및 명령 생성 (Backend - Indicator)

사용자의 입력이나 시스템 상태가 UCL 블록으로 들어오면, **비스타(Vista) 인디케이터**가 이를 해석합니다.

- **실시간 감정 분석:** AI는 답변 전체가 완료되기를 기다리지 않고, **첫 번째 토큰** 단계에서 감정을 판단하여 닉시에게 보낼 표정 명령을 즉시 생성합니다.
- **JSON 명령어 하달:** 백엔드는 `{"emotion": "happy", "intensity": 80}`와 같은 **명령 JSON**을 프론트엔드로 전송합니다.

#### ② 상태 머신 매핑 (Frontend - NEXA NIXIE Interface)

프론트엔드의 Vue 런타임은 전달받은 JSON 명령을 **Rive 상태 머신의 입력값**으로 즉시 치환합니다.

- **UCL 0단계 연동:** UCL의 **에이전트 설정** 정보와 **코일 밸런서** 가중치가 닉시의 '코어 스킨'이나 표정 팩에 반영됩니다.
- **비언어적 피드백:** 예를 들어, UCL상에서 **안정성(Stability) 코일** 가중치가 높아지면 닉시의 시선 처리가 더 신중해지거나 빛의 일렁임이 차분해지는 식의 연동이 일어납니다.

#### ③ 실행 및 추적 (Action & Traceability)

- **직접 제어:** 사용자가 욕설을 하거나 중요 규칙을 위반할 경우, UCL의 **안전 가드레일**이 작동함과 동시에 닉시는 즉시 '당황' 또는 '경고' 애니메이션을 수행합니다.
- **이력 저장:** 닉시가 수행한 모든 동작 상태는 다시 **`project_logs`**나 **`project_chats`**에 저장되어, 향후 사용자의 변심이나 영감을 추적하는 **'지능적 족보'**의 근거가 됩니다.

### 3. 기술적 요약: 데이터 흐름도

1.  **UCL 전략 수립:** 사용자의 의지(WILL)나 시스템 이벤트 발생.
2.  **AI 추론:** 경량 모델(SLM)이 0.1초 내에 감정/의도 판단.
3.  **프로토콜 전송:** 백엔드에서 애니메이션 상태값이 담긴 **JSONB** 패킷 전송.
4.  **Rive 실행:** Vue 환경의 Rive 엔진이 입력값을 받아 닉시의 표정/시선/코어 빛을 연주.

닉시는 UCL의 **살아있는 얼굴**로서 논리적 충돌·조율 과정을 사용자에게 부드럽게 전달합니다.

---

넥사 닉시(NEXA NIXIE) 기능 확장 시 발생할 수 있는 서버 및 브라우저 부하 문제를 해결하기 위해, NEXA 플랫폼은 **'하드웨어 프로파일링'**, **'지능형 자원 분산'**, 그리고 **'시각적 최적화'**라는 세 가지 핵심 전략을 사용합니다.

### 1. 하드웨어 프로파일 기반의 동적 연출 (COLD/WARM/HOT)

사용자의 기기 사양에 따라 닉시의 시각적 복잡도를 자동으로 조절하여 브라우저 부하를 관리합니다.

- **COLD 프로필 (저사양):** 닉시의 복잡한 닉시관 효과나 애니메이션 보간을 최소화하고, 기능 전달 위주의 정적 비트맵이나 단순한 2D 리소스를 사용합니다.
- **WARM 프로필 (중사양):** 주요 상호작용 시에만 닉시관의 느린 잔상 효과를 적용하고 배경 도트는 정적인 상태를 유지합니다.
- **HOT 프로필 (고사양):** 모든 물리 엔진(중력, 마찰 등)과 가스 광원 확산(Glow) 연산을 풀가동하여 최상의 아날로그 미학을 구현합니다.
- **동적 보정:** FPS 45fps 미만 시 연출 등급을 한 단계 낮추어 멈춤 방지.

### 2. 클라이언트-서버 지능 분배 전략

모든 AI 연산을 서버에서 처리하는 것이 아니라, 기기 사양에 따라 연산 위치를 동적으로 결정합니다.

- **프론트엔드 담당:** 닉시의 실시간 시선 추적, 간단한 애니메이션 명령 해석(Rive 엔진), 대화 텍스트 렌더링 등 가벼운 로직을 수행합니다.
- **백엔드 담당:** 무거운 LLM 추론, 감정 분석, 복잡한 맥락 해석 및 5W1H 아톰화 작업을 담당합니다.
- **SLM(소형 모델) 활용:** 닉시의 표정 변화를 위해 0.1초 내에 감정을 판단해야 하는 작업은 백엔드 앞단의 **경량 추론 모델(SLM)**에 맡겨 지연 시간을 최소화합니다.

### 3. 리테인드 모드 및 오프스크린 캔버스 기술

수만 개의 도트와 닉시의 인터랙션을 동시에 처리하기 위한 고도의 렌더링 기술을 적용합니다.

- **리테인드 모드(Retained Mode):** 도트를 객체로 관리해 변경된 ID만 갱신, 불필요한 전체 재렌더링 방지.
- **오프스크린 캔버스(Offscreen Canvas):** 상시 움직이는 배경 레이어와 사용자가 직접 조작하는 닉시/노드 레이어를 분리하여 연산 부하를 획기적으로 낮춥니다.

### 4. 서버 부하 경감을 위한 지능형 최적화

- **계층적 필터링:** 엣지(Sentinel) 단에서 로우 데이터를 5W1H 문장으로 요약하여 서버로 전달함으로써, 서버 AI(Indicator)의 연산 부하를 **90% 이상 절감**합니다.
- **시맨틱 캐시(Semantic Cache):** 동일하거나 유사한 질문에 대해서는 AI 추론 없이 Redis에 저장된 기존 답변을 즉시 반환하여 GPU 부하를 줄입니다.
- **적응형 배칭(Adaptive Batching):** 일상 로그는 배치 처리, 긴급 개입·안전 사건은 즉시 처리(Bypass)하는 우선순위 계층 운영.

### 5. 하위 호환성 및 자원 분산(운영 규격)

닉시 구현이 발전할수록 “현실의 연주(실시간 UI/안전 피드백)”를 유지하기 위해, **기능을 끄고(하위 호환성)**, 연산을 쪼개고(자원 분산)\*\*, 늦게 와도 안전은 먼저 처리하도록(우선순위/드롭/서킷브레이커) 정책을 고정한다.

#### 5.1 클라이언트 기능 게이팅(Backward Compatibility)

부팅 시점에 클라이언트 프로파일을 확정하고, 동일한 UCL 입력을 **기능 수준별로 다른 방식으로 연주**한다.

- **NE-XU-LOW(하위 호환/안전 중심)**
  - Rive 상태 머신: 단일 레이어(기본 표정)만 사용
  - 닉시관(NEXA NIXIE) 점/절차 생성: 비활성화
  - 시선 처리: 샘플링 주기 1/4로 감소(예: 10Hz → 2.5Hz)
  - 서버 감정 추론: 스트리밍/다단계 감정 분석 비활성(요청 1회로 축약)
- **NE-XU-MID(기본 연주/균형)**
  - Rive 상태 머신: 표정 + 코어 빛 2단 입력 반영
  - 닉시관: 주요 전환(VOID/충돌/승낙)에만 제한 활성
  - 시선 처리: 5Hz~10Hz 범위 유지
  - 서버 감정 추론: 2단계(감정 분류 1회 + 강도 조정 1회)까지만 허용
- **NE-XU-HIGH(풀 연주/고성능)**
  - Rive 상태 머신: 다중 상태 전이 + 강도 동시 반영
  - 닉시관: 연속(프레임 일부 구간) 생성/갱신
  - 시선 처리: 10Hz~20Hz 범위 유지
  - 서버 감정 추론: 스트리밍·다단계 분석 허용

전이 규칙(동적 하위 호환):

- FPS가 45fps 미만이 **연속 3초** 동안 유지되면 `NE-XU-HIGH → NE-XU-MID`로 자동 강등
- 오류(서버 타임아웃/추론 실패)가 **연속 2회** 발생하면 `NE-XU-MID → NE-XU-LOW`로 강등

#### 5.2 브라우저 업데이트 예산(Front-end Time Budget)

브라우저의 매 프레임 연산량을 고정 예산으로 제한한다.

- 렌더 루프: 60fps를 목표하되, 논리 업데이트는 **최대 15Hz**로 제한
- 닉시 “새 명령” 생성(감정/코일 반영/표정 상태 전이)은 **최대 10Hz**
- 시선 처리(Pre-Intent 데이터 수집)는 **최대 10Hz**
- 안전 이벤트(규칙 위반/중단 요청)는 우선순위 큐로 분리하고, **즉시 실행**(연산 지연 허용 없음)

#### 5.3 백엔드 자원 분산(Queue + Worker Sharding)

서버는 요청을 한 워커 풀에 몰지 않고 역할별 워커로 분산한다.

- **Emotion Inference Worker**: 감정/강도/상태 추정
- **Atomization Worker**: 5W1H 아톰화, 요약/Extra 분리
- **Govern & Trace Worker**: GOVERN 승격, Why Chain용 ID/참조 사슬 생성, trace 로그 저장
- **Logging/Archive Worker**: project_logs/project_chats 영속화 및 아카이브(배치)

큐 우선순위 규칙:

- 우선(P0): 안전 가드레일, 중단/VOID 전환, WILL-MUST 실행 승인
- 준우선(P1): UI 감정/코일 시각화에 필요한 최신 명령(지연 가능)
- 후순위(P2): 장기 아카이브, 상세 Extra 저장, 재탄생(Archive rebuild)

#### 5.4 백프레셔(Backpressure)와 드롭 정책

큐가 밀리면 “모든 걸 다 처리”하지 않고 **업데이트 종류별로 드롭**한다.

- P1(감정/표정 갱신)은 `drop-oldest(가장 오래된 업데이트부터 드롭)` 정책으로 “가장 최신 1개”만 유지
- P2(아카이브/Extra 상세)는 지연 누적 허용 후 다음 배치로 이월
- P0(안전/중단/권한)는 드롭하지 않고, 필요한 경우 해당 워커만 격리 처리(Bypass)

#### 5.5 서킷 브레이커(Circuit Breaker)로 실패를 정상화

다음 조건 중 하나가 충족되면 감정/아톰화의 고비용 경로를 즉시 끊고 하위 호환으로 전환한다.

- 평균 응답 지연이 **500ms를 1분 동안 초과**
- 오류율이 **5% 이상**(최근 1분)

서킷 브레이커 상태별 동작:

- OPEN: `NE-XU-HIGH/MID` → `NE-XU-LOW`, 감정 추론은 “마지막 성공 응답” 기반으로 강도만 조정
- HALF-OPEN: 오류가 줄면 1명 세션부터 점진 복구(동시 워커 수를 기존의 절반으로 제한)
- CLOSED: 정상 처리로 복귀

#### 5.6 콘텐츠/연산 캐시의 단계화

캐시는 “항상 동일”이 아니라 **수명(VOID/노후화)과 목적**에 따라 층을 분리한다.

- **Emotion Cache(단기)**: 최신 상태(예: 30초 TTL)만 유지하여 과잉 고정 방지
- **Semantic Cache(중기)**: 유사 질문 응답(예: 10분 TTL)으로 추론 비용 절감
- **Govern/Trace Cache(장기 인덱스)**: ID/참조 사슬의 생성 결과만 보존(원문 Extra는 수명 정책에 따름)

### 6. 맥락적 침묵 (부하 절제)

필요할 때만 작동. 사용자가 능숙할 때는 '그림자 모드'로 대기해 자원을 최소화하는 **조용한 지능** 원칙.
