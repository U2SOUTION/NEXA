# files.source_metadata AI 추출 기획

`nexa_db.files` 테이블의 **source_metadata** 필드는 스키마에는 있으나 현재 비어 있는 상태이다.  
특정 이벤트(파일 업로드, DB 반영, 별도 요청)에서 **전용 AI 모델**을 사용해 메타데이터를 추출·검증 후 DB에 입력하는 설계를 정리한다.

---

## 0. 요약(메타데이터) vs 벡터 — 역할 분리와 성능

| 구분 | API | 저장 위치 | 용도 |
|------|-----|-----------|------|
| **요약·메타데이터** | Ollama **Generate (JSON Mode)** | `files.source_metadata` (JSON) | **사람이 읽기 위한** 요약, 키워드, 카테고리 힌트, 제목 등. UI 표시·필터·프롬프트 컨텍스트용. |
| **벡터(임베딩)** | Ollama **Embeddings** | **별도 벡터 필드/테이블** (`file_embeddings` 등) | **유사도 검색·RAG·“비슷한 문서 찾기”** 용. 사람이 직접 읽지 않음. |

- **벡터를 별도 필드에 두는 것이 성능에 유리한 이유**
  - **한 번 계산·저장**: 업로드/DB 반영 시 한 번만 임베딩 생성 후 저장. 검색 시에는 저장된 벡터만으로 유사도(코사인/ANN) 계산하면 되어, 매번 문서를 다시 임베딩할 필요가 없다.
  - **검색 최적화**: 벡터 전용 컬럼(또는 별도 벡터 DB)을 두면 인덱스(예: HNSW, IVFFlat)로 **근사 최근접 이웃(ANN)** 검색이 가능해, 문서 수가 많아져도 빠르게 “유사 문서”를 찾을 수 있다.
  - **역할 분리**: `source_metadata`는 사람·AI가 읽는 **텍스트 메타**, 벡터는 **기계 전용 표현**으로 두면 스키마와 용도가 명확해진다.

따라서 **Embeddings로 벡터 생성 → 별도 벡터 필드/테이블에 저장**하고, **Generate(JSON Mode)로 메타데이터 추출 → `files.source_metadata`에 저장**하는 구성을 권장한다.  
기존 기획의 `file_embeddings` 테이블(벡터 BLOB, model_id, dimension)과 연계하면 된다.

## 1. 목적과 원칙

| 원칙 | 설명 |
|------|------|
| **전용 모델** | 채팅창 모델과 별개로, 메타데이터 추출 전용 모델을 **코드로 지정**한다. 서버 부하를 줄이고, 정확도·데이터 형식 준수 확률을 높이며, 이후 부정확 시 **학습/페르소나/지침서**만 업데이트하기 쉽다. |
| **Zod(JSON Schema)** | 출력 구조를 **Zod 스키마**로 정의하면 검증 정확도가 올라가고, 재학습·여러 AI 협업 작업에서 동일 스키마를 재사용할 수 있다. |
| **Vercel AI SDK** | 기존에 적용된 **Vercel AI SDK**를 사용해 구조화 출력(generateObject 등)을 구현하면 코딩이 단순해진다. |
| **Ollama Generate** | 단일 프롬프트 완성에 적합한 **Ollama `/api/generate`** 를 활용한다. (SDK에서 provider가 generate 엔드포인트를 사용하거나, 필요 시 직접 호출.) |
| **UX 지연 방지** | 탐색기 기획서에 명시된 대로 **기본 정보만 먼저 저장**하고, **상세 분석(메타데이터 추출·임베딩)은 비동기**로 처리한다. 사용자 응답을 막지 않는다. |

## 2. 트리거 이벤트와 비동기 흐름

### 2.1 이벤트 정의

source_metadata를 채우는 시점을 다음 이벤트로 한정한다.

| 이벤트 | 설명 | 우선순위 |
|--------|------|----------|
| **파일 업로드** | `POST /files/upload` 등으로 파일이 저장·`files` INSERT 된 직후, **비동기**로 메타데이터 추출 요청을 넣고 완료 시 `source_metadata` UPDATE. | 필수 |
| **DB 반영** | 문서 폴더에서 "디비에 반영"으로 `files`에 행이 추가될 때, 동일하게 **비동기** 추출 요청 후 `source_metadata` UPDATE. | 필수 |
| **별도 요청** | 관리자/개발자용 "메타데이터 재추출" API 또는 배치. 기존 레코드에 대해 재요청. | 선택 |

### 2.2 기본 정보 우선 저장, 상세 분석은 비동기

**UX 지연을 방지**하기 위해, 탐색기 기획서에 명시된 대로 다음 흐름을 유지한다.

- **1단계(동기)**: 업로드 또는 DB 반영 시 **기본 정보만** 즉시 저장한다.  
  예: `file_path`, `original_name`, `file_type`, `category`, `content_hash`, `source` 등.  
  → 사용자에게는 즉시 "저장됨"·탐색기에 노드/목록 반영으로 응답한다.
- **2단계(비동기)**: **상세 분석**(메타데이터 추출, 임베딩 생성)은 **백그라운드 작업**으로 처리한다.  
  완료 시 `source_metadata`·`file_embeddings` 등을 UPDATE하고, 필요 시 UI에 "분석 완료" 등으로 반영한다.

이렇게 하면 업로드·DB 반영 응답이 AI 처리 시간에 묶이지 않아, 탐색기 사용 시 지연이 발생하지 않는다.

## 3. 형식별 전용 모델 및 모델 관리

메타데이터 추출 대상은 **문서만이 아니라 이미지, 영상, 오디오, 프로그램 코드** 등 다양한 형식이다. 형식마다 입력 형태와 적합한 모델이 다르므로 **형식(또는 category/file_type)별로 전용 모델을 지정**하고, **설정으로 관리**해 코드 수정 없이 모델을 교체·최적화할 수 있게 한다.

### 3.1 형식별 전용 모델

채팅창 모델과 분리하여, **추출 태스크별로** 사용할 모델을 지정한다. 한 개의 “통일 모델”이 아니라 **형식별 매핑**을 둔다.

| 형식(대상) | file_type / category 예시 | 입력 형태 | 전용 모델 용도 | 비고 |
|------------|----------------------------|-----------|----------------|------|
| **문서** | document, documents | 텍스트(본문 또는 앞 N자), 파일명·확장자 | 요약·키워드·제목·sections 추출, JSON 준수 | md, txt, pdf(텍스트 추출) 등 |
| **이미지** | image, images | 이미지 바이너리(base64) 또는 URL, 파일명 | 비전 모델로 설명·alt_text·키워드 | Vision 지원 모델 필요 |
| **영상** | video | 메타(길이, 코덱), 썸네일 또는 키프레임 이미지, 파일명 | 설명·키워드·요약 (이미지 또는 메타 기반) | 1차는 썸네일+메타로 추출 검토 |
| **오디오** | audio | 메타(길이), 파일명, (선택) 스크립트/자막 | 설명·키워드·요약 | 텍스트 있으면 문서 모델 활용 가능 |
| **코드** | (별도 category 또는 file_type) | 소스 코드 일부, 언어·확장자 | 요약·기능 설명·키워드·언어 | 코드 이해 특화 모델 권장 |
| **기타/폴백** | other, 미매칭 | 파일명·확장자만 | 최소한의 메타 추출 또는 스킵 | 공통 소형 모델 또는 null |

- **구현**: `file_type` 또는 `category`(및 확장자)로 위 매핑을 참조하고, 해당하는 **모델 이름**을 설정에서 읽어와 사용한다. 매핑에 없으면 **폴백 모델** 또는 “해당 형식은 추출 스킵” 정책을 적용한다.

### 3.2 모델 선택 가이드

실제 모델은 **끊임없이 탐색·최적화**해야 하므로, 선택 기준과 업데이트 주기를 가이드로 둔다.

| 항목 | 가이드 |
|------|--------|
| **태스크 적합성** | 문서는 텍스트·JSON 출력에 강한 모델, 이미지는 **Vision** 지원 모델, 코드는 **코드 이해** 특화 모델을 우선 검토. |
| **JSON/스키마 준수** | 메타데이터 추출은 **Zod 스키마에 맞는 JSON** 출력이 필수이므로, “지시 따르기”, “구조화 출력”이 잘 되는 모델을 선택. |
| **VRAM·지연** | §② 배치 처리와 조합해, 형식별로 **소형·중형** 모델을 쓰면 채팅용 대형 모델과 스위칭 부담을 줄일 수 있음. |
| **업데이트 주기** | 새 모델·파인튜닝 버전이 나오면 **설정만 변경**해 반영하고, 필요 시 “재추출 정책”(기존 항목을 새 모델로 다시 돌릴지)을 정한다. |

- **문서화**: “현재 권장 모델” 목록(예: 문서=llama3.2:latest, 이미지=llava:latest, 코드=codellama:latest)을 기획서 또는 설정 파일 주석·별도 모델 가이드 문서에 두고, 실험 결과에 따라 주기적으로 갱신한다.

### 3.3 설정 기반 모델 지정 및 업데이트 로직

모델 변경이 **코드 수정 없이** 이루어지도록 **설정(Config)** 으로만 지정하고, 업데이트 시에도 **설정 갱신 + (선택) 재추출**로 처리한다.

| 항목 | 설명 |
|------|------|
| **설정 구조** | 형식(또는 `file_type`/`category`/확장자 그룹) → **모델 이름** 매핑을 **설정 파일**(예: `fileMetadataModels.config.js`, 또는 `aiConfig.js` 확장) 또는 **DB 테이블**에 둔다. 예: `{ document: 'llama3.2:latest', image: 'llava:latest', video: 'llava:latest', code: 'codellama:latest', default: 'llama3.2:latest' }`. |
| **코드 동작** | 추출 서비스는 **파일의 형식만 보고** 설정에서 해당 모델 이름을 조회한 뒤, 그 모델로만 요청한다. 모델 이름이 **하드코딩되지 않도록** 한다. |
| **업데이트 절차** | (1) 새 모델을 Ollama에 pull. (2) 설정에서 해당 형식의 모델 이름만 변경 후 서버 재시작(또는 설정 핫리로드). (3) 필요 시 “해당 형식 전체 재추출” API/배치를 돌려 기존 `source_metadata`를 새 모델 출력으로 갱신. |
| **버전/이력** | 설정을 버전 관리( Git )하고, “언제 어떤 모델로 바꿨는지” 주석 또는 변경 이력으로 남기면, 나중에 품질 비교·롤백이 쉬워진다. |

이렇게 하면 **형식별 전용 모델**과 **모델 선택 가이드**, **설정 기반 업데이트**가 일관되게 반영된 코딩이 가능하다.

## 4. 출력 구조 (Zod 스키마)

`source_metadata`에 들어갈 JSON 구조를 **Zod 스키마**로 정의하고, AI 출력을 이 스키마로 검증한 뒤 DB에 저장한다.

- **공통 필드 예시** (도메인·용도에 따라 확장):
  - `summary`: 파일 내용 요약 (문서/이미지 설명 등)
  - `keywords`: 문자열 배열
  - `category_hint`: 문서 유형 힌트 (기획서, API문서, 메모 등)
  - `language`: 주 사용 언어
  - `extracted_at`: 추출 시각 (ISO 8601)
- **문서(source=docs)** 에 한해 추가 가능 필드: `title`, `sections[]` 등.
- **이미지** 에 한해: `description`, `alt_text` 등.
- **영상·오디오** 에 한해: `duration`, `description` 등.
- **코드** 에 한해: `language`, `purpose`(기능 요약), `frameworks` 등.

형식별로 **스키마 변형**(이미지 전용 필드만 강제 등)이 필요하면, 공통 스키마 + 형식별 `.extend()` 또는 별도 스키마를 두고 추출 시 형식에 맞는 스키마로 검증한다.  
스키마는 **`src/system/schemas/modules/fileSourceMetadata.ts`** 에 정의되어 있으며, 서버에서 import 해서 **검증 + 타입**으로 사용한다.  
AI에는 **JSON Schema**(zod-to-json-schema 등으로 변환) 또는 Zod 스키마 설명을 프롬프트/도구에 넣어 "이 구조만 출력하라"고 엄격히 지시한다.

### 4.1 멀티모달 메타포 추출 전략

단순한 **객체·장면 설명**을 넘어 **추상적 개념(메타포)** 과 **객체 간 관계**를 추출하려면, 형식별로 **도메인에 맞는 룰·프롬프트**와 **모델 선택**으로 세밀하게 제어해야 한다.

#### 4.1.1 이미지 메타포 — 도메인별 전략 분리

이미지 메타포 파악은 **매우 중요한 통찰**을 주지만, 도메인에 따라 전략을 분리한다.

| 도메인 | 전략 | 룰·프롬프트 | 모델 선택 |
|--------|------|-------------|-----------|
| **기계조작 이미지** | **경계 유지**. 기술적·객관적 묘사 위주. 메타포 추출 억제. | "장비·부품·계측치·설비 등 **물리적 구성요소만** 기술. 추상적 해석·상징적 의미 추출 금지." | Vision 모델 중 **객관적 기술 설명**에 강한 모델 우선. 과도한 상상·추론 억제 지침. |
| **철학·예술·개념 이미지** | **메타포 적극 추출**. 단순 설명을 넘어 추상 개념·객체 간 관계 추출. | "객체 간 **관계**, **상징적 의미**, **메타포(은유)**를 추출. 추상적 개념과 시각 요소의 연결을 기술." | Vision 모델 중 **추상·관계·상징** 이해에 강한 모델. 메타포 전용 **프롬프트 스키마** 적용. |

- **구현**: `category`, `domain_hint` 또는 파일 경로·폴더 구분으로 **기계조작 vs 철학**을 판별. 각각 **별도 프롬프트 템플릿**과 **스키마 변형**(기계=description·keywords 중심, 철학=metaphors·relations·symbolic_meanings 추가)을 적용.
- **룰·프롬프트 통합**: Rule Manager(룰_프롬프트_통합_관리_기획)의 **Consumer `metadata_extract`** 에서 `image.machine` vs `image.philosophy` 등 **스코프별 룰**을 할당해, 도메인에 맞는 지침만 주입.

#### 4.1.2 이미지 메타포 전용 스키마(철학 도메인)

철학·예술·개념 이미지용 **Zod 스키마 확장** 예시:

| 필드 | 타입 | 설명 |
|------|------|------|
| `description` | string | 기본 시각적 묘사 |
| `objects` | `{ id, label, role? }[]` | 주요 객체 및 역할 |
| `relations` | `{ from, to, relation_type }[]` | 객체 간 관계(위치·의미·상징) |
| `metaphors` | `{ source, target, meaning }[]` | 추출된 메타포(은유) — "A가 B를 상징" |
| `symbolic_meanings` | string[] | 상징적·추상적 의미 |
| `abstract_concepts` | string[] | 이미지에서 드러나는 추상 개념 |

- **프롬프트**: "다음 이미지에서 **객체**, **객체 간 관계**, **메타포(은유)**, **상징적 의미**, **추상적 개념**을 추출해 주어진 JSON 스키마에 맞게 출력하라."

#### 4.1.3 영상 메타포 추출 전략

| 항목 | 내용 |
|------|------|
| **입력** | 썸네일·키프레임 이미지, 메타(길이·코덱), (선택) 자막/스크립트 |
| **1차** | 각 키프레임에 **이미지 메타포 스키마** 적용. 도메인(기계 vs 철학) 판별 후 해당 룰·프롬프트 사용 |
| **2차** | 키프레임 간 **시퀀스·변화**를 종합해 **서사적 메타포**(전개·대비·반전 등) 추출. "시작 → 중간 → 끝" 구조에서 의미 흐름 추출 |
| **룰·모델** | Rule Manager에서 `video.machine` vs `video.philosophy` 스코프. 비전 모델 + (자막 있으면) 문서 모델 혼합 활용 |

#### 4.1.4 사운드(오디오) 메타포 추출 전략

| 항목 | 내용 |
|------|------|
| **입력** | (선택) Whisper 등 **음성→텍스트** 변환 결과, 메타(길이·포맷), 파일명 |
| **1차** | 텍스트가 있으면 **문서 모델**로 요약·키워드·감정·톤 추출. 텍스트 없으면 **메타·파일명**만으로 최소 메타데이터 |
| **2차(메타포)** | **음악·효과음**의 경우: "리듬·템포·음색과 연관된 **정서·분위기·상징**" 추출. "이 사운드가 무엇을 연상시키는가"를 텍스트(또는 음성 인식 결과) 기반으로 분석 |
| **스키마 확장** | `mood`, `associations`(연상), `symbolic_quality`(상징적 성격) 등. Rule Manager `audio.philosophy` 스코프에서 메타포 추출 룰 적용 |
| **모델** | 음성→텍스트 후 문서/요약 모델. 음악·메타포 특화 모델이 있으면 별도 스코프로 지정 |

#### 4.1.5 정리

- **기계조작 vs 철학·예술**: **룰·프롬프트**와 **모델 선택**으로 도메인별로 정교하게 제어.
- **이미지 → 영상 → 사운드**: 각 형식에 **메타포 전용 스키마·프롬프트**를 두고, Rule Manager의 **스코프·Consumer**로 할당해 통합 관리.

## 8. 데이터 흐름 요약

### 8.1 메타데이터만 (source_metadata)

1. **이벤트 발생** (업로드 완료 / DB 반영 완료 / 재추출 요청) → **기본 정보만 먼저 저장 후 응답**, 상세 분석은 비동기로 이어짐.
2. **파일 식별** (file_id, file_path, original_name, **file_type/category/확장자** → 형식 분류)
3. **형식별 모델 조회** (설정에서 해당 형식의 모델 이름 취득) → **전용 모델로 요청** (Ollama Generate JSON Mode 또는 SDK generateObject, **Zod 스키마** 주입)
4. **응답 검증** (Zod parse, 실패 시 재시도 또는 오류 저장)
5. **DB UPDATE** (`files.source_metadata = 검증된 JSON`, 필요 시 `ai_workflow_*` 필드 갱신)
6. **(선택)** 재학습·페르소나 업데이트 시 동일 스키마로 지침만 수정하면 됨

### 8.2 벡터(Embeddings)와 함께 쓸 때

동일 이벤트에서 **두 가지를 모두** 돌릴 수 있다.

| 단계 | 메타데이터 (사람용) | 벡터 (검색용) |
|------|---------------------|----------------|
| 입력 | 파일명·확장자·내용 일부(또는 전체 텍스트) | 동일 텍스트(또는 청크) |
| API | Ollama **Generate** (JSON Mode) | Ollama **Embeddings** |
| 저장 | `files.source_metadata` | `file_embeddings`(또는 files 내 벡터 컬럼) |
| 활용 | UI 요약·필터·프롬프트 컨텍스트 | 유사도 검색·RAG |

구현 시 **한 번의 후처리 작업**에서 (1) 임베딩 생성 → 벡터 저장, (2) 메타데이터 추출 → `source_metadata` 저장 을 순서대로 수행하면 된다.

## 10. 검토 및 보완 사항

### ① 외부 문서(External Docs) 내용 변경 감지 (Sync Logic)

**상황**: 문서 폴더(NEXA-Documentation, NEXA-Platform/docs 등) 내의 **물리 파일**이 **외부 에디터**(VS Code, 다른 툴 등)에서 수정되었을 때, DB에 반영된 메타데이터·임베딩·캐시가 낡은 상태로 남을 수 있다. 이를 어떻게 감지하고 갱신할지에 대한 정책이 필요하다.

**처리 방향**: (1) 변경 감지 주기·방식, (2) 감지 시 수행할 작업(메타데이터 재추출, content_hash 갱신, 임베딩 재생성 등)을 정의한다.

#### 감지 방식 후보

| 방식 | 설명 | 장점 | 단점 |
|------|------|------|------|
| **크론 + modifiedDate** | 주기적으로(예: 5분마다) 문서 폴더를 스캔하고, 파일의 **mtime(수정 일시)** 와 DB 또는 메타스토어에 저장한 이전 값을 비교. 변경된 파일만 후속 처리. | 구현 단순, 서버 리소스 예측 가능. | 실시간성 낮음. mtime은 의도치 않게 바뀔 수 있음(복사·이동 등). |
| **크론 + content_hash** | 주기적으로 파일 내용을 읽어 **content_hash**(SHA-256 등)를 계산하고, DB의 `content_hash`와 비교. 다르면 내용 변경으로 간주. | **내용 기준**으로 변경 여부 판단해 정확함. | 매 주기마다 파일 읽기·해시 계산 부하. 대용량·많은 파일 시 부담. |
| **하이브리드(modifiedDate → content_hash)** | 먼저 mtime만 비교해 “의심 파일”을 좁힌 뒤, 해당 파일만 content_hash 계산해 변경 여부 확정. | 부하는 줄이면서 내용 변경 정확도 확보. | 구현 복잡도 소폭 증가. |
| **파일 시스템 감시 (inotify / chokidar)** | 문서 폴더 트리에 **watch**를 걸어, 파일 생성·수정·삭제 이벤트를 실시간 수신. 이벤트 발생 시 해당 경로만 큐에 넣어 비동기 처리. | **실시간**에 가깝고, 불필요한 전체 스캔이 없음. | OS별 이벤트 한계(예: 네트워크 드라이브 미지원), 프로세스 재시작 시 구간 누락 가능. |
| **폴링 + ETag/Last-Modified** | 문서를 HTTP로 제공하는 경우, 주기적으로 **HEAD/GET**으로 ETag 또는 Last-Modified를 비교. (로컬 폴더만 있으면 해당 없음.) | HTTP 기반 원격 소스에 적용 가능. | 로컬 문서 폴더에는 보통 미적용. |

**권장**:  
- **1단계**: **크론 + modifiedDate**(또는 **하이브리드: mtime 후 content_hash**)로 시작. 문서 폴더 수·파일 수가 많지 않으면 크론 주기(예: 10분)와 “의심 파일만 해시 비교”로 부하를 제어할 수 있다.  
- **2단계(선택)**: 로컬 전용·실시간성 요구 시 **chokidar** 등으로 감시를 두고, 이벤트 시 해당 경로만 “변경 대기 큐”에 넣어 비동기로 메타데이터·임베딩 재추출 및 `content_hash` UPDATE.

**감지 후 수행 작업**:  
- DB에 해당 경로가 이미 등록된 파일(`files.file_path`가 `docs/{folderId}/{relativePath}` 형태)이면, `content_hash` 갱신 후 **메타데이터 재추출·임베딩 재생성**을 비동기 큐에 넣는다.  
- 아직 DB에 없는 파일이면 “새 파일”로 탐색기·메타데이터 파이프라인에 넣을지 정책(자동 등록 여부 등)은 탐색기 기획서와 합의한다.

### ② 모델 스위칭에 따른 리소스 관리 (Ollama VRAM)

**상황**: 채팅용 **대형 모델**(예: 14B)과 **추출용 소형 모델**(예: 8B)을 동시에 또는 번갈아 사용할 때, 또는 오케스트레이터가 내부적으로 모델을 바꿀 때, Ollama는 VRAM에 모델을 **올리고 내리는 시간**이 필요하다. 작업 큐에서 추출 작업을 **한 건씩** 처리하면 “추출 모델 로드 → 1건 처리 → 언로드 → (채팅 등 다른 모델 사용) → 다시 추출 모델 로드 → 1건 처리 …” 반복으로 **로드/언로드 횟수**가 많아져 지연과 리소스 낭비가 커진다.

**방향**: 추출 작업을 **한 건씩이 아니라 일정 수량씩 모아서(Batch)** 같은 모델이 올라가 있는 상태에서 연속 처리하면, **모델 로드/언로드 횟수를 줄여** VRAM 스위칭 비용을 낮출 수 있다.

#### 배치 처리 요약

| 항목 | 설명 |
|------|------|
| **동작** | 비동기 큐에 쌓인 “메타데이터 추출”(및 필요 시 임베딩) 작업을 **N건 모아서** 한 번에 처리. 추출용 모델을 **한 번 로드**한 뒤 N건을 순차(또는 병렬 한도 내) 처리하고, 다 끝나면 모델을 내린다. |
| **효과** | 로드/언로드가 “큐 1건당 1회”가 아니라 “N건당 1회”로 줄어, VRAM 스위칭에 따른 지연과 부하가 감소한다. 채팅과 추출이 번갈아 일어나도, 추출 쪽은 모아서 한꺼번에 돌리면 스위칭 횟수가 줄어든다. |
| **배치 크기(N)** | 너무 작으면 스위칭 절감 효과가 적고, 너무 크면 “첫 번째 항목이 결과를 받기까지” 대기 시간이 길어질 수 있다. 예: N=5~20, 또는 “최대 대기 시간(예: 30초) 내에 모인 건수” 중 작은 값 등으로 튜닝. |
| **우선순위** | 채팅 요청이 오면 추출용 모델을 언로드하고 채팅 모델을 올리는 등 **우선순위 정책**을 두면, 배치 중간에 중단하고 나중에 이어서 처리하는 로직이 필요할 수 있다. 단순화하려면 “추출 배치가 끝날 때까지 대기” 또는 “채팅 우선 시 남은 추출은 다음 배치로” 같은 규칙을 명시한다. |

**권장**:  
- 추출 전용 워커(또는 큐 소비자)에서 **배치 단위**로 큐를 읽고, **같은 모델 세션**에서 N건을 처리한 뒤 모델을 내리는 흐름을 둔다.  
- N은 환경(VRAM 크기, 동시 채팅 사용 패턴)에 따라 조정하고, 필요 시 “최대 대기 시간”으로 상한을 두어 첫 항목이 지나치게 오래 기다리지 않도록 한다.

### ③ 추출 실패 시 UI/UX 처리 (Error State)

**상황**: AI가 Zod 스키마를 충실히 따르지 못하거나, 분석 중 네트워크·모델·타임아웃 등 오류가 발생했을 때, 현재 문서에는 **로그 처리**(예: `ai_workflow_error`에 메시지 저장, `ai_workflow_status='failed'` 등)만 명시되어 있다. 이 정보를 **탐색기 UI에서도 시각적으로** 보여 주고 **재처리를 유도**하면 사용자가 실패를 인지하고 바로 다시 시도할 수 있다.

**방향**:  
- **백엔드**: 추출 실패 시 기존대로 `ai_workflow_status='failed'`, `ai_workflow_error`(원인 메시지) 등을 DB에 저장.  
- **탐색기 UI**: 목록·트리에서 해당 파일 항목에 **상태값을 시각적으로** 반영하고, **재처리 액션**을 노출한다.

#### UI/UX 구체 제안

| 항목 | 설명 |
|------|------|
| **상태 표시** | `ai_workflow_status === 'failed'` 인 항목에 **아이콘**(예: 경고/에러 아이콘) 또는 **뱃지**(“추출 실패”)를 붙여, 다른 항목과 구분되게 표시. `processing`이면 로딩 인디케이터, `pending`이면 대기 표시 등으로 단계별 구분 가능. |
| **에러 메시지 노출** | 툴팁 또는 행 확장·상세 영역에서 `ai_workflow_error` 내용을 짧게 표시(예: “Zod 검증 실패”, “타임아웃”). 전문 용어는 필요 시 사용자 친화 문구로 매핑. |
| **재처리 유도** | 해당 항목의 **컨텍스트 메뉴** 또는 **액션 버튼**에 “메타데이터 다시 추출”, “재처리” 등을 두고, 클릭 시 `POST /files/:id/extract-metadata`(또는 `reprocess`) 호출 후 상태를 `pending`으로 돌려 큐에 다시 넣음. 성공 시 UI에서 실패 표시가 사라지도록 갱신. |
| **목록/필터** | (선택) 탐색기에서 “실패한 항목만 보기” 필터를 두면, 재처리가 필요한 파일만 모아서 처리하기 쉬움. |

**연계**:  
- `files` 테이블의 `ai_workflow_status`, `ai_workflow_error`를 목록 API 응답에 포함하고, `GlobalFileExplorer`·`ExplorerViewList` 등에서 해당 필드를 읽어 위와 같이 표시·액션과 연결한다.  
- 탐색기 UI 전략(탐색기_UI_전략_구체화, 웹_탐색기_문서폴더_연동_기획서)에서 “파일 항목 상태 표시·재처리 액션”을 요구사항으로 명시해 두면 일관된 UX로 구현할 수 있다.
