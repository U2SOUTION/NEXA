# NEXA GUIDE 플랫폼 구현 단계 및 로드맵

**범위:** NEXA 플랫폼 전체(Knowledge OS, UI 셸, 오케스트레이션 DB, AI·도메인 협업).  
**성격:** `_KNOWLEDGE *` 문서에 한정되지 않는 **상위 구현 순서** 가이드다.

**관련 문서:**

- Knowledge 전용 실행 순서: `_KNOWLEDGE GUIDE 시스템 구축 순서 및 로드맵.md`
- Knowledge DDL SSOT: `_KNOWLEDGE DDL 통합 스키마 및 물리 설계(SSOT).md`
- 오케스트레이션 스키마: `__NEXA 오케스트레이션 스키마 DDL v5.md` 등(명세·DDL v5 문서군)

---

## 구현 단계 (요약)

| 단계 | 내용 |
| :-- | :-- |
| **1** | `_KNOWLEDGE` 관련 기능을 먼저 구현한다. (스키마·Admin·라우팅 등, 세부는 준비에 따라 확장) |
| **2** | AI/도메인 UI 등 **레이아웃 기초**(탭·패널)와 **UX**를 정리·점검한다. |
| **3** | **오케스트레이션 DB**를 구축한다. |
| **4** | AI/도메인에서 **각종 모델**을 적용하고, 오케스트레이션을 붙여 **통합 테스트**한다. |
| **5** | 이후 **도메인별 AI 협업 툴**을 순차적으로 만든다. |

---

## 단계별 메모 (의존·주의)

### 1단계 — Knowledge 우선

- 지식 계층(`nexa_knowledge_*`)·승인·감사·라우팅 최소 루프가 있으면, 이후 단계에서 “UI만 앞서가는” 상황을 줄일 수 있다.
- Knowledge DDL이 `project_assets` 등 **프로젝트 귀속 테이블**을 참조한다면, **같은 PostgreSQL 인스턴스에 최소 스키마**를 두거나, **스키마/DB 분리 전략**을 3단계 이전에 한 줄이라도 확정해 두는 것이 안전하다.

### 2단계 — 레이아웃·UX

- Knowledge Admin·NIXIE·도메인 화면이 **공통 탭/패널 패턴**을 공유하면 4·5단계에서 재사용 비용이 줄어든다.

### 3단계 — 오케스트레이션 DB

- UCL·`project_*`·NIXIE 쉘 등은 4단계 모델·실행과 직접 맞물린다. 3단계에서는 **스키마 + RLS + API 경계**까지 열어두면 4단계가 수월하다.

### 4단계 — 모델·오케스트레이션·테스트

- 1단계 Knowledge와 **Capability·로그·임계(STUCK/ASK 등)** 규약을 맞추는 것이 통합 품질의 핵심이다.

### 5단계 — 도메인별 AI 협업 툴

- 2단계 UI 셸과 4단계 파이프라인을 **그대로 재사용**할지 여부가 속도와 일관성을 가른다.

---

## 이 문서의 위치

- **본 문서:** 플랫폼 전체의 **선후 관계**만 담는다. 세부 체크리스트는 각 도메인 GUIDE·DDL 명세에 둔다.
- **변경 시:** 단계 번호보다 **의존 관계**(Knowledge ↔ 오케스트레이션 ↔ UI)가 깨지지 않게 수정한다.
