**목적**: NEXA 플랫폼에서 사용하는 **기술 스택**을 설치 방식·역할·도메인별로 정리하여, 신규 참여자·운영·확장 시 일관된 용어와 배치 기준을 제공한다.

**관련 문서**: **오케스트레이터 노드·흐름·다이어그램**은 [NEXA-AI]오케스트레이터를 참조한다. (본 문서는 기술 스택·설치·용어에 집중)

### 5.1 멀티모달 입출력·모델 체급 (NEXA-AI)

**목적**: 현재 사용 모델뿐 아니라 다양한 모델을 기준에 따라 언급·검토한 뒤, 단계적으로 **1차 확정**한다. **한 행 = 한 모델**로 두어 체계적으로 관리. 기획서 [NEXA-AI-03], [NEXA-AI-04], [NEXA-AI-07] 참조.

**상태**: `사용중` — 플랫폼에서 이미 사용. `검토` — 기준 대비 검토 중. `1차확정` — 1차 확정 완료.

| 체급           | 모델명                    | 입력                   | 출력                | 특징                                                                             | 상태   |
| -------------- | ------------------------- | ---------------------- | ------------------- | -------------------------------------------------------------------------------- | ------ |
| **나노**       | Whisper (small/tiny)      | 오디오                 | 텍스트              | STT 전용. 경량·저지연. Ollama/별도 서비스.                                       | 사용중 |
| **나노**       | Whisper base 등           | 오디오                 | 텍스트              | 나노 대안. 정확도·속도 트레이드오프.                                             | 검토   |
| **센티널**     | MeloTTS / ChatTTS         | 텍스트                 | 오디오(음성)        | TTS. MeloTTS: 멀티스피커·다국어. ChatTTS: 대화체 특화. 음성 안내·챗봇 음성 출력. | 검토   |
| **센티널**     | Llama 3.2 3B / 8B 등      | 텍스트·이미지          | 텍스트              | 채팅·코드·타이틀. completion/vision. Vercel AI SDK 연동.                         | 사용중 |
| **센티널**     | LLaVA 소·중형             | 이미지+텍스트          | 텍스트              | 이미지 이해·설명. vision.                                                        | 검토   |
| **센티널**     | Phi, Qwen 소형 등         | 텍스트·이미지          | 텍스트              | 경량 채팅·요약.                                                                  | 검토   |
| **센티널**     | Flux.1 Schnell            | 텍스트                 | 이미지              | 텍스트→이미지. 디퓨전 기반, 빠른 추론용. Ollama/API.                             | 검토   |
| **센티널**     | LTX-Video                 | 텍스트·이미지          | 영상                | 텍스트/이미지→영상. 경량·효율 비디오 생성. Lightricks.                           | 검토   |
| **센티널**     | Stable Audio Open 2.5     | 텍스트                 | 오디오(음악·효과음) | 텍스트→오디오. 음악·사운드 효과 생성. 오픈소스. Stability AI.                    | 검토   |
| **인디케이터** | Stable Diffusion 3.5 L    | 텍스트·이미지          | 이미지              | 텍스트/이미지→이미지. 고품질 디퓨전. Large 사이즈. Stability AI.                 | 검토   |
| **인디케이터** | Wan 2.1 / 2.2 (MoE)       | 텍스트·이미지          | 텍스트              | MoE 구조. 대규모·고품질 채팅·추론. 효율적 추론.                                  | 검토   |
| **인디케이터** | LLaVA 대형 / Llama 70B 등 | 이미지·텍스트·키프레임 | 텍스트·JSON         | 메타포·서사 종합·고품질 추론. 영상 서사, 메타데이터 추출.                        | 검토   |
| **인디케이터** | Vision 대형 모델          | 이미지·다중 프레임     | JSON·텍스트         | 도메인별 룰(기계 vs 철학). generateObject(Zod).                                  | 검토   |

- **입력**: 해당 모델이 받는 데이터 유형(오디오, 텍스트, 이미지, 키프레임 등).
- **출력**: 생성 결과(텍스트, JSON 구조 등).
- **특징**: 용도·연동 스택·제약. 행을 추가할 때 동일 컬럼 규칙으로 기입.
- 신규 모델은 위 표에 **한 행씩** 추가하고, 체급·입출력·특징·상태를 채워 검토 후 1차 확정.

**참고**: NEXA-Documentation/NexaAI 상세 분류·도메인(기계 vs 철학) 전략은 해당 폴더 문서 참조.

**Redis 사용법·이점**: 인메모리 키-값 저장소. **TTL**로 일시 데이터 자동 삭제. Device Token·device_members·api_usage 캐시로 DB 부하 절감, 비밀번호 리셋 토큰·세션 저장. **AI 협업**: 채팅·프롬프트 응답 캐시(동일/유사 질문 즉시 반환), RAG 컨텍스트·임베딩 캐시, Bull/BullMQ 작업 큐, 대화 컨텍스트 캐시 → 효율적·빠른 답변·화면 로딩 지원. **장애 대응**: Docker 사용 시 볼륨 매핑 필수. **Persistence**: RDB(스냅샷)·AOF(로그) 중 하나 이상 활성화 권장. 재기동 시 자동 복구. 순수 캐시 용도면 RDB만으로 충분, 세션 등 중요 데이터는 AOF 또는 AOF+RDB 병행.

**Postgres Docker 운영**: 버전 고정·이관·재현성·다중 환경 통일·다른 서비스(Redis·Ollama 등)와 통합 관리에 유리. **데이터 영속성**을 위해 볼륨 매핑 필수. [NEXA-MIGRATE-01] 참고.

**Postgres 선택 이유**: (1) **JSONB** — 가변적인 IoT 센서 데이터의 유연한 저장 및 GIN 인덱싱. (2) **pgvector** — AI 워크스페이스용 벡터 검색(RAG) 인프라 통합. 임베딩·유사도 검색. (3) **RLS** — 도메인별 행 수준 보안, 강력한 데이터 격리. 정책 예시(device_registry·device_members, `current_setting('app.current_user_id', true)`)는 [NEXA-AUTH-01] §4.2.2. (4) **UUID v7** — PK·ID 표준. 보안·B-tree 효율·엣지–플랫폼 호환. gen_random_uuid()(v4) 금지. **생성 주체**: 엣지 디바이스(우선)·앱·확장에서 생성. 서버 부담 최소화. 가능한 한 디바이스 측에서 생성하도록 설계. **주의**: 디바이스의 시계(RTC)가 동기화되지 않으면 v7의 타임스탬프 기반 정렬·시간 순서가 꼬일 수 있음. 디바이스 등록 시 NTP·플랫폼 시각 동기화 서버단에서 검증 로직 필수. [NEXA-MIGRATE-01] §4.1. **캐시 오염 대응**: Redis 등 캐시에는 행 단위 보안이 없음 → 캐시 키에 `user_id`(또는 권한 컨텍스트) 포함, RLS 관련 테이블(device_members 등) 변경 시 해당 캐시 즉시 무효화.

**TimescaleDB**: Postgres 위에 올리는 **시계열 데이터베이스 확장 플러그인**. 별도 DB가 아니라 `CREATE EXTENSION timescaledb`로 활성화. **시계열 데이터**(타임스탬프와 함께 쌓이는 측정값·이벤트)에 최적화. IoT 플랫폼에서 센서 데이터·API 사용량·감사 로그·디바이스 이벤트 등이 해당. **하이퍼테이블** 전략: (1) **청크(chunk)** — `chunk_time_interval`로 시간 단위 분할 저장. 유입량별 가이드라인: 센서 데이터(고빈도) → 1일, API 사용량·디바이스 이벤트 → 1주, 감사 로그(저빈도) → 1주~1개월. 청크 하나가 수백만 행 넘지 않도록 설정. (2) **자동 압축** — `add_compression_policy`로 오래된 청크 압축 정책 적용. Docker는 `timescale/timescaledb:latest-pg16` 등 이미지 사용. [NEXA-MIGRATE-01] §6.2 참고.

**PgBouncer (검토)**: 수천 대 IoT 동시 접속 대비 시 Postgres 커넥션 풀러. RLS가 `current_setting('app.current_user_id')` 등 세션 변수에 의존하므로 **Transaction 모드**는 보안 리스크. **Session 모드** 사용 권장. 디바이스→API→DB 구조라면 API 풀 크기가 우선. [NEXA-MIGRATE-01] 참고.

**MQTT · Message Queue · TimescaleDB · PgBouncer 세트 (IoT 데이터 처리 기준)**:

- **MQTT**: 엣지 디바이스에서 들어오는 **실시간 센서·제어 이벤트 스트림**. 경량·pub/sub.
- **Message Queue (Kafka, RabbitMQ)**: MQTT·HTTP 등에서 수집된 이벤트를 **비동기 작업·배치 처리**로 넘기는 **작업 큐/스트림 처리 계층**.
- **TimescaleDB**: MQ에서 소비된 이벤트를 **시계열 DB**로 저장·집계하는 계층. 센서·로그·API 사용량·디바이스 이벤트의 기준 저장소.
- **PgBouncer**: 대량의 IoT·API 요청이 TimescaleDB/Postgres에 접근할 때, **커넥션 수를 제어·풀링**하는 앞단. Session 모드로 RLS와 함께 사용.

**DB 관리 도구**: **DBeaver**. Postgres·MySQL 등 통합 클라이언트로 스키마·쿼리·데이터 조회·편집.

**무거운 작업 로그 저장 기준** (fluent-ffmpeg, Ollama 등): **Postgres(TimescaleDB)** — 조회·집계·RLS·다중 사용자 접근이 필요한 경우. 예: 인코딩 작업 이력, LLM 호출 이력, 작업별 상태·결과·에러. **별도 로그 파일** — 고빈도·디버그용·스택 트레이스, 단순 텍스트 스트림. 기준: (1) **쿼리·대시보드 필요** → TimescaleDB. (2) **유입량 매우 많음·디버깅 위주** → 파일(로테이션·로그 수집기). (3) **핵심 이벤트만** → TimescaleDB, **전체 상세** → 파일. 하이브리드: 요약·에러는 DB, 상세 스택은 파일.

**FFmpeg Docker 하드웨어 가속**: **nvidia-container-toolkit**을 호스트에 설치하고 Docker 실행 시 `--gpus all`로 GPU를 노출하면, 컨테이너 내 FFmpeg에서 **h264_nvenc**(NVIDIA GPU 인코딩)를 사용할 수 있다. CPU 인코딩 대비 인코딩 속도·서버 부하 분산에 유리하다. 호스트에 NVIDIA GPU와 해당 드라이버가 있어야 하며, 이미지에 NVENC 지원 FFmpeg 빌드가 포함되어 있어야 한다.

**ffmpeg.wasm 사용 정책**: 영상·오디오 **파일 크기 기준**으로 작은 것은 브라우저(ffmpeg.wasm)에서 편집해 서버 분산 효과를 보고, **큰 용량**은 사용자에게 "클라이언트에서 편집(느릴 수 있음)" 또는 "서버에 업로드 후 처리" 중 선택하도록 UI에서 안내한다.

**Cloudflare Tunnel과 MQTT 포트**: Tunnel은 기본적으로 HTTP/HTTPS(443) 구간을 연다. MQTT 기본 포트(1883/8883)는 Tunnel에서 직접 열 수 없으므로, **우회 전략**으로 **MQTT over WebSocket(wss)** 를 443에 올린다. 브로커(Aedes/Mosquitto)에 WebSocket 어댑터를 두고 클라이언트는 `wss://도메인/mqtt` 등으로 접속해, 443 하나로 웹·API·MQTT를 함께 터널링한다.

**MQTT 브로커 전략**: 아직 최종 결정은 아니나, **초반에는 Aedes를 Node 서버에 내장**해 진행하고, 규모·안정성·운영 요구가 커지면 **Mosquitto를 별도 Docker 등으로 분리**해 운영하는 방향을 검토 중이다. 나중에 브로커 전환 시 마이그레이션 부담을 줄이려면 **비즈니스 로직과 통신 로직을 분리(추상화)**해 두는 것이 좋다. 예: 토픽 구독·발행·인가 판단은 서비스 레이어에서 처리하고, 실제 MQTT 연결·메시지 송수신은 브로커(Aedes/Mosquitto)에 의존하는 어댑터로 격리.

## 6. 용어·설치 방식 정리

- **Docker**: 서비스 단위로 컨테이너 실행. GPU 가속 필요 시 호스트 GPU 노출 설정.
- **Native (Server-side)**: 서버 OS에 직접 설치 또는 Node 서버 내 라이브러리.
- **Native (npm)**: 프론트/백엔드 패키지 매니저로 설치.
- **Web Worker**: 브라우저 백그라운드 스레드 API. 무거운 데이터·파싱·계산을 메인 스레드에서 분리해 UI 응답성 유지. **AI 협업·실시간 처리**에서 대용량 파싱·스트리밍 시 활용 권장.

| 벡터 검색     | **Vector Quantization**             | 연속값→이산값 변환. **모델 양자화**: LLM 가중치의 비트 축소(FP32→INT8/4). GGUF, AWQ, GPTQ. 추론 속도·메모리 절약. **데이터 양자화**: 임베딩 벡터 압축(PQ, SQ). IVFFlat·저장·검색 효율. 둘은 대상(가중치 vs 임베딩)과 목적이 다름. | 모델=뇌 용량 줄이기. 데이터=검색창고 압축. 혼동 금지.        |
| 프로젝트 설계 | **프로젝트 DNA**                    | 프로젝트 성격에 따른 양자화·배치·보관 정책. 엄밀 기계(정확도+속도), 스마트팜(균형), 아트(확장성) 등. `project_settings.settings_data`의 `dna` 키에 사용자가 지정.                                                                 | 프로젝트 유전자: "이 프로젝트는 어떤 거친 도구를 쓸 것인가." |
| 프로젝트 설계 | **precision_level**                 | 프로젝트 DNA의 수준. 0=엄밀(기계장치), 1=균형(스마트팜), 2=느슨(아트). 양자화·배치 전략 선택 기준.                                                                                                                                | 정밀도 단계: 숫자가 낮을수록 정확·실시간 우선.               |
| 프로젝트 설계 | **batch_policy**                    | 배칭 규칙. max_batch_size, flush_ms, 우선순위 등. `settings_data.batch_policy`에 JSON으로 저장.                                                                                                                                   | "몇 개 묶어서 언제 보낼지" 규칙.                             |

#### 8.1.2 "선조치" vs 플랫폼 정책·런타임 갱신 (용어 구분)

- **선조치**는 **[문서 1]·[문서 4]** 전용 용어이다. 하드웨어/펌웨어 단, 0.1ms~10ms 단위의 **생존 본능**·절대 안전장치(Hard Reflex)를 의미하며, 인디케이터 추론을 기다리지 않는 로컬 선조치(Reflex)·바이패스(Bypass)를 가리킨다. NEXA-SYSTEM(플랫폼/샌드박스) 문서에서는 **"선조치"를 사용하지 않는다.**
- 플랫폼/샌드박스 단에서 **기능 자격(Capability) ID나 AI 설정을 수정했을 때 런타임에 즉시 시뮬레이션**해 보는 **지능적 민첩성**은 다음으로 표기한다.
  - **즉시 정책 적용** — 설정·역량 변경이 적용된 정책으로 곧바로 반영됨을 강조할 때.
  - **실시간 런타임 갱신** — 캐시·오케스트레이터 등이 재시작 없이 갱신되는 동작을 강조할 때.

### 8.2 모델 체급 (AI·멀티모달) — 지능 계층 명칭 통일

기획서 기준 **3단계** 구분. **명명 규칙:** 하위 하드웨어·지능에는 **Sentinel**(나노/마이크로)을, 상위에는 **Vista Indicator**를 붙여 [문서 1] 지능 위계 및 하드웨어 사양서와 동일하게 통일한다. 용도·리소스·품질에 따라 모델 선택·라우팅 시 참조.

| 체급                  | 영문            | 핵심 정의                                                                                           | 용도·스택 예시                                          | 비유 및 역할                   |
| --------------------- | --------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------ |
| **나노 센티널**       | Nano Sentinel   | 1단계. ESP32 등 최하위 하드웨어. **반사 신경.** 로우 데이터 감시, 노이즈 제거, 5W1H 단편 Fact 추출. | TinyML, STT(Whisper small), 엣지 디바이스.              | 반사: 가벼운 일만 빠르게.      |
| **마이크로 센티널**   | Micro Sentinel  | 2단계. 라즈베리 파이 등 엣지 허브. **인식 지능.** 객체 탐지·사건(Event) 식별, 데이터 비식별화.      | Ollama 3B~13B급, LLaVA 소·중형, YOLO, 채팅·vision 기본. | 인식: 일상 대화·시각 이해.     |
| **비스타 인디케이터** | Vista Indicator | 3단계. 고성능 AI 서버(NAS). **전략적 뇌.** 맥락(Why) 해석, 코일 벨렌서 전략 수립, 사용자 조언.      | 70B급, LLaVA 대형, RAG·메타포 추출·서사 종합·품질 검증. | 전략: 어려운 판단·품질의 척도. |

**데이터의 동기화 (벡터·검색 기준)**  
AI·멀티모달 파이프라인에서 임베딩이 쌓이는 지식·태그·FAQ 등과 **검색 인덱스**를 맞춰 두는 전략을 정리한다.

- **Metric 선택**: 시맨틱·RAG에는 **Metric: Cosine**(`vector_cosine_ops`, 쿼리 `<=>`)을 기본으로 둔다. 임베딩을 단위 벡터로 정규화해 두었다면 **Metric: Inner Product**(`vector_ip_ops`, `<#>`)로 바꿔 써도 동치이며, “값이 클수록 유사”라서 정렬만 반대로 세면 된다. 벡터가 정규화되지 않았거나 거리 기반이 필요하면 **L2 Distance**(`vector_l2_ops`, `<->`)를 고려한다.
- **인덱스와 동기화**: **HNSW**는 삽입·검색이 균형적이므로, 실시간에 가깝게 문서/태그가 추가·수정되는 `project_knowledge`, `project_tags`, `support_faq` 등에는 HNSW를 디폴트로 두고, 삽입 시점부터 인덱스가 따라가게 두면 된다. **IVFFlat**은 centroid를 미리 잡아야 하므로, 대량 임포트·야간 배치처럼 “한 번에 많이 쌓고 나서 검색 위주”일 때 선택하고, 그 직후 한 번 인덱스(재)구축으로 **데이터와 인덱스를 동기화**하는 식으로 쓰는 것이 좋다.
- **운용 요약**: 일상적인 동기화는 “행 추가/수정 시 임베딩 갱신 → HNSW가 자동 반영”으로 유지하고, 대규모 마이그레이션·리인덱싱 후에는 IVFFlat을 쓸 경우 `lists`를 데이터 규모에 맞게 조정한 뒤 한 번 생성·교체하는 흐름을 권장한다. 쿼리 시에는 선택한 Metric과 동일한 연산자(`<=>`, `<#>`, `<->`)를 사용해야 해당 인덱스가 사용된다.

**규칙**

- **위치**: `NEXA-Platform/.env` (루트 하나). `.env.example`은 템플릿으로 커밋.

## 10 DB 앞단(Front-end/Middleware)에 배치

- 하여 시스템의 안정성과 효율성을 높이기 위해 논의했던 주요 안전 장치 키워드들은 다음과 같습니다.
  멀티모달 시스템과 Ollama의 3단계 계층 구조를 고려할 때, 이 장치들은 특히 부하 분산과 응답 속도를 제어하는 핵심 역할을 합니다.

1. 처리량 제어 및 과부하 방지 (Traffic Control)

- Rate Limiting (처리율 제한): 특정 시간 동안 들어오는 요청 수를 제한하여 DB와 AI 모델에 과부하가 걸리지 않도록 차단합니다.
- Throttling (스로틀링): 시스템 리소스 상태에 따라 서비스 수준을 동적으로 조절하여 시스템 다운을 막습니다.
- Circuit Breaker (서킷 브레이커): DB나 AI 서버(Ollama)에 장애가 발생하면 즉시 연결을 차단하고 오류 메시지를 반환하여 장애가 전체 시스템으로 전이되는 것을 방지합니다.

1. 성능 최적화 및 속도 향상 (Performance)

- Caching (캐싱): 동일하거나 유사한 벡터 검색 결과(Embedding)를 Redis 등에 저장해 두었다가, DB까지 가지 않고 즉시 반환합니다.
- Request Collapsing (요청 결합): 짧은 시간에 들어온 동일한 쿼리를 하나로 묶어 DB에 한 번만 요청함으로써 중복 연산을 줄입니다.

1. 데이터 품질 및 보안 (Data Integrity & Security)

- Validation Layer (검증 계층): 들어오는 벡터 데이터의 차원(Dimension)이 맞는지, 데이터가 오염되지 않았는지 DB 입력 전 미리 확인합니다.
- Sanitizer (새니타이저): 입력값에서 악의적인 쿼리나 비정상적인 패턴을 필터링합니다.

1. 멀티모달/분산 환경 특화

- Load Balancer (로드 밸런서): 엣지, 현장(Jetson), 상급 서버 등 3단계 계층 중 가장 적절한 노드로 요청을 배분합니다.
- Message Queue (메시지 큐): 비동기 처리가 필요한 작업(이미지 벡터 추출 등)을 큐에 쌓아두고 순차적으로 처리하여 DB의 순간적인 병목 현상을 방지합니다.

---

정리하자면:
"캐싱으로 속도를 높이고, 서킷 브레이커와 레이트 리밋으로 안정성을 확보하며, 메시지 큐로 비동기 작업을 관리한다"는 핵심 전략을 논의했습니다.
현재 설계 중인 3단계 계층(엣지-현장-상급) 중, 어떤 단계의 안전 장치를 가장 우선적으로 구체화해볼까요? 특히 Jetson 같은 현장 장비는 리소스가 한정적이라 스로틀링 설정이 매우 중요할 수 있습니다.

## Redis는 이 시스템의 '안전 장치'이자 '가속기'로서 핵심적인 역할을 합니다.

- 특히 Ollama 기반의 3단계(엣지-현장-상급) 멀티모달 시스템에서는 단순한 DB 앞단 장치를 넘어 여러 용도로 활용될 수 있습니다.
  Redis를 시스템에 포함시켰을 때 얻을 수 있는 구체적인 효과는 다음과 같습니다.

1. 시맨틱 캐싱 (Semantic Caching)
   가장 강력한 기능입니다. 사용자가 던진 질문이나 이미지의 벡터 값을 Redis에 저장해두고, 유사한 요청이 들어오면 DB(pgvector)까지 가지 않고 Redis에서 즉시 답변을 내보냅니다.

- 효과: Ollama 모델의 추론 비용(GPU/CPU 리소스)과 DB 조회 시간을 획기적으로 줄입니다.
- 안전 장치 측면: DB에 가해지는 반복적인 고부하 쿼리를 원천 차단합니다.

1. 처리율 제한 (Rate Limiting) 구현체
   앞서 언급한 Rate Limiting을 실제로 구현할 때 Redis를 가장 많이 사용합니다.

- 효과: 엣지나 현장(Jetson) 장비에서 감당할 수 없는 수준의 요청이 들어올 때, Redis가 초당 요청 수를 체크하여 초과분을 차단합니다.

1. 메시지 브로커 (Message Broker)
   멀티모달 특성상 이미지나 영상 처리처럼 시간이 걸리는 작업이 많습니다.

- 효과: 요청을 Redis의 List나 Pub/Sub에 쌓아두고, Jetson이나 상급 서버가 여유가 생길 때마다 하나씩 꺼내 처리하게 함으로써 시스템이 뻗는 것을 방지합니다.

1. 3단계 계층 간의 상태 공유 (State Store)

- 효과: 엣지 디바이스에서 처리하던 작업의 상태나 중간 결과를 Redis에 임시 저장해두면, 상급 서버가 이를 이어받아 처리하기 용이합니다. (분산 환경의 접착제 역할)

---

💡 Redis를 포함한 전체 구조 (예시)

1. 사용자 요청 → 2. Redis 캐시 확인 (있으면 즉시 반환) → 3. Redis에서 Rate Limit 체크 → 4. Ollama 임베딩 생성 → 5. pgvector(HNSW/IVFFlat) 검색 → 6. 결과를 Redis에 저장 후 반환

Redis는 특히 Vector Database 기능(RedisVL)도 자체적으로 가지고 있어, pgvector와 병행하거나 아주 가벼운 벡터 데이터는 Redis에서 직접 처리하는 전략도 가능합니다.
지금 구상하시는 구조에서 Redis를 주로 '속도 향상(캐시)' 목적으로 쓰실 계획인가요, 아니면 '서버 간 통신(메시지 큐)' 목적으로 더 비중을 두시나요? 혹은 둘 다 고려 중이신가요? 구체적인 우선순위에 따라 설정 방식이 달라집니다.
