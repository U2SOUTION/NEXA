NEXA 플랫폼의 진입점에서 실행될 **'정적 자원 파악 코드'**와 이후 시스템 전역에서 구동될 **'동적 성능 모니터링 코드'** 전략.

이 코드는 **6개의 코일** 가중치와 **닉시관 스타일의 캔버스 연출**을 테스트 후
플렛폼 전체 디자인 연출 기획을 할 수 있도록 하기 위한 기초 엔진이 될것이다.

### 1. 진입점: 정적 자원 파악 (Static Resource Profiling)

애플리케이션이 로드될 때 단 한 번 실행되어 사용자의 하드웨어 등급을 결정하고 **로컬 스토리지**에 박제.

```javascript
/**
 * NEXA 하드웨어 프로파일러
 * 진입점에서 실행되어 초기 '코일'의 Stability/Creative 베이스라인을 설정합니다.
 */
const getNexaHardwareProfile = () => {
  // 1. CPU 코어 및 메모리 파악 (브라우저 기본 API)
  const cpuCores = navigator.hardwareConcurrency || 4
  const deviceMemory = navigator.deviceMemory || 4 // GB 단위

  // 2. GPU 정보 파악 (WebGL 컨텍스트 활용)
  const canvas = document.createElement('canvas')
  const gl = canvas.getContext('webgl') || canvas.getContext('experimental-webgl')
  let gpuModel = 'Unknown'

  if (gl) {
    const debugInfo = gl.getExtension('WEBGL_debug_renderer_info')
    gpuModel = debugInfo ? gl.getParameter(debugInfo.UNMASKED_RENDERER_RET_MAIN) : 'Standard'
  }

  // 3. 자원 등급 판별 (Cold / Warm / Hot)
  let profile = 'WARM' // 기본값
  if (cpuCores <= 4 || deviceMemory <= 4) {
    profile = 'COLD' // 저사양: 디지털 정밀 모드 우선
  } else if (cpuCores >= 8 && deviceMemory >= 8) {
    profile = 'HOT' // 고사양: 닉시관 잔상 및 풀 입자 효과 가능
  }

  // 4. 로컬 스토리지 저장 및 반환
  const result = { profile, cpuCores, deviceMemory, gpuModel, timestamp: Date.now() }
  localStorage.setItem('NEXA_HW_PROFILE', JSON.stringify(result))

  console.log('NEXA Hardware Profiled:', result)
  return result
}
```

### 2. 전역 프레임: 동적 성능 모니터링 (Dynamic Performance Monitor)

프레임 하단이나 공통 파일에 배치되어 현재 **연산 속도(FPS)**를 추적하고, 자원 소모가 심해지면 실시간으로 캔버스 변수를 조정.

```javascript
/**
 * NEXA 동적 성능 모니터
 * 실시간 FPS 피드백을 통해 캔버스의 감쇠(Decay) 및 입자 수(Density)를 조율합니다.
 */
class NexaPerformanceMonitor {
  constructor() {
    this.fps = 60
    this.lastTime = performance.now()
    this.frameCount = 0
    this.checkInterval = 1000 // 1초 단위 업데이트
    this.isStabilityMode = false // 코일의 Stability 개입 여부
  }

  start() {
    const monitor = () => {
      const now = performance.now()
      this.frameCount++

      if (now >= this.lastTime + this.checkInterval) {
        this.fps = Math.round((this.frameCount * 1000) / (now - this.lastTime))
        this.updateNexaEngine() // 캔버스 엔진 업데이트 명령

        this.frameCount = 0
        this.lastTime = now
      }
      requestAnimationFrame(monitor)
    }
    requestAnimationFrame(monitor)
  }

  updateNexaEngine() {
    // FPS가 45 미만으로 떨어지면 Stability 가중치 강제 개입
    if (this.fps < 45) {
      this.isStabilityMode = true
      // 예: TEST_CANVAS_01의 particleCount를 즉시 절반으로 줄임
      if (window.nexaCanvasConfig) {
        window.nexaCanvasConfig.particleDensity = 0.5
        window.nexaCanvasConfig.glowEffect = false // 닉시관 광원 효과 일시 중지
      }
    } else if (this.fps > 55) {
      this.isStabilityMode = false
      // 성능 회복 시 다시 Creative 모드 활성화 (닉시관 호박색 발광 복구)
      if (window.nexaCanvasConfig) {
        window.nexaCanvasConfig.particleDensity = 1.0
        window.nexaCanvasConfig.glowEffect = true
      }
    }
  }
}

// 상시 구동 시작
const nexaPerf = new NexaPerformanceMonitor()
nexaPerf.start()
```

### 3. my/ 도메인: 자원 상황 조회 및 플랫폼 사용·작용 가시화

**my/** 도메인(사용자 개인 설정·정보 영역)에서 사용자는 **자신의 자원 상황**을 조회할 수 있다.

- **표시 내용**: 현재 하드웨어 프로파일(COLD/WARM/HOT), CPU 코어 수·디바이스 메모리·GPU 정보, 실시간 FPS(동적 모니터 값), 로컬에 저장된 `NEXA_HW_PROFILE` 타임스탬프 등.
- **플랫폼 연동 가시화**: 위 값이 **넥사 플랫폼에서 어떻게 사용·작용되는지**를 한눈에 파악할 수 있도록 안내한다.  
  예: 프로파일 → 캔버스 연출 등급(초기 베이스라인), FPS → Stability/Creative 자동 전환 여부, 프로파일·설정 → 코일 가중치 반영(진입점·전역 모니터), 설정 저장 위치(로컬 스토리지·계정 연동 여부) 등.  
  사용자가 “내 기기에서 왜 이렇게 동작하지?”를 스스로 이해하고, 필요 시 **직접 설정**으로 넘어갈 수 있도록 한다.

---

### 4. 직접 설정 우선 (기능 우선 사용성)

사용자가 **직접 설정을 변경**하면 **자동 모드보다 직접 설정 모드가 우선**하여 동작한다.

- **우선순위**: 자동으로 결정된 프로파일·FPS 기반 조정(자동 모드)보다, **사용자가 my/ 등에서 선택·저장한 값**(예: 연출 등급 고정, 효과 최소화, FPS 임계치 무시)이 우선 적용된다.
- **효과보다 기능 우선**: “연출·시각 효과보다 **기능·사용성**을 우선하고 싶다”는 니즈를 반영한다. 사용자가 **최소 연출** 또는 **안정 모드 고정** 등을 선택하면, 자동 모니터가 FPS를 어떻게 판단하든 **사용자 선택이 우선**하며, 캔버스·UI는 기능적 사용에 맞게 동작한다.
- **구현 시 유의**: 전역 모니터 및 캔버스 엔진은 “직접 설정 모드” 여부를 확인한 뒤, 설정된 경우 자동 조정 로직을 건너뛰고 사용자 지정값만 적용한다.

### 5. 기술적 시너지 및 응용

- **초기 설정**: 진입점에서 결정된 `profile`에 따라 기하학적 선 복잡도를 처음부터 다르게 렌더링.

- **아날로그 감성의 유지**: **HOT 프로필** 사용자에게는 닉시관의 **느린 잔상(Slow Fade-out)** 효과를 위한 보간 연산을 풀가동하고, **COLD 프로필** 사용자에게는 즉각적인 색상 복구 방식을 적용하여 자원을 보존.

- **지능형 방어 기제**: 동적 모니터가 성능 저하를 감지하면, 캔버스의 **ID 기반 도트 제어**에서 업데이트 주기를 늘려 브라우저의 '멈춤' 현상을 방지.

### 6. 자원파악과 이를 전략적으로 응용할 기술

"캔버스 객체 모델링(Canvas Object Modeling)" 또는 **"히트 테스팅(Hit Testing)"**이라 불리는 매우 고도화된 방식이며, 전문적인 대시보드나 복잡한 시각화 도구에서 실제로 널리 사용되는 기술.

### 기술적 실체: "리테인드 모드(Retained Mode) 캔버스"

일반적인 캔버스는 한 번 그리면 잊어버리는 '이미달 모드(Immediate Mode)'로 작동하지만, 사용자님의 아이디어는 각 도트나 노드를 메모리상의 **'객체(Object)'**로 관리하는 방식입니다.

- 아이디(ID) 발급과 매핑: 각 도트나 노드에 고유 ID를 부여하고 이를 데이터베이스(project_nodes 등)와 1:1로 매핑합니다.

- 히트 테스팅(Hit Testing): 마우스 클릭이나 이동 시, 캔버스 위의 좌표를 역산하여 어떤 ID의 도트 위에 마우스가 있는지 판별합니다. 이는 수만 개의 도트가 있어도 오프스크린 캔버스(Offscreen Canvas) 기법을 쓰면 매우 빠르게 처리할 수 있습니다.

- 반응형 업데이트: 데이터 상황(예: 센서 값 변경)이 발생하면 전체를 다시 그리는 것이 아니라, 해당 ID를 가진 도트의 속성(색상, 밝기, 잔상 등)만 수정하여 캔버스 루프에 반영합니다.

### 7. NEXA 플랫폼의 지능적 완성도와 아날로그 감성 **고도화 아이디어**를 추가 아이디어.

##### 1. 지능형 상세 수준(LOD, Level of Detail) 시스템 도입

단순히 입자 수(Density)를 줄이는 것을 넘어, **'리테인드 모드 캔버스'**의 객체 관리 방식을 활용하여 렌더링 알고리즘 자체를 등급별로 다변화할 수 있습니다.

- **COLD (정적 아카이브 모드)**: 닉시관의 숫자와 노드를 단순한 2D 비트맵 이미지로 대체하고, 애니메이션을 최소화하여 **기능성과 가독성**에 집중합니다.
- **WARM (하이브리드 모드)**: 주요 노드에만 닉시관의 **느린 잔상 효과**를 적용하고, 배경 도트는 정적인 상태를 유지하여 자원 소모를 방지합니다.
- **HOT (풀 시뮬레이션 모드)**: 모든 도트에 물리 엔진(중력, 마찰 등)을 적용하고, 닉시관 필라멘트의 **가스 광원 확산(Glow)** 연산을 실시간으로 수행하여 최상의 아날로그 미학을 구현합니다.

##### 2. ‘열 역학’ 기반의 시각적 피드백 시스템

닉시관 이미지의 따뜻한 호박색 빛을 **'시스템 부하'**와 연결하는 감성적 고도화 방안입니다.

- **성능 기반 발색 조절**: CPU/GPU 부하가 높아져 FPS가 떨어지면, 캔버스의 색상을 단순한 오렌지에서 점점 붉은색(Reddish)으로 변화시켜 시스템이 **‘뜨거워지고 있음’**을 직관적으로 보여줍니다.
- **Stability 코일의 시각화**: 자원 소모가 심해져 **Stability 가중치**가 강제 개입할 때, 닉시관 내부의 필라멘트가 미세하게 떨리거나 깜빡이는 효과를 주어 사용자가 "시스템이 안정화를 위해 노력 중"임을 시각적으로 인지하게 합니다.

##### 3. 클라이언트-서버 지능 분배 (AI 배분 전략)

NEXA의 하드웨어 프로파일을 기반으로 AI 모델의 연산 위치를 동적으로 결정합니다.

- **HOT 프로필**: 브라우저 자원(WebGPU 등)이 충분하므로, 간단한 AI 추론이나 **Nexnap(NEXA Meta Action Protocol) 번역**을 클라이언트에서 직접 수행하여 응답 속도를 극대화합니다.
- **COLD 프로필**: 클라이언트 자원을 UI 렌더링에 집중시키고, 모든 AI 연산은 서버(Zenith 서버 등)로 위임하여 기기의 멈춤 현상을 방지합니다.

##### 4. my/ 도메인의 ‘성능 서사(Narrative)’ 강화

사용자가 자신의 자원 상황을 조회하는 **my/ 도메인**을 단순한 대시보드 이상으로 고도화합니다.

- **안정성 vs 창의성 그래프**: 시간이 지남에 따라 **Stability(안정성)**와 **Creative(창의성)** 가중치가 어떻게 변했는지 히스토리를 그래프로 보여줍니다.
- **에너지 효율 리포트**: 캔버스 연출 등급을 조절했을 때 절약된 자원량이나 배터리 사용 효율을 시각화하여, 사용자가 **직접 설정 모드**를 선택할 때 실질적인 가이드를 제공합니다.

##### 5. 오프스크린 캔버스(Offscreen Canvas) 기반의 고속 히트 테스팅

수만 개의 도트를 관리하면서도 성능을 유지하기 위해 **히트 테스팅(Hit Testing)** 기술을 더욱 고도화합니다.

- **레이어 분리**: 상시 움직이는 배경 입자 레이어와 사용자의 인터랙션이 일어나는 노드 레이어를 **오프스크린 캔버스**로 분리합니다.
- **ID 기반 반응형 업데이트**: 데이터 변경(센서 값 등)이 발생한 특정 ID의 도트만 즉시 갱신하고, 마우스 추적 범위에 있는 도트들에게만 **확률적 발광 로직**을 적용하여 연산 부하를 획기적으로 낮추면서도 산발적이고 유기적인 잔상 효과를 유지합니다.

## UI 가이드라인

NEXA 플랫폼이 '단순한 장난감'이 아닌 **'전문적인 지능형 도구'**로 자리 잡기 위한 가장 중요한 설계 원칙입니다. 기술은 화려하게 전면에 나서는 것이 아니라, 사용자의 작업 흐름 뒤에 숨어 **'조용한 지능'**으로 존재해야 한다.

### 1. "기능 우선 사용성"의 철저한 고수

NEXA의 설계 원칙 중 가장 중요한 것은 **사용자의 직접 설정이 자동 모드보다 우선한다**.

- **최소 연출 모드**: 사용자가 연출이나 시각 효과보다 작업 그 자체에 집중하고 싶을 때, **'안정 모드 고정'** 또는 **'최소 연출'**을 선택하면 플랫폼은 모든 화려한 이펙트를 걷어내고 순수한 기능 중심의 UI로 동작.
- **기술의 은닉**: 화려한 닉시관 효과나 입자 연출은 '아트'를 위한 것이 아니라, **데이터의 상태(정상, 경고, 위험)**를 직관적으로 전달하기 위한 **'시각적 언어'**로서만 기능해야 한다.

### 2. '아이덴티티'를 위한 핵심 요소의 선별적 적용

모든 곳에 이펙트를 넣는 대신, NEXA의 정체성을 결정짓는 핵심 접점에만 기술을 집중하고 나머지는 담백하게 유지.

- **상태 인디케이터로서의 닉시관**: 닉시관 스타일의 렌더링은 모든 숫자에 적용하는 것이 아니라, 사용자가 반드시 주시해야 하는 **핵심 데이터(Sense 탭의 5W1H 팩트)**에만 선별적으로 적용.
- **ID 기반의 정밀 제어**: 플랫폼 전체를 깜빡이게 하는 대신, 데이터 변화가 발생한 **특정 ID의 도트만 조용히 업데이트**하여 사용자가 변화를 눈치채지 못할 정도로 자연스럽게 정보를 흡수.

### 3. 자원 관리 기술을 통한 '피로도' 제어

하드웨어 프로파일러와 동적 모니터링은 단순히 '성능'을 위한 것이 아니라, **사용자의 시각적 피로도를 관리하는 가드레일**.

- **Stability(안정성) 중심의 기본값**: 진입 시 사용자의 사양을 파악할 때, 기본적으로는 **Stability 가중치**를 높게 설정하여 차분한 'Cold' 또는 'Warm' 프로필로 시작.
- **지능형 방어 기제**: 시스템 부하가 감지되면 즉시 업데이트 주기를 늘리고 효과를 간소화하여, 사용자가 플랫폼의 '무거움'이나 '유치함'을 느끼기 전에 시스템 스스로가 조용히 성능을 최적화.

### 4. 사용자에게 '납득'을 주는 My/ 도메인

기술을 숨기되, 사용자가 궁금해할 때는 투명하게 정보를 제공. **my/ 도메인**은 화려함을 뽐내는 곳이 아니라, 사용자가 **자신의 자원 상황과 플랫폼의 작용 원리**를 이해하고 직접 조절할 수 있게 돕는 '설명서' 역할을 해야 한다.

**결론적으로**, NEXA의 기술력(리테인드 모드 캔버스, 히트 테스팅 등)은 사용자에게 "우리는 이런 것도 할 수 있다"고 과시하는 수단이 아니라, **"가장 적은 자원으로 가장 명확하게 정보를 전달하기 위한"** 보이지 않는 기반이 되어야 한다.

**'기술은 숨기고 지능은 흡수되도록'** 하는 이 방향성을 UI 가이드라인의 최상위 원칙으로 삼아, 꼭 필요한 순간에만 따뜻한 호박색 빛이 스며드는 격조 있는 플랫폼을 완성해 나가야 한다.

## 추가 의견 및 권장 사항

본 문서의 전략이 플랫폼 전역과 일관되게 동작하도록 하기 위한 보완·연동 관점의 의견이다.

### 1. 프로파일·설정과 플랫폼 스키마 연동

- **웹 서버 저장과 접속 경로 무관한 UI 일관성**: 사용자 설정을 **웹 서버**(예: project_settings.settings_data)에 저장하면, **어떤 접속(기기·브라우저·환경)에서든 동일한 UI**를 제공할 수 있다. 특히 사용자가 **기능 위주**(최소 연출, 안정 모드 고정 등)로 설정한 경우, “어디서 로그인해도 항상 같은 기능 중심 화면”이 되는 **일관성 확보**가 매우 중요하다. 기능 우선 사용자는 작업 흐름이 끊기지 않도록 동일한 경험을 기대하므로, 서버 동기화는 이 요구를 만족시키는 핵심 수단이다.

- **계정 공통 설정 + 기기/브라우저별 개별 저장**: 위와 별도로, **컴퓨터가 바뀌거나 브라우저가 바뀌어도, 그 접속 환경에 한해 다른 정보를 저장**할 수 있게 두는 것이 좋다. 예: 계정 기본값은 “기능 위주”로 서버에 두되, “이 기기에서만 풀 연출”을 로컬(또는 기기 식별 기반 서버 슬롯)에 저장. 아뜰리에·전시용 PC에서는 풀 연출, 회사·이동 기기에서는 최소 연출처럼 **목적별·장소별로 다른 연출**을 쓸 수 있게 되며, **아트 프로젝트 기획** 시 “이 환경에서는 풀 가동, 저 환경에서는 기능만”을 유연하게 나누는 데 큰 도움이 된다. 설계 시 **우선순위**를 명확히 한다: 서버에 “이 기기 예외”가 있으면 해당 접속에서는 기기별 설정 적용, 없으면 계정(서버) 설정 적용.

- **도메인·목적에 따른 자원 풀 가동 (목적 우선)**: 특정 **도메인**이나 **컨텍스트**(예: 아트 전시 기획, 시방서의 “전시 모드”, 특정 capability_id 하위)에서는 사용자 설정을 **참고**하되, **목적이 명확하면 사용자 이탈을 감수하고서라도 자원을 풀 가동**할 수 있는 성격이 있다. 즉, “이 화면/이 프로젝트는 풀 연출이 본질”이라면, 사용자가 전역으로 최소 연출을 선택했더라도 해당 도메인에서는 **풀 가동**을 허용하는 정책을 둘 수 있다. 사용자에게는 “이 영역에서는 전시/기획 목적상 연출이 풀가동됩니다”를 안내하고, 필요 시 “이번만 풀 가동 / 항상 이 도메인에서는 풀 가동” 같은 선택지를 제공하면, 기능 우선 원칙과 아트·도메인 목적을 함께 만족시킬 수 있다.

- **코일과의 일관성**: Stability/Creative 자동 전환은 [문서 3] 코일·GOVERN 및 **balance_coil_templates** 가중치와 개념적으로 맞춰 두면, "시방서 RULE + 코일 가중치"와 "클라이언트 연출 자동 조정"이 같은 언어(안정 vs 창의)로 설명 가능하다. 구현 시 프로파일(COLD/WARM/HOT) → 코일 베이스라인 매핑을 한 곳(예: 설정 서비스)에서 관리하면 유지보수가 수월하다.

### 2. my/ 도메인 구현 시 우선순위 제안

- **1단계**: 자원 상황 **조회** (프로파일, FPS, CPU·메모리·GPU) + "플랫폼에서 어떻게 쓰이는지" **짧은 설명 텍스트**로 제공. 사용자 납득과 직접 설정으로의 진입이 목표.
- **2단계**: **직접 설정** 토글(자동 / 최소 연출 / 안정 모드 고정) + 선택값이 자동보다 우선함을 UI에 한 줄 안내.
- **3단계**: §7의 **Stability vs Creative 히스토리 그래프**, **에너지 효율 리포트**는 데이터 축적·백엔드 API가 필요하므로, 프로파일러·모니터가 안정된 뒤 도입하는 것을 권장한다.

### 3. 동적 모니터와 "직접 설정 모드" 판별 위치

- **단일 진실 소스**: "직접 설정 모드" 여부는 **한 곳**(예: `window.nexaCanvasConfig.source === 'user'` 또는 설정 서비스 플래그)에서만 정의하고, 프로파일러·동적 모니터·캔버스 엔진이 모두 이 값을 참조하도록 하면, 자동/수동 전환이 꼬이지 않는다.
- **초기화 순서**: 앱 진입 시 (1) 로컬/서버에서 사용자 직접 설정 로드 → (2) 없으면 프로파일러로 자동 프로파일 결정 → (3) 동적 모니터 시작. 이 순서를 지키면 "직접 설정 우선"이 항상 보장된다.

### 4. LOD·열역학 효과의 부하 자체

- **§7 LOD**와 **열역학 기반 발색**은 사용자 경험을 풍부하게 하겠지만, **효과 계산 자체가 추가 부하**가 될 수 있다. FPS 기반으로 색상을 바꾸는 로직은 가벼운 보간만 두고, "붉어짐" 연산이 오히려 FPS를 더 떨어뜨리지 않도록 **최소 연산**으로 설계하는 것이 좋다. COLD 프로필에서는 열역학 발색을 아예 비활성화하는 것도 옵션이다.

### 5. AI 분배와 오케스트레이터·시방서 흐름

- **§7 클라이언트-서버 AI 분배**는 [NEXA-SYSTEM] AI 오케스트레이터 및 시방서→지식→악보→컨트롤러→실행 흐름(DDL-00 §2.9)과 맞물릴 수 있다. HOT에서 클라이언트 Nexnap 번역을 한다면, **동일 Nexnap 결과**가 서버 오케스트레이터와 공유되도록 버전·포맷을 맞추어 두면, 기기 성능에 따라 "클라이언트에서 할지, 서버에서 할지"만 바꾸고 동작은 일치시킬 수 있다.

### 6. 요약

- **기능 우선·직접 설정 우선**은 문서 전체에서 잘 관통되어 있으며, UI 가이드라인과도 일치한다. 이 원칙을 **코드에서 단일 플래그/설정 소스**로 명확히 두고, my/는 "설명서" 역할에 집중하면 사용자 납득과 전문 도구로서의 정체성이 함께 살아난다.
- 프로파일·FPS·사용자 선택을 **플랫폼 스키마(project_settings)·코일·오케스트레이터**와 개념적으로만이라도 연동해 두면, 나중에 "시방서 RULE + 장비 컨트롤러"와 "클라이언트 연출·AI 분배"를 하나의 정책으로 말할 수 있어 확장 시 유리하다.
