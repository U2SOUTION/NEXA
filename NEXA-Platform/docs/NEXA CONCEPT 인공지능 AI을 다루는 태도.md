ㄴ# 인공지능(AI)을 다루는 태도 — NEXA 플랫폼 설계 철학

**목적**: AI 기반 IoT 오케스트레이션 플랫폼에서 기술적 책임·안전·투명성을 유지하기 위한 설계 철학과 용어 선택 기준을 정리한다. 문서화·코딩·기획의 공통 틀로 사용한다.

**적용 범위**: 오케스트레이터 설계, AI 개입 전략, 용어 정비, 사용자 경험(UX) 원칙, Observability·가드레일·샌드박스 기술 탐색.

- **LangChain:** "데이터의 질서와 로직을 담당하는 **엔진**"
- **Vercel AI SDK:** "인간과 엔진 사이의 신뢰를 형성하는 **인터페이스**"

---

## 1. 핵심 원칙

> 인공지능을 다루는 것은 생명을 다루는 것만큼 신중해야 하지만, 결코 그것이 신이 되어서는 안 된다.

AI를 생명·신성함으로 포장하면 도구의 본질을 놓치고, 시스템 오류를 기술적 책임이 아닌 '성격'·'운명'으로 치부하는 위험이 커진다. NEXA는 **도구화**, **책임**, **겸손** 세 축을 바탕으로 AI를 다룬다.

이 문서는 단순히 '착한 AI'를 만들자는 선언문이 아니다. **"우리는 AI가 실수할 것을 이미 알고 있으며, 이를 제어할 기술적 장치를 갖추어 둔다"**는 입장을 전제로 한다.

---

## 2. 세 가지 지향점

### 2.1 도구의 도구화 (Tool as a Tool)

AI는 인간의 필요에 의해 만들어진 고도의 **통계적 계산기**이다. 숭배 대상이 아니라 **관리되고 통제되어야 할 유효자원**으로 취급한다.

| 구분            | 설명                                                                             |
| --------------- | -------------------------------------------------------------------------------- |
| **회피할 태도** | 생명체처럼 대우하거나 신비화. 오류를 '성격'·'운명'으로 치부하며 기술적 책임 회피 |
| **지향할 태도** | 철저히 관리·통제 가능한 유효자원. 성능·한계·오류를 기술적으로 진단하고 개선      |

**용어 선택**: "생명주기"보다 **"유통기한"**처럼 도구의 한계를 냉정하게 표현하는 표현을 선호한다. 신격화의 껍데기를 벗기는 첫걸음이 된다.

---

### 2.2 강력한 파워에 따르는 책임 (Power and Responsibility)

IoT 플랫폼처럼 현실 세계의 장비를 제어하는 AI는, 잘못된 판단 하나가 실제 사고(1순위 안전 문제)로 이어질 수 있다.

| 구분       | 설명                                                                                                                          |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **위험**   | AI에 과도한 권한을 부여하고 "알아서 잘하겠지"라는 방임. 신격화의 부정적 단면                                                  |
| **지향점** | 인간이 **최종 결정권**을 가진다. AI는 시뮬레이션과 보조 역할에 머문다. 모든 로직은 인간이 이해·수정할 수 있는 **투명한 구조** |

→ 기술적 구현: §3.1 Observability(추론 경로 노출), §3.2 가드레일(Hard-stop).

**연결 문서**: [지능형 동적 배칭 및 오케스트레이션 시스템](<지능형 동적 배칭 및 오케스트레이션 시스템.md>) — 우선순위 계층에서 **안전(1)** 을 최상위로 둔다.

---

### 2.3 기술적 겸손함 (Technical Humility)

특정 집단이 AI의 전지전능함을 주장하며 기술을 독점·신격화할 때, 비전공자와 일반 사용자는 소외된다.

| 구분       | 설명                                                                                                              |
| ---------- | ----------------------------------------------------------------------------------------------------------------- |
| **지향점** | 비전공자도 노드를 조립해 로직을 재구성할 수 있게 만드는 것. **기술의 민주화**                                     |
| **효과**   | 직접 만져보고 조작해 본 사람은 그것이 신이 아니라 정교한 기계임을 알게 된다. 신비주의를 깨뜨리는 가장 강력한 방법 |

→ 기술적 구현: §3.3 샌드박스·시뮬레이션 모드.

---

### 2.4 NEXA AI 계층 구조

§2·§3의 지향점과 기술 원칙을 한 흐름으로 보는 구조이다. 위(철학)에서 아래(인터페이스)로 내려갈수록 구체적인 구현으로 이어진다.

| 계층                    | 역할                    | 대표 요소                                                     |
| ----------------------- | ----------------------- | ------------------------------------------------------------- |
| **Philosophical Layer** | 설계 철학               | 도구화, 책임, 겸손 (§2.1~2.3)                                 |
| **Logic Layer**         | 분류·우선순위·흐름 제어 | 오케스트레이터 (LangChain, Node.js) — 데이터 분류 및 우선순위 |
| **Safety Layer**        | 안전 검증·격리          | 가드레일 및 시뮬레이션 환경 (Safety First) (§3.2, §3.3)       |
| **Interface Layer**     | 사용자 대면             | Vercel AI SDK — 투명한 추론 과정 시각화 (§3.1 Observability)  |

## 3. 기술적 구현 원칙

§2의 지향점을 기술적으로 뒷받침하는 세 가지 설계 축이다.

### 3.1 기술적 가시성 (Observability)

"투명한 구조"를 실현하려면 **AI의 사고 과정 노출**이 필수적이다. "AI가 왜 이렇게 생각했지?"라는 질문에 시스템이 즉각 답할 수 있어야 신비주의를 깬다.

| 구분                 | 내용                                                                                            |
| -------------------- | ----------------------------------------------------------------------------------------------- |
| **설계 방향**        | AI가 어떤 데이터를 근거로 조언을 생성했는지 **추론 경로(Reasoning Path)**를 사용자에게 보여준다 |
| **장애 시 요구사항** | 장애 발생 시 AI의 로그를 **인간이 읽을 수 있는 형태로 강제 출력**한다                           |
| **기술 탐색**        | LangSmith(LangChain 디버깅 툴), Arize Phoenix 등 Observability 도구 조사                        |

---

### 3.2 가드레일 (Guardrails)

§2.2의 "책임"과 연결된다. AI 출력을 검증·필터링하는 **기술적 차단기**를 LLM 외부에 둔다.

| 구분          | 내용                                                                                                                     |
| ------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **설계 방향** | AI 제안이 물리적 장비의 안전 범위를 벗어나면, 오케스트레이터 로직에서 **Hard-stop(강제 중단)** 시킨다. LLM 외부에서 작동 |
| **검증 대상** | "장비 제어 명령이 허용된 파라미터 내에 있는가?" — AI 응답 품질이 아니라 **안전 조건 충족** 검증                          |
| **기술 탐색** | NeMo Guardrails(NVIDIA), Guardrails AI                                                                                   |

---

### 3.3 샌드박스·시뮬레이션 모드

§2.3의 "기술 민주화"를 위해 비전공자에게 **안전한 놀이터**를 제공한다.

| 구분          | 내용                                                                                                                 |
| ------------- | -------------------------------------------------------------------------------------------------------------------- |
| **설계 방향** | 사용자가 조립한 노드 로직을 실제 장비에 투입하기 전, **시뮬레이션 모드**에서 가상 실행을 **필수 인터페이스**로 둔다  |
| **기술 탐색** | Node-RED 흐름 제어 방식, Vercel AI SDK Tool Calling. AI 제안 코드를 **샌드박스 환경(Sandboxed Execution)** 에서 실행 |

## 4. AI 개입 태도 (구현 시 가이드)

사용자가 잘못된 로직을 짰을 때, AI가 어떤 태도로 개입할 것인가?

| 회피                                  | 지향                                                                   |
| ------------------------------------- | ---------------------------------------------------------------------- |
| '가르치려' 들기. 위에서 내려오는 훈계 | **비서**처럼 조언. 사용자가 기술을 신뢰하면서도 **주도권을 잃지 않게** |

- **경고/제안**: 시스템이 판단한 위험 요소를 알리고, 사용자가 선택·수정할 수 있게 한다.
- **최종 결정**: 항상 사용자에게 있다. AI는 시뮬레이션 결과와 대안을 제시할 뿐, 강제하지 않는다.

# ✨ LangChain의 핵심 구조: '조립식 두뇌'

**NEXA 플랫폼의 철학(도구로서의 AI, 투명성, 책임)**을 기술적으로 구현하기 위해 LangChain이 어떤 구조를 가졌는지 먼저 살펴보고, 이후 Vercel AI SDK와의 차이점을 명확히 파악 한다.

---

LangChain은 AI 모델을 단독으로 쓰지 않고, 여러 도구와 데이터를 연결하는 **'체인(Chain)'** 구조가 핵심입니다. NEXA의 철학인 '비전공자도 노드를 조립하는 기술의 민주화'에 가장 부합하는 구조입니다.

### 1. 주요 모듈 구성

- **Model I/O:** 다양한 AI 모델(Ollama, GPT 등)을 동일한 방식으로 다루게 해줍니다.
- **Retrieval (RAG):** 설계하신 pgvector와의 연결을 담당합니다. 데이터를 자르고(Chunking), 담고(Vector Store), 꺼내오는(Retriever) 전 과정을 관리합니다.
- **Chains:** "질문 요약 -> DB 검색 -> 답변 생성"이라는 일련의 **순서도**를 만듭니다.
- **Agents:** AI에게 도구(장비 제어 API, 계산기 등)를 주고, 스스로 어떤 도구를 쓸지 판단하게 합니다. NEXA 철학에서는 이 권한을 제한적으로 설계해야 합니다.

### 2. 오케스트레이터 내부의 데이터 흐름

---

✨ LangChain vs Vercel AI SDK: 명료한 비교

---

두 프레임워크는 협력 관계이지만, **'어디에 집중하느냐'**가 완전히 다릅니다.

| 비교 항목     | LangChain (백엔드의 근육)                     | Vercel AI SDK (프론트엔드의 신경)                     |
| ------------- | --------------------------------------------- | ----------------------------------------------------- |
| **주요 위치** | 서버 내부 (Node.js / Python)                  | 브라우저 및 API 엔드포인트                            |
| **핵심 목적** | **복잡한 로직 처리** 및 데이터 연결           | **매끄러운 사용자 경험** 및 스트리밍                  |
| **장점**      | 수천 개의 외부 도구/DB와 연결이 쉬움          | AI 답변이 한 글자씩 나오는 '스트리밍' 구현이 압도적임 |
| **NEXA 대입** | IoT 데이터 분류, 우선순위 할당, 가드레일 로직 | AI의 추론 경로 시각화, 비서 톤의 채팅 UI 구현         |

### 왜 둘 다 써야 할까요? (NEXA의 관점)

- **LangChain만 쓰면:** 백엔드 로직은 탄탄하지만, 사용자가 화면에서 AI의 답변을 기다릴 때 '로딩 중' 페이지만 보게 되어 답답함을 느낍니다.
- **Vercel AI SDK만 쓰면:** 화면은 화려하고 빠르지만, 복잡한 IoT 데이터를 분류하거나 pgvector에서 정교하게 값을 꺼내오는 로직을 짜기가 매우 번거롭습니다.

> [!IMPORTANT] > **NEXA 플랫폼의 권장 조합:**
>
> 1. **Vercel AI SDK**를 통해 사용자의 요청을 받고, 실시간 답변 창을 엽니다.
> 2. 그 요청을 뒤에 있는 **LangChain**으로 넘깁니다.
> 3. LangChain은 pgvector와 Redis를 뒤져서 '유통기한' 내의 데이터를 찾고, 철학에 따른 '비서 톤'으로 답변을 조립합니다.
> 4. 완성된 답변을 다시 Vercel AI SDK가 받아 사용자에게 한 글자씩 스트리밍합니다.
