## 2. ESP32 베이스라인 펌웨어 설계

### 2.1 개요

- **공장 초기화** 후에도 **OTA 수신**만큼은 반드시 동작해야 한다. 사용자가 잘못된 펌웨어를 올리거나 설정을 초기화해도, **플랫폼 웹서버 OTA**로 복구 가능하도록 한다.
- 베이스라인 펌웨어는 **Bootloader + App 파티션** 구조를 유지하며, **OTA 파티션**과 **롤백**을 지원한다.

### 2.2 최소 기능 세트 (Baseline Feature Set)

| 기능 | 필수 | 설명 |
|------|------|------|
| **WiFi AP 모드** | ✓ | 초기화 직후 AP로 동작. SSID 예: `NEXA-ESP32-{MAC_뒷6자리}`. **경로 B** 전용. 사용자가 스마트폰/PC로 접속하여 WiFi(STA) 자격 증명 입력. |
| **Improv Serial (USB)** | ✓ | **경로 A** 전용. Improv Wi-Fi 시리얼 표준으로 플랫폼이 USB 연결 시 SSID/비밀번호를 시리얼 전송. AP 접속 단계 생략. |
| **WiFi STA 모드** | ✓ | 입력된 자격 증명으로 라우터 연결. OTA·등록 통신을 위한 네트워크 확보. |
| **OTA 수신 (HTTP/HTTPS)** | ✓ | 플랫폼 웹서버 URL에서 바이너리 다운로드 후 플래시. ESP-IDF `esp_ota_ops` 또는 Arduino OTA 확장 사용. |
| **디바이스 식별** | ✓ | MAC 주소·칩 ID 기반 고유 ID. 등록·OTA 경로 식별에 사용. |
| **간단한 상태 보고** | ✓ | (선택) `/status` 또는 `/info` JSON 응답. 버전·칩 정보·파티션 정보. |

### 2.3 공장 초기화 후 부팅 플로우 및 경로 분기

- 디바이스는 부팅 시 **WiFi 미설정**이면 **경로 B용** AP 모드로 대기. **경로 A** 사용 시 USB 연결 후 플랫폼이 Improv로 자격 증명 전송 시 AP 진입 없이 바로 STA 전환.
- 사용자 등록 흐름은 **경로 A(USB)** 또는 **경로 B(무선)** 중 선택. §3.2 참조.

```
[전원 ON] → [Bootloader] → [App 파티션 실행]
                                  ↓
                    NVS "factory_reset" 또는 초기 상태?
                                  ↓
                          [WiFi AP 모드] (기본)
                                  ↓
                    사용자: 플랫폼 기기등록 페이지에서 "디바이스 설정 열기" 후
                    Captive Portal 또는 설정 페이지(192.168.4.1)에서 SSID/비밀번호 입력
                                  ↓
                    [WiFi STA 연결] → 디바이스가 플랫폼에 등록 요청
                                  ↓
                    사용자: 플랫폼에서 기기 정보·네이밍·API 키 발급
                    플랫폼 웹에서 OTA 트리거 → 펌웨어 수신 → 재부팅
```

- **Captive Portal**: AP 모드 진입 시, 연결된 클라이언트가 아무 URL을 열면 **설정 페이지**로 리다이렉트. SSID/비밀번호 입력 후 저장.
- **설정 페이지**: 단순 HTML 폼 또는 ESP32 내장 웹서버(예: `ESPAsyncWebServer`, `WebServer`)로 제공.

### 2.4 이중 파티션·롤백 전략

| 항목 | 규격 |
|------|------|
| **파티션 테이블** | `ota_0`·`ota_1` 2개 앱 파티션. ESP-IDF 기본 `partitions_two_ota.csv` 또는 동등 구조. |
| **부팅 검증** | 새 파티션 부팅 후 N회 연속 실패 시 **이전 파티션**으로 롤백. `esp_ota_mark_app_invalid_rollback_and_reboot` 사용. |
| **베이스라인 보호** | 베이스라인 펌웨어는 **고정 버전**(예: v0.1.0-baseline)으로 태그. 롤백 시 이 버전으로 복귀 가능하도록 유지. |
| **NVS 플래그** | `factory_reset`·`wifi_configured`·`registered` 등 상태 플래그 저장. 초기화 시 `factory_reset=true`로 리셋. |

### 2.5 OTA 수신 규격 (베이스라인)

| 항목 | 규격 |
|------|------|
| **프로토콜** | HTTP GET 또는 HTTPS GET. URL 예: `https://<platform_host>/api/ota/firmware?deviceId=<id>&version=<current>`. |
| **응답** | 바이너리 스트림 (`Content-Type: application/octet-stream`). 304 Not Modified(업데이트 불필요) 또는 404(해당 버전 없음) 처리. |
| **검증** | (2단계 이상) 서명 검증. [NEXA_시스템_장기_로드맵] OTA 코드 서명 규격 준수. 1단계에서는 체크섬·크기 정도만 적용 가능. |
| **재시도** | 네트워크 실패 시 백오프(1분 → 5분 → 15분)로 재시도. 무한 재시도는 배터리·리소스 고려해 상한 설정. |

### 2.6 펌웨어 주입 시나리오 (요약)

- 펌웨어를 디바이스에 넣는 경로를 **시나리오 1(복구·최초 주입)** 과 **시나리오 2(평시)** 로 구분한다.

| 시나리오 | 전제 | 주입 경로 | 상세 |
|----------|------|-----------|------|
| **시나리오 1** | OTA 펌웨어가 **없거나 망가졌을 때** (공장 출하·초기화·손상) | **USB 연결 + Web Serial** 로 바이너리 **최초 주입** | 디바이스에 OTA 수신 능력이 없으므로, **케이블**로 직렬 전송. Web Serial API 직접 사용 또는 **ESP Web Tools** 라이브러리 활용 권장(개발 시간 단축). [NEXA-NODE-01] §5.1 참조. |
| **시나리오 2** | 디바이스에 **OTA 가능 펌웨어**가 이미 올라가 있고, 네트워크 연결됨 | **OTA** 로 주입 | 아래 2-1·2-2. |
| **2-1 로직 구성 → 빌드 → OTA** | 사용자가 캔버스에서 **로직 구성** (YAML·Lambda) | 포털 웹 프론트 → **Docker(ESPHome 서버)** 빌드 → 생성된 바이너리 반환 → **OTA** 주입 | 포털에서 노드·라인으로 YAML 생성 → 빌드 서비스(Docker ESPHome)에 전달 → 바이너리 수신 → OTA로 디바이스 전송. [NEXA-NODE-01] §3·§4·§5.2 참조. |
| **2-2 특정 펌웨어 바로 선택 → OTA** | 사용자가 **직접 로직을 구성하지 않고** 플랫폼이 제공하는 특정 펌웨어만 선택 | 포털에서 **미리 정의된 펌웨어** 선택 → **OTA** 바로 주입 | 스냅샷(저장된 빌드)·기능 템플릿(플랫폼 제공 코드) 등 **사전 빌드 또는 템플릿 기반** 바이너리 선택 후 OTA. §3.5 참조. |

- **정리**: 시나리오 1은 **복구·최초** 전용. 시나리오 2는 **평시**이며, 2-1은 사용자 맞춤 로직 빌드, 2-2는 플랫폼 제공 펌웨어 즉시 선택.

## 3. NEXA 플랫폼 디바이스 등록 절차

### 3.1 개요 및 이중 경로 정책

- ESP32를 **최초 1회** NEXA 플랫폼에 등록하여 `deviceId`·API 키·그룹 등을 부여한다.
- 등록은 **두 가지 경로**로 지원하여 플랫폼 확장성과 사용자 환경을 모두 수용한다. 둘 다 동일한 등록 API·API 키·플랫폼 흐름으로 수렴한다.

| 경로 | 대상 | WiFi 설정 방식 | AP 접속 여부 |
|------|------|----------------|-------------|
| **경로 A: USB + Serial** | 개발자·복구·dev 보드(펌웨어 없음)·시나리오 1 | ESP Web Tools + **Improv Wi-Fi** 시리얼 전송 | **불필요** |
| **경로 B: 무선 AP** | 공장 출하 제품·OTA 정상·USB 없는 환경 | Captive Portal(192.168.4.1) | **필수** |

### 3.2 경로별 등록 플로우

#### 3.2.1 경로 A: USB + Serial (Improv) — AP 접속 생략

- **적합**: PC와 USB 연결 가능 시. 펌웨어 없음·손상·개발보드 포함.
- **핵심**: 플랫폼 페이지에서 펌웨어 플래시(필요 시)와 WiFi 자격 증명을 **한 화면**에서 처리. AP 접속 단계 **없음**.

```
① 회원가입 및 로그인
         ↓
② 기기등록 페이지 → "USB로 연결" 선택
         ↓
③ USB 연결 후 "시리얼 연결" 버튼 → 포트 선택(브라우저 팝업)
         ↓
④ [선택] 펌웨어가 없으면 ESP Web Tools로 베이스라인 플래시
         ↓
⑤ 플랫폼 UI에서 집 Wi‑Fi SSID/비밀번호 입력 → Improv로 시리얼 전송
         ↓
⑥ 디바이스 STA 연결 → 플랫폼 등록 요청 → 등록 대기 목록에 표시
         ↓
⑦ 디바이스 네이밍·API 키 발급
         ↓
[등록 완료]
```

#### 3.2.2 경로 B: 무선 AP 모드 — Captive Portal

- **적합**: USB 없음. 공장 출하·OTA 보호된 제품. 스마트폰·태블릿 위주 사용.

```
① 회원가입 및 로그인
         ↓
② 기기등록 페이지 → "무선으로 연결" 선택
         ↓
③ Wi‑Fi 목록에서 NEXA-ESP32-xxxxxx 선택 후 연결
         ↓
④ "디바이스 설정 열기" → 192.168.4.1 접속 (Captive Portal)
         ↓
⑤ 집 Wi‑Fi SSID/비밀번호 입력 후 저장
         ↓
⑥ 디바이스 STA 연결 → 플랫폼 등록 요청 → 등록 대기 목록에 표시
         ↓
⑦ 디바이스 네이밍·API 키 발급
         ↓
[등록 완료]
```

#### 3.2.3 공통 단계 (⑤~⑦ 이후)

| 단계 | 내용 | 기술적 구현 |
|------|------|-------------|
| **기기 정보 출력** | 디바이스가 플랫폼 API에 등록 요청 → 등록 대기 목록에 표시 | `GET /api/devices/pending`, `POST /api/devices/register` |
| **디바이스 네이밍** | 사용자 지정 이름 부여 | `POST /api/devices/approve` 시 `nickname` 포함 |
| **API 키 발급·입력** | 플랫폼이 API 키 발급 후 디바이스에 전달 | `apiKey` 생성·DB 저장. 디바이스: WebSocket/폴링 → NVS 저장 |

#### 3.2.4 경로별 기술 구현

| 구분 | 경로 A (USB) | 경로 B (무선 AP) |
|------|--------------|------------------|
| **연결** | Web Serial + ESP Web Tools | 사용자 Wi‑Fi 스캔 후 NEXA-ESP32-xxxx 연결 |
| **WiFi 설정** | Improv Wi-Fi 시리얼 프로토콜 | Captive Portal(192.168.4.1) |
| **플랫폼 UI** | SSID/비밀번호 입력 폼 → 시리얼 전송 | "디바이스 설정 열기" → 192.168.4.1 링크 |
| **등록 API** | 동일 (`/api/devices/*`) | 동일 |

#### 3.2.5 Web Serial API 및 ESP Web Tools 개요

- **Web Serial API**는 브라우저(Chrome, Edge 등)가 **시리얼 포트**에 접근하여 USB로 연결된 디바이스(ESP32 등)와 통신할 수 있게 하는 W3C 표준 API다. **ESP Web Tools** 라이브러리는 플래시·**Improv Wi-Fi** 프로토콜을 지원하여 **경로 A** 개발을 단축한다.
- **포트 선택**: 보안상 사용자 허락 없이 시리얼 포트를 열거할 수 없음. `navigator.serial.requestPort()` 호출 시 브라우저가 **포트 선택 팝업**을 띄우고, 사용자가 선택.
- **지원 브라우저**: Chrome, Edge 등 Chromium 기반. Firefox·Safari 미지원. HTTPS 또는 localhost에서만 동작.

### 3.3 등록 API 스펙 (초안)

| 메서드 | 경로 | 설명 |
|--------|------|------|
| `POST` | `/api/devices/register` | 디바이스 등록 요청(디바이스 → 플랫폼). Body: `{ "mac": "...", "chipId": "...", "firmwareVersion": "0.1.0-baseline", "capabilities": [...] }`. Response: `{ "deviceId": "...", "apiKey": "...", "otaBaseUrl": "..." }`. |
| `GET` | `/api/devices/pending` | 등록 대기 목록. WiFi 설정 성공 후 플랫폼에 접속한 미등록 디바이스 목록. (⑤단계) |
| `POST` | `/api/devices/approve` | 대기 중 디바이스 승인·네이밍·API 키 확정. Body: `{ "mac": "...", "nickname": "..." }`. |

### 3.4 인증·권한

| 구분 | 규격 |
|------|------|
| **등록 요청** | 인증된 플랫폼 사용자만 등록 가능. 세션/토큰 기반. |
| **등록 후** | `apiKey` 또는 `deviceId+secret` 조합으로 디바이스 인증. MQTT·REST·OTA 요청 시 헤더 또는 쿼리로 포함. |
| **DB 연동** | [NEXA-주요_기능_요구사항] §5 devices_iot, devices_firmware 테이블과 매핑. |

### 3.5 등록 디바이스의 펌웨어 업데이트·기능 주입 (시나리오 2-1·2-2)

- **웹 플랫폼에 이미 등록**되어 있고 **OTA 가능 펌웨어**가 올라간 디바이스에 대해서는, 아래 두 가지 방식(시나리오 2-1·2-2)으로 펌웨어를 갱신·추가한다. 시나리오 전체 구조는 §2.6 참조.

#### 3.5.1 스냅샷 기반 OTA 업데이트

| 항목 | 내용 |
|------|------|
| **대상** | 플랫폼에 등록된 디바이스. 과거에 **캔버스·YAML·Lambda**로 빌드·배포한 이력이 있음. |
| **스냅샷** | [NEXA-NODE-01] §2.10의 **시스템 전체 구성 스냅샷**. 배포 전/마일스톤 시점에 저장한 **캔버스+YAML+빌드 ID** 묶음. 라벨 예: "배포 전 2025-03-05", "v1.2.0 안정판". |
| **플로우** | 사용자가 플랫폼 "디바이스 상세" 또는 "OTA 업데이트" 화면에서 **안정적인 스냅샷**을 선택 → 해당 스냅샷에 연결된 **빌드(바이너리)**를 OTA로 해당 디바이스에 전송. |
| **효과** | 이전에 정상 동작하던 구성을 **복원**하거나, 검증된 버전으로 **롤백** 가능. 업데이트 실패 시 "이전 스냅샷으로 복구"로 신속 대응. |

#### 3.5.2 플랫폼 제공 기능 코드 선택·ESPHome 주입

| 항목 | 내용 |
|------|------|
| **대상** | 플랫폼에 등록된 디바이스. **특정 기능**만 추가·교체하고 싶을 때. |
| **플랫폼 제공 코드** | NEXA 플랫폼이 **미리 정의한 기능 템플릿**(예: "MQTT 브리지", "온도 알림", "Coral 스트리밍 노드"). YAML 스니펫 또는 Lambda 코드 형태로 제공. [NEXA-NODE-01] 노드 카테고리·템플릿과 연동. |
| **플로우** | 사용자가 플랫폼에서 **기능 목록** 선택 → 선택한 기능에 해당하는 **YAML/Lambda 조합**이 현재 디바이스 구성(또는 베이스 YAML)에 **병합** → **ESPHome**으로 빌드 → 생성된 바이너리를 **OTA**로 해당 디바이스에 주입. |
| **효과** | 캔버스 설계 없이 **기능 단위**로 빠르게 확장. 초보자는 "MQTT 연동 추가", "센서 알림 추가" 등 **도메인별 기능**만 선택해 적용. |

#### 3.5.3 두 방식 관계

| 방식 | 용도 | 빌드 소스 |
|------|------|------------|
| **스냅샷 OTA** | 과거 정상 구성 **복원·롤백**, 동일 구성 **재배포**. | 저장된 스냅샷에 연결된 **기존 빌드** 바이너리. |
| **기능 주입** | **새 기능** 추가, 플랫폼 템플릿 기반 **부분 업데이트**. | 현재 구성 + 선택한 **기능 템플릿** → **ESPHome 실시간 빌드** → 새 바이너리. |

- 두 방식 모두 **등록된 디바이스**에 한해, 플랫폼 웹에서 **디바이스 선택 → 업데이트 방식 선택 → OTA 실행** 플로우로 제공한다.

## 4. 외부 라이브러리 사용 전략 (기초 뼈대·등록 UX)

- 본 절은 **포괄적인 라이브러리 관리·거버넌스**가 아니라, **OTA 가능 기초 구조**와 **최초 등록을 사용자 친화적으로 만들기 위한** 외부 라이브러리 **선택·사용** 기획에 한정한다.

### 4.1 OTA 가능 기초 구조를 위한 선택

| 목적 | 선택 방안 | 비고 |
|------|------------|------|
| **OTA 바이너리 수신** | `HTTPClient`(Arduino) 또는 `esp_http_client`(ESP-IDF) | 플랫폼 웹서버 URL에서 펌웨어 GET. Arduino `Update`는 USB 전용 OTA이므로, **HTTP 기반** 별도 구현 필요. |
| **파티션·롤백** | ESP-IDF `esp_ota_ops` | Arduino 환경에서는 `Update` + 수동 파티션 관리. 베이스라인은 **ESP-IDF 기반** 권장 시 OTA·롤백 일관성 확보. |
| **빌드·플래시** | PlatformIO | ESP-IDF/Arduino 모두 지원. 베이스라인과 ESPHome 빌드가 **동일 파티션 레이아웃**을 쓰도록 `partitions.csv` 공유. |

### 4.2 최초 등록 UX를 위한 선택

| 사용자 경험 | 라이브러리·방식 | 설명 |
|-------------|-----------------|------|
| **WiFi 설정 (경로 B, AP → STA)** | `WiFiManager`(tzapu) 또는 자체 Captive Portal | 사용자가 ESP32 AP에 연결 시 자동으로 설정 페이지 노출. SSID/비밀번호 입력 후 STA 전환. |
| **Captive Portal** | `DNSServer` + `WebServer` 또는 `ESPAsyncWebServer` | AP 모드에서 모든 HTTP 요청을 설정 페이지로 리다이렉트. 스마트폰에서 "네트워크에 연결"만 해도 설정 화면 진입. |
| **네트워크 내 디바이스 발견** | mDNS (ESP-IDF `mdns` 또는 Arduino `ESPmDNS`) | 동일 LAN에서 `NEXA-ESP32-xxxxxx.local` 형태로 발견. **등록 대기 목록**: WiFi 설정 성공 후 디바이스가 플랫폼 접속 시 목록 노출. |
| **USB 등록 (경로 A)** | **ESP Web Tools** + **Improv Wi-Fi** | USB 연결 후 플랫폼에서 펌웨어 플래시·SSID/비밀번호 시리얼 전송. Improv로 시리얼 수신. AP 접속 생략. §3.2.1·§3.2.5 참조. |

### 4.3 베이스라인 뼈대 권장 조합

- **최소 조합**: WiFi(AP/STA) + **Improv Serial**(경로 A) + `WebServer` + `DNSServer`(Captive Portal, 경로 B) + `HTTPClient`(OTA) + `ArduinoJson` + `Preferences`(NVS). mDNS는 등록 편의 권장.
- **선택 시 고려**: `WiFiManager`는 편리하나 의존성 증가. 베이스라인은 **용량·복잡도**를 낮추려면 `WebServer` + `DNSServer`만으로 Captive Portal을 직접 구현하는 것도 가능.

## 5. 사용자 디바이스 사용법 안내 인쇄·배포 절차

- 사용자에게 **자신의 디바이스**를 전달할 때, **인쇄된 사용법 안내**를 동봉하여 배포한다는 전제 하에 절차를 정리한다.
- 안내 카탈로그는 **경로 A(USB)** 와 **경로 B(무선)** 를 **명확히 구분**하여 구성한다. 대상·포장에 따라 해당 경로 안내만 포함하거나, 둘 다 포함한 통합판을 제작할 수 있다.

### 5.1 제작·포장·배포 측 절차 (제공자)

| 단계 | 절차 | 비고 |
|------|------|------|
| **1** | **안내 카탈로그 제작** | §5.2의 **경로별 컨텐츠**를 기준으로 제작. 통합판 또는 경로별 단독판 선택. |
| **2** | **플랫폼 URL·QR 코드 포함** | NEXA 플랫폼 디바이스 등록/관리 페이지 URL. 모바일용 **QR 코드** 권장. |
| **3** | **디바이스 정보 라벨 점검** | **경로 B용**: `NEXA-ESP32-xxxxxx` SSID 예시. **경로 A용**: USB 연결 안내. |
| **4** | **포장 동봉** | 디바이스 + 전원(USB 케이블 등) + **안내 카탈로그**(경로에 맞는 버전). |
| **5** | **배포** | 사용자에게 전달. (직접 배포·택배·리셀러 경로 등) |

### 5.2 안내 카탈로그 컨텐츠 구성 (경로별 구분)

- 아래 **카탈로그 A**·**카탈로그 B**를 각각 별도 인쇄물로 제작하거나, **통합 카탈로그**에서 "방법 1: USB로 연결" / "방법 2: 무선으로 연결"로 구분하여 수록.

#### 5.2.1 카탈로그 A: 경로 A (USB + Serial) — 개발·복구·dev 보드용

| 단계 | 안내 내용 | 사용자 행동 |
|------|-----------|-------------|
| **1. 준비** | PC(Chrome/Edge), USB 케이블, Wi‑Fi(라우터) 환경, NEXA 플랫폼 계정. | 계정 가입·로그인. |
| **2. 전원 연결** | ESP32를 PC에 USB로 연결. LED 점등으로 부팅 확인. | USB 연결. |
| **3. 기기등록 페이지** | NEXA 플랫폼 접속(URL 또는 QR) → 로그인 → **"디바이스 등록"** → **"USB로 연결"** 선택. | 플랫폼 진입. |
| **4. 시리얼 연결** | "시리얼 연결" 버튼 클릭 → 브라우저 팝업에서 포트 선택 → 허용. | 포트 선택·허용. |
| **5. 펌웨어·WiFi 설정** | [펌웨어 없으면] 플래시 후, 플랫폼 화면에서 **집 Wi‑Fi SSID/비밀번호** 입력 → 전송. | 한 화면에서 완료. |
| **6. 기기 정보·네이밍·API 키** | 플랫폼 "등록 대기" 목록에 디바이스 표시. 이름·API 키 확정. | 등록 완료. |
| **7. 사용 시작** | 플랫폼 대시보드에서 제어·모니터링·OTA. | 사용 시작. |
| **8. 문제 발생 시** | 공장 초기화 후 2~6단계 재진행. 복구 불가 시 동일 경로로 재플래시. | 복구 절차. |

#### 5.2.2 카탈로그 B: 경로 B (무선 AP) — 공장 출하 제품·USB 없음

| 단계 | 안내 내용 | 사용자 행동 |
|------|-----------|-------------|
| **1. 준비** | 스마트폰 또는 PC, Wi‑Fi(라우터) 환경, NEXA 플랫폼 계정. | 계정 가입·로그인. |
| **2. 전원 연결** | USB로 전원 연결. LED 점등으로 부팅 확인. | 전원 ON. |
| **3. 기기등록 페이지** | NEXA 플랫폼 접속(URL 또는 QR) → 로그인 → **"디바이스 등록"** → **"무선으로 연결"** 선택. | 플랫폼 진입. |
| **4. 디바이스 AP 접속** | Wi‑Fi 목록에서 **NEXA-ESP32-xxxxxx** 선택 후 연결. "디바이스 설정 열기" → 192.168.4.1 접속. | ESP32 AP 연결. |
| **5. 집 Wi‑Fi 입력** | Captive Portal 폼에 **SSID·비밀번호** 입력 후 저장. | 집 Wi‑Fi 정보 입력. |
| **6. 기기 정보·네이밍·API 키** | 플랫폼 "등록 대기" 목록에 디바이스 표시. 이름·API 키 확정. | 등록 완료. |
| **7. 사용 시작** | 플랫폼 대시보드에서 제어·모니터링·OTA. | 사용 시작. |
| **8. 문제 발생 시** | 공장 초기화(예: 버튼 길게 누른 채 전원 ON) 후 2~6단계 재진행. | 복구 절차. |

#### 5.2.3 공통 컨텐츠 (두 카탈로그 공유)

| 항목 | 내용 |
|------|------|
| **준비물** | 플랫폼 계정, Wi‑Fi(라우터) 환경 |
| **등록 후** | 기기 정보·네이밍·API 키, 플랫폼 대시보드 사용 |
| **문제 발생 시** | 공장 초기화 방법, 해당 경로 단계 재진행 |

### 5.3 인쇄물 템플릿 권장 구조 (경로별 구분)

- **통합 카탈로그** 예시:

- **버전 관리**: 베이스라인·플랫폼 UI 변경 시 **카탈로그 버전** 동기 갱신. (예: "2025-03 rev.1")

## 6. AI 연동 확장 아이디어

- 아래 시나리오는 [NEXA-AI-03] 등 AI 오케스트레이터·협업 도메인과 연동하여 **복구 모드 시 USB 연결의 가치**를 높이는 확장 방향이다.

### 6.1 웹 시리얼 로그 + AI 오케스트레이터 연동

| 항목 | 내용 |
|------|------|
| **목표** | 최악의 상황(복구 모드)에서 USB 연결 시 **가치 극대화** |
| **시나리오** | ESP Web Tools가 제공하는 **웹 시리얼 로그 뷰어** 기능을 플랫폼의 **AI 오케스트레이터**와 연결 |
| **효과** | 사용자가 USB로 디바이스를 연결했을 때, 실시간 시리얼 로그를 AI가 분석·해석하여 오류 원인 제시, 복구 단계 안내 등 제공 가능 |

### 6.2 브라우저 기반 펌웨어 자동 복구 (Self-Healing)

| 항목 | 내용 |
|------|------|
| **목표** | 잘못된 로직 배포로 인한 기기 고장 시 **원클릭 복구** 유도 |
| **시나리오** | 사용자가 캔버스에서 잘못된 로직을 구성하여 OTA 배포 → 기기가 **무한 루프** 등으로 응답 불가 상태에 빠짐. 플랫폼이 이를 감지(예: 하트비트·폴링 타임아웃)하고 **"기기를 USB로 연결해 주세요. 자동으로 베이스라인 펌웨어를 복구합니다"** 알림 표시 |
| **효과** | 사용자가 USB 연결만 하면 플랫폼이 ESP Web Tools로 베이스라인 플래시·Improv로 WiFi 설정까지 자동 진행 → 재등록 완료 |
