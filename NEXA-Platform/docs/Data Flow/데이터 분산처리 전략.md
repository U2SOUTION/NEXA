# Self-hosted Data Flow

클라우드 서비스(SaaS)와 온프레미스(Local/Self-hosted)를 영리하게 혼합한 하이브리드 전략

클라우드 서비스(SaaS)와 온프레미스(Local/Self-hosted)를 영리하게 혼합한 하이브리드 전략

(1) 웹 브라우저에서 직접 처리하거나,
(2) 자신의 로컬 PC에 파이썬 코드를 띄워 처리하거나,
(3) 원치 않으면 우리 서버가 대행
사용자가

하게 하는 3가지 모드를 유연하게 전환할 수 있는 핵심 기술들을 정리.

## 🌐 1. 웹 브라우저 단에서 직접 처리 (Edge AI Mode)

| 모드 | 코드 | 실행 주체 |

- 핵심 기술: WebLLM 또는 ONNX Runtime Web
- 어떻게 동작하나: 사용자가 Vue 3 대시보드에 접속하면, 브라우저가 Llama 3나 긴밀한 소형 모델(예: Phi-3, Qwen 등)을 사용자 컴퓨터의 브라우저 메모리(WebGPU 활용)에 직접 다운로드하여 실행합니다 [1].
- 구현 방식: 데이터가 우리 서버로 오지 않고, 브라우저 내부에서 센서 값을 읽어 즉시 AI 판단을 내린 뒤 MQTT 명령을 날립니다. 서버 비용은 0원이 됩니다.
  | 브라우저 Edge | `BROWSER_EDGE` (1번) | 사용자 PC WebGPU / WebLLM |

| 클라우드 대행 | `CLOUD_DEFAULT` (3번) | NestJS + 중앙 Ollama (기본) |

## 💻 2. 사용자 로컬 파이썬 프로그램 실행 (Local Agent Mode)

| 로컬 온프레미스 | `LOCAL_ONPREM` (2번) | 고객사 Docker·Ollama 에이전트 |
고객이 라즈베리 파이나 사내 워크스테이션 PC를 가지고 있어서, 거기에 직접 AI 에이전트를 상주시키고 싶어 할 때 사용하는 방식입니다.

- 핵심 기술: Ollama (로컬 설치) + Docker + MQTT Bridge / JWT 인증
- 어떻게 동작하나: 우리가 패키징한 파이썬 에이전트 프로그램을 사용자가 한 줄의 명령어로 실행할 수 있도록 도커 이미지(Docker Image) 형태로 제공합니다.
- 보안 및 연결 기술: 사용자 로컬에서 돌아가는 파이썬 프로그램이 우리 중앙 데이터베이스(PostgreSQL)에 직접 붙으면 보안상 위험합니다. 따라서 우리 메인 서버(NestJS)가 기기별 발급한 JWT 토큰(또는 API Key)을 검증하여, 허가된 MQTT 토픽 채널만 열어주는 보안 게이트웨이 기술이 필요합니다.

## 🗼 3. 사용자가 원치 않을 때: 중앙 서버 대행 (Cloud Agent Mode)

## 기존에 설계했던 NestJS + 중앙 파이썬 서버가 처리하는 정석적인 클라우드 방식입니다.

## 🔀 3가지 모드를 병행하기 위해 필요한 '핵심 공통 기술'

이 하이브리드 전략이 매끄럽게 돌아가려면, 시스템 전체가 "지금 이 기기의 AI 연산 주체는 누구인가?"를 알고 제어할 수 있어야 합니다. 이를 위해 다음 기술들이 필요합니다.

## ① 동적 MQTT 토픽 라우팅 스위치 (Dynamic Routing Switching)

장비나 서버가 구독하는 토픽 뒤에 행위 주체(Actor)를 붙여서 데이터를 분기해야 합니다.

- 중앙 서버 대행 시: myiot/+/+/sensor/+/critical/cloud ➡️ 중앙 파이썬 서버가 처리
- 사용자 로컬 파이썬 처리 시: myiot/+/+/sensor/+/critical/local ➡️ 로컬 파이썬이 가로채서 처리하고, 결과만 완료 토픽으로 보고

## ② Vue 3 기반 '연산 주체 설정' 대시보드 및 메타데이터 관리

- Vue 3 화면에 기기별 설정 스위치를 둡니다: [AI 연산 주체 선택: ▢ 클라우드 대행 ▢ 브라우저 직접 연산 ▢ 로컬 서버 위임]
- 이 설정값은 PostgreSQL의 기기 테이블(DeviceMetadata)에 저장되며, 기기가 처음 부팅하여 NestJS에 연결될 때 "너는 로컬 모드니까 토픽을 .../local로 쏴라" 하고 가이드를 내려줍니다.
  기존에 설계한 **NestJS + 중앙 파이썬(Ollama)** 이 처리하는 정석적인 클라우드 방식입니다.

## ③ 인프라 오토스케일링 (Cloud Auto-scaling)

장비 등록 시 **기본값**이며, 사용자가 별도 설정을 하지 않으면 안전하게 이 모드로 동작합니다.

- 사용자들이 "나 귀찮으니까 클라우드 대행 쓸래"라고 몰리는 순간, 우리 서버의 Ollama 연산 장치(GPU 인스턴스) 부하가 치솟습니다.
- 이를 방지하기 위해 AWS의 Karpenter나 Kubernetes(K8s)의 KEDA 같은 기술을 사용해, MQTT 큐에 쌓인 일감 개수에 따라 중앙 파이썬 서버 개수를 자동으로 늘리고 줄이는(Auto-scaling) 기술이 필수적입니다.

- **핵심 기술:** NestJS, Redis/RabbitMQ, 중앙 Ollama, MQTT Broker

- **어떻게 동작하나:** ESP32 등이 `.../sensor/critical` 등으로 데이터를 발행하면, NestJS가 DB의 `ai_execution_mode`를 확인한 뒤 메시지 큐를 통해 클라우드 파이썬 서버로 일감을 넘깁니다.
  이 병행 전략은 비용 절감과 확장성 면에서 신의 한 수가 될 수 있습니다.

- 일반 가벼운 사용자: Vue 3 브라우저 연산(WebLLM)을 유도하여 서버 부하를 지우고,
- 대규모 공장/기업 고객: 사내 서버에 Ollama + 파이썬 도커를 띄우게 하여(로컬 모드) 완벽한 데이터 보안을 제공하며,
- 돈을 더 내는 프리미엄 고객: 우리 클라우드 서버 자원(대행 모드)을 쓰게 하여 구독형 수익(SaaS)을 창출할 수 있습니다.

## 💻 3. 사용자 로컬 파이썬 프로그램 실행 (Local Agent Mode) — 2번

> 3단계 계층형 서비스 모델(Tiered Service Model)은 비즈니스와 기술적 관점 모두에서 가장 훌륭한 전략입니다.
> 인프라 비용을 최소화(기본값은 3번이지만 1번으로 유도)하면서도, 엔터프라이즈 고객의 특수 요구사항(2번)까지 유연하게 흡수할 수 있는 구조입니다.
> 이 병행 전략을 매끄럽게 구현하기 위해 Vue 3 대시보드 화면, NestJS 관제탑, 그리고 데이터베이스(DB)단에서 준비해야 할 기술적 핵심 요소를 정리해 드립니다.

---

### 🗄️ 1. 데이터베이스(PostgreSQL)의 기기 메타데이터 설계

어떤 기기가 어떤 모드로 작동할지 관리하기 위해, PostgreSQL의 기기 테이블(devices)에 ai_execution_mode라는 상태 컬럼이 필수적으로 들어가야 합니다.

- Mode 값 종류: CLOUD_DEFAULT (3번), BROWSER_EDGE (1번), LOCAL_ONPREM (2번)
- 초기 장비 등록 시: 무조건 CLOUD_DEFAULT (3번)로 세팅되어 서버가 안전하게 대행합니다.

### 💻 2. Vue 3 대시보드에서의 구현 기술 (1번 모드 유도 스위치)

3번(기본 서버 대행)을 쓰던 사용자에게 "1번(브라우저 연산)을 켜시면 서비스 요금이 할인되거나 더 빠른 반응 속도를 얻을 수 있습니다"라고 동의를 구하는 UI/UX 기술입니다.

#### ① 웹 브라우저 자원 체크 및 동의 모달 (WebGPU API)

- 사용자가 1번 모드 스위치를 켜면, 브라우저가 사용자 PC의 그래픽카드 성능을 체크합니다.
- 필요 기술: 브라우저 자바스크립트의 navigator.gpu API를 호출하여 WebGPU 사용 가능 여부를 먼저 확인합니다.
- 사양이 충족되면 *"사용자의 PC 자원(GPU)을 활용하여 로컬 AI 연산을 수행합니다. 동의하십니까?"*라는 안내와 함께 동의(Opt-in)를 받습니다.

#### ② Vue 3 내장형 WebLLM 엔진 구동

- 동의 완료 시, Vue 3 앱 내부에서 @mlc-ai/web-llm 라이브러리가 활성화됩니다.
- 이 엔진은 브라우저 백그라운드(Web Worker)에서 돌아가므로, AI 연산 중에도 사용자가 대시보드 마우스를 움직이거나 차트를 볼 때 버벅임이 전혀 없습니다.

### 🗼 3. NestJS 관제탑의 '동적 라우팅' 및 스위칭 기술 (3번 ↔ 1번 ↔ 2번)

장비가 MQTT로 센서 데이터를 던질 때, NestJS는 DB에 저장된 해당 장비의 ai_execution_mode를 보고 데이터의 흐름을 지휘합니다.

#### ① 3번 모드 (기본 클라우드 대행) 일 때

장비·서버가 구독하는 토픽 뒤에 행위 주체(Actor)를 붙여 분기합니다.

- ESP32가 MQTT 토픽(.../sensor/critical)으로 데이터를 쏩니다.
- NestJS는 이를 감지하고 메시지 큐(Redis/RabbitMQ)를 통해 우리 클라우드 내부의 파이썬 Ollama 서버로 일감을 토스합니다.

#### ② 1번 모드 (사용자 브라우저 연산 동의) 일 때

- **클라우드 대행(3번):** `myiot/+/+/sensor/+/critical/cloud` → 중앙 파이썬 서버
- 장비가 데이터를 쏘면, NestJS는 이를 파이썬 서버로 보내지 않고 웹소켓(Socket.io)을 통해 현재 로그인해서 대시보드를 보고 있는 사용자의 웹 브라우저로 다이렉트 패스합니다.
- 사용자의 브라우저(WebLLM)가 연산을 끝내면, 그 결과값을 다시 NestJS API로 쏘아 DB에 업데이트합니다. (서버 GPU 비용 0원)
- **로컬 파이썬(2번):** `myiot/+/+/sensor/+/critical/local` → 로컬 에이전트가 가로채 처리, 완료 토픽으로만 보고

#### ③ 2번 모드 (특수 요구사항 - 로컬 파이썬) 일 때

- **브라우저(1번):** MQTT 수신 후 NestJS가 WebSocket으로 브라우저에 패스(아래 §구축 전략 참고)
- 고객사에 별도로 세팅된 파이썬 프로그램이 중앙 MQTT 브로커에 접속해 있습니다.
- NestJS는 관제만 하고, 데이터는 고객사의 로컬 파이썬 에이전트가 직접 가로채서 처리한 뒤 결과만 우리 서버로 보고(Report)합니다.

### ② Vue 3 기반 「연산 주체 설정」 대시보드 및 메타데이터

### 🛠️ 이 전략의 도입 단계 시나리오 (로드맵)

개발을 진행하실 때는 이 3가지를 동시에 만들면 스펙이 꼬일 수 있으므로, 제안하신 우선순위에 따라 단계별로 빌드업하는 것을 강력히 추천합니다.

- Phase 1 (기본 다지기): 3번(기본 서버 대행)을 메인으로 삼아, NestJS + PostgreSQL + 파이썬 Ollama + MQTT 인프라의 전체 뼈대를 먼저 완성합니다.
- Phase 2 (비용 절감 최적화): 시스템이 안정화되면 1번(Vue 3 브라우저 연산) 기술을 도입하여 일반 사용자들의 동의를 유도, 서버 GPU 인프라 요금을 획기적으로 낮춥니다.
- Phase 3 (B2B 비즈니스 확장): 플랫폼이 커지고 대기업/공장 고객이 *"우리 데이터 외부 클라우드로 나가는 거 싫다"*고 할 때, 2번(도커 기반 로컬 파이썬 에이전트) 패키지를 옵션 상품으로 판매합니다.

- **3번(클라우드)** 부하 집중 시 GPU 인스턴스를 K8s KEDA 등으로 자동 증감.

정말 흠잡을 데 없이 완벽하고 영리한 하이브리드 아키텍처 비즈니스 모델입니다.
이제 큰 그림과 디테일한 라우팅 전략까지 정리가 되었는데요, Phase 1 단계로 나아가기 위해 NestJS 메인 서버와 파이썬 Ollama 서버 간에 주고받을 공통 데이터 규격(Prisma DB 스키마나 JSON 데이터 형태)을 먼저 짜보는 건 어떠신가요? 아니면 다른 부분부터 설계해 볼까요?

## 구축 전략 (Build Strategy)

> 3단계 계층형 서비스 모델(Tiered Service Model)은 비즈니스·기술 모두에서 유효합니다.

> **인프라 기본은 3번(클라우드)** 으로 두고, 비용 절감(1번)·B2B(2번)를 단계적으로 얹습니다.

### 🗄️ 1. 데이터베이스(PostgreSQL) — 기기 메타데이터

`devices` 테이블에 **`ai_execution_mode`** 컬럼 필수.

| 값 | 모드 |

|----|------|

| `CLOUD_DEFAULT` | 3번 — **초기 등록 기본값** |

| `BROWSER_EDGE` | 1번 |

| `LOCAL_ONPREM` | 2번 |

### 🗼 2. NestJS 관제탑 — 동적 라우팅 및 스위칭 (3번 ↔ 1번 ↔ 2번)

장비가 MQTT로 데이터를 보낼 때, NestJS는 DB의 `ai_execution_mode`를 보고 흐름을 지휘합니다.

#### ① 3번 모드 (기본 클라우드 대행)

- 토픽 `.../sensor/critical` 등 수신 → Redis/RabbitMQ → 클라우드 Ollama.

#### ② 1번 모드 (브라우저 연산 동의)

- NestJS는 파이썬으로 보내지 않고 **WebSocket(Socket.io)** 으로 로그인 중인 대시보드 브라우저로 패스.

- 브라우저(WebLLM) 연산 결과만 NestJS API로 회수·DB 반영.

#### ③ 2번 모드 (로컬 파이썬)

- 고객사 로컬 에이전트가 MQTT에서 직접 구독·처리, NestJS는 관제·결과 수신.

### 💻 3. Vue 3 대시보드 — 1번 모드 유도 UI

3번(기본) 사용자에게 「1번을 켜면 요금 할인·저지연」 등으로 Opt-in 유도.

#### ① WebGPU 체크 및 동의 모달
