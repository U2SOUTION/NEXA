## PRD (Product Requirements Document): Nexion의 요구사항 정의서. (기능, 목적, 타겟)

- 물리적 폴더 구조를 논리적 지도로 치환하고 이를 수동/자동으로 동기화하겠다는 구상은 Nexion의 존재 이유인 **"생각을 잃어버리지 않게 만드는 시스템"**을 구현하는 가장 확실한 방법입니다.

### 1. 핵심 기능 리스트 검토 (UI/UX 관점)

Nexion의 **'독립형 관제 데스크'** 기능.

- **노드(카드) 생성 및 중첩 (DnD):** Vue Flow의 **'부모-자식 계층(Parent-Child Hierarchy)'** 및 **'그룹 노드'** 기능을 통해 물리적으로 구현. 이는 폴더 내의 하위 폴더 구조와 1:1로 매핑.
- **라인 연결과 끊기:** 지능적 족보인 **'Why Chain(인과 사슬)'**을 형성하는 행위로서 실선은 확정된 의지(WILL), 점선은 AI의 제안(ECHO/VOID)으로 표현하도록 설계한다. 여러 시나리오는 **경험**을 통해 추가하고, 관련 문서를 보강한다.
- **Capability ID 발급 및 문서 링크:** Nexion의 핵심인 **'Late Anchoring'** 프로세스로서. 설계도(노드)를 먼저 그린 후 실제 자산(파일)을 드래그하여 연결하면, 시스템이 해당 파일에 **기능 자격(Capability ID)**을 부여하고 족보에 박제 한다.
- **중력 기반 줌 및 팬:'프랙탈 줌'** 혹은 **'시맨틱 줌'**으로 명명. 특히 **'의도 중력(Intent Gravity)'** 축을 통해 사용자의 의지가 강한 노드들이 더 선명하게 응집되거나 폭발하는 연출.

#### 1.1 이 절과 맞물리는 규격 문서(정합·보강 시)

이 PRD는 **진행 그림**을 먼저 세우는 문서다. UI·캔버스·용어의 **기술 세부**는 아래를 기준으로 이후 문서를 맞춘다.

- **Phase 번호·실행 체크박스(담당 문서):** `[NXN] NEXA Nexion 개발 순서와 체크 리스트.md` — **Phase 1~4·Ext·B-ops 번호는 본 문서 §3.2·§3.4와 동일**해야 한다.
- **Vue Flow 채택·`engines/diagram` 과의 관계·부모-자식·시맨틱 줌·LOD:** `[NXN] [UIUX] NEXA Nexion 인터페이스 레이아웃 및 Vue Flow 운영 규약.md` (특히 §4.1~4.2).
- **3패널·독립 도메인 `nexion`·Extension 폴더 경계:** 동 UIUX 문서 §2.
- **Late Anchoring·족보 철학:** `[NXN] [CNCP] NEXA Nexion 지식 OS 관리 및 N-PATH(지도) 설계 철학.md`.

### 2. 내부 작동 로직 분석 (N-PATH 및 인덱싱 관점)

내부 로직: 시스템의 **'무결성'**과 **'추적성'**을 보장하는 뼈대.

- **라인 연결 시 디렉토리 구조 반영 및 정리 로직:** 카드를 옮기거나 연결하는 행위는 파일 시스템의 `mv` 명령과 동기화. 연결이 끊긴 문서가 루트의 카드명 폴더로 이동하여 고아 자산을 방지.
- **카드 선택 시 문서 리스트 출력:** Nexion의 **'Resource Explorer(좌측 드로어)'** 기능으로, 선택된 노드의 Link ID와 연결된 문서만 필터링하여 작업 집중도를 높입니다.
- **고아 자산(Orphaned) 관리:** 노드와 연결되지 않은 파일들을 별도 리스트로 관리하고 N-PATH 루트로 이동시키는 것은 **'자산 불가지론'** 원칙에 따라 실체 파일은 보존하되 논리적 연결만 관리하는 방식입니다.
- **탐색기 이동 시 카드 재배치 (Inode 방식):** `nexa_knowledge_traceability_paths` 테이블이 **Inode** 역할을 수행하여, 외부에서 폴더명이 바뀌어도 **UUID 기반 앵커**를 통해 캔버스 상의 위치를 잃지 않고 추적합니다.
- **자동 생성 및 배치 (Drafting):** 크롤러가 감지한 새 구조를 `is_virtual = true` 상태의 가상 카드로 먼저 보여주고 사용자의 승인(ASK → WILL)을 받는 흐름은 시스템의 안정성을 극대화합니다.

#### 2.1 이 절과 맞물리는 규격 문서(정합·보강 시)

- **N-PATH·크롤러·물리 경로·보안:** `[NXN] [ARCH] N-PATH 보안 및 외부 자산 연동 설계서.md`.
- **테이블·필드·상태 머신:** `[NXN] [SCHM] NEXA Nexion 독립형 인덱스 및 자산 관리 스키마.md`, `[NXN] [DDL] ...` (실행 SQL).
- **REST 계약:** `[NXN] [API] NEXA Nexion API 및 통신 규약.md` (Core vs Extended).
- **테넌트 `project_id` vs 제품 정체성:** `[NXN] [CNCP] NEXA Nexion 지식 OS 관리 및 N-PATH(지도) 설계 철학.md` **§1.2**, API **§2.2.1** — DB·경로에 `project_id`가 필수여도 **워크플로 프로젝트 엔티티와 동일시하지 않는다**.

### 3. 구현 순서 및 전략

UI를 먼저 구성한 뒤 **Late Anchoring**과 **Inode식 추적** 로직을 단계적으로 심어 간다. **'사고의 칠판'** 정체성을 위해 초기 단계에서 시각·인터랙션을 충분히 검토·숙성한 뒤 다음 작업으로 넘어간다.

#### 3.1 전제·범위(이 PRD 기준)

- **프론트 도메인:** Nexion은 **`src/domains/nexion/`** 독립 도메인으로 올린다(플랫폼 `left` / `content` / `right` 3슬롯). `dev` 하위 도구로만 묶는 안은 쓰지 않는다.
- **MVP DB(Tier A):** 최소한 **`nexa_knowledge_traceability_paths`**, **`nexa_knowledge_nexion_doc_node_links`**, **`nexa_knowledge_doc_sync_state`**(크롤러·저장 동기화에 필요한 **최소 컬럼**부터)를 한 묶음으로 본다. **`residency`·전면 RLS·스왑 정책 원장** 등은 **Tier B / 후행**으로 미룬다.
- **Extension:** TipTap·Ollama·용어 추출은 **코어 Phase 번호와 섞지 않고 Phase Ext**로 부른다(API·UI에서 Extended 계약).
- **환경(Phase 0 성격):** `DOCS_PATH`(예: `NEXA-Documentation/`), PostgreSQL·확장, 로컬 PoC vs 공유 DB는 스프린트 착수 전에 한 줄이라도 팀 합의로 고정한다.

#### 3.2 단계 목록(권장 순서) — **NXN 코어 Phase SSOT**

아래 번호가 다른 `[NXN] *` 문서의 “Phase N” 언급과 **어긋나면 안 된다.** 실행용 `[ ]` 체크리스트는 `[NXN] NEXA Nexion 개발 순서와 체크 리스트.md`에 둔다.

1. **Phase 1 — UI 프로토타이핑 (Vue Flow):** 카드 생성, DnD, 라인 연결, (가능하면) 부모-자식·줌에 따른 표시 등 **시각적 경험**을 먼저 확정.
   - _선택 분할:_ **1a** 도메인 셸·3패널 껍데기 → **1b** 캔버스만 최소 동작. 디버깅 시 프레임 이슈와 플로우 이슈를 분리한다.
2. **Phase 2 — DB 뼈대 (Tier A):** 위 MVP DB 세 테이블(및 SCHM·DDL에 따른 제약)로 UI에서 발생한 사건을 **영속화**할 준비를 갖춘다. §3.3에 따라 **Core API** 를 이 단계 초반에 고정·연결한다.
3. **Phase 3 — 백엔드 동기화 (Doc Sync Crawler):** 파일 시스템 스캔으로 DB·UI를 잇는 크롤러를 구현한다.
4. **Phase 4 — Late Anchoring·고아·mv:** `nexion_doc_node_links`로 노드↔`anchor_id` 연결, Orphaned 표시, 카드 이동과 디스크 `mv`·ASK 흐름을 완성한다.
5. **Phase Ext — 지능 확장:** TipTap·Ollama 용어 추출 등을 **독립 모듈**로 추가한다(도메인 `modules/extension/`, API Extended). **코어 Phase 번호와 혼동하지 않는다.**

#### 3.3 계약·타입 전략(리스크 완화)

- **UI만 장기간 진행하면** 나중에 DB·API와 충돌하기 쉽다. Phase 2 **초반**에 `[NXN] [API]` **Core** 엔드포인트 목록을 **이름·역할만이라도** 고정하고, 가능하면 **목(mock) 또는 최소 구현**으로 UI와 연결한다.
- 프론트에서는 **`src/system/types/`** 및 **`src/system/schemas/`(Zod)** 로 요청·응답을 검증·추론하는 방향을 택한다(도메인 내부 전용 `types.ts` 남발 금지 — UIUX §2.4.3과 동일 정책).

#### 3.4 단계별 완료 정의(DoD) 예시(팀이 숫자·문구만 조정)

| 단계      | 완료 정의(예)                                                                               |
| --------- | ------------------------------------------------------------------------------------------- |
| Phase 1   | 로컬에서 저장 없이 캔버스에서 노드·엣지 조작이 재현 가능하다.                               |
| Phase 2   | 선택한 `project_id`(또는 단일 구획)에 대해 경로·노드-링크·동기화 상태가 DB에 기록·조회된다. |

| Phase Ext | 문서 편집·용어 추출이 **코어 캔버스 없이도** 끌 수 있거나, 탭으로 분리해 끌 수 있다.        |

#### 3.5 초기 릴리스에서 늦춰도 되는 것(기대치 관리)

- **자연어 기반 LOD·Fit Score·의도 중력 자동 추론** 등은 본 PRD §1의 비전과 연결되나, **Phase 1~4·Phase Ext의 필수 범위에 넣지 않는다.** 수동 줌·LOD·규칙 기반 연출만으로 먼저 출발한다.
- **Tier B:** RLS 전면, `residency`, 다도메인 `anchor_*` 전개는 플랫폼 배포 단계에서 맞춘다.

## NEXION Desk VS NEXU Canvas

인공지능 협업 설계에서 **Nexion Desk**와 **넥슈 캔버스(NEXU Canvas)**의 역할 혼동을 바로잡고, **'의지 중력(Intent Gravity)'**과 **'다중 자아(Self Facet)'**를 Nexion의 관점에서 어떻게 정의하고 구현해야 하는지 핵심 설계 원칙을 정리.

### 1. Nexion 데스크 vs. NEXU 캔버스의 두 공간의 물리적·논리적 경계

- **넥슈 캔버스 (NEXU Canvas/NIXIE):** 플랫폼의 **'홈(Home)'**이자 **'지능의 얼굴'**입니다. 우주적 스케일(원자~우주)에서 수만 개의 **Capability ID** 도트를 조망하는 **전역 지능 지도**의 역할을 수행합니다.
- **Nexion (NXN):** 개발자가 설계를 시작하기 전 사용하는 **'사고의 칠판'**이자 **'독립형 관제 데스크'**입니다. 특정 프로젝트의 **지능적 족보(Why Chain)**와 **물리적 자산(N-PATH)**을 연결하고 조율하는 **워크스페이스**입니다.

### 2. Nexion 관점에서의 '의지 중력 (Intent Gravity)'

Nexion에서 의지 중력은 단순한 시각 효과가 아니라, **'사유의 밀도'**와 **'자산의 확정성'**을 결정하는 메타 좌표계(X7 축)로 작동합니다.

- **사유의 응집과 폭발:** 사용자의 의지(WILL)가 특정 설계 노드에 집중되면, 해당 노드는 **'폭발(Explosion)'**하여 내부의 **5W1H 참조 사슬(SNT-IND-EFF)**과 연결된 실제 문서(MD 파일)를 데스크에 전면에 부상시킵니다. 반대로 의지가 소홀해지면 상위 개념 노드로 **'함몰(Implosion)'**되어 시각적 노이즈를 제거합니다.
- **역동적 깊이(Depth) 제어:** 인공지능은 사용자의 자연어 입력에서 의도 중력을 식별하여, 관심도가 높은 카드(노드)의 **LOD(디테일 단계)**를 개별적으로 조절합니다. 예를 들어 "보안 설계를 깊게 보고 싶어"라고 하면, 관련 노드만 강제로 상세 정보와 물리적 경로가 보이는 고배율 상태로 전이됩니다.

### 3. Nexion과 '다중 자아 (Self Facet)'의 결합

사용자가 Nexion 데스크에서 **Self Facet(자아의 단면)**을 선택하는 행위는 시스템 전체를 재구성하는 **'역방향 분해(Reverse Decomposition)'**의 트리거가 됩니다.

- **행동 기반 정량화:** 사용자가 "작업하는 나" 또는 "창작하는 나" Facet을 클릭하면, Nexion은 즉시 해당 모드에 맞는 **코일 가중치(6-COILS)**와 **Capability 후보군**을 캔버스 위에 펼쳐 보입니다.
- **Ambient N-MAP 환경:** 별도의 설문 없이 클릭 한 번으로 내부의 **영문 IR(중간 표현)**과 실행 경로가 재합성됩니다. 이는 사용자의 현재 상태에 따라 칠판(Nexion) 위의 악보가 실시간으로 조립되는 과정입니다.

### 4. 지능형 서사 경로 체계(N-PATH)의 운영

Nexion은 물리적 폴더 구조를 논리적 지도로 치환하는 **N-PATH**의 관제탑입니다.

- **폴더명 = Link ID:** Nexion의 카드 계층은 실제 외부 탐색기의 디렉터리 구조와 일체화됩니다.
- **Late Anchoring:** 설계 노드에 의지 중력이 실려 실제 파일이 연결(Anchor)되는 순간, 시스템은 해당 자산에 **Capability ID**를 발급하고 **지능적 족보(Traceability)**에 박제합니다.
- **Inode식 추적:** 파일 이름이 바뀌거나 외부에서 이동되어도 UUID 기반의 **앵커 ID**를 통해 Nexion(NEXU) 캔버스의 위치를 자동으로 유지하며, 정합성이 깨질 때만 **NEXA NIXIE가 NEXU 캔버스 위에서 Jitter(미세 떨림)** 로 사용자에게 알립니다(UIUX §4.3.1).

**요약하자면,** Nexion에서의 설계는 **"의지 중력에 의해 사유의 경로가 선명해지고, 다중 자아 선택을 통해 칠판의 논리 도구가 바뀌며, 그 결과가 N-PATH를 통해 물리적 자산으로 박제되는 과정"**입니다. 넥슈 캔버스가 우주 전체를 보여주는 '지도'라면, Nexion은 그 지도 위의 특정 지점에서 실제 연주를 준비하는 '지휘자의 데스크'로 정의.

### 5. AI협력을 통한 UX의 확장

##### A. 사용자의 의지(WILL)와 '의도 중력'의 정의

NEXA 아키텍처에서 **사용자의 의지** ( **'의도 중력(Intent Gravity)'** )는 시스템을 움직이는 가장 상위의 동력원이자 에너지입니다.

- **의지의 실체 (WILL Pulse):** 헥사곤 프로토콜(HEXAGON)의 **Who(Pulse)** 레이어에서 정의되는 **WILL** 토큰은 사용자의 명시적인 승인과 결정을 의미하며, 실제 물리적 실행(EFF)을 허용하는 최종 권위가 됩니다.
- **의도 중력 (Intent Gravity / X7 축):** 이는 코일(Coil) 가중치 외에 추가된 **'사용자 사유의 무게'**를 정의하는 메타 좌표계입니다. 사용자가 특정 노드에 머무는 시간, 클릭 빈도, 혹은 자연어로 강조한 명령 등이 이 축의 에너지를 생성합니다.
- **응집과 폭발의 원리:**
  - **응집 (Implosion):** 사용자의 의지가 특정 개념에 집중되거나 줌 아웃(Zoom Out)할 때 발생합니다. 수많은 세부 Capability ID 도트들이 **'마침표(.)의 싱귤래리티'**로 빨려 들어가며 상위 도메인 도트 하나로 강력하게 응축됩니다.
  - **폭발 (Explosion):** 사용자가 특정 노드를 상세히 탐색(Zoom In)하거나 실행 명령을 내릴 때 발생합니다. 정적인 상위 도트가 깨지며 내부의 **5W1H 참조 사슬(SNT-IND-EFF)**과 세부 기능들이 사방으로 분화되어 시각적으로 펼쳐집니다.

##### B 자연어 입력 기반 역동적 카드(노드) 깊이(Depth) AI 협력 제어 설계

** 이 기능은 별도의 확장 프로그램으로서 전역에서 사용 가능 하도록 하는 기능이다**

사용자가 "보고 싶은 흐름"을 자연어로 입력하면, AI가 각 카드의 **LOD(Level of Detail)**와 **계층 깊이(Depth)**를 개별적으로 재구성하는 기능의 기초 설계입니다.

    ####### ① 언어적 정규화 및 의도 추출 (Linguistic Routing)

    사용자의 입력을 **Linguistic Routing 엔진**이 실시간으로 분석 >.

    - **추출 로직:** 사용자가 "보안 관련 실행 과정을 상세히 보여줘"라고 입력하면, AI는 `security`, `execution_chain`, `detailed` 등의 키워드를 추출하여 **영문 IR(중간 표현)**로 변환합니다.
    - **가중치 할당:** 추출된 키워드에 따라 관련 Capability ID들의 **의도 중력(X7)** 값을 일시적으로 상향 조정합니다.

    ####### ② 역방향 분해를 통한 깊이 결정 (Reverse Decomposition)

    AI는 전체 지식 지도에서 사용자의 관심 대상이 되는 노드들의 **Depth**를 역동적으로 계산 >.

    - **개별적 깊이 조절:** 관심도가 높은 노드는 `depth` 필드와 상관없이 강제로 **폭발(Explosion)** 상태로 전이시켜 하위 스텝(execution_steps)을 노출합니다.
    - **잔여 적합도(Fit Score) 연동:** 각 노드가 사용자의 질문에 얼마나 부합하는지 **Fit Score**를 산출하고, 이 점수가 높은 노드일수록 더 깊은 계층의 정보(물리적 경로, 상세 메타데이터)를 캔버스 전면에 부상시킵니다.

    ####### ③ 시맨틱 줌(Semantic Zoom) 엔진 가동

    단순히 화면을 키우는 것이 아니라, AI의 판단에 따라 정보의 밀도를 변환 > .

    - **동적 계층 필터링:** AI가 "이 흐름에서는 사실(Fact) 위주로 보라"고 판단하면, 중력 축을 따라 **사실(SNT)** 노드들만 고배율 LOD로 활성화하고 나머지는 도트 형태로 압축(Implosion)합니다.
    - **시각적 피드백 연동:** 확신도가 낮은 경로는 **NIXIE**가 **Jitter**를, 핵심 규범(ERA)이나 승인된 경로는 **Lumina**로 시각적 이정표를 제공합니다(NEXU 캔버스 표면·`nixie_lumina_profile`·UIUX §4.3.1).

    ####### ④ 설계 요약: AI 지휘 매뉴얼

    1.  **Listen:** 자연어 입력에서 5W1H와 의도 중력 대상 식별.
    2.  **Calculate:** 대상 노드들의 개별적 **Fit Score**와 **X7 중력 가중치** 계산.
    3.  **Effect:** 관심 노드는 `is_virtual=false`급의 선명도로 **폭발**시키고, 비관심 노드는 10진법 군집화 로직에 따라 **함몰**시켜 시각적 노이즈 제거.

이 설계를 통해 사용자는 수만 개의 Capability ID 중 자신이 보고 싶어 하는 "사유의 경로"만을 인공지능이 실시간으로 펼쳐주는 **역동적인 지능형 지도**를 경험하게 됩니다.

## Nexion에서 Capability ID를 폴더 및 파일명에만 발급 전략

1.  **계층별 차등 발급:** 도메인 및 메뉴 레벨의 상위 Capability ID(예: `nexa.platform.*`)는 폴더/파일 시스템과 일치시키고, 그 하위의 아주 미세한 액션(원자 단위 스텝)은 문서 내의 **섹션(Anchor)**이나 **JSONB 메타데이터**로 관리하여 파일 개수 폭발을 방지합니다.
2.  **가상 노드 허용:** Nexion 캔버스에서는 `is_virtual = true`를 통해 파일이 없는 상태에서도 ID를 제안(ECHO)하거나 배치할 수 있게 하되, 실제 **물리적 실행(is_virtual = false)**이 일어나는 순간에만 파일을 강제하는 방식을 채택하는 것이 효율적입니다.
