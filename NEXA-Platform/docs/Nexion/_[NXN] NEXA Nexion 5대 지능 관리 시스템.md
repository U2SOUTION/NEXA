## Nexion 5대 지능 관리 시스템

이 문서는 NEXA-OS 지능 자산의 근간을 이루는 Nexion 5대 지능 관리 시스템의 설계 구조와 거버넌스 원칙을 다룹니다.
시스템은 데이터의 골격을 세우는 Database부터 개별 지능에 고유한 영혼을 부여하는 Identity, 기능적 자격을 부여하는 Capability, 공통 언어를 정의하는 Glossary, 그리고 지능형 서사를 물리적 공간에 배치하는 Narrative까지 5단계의 체계적인 설계 및 거버넌스 레이어로 구성됩니다.
이 5대 요소는 지능의 내면적 설계도로서 역할을 수행하며, 실제 실행을 담당하는 런타임 엔진이나 사용자 경험 레이어와는 엄격히 분리되어 운영됩니다.

| 항목          | 내용                                                                                                                  |
| :------------ | :-------------------------------------------------------------------------------------------------------------------- |
| **명명 규칙** | **「Nexion + [관리 대상]」** — 기술명은 배경에 두고 지능적 서사를 전면에 둔다.                                        |
| **범위**      | NEXA-OS 지능 자산을 **설계·거버넌스**하는 **5개 관리 도구**(Database → Identity → Capability → Glossary → Narrative). |

> **정리·정제 툴:** Re-pointing·지능 자산 정제는 **별도 6대가 아니라 `Nexion Identity` 하위(운영자 모듈)**로 둔다. 상세는 본 문서 **「검토: Re-pointing·정제 툴」** 절.

## 파이프라인·위상 정리

이 5가지 도구는 Nexion이라는 큰 틀 안에서 **[데이터 골격(Database) → 정체성(Identity) → 권한(Capability) → 언어(Glossary) → 물리 서사(Narrative)]**로 이어지는 지능 관리 파이프라인을 형성한다.

**위상:** Nexion **5대** = NEXA-OS 지능 자산 **설계·거버넌스 레이어**(런타임 전체 엔진과 구분).

## 생태계 요약 과 Phase B-ops(운영 고도화) 단계의 핵심 체크리스트

- **5대:** **영혼을 설계하는 설계도** (Database→…→Narrative).
- **위 레이어 5개:** **몸·실행·공감·얼굴·시간** — Nexion 번호 **부여 안 함**.

### 시스템의 완성도를 위해 보강이 필요한 **4가지 핵심 영역**.

#### 1. 지능 자산 정제(Refining) 및 Re-pointing 로직의 명확화

Identity(영혼) 관리 시스템에서 정제 툴의 역할은 정의되어 있으나, 운영 시 **참조 사슬의 재배선(Re-pointing)** 절차는 **별도 문서**로 더 구체화한다.

- **보강 필요 사항:** 특정 `identity_id`가 `superseded_by_id` 또는 `replaced_by_id`를 통해 다른 ID로 수렴될 때, `execution_chains`, `project_logs`, `nexa_knowledge_references` 등에 흩어진 수백만 건의 참조를 **백그라운드 배치 작업**으로 어떻게 안전하게 옮길 것인지에 대한 운영 프로세스가 필요.
- **핵심 가드레일:** 슈퍼 관리자만이 이 작업을 수행할 수 있으며, 삭제 전 **참조 카운트 0 검증** 및 **삭제 직전 스냅샷(JSON 덤프)** 보관이 필요하다.

#### 2. 활력 지수(VI) 기반 'Low-Entropy' 모드 UI 반영

Nexion은 개발자의 '사고의 칠판'이므로, 사용자의 상태에 따라 인터페이스가 반응하는 **공감 엔진(Empathy Engine)**과의 연동이 중요함.

- **보강 필요 사항:** 사용자의 활력 지수(VI)가 임계값 미만으로 떨어졌을 때, Nexion의 각 관리 시스템(특히 Database 및 Narrative)이 **'Low-Entropy Throttling'**을 어떻게 수행할지 정의해야 함.
- **구체적 연출:** 예를 들어, VI 저하 시 복잡한 ERD 선들을 숨기고 핵심 노드만 보여주는 **'Static UI'**로 전환하거나, 복잡한 '자원 합성 제안' 기능을 일시적으로 차단하는 제동 로직이 5대 시스템 전체에 걸쳐 고려되어야 함.
- 다만 이 연동은 **공감 엔진 자동 제어만**으로 두지 않고, **Nexion 쪽에서 직접 제어·정책 플래그**로 걸 수 있게 두고, **NIXIE 피드백**은 검증·관측용으로 단계적으로 적용해 본다.

#### 3. NIXIE 비언어 피드백(Jitter/Lumina)의 데이터 결합

5대 시스템의 상태가 사용자에게 **NIXIE**를 통해 어떻게 투영되는지, **데이터 필드·점수 연결**을 보강한다.

- **보강 필요 사항:** `project_logs`에 기록되는 `nixie_feedback` 필드(error_token, parser_version 등)를 5대 시스템의 '신뢰도 점수(Confidence Score)'와 결합해야 함.
- **시각적 증명:** `Nexion Narrative`에서 동기화 불일치가 감지되거나 `Nexion Identity`에서 중복 ID 후보가 발견될 때, 캔버스의 해당 노드가 **미세하게 떨리는(Jitter)** 강도를 `confidence_score`와 실시간 매핑하는 규약이 필요.

#### 4. 섀도우 프로젝트(Shadow Project)와 테넌트 격리 지원

Nexion이 플랫폼 전체의 관제 데스크 역할을 하려면, 정식 프로젝트 밖에서 발생하는 지능 자산도 수용할 수 있어야 한다.

- **보강 필요 사항:** `TRIAL`, `DAILY`, `HELPER` 등 예약된 UUID를 가진 **섀도우 프로젝트**에서 생성된 Identity나 Narrative 자산을 Nexion이 어떻게 시각화하고, 나중에 정식 프로젝트로 **흡수(Absorption)**시킬 것인지에 대한 정책이 필요.
- **데이터 소유권:** `tenant_id`를 통해 RLS(행 수준 보안) 경계를 나누되, 전역 싱글톤인 `identity_id`와의 참조 무결성을 Nexion Capability 시스템에서 어떻게 검증할 것인지 명시.
- 이 주제는 충분히 검토한 뒤, **외부·섀도우 자산을 OS 단에 흡수할지** 여부를 별도 결정한다.

## NEXA 섀도우 프로젝트(Shadow Project) 란?

넥사 OS의 **쉐도우 프로젝트(Shadow Project, 그림자 프로젝트)**는 특정 정식 프로젝트에 귀속되지 않는 활동들을 시스템적으로 관리하기 위해 예약된 고유 ID 체계.
모든 실행 사슬(`execution_chains`)과 지능 자산은 `project_id NOT NULL` 원칙을 지켜야 하므로, 프로젝트 밖의 활동을 수용하기 위해 다음과 같이 **TRIAL**, **DAILY**, **HELPER**로 그 역할을 구체적으로 명시됨 (넥사 오케스트레이션).

각 용어의 구체적인 정의와 운영 규칙은 다음과 같이 설명 된다.

### 1. TRIAL (TRIAL_USER): 비회원 체험 및 휘발성 활동

- **정의:** 플랫폼에 정식 가입하지 않은 비회원이 시스템을 체험하거나, 일시적인 익명 활동을 수행할 때 할당되는 프로젝트 영역입니다.
- **휘발성 정책:** 보안과 자원 효율을 위해 가장 강력한 휘발성 정책을 적용받습니다. 일반적인 지능 사슬이 거치는 `VOID.ARCHIVE`(장기 보존) 단계를 생략하고, 발생 **7일 후 즉시 `VOID.PURGE`(물리 삭제)**가 가능하도록 설계되었습니다.
- **흡수 정책:** 사용자가 TRIAL 상태에서 작업을 수행하다가 정식 계정을 생성하고 프로젝트를 만들면, 해당 TRIAL 사슬은 신규 `project_id`로 승격되어 **장기 기억(Long-term Memory)**으로 편입될 수 있습니다.

### 2. DAILY (DAILY_HELPER): 회원의 프로젝트 외 일상 활동

- **정의:** 정식 가입된 회원이 특정 비즈니스나 기획 프로젝트(예: 넥사 OS 구축 프로젝트 등)에 진입하지 않은 상태에서 수행하는 **개인적이고 일상적인 활동**을 위한 영역입니다.
- **용도:** 일상적인 루틴 기록, 단순 질의응답, 도우미 기능 활용 등이 여기에 해당합니다.
- **위상:** 사용자와 연결되어 있지만 특정 프로젝트의 보안 격리(RLS)와는 별개로 운영되며, 회원의 개인적인 '일상 맥락'을 학습하는 기초 데이터가 됩니다.

### 3. HELPER (GLOBAL_GUIDE): 플랫폼 전역 가이드 및 도우미

- **정의:** 플랫폼 전체 차원에서 제공되는 **글로벌 가이드, 시스템 도우미, 또는 자동화된 헬퍼**의 활동을 관리하는 영역입니다.
- **범위:** 특정 사용자의 사적인 영역을 넘어, 플랫폼 전체에 공통적으로 적용되는 지능적 원칙이나 가이드를 전파할 때 사용됩니다.
- **특성:** `scope_type`이 `GLOBAL`로 분류되며, 시스템의 표준 규범(ERA)과 밀접하게 연동되어 사용자에게 공통된 지능형 인터페이스를 제공하는 주체로 작동합니다.

### 요약 및 기술적 매핑

| 구분       | 내부 예약명    | 주요 타겟                    | 데이터 수명 주기 (VOID)                |
| :--------- | :------------- | :--------------------------- | :------------------------------------- |
| **TRIAL**  | `TRIAL_USER`   | 비회원, 익명 체험자          | **7일 후 즉시 소멸** (가장 짧음)       |
| **DAILY**  | `DAILY_HELPER` | 정식 회원의 일상 활동        | 일반 정책 준수 (90일 잠재 후 아카이브) |
| **HELPER** | `GLOBAL_GUIDE` | 플랫폼 시스템, 전역 에이전트 | 시스템 영구 자산 또는 장기 보존        |

이러한 구분은 넥사 OS가 **"사용자의 모든 활동은 족보(Traceability)를 가져야 한다"**는 원칙을 유지하면서도, 활동의 성격에 따라 데이터의 유통기한과 권한을 다르게 관리할 수 있게 해주는 핵심 장치입니다.

## 운영: 발급(Mint) 경계와 섀도우·현장 데이터

NEXA-OS의 **거버넌스 무결성**과 **시스템의 간결함**을 유지하기 위해, Identity ID가 섀도우 프로젝트(TRIAL, DAILY, HELPER)나 현장 센티널(TICK) 등 **다양한 표면(Surface)** 에서도 **언급·추출**될 수 있게 열리면서, 당초 기획한 **근간 문서 기반의 엄격한 발급 정책**과 **겉으로 충돌하는 것처럼 보일 수 있다.**

이 혼란을 해소하기 위해, **'발급(Minting)'**과 **'참조/추출(Mention/Extraction)'**의 경계를 어떻게 관리하는지 설계 원칙을 바탕으로 정리함.

### 1. Identity ID의 발급 권한: Minting Gate는 여전히 폐쇄적으로 관리

Identity ID(`nexa_identities`)는 플랫폼 전체의 '영혼 원장'이므로, 아무 곳에서나 자동으로 생성되지 않도록 설계되어 있습니다.

- **발급 경계 (Minting Boundary):** 설계상 새로운 Identity ID는 여전히 **nature_tag가 RULE 또는 INTENT인 '근간 기획문서'**에서만 추출 및 정의될 수 있습니다.
- **승인 루프 (ASK → WILL):** 센티널이나 AI(ECHO)가 새로운 개념을 발견하더라도, 시스템은 이를 즉시 글로벌 ID로 발급하지 않습니다. 대신 **'승인 대기(ASK)'** 상태로 큐에 쌓으며, 아키텍트가 이를 검토하여 **최종 승인(WILL)**을 내릴 때만 원장에 박제됩니다.
- **1만 개 용량 유지:** 이 엄격한 게이트키핑 덕분에 ID의 총합을 1만 개 내외로 통제할 수 있으며, NanoID 4자(전체 6자) 체계를 유지할 수 있습니다.

### 2. 섀도우 프로젝트 및 현장 데이터의 처리: "식별"과 "생성"의 차이

TRIAL, DAILY 프로젝트나 센서(TICK)에서 발생하는 지식은 **새로운 ID를 만드는 것이 아니라, 기존 ID를 찾아 연결하는 것**에 집중합니다.

- **언어적 라우팅 (Linguistic Routing):** 현장에서 들어온 날것의 팩트(SNT)는 라우팅 엔진을 통해 **이미 발급된 Identity ID** 중 가장 적절한 것을 찾아 'Mention(재등장)'으로 기록합니다.
- **프로젝트 지식 (Project Knowledge):** 만약 기존 원장에 없는 새로운 개념이라면, 글로벌 `nexa_identities`가 아닌 해당 프로젝트 내부의 **`project_knowledge`** 레이어에만 임시로 머무릅니다. 이는 플랫폼 전체의 '영혼'이 아닌 특정 테넌트의 '휘발성 기억'으로 취급됩니다.

### 3. 발급 체계 확장 시의 장단점 분석

| 구분                      | 장점                                                                              | 단점 및 리스크 (배치 지점)                                         |
| :------------------------ | :-------------------------------------------------------------------------------- | :----------------------------------------------------------------- |
| **기존: 문서 전용 발급**  | ID의 순수성과 정합성이 완벽함. 1만 개 이내 통제가 확실함.                         | 현장의 새로운 발견이나 예외 상황을 즉시 반영하기 어려움.           |
| **보강: 하이브리드 추출** | AI가 실시간으로 새로운 패턴을 발견해 **'규범 승격(Promotion)'**을 제안할 수 있음. | 무분별한 발급 시 ID 범위가 폭발하여 4자 NanoID 체계가 붕괴될 위험. |

### 4. 설계적 해결책: "지능 자산 정제 툴"의 역할

v3.1 설계의 **운영자 전용 정제 툴**이, 무분별 발급·중복에 대한 방어막 역할을 합니다.

- **중복 방지 파이프라인:** AI가 새로운 ID 발급을 제안할 때, 기존 원장과 **벡터 유사도 및 HEXAGON 문맥**을 대조하여 95점 이상일 경우 강제로 기존 ID에 수렴시킵니다.
- **병합 및 교체 관리:** 실수로 중복 발급된 ID가 있다면 `superseded_by_id`를 통해 정본으로 참조를 옮기고(Re-pointing), 구 ID를 삭제하거나 `deprecated` 상태로 관리하여 원장의 결합도를 유지합니다.

### 요약 및 제언

결론적으로 **"Identity ID는 내부 문서에서만 발급한다"**는 대원칙은 유지하되, **현장의 데이터는 '기존 ID를 찾아가는 인덱스'**로 활용하는 것이 현재 아키텍처의 정답입니다.

1.  **6자(Prefix-4자)** ID 체계는 **'전역 원장'**을 위해 엄격히 보호하십시오.
2.  섀도우 프로젝트나 센서 데이터는 새로운 ID를 **'요청(ASK)'**할 수는 있지만, 아키텍트의 승인 없이는 원장에 **'박제(Mint)'**될 수 없습니다.
3.  이 체계가 유지된다면 **1만 개 수준의 고품질 지식 베이스**를 4자 NanoID 본문으로도 충분히 운영할 수 있다.

이러한 **발급 주도권 강제 원칙**은 `nexa_identities` DDL 제약 또는 API 권한 로직에 **명시해야 한다.**
