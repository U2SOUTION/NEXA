# NEXA Generative Music 비전과 NIXIE & MORSE

**문서 목적:** NEXA NIXIE v0.3에서 **Tone.js**(음악·스케줄링)와 **P5.js**(절차적 시각) 도입을 위한 비전, **현재 코드베이스(`nexnapSnapshotStore` 등)와의 용어 정렬**, 갈아타기 로드맵을 한 곳에 정리한다.

**전략 순서:** 사이드바 **3대 UI**(NIXIE 캐릭터 · 닉시 컨트롤 · 사운드 패널)를 먼저 구현해 시청각 피드백을 고정한 뒤, `**src/domains/nexion`** 등 지식·족보 도메인을 얹는다. 본 문서 **§5.6~§5.8이 그 인터페이스·동기·API 계약의 뼈대다.

---

## 1. 비전과 파이프라인 (한 흐름)

지식 운영체제(NEXA-OS)의 추상을 **공감각적 예술(Art Project)**로 옮기고, 닉시 **미션 8(도트 음파)**를 고도화하여 **지능적 맥박**을 소리·시각 서사에 맞춘다.

**[지능적 근거 → 음악 번역 → 시각 투영 → 음악 기획·자산 생성]** 파이프라인:

| 단계        | 기술           | 내용                                                                                                                            |
| ----------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| 지능적 근거 | NEXA-OS / 스펙 | Identity·토큰·판단 흐름이 연주의 입력이 된다. (세부 스키마는 제품 스펙 문서에 두고, 구현 시 `NexnapSnapshot` 등과 매핑표를 둔다.) |
| 음악적 번역 | **Tone.js**    | 위상차·리듬을 주파수·화성·`Tone.Transport`로 스케줄. 모스 리듬·엔벨로프 정밀 제어.                                              |
| 시각적 투영 | **P5.js**      | FFT 등을 받아 도트·성운 등 절차적 생성.                                                                                         |
| 소스 생성   | AI·렌더        | UCL 등 실행 사슬과 연동해 사운드 로고·엠비언트를 자산화(장기).                                                                  |

### 1.1 Tone.js — 음악적 통신 장비(요지)

- **시그니처:** Identity 등을 `PolySynth` 등에 주입해 Musical Signature 후보를 만든다. 6자 ID를 주파수로만 매핑하는 수준을 넘어, NEXA-OS `**nature_tag`(예: RULE / INTENT / FACT)** 와 **신뢰도·provisional** 메타를 함께 넣어 음색·화성 규칙을 정한다 — 상세는 **§2.2 (1).
- **공감·상태:** 활력·필터(예: `AutoFilter` / Lowpass), 신뢰도에 따른 Vibrato·Noise 등으로 **ASK** 등 상태를 청각적으로 구분한다.
- **스냅샷과의 연결:** 의미 6축·DSP 4축은 이미 `nixieSoundAtmosphereMap` / `nixieSoundLayer*`로 정규화되어 있다. Tone 도입 시 이 축을 **Voice/Composer 입력**으로 재사용하는 것이 1차 목표다.

### 1.2 P5.js — 지능형 서사 시각화(요지)

- **도트 음파:** Tone 분석(FFT) → P5에서 도트 집합·강도 반응.
- **데이터 공백(절차적 VOID):** 실측이 없는 구간을 Perlin `noise()` 등으로 채우는 **시각적 공백**을 의미한다. UI 상태 `**how_state === 'VOID'`**(닉시 HUD)와 혼동하지 않도록 본 문서에서는 **「절차적 VOID」**로 부르며, 코드 식별자는 `**NIXIE_VISUAL_PROCEDURAL_GAP`**(`nixieDotMap.ts`, §4.1)로 **OS·UI VOID와 분리**한다.
- **COLD / HOT:** 저부하 시 정적 캔버스, 고부하 시 셰이더 결합 등 단계적 품질(장기).

### 1.3 음악 아카이브(장기)

- 판단·6-COILS 등 스냅샷을 .wav 등으로 렌더·`project_media` 연계하는 상상은 유지하되, **스키마·코일 정의는 NEXA 제품 스펙**과 동기화할 것. 특정 판단(IND)·Why Chain 분기점의 **시청각 스냅샷 자산화**는 **§2.2 (4)** 와 맞춘다.

## 2. 세 레이어 아키텍처 (정의 한 번 + 역할 표)

모든 레이어는 **저장·불러오기**가 가능하고, **Context**가 Voice·Composer 선택을 중재한다. **힌트 시스템:** Context가 온톨로지에 맞춰 추천(수동은 하이라이트, Auto-pilot은 즉시 반영 등) — 세부 UX는 별도 설계.

| 레이어       | 역할                       | AI 제안(예)               | 사용자 제어(예)          |
| ------------ | -------------------------- | ------------------------- | ------------------------ |
| **Context**  | 상황·온톨로지·메타 제어    | 긴박함 감지 → 템플릿 추천 | 상황 노드 선택·저장      |
| **Composer** | 모스·센서 등 → 시간축·화성 | 도리안 코드 진행 제안     | 리듬–음표 매핑 규칙 설계 |
| **Voice**    | 음색·합성·출력             | 날카로운 패치 제안        | 오실·필터 수치·프리셋    |

### 2.1 Voice / Composer / Context — 기능 정립(중복 없이)

- **Voice:** 프리셋 악기 + 커스텀 빌드(`nixieSoundLayerAudio.ts`가 현재 인스턴스 성격을 담당; Tone 이전 시 역할 재검증).
- **Composer:** 기본 리듬·음계 + 사용자 정의 매핑(예: DIT 구간 → 화음).
- **Context:** 온톨로지 KB + 자동 감지 + **Active Hinting**(장르·템포 등 추천 문구).

### 2.2 시스템 고도화를 위한 보강 (Musical Signature · 6-COILS · 공감 스로틀 · Why Chain)

아래는 **NEXA-OS 지능 메타**(Identity·코일·공감·족보)와 **Tone / P5 / 닉시**를 **강결합**할 때의 방향이다. 필드명·임계값(`vi_threshold` 등)은 **제품 스펙·스키마**에서 확정하고, 본 절은 **역할·매핑 규약**만 고정한다.

#### (1) Identity ID 기반 Musical Signature와 `nature_tag` 연동

| 입력(개념)                    | 음악적 해석                                                                                                        |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **6자 Identity ID**           | 단일 주파수·스케일 시드로 쓰되, **끝이 아니라 시작점** — 위성 음·리듬 시드·레이어 분배에 확장                      |
| `**nature_tag` — RULE         | 화성적으로 **안정된 협화음**·적은 비조화 — “규범·합의”가 들리게                                                    |
| `**nature_tag` — INTENT       | 진행·리듬 강조, 목표 음정으로의 **텐션 해소** 패턴을 우선                                                          |
| `**nature_tag` — FACT         | 관측·로그에 가깝게 — **중립 톤**, 노이즈 플로어는 낮게, 변조는 최소                                                |
| **provisional / 낮은 신뢰도** | **디튜닝(Detune)**·**지터(Jitter)**·얕은 **Noise**를 혼합해 **불안정한 음색** — 소리만으로 “아직 확정 아님”을 인지 |

**한 줄:** 지능의 **의미·성격**이 곧 **합성 규칙**이 되게 하여, Musical Signature를 OS 메타와 동기화한다.

#### (2) 6-COILS 가치 필터와 사운드·아트 파라미터 강결합 (Context 레이어)

**Context**가 6-COILS 가중치(또는 정규화된 벡터)를 읽어 **Voice·P5**에 동시에 주입하는 **지능형 이퀄라이징**을 전제한다(구현은 매핑표 1장으로 고정).

| 코일(예시)      | Tone.js (설계)                                                     | P5.js (설계)                                |
| --------------- | ------------------------------------------------------------------ | ------------------------------------------- |
| **Stability** ↑ | 필터 컷오프 **낮춤**, 엔벨로프 **Release 길이** — 정적·안전한 잔향 | 입자·도트 **속도↓**, 색 대비 **완만**       |
| **Creative** ↑  | **비조화 성분**(부분 트라이톤 클러스터·FM 깊이) **활성화**         | **입자 밀도**·레이어 수 **증가**, 변형 강조 |
| **Harmony** ↑   | 간격 좁은 화음·코러스 양                                           | 격자 **대칭**·팔레트 **조화**               |
| **Safety** ↑    | 리미터·소프트 클립·날카로운 대역 억제                              | 경고색·플래시 **제한**(접근성)              |

**원칙:** “코일 = 슬라이더 하나”가 아니라 **Context가 한 번 해석해** Composer/Voice/P5가 같은 의도를 받게 한다.

#### (3) 공감(Empathy) 기반 에너지 쓰로틀링 — 활력 지수(VI)와 Low-Entropy

사용자 **활력 지수(VI)** 가 낮고 엔트로피가 **Low-Entropy** 구간에 들어갈 때(정책: `**vi_threshold` 미만** 등) **인지 부하를 줄이는** 연출을 **강제 규약으로 둔다.

| 층          | 제언                                                                                                                  |
| ----------- | --------------------------------------------------------------------------------------------------------------------- |
| **P5.js**   | 복잡 **셰이더·다중 패스** 연산 **중단** → **정적 비트맵**·단순 `draw()` 경로로 전환(이미 캔버스된 프레임 재사용 가능) |
| **Tone.js** | **로우패스 필터**로 **고주파 강제 절단**(마스터 또는 버스) — “조용한·부드러운” 청각 환경                              |
| **공통**    | §4.1 **COLD** 정책과 별개로, **사람 쪽 부하**를 줄이기 위한 **소프트 런타임 모드**로 명명해 로그·설정에 노출          |

#### (4) 지능적 족보(Why Chain)의 시청각적 박제와 `project_media`

- **트리거:** 특정 **판단(IND)** 이 확정되거나 Why Chain 상 **분기가 닫힌 순간**의 `NexnapSnapshot`(또는 오케스트레이션 `post_state_snapshot`에 대응하는 최소 패키지)을 캡처한다.
- **렌더:** 위 스냅샷을 입력으로 **짧은 사운드 클립**(·선택 시 메타데이터 동반 파형/스펙트럼 이미지)을 **오프라인 또는 백그라운드** 렌더하여 **`project_media`**에 등록한다.
- **서사적 복구:** 이후 **Timeline Branch**로 되돌아올 때, 로그 텍스트뿐 아니라 **당시 시스템의 사유 상태를 소리·빛의 조각으로 재생**할 수 있게 한다 — 단순 감사 로그를 넘어 **감각적 타임머신** 역할.

**스키마:** 미디어 자산에 `why_chain_id` / `ind_ref` / `snapshot_schema_version` 등 **추적 키**를 붙여 SSOT 문서(오케스트레이션·미디어)와 **1:1**로 맞춘다.

## 3. Composer 데이터 매핑과 데이터 인터프리터

**입력 유형 예:** 상징(모스·지식 벡터), 비정형(ASMR 등), 연속(센서), 전통(MIDI·오디오). Composer는 **추상화** 후 공통 규격으로 처리한다.

**데이터 인터프리터(한 줄):**  
`Normalization(0~1)` → `Context Alignment`(같은 0.8이 타격인지 음정인지) → `Generator`(MIDI·CC 등) → **Voice**.

AI 힌트·매핑 자동화 비중은 제품 정책으로 두되, **정규화 규격이 먼저** 있어야 힌트가 안정적이다.

## 4. NEXA-OS / 시뮬 스냅샷과의 용어 정렬

구현에 가까운 SSOT는 Pinia **`nexnapSnapshotStore`**의 `**NexnapSnapshot`**(`src/system/store/nexnapSnapshotStore.ts`)이다. 세계관 용어(6-COILS·UCL·Identity 6자·HEXAGON 토큰)는 **별도 스펙 문서에서 필드와 1:1 매핑표를 둔다.

| 문서·세계관 용어 | 코드 쪽 앵커(현재)                                       |
| ---------------- | -------------------------------------------------------- | ------- | ----------------------------------- | -------------------------------------------------------------------------------------- |
| 흐름·상태        | `how_state` (`FLOW`                                      | `STUCK` | `VOID`) — UI **VOID**는 여기에 대응 |
| 펄스·페르소나    | `who_pulse` (`**WILL`                                    | `ECHO`  | `ASK`                               | `TICK`) — `TICK`은 센티널·장치 사실 축(§4.1). 타입 SSOT는 `nexa-protocol`의 `WhoPulse` |
| 신뢰·임계        | `confidence_score`, `user_defined_threshold`             |
| 동적·엔트로피    | `entropy_level`                                          |
| 의미 6축         | `sound_atmosphere_*`, `sound_atmosphere_mapping_enabled` |
| 모스·HUD         | `morse_*`, `demo_hud_*`, `morse_playback_*`              |

**NEXA-OS (본 문서에서의 의미):** 앱이 구독하는 **스냅샷 + Nexnap 시뮬 규약**을 통칭. **「핵사곤」** 등 내부 별칭은 공식 명칭이 정리되면 표 위에 한 줄로 고정한다.

**6코일 / 사용자 가중치:** 스냅샷 필드로 아직 없으면, 도입 시 `**NexnapSnapshot` 확장안과 함께 표를 갱신한다.

**Identity·지능 메타·족보:** `nature_tag`·provisional·6-COILS·IND·Why Chain·`project_media` 시청각 박제는 **§2.2** 규약과 제품 스키마를 함께 따른다.

### 4.1 NEXA OS 정합: 주요 충돌·주의·해결 (VOID / WhoPulse / 하드웨어 프로필)

갈아타기 전략(Tone·P5·닉시)과 **넥사 OS·지식 스택**을 동시에 쓸 때 아래 세 가지가 가장 자주 꼬인다. **의도적으로 이름·계층을 나누지 않으면** AI 추론·리뷰·온보딩에서 동일 문자열이 다른 개념으로 읽힌다.

#### (1) VOID의 이중·삼중 의미 — 네임스페이스 분리

| 구분                    | 의미                                                                                                        | 코드·문서 앵커                                                                                                                                                  |
| ----------------------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **OS 생애주기 VOID**    | 지식·설계 자산의 **POTENTIAL → ARCHIVE → PURGE** (스왑·상주·운영 DDL)                                       | 용어집·`_KNOWLEDGE`·`nexa_knowledge_residency` 등 — `**how_state` 문자열과 동일하게 취급하지 않는다                                                             |
| **UI·Nexnap 흐름 VOID** | 닉시 HUD·스냅샷 `**how_state === 'VOID'`** — 흐름이 비어 있거나 잠재/영감 모드에 가깝게 읽히는 **상태 한 점 | `HowState`, `setHowState('VOID')`                                                                                                                               |
| **절차적 VOID (시각)**  | 실측 FFT·센서가 없을 때 P5 `noise()` 등으로 채우는 **시각적 공백**                                          | 문서 표기 **「절차적 VOID」**; 코드에서는 `**NIXIE_VISUAL_PROCEDURAL_GAP`** (`'PROCEDURAL_VOID'`, `nixieDotMap.ts`)처럼 **UI 상태 enum과 다른 식별자만 사용한다 |

**해결 요약:** `VOID`라는 토큰을 **한 타입/한 enum에 몰아 넣지 않는다.** OS·스키마·닉시·P5는 각각 표·상수·접두로 구분하고, 본 문서 §1.2·§4 표와 위 표를 SSOT로 삼는다.

#### (2) 페르소나·펄스 (`who_pulse`) — WILL / ECHO / ASK / TICK

- *`*nexa-protocol.ts`의 `WhoPulse`**가 스냅샷·센티널 추상화의 단일 출처이며, `**WILL`·`ECHO`·`ASK`·`TICK`** 네 가지를 포함한다.
- **ASK:** 신뢰도 게이트·승인 대기(운영 규약의 STUCK→ASK)에 대응하는 **의사결정 축**.
- **TICK:** 엣지 센티널·장치·시계열에서 온 **순수 사실 펄스**. 문서만 TICK을 쓰고 코드 레지스트리에 없으면, 장치 기반 사운드/시각 파이프가 끊기기 쉽다 — **스냅샷·프로토콜 타입에 반드시 포함**한다.
- 외부 문서에 옛날 `TICK`만 있거나 `ASK`만 있는 경우, **본 절과 타입 정의를 기준으로 역주(역할 설명)를 붙인다**(이름을 바꾸기보다 역할을 맞춘다).

#### (3) 하드웨어 프로필 COLD / WARM / HOT — Tone·P5 적용 범위

- **COLD(예: ESP32):** 패키지 상한·벡터 탑재 금지 등 **엄격한 제약**이 OS 정책으로 잡혀 있다면, **브라우저 기반 Tone.js·P5.js 스택을 해당 장치 본체에 강제하지 않는다.**
- **WARM/HOT(예: 라즈베리 파이·데스크톱 브라우저):** 본 기획의 Tone·P5·`engines/sound` 본류가 **전제로 하는 런타임**이다.
- **해결 요약:** 갈아타기 로직(스냅샷 계약·모스 타임라인·DSP 의미 축)은 **플랫폼 무관**으로 두되, **실행 바이너리·번들**은 `HardwareProfile` 또는 배포 채널별로 **조건부 로드·대체 구현**(정적 HUD만, Web Audio 경량 경로만 등)을 택한다. COLD에서는 **데이터 모델·이벤트 형식만** 맞추고, 무거운 시각·합성은 **게이트웨이·상위 티어**에서 수행한다는 전제를 문서·아키텍처에 명시한다.

#### (4) COLD·공감 연동 시 UI 적응과 **에너지 모드 배지**

| 모드(표시)  | 트리거(개략)                          | P5.js                                                 | Tone.js / 오디오                                                        |
| ----------- | ------------------------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------- |
| `**normal`  | WARM/HOT, 제약 없음                   | 셰이더·입자·`draw()` 풀 품질                          | 이펙트 체인·폴리포니 전개                                               |
| `**minimal` | COLD 또는 VI/엔트로피 스로틀(§2.2(3)) | **복잡 셰이더·다중 패스 중단**, 도트·단일 레이어 위주 | **다중 이펙트·무거운 리버브 비활성**, 단일 오실·경량 그래프             |
| `**static`  | 극한 COLD 또는 강제 절전              | **정적 비트맵**·마지막 프레임 유지·`redraw()` 최소    | **경량 Web Audio 경로**(단일 `Oscillator`+`Gain` 수준) 또는 무음·클릭만 |

- **배지 위치:** **HEADER** 또는 **FOOTER**에 `normal` / `minimal` / `static` + (선택) `COLD` 아이콘을 고정 노출해, **“왜 단순해 보이는지”** 개발자·파워 유저가 즉시 이해하도록 한다(§5.1과 배치 충돌 시 FOOTER 우선).
- **§2.2(3)** 의 “사람 부하 감소”와 **COLD**는 별 축이지만, UI 모드 문자열은 **하나의 `energyMode`** 로 통합해 로그·원격 진단에 쓴다.

### 5.1 HEADER 전역 조작 — 플레이·일시정지·정지·음소거·파워 (고정)

**한 줄 요약:** “전원” 하나에 몰지 않고 **재생 수송(플레이/일시정지/정지)** · **청취(음소거)** · **세션(파워)** 를 분리한다. 아래 의미는 **제품·구현에서 변경 시 본 절을 먼저 수정**한다.

#### 컨트롤 정의(고정)

| 컨트롤             | 동작(고정)                                                                                                                                                                                             | 기술 대응(개략)                                                                                        |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| **플레이**         | 스케줄된 타임라인·`Transport` **재생을 시작**한다. 일시정지에서 재개할 때도 이 버튼을 쓸 수 있다(또는 일시정지 토글 해제와 동일 동작으로 묶어도 됨 — UI 중복만 피할 것).                               | `Transport.start` (컨텍스트 `resume` 포함)                                                             |
| **일시정지(토글)** | 재생 **위치·내부 상태는 유지**한 채 **진행만 멈춘다**. 다시 누르면 같은 위치에서 재개.                                                                                                                 | `Transport.pause`에 해당하는 동작(구현 API명은 Tone 버전에 따름)                                       |
| **정지**           | 재생을 끊고 **재생 헤드를 초기 위치로 되돌린다**(한 바퀴·한 패턴의 시작 등 — 정확한 앵커는 모스 타임라인 스펙과 동일하게 고정). **일시정지와의 차이:** 일시정지는 “멈춤 + 유지”, 정지는 “멈춤 + 리셋”. | `Transport.stop` + 타임라인 인덱스/클럭 리셋 규칙                                                      |
| **음소거(토글)**   | **스피커(마스터 출력) 청취만** 끈다/켠다. **엔진·분석·스케줄이 돌아가는지**는 별도 옵션으로 두지 않는 한 **유지 가능**(모니터링만 할 때).                                                              | 마스터 `Gain`→0 / 이전 값 복귀, 또는 `Destination` 뮤트                                                |
| **파워**           | **세션 단위 킬 스위치:** `AudioContext` **suspend**, 필요 시 **마이크·탭/시스템 캡처 스트림 종료**, **Transport 정지**, (정책에 따라) 음소거까지 일괄 적용. **브라우저 탭을 닫는 동작은 아님.**        | `AudioContext.suspend`, `getUserMedia`/`getDisplayMedia` 트랙 `stop`, `Transport.stop`, 입력 노드 분리 |

#### 주의(고정) — 혼동 방지

1. **일시정지 vs 정지:** 위 표의 의미를 제품 카피·툴팁에 그대로 반영한다. DAW마다 “정지”가 다르므로 **헤드 리셋 여부는 본 문서의 정지 정의가 SSOT**다.
2. **음소거 vs 파워:** 음소거는 **들리는 것만** 제어한다. 파워는 **입력(마이크·루프백)까지 끊을지**를 정책으로 한 줄 고정한다 — **권장:** 파워 ON→OFF 시 **외부 캡처는 반드시 종료**, 내부 합성만 쓰는 모드에서는 스트림 없음. **“음소거만 했는데 마이크가 켜져 있다”**는 오해를 막기 위해 상태 배지를 분리한다.
3. **헤더 밀도:** 5개를 항상 노출하면 부담이 될 수 있어 **1차: 플레이·정지·음소거**, **2차(⋯ 또는 설정): 일시정지·파워** 등 **단계적 노출**을 허용한다(배치는 UI 과제, **의미는 본 절 유지**).
4. **FOOTER와의 중복:** 표상 **FOOTER**에도 `재생·루프·볼륨`이 있다. **동일 버튼을 두 곳에 두지 말고**, 예) HEADER=**수송(플레이/일시정지/정지)·파워·음소거**, FOOTER=**루프·마스터 볼륨·세션 길이 표시**처럼 **역할을 한 줄로 나눠** 중복을 없앤다(최종 배치는 UI 스케치에서 확정).

### 5.2 MONITOR 입력 — PC 재생음·캡처 (설정·권한·재설정 유도)

**목적:** 앱 내부 합성(Tone 경로)만이 아니라 **컴퓨터에서 재생되는 소리**(또는 마이크·파일)를 분석 파이프라인에 넣어 **MONITOR**(오실로스코프·스펙트럼·VU)에 보이게 하고, 이후 **Composer·Voice 피드백**으로 확장할 수 있는 **입력·권한 기반**을 마련한다.

**전제(플랫폼):** 웹 기준으로는 **마이크·파일**은 표준 API로 연결하기 쉽고, **“PC 전체 믹스(시스템 오디오)”**는 브라우저/OS마다 제약이 크다(탭·창 공유 시 **오디오 포함** 옵션, 또는 Electron·네이티브에서 별도 캡처). 구현 단계에서 **지원 매트릭스**(브라우저·OS)를 한 장으로 고정한다.

#### 설정 항목(개략)

| 설정(개략 키)                    | 역할                                                                     |
| -------------------------------- | ------------------------------------------------------------------------ | ------------ | ------ | ------------------------------------- |
| `monitor.inputSource`            | 입력 소스: `internal`(앱 합성만)                                         | `microphone` | `file` | `systemOrLoopback`(가능한 범위 내) 등 |
| `monitor.analysisTap`            | 분석 대상: 합성 버스 / 외부 입력 버스 / 믹스(가능 시)                    |
| `monitor.permission.mic`         | 마이크 권한 마지막 상태 캐시(진단용, OS와 불일치 시 재요청 유도)         |
| `monitor.permission.systemAudio` | 시스템/공유 오디오 캡처 가능 여부·마지막 거부 사유(가능하면)             |
| `monitor.file.lastPath`          | (선택) 사용자가 고른 로컬 파일 참조 — 보안 정책에 맞게 샌드박스 내에서만 |

#### 권한·체크 대상

| 대상                         | 사용자에게 필요한 동작                                                                    | MONITOR에 연결되는 가치                                                 |
| ---------------------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| **마이크**                   | 브라우저/OS 마이크 허용                                                                   | 외부 음원·보이스·악기 입력 분석                                         |
| **오디오 파일**              | 파일 선택(드래그·다이얼로그)                                                              | 재생·루프 구간을 앱 내에서 읽어 FFT/스코프에 태움                       |
| **시스템·PC 재생음(루프백)** | OS/브라우저별: **화면·탭 공유 + 소리 공유** 체크, 또는 지원 시 **loopback** 디바이스 선택 | 다른 앱·브라우저 탭에서 나는 소리를 MONITOR에 표시(본 기획의 핵심 목표) |

#### 재설정 유도·환경(UX 개략)

1. **상태 표시:** 설정 패널 또는 MONITOR 상단에 **입력 소스별 권한 배지** — `허용` / `거부` / `미요청` / `이 환경에서 미지원`.
2. **거부·실패 시:** 한 줄 이유 + **「권한 다시 요청」** + **OS·브라우저 설정 열기 안내**(링크 또는 스크린샷 가이드). `getUserMedia`·`getDisplayMedia` 실패 코드에 맞춘 문구 분기(기획서 수준에서만 명시, 문구는 제품 카피에서 확정).
3. **시스템 오디오:** “전체 PC 소리”가 안 될 때는 **대안**을 제시 — 예: 캡처할 **탭만** 공유, 또는 **가상 케이블·루프백 드라이버** 안내(고급 사용자용, 별도 섹션/도움말).
4. **AudioContext 정책:** 사용자 제스처 후 `resume`, 단일 컨텍스트와 외부 입력 노드 연결 순서를 **설정 마법사** 한 번에 묶을지(초기 온보딩)는 UX 과제로 남긴다.

#### 권한 체크 프로세스(상태 기계)·배지 — 끊김 방지

**목표:** `mic` / `systemAudio`(또는 디스플레이 캡처+오디오) 각각에 대해 **한눈에 이해 가능한 배지**와 **다음 행동**을 고정한다.

| 단계            | 조건                                           | UI 배지 문구(예)     | 사용자 액션                                                         |
| --------------- | ---------------------------------------------- | -------------------- | ------------------------------------------------------------------- |
| **0. 미요청**   | 아직 `getUserMedia` / `getDisplayMedia` 미호출 | `미요청` · 회색      | 입력 소스 선택 시 **권한 플로우 시작**(반드시 **사용자 제스처** 후) |
| **1. 프롬프트** | 브라우저 네이티브 다이얼로그 표시 중           | `대기 중` · 주황     | OS/브라우저 대화상자에서 허용·거부                                  |
| **2. 허용**     | 스트림 `active`                                | `허용` · 녹색        | 없음(정상) — MONITOR FFT 연결                                       |
| **3. 거부**     | `NotAllowedError` 등                           | `거부` · 빨강        | **「다시 요청」** + **OS 설정 안내** 링크(§5.2 기존 항목)           |
| **4. 미지원**   | 환경이 API 자체 미지원                         | `미지원` · 회색 점선 | **대안 경로** 안내(파일 입력·탭만 공유 등)                          |

**동시에 두 권한이 필요한 경우(예: 루프백):** 마이크와 디스플레이 캡처를 **별 배지**로 나란히 두고, **하나만 실패해도** “부분 연결” 상태를 표시한다(스코프는 내부 합성만 등).

**캐시:** `monitor.permission.*` 에 마지막 **성공/실패 코드·시각**을 저장해, 탭 복귀·새로고침 후에도 배지가 **거짓 허용**을 보이지 않게 한다.

**한 줄:** 권한은 **상태 기계**로 다루고, 배지는 **항상 현재 상태 + 다음 한 스텝**을 말하게 한다.

이 블록은 **구현 세부(Web Audio 노드 그래프)**가 아니라 **무엇을 설정으로 노출하고, 어떤 권한을 어떤 순서로 점검할지**의 기획 고정용이다.

### 5.3 우측 패널 — 탭 분리(고정) · 타임라인 이중 개념 · 그리드 시퀀서

**탭 분리(고정):** **하나의 “모니터” 캔버스에** 오실·스펙트럼과 **그리드 시퀀서를 겹쳐 올리지 않는다.** 우측(또는 한정된) 공간에서는 **탭(또는 세그먼트 컨트롤)**으로 **「재생·분석(MONITOR)」**과 **「편집·작곡(그리드 시퀀서)」**를 **명확히 나눈다.**  
**이유:** **타임라인·스크럽의 의미**가 재생 모드와 편집 모드에서 **달라야** 하므로, 같은 위젯·같은 축을 공유하면 UX가 쉽게 깨진다.

#### 타임라인 개념(이중 — 고정)

| 모드                | 타임라인 축(개략)                                                                  | 수송과의 관계                                                               |
| ------------------- | ---------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **재생·기성 중심**  | 파일/스트림/`Transport` 기준 **재생 헤드** — 스크럽·점프는 **“지금 듣는 위치”**    | **§5.1** 플레이·일시정지·정지·재개와 **동일 모델**                          |
| **크리에이트·편집** | **스텝·마디·그리드 열** — 단위가 **재생 타임라인과 다를 수 있음**(QP·스텝 길이 등) | 편집 규칙은 **시퀀서 스펙**이 SSOT; Transport와의 매핑은 구현에서 표로 고정 |

#### 그리드 기반 시퀀서(요건)

- **가로축:** 시간(Time / Step)
- **세로축:** 음정(Pitch / Note) 또는 **레인(악기·성부·채널)** 등
- **저장:** 편집 결과를 **JSON**으로 직렬화하고 `**nexnapSnapshotStore`의 Sound Profile / Sequence**와 연결해 재생(스키마 분리는 **§5.4).
- **목적:** 모스·문자 메시지를 보지 않아도 **청각·추상적 패턴**으로 인지할 수 있게 함 — **기본 제공 프리셋 + 사용자 구성**을 전제로 한다.

#### 고급 분석(범위 밖으로 둘 수 있음)

`Tone.Meter`(에너지), `Tone.Analyser`(주파수 분포), 크로마그램 유사, 리듬 밀도 등은 **MONITOR·재생 축**과 느슨히 연결하고, **별도 도메인**으로 두어도 된다.

### 5.4 JSON ↔ `NexnapSnapshot` 스키마(고정)

**원칙:** **역할이 다른 데이터는 한 필드에 섞지 않는다.** (필드명·타입은 구현 시 확정하되, **아래 구분은 본 문서가 SSOT**다.)

| 구분              | 역할(SSOT)                                                    | 비고                                        |
| ----------------- | ------------------------------------------------------------- | ------------------------------------------- |
| **Sequence**      | 그리드 편집 결과 — 노트/스텝 이벤트 등 **시퀀스 본문**의 JSON | **편집·버전**의 근거가 되는 데이터          |
| **Sound Profile** | 음색·믹스·레이어 프리셋 등 **프로필**                         | 시퀀스와 **별도 개체/필드** — 참조로만 연결 |

**스냅샷에 넣는 방식(정책 — 한 줄 고정):** `NexnapSnapshot`에는 **(A) Sequence·Profile에 대한 ID 참조**만 두거나, **(B) 특정 시점의 시퀀스/프로필을 임베드(복사)**하거나, **필드별로 (A)/(B)를 명시**한다.

- **참조(A):** 라이브러리의 **최신 편집**이 반영된다.
- **임베드(B):** 그 스냅샷이 찍힌 **시점의 단계**가 고정된다.  
  **혼용 자체가 금지는 아니며**, 각 필드가 **참조인지 복사본인지**를 타입/메타로 **반드시 구분**해야 한다.

아래는 지금까지 논의를 **한 장으로 고정**한 것이다. 구현·이동 시 **여기를 먼저 수정**한다.

| **스토어**                   | `**system/store`에 유지 (`nexnapSnapshotStore` 등)                                                           | 스냅샷·프로필·시퀀스 **참조의 SSOT**. 앱 전역 상태는 이 층이 진실 원천.                                                                |
| **engines**                  | **재생·분석·시퀀서·(Tone 그래프)** 는 `src/engines/` 층에 둔다                                             | **바꿔 끼울 수 있는 런타임**; UI 프레임워크에 덜 묶이게 유지.                                                                          |

**최상위는 패널 2개**이고, **Sound 패널 안에 탭 2개**가 있어 **사용자가 전환하는 주요 화면은 3구역**(NIXIE 1 + Sound 탭 2)이다. 아래 이름을 **문서·기획·코드 주석**에서 통일한다.

| ID(개략)                | 권장 표기                  | 역할(고정)                                                                                                                           |
| ----------------------- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `**PANEL_NIXIE`         | **닉시** / **NIXIE**       | 닉시 **직접 제어**, **HUD·메시지 입력**, **모스 부호 변환**, **시각 연출**(캐릭터·도트·미션 표현). _청각 엔진의 본류는 두지 않는다._ |
| `**PANEL_SOUND`         | **사운드** / **Sound**     | 모스·타임라인과 **동기화된 사운드**, **Tone·레이어·프로필**, **Nexnap·스냅샷 연동** 등 **소리·분석·편집**의 본류. _하위에 탭 2개._   |

| `**SOUND_TAB_SEQUENCER` | **시퀀서** / **Sequencer** | **그리드 시퀀서**(§5.3)·Sequence JSON(§5.4)·크리에이트 모드 타임라인.                                                                |

**혼동 방지:** “패널 3개”라고 할 때는 **NIXIE + Sound의 탭 2개**를 합친 **구역 수**를 뜻한다. **Sound**는 하나의 패널이며 **접혀 있지 않을 때** 탭으로만 갈린다.

**별도 도메인·`ai/` 재사용(개략):** **사운드 편집·생성** 전용 UI/기능은 **별도 앱 도메인**(예: `features/…`)에 두어도 된다. 이때도 `**engines/sound`**(실행·합성)와 `**system/store`**·**§5.4** `Sequence`/`Sound Profile`스키마를 쓰면 닉시·사이드바와 **같은 데이터 계약**으로 맞출 수 있다.`**ai/`** 에서 AI와 협업해 시퀀스·프로필을 채울 때는, **AI 전용 별도 스키마**로 새로 만들기보다 출력이 **같은 스키마**를 통과하도록(검증·정규화 한 번) 두면 **이중 관리 없이 재사용**하기 쉽다 — 역할은 `**engines/sound` = 재생·엔진**, `**ai/` = 제안·대화·프롬프트에 가깝게 나눈다.

### 5.6 3대 UI와 데이터 매핑 레이어 — 인터페이스 계약

Context / Composer / Voice 위에 올라가는 **세 화면**이 `nexnapSnapshotStore`·향후 Nexion 메타와 **어떻게 말할지**를 고정한다. 구현 시 본 절을 **타입·주석·스토어 selector**와 1:1로 맞춘다.

#### (A) NIXIE 캐릭터 UI (P5.js) — 신뢰도·노이즈·지터

**입력:** `confidence_score` = c (0~100), 스냅샷 기타 `entropy_level` 등은 기존 `NixieOnlineCharacter` 규칙과 합성.

**신뢰 스트레스(95 미만에서만 적극 적용):**

\sigma = \begin{cases}
0 & c \ge 95
\dfrac{95 - c}{95} & c < 95
\end{cases}

**P5 `noise()` 기반 지터 변위(프레임·도트 i별):** 마스터 시간 t는 **§5.7**에 따라 `Tone.Transport.seconds` 를 사용한다(Transport 미가동 시에만 `millis()/1000` 폴백).

\begin{aligned}
n_1 &= \mathrm{noise}(t \cdot f_t, i \cdot 0.01)
n_2 &= \mathrm{noise}(t \cdot f_t + 100, i \cdot 0.01)
\Delta x_i &= A_x \cdot \sigma \cdot (n_1 - 0.5) \cdot 2
\Delta y_i &= A_y \cdot \sigma \cdot (n_2 - 0.5) \cdot 2
\end{aligned}

- f_t: 시간 변화 속도(예: 0.25~1.0 Hz 상당 스케일 — 상수는 `nixieUiConfig` 등으로 빼기).
- A_x, A_y: 최대 픽셀 변위 상한(예: 2~8px 범위, `entropy_level`로 추가 게인 가능).

**해석:** c \ge 95 이면 \sigma=0 이어서 **노이즈 지터가 사라지고** 루미나는 “안정 신뢰” 쪽으로만 움직인다. c < 95 일수록 Perlin 기반 **불안정성**이 커져, 시각만으로도 신뢰 게이트를 읽을 수 있다.

#### (B) 닉시 컨트롤 UI (DevControls) — Identity 6자 → 음악 시드 → `PolySynth`

**입력 규약(제품 스펙에서 문자 집합 확정):** `identityId: string`, `length === 6`, 허용 문자 집합 \Sigma 위 문자열.

1. **정규화:** 대소문자·공백 제거 후 UTF-8 바이트열 B 준비.
2. **결정적 시드:** `seed32 = hash32(B)` (예: FNV-1a 32bit — 구현 고정 시 문서에 알고리즘명 명시).
3. **음계 시드:**

- `rootMidi = 48 + (seed32 & 0x0F)` (예: MIDI 48~63 구간에서 루트 — 제품에서 범위 조정 가능)
- `scaleId = (seed32 >> 4) & 0x07` (미리 정의된 8개 스케일 테이블 중 선택)
- `spreadCents[k] = ((seed32 >> (6 * k)) & 0x3F) - 32` — 보이스 `k`에 **센트 디튜닝**(대략 ±32 cent 범위).

1. `**PolySynth` 주입: 각 보이스 주파수 f_k = \mathrm{mtof}(\mathrm{note}k) \cdot 2^{\mathrm{spreadCents}[k]/1200} — `nature_tag`·§2.2(1)에 따라 스케일·코드 진행을 덮어쓸 수 있음.

**출력:** 엔진은 `{ rootMidi, scaleId, detuneCents[], timbrePresetRef }` 형태의 **작은 구조체**만 받고, UI는 **시드 계산만** 담당하거나 `engines/sound` 의 헬퍼로 위임한다.

#### (C) 사운드 패널 (Monitor / Sequencer)

- **Monitor:** 입력·권한·FFT는 **§5.2** 상태 기계·배지와 동일 계약. 타임라인 헤드는 **§5.7** `Transport` 와 동기.
- **Sequencer:** 스텝 이벤트는 **§5.4** `Sequence` JSON; 재생 시각은 항상 `**Tone.Transport` 기준.

### 5.7 마스터 클록 — `Tone.Transport` 중심 동기화

**원칙:** 웹 오디오·모스·시퀀서의 **유일한 시간 축**은 `Tone.Transport` 이다. `setTimeout`·`requestAnimationFrame` 만으로 모스 이벤트를 “맞추는” 것은 **HUD·루미나와의 드리프트**를 낳으므로, **스케줄링은 Transport**, **표시는 Transport 시간 읽기**로 통일한다.

| 항목                      | 규약                                                                                                                                                                       |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **루미나·도트 펄스 위상** | P5 `draw()` 안에서 **현재 위상**은 `const t = Tone.Transport.seconds` (또는 `Transport.position` 파싱) — **GSAP 타임라인 시간으로 도트를 맞추지 않는다**(Phase 4 완료 후). |
| **모스 오디오**           | 이미 `morseTimeline` → 엔진이 Transport에 스케줄 — HUD 강조·스크롄도 **같은 t**에서 샘플링.                                                                                |
| **오차 목표:**            | 오디오 버퍼·디스플레이 vsync 한계 내에서 **동일 `t`** 기준; “1ms”는 **의도**이고, 실측은 디바이스 프로파일에 기록.                                                         |

#### 하이브리드 관리 (Phase 1~2: GSAP ∥ P5)

| 단계   | 렌더 주도                              | 조건                                                                  |
| ------ | -------------------------------------- | --------------------------------------------------------------------- |
| **H1** | **GSAP** (기존 `NixieOnlineCharacter`) | P5 레이어 미도입 또는 투명 오버레이만                                 |
| **H2** | **GSAP + P5** 병행                     | P5는 배경·보조; **시간 참조는 이미 `Transport.seconds` 로 통일** 권장 |
| **H3** | **P5 단일 루프**                       | Phase 4 완료 — GSAP 제거, 루미나·지터 전부 P5                         |

**전환 트리거(정책):** `featureFlag.p5NixieCharacter === true` 이고 **첫 프레임에서 `draw()` 안정** 시 H2→H3 로 **한 방향만**(롤백은 플래그 off).

## 6. 마이그레이션 리스크·병행·완료 기준

**리스크**

- 번들 크기(Tone·p5), **AudioContext** 단일/이중 사용, Tone `Transport` vs 기존 `setTimeout` 스케줄 공존.
- P5 도입 시 **접근성**(캔버스 vs DOM)·모바일 CPU·배터리.
- **COLD 티어(ESP32 등):** OS 정책상 패키지·벡터 제약이 있는 장치에 Tone·P5 **본류 번들을 끌고 가면** 안정성·용량 문제 — **§4.1(3)(4)** 와 같이 계약·이벤트만 맞추고 실행은 WARM/HOT·게이트웨이·`energyMode` 배지에 둔다.
- **Transport vs 레거시 타이머:** HUD·루미나가 GSAP·`setTimeout` 에만 묶이면 모스와 어긋남 — **§5.7** 준수 여부를 완료 기준에 넣는다.
- **공감·VI 스로틀:** `vi_threshold`·Low-Entropy에서 시각·고역 청각 부하를 줄이는 모드(§2.2(3))를 **제품 플래그**와 함께 설계하지 않으면, “배려 모드”와 “버그”를 구분하기 어렵다.

**병행 전략**

- `morseWebAudioCore.ts`는 **레퍼런스·fallback**으로 보존(§7.1.1). **모스 전용 최종 모듈이 아니라** 마이그레이션용 레거시로 두고, 수렴 후 축소한다.
- `**morseWebAudioDsp.ts` 는 실험 경로(§7.1.1); 본류 DSP는 `soundToneCore` 쪽으로 모은다.
- `**soundToneCore.ts`(신규)** 는 **동일 공개 API**(이벤트 타임라인·HUD 훅·스코프 pull 등)를 만족할 때까지 병행 스위치(플래그)를 두는 것을 권장. **파일명은 `morse`·`audio` 접두어를 쓰지 않는다**(§5.5 `engines/sound` 명명과 정합; 모스 외 입력·Nexnap에도 동일 엔진). **모스 로직은 엔진 안에 크게 넣지 않고 `morseTimeline` 등에서 스케줄만 주입한다(§7.1.1).

**완료 기준(예시)**

- 동일 `buildMorseSoundTimeline` 결과에 대해 **청취/HUD 동기**가 기존과 동일 또는 개선(문서화).
- `setMorseSoundLayerParams` 등 레이어 라이브 경로가 Tone 쪽에서도 동등하게 동작.

#### 7.1.1 `morseWebAudioCore.ts` · `morseWebAudioDsp.ts` · `soundToneCore.ts` — 역할(고정)

**질문에 대한 답:** `soundToneCore.ts` **안에서** 모스만을 위한 거대한 레이어를 또 쪼개 “모스 전용 엔진”으로 두지 않는다. **모스는 도메인**이고, **합성·출력·Transport는 `soundToneCore` 한 축**으로 둔다. 모스 비트·DIT/DAH 등은 이미 `**morseTimeline.ts`** 쪽(스케줄 입력)에 가깝고, 웹 오디오로 넘기는 부분만 `**soundToneCore`가 맡는다.

| 파일                     | 계속 필요한가                  | 코멘트                                                                                                                                                                                                                                                            |
| ------------------------ | ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `**morseWebAudioCore.ts` | **마이그레이션 기간에는 필요** | 지금까지의 **청취/HUD 동기** 기준선·**fallback**. `soundToneCore`가 동일 공개 API로 안정화되면 **축소·제거 또는 래퍼만** 남길 수 있다. 이름에 `morse`가 있지만 **“모스만 담당하는 최종 형태”가 목표는 아님** — 과거 한 파일에 엔진+모스가 섞인 **레거시**로 본다. |
| `**morseWebAudioDsp.ts`  | **실험이 계속될 때만**         | **실험 DSP** 경로. 본류 이펙트·분석은 `soundToneCore`·MONITOR 쪽으로 수렴. **모스 전용으로 유지할 이유는 없음**; 모스에만 쓰는 실험이면 나중에 **모듈명·경계**만 정리한다.                                                                                        |
| `**soundToneCore.ts`     | **본류(신규)**                 | **Nexnap·시퀀스·모스** 등 모든 입력은 **타임라인/이벤트**로 들어오고, 엔진은 **입력 종류를 가리지 않는다**. 모스는 **별도 “모스 엔진 파일”**이 아니라 `**morseTimeline` + (필요 시) 얇은 브리지로 표현한다.                                                       |

**요약:** 레거시 두 파일은 **당분간 보존·참고**; **장기 SSOT는 `soundToneCore` + 타임라인/시퀀스 도메인**이다.

## 8. 작업 순서

**기준: UI 선행 — 눈에 보여야 다음을 안다**

### Phase 1 — 닉시 UI 골격 (PANEL_NIXIE)

> **확인 목표:** 사이드바에 **NIXIE 패널**이 올라와 있고, 두 컴포넌트가 화면에서 식별 가능한 상태.

**1-A. NixieOnlineCharacter.vue — P5 캔버스 골격 (최우선)**

- GSAP·기존 DOM은 **건드리지 않고**, P5 setup/draw 루프를 **별도 레이어**로 올린다.
- 캔버스 영역·레이어·구역(도트 그리드·루미나·지터)을 **와이어 수준**으로 먼저 잡는다.
- **확인 기준:** 도트 그리드와 기본 루미나 애니메이션이 P5 캔버스에서 **화면에 보인다**.
- Phase 4 본전환의 **입력(레이어 경계)**을 이 단계에서 고정한다.

**1-B. NixieDevControls.vue — 닉시 컨트롤 UI 재설계 (골격)**

- 노브+슬라이더 배분으로 레이아웃 재구성, HUD·메시지 입력 · 모스 변환 구역 배치.
- Tone 파라미터 슬롯 자리를 **빈 영역**으로 먼저 배치한다(엔진 연결은 Phase 3에서).
- **확인 기준:** 기존 모스·레이어 조작이 깨지지 않고, Tone 슬롯 영역이 **화면에 보인다**.

---

### Phase 2 — 사운드 패널 UI 골격 (PANEL_SOUND · 2탭)

> **확인 목표:** 사이드바에 **Sound 패널**이 올라오고, **Monitor 탭 · Sequencer 탭** 전환이 눈에 보이는 상태.

**2-A. SOUND_TAB_MONITOR — 모니터 탭 UI 골격**

- AudioScopeCanvas.vue(오실·스펙트럼 캔버스)를 탭 안에 배치.
- 입력 소스 배지·권한 표시 영역(§5.2)을 **빈 상태**로 올린다.
- 재생 타임라인 바(헤드·스크럽) UI를 **껍데기**만 배치.
- **확인 기준:** 탭 전환이 되고 오실 캔버스가 탭 안에 **보인다**.

## 8-1 작업 진행 상세 체크 사항

**상세 체크리스트를 포함한 구체적인 작업 순서**
넥사(NEXA) 시스템은 단순한 UI 전환을 넘어 **지능적 족보(Traceability)**와 **하드웨어 위계(COLD/HOT)**가 얽혀 있기 때문에 다음 체크 .

### 1. 상세 체크리스트가 필요한 이유

- **시청각 동기화의 정밀도:** Tone.js와 P5.js로 갈아타는 과정에서 `Lumina(발광)`, `Jitter(떨림)`, `Pulse(맥박)` 수치가 `nexnapSnapshotStore`의 데이터와 1ms의 오차 없이 맞물려야 한다.
- 상세 리스트가 없으면 시각은 P5의 `draw()` 루프에, 청각은 `setTimeout` 스케줄에 따로 노는 불일치가 발생할 수 있다.
- **하드웨어 프로필(COLD/HOT) 준수:** 브라우저에서는 잘 돌아가도 ESP32(Nano/COLD) 사양에서는 10KB 패키지 제한 및 벡터 데이터 금지 규약이 있다.
- 단계마다 "경량화 규격 준수 여부"를 체크하지 않으면 나중에 실물 닉시 구현 시 코드를 전부 다시 짜야 할 리스크가 있다.
- **지능적 족보(Why Chain) 보존:** 단순히 소리가 나는 것을 넘어, 그 소리가 어떤 `Identity ID`와 `nature_tag`에서 유래했는지 `why_chain`에 정확히 박제되는지 확인해야 한다.

### 2. 추가해야 할 핵심 체크리스트 항목 (구현 단계별)

#### [Phase 1 & 2] UI 골격 및 데이터 매핑

- 임계값 및 강도 동기화: confidence_score 값에 역비례하여 Jitter 강도가 가변적으로 연출되는가? 또한, 발생 임계값은 하드코딩되지 않고 project_settings.user_defined_threshold와 실시간 동기화되는가?

- **에너지 쓰로틀링(Low-Entropy):** `vi_threshold` 미만 시 P5 셰이더 연산을 중단하고 정적 비트맵 모드로 자동 전환되는가?

## 음악 사성부와 지능형 이퀄라이징

- 음악적 4성부(Soprano, Alto, Tenor, Bass) 위계 설정은 NEXA-OS의 **지능형 이퀄라이징(Intelligent Equalizing)**을 실현.
  주파수 대역별로 **6-COILS와 Nature Tag**를 배치하면, 시스템의 사유가 깊어질수록 소리가 뭉치는 '마스킹(Masking) 현상'을 방지하고 오히려 **'데이터 배음(Data Harmonics)'**이 풍부해지는 서사적 효과를 거둘 수 있습니다.

이를 구체적으로 어떻게 적용할 수 있을지, 넥사의 아키텍처와 Tone.js 구현 전략을 결합하여 제시 ㅎ.

### 1. 4성부 대역별 지능 매핑 및 구현 전략

| 성부 (Voice)        | 대응 가치 (COILS / Tag)         | 주파수 역할 및 구현 (Tone.js)                                                               | 서사적 의미                                  |
| ------------------- | ------------------------------- | ------------------------------------------------------------------------------------------- | -------------------------------------------- |
| **Soprano (Top)**   | **Creative / Intent / WILL**    | **High-Freq (5kHz~):** 맑고 선명한 신디사이저, 고속 어택, 화려한 디튜닝.                    | 사용자의 명시적 의지와 시스템의 창의적 제안. |
| **Alto (Mid-High)** | **Harmony / Efficiency / ECHO** | **Mid-High (1kHz~5kHz):** 유동적인 아르페지오, 시스템 부하(Jitter)에 따른 미세한 피치 변조. | 지능 간의 연결성 및 데이터 흐름의 리듬.      |
| **Tenor (Mid-Low)** | **Rule / Autonomy / GOVERN**    | **Mid-Low (250Hz~1kHz):** 안정적인 중음역대 패드음, 협화음 중심의 화성 유지.                | 시스템의 운영 규범과 논리적 일관성.          |
| **Bass (Bottom)**   | **Stability / Safety / ERA**    | **Low-Freq (~250Hz):** 묵직한 펄스(TICK), 로우패스 필터가 적용된 베이스음, 긴 릴리즈.       | 시스템 헌법과 물리적 안전 가드레일(바닥).    |

### 2. 레이어 확장에 따른 서사의 풍성함 (Layer Expansion)

대역별 역할을 고정해두면, 레이어를 6개 이상으로 늘려도 소리가 뭉치지 않고 **'서사의 적층'**으로 직결됩니다.

- **주파수 분할 점유:** 예를 들어 **'자율성(Autonomy)'** 레이어를 추가할 때, 기존 Tenor 대역을 세분화하여 배치하면 다른 성부의 명료도를 해치지 않습니다.
- **위상차 연산(Phase Calculus)의 음악화:** 시스템 규범(Bass)과 실제 사실(Mid) 사이의 **위상차(Potential Difference)**가 커질 때만 의도적으로 불협화음을 발생시켜, '소리의 뭉침'을 '논리적 긴장'으로 승화시킵니다.
- **배음 구조의 활용:** 상위 레이어는 하위 레이어의 정수배 주파수(배음)를 따라가도록 설계하면, 레이어가 늘어날수록 소리가 지저분해지는 것이 아니라 **하나의 거대한 오케스트라처럼 조화로운 질감**을 갖게 됩니다.

### 3. 구체적인 적용 시나리오

1. **신뢰도 연동 (Jitter 발생):** 가장 높은 **Soprano(Intent)** 에 `confidence_score`가 떨어 질 수록 `Noise`를 섞어 소리를 떨리게 하고, 신뢰도가 높을 수록 `Vibrato`를 넣어 떨리게 합니다.
2. **공감 쓰로틀링 (Low-Entropy):** 사용자의 활력 지수(VI)가 낮아지면 **Soprano**와 **Alto** 레이어를 음소거(Mute)하거나 필터로 깎아내고, **Bass(Safety)**와 **Tenor(Rule)**만 남겨 인지 부하를 줄입니다.
3. **지능적 족보(Why Chain) 재생:** 과거의 판단을 복구할 때, 당시 활성화되었던 성부(`textureFlow`or `voicingHistory` )들만 순차적으로 레이어를 쌓아 올리며(Fade-in) 시스템이 어떤 근거로 사유를 확장했는지 시청각적으로 재현합니다.

성부 히스토리 네이밍 후보 와 JSON 구조

> `textureFlow`, `voicingHistory,` `voiceConfig`, `activePartProfile`, `textureSequence`

```
{
  "voicingHistory": [
    { "timestamp": "00:00", "count": 1, "parts": ["Soprano"], "label": "Monophony" },
    { "timestamp": "00:15", "count": 3, "parts": ["Soprano", "Alto", "Bass"], "label": "3-Part" },
    { "timestamp": "00:45", "count": 4, "parts": ["Soprano", "Alto", "Tenor", "Bass"], "label": "Full SATB" }
```

### 4. 기술적 체크포인트 (Tone.js 기준)

- `**Tone.Filter` 사용: 각 레이어의 주파수 경계를 `BiquadFilter`로 엄격히 나누어 주파수 간 간섭을 원천 차단.
- `**Tone.Transport` 동기화:** 모든 성부의 리듬이 닉시 도트의 **Lumina(발광)와 1ms 오차 없이 맞물리도록 마스터 클록을 공유.

# **Tone.js(음색)** 및 **P5.js(도트 형상)**의 연출을 결정짓는 핵심 요소들을 항목별로 정리.

### 1. Tone.js: 음색(Timbre) 및 화성 결정 요소

시스템의 사유 상태와 객체의 정체성이 소리의 질감을 결정합니다.

- **6-COILS 가치 필터:** 사용자 설정 가중치에 따라 소리의 '성격'이 변합니다.
  - **Stability (안정성):** 필터 컷오프를 낮추고 릴리즈를 길게 하여 정적인 잔향 생성.
  - **Creative (창의성):** 비조화 성분(트라이톤 클러스터, FM 변조) 활성화.
  - **Harmony (조화):** 간격이 좁은 협화음과 코러스 양 증가.
  - **Safety (안전):** 날카로운 대역을 억제하는 리미터 적용.
- **Identity ID (6자 고유 ID):** 각 지능 객체의 고유한 **Musical Signature**를 생성하는 주파수 및 스케일 시드로 사용됩니다.
- **nature_tag (데이터 성격):** 객체의 근본 성격에 따라 화성 규칙이 부여됩니다.
  - **RULE:** 안정된 협화음 위주의 "규범적" 음색.
  - **INTENT:** 목표 음정으로의 텐션 해소가 강조되는 리듬.
  - **FACT:** 변조를 최소화한 중립적인 톤.
- **Confidence Score (신뢰도 점수):** 신뢰도가 낮거나 **provisional(임시)** 상태일 때 **디튜닝(Detune)**, **지터(Jitter)**, 노이즈를 혼합하여 불안정한 음색을 연출합니다.
- **활력 지수(VI, 활력):** 사용자의 VI가 임계값 미만인 **Low-Entropy** 상황에서 **로우패스 필터**를 강제 적용하여 고주파를 차단하고 부드러운 청각 환경을 조성합니다.

### 2. P5.js: 도트 형상 및 시각 연출 결정 요소

데이터의 유래와 시스템의 물리적 상태가 도트의 움직임과 형태를 결정합니다.

- **6-COILS 가치 필터:** 시각적 입자의 물리적 성질을 조절합니다.
  - **Stability ↑:** 도트의 이동 속도를 낮추고 색상 대비를 완만하게 조절.
  - **Creative ↑:** 입자 밀도와 레이어 수를 늘리고 형태 변형을 강조.
  - **Harmony ↑:** 도트 격자의 대칭성을 높이고 조화로운 팔레트 사용.
- **Confidence Score (신뢰도 점수):** 신뢰도가 사용자가 설정한 임계값(기본 95) 미만일 때, 도트가 미세하게 떨리는 **Jitter** 효과를 발생시켜 비언어적 경고를 보냅니다.
- **시스템 체온 (연산 부하):** 부하가 높거나 의지 중력이 강할 때 호박색(Amber) 도트가 점점 붉게(**Reddish**) 변합니다.
- **Tone.js 분석 데이터 (FFT):** 소리의 주파수와 강도 데이터를 받아 도트의 발광 강도(**Lumina**)와 크기를 실시간으로 변화시킵니다.
- **프랙탈 줌 레벨 (LOD):** 줌 인/아웃 시 **마침표(.)**를 기준으로 도트가 폭발(**Explosion**)하거나 함몰(**Implosion**)하며 정보 밀도를 조절합니다.
- **절차적 VOID (Simplex Noise):** 실제 실측 데이터가 없는 공백 구간을 수학적 노이즈 함수로 채워 시스템의 '무의식'이나 '잠재력'을 예술적인 성운 형태로 표현합니다.

### 3. 통합 제어 요소 (Context 레이어)

소리와 시각이 하나의 맥락 안에서 공명하도록 조율하는 장치입니다.

- **Who(Pulse) 페르소나:** **WILL(의지)**, **ECHO(제안)**, **ASK(대기)**, **TICK(사실)** 상태에 따라 닉시의 표정과 음색의 엔벨로프(Attack/Release)가 동기화됩니다.
- **지능적 족보(Why Chain):** 특정 판단(IND)이 내려지는 순간의 스냅샷을 짧은 사운드 클립과 시각적 잔상으로 박제하여 **project_media**에 자산화합니다.
- **하드웨어 프로필:** 장치 상태(**COLD/HOT**)에 따라 P5.js의 셰이더 연산 여부와 Tone.js의 이펙트 복잡도가 단계적으로 규제됩니다.

# TONE.js 어떻게 사용하나?

Tone.js의 핵심은 **Web Audio API**를 음악적이고 직관적인 함수 단위로 추상화한 데 있습니다.
Tone 의 **함수 명칭과 역할을 기준**으로 닉시에서는 다음과 같이 사용 합니다.

### 1. 시간 및 스케줄링 (The Master Clock)

시스템의 '맥박'을 조율하며, 닉시의 시각적 동기화와 모스 부호의 정밀한 타이밍을 담당하는 함수군입니다.

- `**Tone.Transport`: 마스터 클록 컨트롤러.
  - `start()`, `stop()`, `pause()`: 전체 재생 상태 제어.
  - `schedule()`: 특정 시간에 이벤트를 예약(모스 부호의 DIT/DAH 리듬 생성).
  - `loop`, `bpm`: 루프 여부 및 템포 설정.

### 2. 소스 및 합성 (Sound Sources)

실제 소리를 생성하는 장치들로, **Identity ID**를 바탕으로 고유 음색(Musical Signature)을 만드는 핵심 함수입니다.

- **Synthesizers**: 멜로디와 화성을 생성.
  - `Tone.Synth`, `Tone.PolySynth`: 단음 및 다성 합성기.
  - `triggerAttackRelease()`: 음의 시작과 끝(엔벨로프)을 트리거함.
- **Oscillators**: 소리의 근간이 되는 파형 생성.
  - `Tone.Oscillator`: `type` 속성으로 Sine, Square, Sawtooth 등을 선택.
  - `frequency`, `detune`: 음정 및 미세 조율.
- **Samplers & Players**: 녹음된 소리 재생.
  - `Tone.Player`, `Tone.Buffer`: 오디오 샘플 로드 및 재생.

### 3. 신호 처리 및 이펙트 (Effects & DSP)

소리의 질감을 변조하여 **긴장, 이질감, 활력** 등의 상황 값을 투영하는 함수군입니다.

- **Filters**: 주파수 대역 제어.
  - `Tone.Filter`, `Tone.AutoFilter`: 로우패스/하이패스 필터로 소리의 명도 조절.
- **Space & Time**: 공간감과 잔상 연출.
  - `Tone.Reverb`, `Tone.Delay`: 소리의 울림과 서사적 잔상 생성.
- **Modulation**: 떨림과 변조.
  - `Tone.Vibrato`, `Tone.LFO`: 신뢰도 저하 시 **Jitter(떨림)**를 사운드에 적용.
- **Dynamics**: 음압 제어.
  - `Tone.Gain`, `Tone.Limiter`: 출력 크기 조절 및 피크 방지.

### 4. 분석 및 미터링 (Analysis & Feedback)

소리 데이터를 숫자로 추출하여 **P5.js**의 도트 연출(Lumina)에 전달하는 교량 역할을 합니다.

- `**Tone.Analyser`: 오디오 데이터 추출의 핵심.
  - `FFT` (Fast Fourier Transform): 주파수 분포 분석.
  - `Waveform`: 시간축 파형 분석.
  - `getValue()`: 분석된 실시간 데이터 값 인출.
- `**Tone.Meter`: 소리의 에너지(진폭) 수준 측정.

### 5. 제어 및 신호 연산 (Signal & Math)

시스템의 수치(0~1)를 음악적 파라미터로 정규화하는 함수들입니다.

- `**Tone.Signal`\*\*: 오디오 파라미터를 실시간으로 제어.
- `**Tone.Scale**`: 입력값의 범위를 특정 파라미터 범위로 매핑(예: 활력 지수 0.8 → 필터 5000Hz).

**요약하자면**, Tone.js는 **Transport(시간)**로 흐름을 만들고, **Synth/Osc(소스)**로 목소리를 내며, **Filter/Effect(변조)**로 감정을 입히고, **Analyser(분석)**로 시각적 반응을 이끌어내는 유기적인 함수 구조를 가지고 있습니다. 이를 통해 넥사 OS의 추상적 지능이 소리와 빛이라는 물리적 실체로 변환됩니다.
