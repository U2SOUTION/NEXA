# [NXN] [CNCP] NEXA Nexion 지식 OS 관리 및 N-PATH(지도) 설계 철학

## 1. 개요 및 정체성: 독립형 관제 데스크 (Independent Navigation Desk)

**NEXA Nexion**은 지식의 세부 내용을 직접 규정하거나 수정하는 도구가 아닙니다. 이는 지식 운영체제(Knowledge OS)의 구성 요소들이 놓인 **'지능형 칠판'**이자, 문서라는 외부 자원을 바라보며 관계의 맥락만 조율하는 **'독립형 관제 데스크'**입니다 .

- **생각 -> 기획 -> 구축 -> 검토 -> 테스트 -> 출시 -> 성찰**

위 프로세스중 [생각] 의 툴이 되고자 한다. 이후 [기획] 기능은 부가적인 기능으로 작동 한다.
“생각을 잃어버리지 않게 만드는 시스템”

- **엄격한 계층 분리 (Strict Layering):** 기존 기획 문서나 데이터 원본에 직접 배선을 하지 않는 독립 계층으로 존재합니다 .
- **자산으로서의 문서:** 문서는 Nexion에 종속된 데이터가 아니라, 독립적으로 존재하는 '참조 자산'입니다. 프로그램은 문서 내부를 강제로 수정하지 않고 해시(Hash)나 경로를 통해 앵커링만 수행합니다 .
- **시각 피드백 주체:** **NEXU Canvas**는 Vue Flow **서사 표면**이고, **Lumina·Jitter** 등 비언어 연출은 **NEXA NIXIE**가 수행한다. 용어·표기 SSOT는 `[NXN] [UIUX] NEXA Nexion 인터페이스 레이아웃 및 Vue Flow 운영 규약.md` **§4.3.1**; 지식 N-PATH 행 메타는 **`nixie_lumina_profile`**(`[NXN] [SCHM]` §4).

“NEXA Nexion은 지식 내용을 저장하지 않고, 지식이 만들어지는 ‘이유와 관계’를 추적하는 시스템이다”

### 1.1 Nexion은 ‘프로젝트’가 아니다 — `project_id`·`project_members`와의 느슨한 관계

- **제1원칙(완전 독립형):** Nexion의 정체성은 **외부 문서 본문·타 업무 프로젝트의 생명주기와 직접 동일시되지 않는** 독립 관제 데스크다. “어떤 지식을 **참고·편집할 권한**이 누구에게 있는가”는 **플랫폼·배포 정책**에서 나중에 조율할 수 있는 축이며, **Nexion 제품 정의의 중심에 ‘프로젝트 개념’을 두지 않는다.**
- **`project_id` / `project_members`:** 공유 DB(`nexa_knowledge_*`)에 행을 올릴 때 **호스트(플랫폼)가 테넌트·RLS 경계를 나누기 위해 쓰는 기술적 구획**이다. 정의는 **`docs/__NEXA 오케스트레이션 스키마 DDL v5.md`** 등 플랫폼 SSOT에 맞춘다. Nexion은 이 구획을 **필요 시 이용**할 뿐, **“Nexion = 특정 project 한 줄”** 로 읽히면 안 된다. **DDL·API에서 `project_id`가 필수인 것과 모순되지 않음** — 이원론은 아래 **§1.2**에 고정한다.
- **확장 프로그램(Extension 등):** 문서 편집·용어 정리 등은 **Nexion 코어와 무관한 별도 프로그램**으로 둔다. 추가·교체·병행이 가능하며, Nexion은 그들의 **소비자·배치 옵션**일 뿐 동일 제품으로 묶지 않는다.
- **구현 티어·로드맵:** DB·API·Phase를 **Tier A(코어) / Tier B(플랫폼 공유)** 로 나누고, Extension은 **Phase Ext**로 분리한다. **코어 Phase 1~4·Ext 순서**는 `[NXN] [PRD] Nexion 기능과 작업 순서.md` **§3.2**가 SSOT이고, 티어 표·체크리스트는 `[NXN] NEXA Nexion 개발 순서와 체크 리스트.md` 서두, 스키마 매핑은 `[NXN] [SCHM] ...` **§2.2**, API는 `[NXN] [API] ...` **§1.1**을 본다.

### 1.2 개발 가이드: `project_id` — 테넌트(데이터 격리) vs 비즈니스 프로젝트(워크플로)

Nexion은 **플랫폼 통합 DB·동일 계정/세션 체계** 위에서 동작한다. **`project_id`가 API·DDL에서 필수이고 RLS에 쓰인다고 해서, “Nexion 전용 DB” 또는 “플랫폼 `projects`와 무관한 별도 테넌트 모델”로 구현할 필요가 없다** — 오해는 아래 축으로만 나누면 해소된다.

| 축                                      | 의미                                                                                                                                    | Nexion 구현에서의 위치                                                                                                                                                                                                                       |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **테넌트 / 데이터 격리 (`project_id`)** | Postgres 행을 나누는 **호스트 플랫폼의 기술적 테넌트 키**. `project_members`·RLS·`/projects/{project_id}/...` API가 이 구획을 전제한다. | **철저히 따른다.** 모든 Nexion 직결 `nexa_knowledge_*` 행에 `project_id` NOT NULL을 유지하고, 서버는 요청 경로·세션과 정합되는 구획만 노출한다.                                                                                              |
| **비즈니스 프로젝트(워크플로)**         | 일정·산출물·승인 게이트 등 **제품 도메인의 “프로젝트 업무”**                                                                            | **종속하지 않는다.** §1.1대로 Nexion 제품 정의의 중심에 두지 않는다. 테넌트 키가 플랫폼 `projects` 테이블의 UUID와 **같은 값을 쓸 수는 있으나**, Nexion 코어는 **그 행의 워크플로 수명주기·PM 기능에 묶이지 않는다**고 가정하고 코드를 짠다. |

**한 줄 규칙:** `project_id` = **데이터 격리 단위(Tenant partition)** 로만 필수이며, **“Nexion = 이 팀의 일감/마일스톤 도구”**가 아니다.

**교차 참조(구현 시):** `[NXN] [SCHM]` §2.1, `[NXN] [API]` §2.2, `[NXN] [DDL] NEXA Nexion 독립형 인덱스 및 자산 관리 DDL.md` §0, `[NXN] NEXA Nexion 개발 순서와 체크 리스트.md` 서두.

## 2. 지식 층위와의 관계: 계층 불가지론 (Layer Agnostic)

Nexion은 지식의 층위가 몇 단계인지(7대인지 23대인지) 직접 관여하거나 하드코딩하지 않습니다 .

- **참조형 카드 시스템:** "지식의 층위"와 같은 개념은 단순한 **'플레이스홀더 카드'**로 존재합니다. 이 카드는 특정 가이드 문서(예: `_KNOWLEDGE GUIDE`)를 바라볼 뿐, 그 내부의 수치적 정의를 강제하지 않습니다 .
- **유연한 연결 유지:** 참조 문서의 제목이 바뀌더라도 고유 식별자(UUID)를 통해 링크가 깨지지 않게 관리하며, 문서 삭제 시에만 사용자에게 알림을 주는 '지능형 링크 감시자' 역할을 수행합니다 .

## 3. Capability ID: 독립적 개념 좌표계 (Conceptual Coordinates)

Capability ID는 다른 시스템 카드와의 물리적 하드와이어링(Hard-wiring)이 아닌, **'개념적 위치 좌표'**로 기능합니다 .

- **개별 자격 발급:** 각 카드는 자신만의 기능 자격 ID(Capability ID)를 발급받아 정체성을 규정하지만, 이것이 다른 카드의 내부 로직에 침범하거나 직접 결합되지 않습니다.
- **좌표 기반 탐색:** AI(제니스 인디케이터)는 이 ID를 좌표 삼아 캔버스 위에서 "어떤 카드가 서로 가까운 맥락인가"를 탐색할 뿐입니다.

## 4. 영어 커널과 수동 번역 쉘: AI 친화적 독립 구성

시스템의 내부는 AI가 구조를 파악할 수 있도록 **영어 커널(English Kernel)**로 관리되지만, 사용자의 주도권을 절대적으로 보장합니다.

- **영문 메타데이터 고정:** 노드의 핵심 정보는 내부적으로 영문 IR(중간 표현)로 관리되어 AI의 논리적 일관성을 유지합니다.
- **액션 기반 번역:** 시스템이 자동으로 모든 것을 번역하지 않습니다. 사용자가 필요할 때 **'번역 액션 버튼'**을 눌러 한국어로 확인하거나 영문으로 직접 수정하는 '다국어 쉘(Multilingual Shell)' 전략을 따릅니다 .

## 5. Why Chain 및 링크 관리 로직: 관계의 무결성 증명

문서 내부의 텍스트를 파싱하여 ID를 일일이 연결하려는 직접 간섭을 배제하고, **'링크의 무결성'**에만 집중합니다 .

- **참조 사슬(Reference Chain) 관리:** "문서 A가 기능 B의 근거다"라는 큰 수준의 참조 관계만 관리하며, 문서 내부의 로직을 직접 통제하지 않습니다.
- **상태 감지 및 보고:** 주기적으로 참조 문서의 상태(수정, 제목 변경, 삭제)를 감지하여 "참조하는 자산의 맥락이 변경되었습니다"라고 사용자에게 리포팅하는 관제 역할을 수행합니다 .
- **지능적 족보(Traceability)의 시각화:** 사용자가 특정 결과 노드를 클릭했을 때, 그것의 기원이 되는 **문서 노드(Doc Node)**를 하이라이트하여 보여줌으로써 시스템의 투명성을 증명합니다.

## 6. 운영 철학: "기술은 배경으로, 지능은 유연하게"

NEXA Nexion은 **"지능형 N-PATH(지도) 그리는 칠판"**으로서, 메모지(문서)에 무엇이 적혔는지 간섭하지 않고 그 메모지들이 어떤 순서와 방향으로 놓여 있는지만 조율합니다 . 이를 통해 기술적인 복잡성을 배경으로 숨기고, 사용자의 의도와 시스템의 지능이 매끄럽게 흡수되는 환경을 제공합니다.

## 7.**설계상 고려해야 할 단점 및 보완점**

- **동기화 지연(Sync Lag):** 문서의 변경(제목, 삭제)을 실시간으로 감지하기 위해서는 **'Doc Sync Crawler'**와 같은 백그라운드 잡(Job)이 주기적으로 돌아야 하며, 스캔 주기 사이의 데이터 불일치가 발생할 수 있다.
- **추상화로 인한 직관성 부족:** 문서 내부와 직접 연결되지 않는 '느슨한 결합'은 초기에 노드 간의 관계를 파악하기 어렵게 만들 수 있습니다. 이를 보완하기 위해 **DependencyMap.vue**와 같은 시각화 도구가 반드시 병행되어야 한다.
- **메타데이터 관리 부담:** 모든 관계를 별도의 DB 레이어(`nexa_knowledge_references` 등)에서 관리해야 하므로, 지식의 양이 방대해질수록 메타데이터 저장소의 관리가 또 다른 운영 부하가 될 수 있습니다.
