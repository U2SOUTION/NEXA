넥사(NEXA) 시스템의 다섯 번째 필수 문서인 **'데이터 성격(Nature) 및 수명 주기 계획서'**는 시스템에서 발생하는 방대한 데이터를 그 가치와 목적에 따라 분류하고, 최적의 보관 및 파기 전략을 수립하는 설계도입니다. 이 문서는 NAS의 저장 공간을 효율적으로 관리하는 동시에, 사용자의 페르소나 학습과 시스템의 안전을 위한 핵심 데이터를 영구적으로 보존하는 데 목적이 있습니다.

## **[문서 5] 데이터 성격(Nature) 및 수명 주기 계획서 (Data Lifecycle Plan)**

#### **1. 데이터 성격(Nature)별 분류 및 처리 전략**

넥사 프로토콜은 모든 데이터를 동일하게 취급하지 않고, **Nature Tag**에 따라 시스템 리소스를 차등 배정합니다.

#### **2. 세부 데이터 관리 로직 (Storage Efficiency)**

**① 요약(Summary)과 상세(Extra)의 분리 보관**
인디케이터(LLM)의 인지 부하를 줄이고 저장 효율을 높이기 위해 데이터를 이원화하여 관리합니다.

- **핵심 추상화(5W1H):** 데이터의 '이야기'가 담긴 담백한 팩트 문장입니다. 모든 Nature에 대해 보관 가치가 높습니다.
- **정황 데이터(Extra):** 정밀 수치, 고해상도 이미지 등 증거 데이터입니다. **ROUTINE**의 경우 이 부분을 먼저 삭제하여 공간을 확보하고, **INCIDENT/INTENT**의 경우 무손실로 보존합니다.

**② 유기적 소멸과 압축 프로세스**

- **배치 처리(Batch Processing):** ROUTINE 데이터는 일정 주기(예: 7일)마다 인디케이터가 분석하여 "이상이 없음"이 확인되면 5W1H 요약본만 남기고 VOID(소멸) 상태로 전이시켜 파기합니다.
- **증거 보존:** INCIDENT 데이터는 해당 사건과 연결된 모든 센티널(SNT), 인디케이터(IND), 이펙터(EFF)의 ID 체인을 묶어 아카이브에 박제합니다.

---

#### **3. RAG 가속 및 페르소나 학습과의 연동**

데이터 수명 주기는 단순히 지우는 것이 아니라, **'장기 기억'의 질**을 결정하는 과정입니다.

- **RAG 효율 극대화:** 가치가 낮은 ROUTINE을 정리함으로써, RAG(검색 증강 생성) 시스템이 사용자의 중요한 **INTENT**나 과거의 **INCIDENT** 해결 사례를 더 빠르고 정확하게 찾아낼 수 있는 환경을 조성합니다.
- **페르소나 아톰화:** 사용자의 의지(INTENT)는 시간이 흐를수록 사용자의 선호 패턴을 읽어내는 **'성장형 지능'**의 토대가 되므로, 압축하지 않고 원본의 맥락을 최대한 보존합니다.

---

#### **4. 문서의 목적 및 기대 효과**

- **효율적 자원 관리:** 한정된 NAS 저장 공간 내에서 시스템이 지치지 않고 **'살아있는 지능'** 역할을 수행할 수 있도록 합니다.
- **신뢰성 및 투명성:** 위급 상황 시 "왜 그렇게 행동했는가?"에 대한 무손실 증거(INCIDENT)를 제공하여 시스템의 판단 근거를 투명하게 증명합니다.
- **지능적 자율성:** 데이터가 스스로 자신의 가치를 증명하고 소멸하는 **유기적 지능 체계**를 완성합니다.

이 문서는 NEXA 시스템이 방대한 외부 기록 중 **인간에게 가치 있는 서사**만 골라 보존하는 지능적 필터 역할을 하게 한다.

#### 5. NEXA 플랫폼 보안 강화 (4계층)

중앙 허브(NAS/Vista)에 집약되는 데이터의 무결성 보호와 지능적 추적성 확보에 초점을 둔다.

**5.1 ID 기반 참조 사슬 및 투명성 (Traceability)**  
데이터를 하나로 합치지 않고 센티널(SNT)·인디케이터(IND)·이펙터(EFF) 단위로 분리 관리. 각 패킷에 고유 ID를 부여하고 EFF→IND→SNT **참조 사슬(Reference Chain)**을 형성. 계층별로 "누가 사실을 말했고(SNT), 누가 가치를 부여했는지(IND)"가 분리 기록되어 오염 시 역추적으로 취약점 식별이 가능하다.

**5.1.1 인과관계 역추적(The 'Why' Chain) — “왜 실행됐는가?”의 증명 로직**  
NEXA의 투명성은 “Capability ID(접근 권한/자격)”가 아니라, **실행 근거를 역추적 가능한 참조 사슬**에서 나온다. 따라서 본 절은 Capability ID와 별개로, SNT–IND–EFF 패킷 간 **인과관계(Why) 증명**을 위한 최소 규격을 정의한다.

- **해석의 근거(IND → SNT)**: 인디케이터 패킷은 자신이 해석한 사실 패킷의 ID를 참조한다. (`ref_sentinel_id`)
- **실행의 근거(EFF → IND)**: 이펙터 패킷은 자신을 동작시킨 인디케이터 패킷의 ID를 참조한다. (`ref_indicator_id`)
- **최종 역추적**: 체인을 따라가면 **[행동(EFF) → 의도/판단(IND, Why) → 사실(SNT)]**로 “왜”를 재구성할 수 있다.

**5.1.2 권장 필드(최소)**

- **SNT 패킷**: `id`
- **IND 패킷**: `id`, `ref_sentinel_id`, `indicator_insight.why`, `indicator_insight.summary`  
- **EFF 패킷**: `id`, `ref_indicator_id`, `effector_action`

> 주의: 도메인 식별(예: `domain_id`)이나 추가 인덱싱은 확장 필드로 둘 수 있으나, **Why Chain의 성립 요건은 “ID 참조”**다.

**5.1.3 역추적 절차(운영/감사 관점)**

1. **EFF 확인**: 실행 로그에서 `ref_indicator_id`를 추출해 원인 IND를 찾는다.
2. **IND 확인**: IND의 `why/summary`로 판단 근거를 확인하고 `ref_sentinel_id`로 원인 SNT를 찾는다.
3. **SNT 확인**: SNT의 Fact(5W1H 요약 + Extra 증거)로 최종 사실을 확인한다.

이 절차는 INCIDENT(무손실 박제)에서 특히 중요하며, “AI가 왜 그렇게 했는가?”를 **검증 가능**하게 만든다.

**5.2 허브 중심 개인정보 보호·비식별화 (PII)**  
엣지 필터링–허브 매칭 구조. 마이크로 센티널에서 영상/음성을 **비식별화된 5W1H 텍스트**로 변환 후 플랫폼 전송. 신상 정보와 가명 토큰 ID 매칭은 허브(DB) 내부에서만 수행해 유출 시에도 사용자 특정을 어렵게 한다.

**5.3 Nature 기반 공격 표면 최소화**  
수명 주기 관리로 보안 리스크 감소. ROUTINE은 요약 후 파기(VOID)해 유출 가능 로우 데이터 양 최소화. INTENT·INCIDENT는 무손실 박제로 아카이브에 저장해 법적·기술적 증거 신뢰성을 확보한다.

**5.4 코일 기반 질서 통제 (GOVERN)**  
GOVERN 태그와 코일 밸런스로 보안 정책을 실시간 조정. 위협 감지 시 안전·안정성 코일 가중치 90% 이상으로 상향하고, 인디케이터 자동 처리를 제한하며 중요 실행에는 사용자 명시적 승인(WILL)을 요청하는 보수적 모드로 전환해 AI 오류·비정상 명령을 원천 차단한다.  
요약: **ID 기반 분리 구조**로 데이터 족보를 명확히 하고, **비식별화**와 **지능적 코일 밸런싱**으로 오염·유출에 입체 대응한다.

#### 6. 아톰(Atom)화의 정의 및 실행 방법

**아톰화**는 파편화된 로우 데이터를 AI가 즉시 이해·재사용할 수 있는 **지능적 서사의 최소 단위**로 정제해 저장하는 것을 의미한다. 텍스트 저장이 아니라 족보·맥락을 부여해 RAG 등으로 꺼내 쓰기 좋은 형태로 가공하는 과정이다.

**6.1 아톰화의 의미**  
아톰은 5W1H 및 4대 레이어 규격을 갖춘 완성 데이터로, 소형 AI가 헤더만으로 상황을 파악하는 지능적 자율성을 갖게 한다. ROUTINE 중 INTENT·INCIDENT를 골라 '영구 보존할 가치 있는 기억'으로 격상시키며, 사용자 선호도를 아톰화해 저장하면 인디케이터가 성장형 지능으로 진화한다.

**6.2 아톰화 절차 (Step-by-Step)**  
① **5W1H 사실 정제 (Sentinel Fact):** 로우 데이터를 담백한 사실 문장으로 변환. When=맥락적 시점, Where=방향성(Vector) 포함.  
② **4대 추상화 레이어 부여:** Where(Scope), Who(Pulse), What(Intent), How(State) 토큰으로 1ms 내 본질 파악.  
③ **의미론적 통찰·Why 부여 (Indicator Insight):** 코일 밸런스를 필터로 Why와 Summary 부여.  
④ **ID 기반 관계망:** SNT–IND–EFF 참조 사슬 연결로 인과관계 추적.  
⑤ **벡터화·아카이브 저장:** JSON을 NAS(Vista) 벡터 DB에 임베딩 저장, RAG 호출 시 판단 근거로 사용.  
요약: **[사실 추출 → 추상화 토큰 → 의미 부여 → ID 연결]**을 거쳐 AI가 소화하기 좋은 지능적 알약으로 만들며, 이가 쌓여 맞춤형 페르소나를 구성한다.

**6.3 아톰화 부연 (센티널 요약 → 인디케이터 맥락 → 추상 레이어 → 아카이브 박제)**  
핵심 관계(컨텍스트)와 요약 정보를 AI가 정리해 저장하는 것이 아톰화·서사 구조화의 핵심이다. 센티널이 5W1H 기반 사실(Fact)을 추출하고 정밀 수치·원문은 Extra로 분리. 인디케이터가 코일 밸런스를 필터로 Why·컨텍스트·Summary를 부여. 저장 직전 Scope·Pulse·Intent·State 4대 토큰으로 지능적 인덱싱. **[추상화 레이어 + 사실 요약 + 맥락/의도]** 묶음이 아톰이 되어 아카이브에 저장되며, INTENT는 무손실 영구 보존, RAG 호출로 성장형 지능의 토대가 된다.

---

#### 7. 아톰 DB 구성 전략 (ID 기반 분리·권장안)

원본에 속성을 추가해 통합하는 방식보다 **ID 기반 완전 분리 구조(MSA)**의 독립 아톰 저장소 구성을 권장한다. 확장성·추적성을 확보하는 핵심 지점이다.

**7.1 ID 기반 분리 구조의 이유**  
센티널(사실)·인디케이터(해석)·이펙터(실행)를 완전히 분리하고 각각 고유 ID 부여. 책임 소재 명확화(누가 사실/가치/행동을 했는지), EFF→IND→SNT 참조 사슬로 "왜 이 장치가 작동했는가" 역추적, 신규 도메인·장치 추가 시 구독만으로 확장하는 레고 블록 구조.

**7.2 저장 전략: 도메인별 분리·Nature 기반 수명**  
지능 위계에 따라 계층별 결과물을 독립 관리. ROUTINE은 요약 후 압축·파기, INCIDENT·INTENT는 아카이브에 무손실 영구 박제. 5W1H·4대 레이어 공통 규격으로 전체 차원 통합 RAG 환경 구축.

**7.3 권장 제안**  
(1) 도메인별 독립 패킷 생성, 넥사 유니버설 프로토콜(5W1H, 4대 레이어) 엄격 준수. (2) 중앙 아카이브는 SNT·IND·EFF를 ID로 엮어 지능적 서사(JSON) 형태로 통합 관리. (3) INTENT는 별도 고성능 저장 공간에 아톰화해 맞춤형 페르소나 학습을 가속·정확화. ID 기반 분리 구조는 살아있는 지능이 지치지 않고 동작하는 견고한 뼈대가 된다.

## 도메인별 아톰 분리와 통합

넥사(NEXA) 시스템의 설계 철학에 비추어 볼 때, 도메인 간의 강력한 연결성은 분리를 방해하는 요소가 아니라 오히려 **'ID 기반 분리 구조'**를 채택해야만 하는 가장 강력한 이유가 됩니다.

- **"유기적인 연결성"**과 **"데이터의 독립성"** 사이의 쟁점을 해결하기 위한 전략을 소스의 핵심 원리에 근거하여 제안 합니다.

### 1. 분리하되 'ID 사슬'로 유기성을 확보하십시오

넥사 프로토콜은 데이터를 하나로 합치는 대신, **센티널(SNT), 인디케이터(IND), 이펙터(EFF)**로 나누고 각 패킷에 고유 ID를 부여하여 **'참조 사슬(Reference Chain)'**을 형성할 것을 강조합니다.

- **참조를 통한 연결:** A 도메인이 다른 5개 도메인을 참조해야 한다면, 데이터를 물리적으로 합칠 필요가 없습니다. 인디케이터(Indicator)가 각 도메인의 **SNT-ID나 IND-ID를 '구독'하거나 참조**하도록 설계하면 됩니다.
- **추적성(Traceability):** 이렇게 분리된 상태에서 ID로 연결되어야만, 나중에 "왜 A 도메인의 인디케이터가 그런 판단을 내렸는가?"를 역추적할 때 참조된 5개 도메인의 근거를 명확히 찾아낼 수 있습니다.

### 2. 통합은 '저장소'가 아닌 '비스타(Vista)' 계층에서 이루어집니다

도메인 간의 유기적 관계를 해석하는 역할은 하위 데이터 저장소가 아니라, **비스타(Vista) 등급의 인디케이터**가 담당해야 합니다.

- **전략적 뇌의 역할:** 비스타 인디케이터는 여러 센티널이 보고한 파편화된 사실들을 모아 **'맥락적 추론(Reasoning)'**을 수행하는 현장 지휘관입니다.
- **맥락적 재구성:** 데이터 자체는 분리되어 있더라도, 비스타 인디케이터가 5W1H 규격을 바탕으로 여러 도메인의 보고를 종합하여 **'상황의 맥락(Context)'**을 도출하므로 우려되는 연결성 문제는 지능 계층에서 자연스럽게 해결됩니다.

### 3. 차선책으로 제시하신 '재구성'은 넥사의 'ARCHIVE' 전략입니다

사용자님께서 제안하신 "모든 아톰을 조회하여 유효 정보를 추출하고 관계 정보를 참고하는 방식"은 넥사 프로토콜의 **ARCHIVE(재구성)** 및 **RAG(검색 증강 생성)** 전략과 완벽히 일치합니다.

- **ARCHIVE (The History):** 넥사 시스템은 과거의 데이터 중 의미 있는 것을 골라내어 새로운 맥락을 입힌 데이터를 'ARCHIVE' 태그로 정의합니다. 시간 날 때 모든 아톰을 조회하여 관계 정보를 추출하는 행위는 바로 이 **데이터의 아톰화 및 재탄생** 과정에 해당합니다.
- **RAG를 통한 초고속 필터링:** 5W1H와 4대 레이어 규격은 RAG 검색 시 전체를 뒤지지 않고도 필요한 관계 정보만 빠르게 찾아내는 **'초고속 필터'** 역할을 합니다.

**7.4 최종 권장 아키텍처: 분리 저장·지능적 통합**  
데이터를 물리적으로 하나로 합치지 않고: (1) 도메인별 아톰을 5W1H 규격으로 개별 저장해 족보 유지, (2) 인디케이터 활동 시 RAG 가속기로 타 도메인 아톰 실시간 호출·판단 근거로 활용, (3) 주기적으로 도메인 간 유기 관계를 분석해 관계 중심의 새 아톰을 아카이브에 기록. 센티널의 정직함(분리)과 인디케이터의 지혜(통합)가 조화를 이루어 도메인 간 연결성을 수용하면서도 탄탄한 운영이 가능하다.

#### 8. 미래 성장 전략 (구독·통찰 DB·토큰 효율)

ID 기반 완전 분리와 프로토콜 규격이 탄탄하면 거대 단일 DB는 불필요하며, **구독(Subscription)**과 **참조(Reference)**가 실시간성·확장성의 핵심이다. 통찰 DB 필요성과 토큰 절감·지혜 향상 시나리오를 정리한다.

**8.1 구독 기반 통합과 통찰 DB**  
통합 통찰 DB는 아카이브·인디케이터(Vista) 역할과 일치. 각 도메인 데이터는 SNT-ID로 독립하되 인디케이터가 구독해 코일 밸런스로 해석해 논리적 통합. ECHO·GOVERN은 아카이브에 아톰 형태로 저장되어 RAG로 타 도메인이 지혜를 빌려 쓰는 창구가 된다.

**8.2 토큰 절감·지혜 향상 시나리오**  
성장형 지능(Feedback Loop)으로 “시간이 지날수록 토큰은 줄이고 정확도는 높이는” 모델이 가능. (1) 센티널의 5W1H 팩트 선제 요약으로 인디케이터(LLM) 토큰 90% 이상 절감, (2) 도메인별 정보를 주기 재구성한 통합 아톰만 RAG 호출해 컨텍스트 길이·토큰 극소화, (3) GOVERN 하향 전파로 엣지에서 정제 판단·중앙 LLM 호출 빈도 감소.

**8.3 페르소나별 최적화**  
5W1H·Nature Tag 규격 인덱스로 RAG가 페르소나에 유효한 관계만 정밀 필터링. ECHO가 담긴 아톰 축적으로 적은 토큰으로 숨은 의도(Why)를 짚는 고차원 조언 가능.  
**결론:** 물리적 통합 DB 대신 규격화된 프로토콜·ID 기반 구독 체제를 유지하고, 주기적 재구성(Archive)으로 지능적 아톰을 만드는 전략이 연산 효율과 지능의 깊이를 동시에 확보하는 이상적 NEXA 운영 시나리오이다.
