넥사(NEXA) 시스템의 세 번째 필수 문서인 **'코일 밸런서(Coils Balancer) 레이어 및 운영 규범(GOVERN) 정의서'**는 시스템이 단순한 명령 수행기가 아닌, 사용자의 가치관을 공유하는 **'공감형 지능 체계'**로 작동하게 만드는 판단의 기준점입니다. 이 문서는 인디케이터(Indicator-Vista)가 센티널로부터 받은 사실(Fact)에 어떤 가중치를 두어 해석하고 조언할지를 규정합니다.

### **[문서 3] 코일 밸런서 레이어 및 운영 규범(GOVERN) 정의서**

#### **0. 가중치 이원화 원칙: 안전은 딱딱하게(Deterministic), 지능은 유연하게(Flexible)**

기능 자격(Capability) ID와 동일한 설계 원리를 적용한다. **시스템이 규정하는 가중치**와 **사용자가 조정하는 가중치**를 **완전히 분리**하여, 도메인별로 안정적인 전문 최적화를 보장하면서도 사용자·프로젝트 단위의 자유로운 조정이 시스템 안정을 해치지 않도록 한다.

*   **시스템(도메인) 가중치:** 도메인별로 **시스템 단**에서 규정한다. 하드 도메인(보안·안전·기계 제어)에서는 Safety·Stability에 90% 이상 등 **결정론적(Deterministic)** 최소 보장을 두어, 전문적 최적화와 안정감을 확보한다. 변경 시에는 도메인 정책·배포 절차가 필요하다.
*   **사용자 가중치:** 그 **하위**에 사용자·프로젝트별 가중치를 둔다. 코일은 **프로젝트 밸런서 레이어에서 제한 없이 확장** 가능하며, 창의적 작업에는 보다 복잡한 가중치를 적용할 수 있다. 사용자가 자유롭게 변경해도 **도메인 강제 규칙**과 **원천 기준점**은 유지되도록 설계한다.

**원칙 요약:** **"안전은 딱딱하게(Deterministic), 지능은 유연하게(Flexible)"** — 안전·도메인 정책은 시스템이 딱딱하게 고정하고, 지능·페르소나·조화·창의성은 사용자 가중치로 유연하게 다룬다. [NEXA-SYSTEM] Capability ID의 시스템 역량/사용자 역량 분리와 동일한 이원화 전략이다.

---

#### **1. 코일 밸런서(Coils Balancer) 레이어 체계의 정의 및 역할**
코일 밸런서는 인디케이터가 사건 발생의 근본 이유인 **'Why(동기)'**를 도출할 때 사용하는 **가치 필터(Value Filter)**이며, 기존의 **고정된 항목 수 전제**를 탈피하여 **레이어 기반으로 확장**된다.

핵심 원칙은 다음과 같다.

*   **레이어 원칙:** 코일은 “몇 개를 쓰는가”가 아니라 **어떤 레이어에서 어떤 기준을 강제/허용하는가**로 관리한다.
*   **중복 제거:** 코일 밸런싱 자체가 ‘조화(하모니)’를 찾는 기능이므로, 기본 코일 아이템에서 **Harmony(조화)**는 **중복 개념**으로 간주하여 제거한다.

##### **1.1 원천 밸런서 레이어 (Source Balancer Layer)**
*   **역할:** 시스템의 가장 근본이 되는 **'기본 생존 및 운영 지능'**(최소 동작)을 보장하는 기준점.
*   **구성:** 당장 시급한 기본 5개(변동 가능) 코일로 시작하며, 이는 모든 하위 레이어의 **기준점(baseline)**이 된다.
    *   **안전(Safety):** 물리적 위험 방지 및 생명 보호를 최우선으로 한다.
    *   **안정성(Stability):** 시스템의 일관된 유지 및 예측 가능한 작동을 보장한다.
    *   **효율(Efficiency):** 에너지 소비 최소화 및 최단 경로의 문제 해결을 지향한다.
    *   **자율성(Autonomy):** 시스템이 스스로 판단하고 환경을 조성하는 능동성을 부여한다.
    *   **창의성(Creative):** 정해진 틀을 벗어난 새로운 제안이나 실험적 인터랙션을 허용한다.

##### **1.2 도메인 밸런서 레이어 (Domain Balancer Layer)**
*   **역할:** 특정 전문 영역(보안, 스마트팜, 아트 프로젝트 등)에 특화된 **가치 기준**을 제공한다.
*   **특징:** 시스템 하위에서 도메인 성격에 맞게 코일 아이템을 **추가하거나 가중치를 조절**할 수 있다.
    *   예: **아트 도메인**에서는 원천 레이어 위에 **미학(Aesthetics)**, **공감(Empathy)**, **호기심(Curiosity)** 같은 도메인 코일을 덧씌우거나 비중을 강화한다.
    *   예: **보안/안전 도메인**에서는 Safety/Stability를 더 강하게 고정(결정론)하고, 나머지 코일의 허용 범위를 제한한다.

##### **1.3 프로젝트 밸런서 레이어 (Project Balancer Layer)**
*   **역할:** 개별 프로젝트 단위에서 사용자가 직접 정의하는 **'개인화된 가치 필터'**.
*   **확장성:** 사용자는 필요에 따라 코일 아이템을 **제한 없이 추가**할 수 있으며, 이는 **User Capability(사용자 기능 자격)**와 연동되어 AI의 **페르소나**를 결정한다.

#### **2. 도메인별 가중치 설정 로직 (Weighting Strategy) — 시스템 가중치**

인디케이터의 개입 정도는 **도메인**에 따라 결정된다. 이 절은 **시스템(도메인) 가중치**를 정의하며, **결정론적(Deterministic)** 으로 유지된다. 프로젝트 밸런서 레이어는 그 하위에서 도메인 정책을 침해하지 않는 범위로 오버레이된다.

*   **하드(Hard) 도메인 (보안, 안전, 기계 제어):**
    *   **시스템 가중치:** **Safety(안전) 및 Stability(안정성) 코일에 90% 이상**을 **도메인 단에서 강제 할당**. 사용자가 이 비율을 낮추는 것은 허용하지 않음(안전은 딱딱하게).
    *   **운영 방침:** 인디케이터의 자동 처리 범위를 최소화하고, 모든 결정에 사용자의 직접 개입(WILL)을 요청하는 보수적 모드로 작동한다.
*   **소프트(Soft) 도메인 (기획, 아트 프로젝트, 생활 보조):**
    *   **시스템 가중치:** Autonomy·Creative 및 도메인 코일(예: Aesthetics·Empathy)에 대한 **도메인 기본값**만 규정. 구체적 비중은 **프로젝트 밸런서 레이어**에서 자유롭게 조정(지능은 유연하게).
    *   **운영 방침:** 인디케이터가 더 능동적으로 환경을 조성하고 사용자 취향에 맞는 창의적 피드백을 주도한다.

#### **3. 운영 규범(GOVERN) 태그의 정의 및 진화**
**GOVERN**은 시스템 운영의 근본 원칙이자, 지능이 스스로를 통제하는 **'질서(The Rule)'**를 의미합니다.

*   **내용 정의:** 인디케이터가 내리는 모든 조언과 실행의 논리적 근거입니다. 예를 들어, "에너지 효율 코일 설정에 따라 전력을 10% 절감한다"는 규칙이 이에 해당합니다.
*   **할루시네이션 방지:** 단순히 결과를 제시하는 것이 아니라, 어떤 GOVERN(규범)에 근거해 판단했는지 명시함으로써 AI의 추론 오류가 아님을 증명합니다.
*   **성장형 지능의 핵심:** 비스타(Vista)는 아카이브에 축적된 데이터를 분석하여 새로운 규범을 생성하고, 이를 다시 하부 센티널에게 하향 전파하여 현장 지능을 진화시킵니다.

#### **4. 문서의 목적: 페르소나와 현명한 조언**
*   **일관성 유지:** 동일한 상황이라도 설정된 코일 밸런서에 따라 인디케이터는 일관된 'Why'와 'Summary'를 제공하여 사용자와의 신뢰를 구축합니다.
*   **공감형 피드백:** 사용자의 과거 선택(INTENT)을 분석하여 코일 가중치를 미세 조정함으로써, 시간이 흐를수록 사용자의 숨은 의도까지 알아채는 **맞춤형 페르소나**를 완성합니다.

이 문서는 NEXA 시스템이 단순한 자동화 장치를 넘어 사용자 가치를 이해하고 스스로 질서를 세우는 **살아있는 지능 체계**의 판단 지침서가 된다.

#### 5. 레이어 기반 코일 밸런서 확장 및 UI/오케스트레이션 반영 — 프로젝트 밸런서 레이어 중심

기존의 **고정 수치 확장 방식**은 지양한다. 대신, 코일은 **레이어별로 확장 규칙과 권한이 다르게 적용**되며, UI와 오케스트레이터는 이 레이어 모델을 그대로 반영한다.

**5.1 확장 규칙(권한)**
*   **Source Balancer(원천):** 최소 동작 보장 레이어. 코일 구성은 시스템 핵심 정책에 의해 제한되며(기본 5개 권장), 변경은 신중히 관리된다.
*   **Domain Balancer(도메인):** 도메인 운영 정책 레이어. 도메인별 템플릿이 제공되며, 하드 도메인은 Safety/Stability 같은 하한선을 **결정론적으로 강제**한다.
*   **Project Balancer(프로젝트):** 사용자 정의 레이어. 코일 아이템을 **제한 없이 추가/삭제/가중치 조정**할 수 있으나, 상위 레이어의 강제 규칙을 위반할 수는 없다.

**5.2 UI 관리 시 기술적 장점**
*   **RAG 필터링 정교화:** 프로젝트/도메인 코일에 따라 검색·증거 우선순위가 명확해진다.
*   **Why 도출의 일관성:** 어떤 레이어의 어떤 코일이 판단에 개입했는지 구조적으로 설명 가능해, Summary의 일관성과 신뢰도가 상승한다.
*   **성장형 GOVERN:** 비스타(Vista)가 GOVERN을 생성·하위 전파할 때, “무엇이 기준점(원천)이고 무엇이 도메인/프로젝트 오버레이인지”가 분리되어 진화 방향이 안정된다.

**5.3 저장·선택·오케스트레이터 반영**
*   **저장 단위:** Domain 템플릿 + Project 오버레이(사용자 정의)를 하나의 “프로젝트 밸런서 프로파일”로 저장한다.
*   **선택 로직:** 프로젝트 시작/전환 시 프로파일을 선택하며, 선택된 프로파일은 인디케이터의 Why/Summary, RAG, 실행 정책(질문 빈도, 자동화 허용 등)에 동기화된다.
*   **Capability 연동:** 특정 코일(예: 자동 실행 범위를 넓히는 자율성 강화, 민감정보 접근을 동반하는 보안 강화 등)은 User Capability에 의해 UI에서 편집/상향이 제한될 수 있다.

#### 6. 음성 피드백(Summary) 및 질문·수락·실행 시나리오

**6.1 Summary의 역할**  
인디케이터가 최종 판단 후 사용자에게 건네는 종결 어미. `indicator_insight.summary`를 TTS에 전달해 음성 피드백 완성. 영어 커널–다국어 쉘에 따라 Summary만 한글로 변환 출력.

**6.2 시나리오 A: 보수적 모드 (질문 → 수락/취소 → 실행)**  
안전·안정성 가중치가 높을 때. 인디케이터가 ECHO·SHOULD로 Summary에 "장비를 정지할까요?" 등 발행 → 사용자 WILL 응답. 수락 시 `WILL-MUST`로 이펙터 실행, 취소 시 VOID 전이로 중단.

**6.3 시나리오 B: 자율 모드 (질문 → 알아서 해 → 최적 실행)**  
자율성 가중치가 높거나 INTENT가 충분히 쌓였을 때. 인디케이터가 과거 패턴 기반 제안 후 사용자 "알아서 해" 응답 시 GOVERN으로 승격, 이후 유사 상황에서 MAY/CAN 수준 자율 실행.

#### 7. 인터랙션 시나리오 데이터 예시 (JSON)

#### **[질문 단계: 인디케이터의 제안]**
```json
{
  "id": "IND-QUERY-001",
  "abstraction_layers": {
    "scope": "CORE",
    "pulse": "ECHO-SHOULD",
    "intent": "LINK",
    "state": "FLOW"
  },
  "indicator_insight": {
    "why": {"logic": "IN ORDER TO assist user BASED ON detected intention", "goal": "RESOLVE"},
    "summary": "양손이 가득 차 보이시네요. 부엌 문을 열어드릴까요?",
    "history": "Waiting for user's WILL to proceed."
  }
}
```

#### **[수락 단계: 사용자의 승인(WILL)]**
```json
{
  "id": "SNT-WILL-002",
  "abstraction_layers": {
    "scope": "CORE",
    "pulse": "WILL-MUST",
    "intent": "FACT",
    "state": "FLOW"
  },
  "sentinel_fact": {
    "who": "User_A",
    "what": "Approved the suggestion IND-QUERY-001",
    "when": "Immediate response"
  }
}
```

**요약:** `summary` 필드는 TTS로 그대로 전달하며 시스템 최종 태도를 선언한다. 인디케이터는 현명한 조언자로서 ECHO 제안 → 사용자 WILL 확답 → EFF 실행으로 연결한다. "알아서 해" 응답은 INTENT로 박제되어 RAG 호출 시 질문 없이 의도를 읽는 성장형 지능(한몸)으로 진화한다. 본 시나리오는 사전 문서 3(운영 규범) 및 문서 7(페르소나 전략서)과 연계하여 명시하는 것이 권장된다.
