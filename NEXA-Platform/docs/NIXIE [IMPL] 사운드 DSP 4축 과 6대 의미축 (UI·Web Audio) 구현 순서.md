# NIXIE [IMPL] 사운드 DSP 4축 과 6대 의미축 (UI·Web Audio) 구현 순서

## 1. 목적

- **체험**: 필터·릴리즈·디튜닝·지터 네 축을 슬라이더로 조절하며 청각 변화를 확인한다.
- **운영**: 동일한 네 축을 **수치(또는 정규화 0~1)** 로 유지해, 메시지·상태 이벤트 시 **조합·가중**만 주면 재현 가능하게 한다.
- 본 문서는 **구현 순서**와 **쓰는 기술**을 정리한다. (의미 축 VI/GOVERN 등 → 네 축 매핑은 별도 정책 문서로 둔다.)

**진행 원칙**: 처음부터 분석·역추적까지 넣지 않고, **슬라이더 → 네 축 → 규칙 기반 표시**로 **구현 복잡도를 낮춘 채** 진행한다. 세부는 **구현 후 체험**하며 조정한다.

## 2. 네 축과 Web Audio 대응

| 축                  | 청각 역할                          | 주로 쓰는 API·개념                                                             |
| ------------------- | ---------------------------------- | ------------------------------------------------------------------------------ |
| **필터(Filter)**    | 밝기·먹먹함(저역 통과 시 어두워짐) | `BiquadFilterNode` (`lowpass` 등), `frequency`·`Q`                             |
| **릴리즈(Release)** | 꼬리·잔향 길이(엔벨로프 꼬리)      | `GainNode.gain` 스케줄, `linearRampToValueAtTime` 등                           |
| **디튜닝(Detune)**  | 두 음 높이의 미세 어긋남·입체감    | `OscillatorNode.detune`(cent), 또는 **이중 오실레이터** + `frequency` 오프셋   |
| **지터(Jitter)**    | 미세 떨림·불안정감                 | 피치/게인/패닝에 **저주파·난수 변조**, 또는 `OscillatorNode` + 보조 모듈레이션 |

실제 그래프는 대략 **소스 → (디튜닝/지터가 걸린 발진) → 필터 → 게인(릴리즈 포함) → 출력** 순이 자연스럽다. (지터를 필터 뒤에만 줄지, 발진에 줄지는 취향·부하에 따라 조정.)

## 3. 프런트엔드 기술 스택(권장)

- **UI**: Vue 3 + Quasar(`q-slider` 등), 기존 닉시 패널(`NixieDevControls` 패턴)과 동일한 **로컬 ref + 필요 시 Pinia** 구조.
- **오디오**: 브라우저 **Web Audio API** (`AudioContext`, 노드 연결). 기존 모스 경로(`morseWebAudio.ts`)와 **별도 그래프**로 두거나, 이후 **마스터 체인 앞단**에 삽입하는 방식으로 확장.
- **상태**: 체험용은 **컴포넌트 로컬 ref(0~100 또는 0~1)** 만으로 시작하고, 이벤트 연동이 필요해지면 `NmapSnapshot` 확장 또는 전용 스토어/모듈로 승격.

## 4. 복잡도·표시·매핑 원칙 (구현 복잡도 낮추기)

의미 축(VI·GOVERN 등)과 DSP 축(필터·Hz)은 **문서에서는 한 줄에** 쓰이지만, 코드에서는 **나누는 것**이 유지보수에 유리하다. 여기서는 **사운드 레이어 네 축**과 **표시 정책**만 고정한다.

### 4.1 매핑 레이어

- **메시지·상태 이벤트**는 가능하면 **직접 Hz·dB를 넣지 않는다.**
- **네 축 목표값(또는 델타)** 과 짧은 **매핑 함수·테이블**이 세부 `frequency`·`detune`·지터 깊이 등을 만든다.
- “세부 Hz를 매핑에 숨긴다”는 말은 **이벤트 페이로드가 Hz가 아니라는 뜻**이지, 실제 오디오에서 Hz가 안 바뀐다는 뜻은 아니다. (필요하면 매핑이 `morse_tone_hz`까지 덮어쓸 수 있다.)

### 4.2 표시(Hz·TONE) — **규칙 기반**을 1차 선택

| 방식                              | 내용                                                                               | 복잡도   |
| --------------------------------- | ---------------------------------------------------------------------------------- | -------- |
| **규칙 기반 (권장 1차)**          | 캐리어·디튜닝·(합의된) 유효 피치 식으로 **표시용 숫자**를 계산한다. Analyser 없음. | **낮음** |
| **AudioParam 추적**               | 우리가 스케줄한 값만 읽어 표시에 반영                                              | **중간** |
| **출력 분석(피치·스펙트럼 추정)** | 실제 파형에서 Hz 추정, 스무딩 필요                                                 | **높음** |

- **“TONE 슬라이더는 그대로 두고, 필터·디튜닝만 뒤에서 얹는다”** 는 **UX 정책**으로 가능하다. 이 경우 표시 Hz는 **기준 캐리어**에 맞추고, 나머지는 청각만 바꾼다.
- 반대로 정책상 **캐리어까지 바꿔야** 하면 매핑이 스냅샷 `morse_tone_hz`를 갱신하고 **UI 숫자도 같이 바뀌는** 흐름이 맞다.
- **어느 쪽이 나은지는 구현 후 체험**하며 정해도 된다. 다만 **경계만** 미리 잡아 두면 좋다: 예) “표시는 사용자 TONE, 실제 체인은 TONE + 레이어” vs “표시도 유효 주파수 규칙으로 통일”.

### 4.3 구현 시 최소로 두면 좋은 것

- **캐리어 / 네 축 / 매핑 입력**이 각각 어디서 오는지 한 줄로 적어 둔다.
- 표시는 **규칙 기반**으로 시작하고, **분석 기반**이 필요해지면 그때 단계를 나눈다.

## 5. 작업 순서 (슬라이더 UI 먼저 → 기술 적용)

아래 순서를 권장한다. **항상 UI에서 수치가 먼저 정해지고**, 그다음 단계에서 그 수치를 읽어 소리에 반영한다.

### 단계 A — 슬라이더 UI만 (동작 없음)

1. 닉시 개발 패널(또는 전용 섹션)에 **네 개 슬라이더** 배치.
2. 각 슬라이더에 **라벨·범위** 고정: 예) `0~100` 정규화.
3. 값은 **로컬 `ref` 네 개**에만 바인딩 (`v-model` 또는 `:model-value` + `@update`).
4. 이 단계에서는 **Web Audio 변경 없음**. 화면에 숫자만 맞게 움직이면 완료.

**산출물**: 네 축의 **단일 진실 원천**(체험용)이 화면에 존재.

### 단계 B — 파라미터 객체로 묶기 (완료)

1. 네 `ref`를 하나의 **읽기 쉬운 객체**로 묶는다. 예: `getNixieSoundLayers()` → `{ filter01, release01, detune01, jitter01 }` (모두 0~1 권장).
2. 이후 오디오 모듈·이벤트 핸들러는 **이 객체만** 받도록 설계한다.

**산출물**: UI 변경 시 **한 곳**에서 오디오/이벤트가 구독 가능.  
**구현**: `src/system/nixie/nixieSoundLayerParams.ts` (`getNixieSoundLayers`, `NixieSoundLayerParams`), `NixieDevControls`의 `nixieSoundLayers` computed + watch(구독 지점).

### 단계 C — 최소 오디오 파이프 (소리 나게) (완료)

1. **전용 `AudioContext`**(또는 기존 컨텍스트 공유 정책 확정)와 **마스터 `GainNode`**만 연결.
2. 테스트용 **단일 `OscillatorNode`(사인)** → 마스터 → 스피커로 **고정 톤**이 나오게 한다.
3. 슬라이더는 아직 **마스터 게인**에만 걸어도 되고, 아무 연결 없이 두어도 된다. (그래프 존재 확인이 목적.)

**산출물**: 네 슬라이더와 독립된 **살아 있는** 체인.  
**구현**: `src/system/nixie/nixieSoundLayerAudio.ts` — 모스와 분리된 컨텍스트, 「레이어 파이프(테스트 사인)」토글. (이후 단계 D에서 축별 DSP 연결.)

### 단계 D — 축별로 하나씩 연결 (순서 고정) (완료)

1. **필터**: `BiquadFilterNode`를 삽입. 슬라이더 값 → `frequency`(및 필요 시 `Q`) 매핑. 톤이 **밝↔어두**만 바뀌면 성공.
2. **릴리즈**: 노트 오프(또는 게인 램프 다운) 시 **하강 시간**을 슬라이더로 연장·단축. `GainNode`의 `gain` 스케줄로 구현.
3. **디튜닝**: 오실레이터를 **두 개** 두고 `detune` 또는 `frequency`에 작은 차이를 슬라이더 비례로 준다. **입체감**이 들어오면 성공.
4. **지터**: 아주 작은 범위로 **주기적 또는 난수** 변조(피치/게인 중 하나부터). 슬라이더는 **변조 깊이**만 제어.

**각 서브단계마다** “슬라이더만 움직였을 때 의도한 축만 변하는지” 확인한다.

**구현(지속 테스트 톤 기준)**: `nixieSoundLayerAudio.ts` — **FILTER** → 저역 통과 `frequency`; **RELEASE** → 저속 LFO로 `postFilterGain.gain` 진폭 변조(트레몰로·꼬리 느낌); **DETUNE** → 듀얼 사인 ±`detune`; **JITTER** → 고속 LFO → `detune` 변조(vibrato). 출력 레벨은 `NIXIE_SOUND_LAYER_PROBE_OUTPUT_LINEAR` 고정.

**구현(모스 미리듣기)**: `morseWebAudio.ts`의 `playMorseTimeline` — 동일 매핑(`nixieSoundLayerAudio`의 `filter01ToLowpassHz` 등)으로 **듀얼 사인 → 공유 저역통과 → 트레몰로 → 마스터**; `PlayMorseOptions.soundLayers`·재생 중 `setMorseSoundLayerParams`. **RELEASE**는 트레몰로 외에 **닷/대시 엔벨로프 꼬리 길이**에도 반영. 레이어 파이프(테스트 사인)와 **컨텍스트는 분리**(단계 E 정책 유지).

### 단계 E — 기존 닉시·모스와의 관계 정리

1. 모스 미리듣기(`morseWebAudio`)와 레이어 프로브(`nixieSoundLayerAudio`)는 **별도 `AudioContext`** — 동시 재생 시에도 그래프 충돌 없음. (필요 시 후속으로 컨텍스트 통합 검토.)
2. 건반·합성 음원이 생기면 **동일 네 축**을 그 그래프에도 적용한다.

### 단계 F — 메시지·상태 연동 (후속)

1. 이벤트는 **직접 Hz를 넣지 않고**, “상황 키 → 네 축 목표값 또는 델타”를 **테이블·함수**로 매핑한다.
2. 스냅샷·N-MAP과 동기할 필드가 정해지면 그때 **Pinia/스키마**에 반영한다.

## 6. 요약

- **먼저** 네 슬라이더 UI와 **정규화된 네 값**을 고정하고, **그다음** Web Audio 노드를 **필터 → 릴리즈 → 디튜닝 → 지터** 순으로 하나씩 붙인다.
- 메시지 시에는 **네 축의 조합**으로 재현하고, 세부 Hz·DSP 숫자는 **매핑 레이어**에서만 결정한다.
- UI에 보일 **Hz·TONE** 은 **규칙 기반 표시**로 시작해 복잡도를 낮추고, **캐리어 고정 vs 유효 주파수 표시** 등은 **구현·체험 후** 정해도 된다.
- 출력 파형 **분석으로 Hz를 맞추는 방식**은 1차 범위에서 **제외**하고, 필요 시 별 단계로 추가한다.

## 8. 사운드의 의미 축 (시뮬/내러티브) — 상황·감정·리스크를 숫자로

**서사적 사운드 변조**는 사용자가 텍스트를 읽기 전에, 리듬·질감만으로도 시스템이 어떤 **공기(Atmosphere)** 안에 있는지 느끼게 하는 장치다. 개발 단계에서는 **의미 축 슬라이더(연속값)** 를 두고 Web Audio 노드·모스 타이밍과 **매핑**해 미리 체험하면, 축 이름과 청각 인상을 같이 학습할 수 있다.

**6대 사운드 의미 축:** 긴장, 이질감, 기계성, 공간감, 활력, 조화.

NEXA NIXIE v0.3 **음악적 통신 장비** 관점에서 위 6축에 대해 **시스템 컨텍스트**와 **구현 전략**을 나란히 둔다. (단계 E 이전에 의미·DSP 역할을 합의하기 위한 초안.)

### 의미 축 구현 순서 (권장 스텝)

아래는 **§5 DSP 4축 단계 A~F와 별개**인, **의미 6축** 전용 진행 순서다. 번호는 **의미 단계 M-A ~ M-F**로 표기해 DSP 단계와 혼동하지 않는다.

- **M-A — 슬라이더 UI만**
  - **내용:** 닉시 개발 패널(또는 전용 블록)에 **6개 슬라이더**(긴장·이질감·기계성·공간감·활력·조화). 범위 `0~100` 또는 `0~1` 통일, **로컬 `ref`만** 바인딩. **이 단계에서는 Web Audio·모스에 연결하지 않음.**
  - **산출물:** 화면에 **6축의 단일 진실 원천**(체험용).
  - **구현:** `NixieDevControls.vue` — 사운드 레이어 4축·`q-separator` 아래 `M-A · 의미 6축` 블록, 라벨 TENSION/UNCANNY/… , `atmosphereTension` 등 로컬 `ref` 6개(`0~100`).
- **M-B — 파라미터 객체로 묶기**
  - **내용:** 6개 `ref`를 하나의 객체로 정규화. 예: `getNixieSoundAtmosphere()` → `{ tension01, uncanniness01, mechanical01, space01, vitality01, harmony01 }` (모두 0~1). 타입·필드명은 코드에 한 번만 정의.
  - **산출물:** 이벤트·매핑 레이어가 받을 **의미 벡터**.
- **M-C — 매핑 설계 고정**
  - **내용:** **의미 6축 → DSP 4축(`NixieSoundLayerParams`)** 및 **모스 파생 파라미터**(dit 스케일, 캐리어 오프셋, 패닝 등)로 가는 **표 또는 함수 목록**을 문서·주석으로 고정. 축 상관(긴장 vs 활력 등) 시 **가중치·상한 규칙** 한 줄씩. **구현은 다음 스텝** — 여기서는 “무엇이 어디로 가는지”만 합의.
  - **산출물:** 매핑 SSOT 초안(코드 없어도 됨).
- **M-D — 매핑 구현 (순수 함수)**
  - **내용:** `nixieSoundAtmosphereMap.ts` 등에 **의미 벡터 → DSP 목표**만 계산하는 **순수 함수**(부작용 없음). 필요 시 **의미 → 모스 옵션** 보조 함수 분리. 단위 테스트는 **수치·클램프** 위주.
  - **산출물:** 오디오 모듈이 import 가능한 **매핑 모듈**.
- **M-E — 개발 패널에 연결·체험**
  - **내용:** M-A UI가 **M-D 출력**을 구독하도록 연결. **모드 선택(권장):** (1) **DSP 직접 슬라이더** 유지 + **의미 슬라이더**는 별도 행에서 DSP를 덮어쓰기, 또는 (2) **의미만 표시**하고 DSP는 읽기 전용·미러. **레이어 파이프(테스트 사인)**·**모스 미리듣기**에 동일 매핑 결과를 적용할지 순서대로 검증.
  - **산출물:** 귀·UI로 **의미↔청각** 검증 완료.
- **M-F — 상태·이벤트 연동**
  - **내용:** N-MAP·스냅샷·HUD 이벤트가 **의미 벡터(또는 델타)** 만 보내도록 설계. Pinia 필드·스키마 확정은 **여기서**. 필요 시 **프리셋 = 의미 벡터 스냅샷**만 저장.
  - **산출물:** 운영 시 **직접 Hz 없이** 재현 가능.

**진행 시 유의**

- **DSP 4축 단계 A~D가 이미 구현된 상태**이므로, 의미 축은 **새 슬라이더 묶음의 M-A부터** 쌓으면 된다. 기존 DSP 슬라이더를 제거할 필요는 없다(§8 표 — 의미 vs DSP 역할 분담).
- **조화·스케일**처럼 **순수 모스 사인만으로는 한계가 있는 항목**은 M-C에서 **“모스 경로 / 건반·샘플 경로”** 로 나누어 적어 두고, M-E에서는 모스에 적용 가능한 부분만 먼저 연결한다.

### DSP 4축(필터·릴리즈·디튜닝·지터)과의 관계

| 구분         | 역할                                                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| **의미 6축** | 스냅샷·내러티브가 넘기는 **연속 목표값**(0~1 등). 플레이어에게 보이는 이름은 여기에 맞춘다.                                          |
| **DSP 4축**  | 실제 그래프 노브. **의미 축 → 매핑 함수 → DSP 목표**로만 갱신하거나, 일부 의미 축이 모스 **dit 간격·캐리어**를 직접 건드리기도 한다. |

**긴장**이 필터·피치·dit를 동시에 건드리는 것처럼, 한 의미 축이 **여러 DSP/타임라인 파라미터**로 퍼질 수 있다. 반대로 **이질감 ↔ 지터**, **조화·기계성 ↔ 디튜닝·파형**처럼 겹치는 경우에는 문서·코드에 **어느 축이 1차 주인인지**를 적어 두면 튜닝이 수월하다.

### 구현·기획 검토 메모 (외부 의견)

- **명확해진 점:** 축마다 **컨텍스트 + 전술**이 한 블록에 있어, 기획·사운드·코드가 같은 표를 보고 대화하기 좋다.
- **스케일·화성(조화):** 펜타토닉/증4도 등은 **멜로디·화성이 있는 음원**에 바로 붙고, **순수 모스 사인**만으로는 표현 범위가 좁다. “모스 경로 / 건반·레이어 경로”처럼 **적용 채널**을 나누는 문장을 두면 기대치가 맞는다.
- **공간감:** `ConvolverNode`는 **IR 로딩·지연·CPU**를 동반한다. 1차는 `DelayNode`+피드백으로 얕은 공간만 주고, 컨볼버는 후속으로 두는 식이 안전하다.
- **활력·템포:** `playbackRate`·스케줄 시간축 스케일은 **HUD 동기·타임라인**과 같이 설계해야 한다(모스 문서의 동기 정책과 충돌 검토).
- **축 상관:** 긴장↑와 활력↑가 비슷한 청각(밀도·속도)으로 수렴할 수 있으니, 필요하면 **가중치 표**나 “한 축이 올라갈 때 다른 축 상한” 같은 규칙을 후속 절에 적는다.

### 1. 긴장 (Tension)

- **시스템 컨텍스트:** 긴급도(Urgency 1~5) 및 규범(ERA)과 사실(SNT)의 위상차 반영
- **구현 전략:**
  - **Oscillator:** 기본 주파수(Pitch)를 미세하게 상승.
  - **Timing:** 모스 부호 간격을 좁혀 리듬 밀도 증가.
  - **Filter:** `BiquadFilter`의 주파수를 높여 소리를 날카롭게 연출.

### 2. 이질감 (Uncanniness)

- **시스템 컨텍스트:** 신뢰도 점수 95점 미만(Jitter 발생) 또는 외부 자원 유입(Nebula Influx)
- **구현 전략:**
  - **Modulation:** 피치와 게인에 저주파 난수 변조(Jitter) 적용.
  - **Inharmonicity:** 비조화 주파수를 섞거나 FM 합성을 통한 금속성 질감 추가.
  - **Panning:** 스테레오 위치를 불규칙하게 흔듦.

### 3. 활력 (Vitality)

- **시스템 컨텍스트:** 사용자의 활력 지수(VI)와 직접 동기화(Low-Entropy 모드 연동)
- **구현 전략:**
  - **Envelope:** VI가 낮으면 `GainNode`의 Attack을 부드럽게, Release를 길게 설정.
  - **Tempo:** VI 수치에 따라 전체 재생 속도(timeScale)를 가변 조절.

### 4. 기계성 (Mechanicalness)

- **시스템 컨텍스트:** 건조한 관측 데이터(TICK) 또는 하드웨어 프로필(COLD) 상태 표현
- **구현 전략:**
  - **Waveform:** 디튜닝이 배제된 순수 Square 또는 Saw 파형 사용.
  - **Envelope:** Release를 0에 가깝게 설정하여 딱딱한 스타카토 질감 구현.

### 5. 공간감 (Spaciousness)

- **시스템 컨텍스트:** 무한 줌(Fractal Zoom)의 스케일 및 서사적 잔상(Narrative Trace) 표현
- **구현 전략:**
  - **Reverb:** `ConvolverNode` 또는 `DelayNode`를 활용한 잔향 깊이 조절.
  - **Panning:** L/R/ALL 패닝을 통해 정보의 유입 방향성(Shell context) 시각화와 동기화.

### 6. 조화 (Harmony)

- **시스템 컨텍스트:** 6-COILS 중 '조화' 코일 가중치 및 Identity ID 기반 고유 스케일 반영
- **구현 전략:**
  - **Scale:** 조화가 높으면 펜타토닉/메이저 스케일, 낮으면 증4도 등 불협화음 배치.
  - **Detune:** 두 오실레이터의 `detune` 값을 조절하여 깨끗한 음(High)과 거친 기계음(Low) 사이를 조율.
