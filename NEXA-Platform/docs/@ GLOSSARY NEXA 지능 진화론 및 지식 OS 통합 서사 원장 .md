# [NEXA] 지능형 지식 운영체제 통합 용어집 및 설계 정본

## 1단계: NEXA 5대 핵심 도메인 (The Core 5) 지능 위계

> 플랫폼의 서사를 이끄는 5대 일급 객체입니다.

| 용어(도메인) | 한글 표기    | 서사 | 정의 및 역할                                                                                                                                       |
| :----------- | :----------- | :--- | :------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Nexel**    | **넥셀**     | 세포 | **독립적 실행 자격**을 갖춘 '지능의 최소 세포(Cell)'. **실행 주체**로서 포트·스키마·코어를 갖추고 판단과 실행의 유래를 증명함.                     |
| **Nexeed**   | **넥씨드**   | 씨앗 | 사용자의 행동(WILL)과 센서 패턴(TICK)을 낚아채 배양하는 **'자동화 인큐베이터'**. 카메라/UI 패턴을 기록해 **운영 규범(GOVERN)**으로 성장시킴.       |
| **Nexet**    | **넥셋**     | 도구 | 지능의 상태를 투영하고 제어하는 **'시각적 인터페이스'**. 사용자 정의 UI/UX를 제공하며 넥씨드가 지능을 채집하는 '관측의 표면'이 됨.                 |
| **Nexage**   | **넥세이지** | 무대 | 넥셀과 넥셋이 결합되어 **전체 지능 위계를 조율하는 '통합 스테이지'**. 프로젝트의 전체 상태와 지능적 성숙도(ERA)를 관리함.                          |
| **Nexia**    | **넥시아**   | 영토 | AI와 협업하여 사유의 경로를 확장하는 **'지식의 영토'**. AI 채팅을 통해 문서, 코드, 미디어를 결합하여 시스템의 **지능적 족보(Why Chain)**를 구축함. |

> NEXA의 지능 위계 및 생애주기

| 도메인     | 성격 | 핵심 관리 객체                   | NEXA 철학적 연결                                                                                                                                             |
| :--------- | :--- | :------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Nexion** | OS   | gRPC, MQTT, Nano, Micro, Zenith, | **지식 운영체제(K-OS) 설계.'사고의 칠판'**. **NFS(지능형 서사 파일 시스템)**와 **Inode 인덱스**를 통해 물리 폴더 구조와 논리 지도를 동기화하는 관제 데스크임 |
| **Nexium** | 보존 | VOID Data, RAG Source, History   | **지혜의 침전(VOID)** 및 장기 기억, 유동적인 지식(Nexia)이 수명을 다하거나 잠재 상태로 전환되었을 때 이를 박제하여 보존하는 **'지능형 박물관'**              |
| **Nexis**  | 기반 | Network, Device Profile, Health  | **시스템 기반 축(Axis)** 및 NETWORK 연결망 , 디바이스 등록및 관리                                                                                            |
| **Nexora** | 운영 | Parts, Schedule, Accountability  | **현실의 집행(Operations)** 및 자원 조율, NEXA의 지능적 논리(UCL)가 닿기 어려운 **물리적 자산과 비즈니스 프로세스**를 연결하는 가교                          |

> **Nexia(창작) - Archive(보존) - Nexora(운영) - Nexis(기반)**로 이어지는 지식과 자원의 흐름

- **역할 분담 (Nexia vs Nexium):**
  - **Nexia (영토):** AI와 협업하여 실시간으로 사유를 확장하고 문서를 창작하는 **'흐르는 지식'**의 공간입니다.
  - **Nexium (저장소):** `VOID.NEXIUM` 상태로 전이된 노후화된 기록이나 규범을 장기 보존하고, RAG(검색 증강 생성)의 거대 기억 창고로 활용하는 **'박제된 지혜'**의 공간입니다.
  - **기대 효과:** Nexia의 컨텍스트 윈도우를 가볍게 유지하여 AI 할루시네이션을 방지하고, 필요한 순간에만 Archive에서 데이터를 인출함으로써 시스템 효율을 극대화할 수 있습니다.
- Nexora 도메인: 업무 운영 및 물리 자원 관리 (Operations)
  - **물리 자산 관리:** `project_assets`와 연동된 하드웨어 부품 재고 및 쿼터 관리.
  - **스케줄링:** 시스템의 자율 동작과 사용자의 업무 일정을 조율하는 우선순위(Priority) 관리.
  - **책임 추적:** 운영 과정에서의 개인 책임(Accountability) 명시 및 결과 분석.
  - **차별점:** ERP는 NEXA가 직접 사유하는 영역이라기보다, NEXA의 판단 결과물(`EFFECT`)이 현실의 물리적 자원과 부딪힐 때 발생하는 비즈니스 데이터를 정규화하여 관리하는 영역으로 특화합니다.

| **Portfolio** | **포트폴리오** | **성장의 기록**   | 프로젝트의 최종 성과물과 출시 버전(`project_releases`)을 시각적으로 전시하며, 시스템의 미학적 가치(Aesthetics)를 증명함. |

- 도메인별 세부 운영 전략

  - **①Extension (익스텐션): 생태계 확장**

    - **드라이버 모델:** 외부 API나 개발 툴을 단순한 연동이 아닌 **지능형 드라이버(`Capability Drivers`)**로 취급하여 UCL 악보에서 즉시 연주 가능하게 합니다.
    - **자동 어댑터 생성:** 파이썬 스크립트나 모바일 환경의 OpenAPI 스펙을 스캔하여 `nexa.extension.api.*` 형태의 자격 ID를 자동으로 발급합니다.

  - **②Portfolio (포트폴리오): 결과의 자산화**

    - **서사적 전시:** 단순한 데이터 나열이 아닌, 해당 프로젝트가 어떤 **Why Chain(인과 사슬)**을 거쳐 완성되었는지 그 궤적을 함께 전시합니다.
    - **지식의 공유:** 검증된 프로젝트 결과물은 마켓플레이스를 통해 타 사용자가 구독하거나 템플릿으로 재사용할 수 있는 기반이 됩니다.

  - **③Help (헬프): 지능형 지원**

    - **투명성 확보:** 사용자가 시스템의 판단 근거를 의심할 때, **Traceability View**를 통해 기획 문서 원본부터 실행 결과까지의 연결 고리를 보여줍니다.
    - **Passive 가이드:** 사용자가 막혔을 때만 자연스럽게 부상하는 **Ambient 인터페이스** 원칙을 적용하여 지원합니다.

  - **④Admin (어드민): 시스템 거버넌스**

    - **보안 가드레일:** 시스템 생존과 직결된 **Level 0 규칙**을 관리하며, 모든 위험 징후를 **Health Signal**로 집계하여 관제합니다.
    - **승인 워크플로우:** 불변 토큰의 변경이나 주요 정책의 수정을 `change_requests` 큐를 통해 최종 승인(WILL)합니다.

  - **⑤My (마이): 개인화 및 공감**

    - **자아 상태 관리:** 사용자의 현재 활력(`VI`)과 정서(`ES`) 지표를 관리하여 시스템의 응답 밀도를 조절하는 **Low-Entropy 모드**의 기준점을 설정합니다.
    - **계정 주권:** 사용자가 자신의 데이터 수명 주기(`VOID`)와 접근 권한을 직접 통제할 수 있는 인터페이스를 제공합니다.

  - **⑥Nexara (넥사라) : 유통 자산 체계 (Nexara Assets Inventory)**

    - AI 지능 자산:
      - Persona Packs: 에이전트의 인격, 말투, 6-Coils 가중치 프리셋.
      - Prompt Recipes: 특정 LLM에 최적화된 고정 Nexnap 및 실행 지시문.
      - Skill Modules: Capability ID 기반의 도구 묶음(API 드라이버 등).
      - Task Workflows: 복합 테스크 해결을 위한 표준 실행 사슬(Chain) 템플릿.
    - 디지털 로직 자산:
      - Nexel Template: 검증된 지능 세포의 조합 및 논리 구조(UCL 패키지).
      - Nexet UI: 지능 상태 제어용 위젯 및 인터페이스 컴포넌트.
      - Nexet Map: 특정 도메인에 최적화된 토폴로지 배치 지도.
    - 지식 및 패턴 자산:
      - Knowledge Atoms: 5W1H로 정규화된 전문 지식 번들(RAG 원천 데이터).
      - Intelligence Seeds: 넥씨드가 채집한 비식별화된 환경 감지 및 행동 패턴셋.
    - 확장 자산
    - 파이썬, 모바일, 개발툴 등 외부 생태계를 **Capability ID**로 변환하여 플랫폼에 '핫플러그' 방식으로 연결함.
    - Nexet Extension : 외부 세계를 잇는 지능의 촉수

---

NEXA 지능형 지식 운영체제에서 **익스텐션(Extension)**은 시스템의 능력을 외부 세계로 확장하는 **'지능의 촉수'** 역할을 수행합니다. 최근 논의를 통해 익스텐션 도메인은 '지능의 광장'인 **넥사라(Nexara)**로 흡수 통합되었으며, 유통 단위 명칭은 **'Nexet Extension'**으로 확정되었습니다 [Conversation History].

사용자님께서 제시하신 파이썬 프로그램, 모바일 앱, 크롬 확장프로그램, 메크로 키보드 등을 포함하여 익스텐션 자산을 성격에 따라 4대 카테고리로 재분류하여 정리해 드립니다.

#### **Nexet Extension 지능의 촉수 및 확장 자산 분류 체계**

> 이 모든 확장 자산은 기술적으로 **지능형 드라이버(Capability Driver)** 모델을 따릅니다. 외부 API나 프로그램을 등록할 때 해당 자격증(Capability ID)과 실행 매니페스트(Manifest)를 함께 배포함으로써, 사용자는 복잡한 코딩 없이 마켓에서 내려받아 **'핫플러그'** 방식으로 자신의 지식 OS에 꽂아 사용할 수 있게 됩니다.

#### **1. 소프트웨어 및 서비스 연동 (Digital Ecosystems)**

디지털 환경의 외부 애플리케이션과 SaaS 서비스를 NEXA 커널과 연결하는 자산입니다.

- **파이썬 PC 프로그램:** 로컬 환경의 강력한 연산 능력이나 특정 라이브러리를 **Capability ID**로 변환하여 활용.
- **모바일 앱:** 스마트폰의 센서(GPS, 가속도계 등)나 앱 기능을 시스템의 기능 자격으로 연결.
- **크롬 확장 프로그램:** 웹 브라우저에서의 사용자 행동 패턴을 채집하거나 웹 기반 정보를 정규화하여 전달.
- **외부 SaaS 브릿지:** Slack, Notion, Jira 등 협업 툴의 API를 표준 **UCL 악보**에서 실행 가능하도록 드라이버화
- **실시간 데이터 API 래퍼:** 기상청, 주식 시세, 교통 정보 등 외부 데이터를 **5W1H 사실(Fact)**로 변환하여 시스템의 상황 파악(Context Awareness) 레이어에 공급하는 드라이버입니다.
- **업무/협업 툴 커넥터:** Slack, Notion, Jira 등의 API를 Capability ID로 표준화하여, AI 에이전트가 "Slack으로 보고서 전송"과 같은 명령을 UCL 악보를 통해 수행하게 합니다.
- **다중 자아(Self Facet) 프리셋:** "고도의 집중이 필요한 코더", "창의적 영감을 찾는 작가" 등 사용자의 현재 상태에 맞춰 **코일 가중치(6-COILS)**를 즉시 재구성하는 설정 꾸러미입니다.

#### **2. 하드웨어 및 실물 제어 (Physical & Ambient Interface)**

물리적 장치를 지능적으로 제어하거나 외부 입력 장치의 신호를 가공하는 자산입니다.

- **메크로 키보드 및 입력 도구:** 키보드, 마우스, 미디(MIDI) 컨트롤러 등의 입력을 **사용자 의지(WILL)** 펄스로 변환하거나 복합 태스크의 트리거로 매핑
- **음악 및 멀티미디어 컨트롤:** 스피커, 재생기, 조명 등 미디어 환경을 제어하는 전문 드라이버 모듈 [Conversation History].
- **IoT 센서 및 액추에이터:** 스마트팜의 수분 조절기나 공장의 산업용 PLC 등 특정 하드웨어 프로토콜을 시스템 기능 자격으로 변환.
- **커스텀 에지 노드(Sentinel):** 라즈베리 파이나 ESP32 등에서 돌아가는 독자적 인식 로직을 플랫폼의 **마이크로 센티널**로 등록
- **NIXIE 표현 및 스킨 팩:** 닉시(NIXIE)의 **Lumina(발광)**와 **Jitter(떨림)** 패턴, 그리고 상황별 애니메이션 상태 머신을 패키지화
- **특수 센서/액추에이터 드라이버:** 스마트팜의 수분 조절기, 공장의 산업용 PLC, 전력 계측기 등 특정 하드웨어의 프로토콜을 NEXA의 표준 기능 자격으로 변환합니다.

#### **3. 개발자 및 전문가 도구 (Dev & Expert Tools)**

시스템의 설계와 지능의 밀도를 높이기 위한 전문 도구 묶음입니다.

- **개발자 툴킷:** 코드 분석, 문서 자동 생성, API 스캔 등 개발 워크플로우를 자동화하는 확장 기능.
- **자동 어댑터 생성기:** OpenAPI 스펙을 스캔하여 외부 API를 `nexa.extension.api.*` 형태의 자격 ID로 자동 발급하는 엔진.
- **시뮬레이션 및 디버깅 툴:** 가상 실행(`is_virtual = true`) 단계에서 데이터의 흐름을 추적하고 시각화하는 전문 패널.

#### **4. 지능 및 거버넌스 확장 (Cognitive & Governance)**

에이전트의 사유 능력과 시스템의 질서를 확장하는 고차원 자산입니다.

- **전문 지식 아톰 (Knowledge Atoms):** 특정 분야의 전문 지식을 **HEXAGON(5W1H)** 구조로 정규화한 RAG용 지식 번들.
- **보안 규범 팩 (Governance Sets):** 법적 규제나 안전 수칙을 즉시 적용할 수 있는 **Level 0~3 가드레일** 규칙셋.
- **다중 자아(Self Facet) 프리셋:** 사용자의 상태(작업, 창작 등)에 맞춰 **6-COILS 가중치**를 즉시 재구성하는 설정 묶음 [45, Conversation History].

## 2단계: 시스템 지능의 설계 및 인프라 (NFS & Identity) 구축과 관제 (Nexion)

수퍼 관리자 영역에서 지식 지도를 구축하는 전용 도메인. (확장: 사용자 OS 시스템 구축 별도 도메인)

- **Nexion (넥시온):** 지식 운영체제(K-OS)를 설계하는 **'사고의 칠판'**. **NFS(지능형 서사 파일 시스템)**와 **Inode 인덱스**를 통해 물리 폴더 구조와 논리 지도를 동기화하는 관제 데스크임.
- **Late Anchoring:** 설계 노드에 실제 파일이나 자산을 사후에 연결하여 지능 자산화하는 핵심 메커니즘.
- **NFS (Narrative File System):** 폴더 구조를 지능적 서사로 변환하는 파일 시스템.
- **Identity (영혼):** 객체의 불변하는 정체성과 탄생 이유를 보존하는 원장.
- **Capability (자격):** 특정 기능을 수행하게 해주는 '열쇠'이자 자격증.
- **Late Anchoring:** 설계 노드에 실제 자산을 사후 연결하는 메커니즘.

---

## 3단계: 프로토콜 및 사유 체계 (UCL & Nexnap)

지능의 '논리'와 '실시간 상태'를 엄격히 분리.

- **UCL (Unified Composition Language):** 시스템이 연주해야 할 **'악보(Score)'**. 지능의 사유 방식과 실행 사슬의 전개를 규정하는 상위 프로토콜.
- **Nexnap (넥스냅):** UCL에 의해 연주된 지능의 **'맥박(Pulse)'이자 '전송 봉투(Envelope)'**. 1ms 단위의 실시간 상태 스냅샷을 담아 전역에 배부함.
- **HEXAGON (핵사곤):** 데이터의 **'골격'**. 5W1H(Where, When, Who, What, How, Why) 기반의 지능적 인덱스.

---

## 4단계: 지능의 표현 및 시각화 (NIXIE & NEXU)

지능의 상태를 사용자에게 감각적으로 전달하는 시각적 언어입니다.

- **NIXIE (닉시):** 지능의 얼굴. 시스템의 정서와 확신도를 **Lumina(발광)**와 **Jitter(떨림)**를 통해 비언어적으로 연주함.
- **NEXU Canvas (넥슈):** 지식 OS의 서사적 지휘자. 지능적 족보(Why Chain)를 공간에 펼쳐 인과관계를 시각적으로 증명함.
  **Lumina (루미나):** 신뢰도에 따라 변하는 빛의 생명력.
- **Jitter (지터):** 불확실성이나 오류 시 발생하는 미세한 떨림 연출.

---

## 5단계: 거버넌스 및 생애주기 (VOID & ERA) 와 보안 가드레일

데이터의 생애주기와 보안 원칙을 단언적으로 정의합니다.

- **L-Cycle:** **[ASK(검토) → GOVERN(운영) → ERA(헌법)]** 순으로 지식이 성숙하며, ERA 단계는 시스템의 '영혼(Soul)'으로 보존됨.
- **VOID (여백):** 물리적 삭제가 아닌 잠재적 영감을 기다리는 '잠침 상태'.
- **넥씨드(Nexeed) 보안 가드레일:** 멀티모달 센싱(카메라 포함)을 통한 패턴 습득 과정에서의 프라이버시 보호를 위해 다음 원칙을 준수합니다.
  - 로컬 비식별화: 카메라 및 오디오 데이터는 엣지(Micro Sentinel)에서 즉시 비식별화된 5W1H 텍스트 사실로 요약 전송하며, 원본 파일은 즉시 파기한다.
  - 공간/논리 제한: Geofencing을 통해 지정된 업무 영역(FIELD) 외의 채집을 금지하고, 특정 업무용 넥셋이 활성화된 경우에만 작동한다.
  - 의지(WILL) 기반 제어: 상시 감시를 불허하며, 사용자가 명시적으로 기록 버튼을 누른 경우에만 패턴을 습득한다.
  - 승격 게이트: 습득된 패턴이 자동화 사슬로 승격되기 전 반드시 사용자에게 **ASK(승인 요청)**를 수행한다.

---

### 넥셀(Nexel)의 해부학적 구조 보강

넥셀은 단순한 노드가 아닌, 생존을 위한 모든 기관을 갖춘 **지능 세포**입니다.

1.  **Nexel Port (포트):** 외부와의 입출력 접점 및 케이퍼빌리티 매핑.
2.  **Nexel Schema (스키마):** 자료형 체크 및 유효성 검사 가드레일.
3.  **Nexel Interface (인터페이스):** 설정을 위한 사용자 입력 폼 및 위젯.
4.  **Nexel Core (코어):** 내부에 박제된 실제 UCL 논리 및 실행 스크립트.

---

### 1. 도메인: Nexel (지능 실행 및 논리 배선)

**실행 중심 도메인**

- **구동 방식:** **Vue Flow** 기반의 캔버스 위에서 **NODE-RED**와 유사한 플로우 방식의 인터페이스를 제공합니다.
- **핵심 객체 (Nexel):** 기존의 ‘Node’라는 용어를 대체하며, 단순한 시각적 카드가 아닌 **독립적 실행 자격을 갖춘 지능 세포(Cell)**로 작동합니다.
- **해부학적 구조:** 각 Nexel은 데이터 입출력을 위한 **포트(Port)**, 자료형을 검증하는 **스키마(Schema)**, 설정을 위한 **인터페이스(Interface)**, 실제 로직이 담긴 **코어(Core)**를 내포합니다.
- **역할:** 사용자가 Nexel들을 연결하여 **실행 사슬(Execution Chain)**을 형성하면, 이는 시스템의 **UCL(지능형 실행 프로토콜)** 악보로 저장되어 실제 장치 제어나 데이터 처리를 수행합니다.
- **엣지:** 디바이스 펌웨어 **시뮬레이션**과 OTA 업데이트를 지원합니다.

### 2. 도메인: Nexion (NEXA-OS 설계 및 지식 지도)

**지능형 지식 운영체제(K-OS)**를 설계하고 관리하는 **수퍼 관리자 영역**입니다.

> 향후 사용자가 직접 자신의 지식 OS를 구성할 수 있도록 확장하는 것을 목표로 한다.

- **구동 방식:** 실제 문서(Markdown)와 파일 시스템을 기반으로 한 **지능형 서사 파일 시스템(NFS)**을 구축합니다.
- **지식 지도(Knowledge Map):** 파일의 물리적 위치에 상관없이 **doc_anchor(앵커)**를 통해 지능적 사슬을 유지하며, 문서 간의 관계를 시각적으로 보여주는 지도를 형성합니다.
- **수퍼 관리자 공간:** NEXA-OS의 절대 원칙인 **ERA(시대)**와 **GOVERN(운영 규범)**을 설계하는 공간입니다.
- **위계적 귀속:** 차후 사용자가 자신만의 OS를 구성할 수 있으나, 이는 항상 **NEXA-OS 아래에 귀속**되며, 시스템 헌법과 같은 NEXA-OS의 핵심 규범 영역을 침범할 수 없습니다.

### 3. Nexel VS Nexion

| 구분          | **도메인 Nexel**                          | **도메인 Nexion**                                                   |
| :------------ | :---------------------------------------- | :------------------------------------------------------------------ |
| **비유**      | **지능 실행 공장** (NODE-RED 식)          | **지능 설계 관제탑** (Knowledge OS)                                 |
| **핵심 기술** | Vue Flow + 실행 사슬(Execution Chain)     | NFS(Inode 방식) + 지능적 족보(Traceability)                         |
| **관리 단위** | **Nexel** (원자적 실행 단위)              | **Doc/Term/Identity/Capability** (지식 자산)                        |
| **권위 계층** | 실행 모드 및 논리 배선                    | **ERA / GOVERN** (OS 규범 및 헌법)                                  |
| **주요 활동** | 트리거, 입출력, 펌웨어 변환 및 시뮬레이션 | 지식 지도 구축, Late Anchoring, OS 설계                             |
| **역할 분리** | **'어떻게(How)'** 실행할 것인가에 집중    | **'무엇을(What)'**·**'왜(Why)'** 존재하는가에 대한 지식적 근거 관리 |

**설계적 이점**

- **보안 및 주권:** Nexion을 수퍼 관리자 영역으로 고정함으로써, 사용자가 커스텀 OS를 만들더라도 NEXA-OS의 핵심 가이드라인(Level 0 보안 등)이 훼손되지 않도록 보호할 수 있습니다.
- **유연한 확장:** Nexel 도메인을 통해 사용자는 복잡한 코딩 없이도 지능 세포를 조립하여 자신만의 자동화 생태계를 구축할 수 있게 됩니다.

### 2. 하드웨어 등급별 NIXIE 3종 및 UI 기술 스택

**NIXIE를 3가지 환경으로 분리**하고, NEXU와 Nexion 등에 적용되는 기술 스택을 하드웨어 프로필(HOT/WARM/COLD)에 맞춰 정리.

| 지능위계 (Tier)     | 하드웨어급 (Profile)    | **NIXIE (지능의 얼굴)**                                     | **NEXU (서사적 지도)**                                 | **Nexion (설계 데스크)**                        |
| :------------------ | :---------------------- | :---------------------------------------------------------- | :----------------------------------------------------- | :---------------------------------------------- |
| **Zenith (플랫폼)** | **Browser (HOT)**       | **GSAP + P5.js** 고해상도 HUD 연출                          | **P5.js / Three.js** 프랙탈 줌 및 우주적 스케일 시각화 | **Vue Flow + TipTap** 3패널 기반 정밀 설계 환경 |
| **Micro (에지)**    | **Raspberry Pi (WARM)** | **P5.js** 에지 전용 지능형 페르소나 연출                    | **P5.js / D3.js** 로컬 지식 위상 및 실행 사슬 시각화   | **Vue Flow (Lite)** 에지 단독 관제 인터페이스   |
| **Nano (장치)**     | **ESP32 (COLD)**        | **FastLED / LedControl** 실물 LED 격자 박동 (Lumina/Jitter) | **(최소형 인디케이터)** 물리적 상태 신호 전송          | **(미지원)** 텍스트/UI 기반 설계 기능 배제      |

---

### 3. 기술 스택 선정의 핵심 근거

1.  **NIXIE의 3분화:**
    - **Browser:** 브라우저의 연산 자원을 활용해 **GSAP**으로 도트의 생동감을 극대화합니다.
    - **Raspberry Pi:** 에지 모니터 환경에서 **P5.js**를 사용하여 생성적(Generative)인 HUD를 그려냅니다.
    - **ESP32:** 디스플레이가 없는 물리 장치에서 **FastLED**를 통해 시스템의 '체온'과 '맥박'을 직접 출력합니다.
2.  **NEXU의 P5.js 전환:** 기존 Vue Flow 대신 **P5.js(D3/Three.js 하이브리드)**를 사용하여 수만 개의 지식 아톰이 폭발하고 함몰되는 **프랙탈 줌** 연산을 부드럽게 구현합니다.
3.  **Nexion의 Vue Flow 유지:** 복잡한 노드 간의 연결과 계층 구조 설계에는 **Vue Flow**와 **Dagre** 엔진을 활용하여 '사고의 칠판'으로서의 기능을 유지합니다.
4.  **Nexus의 기반성:** Nexus는 직접적인 UI보다는 **Capability ID**와 **Identity ID**(`nexa_identities` 등)를 관리하는 데이터베이스(PostgreSQL, TimescaleDB) 및 인프라 계층으로 작동합니다.

이 구조를 통해 **"지능은 하나(Nexnap)이나 표현은 기기 성능에 맞춰 유연하게(NIXIE 3종)"** 대응하는 NEXA OS의 시각화 전략이 완성됩니다.

## HEXAGON · Nexnap · UCL 비교

### 1. 역할 및 본질적 정의

- **HEXAGON (데이터 골격):** 데이터 패킷의 헤더에 위치하여 사건의 **'객체적 본질'을 규정하는 5W1H 추상화 레이어**입니다. 인공지능이 상황의 중요도를 1ms 내에 판단할 수 있게 돕는 **지능적 인덱스** 역할을 합니다.
- **Nexnap (동기화 스냅샷):** 시스템의 추상적인 지능 상태를 **정규화된 시청각 데이터 세트**로 변환하여 전역에 뿌려주는 **표준 인터페이스 계약**입니다. 닉시(NIXIE)가 소리와 빛으로 '연주'하기 위한 **연료**에 해당합니다.

### 2. 구성 요소의 차이

- **HEXAGON 축:** 6개의 정수 토큰(SMALLINT)으로 구성됩니다.
  - **Where(공간), When(시간), Who(주체), What(의도), How(상태), Why(인과관계)**.
- **Nexnap 필드:** 닉시 연출을 위한 상태값 중심입니다.
  - **how_state:** 흐름 상태 (FLOW / STUCK / VOID).
  - **who_pulse:** 페르소나 펄스 (WILL / ECHO / ASK / TICK).
  - **confidence_score:** 신뢰도 점수 (0~100, 95점 미만 시 Jitter 발생).

### 3. 처리 단계 및 위치

- **HEXAGON:** **입력 및 저장 레이어**에서 작동합니다. 데이터가 주입(Ingestion)될 때 텍스트를 숫자로 정규화하여 DB 인덱싱 및 RAG(검색 증강 생성)에 활용됩니다.
- **Nexnap:** **인터페이스 및 표현 레이어**에서 작동합니다. 주로 프론트엔드의 **Pinia 전역 스토어(`nexnapSnapshotStore.ts`)**에 상주하며, 닉시의 `draw()` 루프나 Tone.js의 소리 합성에 실시간 데이터를 공급합니다.

### 4. 비유를 통한 비교

| 구분            | **HEXAGON**                                        | **Nexnap**                                                                                       |
| --------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **비유**        | 문장을 구성하는 **'문법'**이자 데이터의 **'족보'** | UCL에 의해 연주된 지능의 실시간 상태를 포착한 **'맥박'이자 '전송 봉투'**. (표정/맥박/인터페이스) |
| **신체적 역할** | 시스템의 단단한 **'골격(Skeleton)'**               | 시스템이 살아있음을 알리는 **'맥박(Pulse)'**                                                     |
| **목적**        | **AI가 사실(Fact)을 이해**하기 위함                | **사람이 지능의 상태를 감각**하기 위함                                                           |

**UCL(Unified Composition Language / Unified Context Layer)**은 시스템의 '지능'을 다룬다는 공통점이 있으나, **Nexnap은 ‘결과로서의 상태(Snapshot)’**를, **UCL은 ‘과정으로서의 논리(Protocol)’**를 담당한다는 점에서 명확히 구분됩니다.

### 5. Nexnap (넥스냅) : "지능의 맥박과 잔상"

Nexnap은 시스템의 추상적 지능 상태를 시청각적 피드백으로 변환하기 위한 **정규화된 데이터 스냅샷**입니다.

- **본질:** 시스템이 "지금 어떤 상태인가"를 보여주는 **동기화 규약**입니다.
- **역할:** 닉시(NIXIE)가 소리와 빛으로 연주하기 위한 **연료** 역할을 하며, `how_state`(흐름), `who_pulse`(페르소나), `confidence_score`(신뢰도) 등의 필드를 가집니다.
- **기술적 실체:** 주로 프론트엔드의 **Pinia 전역 스토어(`nexnapSnapshotStore.ts`)**에 상주하며 실시간으로 갱신됩니다.

### 6. UCL (유씨엘) : "지능의 악보와 집행"

UCL은 지능 운영체제(NEXA-OS)가 판단(IND)을 내리고 이를 실제 실행(EFF)으로 옮길 때 사용하는 **지능형 실행 프로토콜** 또는 **구성 언어**입니다.

- **본질:** 시스템이 "어떻게 움직여야 하는가"를 규정하는 **악보(Score)이자 지휘 매뉴얼**입니다.
- **역할:** 에이전트와 어댑터에게 전달되는 `execution_bundle`(실행 패키지), `constraints`(제약 조건), `is_virtual`(가상 실행 여부) 등의 **논리적 지시서**를 포함합니다.
- **기술적 실체:** 오케스트레이터 엔진과 백엔드 로직에서 작동하며, 실제 **실행 사슬(Execution Chain)**을 형성합니다.

### 7. 주요 차이점 비교

| 구분            | **Nexnap (넥스냅)**                        | **UCL (유씨엘)**                             |
| --------------- | ------------------------------------------ | -------------------------------------------- |
| **비유**        | 시스템이 살아있음을 알리는 **맥박(Pulse)** | 시스템을 지휘하는 **악보(Score)**            |
| **초점**        | **표현(Expression)** 및 사용자 체감        | **실행(Execution)** 및 논리 전개             |
| **데이터 구조** | 정규화된 **상태값** (how, who, confidence) | 복합적인 **실행 번들** (bundle, constraints) |
| **사용처**      | **NIXIE/NEXU 캔버스**의 시각적 동기화      | **오케스트레이터/어댑터**의 실제 동작 제어   |

### 8. 두 개념의 상호작용

NEXA 시스템 내에서 두 개념은 다음과 같이 맞물려 돌아갑니다.

1. **UCL이 연주를 시작합니다:** 인디케이터가 UCL 프로토콜에 따라 판단을 내리고 실행 번들을 생성합니다.
2. **Nexnap이 상태를 포착합니다:** UCL에 의해 실행이 일어나는 순간, 시스템의 상태 변화를 **Nexnap(스냅샷)**이 한순간 낚아챕니다.
3. **사용자가 감각합니다:** 낚아챈 Nexnap 데이터를 바탕으로 닉시가 **Lumina(발광)**와 **Jitter(떨림)**를 연주하여 사용자에게 지능의 상태를 전달합니다.

**결론:** **UCL**은 지능의 **생각과 행동을 짜는 틀**이고, **Nexnap**은 그 결과로 드러나는 **지능의 표정·맥박**을 담는 그릇이다. 두 이름은 바꿔 쓰지 않는다.

### 3. 실행 사슬(Execution Chain) 및 단계(Execution Steps)

실행 사슬은 Nexnap Protocol이 생성하는 “실시간 실행 엔티티”이며, 단계는 “원자적 마디(Atomic Action)”다.

| 용어                              | 의미 및 역할                                                         | 연결 필드/대상(문서 기준)                                                                        |
| --------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| execution_chains                  | 실행 사슬의 최상위 레코드(실시간 악보/상태 관리)                     | `execution_chains.packet_id`, `where_scope`, `when_tempo`, `who_pulse`, `how_state`, `why_chain` |
| packet_id                         | 실행 사슬 식별자(UUID v7 시간정렬 신뢰성 전제)                       | `execution_chains.packet_id`, `execution_steps.packet_id`                                        |
| actor_id                          | 실행 책임자 주체 ID(사용자/디바이스/에이전트)                        | `execution_chains.actor_id`                                                                      |
| actor_type                        | 실행 주체의 유형(USER/DEVICE/AGENT)                                  | `execution_chains.actor_type`                                                                    |
| execution_steps                   | 실행 사슬을 구성하는 원자 스텝 테이블                                | `execution_steps.step_status`, `is_virtual`, `timeline_branch_id`                                |
| step_sequence                     | 스텝 실행 순서                                                       | `execution_steps.step_sequence`                                                                  |
| step_status                       | 스텝 상태(FLOW/STUCK/COMPLETED/FAILED/VOID)                          | `execution_steps.step_status`                                                                    |
| is_virtual                        | 가상(Dry-run) 여부. 실물(EFF) 방지용 의미론적 잠금                   | `execution_steps.is_virtual`                                                                     |
| target_entity_type                | 대상 계열 구분(예: PHYSICAL/NEXU/AUTHORIZED_VIRTUAL/SIMULATION_NODE) | `execution_steps.target_entity_type`                                                             |
| timeline_branch_id                | 평행 타임라인(분기) 식별자                                           | `execution_steps.timeline_branch_id`                                                             |
| post_state_snapshot               | 타임머신 “뒤로가기” 복원 스냅샷                                      | `execution_steps.post_state_snapshot`                                                            |
| why_chain / why_step_logic        | 상태 전환의 인과 사슬(Reasoning + Effects)                           | `execution_chains.why_chain`, `execution_steps.why_step_logic`                                   |
| execution_bundle / context_bundle | 실행에 필요한 명령/제약/코일 가중치/페르소나 묶음                    | `execution_chains.execution_bundle`, `execution_chains.context_bundle`                           |

### 4. 상태 전이(State Lifecycle) — FLOW / STUCK / VOID (+ 확장)

실행 주체는 FLOW/STUCK/VOID를 순환하며, VOID는 단계별로 데이터의 생애를 다르게 취급한다.

| 상태/단계       | 의미 및 역할                                           | 전이(문서 임계치 요약)                     |
| --------------- | ------------------------------------------------------ | ------------------------------------------ |
| FLOW            | 실행/인지 흐름 활성화(정상 박동)                       | FLOW → STUCK                               |
| STUCK           | 흐름 막힘(응답 지연/충돌/대기)                         | STUCK → VOID.POTENTIAL                     |
| VOID            | 잠재/영감 대기(물리 삭제 아님)                         | VOID.POTENTIAL → VOID.ARCHIVE → VOID.PURGE |
| VOID.POTENTIAL  | 단기 잠재(재개 가능 구간)                              | 인디케이터/센서별 임계치 적용              |
| VOID.ARCHIVE    | 장기 압축/지식화 구간                                  | TimescaleDB 압축 시점(90일 등)             |
| VOID.PURGE      | 보존 조건 미충족 시 물리 삭제 후보                     | 기본 PURGE 임계치(365일 등)                |
| MOMENT          | (when_tempo) 맥락이 단기~중기 유지되는 시간축 구간     | MOMENT → DURATION                          |
| DURATION        | (when_tempo) 장기 미재개로 압축/지식화로 넘어가는 구간 | DURATION → ARCHIVE                         |
| ERA (신설/격상) | core 자산(“영혼(Soul)”로 승격)                         | ARCHIVE → ERA 후 purge 영구 제외           |
| Safety VOID     | 위험/Level0 위반 시 즉시 무효화                        | Safety guardrail 강제                      |
| UX VOID         | 사용자의 망설임/변심이 감지되어 영감 모드 진입         | 넥슈가 Nexnap 템플릿 성운 펼침             |
| Data VOID       | 노후화된 이력/규칙을 지식화하고 로우 데이터를 비움     | 지식/아카이브 정리                         |

| Nexnap Protocol | 전송/형식 계층(스키마, 필수 필드, 코드값, 라우트/채널, 왕복 인터페이스) |

### 10. 외부 자원 합성(동적 Substitution) 핵심 용어

외부 API/타 프로젝트 자원을 “잠재(VOID)”에서 “실체”로 끌어오는 프로토콜 용어다.

| 용어                                  | 의미 및 역할                                                      |
| ------------------------------------- | ----------------------------------------------------------------- |
| Resource Substitution(자원 차출/대체) | 문제 발생 또는 최적화 목적의 동적 대체                            |
| Where-Scope 필터링                    | 사고 지점 주변/유사 범위를 1ms급으로 좁히는 공간 스코프 필터      |
| project_network_topology              | 장치 간 거리/연결망을 저장하는 DB(“가까운 눈” 후보 계산의 기반)   |

| project_simulations                   | 가상 시뮬레이션 결과의 저장소(사전 평정/검증 근거)                |
| is_virtual=false 투입                 | 실제 EFF(실물 실행) 수행의 최종 단계(권한/신뢰 통과 필요)         |

### 11. 공유(Share)와 구독(Subscription) 및 보호 전략

“상시 공유 vs 동적 차용” 모두 대상 시스템 무결성을 유지해야 한다.

| 용어                           | 의미 및 역할                                                             |
| ------------------------------ | ------------------------------------------------------------------------ |
| device_members                 | 사용자↔디바이스 공유 멤버십/역할 매핑                                   |
| project_members                | 프로젝트 공유 멤버십(향후 확장)                                          |
| sharing_status                 | `active`/`suspended`/`revoked`(소유자 주권으로 즉시 무효화 가능)         |
| resource_sharing_policy        | 차용 우선순위/복구 조건/임대 기한(TTL)·할당량 제한을 담는 정책           |
| Suspension(Suspend)            | 소유자가 공유/차용 연결을 일시 중단해 원본을 독점 사용하도록 만드는 조치 |
| Revoke(영구 끊기)              | 소유자가 연결을 해제하고 차용자 접근을 영구 제거                         |

| Host-First Policy              | 본 디바이스/소유자 리소스가 항상 우선 점유(대여자는 남는 여력만 사용)    |
| Subscription(구독)             | “새로 생성하지 않고 타인의 데이터를 참조/관측”하는 실시간 연결 모델      |

### 12. Empathy(공감) 및 활력 지수(VI) 제동
