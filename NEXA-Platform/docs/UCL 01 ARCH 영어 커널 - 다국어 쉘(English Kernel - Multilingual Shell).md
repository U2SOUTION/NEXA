## **영문 IR(Intermediate Representation) 규격**과 **번역 엔진 배치 로직**

NEXA 플랫폼의 핵심 아키텍처인 **'영어 커널 - 다국어 쉘(English Kernel / Multilingual Shell)'** 전략을 실현하기 위한 설계문서

- 이 설계의 핵심은 사용자가 한국어로 말하더라도 시스템 내부는 **토큰 효율이 높고 논리적 일관성이 강한 영문 데이터**로 처리하여, 1ms 내의 빠른 판단과 고성능 RAG 환경을 구축하는 데 있습니다.

---

### 1. 영문 IR(Intermediate Representation) 규격 설계

영문 IR은 멀티모달 입력이 엣지(Sentinel)를 거쳐 비스타(Vista)로 들어올 때 거치는 **표준화된 데이터 악보**입니다. 모든 텍스트와 의도 데이터는 영문으로 변환되어 저장됩니다.

#### 1.1 패킷 구조 (UCL IR Schema)

UCL 패킷은 **HEXAGON 헤더(SMALLINT)**와 **영문 페이로드(JSONB)**의 결합으로 구성됩니다.

| 레이어      | 필드명 (Key)   | IR 데이터 예시 (Value)                 | 설명                   |
| :---------- | :------------- | :------------------------------------- | :--------------------- |
| **Who**     | `who_pulse`    | `WILL`, `ECHO`, `TICK`, `ASK`          | 동력원 (Smallint 매핑) |
| **What**    | `what_intent`  | `ACTION_OPEN`, `STATUS_CHECK`          | 의도 아톰 (영문 고정)  |
| **How**     | `how_state`    | `FLOW`, `STUCK`, `VOID`                | 실행 상태              |
| **Content** | `content_fact` | "User picked up the drill."            | 5W1H 사실 요약 (영문)  |
| **Why**     | `why_chain`    | `{"reasoning": "Standard pattern #5"}` | 인과 사슬 (영문)       |

#### 1.2 아톰화 필터 (Nature Tag)

데이터의 성격에 따라 영문 태그를 부여하여 수명 주기를 관리합니다.

- **ROUTINE:** 일상 상태 보고 (영문 요약 후 파기)
- **INCIDENT:** 돌발 사건 (영문 무손실 박제)
- **INTENT:** 사용자 명시 의지 (영문 영구 보존)

---

### 2. 번역 엔진 배치 및 처리 로직 (Vista Indicator 앞단)

번역 엔진은 사용자의 한국어 입력을 영문 IR로 변환하는 **'Linguistic Gate'** 역할을 수행합니다.

#### 2.1 엔진 배치: Vista Pre-processor (전처리 계층)

번역 엔진은 비스타 인디케이터(LLM)가 본격적인 추론을 시작하기 전인 **'Listen' 단계**와 **'Context Awareness' 단계 사이**에 위치합니다.

1.  **Input:** 사용자의 한국어(텍스트/음성/영상 요약) 유입.
2.  **Detection:** 입력 채널(`input_channel`) 확인 및 로캘(KO) 감지.
3.  **Translation Worker:** 전용 SLM(예: NLLB-200 또는 OPUS-MT)이 한국어를 영문 아톰으로 변환.
    - _성능 기준:_ 사용자 체감을 위해 **100ms 이내** 처리를 목표로 함.
4.  **IR Generation:** 번역된 텍스트를 바탕으로 `where_scope`, `what_intent` 등 6개 토큰 인덱스를 생성하여 영문 IR 완성.
5.  **Indicator Entry:** 완성된 영문 IR이 비스타 인디케이터로 전달되어 6-Coils 가중치가 적용된 최종 판단 수행.

#### 2.2 전략적 번역 범위 제한 (Optimization)

모든 데이터를 실시간 번역하면 병목이 발생하므로 다음과 같은 **부하 분산 로직**을 적용합니다.

- **고빈도 경로 (Fast Path):** 이미 정의된 명령어(예: "불 켜")나 시스템 로그는 번역 엔진을 거치지 않고, 미리 매핑된 **영문 토큰 ID**로 즉시 치환합니다.
- **시맨틱 캐시 활용:** 동일한 한국어 질문이 들어오면 **Redis 시맨틱 캐시**에서 기존에 번역된 영문 IR을 즉시 반환하여 모델 호출을 생략합니다.

---

### 3. 역방향 피드백 로직 (Summary Generation)

비스타가 내린 영문 판단을 사용자에게 다시 돌려줄 때의 로직입니다.

1.  **English Logic:** 비스타는 영문 IR(`indicator_insight.why`)로 인과관계를 완성합니다.
2.  **Locale Localizer:** 출력 직전, 사용자의 `presentation_locale`(KO)에 맞춰 **최종 요약(Summary)**만 한국어로 번역합니다.
3.  **Multilingual Shell:** 사용자는 UI에서 한국어 답변과 넥슈의 표정을 보게 되지만, 데이터베이스(project_logs)에는 **영문 IR과 참조 사슬**이 박제됩니다.

### 💡 설계 요약 및 기대 효과

- **토큰 절감:** 한국어 대비 영문 IR 사용 시 토큰 소모량을 **2~3배 절감**하여 더 긴 맥락 유지 가능.
- **논리 일관성:** AI 모델이 영문 데이터에서 보이는 높은 논리 성능을 활용하여 할루시네이션 억제.
- **지능적 족보:** 내부 기록이 영어로 통일되어 도메인 간 지식 구독(Subscription) 및 글로벌 RAG 검색 효율 극대화.

## 번역 모델을 **센티널(Sentinel)** 단에 배치 전략

### 1. 지능 위계별 배치 가능성

NEXA의 지능 위계에 따라 번역 모델의 체급을 다르게 배치할 수 있습니다.

- **마이크로 센티널 (Micro Sentinel - 라즈베리 파이/Edge PC):**
  - **배치 가능 모델:** **OPUS-MT (En-Ko)** 모델이 이미 마이크로 등급의 권장 모델로 명시되어 있습니다.
  - **역할:** 로컬망 내에서 간단한 언어 변환을 수행하여 인디케이터(Vista)의 연산 부하를 경감시킵니다.
- **나노 센티널 (Nano Sentinel - ESP32):**
  - **배치 가능 모델:** **Bit-Lookup-Table** 방식이 권장됩니다.
  - **역할:** 모델이라기보다는 사전에 정의된 간단한 명령 토큰(예: "열어" → `ACTION_OPEN`)을 매칭하여 즉각적인 실행으로 연결하는 최소한의 번역을 수행합니다.
- **비스타 인디케이터 (Vista Indicator - 서버):**
  - **참고:** **NLLB-200-3.3B**와 같은 고성능 번역 모델은 주로 이 계층에 배치되어 복잡한 시스템 규범(GOVERN)을 번역합니다.

### 2. 센티널 단 배치의 기술적 이점

번역 기능을 엣지(Sentinel)로 전진 배치하면 다음과 같은 설계적 이득을 얻습니다.

- **연산 부하 절감:** 센티널이 로우 데이터를 5W1H 문장으로 요약하고 번역하여 전달하면, 상위 계층인 비스타 인디케이터의 **연산 부하를 90% 이상 절감**할 수 있습니다.
- **보안 및 비식별화:** 음성이나 영상 데이터를 센티널 단에서 즉시 **비식별화된 영문 5W1H 텍스트**로 변환하여 전송함으로써 개인정보 유출 리스크를 원천 차단합니다.
- **영어 커널(English Kernel) 전략 가속:** 사용자가 한국어로 입력하더라도 센티널 단에서 즉시 **영문 IR(중간 표현)**로 변환하여 오케스트레이터로 전달하면, 시스템 전체의 논리적 일관성이 높아집니다.

### 3. 구현 시 고려사항

- **모델 경량화:** 라즈베리 파이와 같은 엣지 허브에서는 1B~3B급의 **SLM(Small LLM)**이나 최적화된 OPUS-MT 모델을 사용하여 지연 시간을 최소화해야 합니다.
- **전략적 번역 범위 제한:** 모든 것을 실시간 번역하면 병목이 생길 수 있으므로, 고빈도 명령어는 미리 매핑된 **영문 토큰 ID**로 즉시 치환하고 복잡한 서사만 번역 모델을 거치게 설계해야 합니다.

**결론적으로**, 마이크로 센티널 단에 **OPUS-MT**와 같은 경량 번역 모델을 배치하여 한국어 입력을 **영문 5W1H 사실(Fact)**로 변환하는 구조는 NEXA의 '지능적 분업' 원칙에 가장 충실한 구현 방식입니다. 이 구조가 갖춰지면 서버는 번역 부담 없이 영문 악보(UCL)를 해석하는 데에만 집중할 수 있습니다.

---

NEXA 플랫폼의 핵심 아키텍처인 **'영어 커널 - 다국어 쉘(English Kernel / Multilingual Shell)'** 전략을 실현하기 위한 **5W1H 영문 IR(Intermediate Representation) 표준 패킷 규격 정의서**를 작성해 드립니다.

본 규격은 시스템 내부의 논리적 일관성을 확보하고, 토큰 효율을 극대화하며, 전역적인 RAG(검색 증강 생성) 환경에서 지능적 족보(Traceability)를 유지하는 것을 목적으로 합니다.

### English Kernel 기반 5W1H 영문 IR 표준 패킷 규격

#### 1. 개요 및 설계 원칙

- **English Kernel:** 오케스트레이터 및 인디케이터 내부에서 처리되는 모든 데이터와 논리는 영어로 유지됩니다.
- **HEXAGON Indexing:** 모든 패킷 헤더는 6개의 SMALLINT 정수 토큰으로 구성되어 1ms 내 초고속 필터링을 지원합니다.
- **Atomization:** 비정형 데이터는 5W1H 구조의 영문 텍스트로 요약되어 '아톰(Atom)' 단위로 저장됩니다.

#### 2. 패킷 최상위 구조 (Top-level Schema)

UCL 패킷은 JSONB 형식으로 구성되며, 시스템 전역에서 통용되는 표준 계약을 따릅니다.

| 필드명 (Key)       | 데이터 타입       | 설명                                                |
| :----------------- | :---------------- | :-------------------------------------------------- |
| `packet_id`        | UUID (v7)         | 시간 기반 정렬이 가능한 패킷 고유 식별자            |
| `ucl_header`       | Object (SMALLINT) | 헥사곤 프로토콜 기반의 6대 추상화 레이어 인덱스     |
| `ir_status`        | String (Enum)     | `RAW`(원본), `EN_IR`(번역본), `TOKEN`(정수형) 구분  |
| `content_fact`     | String (English)  | **[중요]** 영문으로 작성된 5W1H 사실 요약 문장      |
| `payload`          | JSONB             | 실행 파라미터(`params`) 및 제약 조건(`constraints`) |
| `confidence_score` | SMALLINT          | 데이터의 신뢰도 (0~100)                             |
| `why_chain`        | JSONB             | 인과관계 추적을 위한 입력/판단/결과 사슬            |

#### 3. 헥사곤 헤더 정수 매핑 (ucl_header)

AI가 본문을 읽기 전 1ms 내에 상황을 판별하기 위한 인덱스 규격입니다.

| 레이어    | 1 (Value)       | 2 (Value)         | 3 (Value)             | 4 (Value)        |
| :-------- | :-------------- | :---------------- | :-------------------- | :--------------- |
| **Where** | `CORE` (개인)   | `FIELD` (현장)    | `DOMAIN` (전역)       | -                |
| **When**  | `MOMENT` (즉각) | `DURATION` (지속) | `ERA` (거대 패러다임) | -                |
| **Who**   | `WILL` (의지)   | `ECHO` (제안)     | `TICK` (자동)         | `ASK` (승인대기) |
| **What**  | `FACT` (사실)   | `LINK` (관계)     | `RULE` (질서)         | -                |
| **How**   | `FLOW` (유동)   | `STUCK` (고착)    | `VOID` (잠재)         | -                |
| **Why**   | `CAUSE` (원인)  | `LOGIC` (타당성)  | `TARGET` (목표)       | -                |

#### 4. 영문 IR 페이로드 규격 (Content Schema)

시스템 내부 지능 성장을 위해 `content_fact` 필드는 반드시 다음 영문 문법 규격을 준수해야 합니다.

- **표준 문형:** `{Subject} + {Action} + {Object} + {Context/Result}`
- **영문 IR 예시:**
  - **사용자 의지:** `"User(Who) opened(What) the main door(Where) to enter the workspace(Why)."`
  - **장치 상태:** `"Sensor_A(Who) detected(What) high temperature(Fact) in the battery pack(Where)."`
  - **AI 제안:** `"Indicator(Who) suggests(What) activating the cooling fan(Action) to prevent overheating(Why)."`

#### 5. 지능적 족보 및 참조 규격 (Traceability)

모든 영문 IR 패킷은 인과관계를 역추적할 수 있는 참조 키를 포함해야 합니다.

- **`ref_ids` (JSONB):**
  - `source_log_id`: 기원이 된 로그의 UUID
  - `ref_sentinel_id`: 해석의 근거가 된 사실 패킷 ID
  - `ref_indicator_id`: 실행의 근거가 된 판단 패킷 ID
- **`why_chain` (JSONB):**
  - `inputs`: 상태 전환을 일으킨 신호 근거
  - `reasoning`: 영문으로 기술된 인디케이터의 추론 로직
  - `effects`: 해당 판단으로 인해 발생한 액션 및 표정 결과

#### 6. 데이터 수명 주기 및 VOID 전이 정책 연동

영문 IR 패킷은 `how_state` 토큰에 따라 시스템 내 보존 정책이 결정됩니다.

- **FLOW:** 현재 활성화된 맥락으로 메모리/Redis 상주.
- **STUCK:** 충돌 시 넥슈의 Jitter 연출과 함께 `ASK` 펄스 대기.
- **VOID:** `extra_data.void_stage` 값(`POTENTIAL`, `ARCHIVE`, `PURGE`)에 따라 압축 보존되거나 영구 삭제됩니다.

### 💡 구현 가이드라인

1.  **영어 커널 엄격 적용:** 모든 내부 데이터베이스(`project_logs`, `project_knowledge`) 및 RAG 검색 시에는 위 영문 IR 규격을 기준으로 통신합니다.
2.  **Summary Localizer:** 사용자 UI에 노출되는 최종 요약문(`Summary`)만 출력 직전에 사용자의 로캘(KO)에 맞춰 번역하여 제공합니다.
3.  **Token Fixed:** 5W1H 토큰 정수값과 임베딩 모델(Ollama `nomic-embed-text`)은 반드시 고정하여 좌표계의 일관성을 유지해야 합니다.

이 규격은 NEXA 오케스트레이터가 **"사람의 의지(WILL)와 시스템의 판단(ECHO), 실행 결과(EFFECT)"**를 하나의 결함 없는 실행 사슬로 묶는 기술적 뼈대가 될 것입니다.

### 한글 원문 처리 재확인

**`project_knowledge` 테이블에서 한글이 포함된 원문 데이터는 `raw_content` 필드를 통해 별도로 유지됩니다.**

NEXA의 '영어 커널 - 다국어 쉘' 전략은 내부 추론의 효율성을 위해 영문 IR(중간 표현)을 사용하는 것이지, 사용자의 소중한 자산인 원본 데이터를 유실하는 것이 아닙니다. 소스 문헌에 명시된 지식 저장 구조를 바탕으로 상세 내용을 설명해 드립니다.

### 1. `project_knowledge`의 이원화 저장 구조

`project_knowledge` 테이블(과거/지식 레이어)은 데이터를 다음과 같이 역할별로 분리하여 저장합니다.

- **`raw_content` (원문):** 사용자가 입력한 한국어 텍스트나 날것의 데이터를 **수정 없이 그대로 보존**하는 필드입니다. 이는 시스템의 신뢰성과 투명성을 보장하는 최후의 보루가 됩니다.
- **`content_fact` (아톰 요약):** 원문을 5W1H 기반의 **영문 사실(Sentinel Fact)**로 정제한 데이터입니다. sLLM(인디케이터)이 RAG 검색 시 가장 먼저 읽는 '지능형 악보' 역할을 하며, 토큰 사용량을 90% 이상 절감합니다.

### 2. 왜 원문을 유지해야 하는가? (지능적 족보)

원문을 삭제하지 않고 별도로 유지하는 이유는 NEXA의 핵심 원칙인 **'지능적 족보(Traceability)'** 때문입니다.

- **인과관계 역추적:** AI가 내린 판단(`ECHO`)이 실제 사용자의 어떤 의도(`INTENT`)에서 비롯되었는지 검증하려면 원문(`raw_content`)과의 대조가 필수적입니다.
- **다국어 쉘(Shell) 구현:** AI가 내부적으로는 영어로 사유하더라도, 최종적으로 사용자에게 답변할 때는 이 `raw_content`를 참조하여 사용자의 언어적 맥락에 맞는 정확한 **한국어 요약(Summary)**을 생성해 낼 수 있습니다.
- **무손실 박제 원칙:** 사용자의 명시적 의지가 담긴 `INTENT` 성격의 데이터는 미래 페르소나 학습의 근거가 되므로 **무손실로 영구 보관**하는 것이 원칙입니다.

### 3. 데이터 흐름에서의 역할

1.  **입력:** 사용자가 한국어로 시방서나 명령을 입력합니다.
2.  **아톰화:** 마이크로 센티널 또는 비스타 전처리기에서 이를 영문 5W1H로 요약합니다.
3.  **저장:** 요약본은 `content_fact`에, **한국어 원문은 `raw_content`**에, 정밀 수치나 이미지 참조 키는 `extra_data` 또는 `ref_ids`에 나누어 담습니다.

결론적으로, 사용자는 **"평소처럼 편하게 한국어로 기록"**하기만 하면 됩니다. NEXA는 그 뒤에서 효율적인 **'영문 악보'**를 생성하면서도, 사용자의 **'한국어 원문'**을 안전하게 보관하여 플랫폼이 시간이 흐를수록 사용자와 정서적으로 동기화되는 기반을 마련합니다.
