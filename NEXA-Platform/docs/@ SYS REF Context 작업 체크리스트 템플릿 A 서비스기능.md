# {Context} PLAN {Context명} 작업 체크리스트

> 템플릿 A — 서비스 기능 중심 (AIS, NOD, BRD, ARC, TRC 등)
> 복사 후 {Context}, {Context명} 부분을 실제 값으로 교체하여 사용

---

## 0. 작업 시작 전 확인

- [ ] `SYS ARCH NEXA 전체 아키텍처` 읽기 — 전체 구조에서 이 Context의 위치 파악
- [ ] `SYS GLOSSARY NEXA 플랫폼 용어집` 확인 — 이 Context에서 쓰는 용어 정의 확인
- [ ] `DDL SCHEMA NEXA DB 설계 명세서` 확인 — 관련 테이블 파악
- [ ] `{Context} ARCH` 문서 읽기 — 이 Context 전체 구조 파악
- [ ] `SYS PLAN NEXA 전체 작업 순서` 확인 — 현재 작업 범위 확인

---

## 1. 방향 및 개념 정의

- [ ] `{Context} VISION` 또는 `{Context} CONCEPT` 작성 또는 확인
      → 이 Context가 왜 존재하는가, 무엇을 해결하는가

---

## 2. 요구사항 정의

- [ ] `{Context} PRD` 또는 `{Context} REQ` 작성
      → 사용자 관점에서 무엇이 필요한가
      → 기능 목록, 비기능 요구사항 (성능, 보안, 접근성)
      → 우선순위 정의

---

## 3. 제안 및 검토

- [ ] `{Context} RFC` 작성 — 구현 방향 제안
      → 기술 선택 이유
      → 대안과 비교
      → 미결 사항 목록
- [ ] RFC 검토 완료 후 → `{Context} ADR`로 전환
      → 결정 이유와 맥락 기록

---

## 4. 구조 설계

- [ ] `{Context} ARCH` 작성
      → 컴포넌트 구성
      → 외부 연동 (다른 Context, 외부 API)
      → 데이터 흐름
- [ ] 관련 Context와 인터페이스 협의
      → API 계약 정의
      → 이벤트/메시지 구조 정의

---

## 5. 세부 설계

- [ ] `{Context} DESIGN` 작성
      → UI 흐름 및 화면 구성
      → 컴포넌트 구조
      → 상태 관리 방식
- [ ] `{Context} SPEC` 작성
      → API 엔드포인트 및 파라미터
      → 입력 유효성 검사 조건
      → 오류 처리 및 예외 케이스
      → 권한 및 접근 제어

---

## 6. 데이터 구조 정의

- [ ] `{Context} SCHEMA` 작성 또는 `DDL SCHEMA` 업데이트
      → 테이블 및 컬럼 정의
      → 인덱스 전략
      → 마이그레이션 계획

---

## 7. 구현

- [ ] 백엔드 API 구현
      → SPEC 기준으로 엔드포인트 구현
      → 단위 테스트 작성
- [ ] 프론트엔드 구현
      → DESIGN 기준으로 UI 구현
      → 컴포넌트 테스트
- [ ] 통합 테스트
      → 다른 Context와 연동 확인
      → 엣지 케이스 확인

---
