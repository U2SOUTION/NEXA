## 2. ESP32 베이스라인 펌웨어 설계

### 2.1 개요

공장 초기화 후에도 OTA 수신만큼은 반드시 동작해야 한다.
사용자가 잘못된 펌웨어를 올리거나 설정을 초기화해도
플랫폼 웹서버 OTA로 복구 가능하도록 한다.

### 2.2 최소 기능 세트 (Baseline Feature Set)

| 기능                      | 필수 | 설명                                                                                                           |
| ------------------------- | ---- | -------------------------------------------------------------------------------------------------------------- |
| **WiFi AP 모드**          | ✓    | 초기화 직후 AP로 동작. SSID: `NEXA-ESP32-{MAC 뒷6자리}`. 경로 B 전용.                                          |
| **Improv Serial (USB)**   | ✓    | 경로 A 전용. Improv Wi-Fi 시리얼 표준으로 플랫폼이 USB 연결 시 SSID·비밀번호를 시리얼 전송. AP 접속 단계 생략. |
| **WiFi STA 모드**         | ✓    | 입력된 자격증명으로 라우터 연결. OTA·등록 통신을 위한 네트워크 확보.                                           |
| **OTA 수신 (HTTP/HTTPS)** | ✓    | 플랫폼 웹서버 URL에서 바이너리 다운로드 후 플래시.                                                             |
| **MQTT 클라이언트**       | ✓    | 등록 승인 후 provision 토픽 구독. 이후 운영 데이터 발행·명령 수신.                                             |
| **디바이스 식별**         | ✓    | MAC 주소·칩 ID 기반 고유 ID. 등록·OTA 경로 식별에 사용.                                                        |
| **NVS 저장**              | ✓    | WiFi 자격증명·device_secret·Capability ID·OTA URL 영구 저장.                                                   |
| **상태 보고**             | ✓    | `/status` JSON 응답. 버전·칩 정보·파티션 정보.                                                                 |

### 2.3 공장 초기화 후 부팅 플로우

```
[전원 ON] → [Bootloader] → [App 파티션 실행]
                                  ↓
                    NVS "wifi_configured" 확인
                      ↓                   ↓
                   미설정                설정됨
                      ↓                   ↓
              [WiFi AP 모드]        [WiFi STA 연결]
              NEXA-ESP32-xxxx             ↓
                      ↓            [MQTT 브로커 연결]
              경로 A or B                 ↓
              WiFi 자격증명 수신    [데이터 발행·명령 수신]
                      ↓
              [WiFi STA 연결]
                      ↓
              [POST /api/devices/register]
                      ↓
              [pending 대기]
                      ↓
              [사용자 승인]
                      ↓
              [MQTT provision 수신]
                      ↓
              [NVS 저장 → 재부팅]
                      ↓
              [정식 MQTT 연결]
```

### 2.4 이중 파티션·롤백 전략

| 항목                | 규격                                                                                                          |
| ------------------- | ------------------------------------------------------------------------------------------------------------- |
| **파티션 테이블**   | `ota_0`·`ota_1` 2개 앱 파티션. `partitions_two_ota.csv` 기반.                                                 |
| **부팅 검증**       | 새 파티션 부팅 후 N회 연속 실패 시 이전 파티션으로 롤백. `esp_ota_mark_app_invalid_rollback_and_reboot` 사용. |
| **베이스라인 보호** | 베이스라인 펌웨어는 고정 버전(예: v0.1.0-baseline)으로 태그. 롤백 시 이 버전으로 복귀 가능하도록 유지.        |
| **NVS 플래그**      | `factory_reset`·`wifi_configured`·`registered`·`provision_done` 등 상태 플래그 저장.                          |

### 2.5 OTA 수신 규격

| 항목            | 규격                                                                                    |
| --------------- | --------------------------------------------------------------------------------------- |
| **프로토콜**    | HTTPS GET. URL: `https://{platform}/api/ota/firmware?deviceId={id}&version={current}`   |
| **인증**        | `X-Device-Token: {device_secret}` 헤더. 미인증 요청 거부.                               |
| **응답**        | 바이너리 스트림 (`application/octet-stream`). 304(업데이트 불필요)·404(버전 없음) 처리. |
| **검증**        | 체크섬·크기 검증 (1단계). 코드 서명 검증 (장기 로드맵).                                 |
| **재시도**      | 네트워크 실패 시 백오프 (1분 → 5분 → 15분). 상한 설정.                                  |
| **MQTT 트리거** | `nexa/u/{user_id}/device/{mac}/ota` 토픽 수신 시 즉각 OTA 시작.                         |

### 2.6 펌웨어 주입 시나리오

| 시나리오         | 전제                       | 주입 경로                               |
| ---------------- | -------------------------- | --------------------------------------- |
| **시나리오 1**   | OTA 펌웨어가 없거나 손상됨 | USB + Web Serial로 베이스라인 최초 주입 |
| **시나리오 2-1** | OTA 가능 펌웨어 보유       | 캔버스 로직 구성 → ESPHome 빌드 → OTA   |
| **시나리오 2-2** | OTA 가능 펌웨어 보유       | 플랫폼 제공 템플릿 선택 → OTA 즉시 주입 |

## 3. NEXA 플랫폼 디바이스 등록 절차

### 3.1 등록 경로 전체 비교 — A~D

| **펌웨어 사전 탑재** | 불필요                    | **필수**                       | **필수**                 | **필수**                       |

| **iOS 지원**         | ✅                        | ✅                             | ❌ (Safari 미지원)       | ✅                             |
| **모바일 지원**      | ❌                        | ✅                             | Android Chrome만         | ✅                             |
| **보안성**           | ⭐⭐⭐ HMAC 서명          | ⭐⭐ HTTP 평문 (비밀번호 구간) | ⭐⭐⭐ BLE 페어링 암호화 | ⭐⭐⭐⭐ 넥슈 인증 + 로컬 채널 |

### 3.2 이중 등록 경로

```
① 회원가입·로그인
         ↓
② 기기등록 페이지 → "USB로 연결" 선택
         ↓
③ USB 연결 → 브라우저 팝업에서 시리얼 포트 선택·허용
         ↓
④ [펌웨어 없으면] ESP Web Tools로 베이스라인 플래시
         ↓
⑤ 플랫폼 UI에서 집 WiFi SSID·비밀번호 입력
   → Improv 프로토콜로 시리얼 전송 (AP 접속 없음)
         ↓
⑥ 디바이스 STA 연결
   → POST /api/devices/register 호출
   → pending_devices에 저장 (TTL 10분)
         ↓
⑦ 플랫폼 "등록 대기" 목록 표시
   → 사용자 승인·네이밍·도메인·위치 입력
   → 서버가 Capability ID 자동 생성
         ↓
⑧ MQTT provision 토픽으로 자격증명·Capability ID 전달
   → 디바이스 NVS 저장
         ↓
[등록 완료 → 정식 MQTT 연결]
```

### 3.3 경로 B — 무선 AP + Captive Portal

```
① 회원가입·로그인
         ↓
② 기기등록 페이지 → "무선으로 연결" 선택
         ↓
③ WiFi 목록에서 NEXA-ESP32-{MAC 뒷6자리} 선택
         ↓
④ "디바이스 설정 열기" → 192.168.4.1 접속
   Captive Portal에서 집 WiFi SSID·비밀번호 입력·저장
         ↓
⑤ 디바이스 STA 연결
   → POST /api/devices/register 호출
   → pending_devices에 저장 (TTL 10분)
         ↓
⑥ 플랫폼 "등록 대기" 목록 표시
   → 사용자 승인·네이밍·도메인·위치 입력
   → 서버가 Capability ID 자동 생성
         ↓
⑦ MQTT provision 토픽으로 자격증명·Capability ID 전달
   → 디바이스 NVS 저장
         ↓
[등록 완료 → 정식 MQTT 연결]
```

> **Captive Portal 보안 주의 (v0.2 추가)**
> 192.168.4.1은 HTTP (암호화 없음)
> → 비밀번호 필드 masking 필수
> → 입력·저장 후 즉시 AP 모드 종료
> → 전송 세션 단발성 처리
> → 가능하면 WiFi 비밀번호 대신 WPS 또는 QR 방식 장기 검토

### 3.5 경로 C — BLE + Web Bluetooth

```
전제: 베이스라인 펌웨어 탑재 디바이스
지원: PC Chrome·Edge · Android Chrome
미지원: iOS Safari · Firefox

① 플랫폼 로그인

② 디바이스: 전원 ON
   → BLE 광고 시작 ("NEXA-A1B2C3")

③ 넥슈: "새 디바이스 발견됐어요. 등록할까요?"
   → 브라우저가 BLE 스캔으로 자동 감지

④ 사용자: '등록' 클릭
   → 브라우저 팝업에서 BLE 디바이스 선택·허용

⑤ 브라우저 → BLE → 디바이스:
   현재 연결된 WiFi 정보 자동 전달

⑥ 디바이스: STA 연결
   → POST /api/devices/register 호출
   → pending 저장

⑦ 사용자: 이름·위치 입력 → 승인
   → Capability ID 확정
   → MQTT provision 전달

⑧ 넥슈: "등록됐어요 ✓"
   총 사용자 동작: 로그인 + 클릭 2회

보안:
  BLE 페어링 암호화 적용
  WiFi 비밀번호 BLE 채널로 암호화 전송
```

### 3.6 경로 D — 넥슈 허브 자동 감지

```
전제:
  1. 베이스라인 펌웨어 탑재 디바이스 (NEXA 배포 제품)
  2. 넥슈 실물 허브가 같은 네트워크에 존재

① 플랫폼 로그인

② 디바이스: 전원 ON
   → AP 모드 or BLE 광고 시작

③ 넥슈 허브: 자동 감지
   → mDNS or BLE로 미등록 디바이스 탐지
   → 플랫폼에 발견 이벤트 전송

④ 넥슈 (UI): "새 디바이스가 발견됐어요"
   → 사용자 확인 요청

⑤ 사용자: '등록' 클릭
   → 넥슈 허브가 WiFi 정보 로컬 채널로 전달

⑥ 디바이스: STA 연결 → register 호출

⑦ 자동 승인 or 사용자 이름·위치 입력
   → Capability ID 확정
   → MQTT provision 전달

⑧ 넥슈: "등록됐어요 ✓"
   NIXIE 캔버스에 새 도트 생성

공 ESP32 불가 이유:
  펌웨어 없음 → AP·BLE 모드 없음
  → 넥슈 허브가 감지할 신호 없음
  → 반드시 경로 A로 베이스라인 먼저 주입

보안:
  넥슈 허브 인증 + 로컬 채널
  외부 인터넷 노출 없이 WiFi 정보 전달
  가장 높은 보안성
```

### 3.5 Capability ID — 등록 시점 확정 (v0.2 신규)

**등록 요청 시 (약식 capabilities)**

```json
POST /api/devices/register
{
  "mac": "A1B2C3D4E5F6",
  "chipId": "ESP32_ABCDEF",
  "firmwareVersion": "v0.1.0-baseline",
  "capabilities": [
    "sensor.temperature",
    "sensor.humidity",
    "actuator.valve"
  ]
}
```

이 시점의 capabilities는 기능 유형만 표시한다.
Capability ID는 승인 시점에 확정된다.

**승인 시 (Capability ID 자동 생성)**

```json
POST /api/devices/approve
{
  "mac": "A1B2C3D4E5F6",
  "nickname": "스마트팜 A구역 복합 센서",
  "domain": "farm",
  "location": "field_a"
}
```

서버가 자동 생성하는 Capability ID:

```
nexa.{user_id}.farm.field_a.sensor.temperature.v1
nexa.{user_id}.farm.field_a.sensor.humidity.v1
nexa.{user_id}.farm.field_a.actuator.valve.v1
```

MQTT 토픽 자동 결정:

```
nexa/u/{user_id}/farm/field_a/sensor/temperature/{mac}/data
nexa/u/{user_id}/farm/field_a/sensor/humidity/{mac}/data
nexa/u/{user_id}/farm/field_a/actuator/valve/{mac}/data
```

**provision — MQTT로 전달 (폴링 대신)**

```
토픽: nexa/u/{user_id}/device/{mac}/provision
QoS: 1
Retain: true (재연결 시에도 수신)

페이로드:
{
  "device_id": "uuid",
  "device_secret": "64자 비밀키",
  "capabilities": [
    "nexa.usr_001.farm.field_a.sensor.temperature.v1",
    "nexa.usr_001.farm.field_a.sensor.humidity.v1",
    "nexa.usr_001.farm.field_a.actuator.valve.v1"
  ],
  "void_sec": 30,
  "coils": ["precision", "sensitivity"],
  "ota_url": "https://app.yourdomain.com/api/ota/firmware"
}
```

디바이스 수신 후:

```
1. NVS에 device_secret·capabilities·ota_url 저장
2. provision 토픽 구독 해제
3. 이후 HMAC 서명으로 정식 MQTT 연결
4. Capability ID 기반 동적 토픽으로 데이터 발행 시작
```

### 3.6 pending 보안 보완 (v0.2 신규)

**문제**

```
POST /api/devices/register는 비인증 엔드포인트
→ 악의적으로 수천 개의 가짜 pending 요청 가능
→ 사용자 화면 오염
→ DOS 공격 가능성
```

**방어 전략**

```
Rate Limiting:
  동일 IP → 분당 5회 제한
  동일 MAC → 시간당 10회 제한
  초과 시 30분 자동 차단

TTL:
  pending 항목 10분 후 자동 삭제
  10분 안에 승인 안 하면 재등록 필요

중복 방지:
  같은 MAC의 pending이 이미 있으면
  기존 항목 TTL 초기화 후 재사용
  새 항목 생성 금지

보안 로그:
  비정상 요청 → security_events 기록
  IP 기반 반복 시도 자동 탐지
```

### 3.7 등록 API 스펙 (v0.2 보완)

| 메서드   | 경로                    | 인증                   | 설명                                                                      |
| -------- | ----------------------- | ---------------------- | ------------------------------------------------------------------------- |
| `POST`   | `/api/devices/register` | 없음 (Rate Limit 적용) | 디바이스 등록 요청. Body: `{mac, chipId, firmwareVersion, capabilities}`  |
| `GET`    | `/api/devices/pending`  | JWT (사용자)           | 등록 대기 목록 조회 (TTL 10분 이내)                                       |
| `POST`   | `/api/devices/approve`  | JWT (사용자)           | 승인·네이밍·Capability ID 확정. Body: `{mac, nickname, domain, location}` |
| `GET`    | `/api/devices`          | JWT (사용자)           | 등록된 디바이스 목록                                                      |
| `PATCH`  | `/api/devices/:id`      | JWT (사용자)           | 디바이스 정보 수정                                                        |
| `DELETE` | `/api/devices/:id`      | JWT (사용자)           | 디바이스 삭제                                                             |
| `GET`    | `/api/ota/firmware`     | device_secret          | OTA 바이너리 제공                                                         |

### 3.8 인증·권한

| 구분          | 규격                                                            |
| ------------- | --------------------------------------------------------------- |
| **등록 요청** | 비인증 허용 (Rate Limit 필수). pending 저장만. 소유자 미확정.   |
| **승인**      | JWT 인증 사용자만. 승인 시점에 user_id와 디바이스 연결.         |
| **등록 후**   | device_secret + HMAC-SHA256 서명. MQTT·OTA 요청 모두 서명 검증. |
| **토픽 격리** | EMQX ACL로 user_id 기반 자신의 토픽만 접근.                     |

### 3.9 복구 시나리오

**VI (Vitality Index · 활력 지수) 0.0 감지 (응답 없음)**

```
플랫폼이 VI 0.0 감지 (VOID 상태)
  → 넥슈 알림: "디바이스를 USB로 연결하면 자동 복구합니다"
  → 사용자 USB 연결
  → ESP Web Tools로 베이스라인 재플래시
  → Improv로 WiFi 재설정
  → 재등록 절차 진행
```

**OTA 실패 → 자동 롤백**

```
새 펌웨어 부팅 실패
  → 이전 파티션 자동 복귀
  → 플랫폼에 롤백 이벤트 MQTT 발행
  → 사용자에게 알림
```

## 4. 외부 라이브러리 사용 전략

### 4.1 OTA 가능 기초 구조

| 목적                  | 선택 방안                                             | 비고                                                   |
| --------------------- | ----------------------------------------------------- | ------------------------------------------------------ |
| **OTA 바이너리 수신** | `HTTPClient`(Arduino) 또는 `esp_http_client`(ESP-IDF) | HTTPS GET. device_secret 헤더 포함.                    |
| **파티션·롤백**       | ESP-IDF `esp_ota_ops`                                 | Arduino `Update`는 USB 전용. HTTP 기반 별도 구현 필요. |
| **빌드·플래시**       | PlatformIO                                            | ESP-IDF/Arduino 모두 지원. `partitions.csv` 공유.      |
| **MQTT 클라이언트**   | PubSubClient 또는 AsyncMqttClient                     | provision 토픽 구독·데이터 발행.                       |
| **HMAC 서명**         | mbedtls (ESP32 내장)                                  | device_secret 기반 HMAC-SHA256.                        |
| **NVS 저장**          | Preferences 라이브러리                                | device_secret·Capability ID·OTA URL 저장.              |

### 4.2 최초 등록 UX

| 사용자 경험                 | 라이브러리·방식                                    | 설명                                                   |
| --------------------------- | -------------------------------------------------- | ------------------------------------------------------ |
| **경로 B — Captive Portal** | `DNSServer` + `WebServer` 또는 `ESPAsyncWebServer` | AP 모드에서 모든 HTTP 요청을 설정 페이지로 리다이렉트. |
| **경로 B — WiFi 관리**      | `WiFiManager`(tzapu) 또는 자체 구현                | SSID·비밀번호 입력 후 STA 전환.                        |
| **경로 A — USB 등록**       | ESP Web Tools + Improv Wi-Fi                       | 플랫폼에서 펌웨어 플래시·SSID 시리얼 전송.             |
| **디바이스 발견**           | mDNS (`ESPmDNS`)                                   | `NEXA-ESP32-xxxxxx.local` 형태로 LAN 발견.             |
| **ArduinoJson**             | ArduinoJson                                        | HEXAGON 패킷·provision 페이로드 파싱.                  |

### 4.3 베이스라인 권장 조합

```
최소 필수:
  WiFi (AP/STA)
  Improv Serial (경로 A)
  WebServer + DNSServer (경로 B Captive Portal)
  HTTPClient (OTA)
  PubSubClient (MQTT)
  mbedtls (HMAC 서명)
  Preferences (NVS)
  ArduinoJson (패킷 파싱)

선택:
  WiFiManager (편의성, 의존성 증가)
  mDNS (LAN 발견 편의)
  AsyncMqttClient (비동기 MQTT)
```

## 5. 두 가지 등록 시나리오 현재 구현 상태

| 시나리오      | 주체          | 플로우                                                                  | 현재 구현                   |
| ------------- | ------------- | ----------------------------------------------------------------------- | --------------------------- |
| **수동 등록** | 사용자 먼저   | 로그인 → MY → 디바이스 등록 → device_token 발급 → 디바이스에 입력       | ✅ 구현됨                   |
| **자동 등록** | 디바이스 먼저 | 디바이스 WiFi 획득(경로 A/B) → register → pending → approve → provision | 🔜 경로 A/B UI 구현 시 추가 |

**통합 방향**:
두 시나리오 모두 장기 지원.
수동 등록은 현재 사용 가능.
자동 등록은 ESP32 베이스라인·경로 A/B UI 구현 시 API·UI 추가.

## 6. 사용자 디바이스 사용법 안내 카탈로그

### 6.1 제작·배포 절차

| 단계  | 절차                                                     |
| ----- | -------------------------------------------------------- |
| **1** | 경로별 카탈로그 제작 (통합판 또는 경로별 단독판)         |
| **2** | 플랫폼 URL·QR 코드 포함                                  |
| **3** | 디바이스 정보 라벨 점검 (`NEXA-ESP32-xxxxxx` SSID 예시)  |
| **4** | **브라우저 요구사항 명시** (경로 A: PC Chrome·Edge 전용) |
| **5** | 포장 동봉 후 배포                                        |

### 6.2 카탈로그 A — 경로 A (USB, PC Chrome·Edge 전용)

| 단계                    | 안내 내용                                                             | 사용자 행동       |
| ----------------------- | --------------------------------------------------------------------- | ----------------- |
| **1. 준비**             | PC (Chrome 또는 Edge 필수), USB 케이블, WiFi 환경, NEXA 계정.         | 계정 가입·로그인. |
| **2. 전원 연결**        | ESP32를 PC에 USB로 연결. LED 점등 확인.                               | USB 연결.         |
| **3. 기기등록 페이지**  | NEXA 플랫폼 → "디바이스 등록" → "USB로 연결" 선택.                    | 플랫폼 진입.      |
| **4. 시리얼 연결**      | "시리얼 연결" 버튼 → 브라우저 팝업에서 포트 선택·허용.                | 포트 선택.        |
| **5. 펌웨어·WiFi 설정** | [펌웨어 없으면] 베이스라인 플래시. 집 WiFi SSID·비밀번호 입력 → 전송. | 한 화면에서 완료. |
| **6. 등록 승인**        | 플랫폼 "등록 대기" 목록에서 디바이스 선택 → 이름·위치 입력 → 승인.    | 등록 완료.        |
| **7. 사용 시작**        | 플랫폼 대시보드에서 제어·모니터링·OTA.                                | 사용 시작.        |
| **8. 문제 발생**        | 공장 초기화 후 2~6단계 재진행.                                        | 복구.             |

> **⚠️ 경로 A는 PC Chrome 또는 Edge에서만 동작합니다.**
> Firefox·Safari·모바일 브라우저는 지원하지 않습니다.
> 해당 브라우저 사용 불가 시 경로 B(무선)를 이용하세요.

### 6.3 카탈로그 B — 경로 B (무선, 모든 기기·브라우저)

| 단계                    | 안내 내용                                                                   | 사용자 행동        |
| ----------------------- | --------------------------------------------------------------------------- | ------------------ |
| **1. 준비**             | 스마트폰 또는 PC, WiFi 환경, NEXA 계정.                                     | 계정 가입·로그인.  |
| **2. 전원 연결**        | USB로 전원 연결. LED 점등 확인.                                             | 전원 ON.           |
| **3. 기기등록 페이지**  | NEXA 플랫폼 → "디바이스 등록" → "무선으로 연결" 선택.                       | 플랫폼 진입.       |
| **4. 디바이스 AP 접속** | WiFi 목록에서 `NEXA-ESP32-xxxxxx` 선택. "디바이스 설정 열기" → 192.168.4.1. | ESP32 AP 연결.     |
| **5. 집 WiFi 입력**     | Captive Portal 폼에 SSID·비밀번호 입력 후 저장.                             | 집 WiFi 정보 입력. |
| **6. 등록 승인**        | 플랫폼 "등록 대기" 목록에서 디바이스 선택 → 이름·위치 입력 → 승인.          | 등록 완료.         |
| **7. 사용 시작**        | 플랫폼 대시보드에서 제어·모니터링·OTA.                                      | 사용 시작.         |
| **8. 문제 발생**        | 공장 초기화(버튼 길게 누른 채 전원 ON) 후 2~6단계 재진행.                   | 복구.              |
