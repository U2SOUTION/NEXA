# NEXA UCL 파싱 로직의 5단계 프로토콜 프레임워크

> **플랫폼 철학 (Principle Statement)**
> "사람을 단순함에서 해방시켜, 더 넓은 의식과 더 온화한 삶으로 이어주는 겸허한 공간"

---

## 0. 철학 레이어 (Philosophy Layer) — 모든 단계의 뿌리

> 이 레이어는 코드가 아니라 **판단의 기준**이다.
> 모든 단계는 아래 5가지 원칙을 위반하지 않아야 한다.

| 원칙                | 정의                                         | 실제 적용                         |
| ------------------- | -------------------------------------------- | --------------------------------- |
| **Liberation**      | 단순·반복은 AI가, 판단·창조는 사람이         | 자동화 가능한 것은 확인 없이 처리 |
| **Humanity**        | 사람이 소외되는 방향으로 작동하지 않는다     | 실행 전 사람 확인 단계 보장       |
| **Domain Fluidity** | 농업·산업·일상·예술의 경계를 구분하지 않는다 | 어댑터를 도메인 중립적으로 설계   |
| **Expansion**       | 의식이 더 넓어지도록 새로운 연결을 제시한다  | 답변 후 확장 관점 제안            |
| **Humility**        | 화려함보다 본질, 복잡함보다 단순함           | 불필요한 출력 제거, 핵심만 전달   |

---

## 권한 레이어 (Authority Layer) — 선 룰을 누가 만들고 수정하는가

```
Level 0 — 시스템 절대 규칙 (수정 불가)
  └─ 예: "사람의 안전을 위협하는 명령은 실행하지 않는다"
  └─ 예: "최종 결정은 항상 사람에게 있다"

Level 1 — 플랫폼 운영자 규칙 (관리자만 수정)
  └─ 예: "우천 시 창문 개방 금지"
  └─ 예: "결제는 반드시 2차 인증"

Level 2 — 사용자 정의 규칙 (사용자가 편집 가능)
  └─ 예: "오전 7시 이전 알림 금지"
  └─ 예: "내 취향 기반 콘텐츠 우선"

Level 3 — AI 학습 제안 규칙 (사용자 승인 후 적용)
  └─ 예: "최근 3회 거절한 패턴 → 룰 추가 제안"
  └─ 예: "자주 쓰는 조합 → 단축 룰 생성 제안"
```

> **충돌 시 우선순위**: Level 0 > Level 1 > Level 2 > Level 3

## 1단계 — Listen (멀티모달 입력)

### 핵심 목표

다양한 형태의 입력을 **5W1H 표준 데이터 모델(JSONB)**로 일원화한다.

### 입력 전처리 분리 구조

```
[텍스트 입력]  ──┐
[음성 입력]    ──┼──→ [타입별 전처리기] ──→ [5W1H JSONB 통합기] ──→ 2단계
[영상 입력]    ──┘
```

### 5W1H 중간 언어 (Intermediate Representation) 표준

```jsonb
{
  "who":   "사용자 ID 또는 요청 주체",
  "what":  "실행 요청 행위 (동사 + 목적어)",
  "when":  "시간 조건 또는 즉시",
  "where": "대상 공간 또는 시스템",
  "why":   "추론된 의도 (생략 가능)",
  "how":   "방식 또는 파라미터",
  "raw":   "원본 입력 보존",
  "input_type": "text | voice | video",
  "confidence": 0.0 ~ 1.0
}
```

### 예시

```jsonb
{
  "who":   "user_001",
  "what":  "창문 열기",
  "when":  "즉시",
  "where": "거실",
  "why":   "환기 추정",
  "how":   "전체 개방",
  "raw":   "창문 좀 열어줘",
  "input_type": "voice",
  "confidence": 0.91
}
```

### 예외 흐름

| 상황                      | 처리 방식                                        |
| ------------------------- | ------------------------------------------------ |
| 입력 신호 없음            | 타임아웃 후 재요청 또는 대기                     |
| 변환 실패 (노이즈·불명확) | confidence 0.5 미만 → 2단계에 불확실 플래그 전달 |
| 지원하지 않는 입력 형식   | 사용자에게 지원 형식 안내 후 종료                |
| 악의적 입력 감지          | Level 0 규칙 발동 → 즉시 차단 후 로그 기록       |

## 2단계 — Context Awareness (상황 인지 및 검토)

### 핵심 목표

명령만 보는 것이 아니라 **현재 상태(State)** 와 **허용 규칙(Rule)** 을 대조하여 충돌을 감지한다.

### 상태 + 룰 대조 구조

```
[5W1H JSONB]
      │
      ▼
[현재 상태 조회]          [선 룰 조회 (Level 0~3)]
  - 기기 상태               - 절대 규칙
  - 환경 센서               - 운영자 규칙
  - 사용자 컨텍스트          - 사용자 규칙
  - 최근 대화 이력           - AI 학습 룰
      │                          │
      └──────────┬───────────────┘
                 ▼
          [충돌 감지기]
         /            \
    충돌 없음         충돌 있음
        │                 │
     3단계          [충돌 해소 엔진]
```

### 충돌 해소 우선순위

```
1순위: 안전 룰 (Level 0) — 항상 절대 우선
2순위: 사용자 명시 의도 — "반드시"·"꼭" 등 강조 표현
3순위: 운영자 규칙 (Level 1)
4순위: 사용자 정의 룰 (Level 2)
5순위: 시스템 기본값
```

### 충돌 감지 예시

| 명령 (What) | 상황 (When/Where) | 선 룰                   | 결과                     |
| ----------- | ----------------- | ----------------------- | ------------------------ |
| 창문 열기   | 현재 비가 옴      | 우천 시 개방 금지       | ⚠️ 충돌 → 사용자 확인    |
| 가스 켜기   | 외출 상태 감지    | 외출 중 가스 금지       | ❌ Level 0 차단          |
| 음악 재생   | 오전 6시          | 오전 7시 이전 알림 금지 | ⚠️ 충돌 → 무음 모드 제안 |
| 결제 실행   | 정상 상태         | 결제 2차 인증 필수      | 👤 인증 요청 후 진행     |

### 예외 흐름

| 상황                        | 처리 방식                               |
| --------------------------- | --------------------------------------- |
| 상태 조회 실패 (센서 오류)  | 안전 방향으로 보수적 판단 후 3단계 전달 |
| 룰 DB 접근 불가             | Level 0 절대 규칙만 적용 후 진행        |
| 충돌 해소 불가 (룰 간 모순) | 상위 Level 룰 우선 적용 + 운영자 알림   |
| 새로운 상황 (룰 미정의)     | 불확실 플래그 추가 후 3단계로 전달      |

## 3단계 — Decision Making (의사결정 계층)

### 핵심 목표

**확신도(Confidence) × 위험도(Risk) × 긴박도(Urgency)** 를 계산하여 실행 모드를 결정한다.

### Decision Matrix (핵심 알고리즘)

| 확신도 | 위험도 | 룰 충돌      | 긴박도      | 실행 모드                   | NEXA 철학  |
| ------ | ------ | ------------ | ----------- | --------------------------- | ---------- |
| High   | Low    | 없음         | Any         | ✅ 즉시 실행                | Liberation |
| High   | Low    | 있음         | Low         | 🔔 충돌 보고 후 대기        | Humanity   |
| High   | Mid    | 없음         | Low         | 👤 사용자 확인 요청         | Humanity   |
| Low    | Any    | Any          | Low         | 👤 사용자 확인 요청         | Humanity   |
| Any    | High   | Any          | Low         | ❌ 조언·거절                | Humanity   |
| Any    | Any    | Level 0 위반 | Any         | 🚫 즉시 차단 + 로그         | Humility   |
| Any    | Any    | Any          | High (긴박) | 🚨 긴박 모드 (룰 일부 우회) | Liberation |

### 확신도·위험도·긴박도 계산 기준

```
확신도 (Confidence)
  - 1단계 입력 confidence 값 상속
  - 2단계 충돌 없음 시 +0.1 보정
  - 2단계 충돌 있음 시 -0.2 보정

위험도 (Risk)
  - Low  : 되돌리기 쉬운 행동 (불 켜기, 음악 재생)
  - Mid  : 되돌리기 가능하나 확인 필요 (결제, 문 열기)
  - High : 되돌리기 어렵거나 안전 관련 (가스, 삭제, 외부 전송)

긴박도 (Urgency)
  - High : 화재·응급·시간 임박 감지 시
  - Low  : 일반 상황
```

### 실행 모드별 동작

```
✅ 즉시 실행    → 4단계 어댑터로 바로 전달
👤 확인 요청   → 사용자에게 요약 보고 → 승인 대기 → 승인 시 4단계
🔔 충돌 보고   → 충돌 내용 설명 → 사용자 선택 요청
❌ 조언·거절   → 이유 설명 + 대안 제시 → 종료
🚫 즉시 차단   → 차단 이유 기록 + 운영자 알림 → 종료
🚨 긴박 모드   → Level 1~2 룰 우회 + 사후 보고
```

### 예외 흐름

| 상황                    | 처리 방식                                |
| ----------------------- | ---------------------------------------- |
| 확신도·위험도 계산 불가 | 보수적 판단 → 👤 확인 요청으로 fallback  |
| 사용자 확인 타임아웃    | 기본값(거절 또는 안전 행동) 적용 후 로그 |
| 긴박 모드 오판 감지     | 사후 피드백으로 긴박도 기준 재조정       |

## 4단계 — Adapter Execution (어댑터 실행)

### 핵심 목표

UCL 파서의 **논리 명령(Abstract Command)** 을 실제 기기·서비스가 이해하는 **네이티브 API 명령**으로 번역한다.
파서는 "무엇을 할지"만 결정하고, "어떻게 할지"는 어댑터가 해결한다.

### 도메인 독립 구조

```
[UCL 파서 논리 명령]
"온도를 2도 높여라"
        │
        ▼
[어댑터 레지스트리] ── 현재 등록된 어댑터 목록 조회
        │
   ┌────┴────┐
   ▼         ▼
[에어컨 어댑터]   [보일러 어댑터]   [기타 어댑터...]
set_temp(+2)      set_heat(+2)
Samsung API       KD Boiler API
```

### 어댑터 종류 (도메인별)

| 도메인    | 어댑터 예시             | NEXA 철학 연결         |
| --------- | ----------------------- | ---------------------- |
| 일상·IoT  | 조명·온도·보안·가전     | Liberation (반복 해방) |
| 업무      | 문서·이메일·캘린더·결제 | Liberation             |
| 농업      | 센서·드론·관개 시스템   | Domain Fluidity        |
| 산업      | 설비·모니터링·물류      | Domain Fluidity        |
| 예술·창작 | 이미지·음악·영상 생성   | Expansion              |
| 지식      | RAG 검색·문서 분석      | Expansion              |

### 어댑터 실패 처리

```
실행 시도
    │
    ├─ 성공 → 5단계 피드백
    │
    ├─ 실패 → [대체 어댑터 탐색]
    │              │
    │         대체 있음 → 대체 어댑터 실행 → 사용자에게 "대체 실행" 보고
    │         대체 없음 → 실패 보고 + 수동 처리 안내
    │
    └─ 부분 성공 → 성공 부분 보고 + 실패 부분 수동 처리 요청
```

### 예외 흐름

| 상황                     | 처리 방식                                      |
| ------------------------ | ---------------------------------------------- |
| 어댑터 미등록 도메인     | 사용자에게 안내 + 어댑터 추가 제안             |
| API 응답 지연 (타임아웃) | 재시도 2회 → 실패 처리                         |
| 권한 없는 API 호출       | 권한 확인 요청 후 재시도 또는 취소             |
| 어댑터 버전 불일치       | 레지스트리 업데이트 알림 + 구버전으로 fallback |

## 5단계 — Feedback Loop (피드백 루프)

### 핵심 목표

단순 결과 보고를 넘어 **즉각·단기·장기** 3계층으로 피드백을 처리하여 플랫폼이 시간과 함께 성장한다.

### 피드백 3계층 구조

```
[실행 결과: 성공 / 실패 / 부분 성공]
              │
    ┌─────────┼─────────┐
    ▼         ▼         ▼
[즉각 피드백] [단기 학습] [장기 진화]
이번 실행     이 사용자   플랫폼 전체
결과 보고     패턴 업데이트  패턴 분석
```

### 즉각 피드백 (Immediate)

```
- 성공: "창문을 열었습니다" + 현재 상태 보고
- 실패: "창문을 열지 못했습니다 + 이유 + 대안 제시"
- 부분 성공: "거실 창문은 열었으나 안방 창문은 실패했습니다"
- 긴박 모드 사후: "긴박 상황으로 룰을 우회하여 실행했습니다" + 승인 요청
```

### 단기 학습 (Short-term Learning)

```
- 사용자가 3회 이상 같은 패턴 실행 → Level 3 룰 추가 제안
- 사용자가 확인 요청을 항상 승인 → 해당 명령을 즉시 실행으로 격상 제안
- 사용자가 특정 제안을 반복 거절 → 해당 제안 빈도 감소
→ 모든 변경은 사용자 승인 후 적용 (Humanity 원칙)
```

### 장기 진화 (Long-term Evolution)

```
- 전체 사용자 패턴 분석 → 새로운 어댑터 필요성 감지 → 개발 제안
- 자주 충돌하는 룰 조합 감지 → 룰 구조 개선 제안
- 도메인 사용 빈도 분석 → 플랫폼 확장 방향 제시
  (개인 → 팀 → 범용 → 아트 플랫폼으로의 진화 경로 추적)
```

### 예외 흐름

| 상황                  | 처리 방식                                   |
| --------------------- | ------------------------------------------- |
| 기기 응답 없음        | 타임아웃 후 "확인 불가" 보고 + 재확인 요청  |
| 학습 데이터 부족      | 최소 5회 이상 패턴 확인 후 제안             |
| 사용자 피드백 거절    | 학습 보류 + 3회 거절 시 해당 패턴 학습 중단 |
| 장기 진화 제안 과부하 | 제안 빈도 제한 (주 1회 이하)                |

## 전체 흐름도

```
[입력]
  │
  ▼
[1단계: Listen]
  5W1H JSONB 변환
  │
  ├─ 변환 실패 → 재요청
  │
  ▼
[2단계: Context Awareness]
  상태 + 선 룰 대조
  충돌 감지 및 해소
  │
  ├─ Level 0 위반 → 즉시 차단
  │
  ▼
[3단계: Decision Making]
  확신도 × 위험도 × 긴박도
  Decision Matrix 적용
  │
  ├─ 즉시 실행 ──────────────────────┐
  ├─ 확인 요청 → 사용자 승인 → ───┤
  ├─ 조언·거절 → 종료               │
  └─ 긴박 모드 → ──────────────────┤
                                    ▼
                          [4단계: Adapter Execution]
                          논리 명령 → 네이티브 API
                          어댑터 선택 및 실행
                                    │
                          ├─ 실패 → 대체 어댑터 시도
                                    │
                                    ▼
                          [5단계: Feedback Loop]
                          즉각 · 단기 · 장기 피드백
                          사용자 보고 + 학습 + 진화
```
