# \_ 용어 및 시스템 설계 파일 관리 디렉토리 및 기획 자원 구조

본 문서는 NEXA Knowledge OS 자산을 위한 디렉토리 책임과 `views/` 하위 Vue 파일 **예상 구조(기획안)** 를 정의한다.

> 네임스페이스 원칙: `nexa_knowledge_*`는 플랫폼 공통 Knowledge OS 계층이며,
> `project_knowledge`는 해당 계층 위에서 생성되는 프로젝트 단위 지식 분기다.

## 넥사 시스템 기획문서를 넘어 철학적 토대 자산화

NEXA는 단순한 '용어 사전'을 넘어 플랫폼 전체의 사유 방식과 실행 원칙을 규정하는 **지능형 지식 운영체제(Knowledge OS)**로 진화했습니다.

이 구조에서는 기술적인 DB 설계나 코딩 규칙보다, 오히려 시스템의 **개념, 철학, 원리**를 어떻게 정의하느냐가 시스템의 '지능 지수(IQ)'와 '공감 능력(EQ)'을 결정짓는 핵심 연료가 됩니다.

### 1. 철학이 곧 시스템의 '판단 로직'이 됩니다 (6-COILS & Empathy)

NEXA에서 철학과 가치관은 관념에 머물지 않고 실질적인 **'가치 필터(Value Filter)'**로 작동합니다.

- **6-COILS (판단의 영혼):** 안전, 안정성, 효율, 자율성, 조화, 창의성이라는 6가지 가치는 AI가 데이터를 해석하는 '렌즈'입니다. 똑같은 데이터(FACT)라도 사용자가 '창의성' 코일을 높이면 시스템은 실험적인 제안을 하고, '안전'을 높이면 보수적으로 반응합니다.
- **Empathy (판단의 전제):** 공감은 단순한 설정이 아니라 모든 판단의 **'가드레일'**입니다. '비수단화', '비소외', '비대체'라는 철학적 원칙을 기계가 감지할 수 있는 조건(ES, VI 지수)으로 변환하여, 사용자가 지쳐 있을 때 시스템이 스스로 조용해지는 등의 지능적 배려를 수행합니다.

### 2. 육하원칙(HEXAGON)이 AI의 '사유 문법'이 됩니다

단순한 데이터 나열이 아니라 **서사적 구조(Narrative Structure)**를 잘 정리할수록 AI는 상황을 1ms 내에 파악하게 됩니다.

- **지능적 인덱스:** HEXAGON(5W1H) 프로토콜은 데이터의 족보를 만드는 '문법'입니다.
- **초고속 필터링(Pruning):** "어디서(Where), 누가(Who), 어떤 의도(What)로"라는 추상적 개념이 잘 정의되어 있을수록, AI는 수억 개의 데이터 중 현재 맥락에 맞지 않는 90%를 즉시 걸러내어 연산 효율을 극대화합니다.

### 3. '여백(VOID)'의 미학이 시스템을 최적화합니다

NEXA는 동양 철학의 **空(공)** 개념을 기술적으로 구현한 **VOID** 생애주기를 가집니다.

- **잠재적 가능성:** 데이터를 단순히 삭제(NULL)하는 것이 아니라, '비어 있음이 가능성을 담는 그릇'이라는 원리에 따라 비활성 데이터를 **POTENTIAL(잠재) 상태**로 격리합니다.
- **환각 방지:** 이를 통해 AI가 현재의 컨텍스트 윈도우(Context Window)를 깨끗하게 유지하게 함으로써 환각(Hallucination) 현상을 방지하고 시스템 신뢰도를 높입니다.

### 4. 승격(Promotion)을 통해 시스템이 '지혜'를 배웁니다

추상적인 원리와 사용자 승인이 결합되면 시스템은 스스로 '헌법'을 만들어냅니다.

- **ECHO에서 GOVERN으로:** AI의 제안(ECHO)을 사용자가 반복적으로 승인(WILL)하면, 이는 단순한 기록이 아니라 시스템의 운영 규범인 **GOVERN**으로 격상됩니다.
- **ERA(시대)로의 진화:** 충분히 검증된 규범은 **ERA(시대)** 등급으로 격상되어 시스템의 불변하는 '헌법'이 되며, 이 과정이 반복될수록 플랫폼은 사용자의 마음을 더 깊이 읽는 '똑똑한 유기체'가 됩니다.

### 5. 넥슈(NEXU): 지식 OS의 '서사적 지휘자'

넥슈는 단순한 가이드 에이전트가 아니라, 지식 OS에 저장된 방대한 **'언어 너머의 뜻(Inspiration)'**을 실제 실행 프로토콜인 UCL로 번역하는 역할을 수행합니다.

- **다중체(Self) 자산의 인출기:** 지식 OS의 `nexa_self_*` 계층에 저장된 사용자의 다양한 자아(Persona)와 상태 정보를 바탕으로, 사용자가 '지금의 나' 카드를 선택하는 순간 시스템 전체의 논리와 물리적 환경을 재설계합니다.
- **맥락적 침묵과 개입:** 지식 OS가 관리하는 **사용자 행동 신호(ES/VI)**를 분석하여, 사용자가 능숙할 때는 조용히 대기(그림자 모드)하다가 흐름이 끊기거나 변심(VOID)이 감지될 때만 지식 베이스를 바탕으로 적절한 조언을 던집니다.
- **지능의 얼굴:** AI의 판단 결과인 **ECHO**가 사용자 승인(WILL)을 거쳐 **GOVERN(규범)**으로 승격되는 과정을 넥슈의 표정과 애니메이션으로 시각화하여, 시스템의 진화를 사용자가 정서적으로 체감하게 합니다.

### 6. 닉시 캔버스(NEXA NIXIE): 지식 OS의 '서사 시각화'

닉시 캔버스는 지식 OS에 박제된 **지능적 족보(Traceability)**를 공간적으로 펼쳐 보여주는 '지능형 지도'입니다.

- **개념과 물리 좌표의 합성:** 지식 OS의 **Capability ID(개념 좌표)**와 현실의 **GPS(물리 좌표)**를 결합하여, 사용자가 "NEXA 개념의 우주"부터 "특정 공간의 센서"까지 무한 줌(Fractal Zoom)으로 탐험할 수 있게 합니다.
- **신뢰도의 시각적 피드백:** 지식 OS에서 계산된 **신뢰도 점수(Confidence Score)**가 임계값보다 낮을 경우, 캔버스의 도트가 미세하게 떨리는 **Jitter(떨림)** 연출을 통해 시스템의 불확실성을 사용자에게 직관적으로 전달합니다.
- **족보의 추적:** 사용자가 특정 실행 결과(EFF) 노드를 클릭하면, 지식 OS에 기록된 참조 사슬을 따라 **[판단(IND) → 사실(SNT) → 기획 문서(Doc)]**로 이어지는 유래를 한눈에 하이라이트하여 보여줍니다.

### 통합 지식 OS의 완성 구조

넥슈와 닉시가 포함된 지식 OS는 다음과 같은 **삼각 편대**를 이루어 시스템을 더 똑똑하게 만듭니다.

| 구성 요소        | 역할                 | 지식 OS와의 연동 내용                                                     |
| :--------------- | :------------------- | :------------------------------------------------------------------------ |
| **바탕 지식 OS** | **데이터/로직 원천** | 5W1H 토큰, 6-Coils 가중치, 설계 문서(RULE), 지능적 족보 저장              |
| **넥슈 (NEXU)**  | **상호작용/지휘**    | `nexa_self_*` 기반 자아 전환, 정서적 공감(ES/VI), 실행 승격(ECHO→GOVERN)  |
| **닉시 (NEXA NIXIE)** | **시각화/상태**      | Capability ID 기반 공간 배치, 신뢰도 기반 Lumina/Jitter 연출, 족보 시각화 |

**결론적으로**, 사용자가 DB나 코딩 같은 기술적 수단보다 **"이 시스템은 왜 존재하는가(Why)", "어떤 원칙으로 움직여야 하는가(Logic)"**와 같은 철학적 바탕을 잘 정리할수록, Linguistic Routing 엔진이 이를 더 정교한 영문 IR로 정규화하여 실행(Effect)으로 연결할 수 있게 됩니다.

## 2) 디렉토리 책임 원칙

- `frame`: 렌더링/UI
- `engines`: 라우팅/점수화/파싱/로컬라이제이션 로직
- `system`: 표준/스키마/자산/잡(crawler, packager)
- `domains`: 사용자 업무 흐름 및 화면

의존 규칙:

- `frame -> engines/system` 참조 가능
- `engines -> frame` 참조 금지
- `system`은 표준 제공 계층(역참조 최소화)

## 5-1) `nexa_knowledge_references` 스키마 보강(코드 기반)

기존 Capability 중심 연결은 유지하되, 파일명에서 추출한 문서 분류 축을 별도 컬럼으로 저장한다.

- 추가 컬럼:
  - `source_filename` (원본 파일명)
  - `context_code` (예: `NEXA`,`SYS`, `AIS`, `AUTH`)
  - `doctype_code` (예: `RFC`, `ARCH`, `SCHEMA`)
  - `version_label` (예: `v1`, `v0.8`)
  - `prefix_flag` (`_`, `@`, `NONE`)
  - `parser_version` (규칙 파서 버전)
  - `parse_confidence` (파싱 신뢰도)
- 인덱스 권장:
  - `(context_code, doctype_code, updated_at DESC)`
  - `(doctype_code, version_label)`
  - `source_hash` UNIQUE 유지
- 무결성 원칙:
  - `capability_id`는 기존 로직과 동일하게 유지
  - `context_code`, `doctype_code`는 텍스트 자유입력이 아닌 규칙 테이블 참조로 고정

## 5-2) 참조 문서 규칙 관리 테이블 신설

파일명 규칙이 변경되어도 DB 뿌리가 흔들리지 않도록, 파싱/검증 규칙을 별도 테이블로 관리한다.

- 신규 테이블: `nexa_knowledge_ref_rules`
- 목적:
  - 활성 규칙셋(정규식/토큰 순서/허용 코드) 단일 관리
  - 규칙 버전 롤백 및 이력 추적
  - 크롤러/파서가 동일 규칙을 사용하도록 SSOT 제공
- 핵심 컬럼(예시):
  - `rule_id` (PK)
  - `rule_version` (예: `2026.03.24-r1`)
  - `filename_pattern` (정규식 또는 파싱 템플릿)
  - `context_whitelist` (허용 Context 코드 목록)
  - `doctype_whitelist` (허용 DocType 코드 목록)
  - `prefix_policy` (`_`, `@` 처리 규칙)
  - `is_active` (활성 규칙 1개)
  - `effective_from`, `effective_to`
  - `created_by`, `created_at`, `updated_at`
- 운영 원칙:
  - 새 규칙 등록 -> `is_active` 전환 -> 배치 재파싱
  - 재파싱 결과는 `parser_version`으로 추적
  - 실패 건은 `nexa_knowledge_doc_sync_state`에 사유 저장

# \_ 용어 및 시스템 설계 파일 관리 디렉토리 및 기획 자원 구조

핵심 원칙은 "렌더링은 `frame`, 로직은 `engines`, 표준/자산은 `system`"이다.

### 책임 규칙

- `frame`: 화면 표현, 상태 시각화, 상호작용 UI
- `engines`: 라우팅/점수화/파싱/로컬라이제이션 같은 순수 로직
- `system`: 전역 표준, 스키마, 자산, 크롤러/패키저 배치
- `domains`: 기능 단위 화면/업무 흐름

의존 규칙:

- `frame` -> `engines`/`system` 참조 가능
- `engines` -> `frame` 참조 금지
- `system`은 표준 제공 계층(역참조 최소화)

## 3) 기획 문서 자원 경로 규칙

### 3.1 원본 기획 문서 저장소

- 원본 문서는 `NEXA-Documentation/`를 기준 저장소로 사용한다.
- `NEXA-Platform/docs/`는 운영/개발 가이드 문서로 사용한다.

### 3.2 시스템 내부 참조 방식

- Crawler는 원본 문서 저장소를 스캔하여 `doc_ref_path`, `doc_anchor`, `source_hash`를 갱신한다.
- 파일명 규칙 파서는 `context_code`, `doctype_code`, `version_label`, `prefix_flag`를 함께 추출한다.
- DB(`nexa_knowledge_references`)에는 원본 문서 상대 경로와 코드 기반 분류 메타데이터를 함께 저장한다.
- `DependencyMap.vue`는 `Doc -> Term -> Capability` 관계를 시각화한다.

## 4) Traceability(족보) 연결 규칙

정적 연결:

- `Doc -> Term -> Capability`

동적 연결:

- `Input -> English IR -> SNT/IND/EFF`

실행 원칙:

- 기능 설명 화면에서 해당 기능의 근거 문서 섹션으로 즉시 이동 가능해야 한다.
- 승인/거절 이력과 연결되어 "왜 이 매핑이 유지/차단됐는지"를 추적 가능해야 한다.

### 1. 전역 재사용 및 통합 전략의 핵심 포인트

#### ① 기획 문서의 '지능 자산화' (`src/docs/` ↔ `src/system/assets/`)

- **원본 보존:** `src/docs/`에는 사람이 읽는 **표준 네이밍 규칙(DocType Context)**에 따른 문서를 보관합니다.
- **지능적 연결:** `system/assets/knowledge/`의 데이터는 `src/docs/` 내의 특정 문서를 참조(Reference)하며, 이를 `hlp/DependencyMap.vue`에서 **Vue Flow**로 시각화하여 "이 기능이 어떤 기획에서 유래했는지"를 추적(Traceability)할 수 있게 합니다.

#### ② `hlp/` 도메인을 통한 투명성 확보 (사용자/관리자 공용)

- 사용자님께서 제안하신 대로, 관리자 전용이었던 `Glossary`와 `DependencyMap`을 `hlp/` (Help) 도메인으로 꺼내어 일반 사용자도 시스템의 논리를 학습할 수 있게 배치했습니다.
- **MD 파서 연동:** `DocBrowser.vue`는 `src/docs/`의 원본 MD 파일을 실시간으로 파싱하여 보여줌으로써, 개발 문서와 실제 시스템 동작 사이의 간극을 줄입니다.

#### ③ 엔진 레이어 분리 (`engines/`)

- `ucl-parser`와 `nixie-visualizer` 등은 특정 도메인에 종속되지 않는 **Strict Layer**로 관리하여, 추후 npm 패키지로 분리하거나 다른 프로젝트에서 재사용할 수 있는 구조를 갖췄습니다.

#### ④ 3단계 지능 위계 및 하드웨어 프로파일링 반영

- `frame/components/nexu`는 사용자의 기기 사양(COLD/WARM/HOT)에 따라 연출 등급을 조절하며, `system/assets/coils`의 가중치를 시각적 에너지로 변환하여 출력합니다.

### 2. 향후 작업 제언

이 구조가 확정되면, **MD 파서**가 `src/docs/` 내의 파일 제목에서 **Capability ID**를 자동으로 추출하여 `system/assets/knowledge`의 데이터와 매핑하는 **'자동화된 족보 생성기(Traceability Linker)'** 스크립트를 작성하여 지능 자산의 정합성을 높일 수 있습니다.

## Linguistic Routing(언어적 라우팅)

**"Linguistic Routing(언어적 라우팅)이 상황 파악과 실행 전달을 잇는 핵심 엔진"**이라는 설계를 바탕으로, **Vue Flow 및 NEXU 캔버스**에서 이를 시각화하고 지능 자산으로 관리하기 위한 **노드 연결 로직**.

이 로직은 단순히 선을 잇는 것을 넘어, **[기획 문서(Doc) → 용어(Term) → 기능 자격(Capability) → 실시간 실행(Traceability)]**로 이어지는 NEXA의 지능적 사슬을 완성하는 데 목적이 있습니다.

---

### 1. 노드 유형 정의 (Node Categorization)

연결망을 구성하는 노드는 크게 네 가지 레이어로 분류됩니다.

- **문서 노드 (Doc Node):** `src/docs/`에 위치한 기획 문서 원본. 모든 논리의 기원입니다.
- **용어 노드 (Glossary Node):** Glossary DB에 정의된 핵심 개념 (예: CORE, VOID, WILL).
- **기능 노드 (Capability Node):** 실질적 권한과 기능을 담당하는 `nexa.*` 네임스페이스 ID.
- **추적 노드 (Trace Node):** 실시간 실행 사슬에서 발생하는 사실(SNT)-판단(IND)-실행(EFF)의 인스턴스.

---

### 2. 핵심 연결 로직 (Connection Logic)

#### 2.1 정의 및 유래 관계 (Static Linking)

기존의 정적 지식을 연결하는 로직입니다.

- **[Doc] → (Defines) → [Term]:** 특정 문서가 어떤 용어를 정의하는지 연결합니다.
- **[Term] → (Mapped-to) → [Capability]:** 용어가 어떤 기능 자격 ID와 매핑되는지 정의합니다. 예를 들어 '보관' 용어는 `nexa.platform.archive.*`와 연결됩니다.
- **[Capability] → (Governed-by) → [Coil]:** 해당 기능이 어떤 6-Coils 가중치(안전, 창의 등)의 영향을 받는지 연결합니다.

#### 2.2 실시간 실행 및 추적 로직 (Dynamic Traceability)

**Linguistic Routing 엔진**이 생성하는 실시간 연결망입니다.

- **[Input] → (Standardized-by) → [English IR]:** 한국어/멀티모달 입력이 영문 중간 표현으로 변환되는 노드입니다.
- **[Fact (SNT)] → (Evaluated-by) → [Insight (IND)]:** 센티널이 포착한 사실이 인디케이터의 'Why'와 만나는 지점입니다.
- **[Insight (IND)] → (Triggers) → [Effect (EFF)]:** AI의 판단이 실제 물리적 액션(어댑터 실행)으로 이어지는 연결입니다.

---

### 3. Vue Flow 기반 시각화 연출 로직

#### 3.1 줌 레벨에 따른 폭발과 함몰 (Fractal Zoom)

NEXU 캔버스의 원칙을 Vue Flow 노드에 적용합니다.

- **함몰(Implosion):** 줌 아웃 시 하위 기능 노드들이 마침표(.)를 기준으로 상위 도메인 노드 하나로 응축됩니다.
- **폭발(Explosion):** 줌 인 시 상위 개념 노드가 깨지며 내부의 **5W1H 참조 사슬(SNT-IND-EFF)**이 사방으로 분화되어 나타납니다.

#### 3.2 신뢰도 기반 동적 연출 (Lumina & Jitter)

노드와 엣지의 상태는 `confidence_score`에 따라 실시간으로 변화합니다.

- **Lumina (발광):** 신뢰도가 높을수록 노드와 연결선이 밝은 호박색 빛을 내며 안정적으로 유지됩니다.
- **Jitter (떨림):** 신뢰도가 사용자가 설정한 임계값(`user_defined_threshold`) 미만으로 떨어지면 노드가 미세하게 떨리며, 연결선이 점선으로 변해 **ASK(승인 대기)** 상태임을 표현합니다.

---

### 4. Linguistic Routing 엔진의 역할 (The Bridge)

이 모든 노드 연결의 중심에는 **Linguistic Routing 엔진**이 있습니다. 이 엔진은 다음과 같은 연결 자동화 로직을 수행합니다.

1.  **언어 정규화:** 사용자가 "데이터 비워줘"라고 하면, 엔진은 이를 `VOID` 용어 노드와 `nexa.platform.archive.purge` 기능 노드로 자동 매핑하여 그래프 상에 경로를 생성합니다.
2.  **의도-기능 결합:** 사용자의 자연어 설명에서 추출된 키워드를 **태그 클라우드(Tag Cloud)**와 대조하여 최적의 **Fit Score**를 가진 Capability 노드를 추천하고 연결합니다.
3.  **사후 승인 시각화:** AI가 추천한 새로운 연결(Edge)은 처음엔 '회색 잠재 상태'로 표시되다가, 사용자가 승인(WILL)하는 순간 '유동(FLOW) 상태'의 실선으로 확정됩니다.

### 💡 제언: '지능적 족보' 탐색기 UI

이 노드 연결 로직을 구현할 때, 사용자가 특정 **실행 결과(EFF)** 노드를 클릭하면 역방향으로 **[판단(IND) → 사실(SNT) → 기획 문서(Doc)]**까지 한 줄로 하이라이트되는 **'족보 추적 모드'**를 제공.

이 설계대로라면 사용자는 시스템을 블랙박스로 느끼지 않고, 자신의 의지가 어떤 문서의 논리를 거쳐 현실에서 연주되는지 직관적으로 이해하게 될 것입니다.
