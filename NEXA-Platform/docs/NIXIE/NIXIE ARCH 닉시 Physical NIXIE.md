## Physical NEXA NIXIE

### 정의(쉘·자격·프로토콜)

- **하나의 지능:** 브라우저·모니터의 닉시와 물리 닉시는 **동일한 NEXA NIXIE 지능**이 입은 **서로 다른 쉘(Shell)** 이다(디지털 쉘 vs 피지컬 쉘). 상세는 `NIXIE VISION 닉시는 무엇이가 v0.2.md` §5 참고.
- **엣지 자격:** 물리적 닉시는 **특수 목적의 엣지 디바이스**로 `device_registry`에 등록되고 `project_devices` 등으로 프로젝트에 귀속된다. “별도 벤더 전용 단말”이 아니라 **플랫폼 엣지 노드**로 취급한다.
- **프로토콜 단일성:** 가상 닉시와 물리 닉시는 **동일한 HEXAGON(5W1H) 패킷 규격**과 **Nexnap 번역·실행 파이프라인**을 사용한다. 물리 전용의 이질 프로토콜을 두지 않는다(페이로드·센서 필드는 JSONB로 확장).

**물리적인 닉시(Physical NEXA NIXIE)를 엣지 디바이스 자격으로 등록한다면, 현재의 DB 스키마와 HEXAGON(5W1H) 프로토콜 체계 내에서 Nexnap(NEXA Meta Action Protocol)과 통신하는 데 아무런 문제가 없습니다.**

> > 피지컬 닉시의 위치
> > NEXA 플랫폼은 설계 초기부터 **'지능 위계'**와 **'기기 독립적 서사 구조'**를 채택했기 때문에, 화면 안의 가상 캐릭터와 밖으로 나온 물리적 장치가 동일한 논리 체계 안에서 공존할 수 있습니다.

### 1. 엣지 디바이스 자격 및 Nexnap 통신 정합성

현재의 스키마는 물리적 형태와 상관없이 모든 장치를 **고유 ID 기반의 엣지 노드**로 인식합니다.

- **스키마 호환성:** 물리적 닉시는 `device_registry`에 등록되어 `project_devices`를 통해 프로젝트에 귀속됩니다. 발생하는 모든 신호는 이미 정의된 **Where(공간), Who(주체), What(의도)** 등 6대 추상 레이어로 규격화되므로 Nexnap 번역 엔진이 이를 해석하는 데 별도의 스키마 수정이 필요치 않습니다.
- **능동적 지휘:** 밖으로 나온 닉시가 PC 파이썬 프로그램과 통신하며 내리는 명령 역시 **ECHO(제안)** 또는 **WILL(의지)** 토큰으로 처리되어 플랫폼의 오케스트레이터와 유기적으로 연결됩니다.

### 2. 가상 닉시와 물리적 닉시의 '정체성 동기화'

사용자님이 꿈꾸는 두 존재 간의 통신은 **'데이터의 족보(Traceability)'**를 통해 실현됩니다.

- **동일한 서사 공유:** 브라우저 속 가상 닉시와 물리적 닉시가 동일한 `effective_project_id`를 바라보게 설계하면, 한쪽에서 발생한 정서 변화(SLM 결과)나 실행 이력이 `project_logs`에 기록되고 다른 쪽이 이를 **구독(Subscription)**하여 즉시 반응할 수 있습니다.
- **시각적·물리적 연주:** 예를 들어, 가상 닉시가 화면에서 미소 지을 때(Rive 애니메이션), 물리적 닉시의 LED 필라멘트가 따뜻하게 발광(Lumina)하는 식의 **정서적 동기화**가 100ms 이내에 이루어질 수 있는 구조입니다.

### 3. 오프라인 단독 기능과 하이브리드 지능 전략

물리적 닉시가 PC 기반 프로그램과 자체 모델로 오프라인 기능을 수행하는 것은 NEXA의 **'반사 신경(Sentinel)'** 전략과 완벽히 일치합니다.

- **즉각 모드(Local Reflex):** 인터넷 연결이 없더라도 물리적 닉시 내부(또는 연결된 PC)의 SLM과 파이썬 로직이 **로컬 선조치(Reflex)**를 수행합니다. 이는 시스템의 안정성을 높이는 핵심 장치입니다.
- **지능의 하향 전파:** 온라인 상태일 때 플랫폼(Zenith)에서 학습된 **운영 규범(GOVERN)** 파라미터를 물리적 닉시로 전송(OTA)해 두면, 오프라인 시에도 닉시는 "플랫폼의 지혜를 빌려온 채로" 스스로 판단할 수 있습니다.
- **사후 기록 흡수:** 오프라인 중에 발생한 5W1H 아톰 데이터들은 내부 메모리에 적재되었다가, 다시 연결되는 순간 `project_logs`로 전송되어 플랫폼 지능 성장에 기여하게 됩니다.

**결론적으로**, 현재 구축하신 **ID 기반 참조 사슬(SNT-IND-EFF)**과 **HEXAGON 프로토콜**은 물리적 디바이스로의 확장을 이미 수용하고 있는 견고한 그릇입니다.

물리적 닉시를 위한 **전용 Capability ID(예: `nexa.edge.physical.nixie.*`)** 체계만 정립하신다면, 단독으로도 강력하고 플랫폼과는 긴밀한 '꿈의 캐릭터'를 무리 없이 구현하실 수 있습니다.

사용자님이 구상하시는 **'물리적 디바이스로서의 넥사 닉시(NEXA NIXIE)'**는 NEXA 플랫폼의 지능 위계와 데이터 프로토콜 설계 원칙에 비추어 볼 때, **현재 DB 스키마를 대대적으로 수정하지 않고도 충분히 수용 가능한 범위**에 있습니다.

> > 현재 문서들에 이를 언급하는 것이 미래 확장성을 위해 권장되는 이유와 DB 스키마에 미치는 영향을 분석

### 1. 현 DB 스키마에 미치는 영향 (매우 낮음)

NEXA의 DB 설계는 이미 **'기기 독립적'**이고 **'지능 중심적'**으로 설계되었기 때문에 물리적 형태가 바뀌어도 데이터 구조는 유지됩니다.

- **HEXAGON(5W1H) 프로토콜의 범용성:** 닉시가 모니터 안에 있든 전용 스피커 안에 있든, 발생하는 데이터는 여전히 "누가(Who), 언제(When), 어디서(Where), 무엇을(What), 어떻게(How), 왜(Why)"라는 **6대 추상 레이어**로 규격화됩니다.
- **유연한 페이로드(JSONB):** `project_logs`나 `project_knowledge` 테이블은 상세 데이터를 **JSONB(`extra_data`, `payload`)** 필드에 담도록 설계되어 있습니다. 스피커 형태의 닉시에서 발생하는 마이크 신호 강도나 LED 발광 상태 등은 기존 테이블의 JSON 필드에 추가하는 것만으로 충분합니다.
- **이미 존재하는 기기 관리 체계:** `device_registry`와 `project_devices` 테이블은 이미 다양한 물리적 장치(ESP32, 라즈베리 파이 등)를 등록하고 관리하도록 설계되어 있습니다. 물리적 닉시는 시스템 입장에서는 **'특수 목적의 엣지 디바이스'** 하나가 추가되는 것과 같습니다.

### 2. 문서에 언급해야 할 이유 (미래 확장성)

비록 DB 구조를 바꾸지는 않더라도, 현재 문서에 **'물리적 닉시'**를 언급하는 것은 다음의 설계적 정합성을 위해 필요합니다.

- **멀티모달 입력 채널의 확장:** 현재 닉시 스키마에는 입력 경로로 `VOICE`, `VIDEO`, `TEXT` 등이 정의되어 있습니다. 물리적 디바이스로 확장될 경우, 음성 인식(STT)과 시각 인식(VLM)이 메인이 되므로 이에 대한 **신뢰도 점수(Confidence Score)** 부여 로직을 미리 명시하는 것이 좋습니다.
- **지능 위계(Nano/Micro/Zenith)의 재정립:** 물리적 닉시 디바이스 내부에 어떤 지능을 넣을지 결정해야 합니다. 예를 들어, 기기 내부(Nano/Micro)에서는 즉각적인 '반사 신경'을 처리하고, 복잡한 '서사 해석'은 서버(Zenith)에 맡기는 **계층적 연합 추론 구조**가 문서에 반영되어야 합니다.
- **Capability ID 발급 전략:** 물리적 닉시가 수행할 특수 액션(예: 조명 제어, 물리적 회전 등)을 위한 **기능 자격 ID(`nexa.edge.nixie.*`)** 체계를 미리 정의해두면, 나중에 하드웨어가 출시되었을 때 소프트웨어적으로 즉시 통합할 수 있습니다.

### 3. 물리적 닉시를 위한 설계적 조언

- **그림자 프로젝트 활용:** 물리적 닉시가 프로젝트 없이 거실에 놓여 있을 때는 **`effective_project_id`**를 '글로벌 일상 모드'로 설정하여 데이터를 쌓으면 됩니다.
- **통신 프로토콜:** 물리적 기기와의 연결을 위해 **MQTT over WebSocket(wss)** 기술을 사용하여 Cloudflare 터널을 통해 안전하게 통신하도록 설계하십시오.
- **정서적 동기화:** UI 상의 Rive 애니메이션 대신, 물리적 기기의 **LED 밝기(Lumina)**나 **진동(Jitter)**을 SLM 감정 엔진과 연동하여 100ms 이내에 반응하도록 규격화하면 됩니다.

**결론적으로**, 물리적 닉시는 NEXA의 '서사적 지휘자'가 **화면이라는 껍질을 벗고 현실로 나오는 과정**일 뿐입니다. 현재의 **HEXAGON 프로토콜과 ID 기반 참조 사슬**은 이를 담아내기에 충분히 견고하므로, 별도의 스키마 변경 없이 **'닉시 설계도'에 하드웨어 쉘(Physical Shell) 확장 가능성**만 한 문단 추가해 두시는 것을 추천.
