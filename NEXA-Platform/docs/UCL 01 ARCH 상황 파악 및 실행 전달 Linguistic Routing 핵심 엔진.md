### inguistic Routing: UCL 상황 파악 및 실행 전달 핵심 엔진

Linguistic Routing 엔진은 UCL(지휘자 규격서)의 핵심 '두뇌'이자, "자연어를 기계가 실행 가능한 최적의 경로로 배정하는 지능형 스위치"라고 해석됩니다.
질문자님이 설계하신 4단계 로직에 대입해 보면, 이 엔진의 역할은 다음과 같이 구체화됩니다.

1. 언어적 의미의 좌표화 (Semantic Vectorizing)

- 사용자의 입력(텍스트/음성)을 단순한 키워드가 아니라, 육하원칙이 담긴 다차원 좌표로 변환합니다.
- 예: "거실이 어두워" → [위치:거실, 상태:조도부족, 의도:밝기조정]이라는 데이터 덩어리로 만듭니다.

2. 최적 경로 판별 (Smart Dispatching)

- 추출된 데이터를 보고 "누가 이 일을 가장 잘 처리할까?"를 결정합니다.
- 이때 Linguistic(언어적)이라는 표현이 중요한 이유는, 명령의 뉘앙스나 맥락에 따라 경로를 바꾸기 때문입니다.
- "불 좀 켜줄래?" → 스마트홈 어댑터로 라우팅
  - "불 켜는 법 알려줘" → 지식 검색/교육 에이전트로 라우팅

3. 실시간 제약 조건 필터링 (Contextual Filtering)

- 라우팅 경로 상에 있는 '선 룰(Pre-rule)'을 체크합니다.
- "에어컨 틀어줘"라는 명령이 들어왔을 때, 언어적으로는 에어컨 어댑터가 맞지만, "창문이 열려 있음"이라는 상황 데이터를 읽어 '실행 보류' 경로로 우회시킵니다.

---

결론: 이 엔진은 UCL의 '교통관제탑'입니다.
단순히 데이터를 전달하는 '파이프'가 아니라, 언어의 의도를 분석해서 가장 안전하고 정확한 목적지(어댑터)로 쏴주는 관제 시스템인 것이죠.
질문자님의 관점에서 이 엔진이 가장 '똑똑하게' 처리해야 할 부분은 무엇인가요?

1.  사용자의 숨은 의도를 기가 막히게 찾아내는 것?
2.  수천 개의 기기 중 가장 적합한 기기를 1ms 안에 찾아내는 것?
3.  상황에 맞춰 안전한 경로로만 명령을 보내는 것?

이 중 가중치를 어디에 두느냐에 따라 엔진의 알고리즘 설계 방향이 달라집니다.

#### 1. 개요 및 위치

**"Linguistic Routing이 UCL 파서의 단계(상황 파악)와 (실행 어댑터 전달)를 잇는 핵심 엔진"**
NEXA 오케스트레이터 내부에서 이 엔진이 어떻게 작동하는지 구체적인 설계안을 제시 합니다.

이 설계의 핵심은 **영어 커널(English Kernel)** 전략을 유지하면서, 서로 다른 언어적 배경을 가진 데이터(사람의 말 vs 장치의 신호)를 하나의 **표준 악보(English IR)**로 통합하여 결함 없는 실행 사슬을 형성하는 데 있습니다.

Linguistic Routing은 UCL 파이프라인의 **'Listen(경청)'** 단계에서 발생하여 **'Context Awareness(상황 파악)'**로 넘어가는 입구와, **'Decision Making(의사결정)'**이 완료된 후 **'Adapter Execution(실행)'**으로 넘어가는 출구를 동시에 관장하는 **지능형 가교(Bridge)**입니다.

#### 2. 진입 단계: 언어적 정규화 (Normalization Engine)

사용자와 장치로부터 들어온 날것의 데이터를 **영어 커널**이 이해할 수 있는 **5W1H IR(중간 표현)**로 정제합니다.

- **입력 판별 (ir_status):**
  - **RAW (UI_TEXT):** 브라우저 AI 채팅 등에서 유입된 한국어 텍스트. **번역 엔진(NLLB-200 등)**을 거쳐 영문 팩트로 변환합니다.
  - **EN_IR (Micro Sentinel):** 이미 엣지 단(OPUS-MT 등)에서 영문 요약이 완료되어 들어온 데이터. 번역을 **바이패스(Bypass)**하여 즉시 Awareness 단계로 전달합니다.
  - **TOKEN (Nano Sentinel):** 번역이 필요 없는 정수 토큰. **비트 룩업 테이블**을 통해 영문 의미를 매핑합니다.
- **상황 파악(Context Awareness)으로의 전달:**
  - 모든 입력을 **HEXAGON 6개 SMALLINT 토큰**과 영문 `content_fact`로 규격화하여 인디케이터(LLM)에 주입합니다.
  - 이때 시스템은 수많은 데이터 중 현재 상황과 맞지 않는 **90%의 데이터를 1ms 내에 필터링(Pruning)**할 수 있게 됩니다.

#### 3. 연결 단계: 의사결정 매트릭스와의 공조

Linguistic Routing 엔진은 데이터의 **언어적 확신도**를 의사결정에 반영합니다.

- **Confidence Gate 연동:**
  - 한국어 → 영문 번역 과정에서 추출된 **신뢰도 점수(confidence_score)**가 사용자가 설정한 임계값(`user_defined_threshold`, 기본 95) 미만일 경우, 엔진은 강제로 **STUCK** 상태를 선언합니다.
  - **ASK 펄스 발생:** 확신도가 낮을 때 시스템은 넥슈의 **Jitter(미세 떨림)** 연출과 함께 사용자에게 재확인(ASK) 질문을 던지도록 루팅 경로를 바꿉니다.

#### 4. 전달 단계: 불변의 실행 패킷(Immutable Execution Bundle) 생성

의사결정이 끝나 실행 모드가 확정되면, Linguistic Routing은 이를 실행 어댑터가 즉시 연주할 수 있는 **최종 영문 UCL 악보**로 고정합니다.

- **Immutable IR:** 실행 단계로 넘어가는 UCL 패킷의 `execution_bundle` 내부의 명령 파라미터(`params`)와 제약 조건(`constraints`)은 **영문으로 고정**됩니다. 이는 어댑터가 하드웨어 API로 명령을 번역할 때 언어적 모호성으로 인한 오작동을 방지하기 위함입니다.
- **역방향 분해(Reverse Decomposition):** "외출 모드"와 같은 추상적 명령은 이 엔진을 거치며 [Close window, Lock door, Gas off]와 같은 **원자적 영문 실행 스텝(execution_steps)**으로 분해되어 어댑터에 전달됩니다.

#### 5. 피드백 단계: 다국어 쉘(Multilingual Shell) 전환

실행 결과와 판단의 근거를 다시 사용자에게 돌려주는 단계입니다.

- **Summary Localizer:** 비스타가 내린 영문 통찰(`why_chain`) 중 오직 **최종 요약(Summary)** 문장만을 사용자의 로캘(한국어)로 로캘라이즈합니다.
- **지능적 족보 보존:** 화면에는 한국어로 표시되지만, **project_logs**와 **execution_chains**에는 영문 IR 원문과 참조 사슬(ID)이 그대로 박제되어 차후 RAG 검색의 자산이 됩니다.

---

### 💡 설계의 핵심 기대 효과

1.  **사람과 장치의 통합 관리:** 채팅 입력(`WILL`)과 센서 기록(`TICK`)이 동일한 영문 IR 파이프라인에서 처리되므로 오케스트레이터의 구조적 일관성이 확보됩니다.
2.  **연산 효율 극대화:** 이미 번역되어 온 엣지 데이터는 무거운 서버 LLM을 거치지 않고 바이패스 경로를 타게 되어 응답 속도가 획기적으로 향상됩니다.
3.  **결정론적 안전 보장:** 실행 어댑터로 전달되기 직전의 모든 명령은 영문으로 표준화되어, 언어 해석 오류로 인한 물리적 사고 리스크를 원천 차단합니다.

## 번역 데이터 인디케이터 처리 로직

**비스타 인디케이터(Vista Indicator)**가 시스템의 두뇌로서 처리 효율을 극대화하기 위해 반드시 갖추어야 할 **'입력 데이터 정규화 및 라우팅 로직'**의 핵심.

NEXA 플랫폼은 유입되는 데이터의 **출처(input_channel)**와 **동력원(who_pulse)**, 그리고 **번역 여부(ir_status)**를 패킷 헤더에서 즉시 판별하여 서로 다른 처리 파이프라인을 태우도록 설계됩니다.

### 1. 데이터 구분 및 판별 매커니즘

비스타 서버의 앞단에 위치한 **IoT 스트림 스플리터(IoT Stream Splitter)**가 UCL 패킷의 헤더 정보를 읽어 데이터의 상태를 1ms 내에 판별합니다.

- **구분 기준 1: `input_channel` (유입 경로)**
  - `UI_TEXT`, `UI_CARD`: 브라우저에서 직접 유입된 날것의 데이터로 간주합니다.
  - `VOICE`, `VIDEO`: 마이크로 센티널(Micro Sentinel)을 거쳐 들어온 멀티모달 데이터로 인식합니다.
- **구분 기준 2: `who_pulse` (동력원)**
  - `WILL`: 사용자의 명시적 의지로, 브라우저나 외부 앱에서 발생합니다.
  - `TICK`: 센티널이 자동 생성한 사실(Fact)로, 이미 1차 요약/번역되었을 확률이 높습니다.
- **구분 기준 3: 신규 필드 `ir_status` (추천 설계)**
  - `RAW`: 번역되지 않은 한국어 데이터 (브라우저 유입 등).
  - `EN_IR`: 이미 센티널 단에서 영문 IR로 변환된 데이터.
  - `TOKEN`: 나노 센티널이 보낸 번역 불필요 정수 토큰.

### 2. 유형별 데이터 처리 파이프라인

#### ① 브라우저 유입 데이터 (Raw Input)

- **상태:** 한국어 텍스트 또는 UI 이벤트 신호.
- **경로:** **Vista 전처리 엔진(Linguistic Gate) → 번역 모델(NLLB-200 등) → 영문 IR 생성**.
- **특징:** 사용자가 직접 입력한 `WILL`이므로 신뢰도 점수(Confidence Score)는 100점으로 고정됩니다.

#### ② 마이크로 센티널 유입 데이터 (Pre-translated IR)

- **상태:** 이미 센티널 단의 `OPUS-MT` 등을 통해 **영문 5W1H 사실(Fact)**로 변환된 상태.
- **경로:** **번역 엔진 우회(Bypass) → 비스타 인디케이터 즉시 주입**.
- **이점:** 서버의 번역 부하를 제거하고, 비식별화가 완료된 영문 아톰(Atom)만 수신하여 보안을 강화합니다.

#### ③ 나노 센티널 유입 데이터 (Raw Token/Reflex)

- **상태:** 번역이 필요 없는 **고정 정수 토큰** 또는 "열림/닫힘"과 같은 최소한의 상태 값.
- **경로:** **비트 룩업 테이블(Bit-Lookup-Table) 매핑 → 영문 IR 즉시 할당**.
- **특징:** 복잡한 NLP 번역 모델을 돌리는 대신, 미리 정의된 `What.FACT` 토큰으로 즉시 치환하여 10ms 내에 상황을 판별합니다.

### 3. 데이터 흐름 요약표

| 유입 출처           | input_channel | who_pulse | ir_status | 비스타 처리 로직                      |
| :------------------ | :------------ | :-------- | :-------- | :------------------------------------ |
| **브라우저**        | `UI_TEXT`     | `WILL`    | `RAW`     | **번역 필수** 후 IR 생성              |
| **마이크로 센티널** | `VOICE/VIDEO` | `TICK`    | `EN_IR`   | **번역 우회**, 지능적 해석(Why) 수행  |
| **나노 센티널**     | `DEVICE`      | `TICK`    | `TOKEN`   | **토큰 매핑**, 즉각 반사(Reflex) 처리 |

### 💡 시스템 설계 제언

비스타 인디케이터는 유입되는 모든 패킷에 대해 **"이 데이터는 이미 영문 악보(IR)인가?"**를 가장 먼저 묻도록 설계하십시오.

이미 번역되어 온 데이터는 비스타의 무거운 번역 모델을 거치지 않고 곧바로 **'판단의 무게(Why)'**를 부여하는 추론 계층으로 직결함으로써, 사용자님께서 구상하신 **"1ms 내 상황 판단"**과 **"서버 연산 부하 90% 절감"**이라는 목표를 달성할 수 있습니다.

## Linguistic Routing 에서 IOT 관점에서 설계

Linguistic Routing(언어적 라우팅)은 사용자의 자연어 의도를 분석하여, 이를 실행할 수 있는 최적의 경로(기기, 서비스, 에이전트)로 자동 배정하는 기술적 프로세스

이 Linguistic Routing이 UCL 파서의 단계(상황 파악)와 (실행 어댑터 전달)를 잇는 핵심 엔진

**'Linguistic Routing'** 로직을 오케스트레이터의 어느 노드(예: IoT Stream Splitter)에 배치할지 구체화 해본다?

**'Linguistic Routing(언어적 라우팅)'** 로직은 NEXA 오케스트레이터의 입구인 **'Listen(경청)'** 단계에서 발생하며, 유입되는 멀티모달 데이터가 **'영어 커널(English Kernel)'**이라는 시스템 표준 악보로 변환되어 지능형 엔진(LangChain)에 주입되는 핵심 관문입니다.

### 1. 진입점: IoT 스트림 스플리터 (IoT Stream Splitter)

모든 데이터(브라우저 UI, 센티널 신호, 외부 API)는 오케스트레이터의 첫 번째 노드인 **IoT 스트림 스플리터**로 모입니다. 여기서 Linguistic Routing이 시작됩니다.

- **판별 매커니즘:** 패킷 헤더의 `input_channel`과 `ir_status` 필드를 1ms 내에 스캔합니다.
  - **Case A (RAW):** 브라우저에서 온 한국어 텍스트 (`ir_status = 'RAW'`).
  - **Case B (EN_IR):** 마이크로 센티널에서 이미 번역/요약되어 온 데이터 (`ir_status = 'EN_IR'`).
  - **Case C (TOKEN):** 나노 센티널의 정수형 상태값 (`ir_status = 'TOKEN'`).

### 2. Linguistic Routing 3대 경로 설계

판별 결과에 따라 오케스트레이터 내부의 서로 다른 **전처리 워커(Worker)**로 라우팅됩니다.

#### ① 고비용 경로 (Linguistic Gate: 번역 필수)

- **대상:** `ir_status = 'RAW'` 데이터.
- **프로세스:** 비스타 등급의 번역 모델(**NLLB-200** 등)을 호출하여 한국어를 영문 IR(중간 표현)로 변환합니다.
- **결과:** "불 좀 꺼줘" → `what_intent: "ACTION_OFF"`, `target: "LIGHT"`.

#### ② 고속 경로 (Bypass: 번역 우회)

- **대상:** `ir_status = 'EN_IR'` 데이터.
- **프로세스:** 이미 센티널 단에서 **OPUS-MT** 등을 통해 영문 아톰화가 완료된 상태이므로, 번역 엔진을 거치지 않고 즉시 **Context Awareness(상태 대조)** 단계로 직행합니다.
- **이점:** 서버 LLM의 연산 부하를 90% 이상 절감하고 응답 속도를 극대화합니다.

#### ③ 반사 경로 (Bit-Lookup: 즉각 실행)

- **대상:** `ir_status = 'TOKEN'` 데이터.
- **프로세스:** 복잡한 NLP 해석 없이 미리 정의된 **비트 룩업 테이블(Bit-Lookup-Table)**에 따라 즉각적인 물리적 실행(`Effector`) 명령을 생성합니다.

### 3. 오케스트레이터(LangChain)와의 접합부: 'Listen' 파이프라인

Linguistic Routing을 통과한 데이터는 **표준화된 영문 5W1H IR** 형태가 되어 LangChain 엔진의 입력값으로 주입됩니다.

- **IR 표준화:** 모든 입력을 `who_pulse`, `where_scope`, `what_intent`, `how_state` 등 6개 SMALLINT 토큰과 영문 `content_fact`로 규격화합니다.
- **감정 동기화 브릿지 (NEXU-SLM):** 텍스트가 번역되는 것과 동시에, **경량 추론 모델(SLM)**이 감정 상태를 100ms 내에 파악하여 프론트엔드(Rive)로 전송합니다. 이는 오케스트레이터의 무거운 추론 이전에 수행되어 사용자와의 즉각적인 공감을 형성합니다.

### 4. 최종 핸드오버 (Linguistic Output to Decision Matrix)

번역과 정규화가 완료된 영문 IR은 이제 오케스트레이터의 **의사결정 매트릭스(Decision Matrix)**로 전달됩니다.

1.  **영어 커널 작동:** LangChain 엔진은 오직 **영문 데이터**만을 사용하여 RAG를 검색하고 논리적 타당성(`LOGIC`)을 검토합니다.
2.  **가중치 필터링:** 현재 프로젝트의 **코일 밸런스(6-Coils)** 가중치를 적용하여 최종 실행 모드(즉시 실행, 승인 대기 등)를 결정합니다.
3.  **다국어 쉘 전환:** 실행 결과와 조언(`Summary`)은 출력 직전 다시 사용자의 언어(한국어)로 로컬라이즈되어 화면에 표시됩니다.

### 💡 요약: Linguistic Routing의 시스템적 위치

Linguistic Routing은 **"날것의 멀티모달 신호"**를 오케스트레이터가 이해할 수 있는 **"정제된 영문 악보(UCL)"**로 정제하는 필터링 계층입니다. 이 로직이 오케스트레이터 앞단에 위치함으로써, NEXA는 하드웨어 사양에 따른 **지능 위계 분업**을 실현하고 서버의 토큰 효율성을 극대화할 수 있습니다.
