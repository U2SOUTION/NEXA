### 8. 멀티윈도우 아키텍처 규격 (Multi-Window Architecture Specification)

## 8.1 목적과 범위

본 문서는 NEXIA 탭 프로파일(기본 7개 포함)을 멀티 모니터/멀티 창 환경에서 안정적으로 운영하기 위한 아키텍처와 운영 기준을 정의한다.

## 8.2 적용 시나리오

- Synapse와 Glos를 분리해 병렬 작업할 때
- Cockpit 모니터링과 Physis 결과물을 동시 확인할 때
- 장시간 집중 작업에서 창 레이아웃 복원이 필요할 때

## 8.2.1 탭 가변 구조 대응

- 멀티윈도우는 고정 탭 수를 전제하지 않는다.
- 창 생성은 탭 레지스트리 기반으로 동적으로 수행한다.
- 신규 탭 추가 시 `route`, `riskLevel`, `defaultWindowPolicy`를 필수 등록한다.

## 8.3 설계 원칙

- 단일 로직 인스턴스: 핵심 실행 컨텍스트는 중앙 오케스트레이터로 단일화한다.
- 창 독립성: UI는 분리하되 상태 소스는 분산되지 않게 유지한다.
- 충돌 방지: 한 시점 한 제어권(음성/STT/고위험 실행)을 보장한다.
- 복구 우선: 비정상 종료 후 레이아웃과 세션을 자동 복원한다.

## 8.4 구성 요소

| 구성 | 기술 | 책임 |
| --- | --- | --- |
| Window Manager | `window.open`, `Screen Details API` | 창 생성/배치/복원 |
| Sync Bus | `BroadcastChannel` | 창 간 이벤트 전파 |
| Shared Runtime | `SharedWorker` | 공통 실행 컨텍스트 유지 |
| Collaboration State | `Yjs` | 문서/그래프 실시간 동기화 |
| UI State | `Pinia` | 탭/드로어/선택 상태 유지 |

## 8.5 상태 동기화 정책

- 이벤트 채널은 단일 명명 규칙(`nexia.window.sync.v1`)을 사용한다.
- 모든 메시지는 `requestId`, `sourceWindowId`, `target`, `timestamp`를 포함한다.
- 동기화 우선순위:
  1. 보안/긴급 정지 이벤트
  2. 실행 제어 이벤트
  3. UI/레이아웃 이벤트

## 8.6 제어권(Handover) 규칙

- STT/마이크 제어권은 단일 창만 보유 가능.
- 제어권 요청 충돌 시 `Cockpit`이 우선권을 가진다.
- 고위험 실행(배포/IoT 제어)은 창에서 직접 실행하지 않고 Cockpit 승인 플로우로 위임한다.

## 8.7 레이아웃 복원 정책

- 저장 항목: 창 위치, 크기, 탭 매핑, 포커스 순서.
- 저장 주기: 사용자 변경 후 debounce 500ms.
- 복원 시점: 로그인 완료 후 1회 자동 복원.
- 실패 시: 안전 레이아웃(단일 창 Cockpit)로 폴백.

## 8.8 장애 대응

- 창 비정상 종료: 세션 잠금 없이 해당 창 작업만 격리.
- Sync 버스 지연: 로컬 임시 큐 적재 후 재전송.
- SharedWorker 재시작: 런타임 재결합 후 미완료 작업 재동기화.

## 8.9 KPI

| 항목 | 기준 |
| --- | --- |
| 창 간 상태 전파 지연 | 평균 50ms 이하 |
| 창 레이아웃 복원 성공률 | 99% 이상 |
| 제어권 충돌 자동 해결률 | 95% 이상 |
| 창 비정상 종료 복구 시간 | 3초 이하 목표 |
