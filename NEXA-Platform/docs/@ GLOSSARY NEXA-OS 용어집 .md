### "지능 진화론"의 완성

1.  **Identity(영혼):** **Nexel**은 각자 고유한 Identity를 가지며 시스템의 영혼을 형성합니다.
2.  **Why Chain(족보):** **Nexia**에서의 탐험은 단순히 채팅 기록을 남기는 것이 아니라, 끊어지지 않는 지능적 족보를 만드는 과정입니다.
3.  **VOID(여백):** **Nexeed**로 성장하지 못한 기록이나 사용되지 않는 **Nexet**은 VOID 상태로 전환되어 시스템의 잠재적 영감으로 보존됩니다.

## Nexel (넥셀)의 상세 메타포

**"세포는 작지만 그 안에 생존을 위한 모든 기관을 갖추고 있는"**는 생물학적 메타포

#### 1, Nexel의 해부학적 구조 (Nexel Anatomy)

단순히 '노드'라 부르던 시각적 객체를, 내부 동작 원리에 따라 4가지 핵심 기관으로 세분화하여 정의합니다.

| 기관 명칭                        | 역할 및 포함 요소                                    | 기술적 매핑 (UCL/API)                    |
| :------------------------------- | :--------------------------------------------------- | :--------------------------------------- |
| **Nexel Port (포트)**            | 외부와의 데이터 입출력 접점. IO 포인트, 핸들러.      | `input_channel`, `capability_id`         |
| **Nexel Schema (스키마)**        | 자료형 체크, 유효성 검사, 제약 조건 관리.            | `constraints`, `token_value`             |
| **Nexel Interface (인터페이스)** | 사용자가 값을 입력하거나 상태를 보는 폼(Form), 위젯. | `metadata.canvas_layout_hint`, `UI_CARD` |
| **Nexel Core (코어)**            | 내부 논리 연산, 실행 스크립트, 의사결정 로직.        | `UCL Score`, `why_chain.reasoning`       |

#### 2. Nexel의 유형화 전략 (Tagging & Typing)

별도의 복잡한 이름을 붙이는 대신, Nexel 내부에 **'Nature Tag(성격 태그)'**를 부여하여 분류합니다. AI(제니스)는 이 태그를 보고 해당 Nexel의 용도를 1ms 내에 판별합니다.

- **Logic Nexel:** 순수 연산 및 데이터 필터링 기능 수행.
- **Device Nexel:** 실물 하드웨어(IoT)나 가상 장치에 매핑된 실행 주체.
- **Bridge Nexel:** 외부 API(Slack, OpenAI 등)와의 통신 및 데이터 변환 담당.
- **Archive Nexel:** 과거의 지식이나 기록을 현재 실행 사슬로 불러오는 포털 역할.

### 1. 도메인: Nexel (지능 실행 및 논리 배선)

**실행 중심 도메인**

- **구동 방식:** **Vue Flow** 기반의 캔버스 위에서 **NODE-RED**와 유사한 플로우 방식의 인터페이스를 제공합니다.
- **핵심 객체 (Nexel):** 기존의 'Node'라는 용어를 대체하며, 단순한 시각적 카드가 아닌 **독립적 실행 자격을 갖춘 지능 세포(Cell)**로 작동합니다 [Conversation History].
- **해부학적 구조:** 각 Nexel은 데이터 입출력을 위한 **포트(Port)**, 자료형을 검증하는 **스키마(Schema)**, 설정을 위한 **인터페이스(Interface)**, 실제 로직이 담긴 **코어(Core)**를 내포합니다 [Conversation History].
- **역할:** 사용자가 Nexel들을 연결하여 **실행 사슬(Execution Chain)**을 형성하면, 이는 시스템의 **UCL(지능형 실행 프로토콜)** 악보로 저장되어 실제 장치 제어나 데이터 처리를 수행합니다.
- 엣지 디바이스 펌웨어를 시물레이션과 OTA 업데이트

### 2. 도메인: Nexion (NEXA-OS 설계 및 지식 지도)

**지능형 지식 운영체제(K-OS)**를 설계하고 관리하는 **수퍼 관리자 영역**입니다.

> 차후에 사용자들도 직접 자신의 지식 OS를 구성 할 수 있도록 해준다

- **구동 방식:** 실제 문서(Markdown)와 파일 시스템을 기반으로 한 **지능형 서사 파일 시스템(NFS)**을 구축합니다.
- **지식 지도(Knowledge Map):** 파일의 물리적 위치에 상관없이 **doc_anchor(앵커)**를 통해 지능적 사슬을 유지하며, 문서 간의 관계를 시각적으로 보여주는 지도를 형성합니다.
- **수퍼 관리자 공간:** NEXA-OS의 절대 원칙인 **ERA(시대)**와 **GOVERN(운영 규범)**을 설계하는 공간입니다.
- **위계적 귀속:** 차후 사용자가 자신만의 OS를 구성할 수 있으나, 이는 항상 **NEXA-OS 아래에 귀속**되며, 시스템 헌법과 같은 NEXA-OS의 핵심 규범 영역을 침범할 수 없습니다.

### 3. 도메인별 역할 비교 및 정합성

| 구분           | **도메인 Nexel**                          | **도메인 Nexion**                                                   |
| :------------- | :---------------------------------------- | :------------------------------------------------------------------ |
| **비유**       | **지능 실행 공장** (NODE-RED 식)          | **지능 설계 관제탑** (Knowledge OS)                                 |
| **핵심 기술**  | Vue Flow + 실행 사슬(Execution Chain)     | NFS(Inode 방식) + 지능적 족보(Traceability)                         |
| **관리 단위**  | **Nexel** (원자적 실행 단위)              | **Doc/Term/Identity/Capability** (지식 자산)                        |
| **권위 계층**  | 실행 모드 및 논리 배선                    | **ERA / GOVERN** (OS 규범 및 헌법)                                  |
| **주요 활동**  | 트리거, 입출력, 펌웨어 변환 및 시뮬레이션 | 지식 지도 구축, Late Anchoring, OS 설계                             |
| **역할 분리:** | **'어떻게(How)'** 실행할 것인가에 집중    | **'무엇을(What)'**.**'왜(Why)'** 존재하는가에 대한 지식적 근거 관리 |

### 4. 설계적 이점

- **보안 및 주권:** Nexion을 수퍼 관리자 영역으로 고정함으로써, 사용자가 커스텀 OS를 만들더라도 NEXA-OS의 핵심 가이드라인(Level 0 보안 등)이 훼손되지 않도록 보호할 수 있습니다.
- **유연한 확장:** Nexel 도메인을 통해 사용자는 복잡한 코딩 없이도 지능 세포를 조립하여 자신만의 자동화 생태계를 구축할 수 있게 됩니다.

### 3. 기술 스택 선정의 핵심 근거

1.  **NIXIE의 3분화:**
    - **Browser:** 브라우저의 연산 자원을 활용해 **GSAP**으로 도트의 생동감을 극대화합니다.
    - **Raspberry Pi:** 에지 모니터 환경에서 **P5.js**를 사용하여 생성적(Generative)인 HUD를 그려냅니다.
    - **ESP32:** 디스플레이가 없는 물리 장치에서 **FastLED**를 통해 시스템의 '체온'과 '맥박'을 직접 출력합니다.
2.  **NEXU의 P5.js 전환:** 기존 Vue Flow 대신 **P5.js(D3/Three.js 하이브리드)**를 사용하여 수만 개의 지식 아톰이 폭발하고 함몰되는 **프랙탈 줌** 연산을 부드럽게 구현합니다.
3.  **Nexion의 Vue Flow 유지:** 복잡한 노드 간의 연결과 계층 구조 설계에는 **Vue Flow**와 **Dagre** 엔진을 활용하여 '사고의 칠판'으로서의 기능을 유지합니다.
4.  **Nexus의 기반성:** Nexus는 직접적인 UI보다는 **Capability ID**와 **Identity ID**(`nexa_identities` 등)를 관리하는 데이터베이스(PostgreSQL, TimescaleDB) 및 인프라 계층으로 작동합니다.

이 구조를 통해 **"지능은 하나(Nexnap)이나 표현은 기기 성능에 맞춰 유연하게(NIXIE 3종)"** 대응하는 NEXA OS의 시각화 전략이 완성됩니다.

## HEXAGON VS Nexnap VS UCL

### 1. 역할 및 본질적 정의

- **HEXAGON (데이터 골격):** 데이터 패킷의 헤더에 위치하여 사건의 **'객체적 본질'을 규정하는 5W1H 추상화 레이어**입니다. 인공지능이 상황의 중요도를 1ms 내에 판단할 수 있게 돕는 **지능적 인덱스** 역할을 합니다.
- **Nexnap (동기화 스냅샷):** 시스템의 추상적인 지능 상태를 **정규화된 시청각 데이터 세트**로 변환하여 전역에 뿌려주는 **표준 인터페이스 계약**입니다. 닉시(NIXIE)가 소리와 빛으로 '연주'하기 위한 **연료**에 해당합니다.

### 2. 구성 요소의 차이

- **HEXAGON 축:** 6개의 정수 토큰(SMALLINT)으로 구성됩니다.
  - **Where(공간), When(시간), Who(주체), What(의도), How(상태), Why(인과관계)**.
- **Nexnap 필드:** 닉시 연출을 위한 상태값 중심입니다.
  - **how_state:** 흐름 상태 (FLOW / STUCK / VOID).
  - **who_pulse:** 페르소나 펄스 (WILL / ECHO / ASK / TICK).
  - **confidence_score:** 신뢰도 점수 (0~100, 95점 미만 시 Jitter 발생).

### 3. 처리 단계 및 위치

- **HEXAGON:** **입력 및 저장 레이어**에서 작동합니다. 데이터가 주입(Ingestion)될 때 텍스트를 숫자로 정규화하여 DB 인덱싱 및 RAG(검색 증강 생성)에 활용됩니다.
- **Nexnap:** **인터페이스 및 표현 레이어**에서 작동합니다. 주로 프론트엔드의 **Pinia 전역 스토어(`nexnapSnapshotStore.ts`)**에 상주하며, 닉시의 `draw()` 루프나 Tone.js의 소리 합성에 실시간 데이터를 공급합니다.

### 4. 비유를 통한 비교

| 구분            | **HEXAGON**                                        | **Nexnap**                                                                                       |
| --------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| **비유**        | 문장을 구성하는 **'문법'**이자 데이터의 **'족보'** | UCL에 의해 연주된 지능의 실시간 상태를 포착한 **'맥박'이자 '전송 봉투'**. (표정/맥박/인터페이스) |
| **신체적 역할** | 시스템의 단단한 **'골격(Skeleton)'**               | 시스템이 살아있음을 알리는 **'맥박(Pulse)'**                                                     |
| **목적**        | **AI가 사실(Fact)을 이해**하기 위함                | **사람이 지능의 상태를 감각**하기 위함                                                           |

**UCL(Unified Composition Language / Unified Context Layer)**은 시스템의 '지능'을 다룬다는 공통점이 있으나, **Nexnap은 ‘결과로서의 상태(Snapshot)’**를, **UCL은 ‘과정으로서의 논리(Protocol)’**를 담당한다는 점에서 명확히 구분됩니다.

### 5. Nexnap (넥스냅) : "지능의 맥박과 잔상"

Nexnap은 시스템의 추상적 지능 상태를 시청각적 피드백으로 변환하기 위한 **정규화된 데이터 스냅샷**입니다.

- **본질:** 시스템이 "지금 어떤 상태인가"를 보여주는 **동기화 규약**입니다.
- **역할:** 닉시(NIXIE)가 소리와 빛으로 연주하기 위한 **연료** 역할을 하며, `how_state`(흐름), `who_pulse`(페르소나), `confidence_score`(신뢰도) 등의 필드를 가집니다.
- **기술적 실체:** 주로 프론트엔드의 **Pinia 전역 스토어(`nexnapSnapshotStore.ts`)**에 상주하며 실시간으로 갱신됩니다.

### 6. UCL (유씨엘) : "지능의 악보와 집행"

UCL은 지능 운영체제(NEXA-OS)가 판단(IND)을 내리고 이를 실제 실행(EFF)으로 옮길 때 사용하는 **지능형 실행 프로토콜** 또는 **구성 언어**입니다.

- **본질:** 시스템이 "어떻게 움직여야 하는가"를 규정하는 **악보(Score)이자 지휘 매뉴얼**입니다.
- **역할:** 에이전트와 어댑터에게 전달되는 `execution_bundle`(실행 패키지), `constraints`(제약 조건), `is_virtual`(가상 실행 여부) 등의 **논리적 지시서**를 포함합니다.
- **기술적 실체:** 오케스트레이터 엔진과 백엔드 로직에서 작동하며, 실제 **실행 사슬(Execution Chain)**을 형성합니다.

### 7. 주요 차이점 비교

| 구분            | **Nexnap (넥스냅)**                        | **UCL (유씨엘)**                             |
| --------------- | ------------------------------------------ | -------------------------------------------- |
| **비유**        | 시스템이 살아있음을 알리는 **맥박(Pulse)** | 시스템을 지휘하는 **악보(Score)**            |
| **초점**        | **표현(Expression)** 및 사용자 체감        | **실행(Execution)** 및 논리 전개             |
| **데이터 구조** | 정규화된 **상태값** (how, who, confidence) | 복합적인 **실행 번들** (bundle, constraints) |
| **사용처**      | **NIXIE/NEXU 캔버스**의 시각적 동기화      | **오케스트레이터/어댑터**의 실제 동작 제어   |

### 8. 두 개념의 상호작용

NEXA 시스템 내에서 두 개념은 다음과 같이 맞물려 돌아갑니다.

1. **UCL이 연주를 시작합니다:** 인디케이터가 UCL 프로토콜에 따라 판단을 내리고 실행 번들을 생성합니다.
2. **Nexnap이 상태를 포착합니다:** UCL에 의해 실행이 일어나는 순간, 시스템의 상태 변화를 **Nexnap(스냅샷)**이 한순간 낚아챕니다.
3. **사용자가 감각합니다:** 낚아챈 Nexnap 데이터를 바탕으로 닉시가 **Lumina(발광)**와 **Jitter(떨림)**를 연주하여 사용자에게 지능의 상태를 전달합니다.

**결론:** **UCL**은 지능의 **생각과 행동을 짜는 틀**이고, **Nexnap**은 그 결과로 드러나는 **지능의 표정·맥박**을 담는 그릇이다. 두 이름은 바꿔 쓰지 않는다.

## 운영 레퍼런스: 데이터 흐름·스키마 연계

아래는 **펄스(Who) → 식별(Identity ID) → 실행 사슬 → 상태·HEXAGON·COILS → Nexnap·Capability → 신뢰·공유·Empathy·캔버스**까지를 **필드·테이블** 관점에서 잇는 **운영용 레퍼런스**다. 상위 정의는 **§3-A~3-D**를 따르며, 이 절은 **흐름·DDL 연결**에 초점을 둔다.

### 1. 펄스(Pulse) 및 승인 계층 (Who / Pulse)

펄스는 “누가(또는 무엇이) 이 결정을 만들었는가”를 표시하는 1차 근거다.

| 약어   | 풀네임 (Full Name)         | 의미 및 역할                                                                           | 질문자님의 해석 (장기 기억 관점) |
| ------ | -------------------------- | -------------------------------------------------------------------------------------- | -------------------------------- |
| WILL   | User Intent (Approval)     | 사용자의 명시적 의도/승인. 실제 투입(실물 실행) 권한의 기준                            | 단기 실행 / 최종 승인            |
| ECHO   | AI Echo / Assessment       | AI의 판단/재해석 제안. 일반적으로 직접 집행보다는 ASK/WILL로 이어질 “말 걸기”의 시작점 | 중기 기억 / 제안 계층            |
| TICK   | Device/Sensor Fact         | 디바이스/센서가 발생시키는 사실(관측). 검증 가능한 SNT(사실) 생성 원천                 | 사실 저장 / 센서 족보            |
| ASK    | Assessment & Key-check     | 불확실·위험·권한 문제 등으로 사용자 승인/선택이 필요한 상태                            | 단기 기억 / 판단 중              |
| GOVERN | Governance                 | 규칙이 운영 단계로 승격되어 통제/관리 대상이 되는 흐름                                 | 운영 중 / 절차적 고착            |
| ERA    | Established Rule Authority | 시스템 생존과 직결된 절대 원칙(헌법) 단계(고정, 수정 불가)                             | 장기 기억 / 불변 권위            |

### 2. Identity ID · 족보 원장 (Nexion Identity)

**§3-B**의 **Identity ID**와 같은 축이다. **펄스(Who)**·**실행 사슬(actor_id)** 과 **영혼 원장**을 섞지 않도록 아래를 구분한다.

| 구분 | 의미 및 연계 |
| --- | --- |
| **Identity ID** | **`nexa_identities`** 원장의 **6자** 식별자. 족보·`domain_tags`·승계 체인. 세부 규칙·정제 UI는 **Identity v3.1**·NXN ②. |
| **`actor_id` 등** | **실행 사슬** `execution_chains.actor_id` — **당회 실행**의 책임 주체(USER / DEVICE / AGENT 인스턴스). **장기 정체성·족보의 정본 SSOT**는 Identity ID 측과 역할을 나눈다. |
| **⑤ Narrative · Glossary** | 파일 서사·`anchor_id`·Glossary **용어 행**은 각각 Narrative·용어 축 — **Identity ID(식별자)** 와 혼동하지 않는다. |

### 3. 실행 사슬(Execution Chain) 및 단계(Execution Steps)

실행 사슬은 Nexnap Protocol이 생성하는 “실시간 실행 엔티티”이며, 단계는 “원자적 마디(Atomic Action)”다.

| 용어                              | 의미 및 역할                                                         | 연결 필드/대상(문서 기준)                                                                        |
| --------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| execution_chains                  | 실행 사슬의 최상위 레코드(실시간 악보/상태 관리)                     | `execution_chains.packet_id`, `where_scope`, `when_tempo`, `who_pulse`, `how_state`, `why_chain` |
| packet_id                         | 실행 사슬 식별자(UUID v7 시간정렬 신뢰성 전제)                       | `execution_chains.packet_id`, `execution_steps.packet_id`                                        |
| actor_id                          | 실행 책임자 주체 ID(사용자/디바이스/에이전트)                        | `execution_chains.actor_id`                                                                      |
| actor_type                        | 실행 주체의 유형(USER/DEVICE/AGENT)                                  | `execution_chains.actor_type`                                                                    |
| execution_steps                   | 실행 사슬을 구성하는 원자 스텝 테이블                                | `execution_steps.step_status`, `is_virtual`, `timeline_branch_id`                                |
| step_sequence                     | 스텝 실행 순서                                                       | `execution_steps.step_sequence`                                                                  |
| step_status                       | 스텝 상태(FLOW/STUCK/COMPLETED/FAILED/VOID)                          | `execution_steps.step_status`                                                                    |
| is_virtual                        | 가상(Dry-run) 여부. 실물(EFF) 방지용 의미론적 잠금                   | `execution_steps.is_virtual`                                                                     |
| target_entity_type                | 대상 계열 구분(예: PHYSICAL/NEXU/AUTHORIZED_VIRTUAL/SIMULATION_NODE) | `execution_steps.target_entity_type`                                                             |
| timeline_branch_id                | 평행 타임라인(분기) 식별자                                           | `execution_steps.timeline_branch_id`                                                             |
| post_state_snapshot               | 타임머신 “뒤로가기” 복원 스냅샷                                      | `execution_steps.post_state_snapshot`                                                            |
| why_chain / why_step_logic        | 상태 전환의 인과 사슬(Reasoning + Effects)                           | `execution_chains.why_chain`, `execution_steps.why_step_logic`                                   |
| execution_bundle / context_bundle | 실행에 필요한 명령/제약/코일 가중치/페르소나 묶음                    | `execution_chains.execution_bundle`, `execution_chains.context_bundle`                           |

### 4. 상태 전이(State Lifecycle) — FLOW / STUCK / VOID (+ 확장)

실행 주체는 FLOW/STUCK/VOID를 순환하며, VOID는 단계별로 데이터의 생애를 다르게 취급한다.

| 상태/단계       | 의미 및 역할                                           | 전이(문서 임계치 요약)                     |
| --------------- | ------------------------------------------------------ | ------------------------------------------ |
| FLOW            | 실행/인지 흐름 활성화(정상 박동)                       | FLOW → STUCK                               |
| STUCK           | 흐름 막힘(응답 지연/충돌/대기)                         | STUCK → VOID.POTENTIAL                     |
| VOID            | 잠재/영감 대기(물리 삭제 아님)                         | VOID.POTENTIAL → VOID.ARCHIVE → VOID.PURGE |
| VOID.POTENTIAL  | 단기 잠재(재개 가능 구간)                              | 인디케이터/센서별 임계치 적용              |
| VOID.ARCHIVE    | 장기 압축/지식화 구간                                  | TimescaleDB 압축 시점(90일 등)             |
| VOID.PURGE      | 보존 조건 미충족 시 물리 삭제 후보                     | 기본 PURGE 임계치(365일 등)                |
| MOMENT          | (when_tempo) 맥락이 단기~중기 유지되는 시간축 구간     | MOMENT → DURATION                          |
| DURATION        | (when_tempo) 장기 미재개로 압축/지식화로 넘어가는 구간 | DURATION → ARCHIVE                         |
| ERA (신설/격상) | core 자산(“영혼(Soul)”로 승격)                         | ARCHIVE → ERA 후 purge 영구 제외           |
| Safety VOID     | 위험/Level0 위반 시 즉시 무효화                        | Safety guardrail 강제                      |
| UX VOID         | 사용자의 망설임/변심이 감지되어 영감 모드 진입         | 넥슈가 Nexnap 템플릿 성운 펼침             |
| Data VOID       | 노후화된 이력/규칙을 지식화하고 로우 데이터를 비움     | 지식/아카이브 정리                         |

### 5. HEXAGON Protocol(핵사곤) 및 5W1H 골격

핵사곤은 “데이터 패킷의 헤더”로서 사건/맥락의 본질을 6축으로 고정한다.

| 축    | 약어/의미                            | 예시(문서 기준)            |
| ----- | ------------------------------------ | -------------------------- |
| Where | 공간/영향 범위(Scope)                | SELF/FIELD/DOMAIN          |
| When  | 시간적 맥락(Tempo)                   | MOMENT/DURATION/ERA        |
| Who   | 주체(Pulse 동력원)                   | WILL/ECHO/TICK/ASK         |
| What  | 데이터 성격(의도/팩트 유형)          | FACT/LINK/RULE/INTENT      |
| How   | 실행 상태(Flow 계열)                 | FLOW/STUCK/VOID            |
| Why   | 인과/판단 카테고리(코일 밸런서 관여) | Why/Decision Matrix 근거군 |

### 7. Nexnap Layer vs Nexnap Protocol

**Nexnap** 아래에서 **정책·의미**와 **전송·형식**을 나눈 것이다. **동기화 스냅샷**(Pinia·NIXIE)은 위 3-A 표 **Nexnap** 행의 **②**와 같고, 아래는 **① Nexnap Protocol** 축의 세분이다.

| 구분            | 의미 및 역할                                                            |
| --------------- | ----------------------------------------------------------------------- |
| Nexnap Layer    | 의미/정책 계층(목표 해석, 상태 추적, 충돌 조정, 컨텍스트 축적)          |
| Nexnap Protocol | 전송/형식 계층(스키마, 필수 필드, 코드값, 라우트/채널, 왕복 인터페이스) |

### 10. 외부 자원 합성(동적 Substitution) 핵심 용어

외부 API/타 프로젝트 자원을 “잠재(VOID)”에서 “실체”로 끌어오는 프로토콜 용어다.

| 용어                                  | 의미 및 역할                                                      |
| ------------------------------------- | ----------------------------------------------------------------- |
| Resource Substitution(자원 차출/대체) | 문제 발생 또는 최적화 목적의 동적 대체                            |
| Where-Scope 필터링                    | 사고 지점 주변/유사 범위를 1ms급으로 좁히는 공간 스코프 필터      |
| project_network_topology              | 장치 간 거리/연결망을 저장하는 DB(“가까운 눈” 후보 계산의 기반)   |
| Meaning Lock                          | is_virtual=true로 안전성 검증 후, WILL 시 is_virtual=false로 전환 |
| Reverse Decomposition                 | 기존 실행 계획을 대체 자원에 맞는 새 Nexnap 패킷으로 재조립       |
| project_simulations                   | 가상 시뮬레이션 결과의 저장소(사전 평정/검증 근거)                |
| is_virtual=false 투입                 | 실제 EFF(실물 실행) 수행의 최종 단계(권한/신뢰 통과 필요)         |

### 11. 공유(Share)와 구독(Subscription) 및 보호 전략

“상시 공유 vs 동적 차용” 모두 대상 시스템 무결성을 유지해야 한다.

| 용어                           | 의미 및 역할                                                             |
| ------------------------------ | ------------------------------------------------------------------------ |
| device_members                 | 사용자↔디바이스 공유 멤버십/역할 매핑                                   |
| project_members                | 프로젝트 공유 멤버십(향후 확장)                                          |
| sharing_status                 | `active`/`suspended`/`revoked`(소유자 주권으로 즉시 무효화 가능)         |
| resource_sharing_policy        | 차용 우선순위/복구 조건/임대 기한(TTL)·할당량 제한을 담는 정책           |
| Suspension(Suspend)            | 소유자가 공유/차용 연결을 일시 중단해 원본을 독점 사용하도록 만드는 조치 |
| Revoke(영구 끊기)              | 소유자가 연결을 해제하고 차용자 접근을 영구 제거                         |
| Owner Sovereignty(소유자 주권) | 우선권은 항상 소유자에게 있으며, 대상 무결성은 훼손되지 않음             |
| Host-First Policy              | 본 디바이스/소유자 리소스가 항상 우선 점유(대여자는 남는 여력만 사용)    |
| Subscription(구독)             | “새로 생성하지 않고 타인의 데이터를 참조/관측”하는 실시간 연결 모델      |

### 12. Empathy(공감) 및 활력 지수(VI) 제동

Empathy는 실행의 ‘사람 중심’ 가드레일이다.

| 용어                 | 의미 및 역할                                                        |
| -------------------- | ------------------------------------------------------------------- |
| Empathy Engine       | 행동 신호(체류/발화/롤백/취소 등)로 ES·VI·PP를 계산                 |
| ES (Empathy Score)   | 사람의 정서/도움 필요도를 나타내는 지수                             |
| VI (Vitality Index)  | 사용자의 활력/피로도를 나타내는 지수(낮으면 제동)                   |
| PP (Pace Preference) | 응답 속도 선호(fast/normal/slow)                                    |
| VI 임계값            | VI 구간별로 자율 실행/제안 강도를 조절하는 기준                     |
| Low-Entropy 모드     | VI가 낮을 때 복잡한 자원 합성 제안을 중단하고 로컬/안정 자원만 사용 |
| ES·VI·PP 연동        | Empathy 신호를 system prompt 톤/실행 큐로 반영                      |

### 13. NEXU·NIXIE 캔버스 표현 언어

데이터·상태를 **서사적 시각 언어**로 투영하는 캔버스 체계다. (**NEXU** Why Chain 증명 · **NIXIE** 비언어 연출.)

| 용어                      | 의미 및 역할                                                                               |
| ------------------------- | ------------------------------------------------------------------------------------------ |
| NEXA NIXIE / NEXU Canvas  | HEXAGON×6-COILS 기반 지능형 서사 시각화 캔버스                                             |
| Lumina                    | 신뢰도·상태(체온/부하)에 따라 발광 강도와 색온도가 변하는 “빛의 생명력”                    |
| Jitter                    | 불확실/긴장/오류 상황에서 도트가 미세 떨리는 연출                                          |
| Fractal Sync              | Capability ID 마침표(.) 계층에서 폭발/함몰(10-100-1000 군집화) 전이                        |
| Implosion(함몰)           | Zoom Out 시 상위 개념으로 응축                                                             |
| Explosion(폭발)           | Zoom In 시 세부가 사방으로 분화                                                            |
| Mixer Node                | Where(GPS)와 Capability ID(논리 좌표)를 조율해 도트를 배치                                 |
| LOD                       | COLD/WARM/HOT 하드웨어 프로필에 따른 연출/연산 강도                                        |
| COLD                      | 최소 애니메이션/가독성 우선 모드                                                           |
| WARM                      | 하이브리드 연출 모드                                                                       |
| HOT                       | 풀 시뮬레이션/잔상 최대 모드                                                               |
| 외부 도트 인입(VOID→편입) | Nexnap-08에서 외부 자원이 VOID 외곽에서 클러스터 폭발로 현재 좌표계로 편입되는 연출 가이드 |

### 14. 에러 코드 및 서사적 애니메이션 매핑(넥슈/Rive)

에러는 텍스트보다 먼저 표정/연출로 심각도를 전달한다.

| error_code              | 넥슈(Rive) 상태                | 캔버스 연출(요약)             |
| ----------------------- | ------------------------------ | ----------------------------- |
| ADAPTER_TIMEOUT         | Confused(고개 갸우뚱)          | 해당 장치 도트 Jitter         |

| ADAPTER_PARTIAL_SUCCESS | 고민 표정 + ASK 대기 유도      | 성공/실패 도트 구분           |
