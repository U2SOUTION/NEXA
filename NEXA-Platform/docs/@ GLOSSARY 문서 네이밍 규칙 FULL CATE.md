# GLOSSARY SYS 문서 네이밍 규칙

> NEXA 플랫폼 문서 관리 표준 — 파일명 구성 규칙 및 코드 참조표

---

## 파일명 구조

```
{DocType} {CONTEXT 번호} {한글 제목} v{N}.md
```

| 구성 요소 | 규칙 |
|-----------|------|
| 구분자 | 공백만 사용. 언더바·하이픈 없음 |
| DocType | 항상 맨 앞, 대문자 |
| Context | 번호가 없는 경우 코드만, 있는 경우 코드 + 공백 + 번호 |
| 제목 | 한글 중심, 고유명사·전문용어는 영문 병기 |
| 버전 | 개정이 예상되는 문서만 끝에 v1, v2... 붙임. 단발성 문서는 생략 |
| 진행 중 | 파일명 맨 앞에 `_` 하나. 탐색기 상단 고정 + 미완료 표시 |

### 예시

```
VISION SYS NEXA가 무엇을 하는가.md
ARCH SYS NEXA 전체 아키텍처 v1.md
SPEC AIS 04 AI 협업 TS 타입 스키마.md
SCHEMA DDL 00 NEXA DB 설계 명세서 v5.md
ADR PRJ 15 프로젝트 데이터 격리 구조.md
GLOSSARY SYS 기술 스택 통합 용어집.md
RUNBOOK INF 08 디바이스 등록 절차.md
_ RFC AIS AI 워크스페이스 웹서치 자원전략.md
```

## DocType 코드표

개발 프로세스 순서 기준으로 정렬되어 있습니다.
전체를 익힌 후 자주 쓰지 않는 타입은 자연스럽게 통합·축약해서 사용하세요.

### 1단계 — 탐색 / 아이디어

막연한 목적에서 출발해 가능성을 확인하는 단계입니다.

| # | 코드 | 풀 네임 | 선택 가이드 |
|---|------|---------|------------|
| 01 | `NOTE` | Note | 단편적인 메모, 생각 조각. 아직 문서 형태가 아닌 것 |
| 02 | `SPIKE` | Spike / Exploration | "이게 가능한가" 기술 탐색. 결과가 목적을 바꿔도 됨 |
| 03 | `VISION` | Vision Document | 왜 만드는가, 어디로 가는가. 방향과 목적의 최초 정의 |
| 04 | `CONCEPT` | Concept Document | 핵심 개념과 용어 정의. VISION보다 구체적인 아이디어 |

### 2단계 — 요구사항 / 기획

무엇을 만들지 정의하는 단계입니다.

| # | 코드 | 풀 네임 | 선택 가이드 |
|---|------|---------|------------|
| 05 | `PRD` | Product Requirements Document | 제품 전체의 요구사항. 기능·비기능·제약 조건 포함 |
| 06 | `REQ` | Requirements | PRD보다 범위가 작은 단위 요구사항. 특정 기능·모듈 대상 |
| 07 | `BRD` | Business Requirements Document | 비즈니스 목표와 정책 중심의 요구사항. 기술보다 업무 관점 |
| 08 | `MRD` | Market Requirements Document | 시장·사용자 관점의 요구사항. 경쟁 분석, 타깃 사용자 정의 |
| 09 | `USE CASE` | Use Case Document | 사용자가 시스템과 상호작용하는 시나리오 기술 |
| 10 | `USER STORY` | User Story | 사용자 관점의 기능 요구사항. "~로서 ~하고 싶다" 형식 |

### 3단계 — 제안 / 결정

방향을 제안하고 결정을 기록하는 단계입니다.

| # | 코드 | 풀 네임 | 선택 가이드 |
|---|------|---------|------------|
| 11 | `RFC` | Request for Comments | 아직 결정 전. 방향 제안 및 검토 요청. 초안·기획안 |
| 12 | `RFP` | Request for Proposal | 외부 제안 요청. 벤더·파트너에게 솔루션 제안을 요청할 때 |
| 13 | `PROPOSAL` | Proposal | 내부 제안서. 새로운 기능·방향·투자를 제안할 때 |
| 14 | `ADR` | Architecture Decision Record | 결정 완료 후 이유와 맥락 기록. RFC가 확정되면 ADR로 전환 |

### 4단계 — 설계

어떻게 만들지 정의하는 단계입니다.

| # | 코드 | 풀 네임 | 선택 가이드 |
|---|------|---------|------------|
| 15 | `ARCH` | Architecture Document | 전체 구조와 컴포넌트 관계. 시스템이 어떻게 구성되는가 |
| 16 | `HLD` | High Level Design | 상위 수준 설계. ARCH와 유사하나 더 넓은 관점 |
| 17 | `LLD` | Low Level Design | 하위 수준 설계. 클래스, 함수, 알고리즘 등 구현 직전 단계 |
| 18 | `DESIGN` | Design Document | UI 흐름, 모듈 내부 구조, 인터페이스 정의 |
| 19 | `WIREFRAME` | Wireframe Document | UI 와이어프레임 및 화면 흐름 정의 |
| 20 | `SPEC` | Specification | 동작 명세. 입력/출력/조건/예외까지 정밀하게 정의 |
| 21 | `API` | API Specification | API 엔드포인트, 파라미터, 응답 형식 명세 |
| 22 | `SCHEMA` | Schema Document | 데이터 구조 정의. DB 테이블, JSON 구조, API 페이로드 |
| 23 | `ERD` | Entity Relationship Diagram | 데이터 엔티티 간 관계 정의. SCHEMA 작성 전 선행 문서 |
| 24 | `FLOW` | Flow Document | 업무 흐름, 데이터 흐름, 상태 전이 등 흐름 중심 설계 |
| 25 | `PROTO` | Prototype Document | 프로토타입 제작 기록 및 검증 결과 |

### 5단계 — 구현 / 검증

만들고 확인하는 단계입니다.

| # | 코드 | 풀 네임 | 선택 가이드 |
|---|------|---------|------------|
| 26 | `IMPL` | Implementation Note | 구현 중 결정 사항, 기술 선택 이유 등 개발 메모 |
| 27 | `TEST` | Test Plan / Test Case | 테스트 계획, 시나리오, 케이스 정의 |
| 28 | `QA` | QA Document | 품질 검증 기준과 결과 기록 |
| 29 | `REVIEW` | Review Document | 코드 리뷰, 설계 리뷰, 문서 리뷰 결과 |

### 6단계 — 운영 / 유지보수

배포 이후 운영하는 단계입니다.

| # | 코드 | 풀 네임 | 선택 가이드 |
|---|------|---------|------------|
| 30 | `GUIDE` | Guide | 사용 방법 설명. 설치, 설정, 사용법 등 절차 중심 |
| 31 | `RUNBOOK` | Runbook | 반복 운영 절차. 배포, 장애 대응, 점검 체크리스트 |
| 32 | `SOP` | Standard Operating Procedure | 표준 운영 절차. RUNBOOK보다 공식적이고 상세한 절차서 |
| 33 | `POSTMORTEM` | Postmortem | 장애·사고 이후 원인 분석 및 재발 방지 기록 |
| 34 | `CHANGELOG` | Changelog | 버전별 변경 이력. 기능 추가·수정·삭제 기록 |
| 35 | `RELEASE` | Release Note | 배포 시 사용자에게 전달하는 변경 내용 요약 |

### 7단계 — 참조 / 기준

언제든 참조되는 기준 문서입니다.

| # | 코드 | 풀 네임 | 선택 가이드 |
|---|------|---------|------------|
| 36 | `GLOSSARY` | Glossary | 용어 정의 모음. 시스템 내 공통 언어 정리 |
| 37 | `REF` | Reference | 확정된 기준 자료. 다른 문서들이 참조하는 마스터 문서 |
| 38 | `FAQ` | Frequently Asked Questions | 자주 묻는 질문과 답변 모음 |
| 39 | `REPORT` | Report | 분석·조사·실험 결과 보고서 |
| 40 | `LOG` | Log | 작업 기록, 실험 기록, 회의록 등 시간순 기록 |

## NEXA 축약 세트 (1인 개발 기준)

40개 전체 중 현재 NEXA 플랫폼 단계에서 실질적으로 필요한 타입만 추린 세트입니다.
익숙해지면 이 목록을 기준으로 사용하고, 필요시 전체 표를 참조하세요.

| # | 코드 | 대응 전체 타입 | 사용 시점 |
|---|------|--------------|----------|
| 1 | `NOTE` | NOTE | 단편 메모, 아이디어 조각. 구조 없어도 됨 |
| 2 | `SPIKE` | SPIKE | 기술 가능성 탐색. 결과가 방향을 바꿔도 됨 |
| 3 | `VISION` | VISION | 왜 만드는가. 목적과 방향의 최초 정의 |
| 4 | `PRD` | PRD + BRD + MRD | 무엇을 만드는가. 기능·정책·사용자 요구사항 통합 |
| 5 | `RFC` | RFC + PROPOSAL | 아직 결정 전. 방향 제안·검토 요청·초안 |
| 6 | `ADR` | ADR | 결정 완료. 이유와 맥락 기록 |
| 7 | `ARCH` | ARCH + HLD | 전체 구조. 기술 스택, 컴포넌트 관계 |
| 8 | `DESIGN` | DESIGN + LLD + WIREFRAME | 세부 설계. UI 흐름, 모듈 내부, 화면 구성 |
| 9 | `SPEC` | SPEC + API | 동작 명세. 입출력·조건·예외, API 엔드포인트 |
| 10 | `SCHEMA` | SCHEMA + ERD | 데이터 구조. DB 테이블, 엔티티 관계 |
| 11 | `GUIDE` | GUIDE + RUNBOOK + SOP | 절차·운영. 사용법, 배포, 반복 작업 |
| 12 | `LOG` | LOG + CHANGELOG + IMPL | 기록. 작업 메모, 변경 이력, 실험 결과 |
| 13 | `GLOSSARY` | GLOSSARY + REF | 기준 자료. 용어 정의, 마스터 문서 |

### 통합 근거

```
PRD 로 통합    ←  BRD(업무 정책), MRD(시장·사용자) 는 1인 개발에서 PRD 안에 포함 가능
ARCH 로 통합   ←  HLD 는 ARCH 와 사실상 같은 역할
DESIGN 으로 통합  ←  LLD·WIREFRAME 은 DESIGN 문서 안에 섹션으로 구분 가능
SPEC 으로 통합  ←  API 명세는 SPEC 문서 안에 포함 가능
SCHEMA 로 통합  ←  ERD 는 SCHEMA 작성 전 선행 내용으로 같은 파일에 포함 가능
GUIDE 로 통합   ←  RUNBOOK·SOP 는 현재 운영 단계가 아님
LOG 로 통합    ←  IMPL·CHANGELOG 는 기록 성격으로 동일
GLOSSARY 로 통합  ←  REF 는 GLOSSARY 와 함께 기준 문서 역할
```

### 나중에 추가될 타입 (운영 단계 진입 시)

```
RUNBOOK   →  배포·장애 대응 절차가 반복될 때
POSTMORTEM  →  운영 중 사고가 발생했을 때
RELEASE   →  사용자에게 배포 내용을 전달할 때
QA        →  테스트 체계가 필요해질 때
```

## DocType 선택 흐름

```
지금 어느 단계인가?

[ 탐색 · 아이디어 ]
  단편 메모, 아직 구조 없음             → NOTE
  기술이 가능한지 먼저 확인             → SPIKE
  왜 만드는가, 목적·방향 정의           → VISION
  핵심 개념과 용어를 정리               → CONCEPT

[ 요구사항 · 기획 ]
  제품 전체 요구사항                    → PRD
  특정 기능·모듈 요구사항              → REQ
  비즈니스·업무 정책 중심              → BRD
  시장·사용자·경쟁 분석 중심           → MRD
  사용자 시나리오 기술                  → USE CASE / USER STORY

[ 제안 · 결정 ]
  아직 검토 중, 방향 제안               → RFC
  외부에 솔루션 제안 요청               → RFP
  내부 제안서                           → PROPOSAL
  결정 완료, 이유와 맥락 기록           → ADR

[ 설계 ]
  전체 구조, 컴포넌트 관계              → ARCH / HLD
  모듈 내부, 구현 직전 상세 설계        → LLD
  UI 흐름, 인터페이스 정의              → DESIGN
  UI 화면 구성, 와이어프레임            → WIREFRAME
  동작 명세, 입출력·예외 조건           → SPEC
  API 엔드포인트·파라미터 명세          → API
  데이터 구조, DB 테이블                → SCHEMA
  엔티티 관계 정의                      → ERD
  업무·데이터·상태 흐름                 → FLOW
  프로토타입 제작 및 검증               → PROTO

[ 구현 · 검증 ]
  구현 중 결정 메모                     → IMPL
  테스트 계획·케이스                    → TEST
  품질 검증 기준·결과                   → QA
  리뷰 결과 기록                        → REVIEW

[ 운영 · 유지보수 ]
  사용 방법·설치·설정                   → GUIDE
  반복 운영 절차                        → RUNBOOK
  공식 표준 운영 절차                   → SOP
  장애·사고 원인 분석                   → POSTMORTEM
  버전별 변경 이력                      → CHANGELOG
  배포 시 변경 내용 요약                → RELEASE

[ 참조 · 기준 ]
  용어 정의 모음                        → GLOSSARY
```
