# GLOSSARY SYS 문서 네이밍 규칙

> NEXA 플랫폼 문서 관리 표준 — 파일명 구성 규칙 및 코드 참조표

---

## 파일명 구조

```
{Context} {번호} {DocType} {한글 제목} v{N}.md
```

Context를 맨 앞에 두어 작업 단위로 문서를 그룹핑합니다.

| 구성 요소 | 규칙                                                           |
| --------- | -------------------------------------------------------------- |
| 구분자    | 공백만 사용. 언더바·하이픈 없음                                |
| Context   | 맨 앞. 번호가 없는 경우 코드만, 있는 경우 코드 + 공백 + 번호   |
| DocType   | 대문자                                                         |
| 제목      | 한글 중심, 고유명사·전문용어는 영문 병기                       |
| 버전      | 개정이 예상되는 문서만 끝에 v1, v2... 붙임. 단발성 문서는 생략 |
| 진행 중   | 파일명 맨 앞에 `_` 하나. 탐색기 상단 고정 + 미완료 표시        |

### 예시

```
SYS VISION 무엇을 하고 있는가.md
SYS ARCH NEXA 전체 아키텍처 v1.md
AIS 04 SPEC AI 협업 TS 타입 스키마.md
DDL 00 SCHEMA NEXA DB 설계 명세서 v5.md
PRJ 15 ADR 프로젝트 데이터 격리 구조.md
SYS GLOSSARY 기술 스택 통합 용어집.md
INF 08 RUNBOOK 디바이스 등록 절차.md
_ AIS RFC AI 워크스페이스 웹서치 자원전략.md
```

## DocType 코드표

개발 프로세스 순서 기준으로 정렬되어 있습니다.

### 탐색 / 정의 단계

| #   | 코드      | 풀 네임          | 선택 가이드                                                     |
| --- | --------- | ---------------- | --------------------------------------------------------------- |
| 01  | `VISION`  | Vision Document  | 왜 만드는가, 무엇을 해결하는가. 방향과 목적을 처음 정의할 때    |
| 02  | `CONCEPT` | Concept Document | 핵심 개념, 용어, 아이디어의 의미를 정의할 때. VISION보다 구체적 |
| 03  | `REQ`     | Requirements     | 무엇을 만들어야 하는가. 기능/비기능 요구사항 목록               |

### 제안 / 결정 단계

| #   | 코드  | 풀 네임                      | 선택 가이드                                                    |
| --- | ----- | ---------------------------- | -------------------------------------------------------------- |
| 04  | `RFC` | Request for Comments         | 아직 결정 전. 방향을 제안하고 검토를 요청할 때. 초안·기획안    |
| 05  | `ADR` | Architecture Decision Record | 결정이 완료된 후 이유와 맥락을 기록. RFC가 확정되면 ADR로 전환 |

### 설계 단계

| #   | 코드     | 풀 네임               | 선택 가이드                                                      |
| --- | -------- | --------------------- | ---------------------------------------------------------------- |
| 06  | `ARCH`   | Architecture Document | 전체 구조와 컴포넌트 관계. 시스템이 어떻게 구성되는가            |
| 07  | `DESIGN` | Design Document       | ARCH보다 세부적인 설계. UI 흐름, 모듈 내부 구조, 인터페이스 정의 |
| 08  | `SPEC`   | Specification         | 동작을 정밀하게 명세. 입력/출력/조건/예외까지 정의된 기술 문서   |
| 09  | `SCHEMA` | Schema Document       | 데이터 구조 정의. DB 테이블, JSON 구조, API 페이로드 형태        |

### 운영 / 참조 단계

| #   | 코드       | 풀 네임   | 선택 가이드                                                  |
| --- | ---------- | --------- | ------------------------------------------------------------ |
| 10  | `GUIDE`    | Guide     | 방법을 설명하는 문서. 설치, 설정, 사용법 등 절차 중심        |
| 11  | `RUNBOOK`  | Runbook   | 운영 중 반복 수행하는 절차. 배포, 장애 대응, 점검 체크리스트 |
| 12  | `GLOSSARY` | Glossary  | 용어 정의 모음. 팀/시스템 내 공통 언어를 정리할 때           |
| 13  | `REF`      | Reference | 확정된 기준 자료. 다른 문서들이 참조하는 마스터 문서         |

## DocType 선택 흐름

```
이 문서가 처음 방향을 잡는 문서인가?
  └─ 아직 막연한 목적 수준       → VISION
  └─ 개념과 용어를 정의          → CONCEPT
  └─ 요구사항을 나열             → REQ

결정 전인가, 결정 후인가?
  └─ 아직 검토 중, 초안          → RFC
  └─ 결정 완료, 이유를 남김      → ADR

설계 문서인가?
  └─ 전체 구조, 컴포넌트 관계    → ARCH
  └─ 세부 설계, UI 흐름          → DESIGN
  └─ 동작 명세, 입출력 조건      → SPEC
  └─ 데이터 구조, DB 테이블      → SCHEMA

운영·참조 문서인가?
  └─ 사용 방법, 설치 절차        → GUIDE
  └─ 반복 운영 절차              → RUNBOOK
  └─ 용어 정의 모음              → GLOSSARY
  └─ 확정된 기준 자료            → REF
```
