# [NEXA-NODE-01] ESPHome YAML 제너레이터 및 웹 펌웨어 배포 기획

**목적**: `/nexa-node` 도메인에서 **D3.js + 노드 + 라인** 기반 시각 편집으로 ESPHome용 **YAML을 생성**하고, YAML로 부족한 **고급 로직은 C++ 스타일 Lambda 코드 작성기**로 보완(저수준 제어 가능)한 뒤, **ESPHome에 전달하여 바이너리를 받아** 웹 브라우저에서 **개발 디바이스에 직접 펌웨어 업로드(USB)** 또는 **OTA 업데이트**를 수행한다. **초보자**는 직관적 노드 배치로, **전문가**는 에지 AI 고속 통신·전체 시스템 모니터링·Lambda 저수준 제어를 모두 쓰는 **하이브리드 아키텍처**를 지향하며(§0.3), 이 과정 전반에 **현재 기획 중인 AI 협업**을 연동한다.

**적용 도메인**: `/nexa-node` (NEXA NODE)

**작성일**: 2025-03

---

## 0. 배경 및 목표

### 0.1 배경

- ESPHome은 **YAML 설정**으로 디바이스(ESP8266/ESP32) 구성을 정의하고, **ESPHome CLI(Python 기반)** 가 이를 C++ 펌웨어로 빌드·플래시한다.
- **의도**: 사용자가 **별도로 Python/ESPHome CLI를 설치**할 필요 없이, NEXA 플랫폼 **웹 브라우저 안**에서 전체 흐름을 처리하고자 한다. 빌드는 백엔드(Docker ESPHome 서버 등)에서 수행. 가능하면 **사용자 측 외부 의존성을 줄이는** 방향이다. (ESPHome CLI·로컬 대시보드는 개발·테스트·YAML 검증용으로 별도 활용 가능.)
  1. **시각적 YAML 편집**: 노드·라인 기반 UI로 구성을 그리면 **ESPHome 호환 YAML**이 생성된다.
  2. **고급 로직**: YAML만으로 표현하기 어려운 로직은 **Lambda 코드 작성기**로 작성 후 ESPHome 빌드 파이프라인에 포함한다.
  3. **빌드·수신**: 생성된 YAML(+ Lambda 코드)을 **ESPHome 빌드 서비스**에 전달하고 **바이너리**를 받는다.
  4. **배포**: 받은 바이너리를 **웹 브라우저에서** 개발 디바이스에 **USB(직렬)** 또는 **OTA**로 업로드한다.
- **AI 협업**: [NEXA-AI-03] AI 협업형 멀티 에디터 플랫폼과 연동하여, 노드 추천·YAML/Lambda 스니펫 생성·오류 해석·자동완성 등을 지원한다.
- **대상·확장 방향**: 초보자부터 **전문적인 시스템 구축자(Professional Integrators)**까지 만족시키기 위해, **여러 대의 ESP32**와 **Jetson Orin Nano, Google Coral**과 같은 고성능 **에지 컴퓨팅(Edge AI)** 장치를 결합한 **하이브리드 시스템** 구축을 중요한 방향으로 둔다. 이를 위해 에지 장치와 ESP32 간 데이터 파이프라인을 설계할 수 있는 전용 노드 타입을 지원한다.

### 0.3 하이브리드 아키텍처 (초보자·전문가 동시 수용)

- **핵심 원칙**: 초보자를 위해 **직관적인 노드 배치**를 제공하면서, 전문가를 위해 **에지 AI와의 고속 통신 노드**, **전체 시스템 모니터링 뷰**, **C++ Lambda를 통한 저수준 제어**를 모두 열어 두는 **하이브리드 아키텍처**를 지향한다.

| 대상 | 제공 요소 | 본 문서 내 대응 |
|------|-----------|-----------------|
| **초보자** | **직관적인 노드 배치**: 드래그·드롭으로 센서·출력·논리 노드를 놓고 라인으로 연결하면 YAML이 자동 생성. 소켓 색상 코딩으로 잘못된 연결 방지. AI가 노드 배치·연결 시 YAML 스니펫 제안(§6.2). | §2 노드 카테고리·소켓 타입, §2.4 색상 코딩, §6.2 캔버스 동작 기반 AI, 점진적 확장(일부 노드만 먼저 구현). |
| **전문가** | **에지 AI 고속 통신 노드**: Coral/Jetson과의 브리지·스트리밍·추론·피드백 루프 노드(§2.2.1·§2.2.3). **전체 시스템 모니터링 뷰**: Nexus Map 확장 토폴로지, CPU/메모리·지연시간 실시간 엣지 애니메이션(§2.9). **C++ Lambda 저수준 제어**: Lambda 코드 작성기로 타이밍·레지스터·상태 머신·커스텀 프로토콜 등 세밀한 제어(§3). | §2.2.1 에지 노드, §2.2.3 Coral/Jetson 활용, §2.9 토폴로지 뷰, §2.10 배치 배포, §3 Lambda(C++ 스타일), §2.2.2 FSM·안전 이중화. |

- **정리**: 하나의 플랫폼에서 “쉽게 시작하는 노드 편집”과 “에지 AI·시스템 뷰·저수준 Lambda”가 공존하도록 설계하며, 사용자 숙련도에 따라 노출되는 노드·메뉴·뷰를 단계적으로 확장하는 구성을 권장한다.

- **경로**: `path: 'nexa-node'`, **컴포넌트**: `NodeDomain.vue` → `NodeContent.vue`.
- **엔진**: `NodeCanvas`(다이어그램), `useNexaNodeStore`(Pinia) — 노드·링크·블루프린트·디바이스 카탈로그.
- **역할**: 자동화 워크플로우 설계 및 시뮬레이션(Mock/Live), VirtualIotDevice·VirtualCanvas 등.
- **인터콤**: `useDomainIntercom('automation')`.

### 1.2 확장 방향

- **기존 캔버스/스토어**를 **ESPHome YAML 제너레이터**용으로 확장하거나, **nexa-node 내부에 전용 뷰/모드**를 둔다.
  - 예: 좌측 네비에서 "자동화 캔버스" | "ESPHome YAML" | "Lambda 로직" 등 탭 또는 서브메뉴로 구분.
- **노드 타입**을 ESPHome 컴포넌트에 맞게 정의(센서, 스위치, LED, WiFi, API, MQTT, 등)하고, **노드–노드 연결(라인)** 이 YAML의 **의존/바인딩** 관계로 매핑되도록 설계.
- **Lambda 코드 작성기**는 nexa-node 내 **패널 또는 모달**로 제공. (AI 도메인과 유사하게 Monaco 또는 코드 전용 에디터 임베드.)

## 2. YAML 제너레이터 (D3.js + 노드 + 라인)

### 2.1 개요

- **시각 편집**: 캔버스에 **노드**(ESPHome 컴포넌트에 대응)를 배치하고, **라인**으로 노드 간 연결(데이터/트리거 바인딩)을 표현.
- **출력**: 편집 결과를 **ESPHome 호환 YAML** 문자열로 직렬화. 기존 NodeCanvas의 노드/링크 스키마를 **YAML 스키마**로 변환하는 **제너레이터** 모듈이 필요.

#### 설계 체크: 통합 캔버스에서 Jetson(AI) ↔ ESP32(IO) 데이터 흐름(Edge)

- **질문**: 사용자가 **통합 캔버스**에서 Jetson(AI)과 ESP32(IO) 간의 **데이터 흐름(Edge)**을 그릴 수 있도록 설계되었는가?
- **결론**: **예.** 아래와 같이 설계되어 있다.

| 체크 항목 | 설계 반영 내용 |
|-----------|----------------|
| **통합 캔버스** | nexa-node의 **ESPHome YAML 전용 캔버스**(§7.1) 또는 **시스템 위상 뷰**(§2.9)에서 **Jetson·Coral·ESP32**를 모두 **동일 캔버스**의 노드로 배치. "로직 캔버스"와 Nexus Map이 동일 관계망 데이터를 공유하므로, 한쪽에서 그린 노드·엣지가 시스템 전체 설계로 일관되게 반영됨. |
| **Jetson(AI) 노드** | **에지 AI 추론(Inference)** 노드(§2.2.1·§2.2.4)가 Jetson/Coral에서 구동되는 AI 모델을 대변. 입력 소켓(센서 데이터·이미지 스트림)과 출력 소켓(추론 결과)을 가지므로, **라인(Edge)**으로 다른 노드와 연결 가능. |
| **ESP32(IO) 노드** | **입력·센서**(6), **출력·구동**(9), **고속 스트리밍**, **Coral 브리지** 등이 ESP32 측 IO를 대변. 동일 캔버스에 배치되며 입·출력 소켓으로 **라인(Edge)** 연결 가능. |
| **Edge(라인)로 데이터 흐름 표현** | §2.3: **라인** = 노드 A 출력 → 노드 B 입력. 바인딩/트리거로 YAML에 반영. §2.4 소켓 색상·타입 일치로 **호환되는 연결만** 허용. §2.8에서 엣지 위 **데이터 흐름 애니메이션**으로 시각화. |
| **방향성** | **ESP32 → Jetson**: 센서/스트리밍 노드 출력 → 에지 AI 추론 노드 입력(§2.2.1, §2.2.3 브리지). **Jetson → ESP32**: 추론 노드 출력 → 서보·릴레이 등 제어 노드 입력, **피드백 루프**로 명시(§2.2.3). |

- **구현 시 유의**: 캔버스 모드가 "단일 ESP32 로직" vs "시스템 전체(다중 디바이스·에지 포함)"를 선택할 수 있도록 하면, 통합 캔버스에서 Jetson과 ESP32를 함께 그리는 시나리오가 명확히 지원된다. §2.7 그룹 노드·§2.9 계층형 뷰와 함께 사용.

### 2.2 노드 카테고리 (ESPHome 대응)

| 번호 | 카테고리 | 기능 요약 |
|------|----------|-----------|
| 1 | **디바이스/코어** | Board Type, WiFi, OTA, Logging 등 ESP32 하드웨어 설정 |
| 2 | **논리·연산** | AND, OR, NOT, Compare(A>B), Range Check |
| 3 | **시간·스케줄** | RTC, SNTP, Cron, Uptime |
| 4 | **데이터 처리** | 문자열 결합, 수열(Array), 데이터 변환(Float→Int 등) |
| 5 | **특수효과·라이트** | Addressable LED(WS2812B) 패턴, PWM 페이딩, 스텝모터 가속/감속 곡선 |
| 6 | **입력·센서** | 물리 버튼, 온도/습도/조도 센서, 가상 데이터 발생기 |
| 7 | **물리 환경** | 센서 이전 단계, 물·불·자연·우주 등 환경 모사 |
| 8 | **사용자 제작** | 규격 제시 → 제작·테스트·배포 환경 |
| 9 | **출력·구동** | 릴레이, 서보, PWM, 스텝모터, 팬, 밸브/펌프 |
| 10 | **통신·연동** | MQTT, REST API, Home Assistant, WebSocket, Webhook |
| 11 | **상태·메모리** | 전역 변수, 카운터, 플래그, 상태머신, 이전값 보관 |
| 12 | **안전·제한** | 과전류/과열, 상하한(클램프), 데드밴드, 쿨다운, 비상정지 |
| 13 | **디버그·진단** | 로그(레벨/태그), 값 모니터/히스토리, 워치독, 전원/메모리/네트워크 |
| 14 | **표시·피드백** | OLED/LCD, 네오픽셀 상태, 부저/진동, 로컬 알림 |
| 15 | **저장·영속** | NVS/파일/SD 저장·복원, 스냅샷, 로그 파일 |
| 16 | **조건·라우팅** | 스위치(분기), 필터, 샘플/쓰로틀, 병합(다입력→1출력) |
| 17 | **에지 AI 게이트웨이(Edge AI Bridge)** | Inference Node, Data Streamer. 전문가용. §2.2.4 참조. |
| 18 | **고급 상태 머신(Advanced State Orchestration)** | FSM Node, Global Sync Node. 전문가용. §2.2.5 참조. |
| 19 | **저수준 하드웨어 커스텀(Low-level Hardware)** | Register Access Node, Custom Protocol Node. 전문가용. §2.2.6 참조. |

- 노드 **속성**(예: GPIO 핀 번호, 이름, 업데이트 주기)은 **노드 패널/폼**에서 편집하고, 이 값이 YAML 키·값으로 반영된다.
- **구현 순서**: 초기에는 위 카테고리 중 일부(예: 1·6·9·10 등 핵심만)만 노드 타입으로 구현하고, 시간이 될 때마다 카테고리·노드 타입을 추가하는 **점진적 확장**으로 진행한다.

#### 2.2.1 에지 AI·하이브리드 시스템 전용 노드 (ESP32 + Jetson / Coral 등)

- 기존 센서·출력 위주 노드에서 벗어나, **에지 장치(Jetson, Coral)**와 ESP32 간 **데이터 파이프라인**을 설계할 수 있는 노드를 추가한다. 고성능 에지 연산과 ESP32 네트워크를 결합한 하이브리드 시스템 구축에 사용한다.

| 노드 타입 | 역할 | 입력 | 출력 | 연동·비고 |
|-----------|------|------|------|------------|
| **에지 AI 추론(Inference)** | Jetson·Coral 등에서 구동되는 AI 모델(객체 인식, 음성 인식, 이상 징후 감지 등)을 대변. | ESP32에서 수신한 **센서 데이터(숫자)** 또는 **이미지 스트림**. | **추론 결과**(분류 값, 확률 등, 숫자/문자열). | 에지 서버 URL·모델 식별자 등 속성으로 설정. |
| **고속 데이터 스트리밍(Stream)** | ESP32-CAM·고주파 진동 센서 등 **고대역폭** 데이터를 에지 서버로 실시간 전송. | 센서 데이터 또는 이미지/오디오 스트림. | — (전송 완료·상태 이벤트 등 선택). | **통신·연동** 카테고리 확장. 프로토콜: RTSP, WebRTC, gRPC 등. MQTT/API보다 높은 대역폭 설정. |
| **전처리·특징 추출(Preprocessing)** | AI 모델에 보내기 전, **ESP32 Lambda**로 데이터 필터링·정규화·FFT(고속 푸리에 변환) 등 수행. | 원시 센서 데이터(숫자) 또는 스트림. | 전처리된 값·특징 벡터(숫자/수열). | Lambda 작성기와 연동. 에지 추론 노드 또는 스트리밍 노드의 상단에 연결. |

- 위 노드는 **통신·연동(10)** 또는 별도 카테고리 **에지 AI·고성능 연산**으로 분류하며, 점진적 확장 시 구현한다.

#### 2.2.2 고급 템플릿·AI 협업 (상태 머신, 안전·이중화)

- 전문 로직 구현을 위한 **고급 템플릿** 노드와 **AI 오케스트레이터** 연동을 포함한다.

| 노드 타입 | 역할 | AI 협업·연동 |
|-----------|------|--------------|
| **상태 머신(FSM)** | 복잡한 산업용 로직을 위해 단순 연결이 아닌 **상태(State)** 와 **전이(Transition)** 를 정의하는 노드. FSM 그래프(상태·전이 조건·진입/퇴출 액션)를 캔버스 또는 전용 UI로 편집 → Lambda/C++ 코드 생성. | 사용자가 **AI 오케스트레이터**에게 "안전 정지 루틴을 포함한 5단계 상태 머신 C++ 코드를 짜줘" 등으로 요청 → **Lambda 코드**를 자동 생성하여 해당 노드 또는 Lambda 작성기에 삽입. §6 채팅/요청 기반 시나리오와 연동. |
| **안전·이중화(Redundancy) / 하트비트** | **안전·제한(12)** 카테고리 강화. 특정 ESP32가 **다운**되었을 때 **에지 서버(Jetson)** 가 이를 감지하고 **대체 동작**을 지시하기 위한 **하트비트(Heartbeat)** 노드. ESP32 → 에지 주기적 alive 신호; 미수신 시 에지가 페일오버·대체 제어 지시. | 에지 서버 측 로직(감지·대체 지시)은 Nexus Map·시스템 토폴로지와 연동. 필요 시 오케스트레이터에 "하트비트 끊김 시 대체 시퀀스 제안해줘" 등 요청 가능. |

- **FSM 노드**: 입·출력 소켓은 **현재 상태**(숫자/문자열), **전이 트리거**(이벤트), **진입/퇴출** 신호 등으로 정의. YAML에서는 `lambda:` 블록 또는 custom component로 직렬화.
- **하트비트 노드**: 주기·타임아웃·재연결 정책을 속성으로 설정. 통신·연동(10) 또는 안전·제한(12) 확장으로 분류.

#### 2.2.3 하드웨어 가속기(Coral / Jetson) 활용 방안

- 에지 AI·하이브리드 시스템에서 **Coral USB 가속기**와 **Jetson Orin Nano**를 구체적으로 어떻게 쓰는지, 노드·데이터 흐름·시각화 관점으로 정리한다.

| 가속기 | 활용 방안 | 노드·캔버스 반영 |
|--------|------------|------------------|
| **Coral USB 가속기** | ESP32에서 수집된 **가벼운 데이터**(센서 값·이벤트·작은 이미지 등)를 **Coral이 탑재된 라즈베리 파이(RPi)** 로 전달하여 **고속 추론**을 수행하는 파이프라인. | **브리지 노드(Bridge Node)** 기획: ESP32 측 "전송" 소켓 → RPi+Coral 주소(URL/포트)·프로토콜 설정 → Coral 추론 노드. 캔버스에서 "ESP32 센서 → 브리지 → Coral 추론 → 결과" 흐름을 한 눈에 설계. 브리지 노드 속성: 대상 호스트(RPi IP)·포트·페이로드 형식(JSON 등). |
| **Jetson Orin Nano** | 단순 센서 처리 이상으로, **Jetson에서 처리된 복잡한 비전 인식 결과**(객체 위치·클래스·신뢰도 등)를 기반으로 **ESP32가 서보 모터 등을 정밀 제어**하는 **역방향 피드백 루프(Feedback Loop)**. | **피드백 루프 시각화**가 중요: Jetson 비전 노드(출력: 좌표·클래스 등) → ESP32 제어 노드(입력: 목표 각도/위치) → 서보·구동기. 캔버스·시스템 토폴로지 뷰(§2.9)에서 **에지 → ESP32** 방향의 라인을 명확히 표시하고, §2.8 엣지 데이터 흐름 애니메이션으로 "인식 결과 → 제어 명령" 실시간 표시. **역방향 피드백** 전용 레이어 또는 라인 스타일(점선·색상)로 구분 권장. |

- **정리**: (1) **Coral** = ESP32 → RPi+Coral **브리지 노드**로 가벼운 데이터 고속 추론 경로 설계. (2) **Jetson** = 비전 결과 → ESP32 정밀 제어 **피드백 루프** 설계·시각화를 우선하여, 전문 구축자가 루프 구조를 한눈에 파악하고 검증할 수 있도록 한다.

#### 2.2.4 에지 AI 게이트웨이 (Edge AI Bridge) — 전문가용 카테고리 확장

- 전문가를 위한 추가 노드 카테고리로 **에지 AI 게이트웨이(Edge AI Bridge)** 를 둔다. 에지 서버(Jetson/Coral)와 ESP32 간 **입력·스트리밍·추론** 경로를 하나의 게이트웨이 개념으로 묶어 설계할 때 사용한다. 메인 카테고리 **17번**에 대응(§2.2 표 참조).

| 노드 타입 | 역할 | 입·출력 요약 |
|-----------|------|--------------|
| **Inference Node** | Jetson/Coral에서 구동되는 **AI 모델**(객체 인식, 소리 분석 등)의 **입력·출력**을 정의. 모델 식별자·에지 서버 URL·입력 포맷(이미지/센서 벡터 등)·출력 스키마(분류·확률·바운딩 박스 등)를 노드 속성으로 설정. | 입력: ESP32에서 수신한 센서 데이터(숫자) 또는 이미지/오디오 스트림. 출력: 추론 결과(분류 값, 확률, 메타데이터 등). §2.2.1 에지 AI 추론과 동일 범주. |
| **Data Streamer** | **ESP32-CAM** 또는 **센서 데이터**를 **RTSP / WebRTC / gRPC** 프로토콜로 에지 서버에 **실시간 스트리밍**하는 노드. 대역폭·코덱·해상도·주기 등 속성으로 설정. | 입력: 센서 데이터 또는 이미지/오디오 스트림. 출력: 전송 상태·완료 이벤트 등(선택). §2.2.1 고속 데이터 스트리밍과 동일 범주. |

- 카테고리 **17 에지 AI 게이트웨이**는 위 두 노드(Inference Node, Data Streamer)를 포함하며, 노드 팔레트에서 "에지 AI 게이트웨이" 하위로 묶어 전문가용으로 노출하는 구성을 권장한다.

#### 2.2.5 고급 상태 머신 (Advanced State Orchestration) — 전문가용 카테고리 확장

- 전문가를 위한 **고급 상태 오케스트레이션** 카테고리. 복잡한 산업용 시퀀스와 **여러 대의 ESP32 간 분산 제어**를 상태·동기화 관점으로 설계할 때 사용한다. 메인 카테고리 **18번**에 대응(§2.2 표 참조).

| 노드 타입 | 역할 | 입·출력·연동 요약 |
|-----------|------|-------------------|
| **FSM (Finite State Machine) Node** | **복잡한 산업용 시퀀스**를 **상태(State)** 와 **전이(Transition)** 로 시각화하여 설계. 상태 그래프를 캔버스 또는 전용 UI로 편집 → Lambda/C++ 코드 생성. | 입력: 전이 조건(이벤트/숫자). 출력: 현재 상태(숫자·문자열), 전이 발생(이벤트). 상세·AI 협업은 §2.2.2 참조. |
| **Global Sync Node** | **여러 대의 ESP32** 간에 **상태를 동기화**하거나 **전역 변수를 공유**하는 **분산 제어 로직**을 생성. MQTT/API 또는 전용 동기화 프로토콜로 디바이스 간 일관된 상태·변수 공유. | 입력: 로컬 상태/변수, 동기화 트리거(이벤트). 출력: 동기화된 값(숫자·문자열·불리언), 동기화 완료(이벤트). 속성: 동기화 그룹 ID·주기·타임아웃. |

- 카테고리 **18 고급 상태 머신**은 FSM Node·Global Sync Node를 포함하며, 노드 팔레트에서 "고급 상태 머신" 하위로 묶어 전문가용으로 노출하는 구성을 권장한다.

#### 2.2.6 저수준 하드웨어 커스텀 (Low-level Hardware) — 전문가용 카테고리 확장

- **C++ Lambda를 통한 저수준 제어**(§0.3)를 구체화하는 노드. 레지스터 직접 접근·비표준 프로토콜 등 ESPHome YAML만으로 표현하기 어려운 **하드웨어 직접 제어**를 Lambda 코드 생성과 연결한다. 메인 카테고리 **19번**에 대응(§2.2 표 참조).

| 노드 타입 | 역할 | 입·출력·연동 요약 |
|-----------|------|-------------------|
| **Register Access Node** | **특정 레지스터**에 직접 값을 **쓰거나 읽는** Lambda 코드를 생성. 주소·마스크·비트 필드 등 속성으로 설정 → 해당 레지스터 접근용 C++ 스니펫 또는 Lambda 블록 출력. | 입력: 쓸 값(숫자), 읽기 트리거(이벤트). 출력: 읽은 값(숫자), 쓰기 완료(이벤트). Lambda 작성기·AI 오케스트레이터와 연동해 레지스터 접근 코드 생성. |
| **Custom Protocol Node** | **비표준 통신 프로토콜** 구현을 위한 **비트뱅잉(Bit-banging)** 및 **정밀 타이밍 제어** 노드. GPIO 토글·지연·패턴을 Lambda로 생성. UART/I2C/SPI 외 커스텀 프로토콜(예: 1-Wire 변형, LED 프로토콜) 설계 시 사용. | 입력: 전송할 데이터(숫자·문자열), 시작 트리거(이벤트). 출력: 수신 데이터(숫자·문자열), 완료/에러(이벤트). 속성: 핀·타이밍 파라미터·패턴. |

- 카테고리 **19 저수준 하드웨어 커스텀**은 Register Access Node·Custom Protocol Node를 포함하며, 노드 팔레트에서 "저수준 하드웨어" 하위로 묶어 전문가용으로 노출하는 구성을 권장한다.

### 2.3 라인(연결)의 의미

- **라인**: 노드 A의 출력 → 노드 B의 입력. YAML에서는 다음 중 하나로 표현될 수 있음.
  - **바인딩**: 한 컴포넌트의 상태가 다른 컴포넌트의 `id`로 참조됨.
  - **트리거/콜백**: 이벤트가 발생한 컴포넌트가 다른 컴포넌트를 제어.
- **제너레이터**: 노드·라인 그래프를 **순회**하여, ESPHome YAML 문서 구조(순서·들여쓰기·키 이름)를 생성하는 규칙을 정의.

### 2.4 소켓 색상 코딩 (Color-coded Sockets)

- 노드 입·출력 **소켓을 타입별로 색상 구분**하면, 서로 호환되지 않는 노드끼리 연결하는 실수를 **시각적으로 방지**할 수 있다(엄격 안전).

| 타입 | 색상 | 용도 예 |
|------|------|---------|
| **불리언** (On/Off) | 빨간색 | 스위치 상태, 릴레이 on/off |
| **숫자** (Float/Int) | 회색/초록색 | 센서 값, PWM, 비교 연산 |
| **문자열** (String) | 보라색 | 로그 메시지, MQTT payload |
| **이벤트** (Trigger) | 노란색 | 버튼 클릭, 조건 충족 시 콜백 |

- 연결 시 **소켓 타입이 일치하는 경우에만** 라인 허용(또는 경고)하도록 검증 규칙 적용 권장.

#### 엄격한 타입 검증 (Strict Validation) — 설계 단계에서 차단

- **질문**: 소켓 색상 코딩 시스템을 통해 **에지 서버와 단말 노드 간**의 **데이터 타입 불일치**를 **설계 단계에서 차단**하는 기획이 잘 되어 있는가?
- **결론**: **예.** 아래와 같이 설계되어 있으며, 구현 시 **연결 시점 검증**으로 설계 단계에서 불일치를 차단한다.

| 구분 | 내용 |
|------|------|
| **소켓 색상 코딩** | §2.4: 네 가지 타입(불리언·숫자·문자열·이벤트)별 **색상** 부여. 사용자가 라인을 그을 때 **출력 소켓 색상**과 **입력 소켓 색상**이 다르면 시각적으로 "연결 부적합"을 인지. |
| **노드별 소켓 정의** | §2.5: **에지 서버 측 노드**(에지 AI 추론, Data Streamer, Coral 브리지 등)와 **단말(ESP32) 노드**(센서, 출력·구동, 전처리 등) 모두 **입·출력 소켓의 데이터 타입**을 표로 정의. 이 정의가 검증의 **스키마**가 됨. |
| **에지 서버 ↔ 단말 간 검증** | **에지 AI 추론** 출력 = 분류/확률(숫자·문자열). **ESP32 제어 노드**(서보·릴레이 등) 입력 = 숫자 또는 불리언. 타입이 맞을 때만 라인 허용. 반대로 **ESP32 센서** 출력(숫자) → **에지 AI 추론** 입력(숫자·스트림)도 타입 일치 시에만 연결. **타입 불일치** 시 라인 연결을 **거부**하거나 **경고**하여 설계 단계에서 차단. |
| **설계 단계 차단** | 검증은 **캔버스에서 라인을 연결하는 시점**(드래그 완료·드롭)에 수행. 타입 불일치 시 연결 생성 자체를 막거나(엄격 모드) 경고 후 사용자 확인으로 제한. **빌드·배포 전**에 잘못된 연결이 스토어·YAML에 남지 않도록 함. |
| **구현 요약** | 각 노드 타입별 소켓 정의(§2.5)를 **검증 규칙 테이블**로 유지. 라인 연결 시 "출력 소켓 타입 ↔ 입력 소켓 타입" 비교. 일치하면 허용, 불일치면 거부/경고. 소켓 색상은 **시각적 피드백**으로 동일 타입만 연결하도록 유도. |

- **정리**: 소켓 색상 코딩 + 노드별 소켓 타입 정의 + **연결 시점 타입 검증**으로, **에지 서버(Jetson/Coral) 노드와 단말(ESP32) 노드 간** 데이터 타입 불일치를 **설계 단계에서 차단**하는 기획이 되어 있다. 구현 시 "엄격 모드(거부)" vs "경고 모드(경고 후 허용)" 정책을 선택할 수 있도록 한다.

### 2.5 노드별 입·출력 소켓 정의 (Socket Type per Node)

- 각 **노드 타입**마다 **입력 소켓**과 **출력 소켓**의 개수·이름·**데이터 타입(Socket Type)**을 정의한다. §2.4의 네 가지 타입(불리언, 숫자, 문자열, 이벤트)을 사용하며, 이 정의에 따라 연결 검증·엣지 애니메이션·AI YAML 생성이 동작한다.
- **초기 구현**에서는 핵심 노드(예: 아래 표)만 정의하고, 카테고리 확장 시 점진적으로 추가한다.

| 노드 (예시) | 입력 소켓 | 출력 소켓 | 비고 |
|-------------|------------|------------|------|
| **DHT 온도·습도 센서** | — | 온도(숫자), 습도(숫자) | sensor, platform: dht |
| **GPIO 버튼** | — | 눌림(이벤트), 상태(불리언) | binary_sensor, on_press 등 |
| **on_value_range (범위 조건)** | 값(숫자) | 조건 충족(이벤트) | 논리 노드, YAML 조건문 결합 |
| **릴레이 / 스위치** | 제어(불리언), 트리거(이벤트) | 상태(불리언) | output / switch |
| **PWM 출력** | 값(숫자) | — | light, fan 등 |
| **MQTT 발행** | 값(숫자/불리언/문자열) | — | mqtt publish |
| **MQTT 구독** | — | payload(문자열), topic(문자열) | mqtt subscribe |
| **에지 AI 추론** | 센서 데이터(숫자), 이미지 스트림(전용 소켓) | 분류/확률(숫자·문자열) | Jetson/Coral 모델 대변 |
| **고속 스트리밍(Stream)** | 센서/이미지 스트림 | 전송 상태(이벤트) 등 | RTSP, WebRTC, gRPC |
| **전처리·특징 추출** | 원시 데이터(숫자/스트림) | 전처리 값·특징(숫자/수열) | Lambda(필터, 정규화, FFT) |
| **상태 머신(FSM)** | 전이 조건(이벤트/숫자) | 현재 상태(숫자·문자열), 전이 발생(이벤트) | 고급 템플릿, Lambda/C++ 생성 |
| **안전·이중화(하트비트)** | — (주기 발신) | alive(이벤트), 타임아웃(이벤트) | 에지 서버 감지·대체 동작 |
| **Coral 브리지(Bridge)** | ESP32 센서/이벤트(숫자·이벤트) | — (RPi+Coral로 전달) | 가벼운 데이터 → Coral 고속 추론, §2.2.3 |
| **Global Sync** | 로컬 상태/변수, 동기화 트리거(이벤트) | 동기화된 값(숫자·문자열·불리언), 동기화 완료(이벤트) | 다중 ESP32 분산 제어, §2.2.5 |
| **Register Access** | 쓸 값(숫자), 읽기 트리거(이벤트) | 읽은 값(숫자), 쓰기 완료(이벤트) | 레지스터 직접 접근 Lambda, §2.2.6 |
| **Custom Protocol** | 전송 데이터(숫자·문자열), 시작(이벤트) | 수신 데이터(숫자·문자열), 완료/에러(이벤트) | 비트뱅잉·정밀 타이밍, §2.2.6 |

- 그룹 노드: 그룹 **입·출력**은 내부에 노출된 소켓을 그대로 대리하며, 타입은 내부 연결과 동일하게 정의한다.

### 2.6 기술 선택

- **D3.js**: 노드·링크 시각화, 드래그, 줌, 패닝. 기존 `NodeCanvas`가 D3 기반이면 재사용 또는 확장.
- **대안**: Vue Flow, Rete.js 등 **노드 기반 에디터** 라이브러리로 대체 가능. 요구사항은 **노드 타입 정의 + 라인 + 속성 폼 → YAML 직렬화**.
- **YAML 생성**: 노드/링크를 **중간 JSON**으로 옮긴 뒤, **ESPHome YAML 스키마**에 맞는 문자열을 생성하는 **코드 제너레이터** 함수. (템플릿 또는 AST 스타일.)

### 2.7 그룹 노드 및 다중 디바이스 뷰

- **기본 단위**: 로직 구성·시뮬레이션은 **1대의 ESP32**를 기준으로 한다. 한 디바이스당 하나의 YAML(캔버스) 단위로 설계.
- **다수 디바이스 관리**: 수십 대의 ESP32로 하나의 시스템을 이룰 때, **전체 관계·구성·로직**을 한눈에 검토하기 위해 다음을 지원한다.
  - **그룹 노드(Group Node)**: 특정 기능(예: 화재 감지 로직, 구역별 조명 제어)을 **하나의 그룹 노드**로 묶을 수 있다. 그룹 노드는 **접기/펼치기**로 **내부 노드·라인을 숨기거나 나타낼** 수 있어, 시스템 수준 뷰에서 복잡도를 줄인다.
  - 그룹 노드 펼침 시: 해당 기능을 구성하는 하위 노드·연결이 캔버스에 표시되어 편집 가능.
  - 그룹 노드 접힘 시: 하나의 블록(아이콘·라벨)으로만 표시되어, 다른 ESP32 또는 그룹과의 **관계·데이터 흐름**만 집중해서 검토 가능.
- **전체 검증**: 다중 ESP32·그룹 노드가 있는 시스템에서, 디바이스 간 입력/출력 호환, 이벤트·데이터 경로 일관성 등 **관계·구성·로직 검증** 기능을 제공하는 것을 목표로 한다.

### 2.8 엣지(라인) 데이터 흐름 시각화

- 관계가 복잡해질수록 **데이터 흐름**을 눈으로 확인하는 것이 중요하다. 노드 사이를 잇는 **엣지(Edge/라인) 위**로, 현재 흐르는 **데이터 값 또는 신호**를 **애니메이션**으로 표시한다.
  - **표시 내용**: 소켓 타입에 따라 예시 — 불리언(On/Off)은 펄스·점멸, 숫자는 값이 라인 근처에 흐르는 텍스트/배지, 이벤트는 트리거 순간 강조 등. (편집 모드에서는 최신 값·상태, 시뮬레이션/라이브 모드에서는 실시간 값 반영.)
  - **효과**: 어느 경로로 값이 전달되는지, 트리거가 어디서 발생했는지 한눈에 파악 가능. 디버깅·전체 관계 검토 시 유리.
- 구현 시: 엣지 위를 따라 이동하는 마커(원·선)·값 라벨 애니메이션, 또는 라인 색상/두께로 활성도 표현 등 중 선택·조합.

#### 시각적 디버깅 (Visual Debugging) — 실시간 스트림·AI 추론 결과·병목 파악

- **질문**: 엣지(라인) 위로 흐르는 **실시간 데이터 스트림**과 **AI 추론 결과(Confidence Score 등)**를 애니메이션으로 표시하여 **병목 지점**을 파악할 수 있는 로직이 있는가?
- **결론**: **예.** §2.8 및 §2.9와 아래 로직으로 설계한다.

| 구분 | 내용 |
|------|------|
| **실시간 데이터 스트림** | 시뮬레이션/라이브 모드에서 엣지 위로 **실시간 데이터**가 흐르는 것처럼 애니메이션 표시(값 라벨·마커 이동·라인 색상/두께). 데이터 소스는 ESP32/에지 서버의 **스트리밍·상태 API** 또는 모니터링 경로. §2.8 표시 내용과 동일. |
| **AI 추론 결과 표시** | **에지 AI 추론 노드**(§2.2.1) 출력에 연결된 엣지에는 **추론 결과**를 애니메이션으로 표시. 예: **Confidence Score**(신뢰도), **분류 클래스**, **바운딩 박스 요약** 등. 해당 노드 출력 소켓 타입(숫자·문자열)에 맞춰 라인 근처 또는 툴팁에 표시. |
| **병목 지점 파악** | **병목 파악**을 위해 (1) 엣지별 **지연시간(Latency)**·**전송률(Data Rate)**을 실시간으로 표시(§2.9 전문가 기능 확장). (2) 값이 **쌓이거나 지연**되는 구간을 라인 색상(예: 적색=지연 큐 적체) 또는 배지로 강조. (3) 노드·엣지별 **처리량/대기량** 메트릭을 수집해 "느린 구간"을 시각적으로 구분. |
| **로직 요약** | 실시간 스트림·AI 추론 결과·지연/전송률 메트릭을 **동일한 엣지 애니메이션 레이어**에서 결합. 디버그/모니터 전용 뷰(§2.9 시스템 위상 또는 캔버스 "라이브" 모드)에서 활성화. 데이터는 에이전트·API로 수집 후 프론트엔드에서 엣지에 바인딩. |

- **정리**: 엣지 위 **실시간 데이터 스트림** + **AI 추론 결과(Confidence Score 등)** 애니메이션과, **Latency/Data Rate/큐 적체** 시각화를 통해 **시각적 디버깅** 및 **병목 지점 파악**이 가능하도록 하는 로직을 목표로 한다.

### 2.9 시스템 토폴로지 뷰 (Nexus Map 확장) — 전문 구축자

- 전문 구축자(Professional Integrators)를 위해 **개별 기기가 아닌 전체 시스템의 위상(Topology)** 및 **계층 구조** 설계를 염두에 둔다. [NEXA-AI-03] §8.6 **Nexus Map**과 연동하여, **시스템 토폴로지 뷰**를 제공한다.

#### 계층형 뷰 (Hierarchical Topology)

- 시스템 토폴로지를 **3계층**으로 구분하여 설계·시각화한다. Nexus Map·시스템 위상 뷰에서 **계층별 레이어**로 노드를 배치하거나, 트리/그래프에서 상·하위 관계로 표현할 수 있다.

| 계층 | 역할 | 장치 예 | 설명 |
|------|------|---------|------|
| **최상위** | **에지 서버** — 시스템 전체의 **두뇌** 및 **AI 추론** 담당. | Jetson Orin Nano | 비전·음성·이상 감지 등 복잡한 추론, 다수 디바이스에 대한 제어 결정·피드백 루프 지시. |
| **중간** | **게이트웨이** — **데이터 수집** 및 **전처리**. | Raspberry Pi + Coral | ESP32·센서에서 올라온 데이터 수집·집약, Coral로 고속 추론 또는 전처리 후 상위 Jetson으로 전달. |
| **말단** | **에지 노드** — **실제 센서 데이터 수집** 및 **액추에이터 제어**. | ESP32 | 온도·조도·이미지·스위치 등 수집, 릴레이·서보·LED 등 구동. |

- 캔버스·Nexus Map에서 **계층별로 노드 그룹화**하거나, **위에서 아래로** 데이터 흐름이 내려가는 뷰(트리 또는 다단 레이아웃)를 지원하면, 전문 구축자가 전체 아키텍처를 한눈에 파악할 수 있다.

#### Nexus Map 연동 및 연결 상태 시각화

| 구분 | 내용 |
|------|------|
| **실물 노드 등록** | **모든 디바이스**(ESP32·RPi+Coral·Jetson)를 Nexus Map의 **실물 노드**로 등록. §8.6 노드 종류(실물/논리)·레이어와 호환. nexa-node의 그룹 노드·디바이스 목록·연결 관계와 동일 데이터 소스를 공유. |
| **물리적/논리적 연결 상태** | 디바이스 간 **물리적·논리적 연결 상태**를 **실시간 애니메이션**으로 시각화. 엣지(연결선) 또는 노드 배지에 **RSSI**(신호 강도), **Latency**(지연시간), **Data Rate**(데이터 전송률) 등을 표시. §2.8 엣지 데이터 흐름 시각화를 확장. |
| **기능** | Nexus Map과 연동. **중앙의 Jetson Orin Nano**(또는 Coral 등 에지 서버)를 중심으로 **수십 대의 ESP32**가 어떻게 배치되고 **데이터가 흐르는지** 시각화. 노드 = 장치(ESP32·Jetson·Coral), 엣지 = 데이터/제어 경로. |
| **데이터 소스** | nexa-node의 **그룹 노드·디바이스 목록·연결 관계**와 Nexus Map의 **실물 노드**(§8.6)를 매핑. 동일한 관계망 데이터를 "로직 캔버스(nexa-node)"와 "시스템 위상 뷰(Nexus)" 양쪽에서 공유·표시. |
| **전문가 기능** | 각 장치의 **CPU/메모리 점유율**, **네트워크 지연시간(Latency)** 를 **실시간**으로 수집하여, 엣지(연결선) 위 **애니메이션**으로 모니터링. **RSSI·Data Rate**도 엣지 또는 툴팁에 표시. §2.8 확장. 장치별 상태는 노드 배지 또는 툴팁으로 표시. |
| **구현 방향** | ai 도메인 Nexus 탭(nexus) 또는 nexa-node 전용 "시스템 위상" 모드에서 동일 그래프 렌더. 장치 메트릭·연결 품질(RSSI, Latency, Data Rate)은 ESP32/에지 서버의 **API·에이전트** 또는 기존 모니터링 경로에서 수집. [NEXA-AI-03] §8.6 노드 종류(실물/논리)·레이어·연결 규칙과 호환되도록 노드 타입·엣지 스키마 확장. |

### 2.10 배치 배포(Batch Deployment) 및 버전 관리 — 전문 구축자

- 수십 대의 ESP32에 **동일하거나 유사한 로직**을 **한 번에 배포**하는 기능을 목표로 한다. §2.7 그룹 노드 기능을 확장하여, **디바이스 그룹** 단위로 바이너리를 **OTA 동시 업데이트**하는 워크플로우를 설계한다.

| 구분 | 내용 |
|------|------|
| **그룹 노드 확장** | "A구역 조명 제어 그룹", "1층 온도 센서 그룹" 등 **기능/구역별 그룹**에 속한 **모든 디바이스**를 하나의 배포 대상으로 정의. 그룹 노드 또는 별도 **디바이스 그룹** 엔티티에 디바이스 ID 목록·OTA 설정(순차/병렬, 타임아웃)을 보관. |
| **배치 배포 워크플로우** | (1) 캔버스에서 해당 그룹용 YAML(+ Lambda)로 **빌드** → 바이너리 1개 생성. (2) "배치 OTA" 선택 시 **그룹에 속한 모든 ESP32**에 동일 바이너리를 **OTA로 동시(또는 순차)** 전송. (3) 진행률·성공/실패를 디바이스 단위로 표시. |
| **버전 관리** | 그룹별 또는 디바이스별 **펌웨어 버전**(빌드 ID·타임스탬프·태그)을 기록. 롤백 시 "이전 버전으로 재배포" 옵션 제공. Nexus Map·시스템 토폴로지 뷰에서 "현재 디바이스별 펌웨어 버전" 표시 시 전문 구축자가 불일치를 한눈에 파악 가능. |
| **시스템 전체 구성 스냅샷·일괄 복구** | **시스템 전체 구성**(노드 그래프·라인·노드별 속성·YAML·Lambda·디바이스 그룹 매핑)을 **스냅샷**으로 저장. **업데이트 실패 시** 또는 사용자 요청 시, **전체 노드(디바이스)**를 **이전 정상 상태**로 **일괄 복구(롤백)**하는 기능을 목표로 한다. §2.10.1 참조. |
| **설계 방향** | 빌드 산출물과 디바이스 그룹을 연결하는 **배포 정책** 테이블(어떤 그룹에 어떤 바이너리를 언제 배포했는지) 유지. OTA 동시 전송 시 네트워크 부하·실패 시 재시도 정책(재시도 횟수, 건너뛰기 여부)을 기획 단계에서 정의. |

#### 2.10.1 시스템 전체 구성 스냅샷 및 업데이트 실패 시 일괄 복구(롤백)

- **배경**: 배치 OTA 등으로 업데이트한 뒤 **일부 디바이스 실패** 또는 **전체 롤백이 필요한 상황**에서, **이전에 정상 동작하던 시스템 전체 구성**으로 되돌릴 수 있어야 한다.
- **스냅샷 저장**: **시스템 전체 구성**을 스냅샷으로 저장. 저장 대상: (1) **캔버스 상태**(노드 목록·라인 목록·노드별 속성), (2) **YAML·Lambda** 문자열, (3) **디바이스 그룹 ↔ 펌웨어 버전** 매핑, (4) (선택) Nexus Map/토폴로지 뷰 상태. 스냅샷은 **배포 전** 또는 **주기·마일스톤**으로 생성하고, 스냅샷 ID·타임스탬프·라벨(예: "배포 전 2025-03-05")을 부여.
- **업데이트 실패 시 일괄 복구**: 배치 배포 후 **실패 감지**(디바이스 단위 실패·타임아웃) 또는 사용자가 "롤백" 선택 시, **선택한 스냅샷**에 대응하는 **이전 정상 펌웨어 버전**을 해당 그룹·디바이스에 **일괄 재배포**. 즉, **전체 노드(디바이스)**를 이전 정상 상태로 되돌리는 **일괄 복구** 워크플로우를 지원하는 것을 목표로 한다.
- **구현 방향**: 스냅샷 메타(스냅샷 ID, 생성 시점, 연결된 빌드 ID 목록)와 **배포 정책** 테이블을 연계. "이 스냅샷으로 롤백" 선택 시 → 해당 스냅샷에 묶인 빌드(또는 이전 성공 배포 빌드)를 그룹 전체에 OTA 재전송. 캔버스·YAML은 스냅샷에서 복원하여 편집 화면도 이전 구성과 일치시킬 수 있도록 한다.

## 3. Lambda 코드 작성기 (C++·저수준 제어)

### 3.1 역할

- YAML만으로는 **복잡한 조건·연산·상태 머신** 등을 표현하기 어렵다. **Lambda 코드 작성기**는 그러한 **고급 로직**을 **코드**로 작성하는 UI이며, **전문가**를 위해 **C++ Lambda를 통한 저수준 제어**(타이밍·레지스터·커스텀 프로토콜·상태 머신 등)를 열어 둔다(§0.3 하이브리드 아키텍처).
- ESPHome에서 `lambda:` 블록은 보통 **C++ 스타일의 람다**로, `id(센서).state` 등으로 다른 컴포넌트를 참조한다. 본 기획의 "Lambda"는 그와 동일한 역할을 하는 **텍스트 코드**를 편집하는 것이다.

### 3.2 기능 요구사항

- **에디터**: Monaco Editor 또는 동일한 수준의 **코드 에디터** (문법 강조, 자동완성, 오류 표시).
- **언어/문법**: ESPHome Lambda 문법(C++ 유사) 또는 플랫폼이 정의한 **제한된 DSL**.
- **연동**: 작성된 코드는 **YAML 제너레이터 출력**에 `lambda:` 블록으로 삽입되거나, **별도 파일**로 ESPHome 빌드 입력에 함께 전달.
- **AI 연동**: "이 조건으로 Lambda 작성해줘", "오류 수정해줘" 등 채팅/오케스트레이터와 연동.

### 3.3 데이터 흐름

- 사용자가 **노드·라인**으로 구성을 그리면 → **YAML**(기본 구조) 생성.
- 사용자가 **Lambda 작성기**에서 고급 로직을 작성하면 → 해당 코드가 **특정 노드/컴포넌트의 `lambda:`** 에 붙거나 **글로벌 스크립트**로 포함.
- **최종 출력**: YAML 문자열(+ Lambda 블록 내장) 또는 YAML + 별도 Lambda 파일 묶음 → **빌드 서비스**로 전달.

## 4. 빌드·바이너리 수신

### 4.1 빌드 서비스 (시나리오 2-1 파이프라인)

- **역할**: 시나리오 2-1(로직 구성 → 빌드 → OTA)에서 **포털 로직 구성 결과**를 **바이너리**로 변환. [NEXA-NODE-03] §2.6 참조.
- **입력**: 생성된 **YAML**(+ Lambda 포함 또는 별도 파일).
- **처리**: ESPHome 빌드 엔진(**Docker ESPHome 서버** 또는 Python 기반 **ESPHome CLI**)이 **컴파일**하여 **바이너리(.bin)** 생성. (ESPHome CLI·로컬 대시보드는 개발·YAML 검증·디버깅용으로 별도 활용 가능.)
- **배치**: 빌드 서비스는 **백엔드 서버** 또는 **별도 Docker/서비스**로 운영. NEXA 플랫폼(웹)은 **HTTP/WebSocket**으로 YAML을 전송하고, **빌드 완료 시 바이너리 URL 또는 스트림**을 수신.

### 4.2 웹 클라이언트 역할

- YAML(+ Lambda) **제출** → 빌드 **요청**.
- **폴링 또는 WebSocket**으로 빌드 **진행률/완료** 수신.
- 완료 시 **바이너리 파일** 다운로드 또는 **메모리 버퍼**로 보유 → 다음 단계(USB/OTA)에서 사용.

### 4.3 보안·리소스

- 빌드 서비스는 **인증·권한** 필요. NEXA 사용자 세션과 연동 검토.
- 빌드 부하는 **서버/컨테이너**에서 처리하므로, 브라우저는 **경량**하게 유지.

## 5. 웹 브라우저에서 펌웨어 업로드 (USB / OTA)

- **펌웨어 주입 시나리오 요약**: [NEXA-NODE-03] §2.6 참조. **시나리오 1**(OTA 없음·손상 → USB+Web Serial 최초 주입) | **시나리오 2-1**(로직 구성 → Docker ESPHome 빌드 → OTA) | **시나리오 2-2**(특정 펌웨어 선택 → OTA).

### 5.1 USB 직접 업로드 (시나리오 1: 복구·최초 주입)

- **용도**: OTA 펌웨어가 **없거나 망가졌을 때** (공장 출하·초기화·손상). 디바이스에 OTA 수신 능력이 없으므로 **USB + Web Serial**로 바이너리를 **최초 주입**한다.
- **웹 브라우저에서 디바이스와 유선 연결**: **Web Serial API**를 직접 사용해도 되지만, 이미 잘 구성된 **ESP Web Tools** 라이브러리(Espressif)를 사용하면 **개발 시간을 단축**할 수 있다. ESP Web Tools는 Web Serial + ESP 플래시 프로토콜을 브라우저에서 제공하므로, 별도 프로토콜 구현 없이 통합 가능.
- **플로우**: 사용자가 "디바이스에 업로드" 선택 → **시리얼 포트 선택** (브라우저 팝업) → 빌드된 **바이너리**를 플래시.
- **esptool**: Python 기반 CLI 도구(esptool)는 **추후 고도화 시 검토** 대상. (예: 로컬 CLI·스크립트 자동화 등)

### 5.2 OTA 업데이트 (시나리오 2: 평시)

- **용도**: 디바이스에 OTA 가능 펌웨어가 이미 올라가 있고 네트워크 연결된 **평시** 상황. **2-1**: 로직 구성 → Docker ESPHome 빌드 → 바이너리 반환 → OTA. **2-2**: 포털에서 특정 펌웨어 선택 → OTA 바로 주입. [NEXA-NODE-03] §2.6·§3.5 참조.
- 디바이스가 **이미 네트워크에 연결**되어 있고 **OTA 지원**이 되어 있으면, **브라우저 또는 백엔드**에서 해당 디바이스 **IP·포트**로 **OTA 프로토콜**에 따라 바이너리를 전송.
- **플로우**: 사용자가 "OTA 업데이트" 선택 → **대상 디바이스 선택**(목록은 네트워크 스캔 또는 수동 등록) → 바이너리 전송.
- **프로토콜**: ESPHome OTA 포맷 또는 표준 ESP OTA. 브라우저에서 **HTTP POST**로 OTA 서버(디바이스)에 보낼 수 있으면 브라우저만으로 가능.

### 5.3 정리

| 시나리오 | 방식                  | 용도                                           | 장점                                                  | 단점                                                |
|----------|-----------------------|------------------------------------------------|------------------------------------------------------|-----------------------------------------------------|
| **1**    | **USB (Web Serial)**  | OTA 없음·손상 시 **최초·복구** 주입            | ESP Web Tools 라이브러리 활용 시 개발 시간 단축. 케이블만 있으면 됨. | Chrome/Edge 등 제한. HTTPS 필요. |
| **2-1**  | **OTA**               | 로직 구성 → Docker 빌드 → 바이너리 → OTA       | 사용자 맞춤 로직, 평시 업데이트에 편리               | 디바이스가 네트워크·OTA 활성화 상태여야 함          |
| **2-2**  | **OTA**               | 포털 제공 특정 펌웨어 선택 → OTA               | 로직 구성 없이 빠른 적용, 스냅샷·기능 템플릿 즉시 선택 | 디바이스가 네트워크·OTA 활성화 상태여야 함          |
| (보조)   | **바이너리 다운로드** | USB·OTA 모두 어려울 때                         | 구현 단순                                             | 사용자가 **ESPHome CLI·로컬 대시보드** 또는 esptool로 수동 플래시. 플랫폼 외부 도구 활용. |

- **1단계**: **바이너리 다운로드** + **OTA**(가능 시)까지 지원. **USB Web Serial**(시나리오 1)은 2단계 또는 PoC로 검토.

## 6. AI 협업 연동

### 6.1 연동 포인트 ([NEXA-AI-03] 기준)

- **오케스트레이터(useAiOrchestrator)**: nexa-node에서 "이 구성을 YAML로 바꿔줘", "이 노드에 맞는 Lambda 예시 만들어줘" 등 **요청**을 채팅 또는 패널에서 보내면, 오케스트레이터가 **컨텍스트**(현재 노드 그래프, 선택된 노드, 기존 YAML 스니펫)를 담아 **모델 호출** → **YAML/Lambda 스니펫** 또는 **수정 제안** 반영.
- **패널·Focus Stack**: nexa-node에서 **YAML 제너레이터 캔버스**, **Lambda 작성기 패널**을 열어 두면, AI가 "현재 열린 패널" 컨텍스트로 **지칭**("방금 수정한 Lambda", "두 번째 노드")을 해석할 수 있도록 연동.
- **Nexus Map**: ESPHome 디바이스·노드를 **실물 노드**로 Nexus Map에 등록하고, **데이터 흐름·연결**을 맵에서 시각화하는 확장 가능.

### 6.2 구체 시나리오

#### 캔버스 동작 기반 (노드 배치·연결 시 자동 생성)

| 사용자 동작 | AI 협력 결과 |
|-------------|--------------|
| 캔버스에 **센서 노드**를 놓음 | 해당 센서에 필요한 YAML 생성. 예: `sensor:` → `platform: dht` 등 플랫폼·핀 설정 스니펫. |
| **논리 노드**를 (기존 노드에) 연결함 | 조건문 YAML 생성 후 기존 블록과 결합. 예: `on_value_range:` 등으로 범위 조건 코드 생성·삽입. |

- 즉, **노드를 배치하거나 라인으로 연결하는 행위**만으로도 AI가 적절한 YAML 조각을 제안·생성하고, 제너레이터가 이를 그래프와 함께 반영할 수 있도록 한다.

#### 채팅/요청 기반

| 시나리오        | 설명                                                                                                  |
| --------------- | ----------------------------------------------------------------------------------------------------- |
| **노드 추천**   | "온도 센서 추가하고 30도 넘으면 릴레이 켜줘" → AI가 노드 타입·연결·초기 YAML 스니펫 제안.             |
| **Lambda 생성** | "위 스위치가 눌리면 LED 3초간 점등" → Lambda 코드 스니펫 생성 후 Lambda 작성기 또는 해당 노드에 삽입. |
| **FSM Lambda 생성** | "안전 정지 루틴을 포함한 5단계 상태 머신 C++ 코드를 짜줘" → **상태 머신(FSM) 노드**용 Lambda/C++ 코드 자동 생성·삽입. §2.2.2 고급 템플릿 연동. |
| **AI 최적화 제안 + Lambda 생성** | 오케스트레이터가 **최적화 제안**(예: "ESP32에서 FFT 연산을 수행하여 Jetson의 연산 부하를 줄이라")을 하고, 이에 맞는 **Lambda 코드를 자동 생성**하여 **전처리·특징 추출** 노드(§2.2.1) 또는 해당 노드의 Lambda 작성기에 삽입. §6.2.1 AI 최적화 참조. |
| **오류 해석**   | 빌드 실패 시 **에러 로그**를 채팅에 붙여넣으면, AI가 **원인·수정 제안** 제시.                         |
| **문서 검색**   | "ESPHome에서 MQTT 사용법" → 내부/외부 문서 기반 답변 + YAML 예시.                                     |

#### 6.2.1 AI 최적화 (AI-Assisted Optimization)

- **질문**: AI 오케스트레이터가 "ESP32에서 FFT 연산을 수행하여 Jetson의 연산 부하를 줄이라"는 등의 **최적화 제안**을 하고 **Lambda 코드를 자동 생성**할 수 있는가?
- **결론**: **예.** 아래와 같이 설계한다.

| 구분 | 내용 |
|------|------|
| **최적화 제안** | 오케스트레이터가 현재 **노드 그래프·데이터 흐름**(ESP32 → Jetson 스트리밍/추론)을 컨텍스트로 받아, **연산 분배·대역폭·지연** 관점에서 제안. 예: "원시 센서 스트림을 Jetson으로 보내지 말고, ESP32에서 FFT 후 특징 벡터만 전송하면 Jetson 부하·네트워크 부하가 줄어듭니다." |
| **Lambda 자동 생성** | 제안이 **ESP32 측 전처리**(필터, 정규화, FFT 등)일 경우, **전처리·특징 추출 노드**(§2.2.1)에 대응하는 **Lambda(C++) 스니펫**을 생성. 사용자가 "적용" 시 해당 노드의 Lambda 또는 Lambda 작성기에 삽입. 기존 "Lambda 생성"·"FSM Lambda 생성"과 동일한 채팅/요청 기반 플로우. |
| **연동** | §2.2.1 전처리 노드가 Lambda 작성기와 연동되므로, AI가 생성한 FFT/필터 코드는 해당 노드에 붙어 YAML `lambda:` 블록으로 직렬화되고 빌드에 포함됨. |

- **정리**: 사용자가 "Jetson 부하 줄이는 방법 알려줘" 또는 "이 구간을 ESP32에서 전처리하게 바꿔줘" 등으로 요청하면, 오케스트레이터가 **최적화 제안**과 함께 **Lambda 코드**를 생성·삽입할 수 있도록 하는 시나리오를 목표로 한다.

### 6.3 구현 방향

- nexa-node는 **도메인 인터콤**으로 `automation`을 이미 보고하므로, **AI 도메인·오케스트레이터**가 "현재 활성 도메인/탭"으로 nexa-node를 인식할 수 있게 함.
- **컨텍스트 주입**: 노드 그래프(JSON), 현재 선택 노드, YAML(현재 생성본), Lambda 코드 조각을 **오케스트레이터**에 전달할 수 있는 **API·이벤트** 설계. (보안·토큰 길이 주의.)

### 6.4 AI 도메인에서의 소스 수정 → nexa-node 반영 (역방향 동기화)

- **배경**: nexa-node에서 생성한 YAML/Lambda는 빌드 후 **바이너리**가 되며, AI 도메인(채팅·코드 패널)에서는 이 **소스(YAML/Lambda)**를 보거나 AI가 생성·수정한 스니펫을 사용자가 **직접 편집**할 수 있다. 그 편집 결과가 **nexa-node 도메인에 반영**되어야 캔버스·스토어·다음 빌드가 일치한다.
- **목표**: AI 도메인에서 수정된 **YAML** 또는 **Lambda**가 nexa-node의 스토어(및 필요 시 캔버스)에 반영되도록 하는 **역방향 동기화** 로직을 정의한다.

#### 필요한 로직 요약

| 구분 | 내용 |
|------|------|
| **공유 상태·이벤트** | ai와 nexa-node가 같은 **프로젝트/문서**의 "현재 YAML", "현재 Lambda(노드별·글로벌)"를 공유. AI에서 수정 시 **인터콤 이벤트** 또는 **플랫폼 스토어**로 전파(예: `nexa-node:yaml-updated`, `nexa-node:lambda-updated`, payload에 projectId, yaml 문자열 또는 lambda 문자열·nodeId). |
| **Lambda 수정 반영** | AI 도메인에서 Lambda 스니펫 적용 시 → 이벤트/스토어로 **nodeId별 또는 글로벌 Lambda** 전달. nexa-node는 수신 시 **스토어만 갱신**(해당 노드의 lambda 필드 또는 글로벌 Lambda). 캔버스 구조는 변경 없음. |
| **YAML 수정 반영** | AI 도메인에서 YAML 전체(또는 블록) 수정 시 → **옵션 A**: 수신한 YAML을 **역파싱(YAML → 그래프)**하여 노드·라인·속성을 복원하고 캔버스·스토어를 갱신. **옵션 B**: 수신 YAML을 "임포트 소스"로만 저장하고 다음 빌드에 사용, 캔버스는 "소스와 불일치"로 표시 후 사용자가 "캔버스에 반영(역파싱)" 또는 "YAML을 주 소스로 사용" 중 선택. |
| **역파싱(YAML→그래프)** | 옵션 A를 채택할 경우, ESPHome YAML 파서를 두어 `sensor:`, `on_value_range:` 등 **지원 블록**을 노드·라인·속성 중간 표현으로 변환. 제너레이터의 역함수. 지원 범위는 구현 단계별로 확대(초기에는 자주 쓰는 컴포넌트만). |
| **충돌·정책** | 동시에 nexa-node 캔버스와 AI 쪽에서 수정했을 때: **마지막 쓰기 우선**, 또는 **버전/타임스탬프**로 "어느 쪽을 기준으로 할지" 사용자 선택. nexa-node가 "외부에서 YAML이 갱신됨" 시 사용자에게 "캔버스 덮어쓰기 / 유지(빌드만 YAML 사용)" 등 알림 권장. |

#### 데이터 흐름 (역방향)

1. **nexa-node → AI**: (기존) 컨텍스트 주입으로 그래프·YAML·Lambda를 오케스트레이터에 전달.
2. **AI에서 사용자가 YAML/Lambda 수정 적용**: 채팅에서 "적용" 또는 코드 패널에서 편집 저장 시, ai 도메인이 **인터콤 발행** 또는 **공유 스토어 갱신** (projectId + 수정된 YAML 또는 Lambda + nodeId 등).
3. **nexa-node 수신**: 해당 projectId의 현재 프로젝트라면 스토어 갱신. YAML인 경우 위 옵션 A/B에 따라 캔버스 갱신 또는 "임포트 대기" 상태로 전환.
4. **다음 빌드**: nexa-node는 항상 "현재 스토어 기준 YAML(+ Lambda)"로 빌드 요청하므로, AI에서 반영된 내용이 그대로 빌드에 사용됨.

#### 구현 시 고려사항

- **ai 도메인 측**: 오케스트레이터 또는 코드 패널에서 "nexa-node 프로젝트용 YAML/Lambda가 수정됨"을 알릴 **이벤트 발행** 또는 **store commit** API 확정. [NEXA-AI-03]의 도메인 인터콤·공유 스토어 규격에 맞춰 페이로드 형식 정의.
- **nexa-node 측**: 인터콤 구독 또는 스토어 watch로 "외부 YAML/Lambda 갱신" 수신 → Lambda는 스토어 반영, YAML은 역파싱 또는 임포트 플로우 실행. 역파싱기는 별도 모듈로 두고, ESPHome YAML 서브셋부터 단계적 지원.
