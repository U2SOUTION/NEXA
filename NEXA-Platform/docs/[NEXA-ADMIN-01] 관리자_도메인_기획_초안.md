# [NEXA-ADMIN-01] 관리자 도메인 기획 초안

**목적**: **슈퍼 관리자(Super Admin)** 전용 **관리자 도메인(Admin Domain)** 을 추가하고, 회원 Tier별 도메인·하위 메뉴 접근 제어, API 사용 리미트, 회원 목록 등 플랫폼 운영에 필요한 관리 기능을 한곳에서 수행할 수 있도록 하는 **초안**을 정리한다. 선행 기획으로 요구사항·메뉴 항목을 도출해 두고, 회원/비회원 접근 정책이 확정된 뒤 상세 설계·구현 순서를 정할 수 있도록 한다.

**적용 범위**: 프론트 `src/domains/admin/**`, 서버 관리 전용 API·미들웨어, DB(권한·리미트·감사 등)

**참조 문서**: [NEXA-AUTH-01] 계정·인증·권한, [NEXA-CAPABILITY-01] ⭐ Capability ID 체계 및 Tier 접근 권한, [NEXA-STACK-01] 기술 스택·용어, [NEXA-PLATFORM-TS-01] TS 전략

**문서 성격**: **초안**. 메뉴 항목·개념 정리 위주. 세부 API·DB 스키마·UI 와이어프레임은 추후 정리.

**작성일**: 2025-03

---

## 1. 배경 및 목표

### 1.1 배경

- 플랫폼에 **회원 Tier**(예: free / pro / enterprise) 및 **도메인별·메뉴별 접근 제어**가 필요해질 수 있음.
- **API 사용량·리미트**를 Tier 또는 개별 회원 단위로 관리할 필요가 있음 ([NEXA-AUTH-01]의 api_usage 등과 연계).
- **회원 목록·상태·정책**을 슈퍼 관리자가 조회·변경할 수 있는 화면이 있으면 운영·지원에 유리함.
- 위 기능을 **일관된 관리자 도메인**에서 제공하면, 권한 정책·감사·확장이 수월함.

### 1.2 목표

| 목표 | 설명 |
|------|------|
| **관리자 도메인 추가** | 슈퍼 관리자 전용 메뉴/레이아웃. 일반 회원·비회원은 접근 불가. |
| **Tier별 도메인 접근 관리** | Tier(예: free/pro/enterprise)별로 접근 허용 도메인 목록 설정. |
| **도메인 내 하위 메뉴 접근 관리** | 도메인 단위를 넘어, 도메인 내 특정 하위 메뉴(탭·섹션) 단위로 접근 허용/차단. |
| **API 사용 리미트 설정** | Tier 또는 회원별 API 호출 한도·기간 단위 설정. |
| **회원 목록·상태 관리** | 회원 검색·Tier 변경·비활성화·감사 등. |
| **기타 슈퍼 관리자 기능** | 감사 로그, 시스템 설정, 공지, 엣지·OTA 등 필요 시 확장. |

## 2. 접근 대상 및 역할 정의

### 2.1 슈퍼 관리자(Super Admin)

- **정의**: 플랫폼 전역의 **회원·접근 정책·API 리미트·시스템 설정** 등을 관리할 수 있는 최고 권한 역할.
- **식별**: [NEXA-AUTH-01]의 사용자 테이블(users)에 **역할(role)** 또는 **is_super_admin** 플래그로 구분. (구체 필드명·ENUM은 접근 정책 확정 시 정의.)
- **접근**: **관리자 도메인**은 슈퍼 관리자만 라우트·메뉴 진입 가능. 그 외 회원·비회원은 403 또는 리다이렉트.

### 2.2 일반 회원·비회원

- 관리자 도메인 **미노출** 또는 노출되더라도 **진입 시 권한 검사로 차단**.
- 회원/비회원 접근 정책은 별도 문서에서 정리 후, 본 도메인의 "누가 무엇을 볼 수 있는지"와 연계.

### 3.3 엣지 및 OTA 관리 (중요)

OTA는 다음 **세 가지 배포 방식**을 모두 지원하도록 설계한다.

| 배포 방식 | 설명 |
|-----------|------|
| **관리자 강제 밀어넣기 (Push-based OTA)** | 관리자가 특정 그룹/기기에 업데이트를 강제로 푸시. |
| **엣지 자율 업데이트 (Pull-based OTA / Auto-update)** | 엣지 기기가 주기적으로 서버를 조회해 새 버전이 있으면 자동 다운로드·적용. |
| **사용자 승인 업데이트 (User-consented OTA)** | 사용자(앱/웹)에게 업데이트 안내 후, 사용자가 승인한 경우에만 적용. |

| 메뉴명 | 주요 기능 | 비고 |
|--------|-----------|------|
| **펌웨어 저장소** | 바이너리 업로드, 버전(v1.0.1 등) 관리, 변경 이력(Changelog) 작성 | 모든 OTA의 원천 |
| **배포 그룹 관리** | 베타 테스터 그룹, 모델 A 그룹, 지역별 그룹 등 기기 묶음 관리 | 분산 업데이트의 단위 |
| **배포 캠페인** | 어떤 펌웨어를 어느 그룹에 어떤 방식(강제/자율/승인)으로 보낼지 정의 | 실제 업데이트 실행 단위 |
| **OTA 실시간 로그** | 현재 진행 중인 기기 수, 성공/실패율, 에러 코드 통계 | 운영 모니터링 |

| 기타(선택) | 비고 |
|------------|------|
| 비정상 기기 원격 재부팅(Reboot) 트리거 | |
| 기기 소유권 강제 이전 및 등록 해제(Unbind) | |

### 3.6 AI 협력 및 리소스 관리

AI 도메인(nexa-ai)의 핵심 로직인 **페르소나, 스킬, 에이전트** 등을 관리자가 중앙에서 제어·모니터링하는 섹션. 모델 인벤토리·리소스 배분, 페르소나·스킬 관리, 에이전트·오케스트레이터, AI 성능·품질 감사(LLMOps)를 포괄.

| 메뉴명 | 주요 기능 | 비고 |
|--------|-----------|------|
| **모델 인벤토리** | Ollama 로컬 모델(Llama3, Mistral 등) 및 클라우드 모델(GPT, Claude) 상태 관리 | 모델별 가용성 체크 |
| **페르소나 빌더** | AI의 말투, 성격, 기본 지식(System Prompt) 템플릿 관리 | 공통 페르소나 배포 |
| **스킬(Tools) 라이브러리** | AI가 사용할 수 있는 함수(웹 검색, DB 조회, 엣지 제어 등) 정의 | Function Calling 관리 |
| **에이전트/태스크 설계** | 특정 목적(코드 리뷰, 로그 분석 등)을 가진 에이전트 구성 | 워크플로우 템플릿 |
| **오케스트레이터 설정** | 여러 에이전트 간의 협업 규칙 및 우선순위 알고리즘 관리 | 멀티 에이전트 제어 |
| **AI 추론 모니터링** | 토큰 사용량, 응답 속도(Latency), 추론 비용 실시간 시각화 | 성능 및 비용 최적화(LLMOps) |

### 3.7 UI/UX 및 테마 관리

플랫폼의 **시각적 요소**와 **사용자 경험(UX) 접점**을 관리자가 직접 제어하는 기능. 브랜드·테마, 컴포넌트·레이아웃, 문구·온보딩까지 한곳에서 설정 가능하도록 한다.

| 메뉴(기능) 명 | 비고 |
|--------------|------|
| **글로벌 테마 설정** | 브랜드 컬러(Primary/Secondary), 다크모드 기본값, 폰트 스타일 관리 |
| **컴포넌트 라이브러리 제어** | 특정 UI 컴포넌트(차트, 데이터 테이블 등)의 사용 여부 및 버전 관리 |
| **대시보드 레이아웃 템플릿** | Tier별 또는 도메인별 기본 대시보드 위젯 배치 설정 |

| **런처/사이드바 구성** | 도메인 아이콘, 메뉴 순서, 그룹화 방식 커스텀 설정 |

## 4. 상세 기획

§3 메뉴(기능)별 **상세 기획 내용**이다. 기존 Tier/도메인/메뉴 접근, API 리미트, 회원 관리, Impersonation, 쿼터 시각화, 예약 설정과 신규 항목(엣지·OTA, 부관리자, 캐시 Flush, 템플릿 편집기 등)을 통합 정리.

### 4.1 계정 및 권한 관리

#### Tier별 도메인 접근·하위 메뉴 접근

| 항목 | 설명 |
|------|------|
| **목적** | 회원 Tier(예: free, pro, enterprise)별로 **접근 가능한 도메인** 목록 및 **도메인 내 하위 메뉴·액션** 단위 접근 설정. |
| **Capability ID 체계** | **[NEXA-CAPABILITY-01] ⭐** 참고. `nexa.archive`, `nexa.archive.hub`, `nexa.archive.hub.export` 등 계층 ID, 와일드카드(`nexa.archive.*`), `tiers`·`capabilities`·`tier_allowed_capabilities` 테이블, 동기화·캐싱·우회 방어. |
| **도메인 예시** | home, nexa-board, nexa-panel, automation, infra, dev, nexa-erp, nexa-archive, nexa-ai, my, settings 등 (domainRegistry 기준). Capability ID는 `nexa.` 네임스페이스로 통일. |
| **관리 내용** | Tier별 역량(Capability) 허용 목록. UI에서 "이 메뉴만 허용" / "이 메뉴 및 모든 하위 기능 허용" 라디오로 구분, `.*` 자동 처리. |
| **저장** | `tiers`, `capabilities`, `tier_allowed_capabilities`. [NEXA-CAPABILITY-01] §3. |
| **구현 참고** | `capabilityRegistry`·`domainRegistry`에서 도메인/메뉴 선언. `hasCapability(userCapabilities, required)`로 라우트·API·UI 검사. 적용 전략은 점진적(신규 적용, 기존은 수정 시 보강). [NEXA-CAPABILITY-01] §7.1. |

#### 회원 목록·강제 탈퇴·비밀번호·메모

| 항목 | 설명 |
|------|------|
| **전체 회원 목록** | 가입일, 마지막 접속, Tier 등 필터·검색. 상세에서 Tier 변경·비활성화. |
| **강제 탈퇴(Soft Delete)** | 회원 계정 비활성화 및 복구 기능. 삭제 시점·복구 이력 감사 로그 기록. |
| **비밀번호 수동 초기화** | 임시 비밀번호 발급·전달. (선택) 이메일로 임시 비밀번호 발송. |
| **회원별 메모** | 특이사항 기록용. 관리자만 조회 가능. users 확장 또는 별도 `user_admin_notes` 테이블. |
| **개인정보** | 목록·상세 노출 시 개인정보 보호 정책에 맞게 마스킹·접근 로그 등 검토. |

#### 관리자 역할 위임 (부관리자)

| 항목 | 설명 |
|------|------|
| **목적** | 슈퍼 관리자 외에 **운영자, 고객지원** 등 부관리자 역할을 두어, 제한된 관리 기능만 위임. |
| **관리 내용** | 역할별 접근 가능 메뉴(예: 회원 목록 조회만, Tier 변경 불가 등) 정의. users에 role 또는 별도 admin_roles 테이블. |
| **참고** | 상세 권한 스펙(어떤 역할이 어떤 API/메뉴에 접근 가능한지)은 [NEXA-AUTH-01] 및 상세 기획에서 정의. |

#### 사용자 페르소나 미리보기 (Impersonation)

| 항목 | 설명 |
|------|------|
| **기능** | 슈퍼 관리자가 **특정 회원의 화면을 동일하게** 대리해서 보는 기능. |
| **동작** | 회원 목록에서 **[로그인 대행]** 버튼 선택 시, 해당 사용자의 권한(Tier·도메인/메뉴 접근)이 적용된 상태로 플랫폼 UI 확인. |
| **목적** | "정회원인데 왜 이 메뉴가 안 보이죠?" 등 CS 문의 시 원인 파악·즉각 지원. |
| **구현 참고** | 세션/토큰에 "실제 로그인 사용자(관리자)"와 "대행 대상 user_id" 구분 저장. API·프론트는 대행 대상 기준 권한 적용. 감사 로그에 대행 조회 기록 필수. |
| **보안** | 슈퍼 관리자만 사용. 대행 세션은 읽기 위주 권장. 개인정보 노출 시 접근 로그·정책 준수. |

### 4.2 리소스 및 API 관리

| **관리 내용** | API 경로(또는 서비스 키)별 enabled 플래그. Redis 또는 DB 저장. 미들웨어에서 차단 목록 조회 후 503/423 반환. |

### 4.3 엣지 및 OTA 관리 (핵심)

#### 배포 방식 (세 가지 모두 지원)

| 방식 | 설명 |
|------|------|
| **1. 관리자 강제 밀어넣기 (Push-based OTA)** | 관리자가 배포 캠페인에서 "강제"를 선택하면, 대상 그룹/기기에 서버가 업데이트를 푸시. 기기는 수신 후 적용(또는 스케줄에 따라 적용). |
| **2. 엣지 자율 업데이트 (Pull-based OTA / Auto-update)** | 엣지 기기가 주기적으로 서버에 새 버전 여부를 조회. 배포 캠페인에서 "자율"로 열린 캠페인이 있으면 기기가 자동 다운로드·적용. |
| **3. 사용자 승인 업데이트 (User-consented OTA)** | 배포 캠페인을 "승인" 방식으로 설정 시, 사용자(앱/웹)에게 업데이트 안내가 노출되고, 사용자가 승인한 경우에만 다운로드·적용. |

#### 메뉴별 상세

| 메뉴 | 주요 기능 | 비고 |
|------|-----------|------|
| **펌웨어 저장소** | 바이너리 업로드, 버전(v1.0.1 등) 관리, 변경 이력(Changelog) 작성. 기기 종류(ESP32, ESP8266, RP2040 등)별 구분. | 모든 OTA의 **원천**. 배포 캠페인에서 여기서 버전 선택. |
| **배포 그룹 관리** | 베타 테스터 그룹, 모델 A 그룹, 지역별 그룹 등 **기기 묶음** 관리. 기기-그룹 매핑. | **분산 업데이트의 단위**. 캠페인은 "어느 그룹에" 보낼지 지정. |
| **배포 캠페인** | **어떤 펌웨어**를 **어느 그룹**에 **어떤 방식(강제/자율/승인)**으로 보낼지 정의. 스케줄(예: 새벽 순차) 설정. | **실제 업데이트 실행 단위**. 생성·시작 시 위 세 방식 중 하나 선택. |
| **OTA 실시간 로그** | 현재 진행 중인 기기 수, **성공/실패율**, **에러 코드 통계**. 캠페인별·그룹별 조회. | **운영 모니터링**용. |

#### 기타 (선택)

| 항목 | 설명 |
|------|------|
| **비정상 기기 원격 재부팅** | Reboot 트리거. 기기 상태 비정상 시 원격 재부팅 명령. |
| **기기 소유권·등록 해제** | 기기 소유권 강제 이전, 등록 해제(Unbind). 기기-회원 매핑 변경·해제. |

**참고**: [NEXA-NODE-01] ESPHome·펌웨어 배포 기획과 연계. 엣지·OTA는 별도 도메인(예: nexa-node)으로 분리 검토 가능.

### 4.6 AI 협력 및 리소스 관리

AI 도메인(nexa-ai)의 **페르소나, 스킬, 에이전트, 오케스트레이터**를 관리자가 중앙에서 제어·모니터링. **모델 인벤토리·리소스 배분**, **페르소나·스킬 관리**, **에이전트·오케스트레이터**, **AI 성능·품질 감사(LLMOps)** 를 포괄.

#### 메뉴별 상세

| 메뉴 | 주요 기능 | 비고 |
|------|-----------|------|
| **모델 인벤토리** | Ollama 로컬 모델(Llama3, Mistral 등) 및 클라우드 모델(GPT, Claude) **상태 관리**. 모델별 가용성 체크, Tier별 접근 매핑. | 리소스 배분의 기준. |
| **페르소나 빌더** | AI의 말투, 성격, **System Prompt 템플릿** 관리. 공통 페르소나 배포. | |
| **스킬(Tools) 라이브러리** | AI가 사용할 수 있는 **함수**(웹 검색, DB 조회, 엣지 제어 등) 정의. **Function Calling** 관리. | 스킬 실행 시 권한 검증 연동. |
| **에이전트/태스크 설계** | 특정 목적(코드 리뷰, 로그 분석 등)을 가진 **에이전트 구성**. 워크플로우 템플릿. | |
| **오케스트레이터 설정** | 여러 에이전트 간 **협업 규칙·우선순위 알고리즘** 관리. 멀티 에이전트 제어. | 변경 시 캐시 무효화(아래 참고). |
| **AI 추론 모니터링** | **토큰 사용량**, **응답 속도(Latency)**, **추론 비용** 실시간 시각화. | **LLMOps**·성능·비용 최적화. |

#### AI 협력 관리 인가 구조

| 항목 | 설명 |
|------|------|
| **모델 접근 권한** | **`tier_model_access`** 테이블로 Tier별 사용 가능 모델 제한. 예: BASIC 회원은 경량 모델만, PRO 회원은 고성능 모델 사용. 추론 API 호출 시 해당 테이블(또는 Redis 캐시) 조회 후 허용 여부 판단. |
| **스킬 실행 권한** | AI가 수행하려는 **스킬**이 현재 사용자의 권한 범위를 넘어서는지 **미들웨어에서 실시간 검증**. 스킬 ID·Tier(또는 role) 매핑 테이블과 연동. 초과 시 해당 스킬 호출 거부. |
| **오케스트레이터 캐싱** | 복잡한 에이전트 협업 로직은 변경이 잦지 않으므로 **Redis에 구조화하여 저장**. 관리자가 오케스트레이터 설정을 수정할 때만 해당 키 **FLUSH**하여 성능 최적화. |

#### 페르소나·스킬·태스크 공유 및 마켓 확장 (비전)

[NEXA-AUTH-01]의 **device_members**가 사용자–디바이스 관계를 연결하고 **디바이스 공유**를 가능하게 하듯, **페르소나·스킬·에이전트/태스크**를 **템플릿** 개념으로 관리해 **회원 간 공유**로 확장할 수 있다.

| 항목 | 설명 |
|------|------|
| **페르소나 템플릿** | 페르소나를 템플릿으로 저장. 사용자가 **캐릭터에 도메인별 페르소나**를 할당·조합 가능. 다른 회원이 만든 페르소나 템플릿을 **공유**받아 사용. |
| **스킬·태스크 공유** | 스킬(Tools)·에이전트/태스크(워크플로우)도 템플릿화하여 **회원 간 공유** 가능. |
| **오픈 마켓 확장** | 공유를 **무료/유료**로 확장하면 플랫폼 내 **오픈 마켓** 형태 가능. 전문가 제작 페르소나·스킬·태스크의 유로 배포 등. 관리자 도메인에서 마켓 승인·과금 정책 등 연동 검토. |

- **제공 방식**: 플랫폼 **기본(디폴트)** 제공 + 사용자 **직접 추가** 가능. 사용자 추가분이 기본을 **완전 오버라이드**할지 **추가만** 허용할지는 실제 경험을 보며 판단.

**참고**: [NEXA-AI-01] 웹 탐색기·문서폴더 연동 등 AI 도메인 기획과 연계. [NEXA-SMART-GUIDE] §5 페르소나·스킬·태스크 공유 비전과 동일 개념. nexa-ai 도메인 내에서 위 설정을 조회·적용.

| **런처/사이드바 구성** | **도메인 아이콘**, **메뉴 순서**, **그룹화 방식** 커스텀 설정. domainRegistry·사이드바 설정과 연동. | 접근 권한(Tier)과 결합해 노출 제어. |
| **사용자 가이드/온보딩** | 신규 회원 대상 **툴팁**, **가이드 팝업** 시나리오 및 **노출 로직** 관리. 단계별 시나리오·스킵 옵션. | 첫 로그인·도메인 진입 시 트리거. |

**저장·적용**: 테마·레이아웃·i18n·사이드바 설정은 DB 또는 설정 저장소에 저장. 프론트는 로그인 시 또는 설정 API로 조회 후 적용. 캐시(Redis)·CDN으로 정적 자산 배포 시 TTL 고려.

## 5. 도메인·하위 메뉴 식별 (구현 시 참고)

- **도메인 ID**: 프론트 `domainRegistry`(또는 동일 계열 설정)에 정의된 키와 1:1 매칭. 예: `home`, `dev`, `nexa-ai`, `my`.
- **하위 메뉴**: 도메인 내 사이드바·탭·라우트 단위. 예: dev 도메인 내 "문서 관리", "테마 매니저", "에러 트래킹" 등. 각 도메인별로 **메뉴 ID 또는 라우트 경로**를 정리해 두면, "Tier별 하위 메뉴 접근" 정책과 매핑 가능.
- **정책 적용 위치**: 프론트는 **라우트 가드·사이드바 렌더링 시** "현재 사용자 Tier + 도메인/하위 메뉴 접근 설정"을 조회해 노출·진입 허용 여부 결정. 서버는 **API 단**에서 동일 정책으로 403 등 처리 가능.

**접근 제어 로직 구현 시 DB 부하 절감**

- **프론트엔드**: `domainRegistry` 각 항목에 `requiredTier`(또는 접근 정책 키) 속성을 두고, 관리자 페이지에서 설정한 정책을 **로그인 시점에 권한 매핑 테이블 형태로 한 번에 내려받아** 메모리(Vuex/Pinia)에 캐싱. 라우트 가드·사이드바는 이 캐시만 참조하여 DB/API 재조회 없이 판단.
- **백엔드**: Redis에 **`tier_access_map`** 을 해시 구조로 저장해 두고, 모든 API 요청 미들웨어에서 **O(1)** 로 권한 체크. 정책 변경 시 해당 맵만 갱신하면 되며, 요청마다 DB 조회를 하지 않음.

## 6. 선행·의존 사항

| 항목 | 내용 |
|------|------|
| **회원/비회원 접근 정책** | "어떤 도메인을 비회원에게 열지, 회원 Tier별로 무엇을 열지"가 정해져야 관리자 화면에서 설정하는 값과 의미가 맞음. 정책 확정 후 본 도메인 상세 기획 권장. |
| **Tier·역할 정의** | [NEXA-AUTH-01] 또는 별도 문서에서 Tier(또는 role) Enum·의미 확정. free / pro / enterprise 등. |
| **인증·인가** | JWT·미들웨어에서 `user.role` 또는 `user.is_super_admin` 등으로 슈퍼 관리자 여부 판단. 관리자 전용 API는 동일 조건으로 가드. |
| **DB** | users에 역할/Tier 컬럼. [NEXA-CAPABILITY-01] 체계 기반으로 `tiers`·`capabilities`·`tier_allowed_capabilities`. 기타 api_limit_policy·audit_log 등은 상세 기획 시. |

## 7. 구현 순서 제안 (초안)

1. **접근 정책·Tier 정의** 확정.
2. **관리자 도메인** 프론트 껍데기: 라우트, 레이아웃, 사이드바에 "관리자" 메뉴 추가. 슈퍼 관리자만 진입 가능하도록 가드.
3. **Tier별 도메인 접근**: [NEXA-CAPABILITY-01] Capability 체계 기반 구축. 설정 화면·API·DB. 이후 프론트에서 `hasCapability`로 메뉴 노출·라우트 가드.
4. **도메인 내 하위 메뉴 접근** 확장 (도메인·메뉴 키 정의 후 동일 패턴).
5. **API 리미트** 정책 테이블·설정 화면·미들웨어 연동. 쿼터 시각화·위험군·알림 설정.
6. **회원 목록·관리** 화면·API (강제 탈퇴·복구, 비밀번호 초기화, 메모, Impersonation).
7. **부관리자 역할 위임** (필요 시).
8. **엣지·OTA 관리**는 [NEXA-NODE-01] 연계 후 별도 도메인 또는 본 도메인 내 메뉴로 구현.
9. **AI 협력·리소스 관리**는 [NEXA-AI-01] 연계. 모델 인벤토리·tier_model_access, 페르소나·스킬·에이전트·오케스트레이터 설정, AI 추론 모니터링(LLMOps).
10. **UI/UX·테마 관리**: 글로벌 테마, 컴포넌트 제어, 대시보드 레이아웃 템플릿, i18n, 런처/사이드바 구성, 사용자 가이드/온보딩.
11. **감사 로그·공지·점검 모드·템플릿 편집기·시스템 상태** 등은 필요 시 순차 추가.
