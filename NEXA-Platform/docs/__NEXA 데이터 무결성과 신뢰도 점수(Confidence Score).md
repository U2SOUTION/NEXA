# NEXA 데이터 무결성과 신뢰도 점수(Confidence Score)

NEXA 플랫폼의 데이터 무결성과 지능적 의사결정 품질을 높이기 위해,
신뢰도 점수(Confidence Score / Fit Score)의 저장 위치, 부여 로직, 운영 활용 방식을 정의한다.

---

## 1) 신뢰도 점수 저장 설계

신뢰도 점수는 데이터 성격에 따라 로그(실시간), 지식(아카이브), 제안(AI 추천) 계층에 배치한다.

| 대상 테이블            | 필드명             | 타입       | 설명                                                      |
| ---------------------- | ------------------ | ---------- | --------------------------------------------------------- |
| `project_logs`         | `confidence_score` | `SMALLINT` | 실시간 이벤트 확신도. 빈번한 필터링을 위해 컬럼 저장 권장 |
| `project_knowledge`    | `confidence_score` | `SMALLINT` | 지식 검증 수준. RAG 정렬/필터 가중치                      |
| `capability_proposals` | `fit_score`        | `SMALLINT` | AI 추천 자격과 사용자 의도의 부합도(0~100)                |
| `project_orchestra`    | `skill_threshold`  | `JSONB`    | 스킬별 자율 실행 최소 임계값                              |

> `extra_data`/`metadata` JSONB 저장도 가능하나, 검색/정렬이 많으면 별도 컬럼이 유리하다.

---

## 2) Pulse별 점수 부여 로직

헥사곤 프로토콜 `Who(Pulse)`에 따라 점수 산출 주체와 기준이 다르다.

| Pulse  | 부여 주체             | 점수 산출 기준                         | 관련 기술        |
| ------ | --------------------- | -------------------------------------- | ---------------- |
| `TICK` | Sentinel (Nano/Micro) | SNR, 임계치 근접도, TinyML 확률        | TinyML, 인터락   |
| `ECHO` | Indicator (Zenith)    | LLM 확신도(Logprobs), 코일 부합도(Fit) | LLM, 6-Coils     |
| `WILL` | User/Admin            | Tier 권한, 명시적 승인 여부            | Tier, Capability |
| `ASK`  | System Hybrid         | 과거 승인/거절 이력 기반 통계          | Feedback Loop    |

## 3) 활용 전략

### 3.1 지능형 가드레일

- `project_logs.confidence_score`가 임계치 미만이면 즉시 실행 대신 `ASK`로 전환
- 임계값 기준:
  - `project_settings.user_defined_threshold`
  - 코일 밸런서(특히 Stability/Safety) 정책

### 3.2 RAG 최적화

- 유사도가 높아도 `confidence_score`가 낮은 지식은 우선순위를 낮춤
- “의미 유사도 + 신뢰도” 하이브리드 랭킹 적용

### 3.3 UI 피드백

- Nixie UI에서 점수를 밝기/노이즈(Jitter)로 시각화
- 낮은 점수는 “모호한 판단 상태”를 비언어적으로 전달

---

## 4) 상세 부여 방식

### 4.1 디바이스 데이터 (`TICK`)

- 엣지(Sentinel)가 현장 팩트에 대해 기술적 정밀도 점수를 부여
- 입력 예시:
  - 센서 SNR
  - 임계치 오차율
  - TinyML 확률값(예: 0~1 또는 %)
  - `is_time_synced` 기반 시간 신뢰도 보정

### 4.2 순수 AI 자동결정 (`ECHO`)

- 인디케이터가 모델 추론 확신도 + 코일 부합도로 점수 부여
- 예시 규칙:
  - 95 미만: `ASK` 전환
  - 95 이상: 자동 실행 후보

### 4.3 사람 결정 데이터 (`WILL`)

- 사용자의 Tier 및 명시적 승인에 따라 최종 확정
- 명시적 최종 승인 시 최고 신뢰 구간으로 승격 가능

### 4.4 협력 데이터 (`ASK`)

- AI 제안에 대한 사용자 반응 이력을 통계화해 동적 보정
- 동일 유형 의사결정에서 추천 신뢰도 자동 튜닝

---

## 5) 벡터 데이터와 신뢰도 점수의 관계

신뢰도는 벡터에 “녹여 넣는 값”이 아니라, 벡터 검색 결과를 실행 가능성으로 변환하는 별도 레이어다.

### 5.1 분리 이유

- 벡터(`embedding`): 의미 좌표(유사도 계산)
- 신뢰도(`confidence_score`): 실행 판단 필터
- 같은 문서 벡터라도 운영 정책/코일 상태에 따라 실행 임계값은 달라질 수 있음

### 5.2 하이브리드 리트리버

1. 벡터 검색으로 후보 지식 조회
2. 신뢰도 점수로 재정렬/필터
3. 최종 실행/응답 생성

### 5.3 운영 이점

- 신뢰도만 업데이트 가능(리임베딩 불필요)
- 상황 변화에 따라 판단 가중치를 빠르게 조정 가능

## 6) 데이터 출처 3분류와 매핑

| 분류                 | Pulse                   | Intent/Nature              | ID 체계          | 설명                   |
| -------------------- | ----------------------- | -------------------------- | ---------------- | ---------------------- |
| 디바이스 생성 데이터 | `TICK`                  | `FACT`, `ROUTINE/INCIDENT` | `SNT-ID`         | 센티널이 포착한 사실   |
| 사람 결정 데이터     | `WILL`(승인 대기 `ASK`) | `INTENT`, `RULE`           | 사용자/승인 체계 | 사용자 의지 기반 확정  |
| 순수 AI 자동결정     | `ECHO`                  | `GOVERN`, `RULE`           | `IND-ID`         | 인디케이터의 자율 판단 |

---

## 7) 점수 생성 주체의 가중 전략

### 7.1 엣지(Sentinel)

- 물리적 정밀도 기반 원점수 생성
- 저비용 계산(SNR/확률값 재사용)

### 7.2 인디케이터(Indicator/Zenith)

- 맥락 보정(환경/상황/정책)
- 코일 밸런스 부합도 검증
- 자율 실행 게이트 판정(실행 vs ASK)

### 7.3 사용자(WILL)

- 승인으로 최종 신뢰 확정
- 운영 규범(GOVERN) 반영의 최종 책임 주체

---

## 8) 권장 문구(문서 삽입용)

> NEXA 플랫폼은 지능의 무게를 분산 관리한다.  
> 중앙 인디케이터가 상황 맥락을 종합 판단하는 것과 별개로, 최전방 엣지(Sentinel)도 SNR/TinyML 확률값 기반의 신뢰도 점수를 직접 생성할 수 있다.  
> 생성된 점수는 `project_logs` 등 신뢰도 필드에 즉시 반영되며, 자율 실행 게이트와 `ASK` 전환 정책의 핵심 근거로 사용된다.

---

## 9) 결론

1~8절을 한눈에 요약한다. 세 관점(역할·구조·준비도)을 표로 나누면 나중에 발표·온보딩용으로도 읽기 쉽다.

| 관점 | 핵심 정리 |
| ---- | --------- |
| **역할** | 신뢰도 점수는 자율 실행 vs `ASK`(승인 대기) 등 **실행 여부**를 가르는 핵심 레이어다. 가드레일·RAG·UI 피드백 모두 이 값을 전제로 동작한다. |
| **구조** | 벡터(`embedding`)는 **의미(유사도)** , 신뢰도는 **판단(실행 필터)** 이다. 분리 저장하면 리임베딩 없이 정책·코일만 바꿔 임계값을 조정할 수 있어 정합성과 운영 유연성에 유리하다. |
| **준비도** | `project_logs`·`project_knowledge`·`capability_proposals`·`project_orchestra` 등에 점수·임계 필드가 설계되어 있어, Pulse별 부여 로직과 가드레일·RAG 가중을 **바로 적용·실험할 수 있는** 수준의 스키마다. |
