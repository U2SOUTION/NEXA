# 룰·프롬프트 통합 관리 기획 (초안)

앞으로 **룰/시스템 프롬프트**가 채팅뿐 아니라 오케스트레이터, Nexus Map, 메타데이터 추출, 시스템 보조 등 **다양한 사용처**에서 중요해지고, **모델·프로젝트·태스크별**로 수많은 룰을 생성·적용·수정해야 할 전망이다.  
이 문서는 **한 군데서 통합 관리**할 수 있는 방향을 정리한 초안이다. 막막함을 줄이기 위해 **개념 구조**와 **단계적 접근**을 제안한다.

---

## 1. 현황

| 항목         | 내용                                                                                                                                |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| **사용처**   | 현재는 **채팅**에서만 시스템/채널/채팅 수준의 지침(instruction) 사용.                                                               |
| **저장**     | `useAiChannels`: localStorage (`nexa-ai-channels`). 시스템·채널·채팅별 instruction 문자열.                                          |
| **하드코딩** | `MARKDOWN_ONLY_RULE` 등 상위 공통 룰은 코드에 고정.                                                                                 |
| **적용**     | `getEffectiveInstruction()`에서 시스템 → 채널 → 채팅 순으로 **문자열 결합** 후, chat/chatStream 호출 시 `systemInstruction`로 전달. |

- **한계**: 사용처가 늘어나면 “채팅용 instruction”과 “오케스트레이터용 룰”, “Nexus용 룰”, “메타 추출용 지침” 등이 **여기저기 흩어지고**, 모델·프로젝트별로 다른 룰을 쓰려면 구조가 복잡해진다.

---

## 2. 목표 (통합 관리가 필요한 이유)

- **한 군데서** 룰/프롬프트를 **생성·수정·버전 관리·재사용**할 수 있게 한다.
- **사용처(Consumer)** 는 “지금 이 컨텍스트에 필요한 룰”만 **키/스코프**로 조회해서 쓰고, 룰 내용은 중앙에서 관리한다.
- **모델·프로젝트·태스크**가 바뀌어도, “어떤 룰 세트를 쓸지”만 지정하면 되도록 한다.
- 나중에 **새 사용처**가 생겨도, “새 Consumer 등록 + 룰 세트 하나 만들고 연결”만 하면 확장 가능하게 한다.

---

## 2.1 범위와 경계 구분 (Nexus Map, AI 관제 패널과의 관계)

현재 기획안은 **ai 도메인** 규모에서 1차로 소화 가능하다. 확장 단계와 **Nexus Map**, **AI 관제 패널**과의 역할 구분을 명확히 둔다.

### 2.1.1 3대 핵심 UI 개요

| 단계 | 범위 | 비고 |
|------|------|------|
| **현재(1차)** | ai 도메인 내. 채팅·오케스트레이터·메타추출·Nexus 등에서 룰/프롬프트 통합 관리. | 본 문서가 다루는 규모. |
| **1차 확장** | **모든 도메인**에서 AI 협력(직·간접) 적용. archive, parts, dev 등에서도 룰·Resolution API 호출. | rule_sets·rule_assignments는 도메인 무관하게 공통 사용. |
| **2차 확장** | **수많은 IoT 엣지 디바이스 AI** 설계·적용. 엣지별 모델·룰 배포, 동기화. | 엣지 디바이스는 “원격 Consumer” 또는 별도 **AI 관제 패널**에서 관리. |

### Nexus Map과의 구분

| 구분 | 룰·프롬프트 통합 관리 (본 문서) | Nexus Map |
|------|--------------------------------|------------|
| **역할** | **룰/프롬프트 내용**의 생성·수정·버전·Resolution. “무슨 지침을 줄 것인가.” | **관계망 시각화**·**할당**(파일↔페르소나/스킬/테스크)·**연결 규칙** 검증. “누가 무엇과 연결되는가.” |
| **겹치는 부분** | 페르소나·스킬·테스크 개념, 그래프 UI(노드·라인). | 동일. |
| **경계** | 룰 **본문(content)** 과 **Resolution**(어떤 룰이 어떤 컨텍스트에서 쓰일지)는 본 쪽. Nexus는 **노드·엣지 데이터**(할당, 연결)와 **캔버스 UX**. 룰 관리 UI에서 “페르소나·스킬 노드 연결”은 Nexus와 **연동**하되, **룰 본문 편집·Resolution**은 본 쪽 전담. Nexus에서 “이 파일에 이 페르소나/스킬 할당”하면, 룰 쪽은 “그 페르소나/스킬에 해당하는 룰”을 Resolution에 반영. |
| **정리** | 룰 **내용**과 **해석(Resolution)** 담당. Nexus는 **관계·할당** 담당. 둘 다 “페르소나·스킬·테스크”를 쓰지만, **룰 쪽 = 텍스트(지침)**, **Nexus 쪽 = 그래프(누가-무엇 연결)**. |

### AI 관제 패널과의 구분 (향후 전용 패널 가정)

고도로 전문적인 **운영·모니터링** 데이터는 **독립된 'AI 관제 패널'** 로 분리하는 것을 전제로, 본 룰·프롬프트 관리와 역할을 나눈다.

| 구분 | 룰·프롬프트 통합 관리 (본 문서) | AI 관제 패널 (독립, 향후) |
|------|--------------------------------|---------------------------|
| **역할** | 룰/프롬프트 **내용** 관리, Resolution, 적용 대상 지정. | **학습 데이터셋** 관리, **모델 재배포** 현황, **성능 지표**(Precision, Recall, F1 등), 추론 지연·에러율, 엣지 디바이스 상태·버전 등. |
| **데이터** | rule_sets, rule_assignments, 페르소나·스킬·테스크(룰 적용 대상). | 학습/검증 데이터, 모델 아티팩트, 배포 이력, 메트릭 시계열, 엣지 디바이스 인벤토리. |
| **정리** | “**무슨 지침을 줄지**”에 집중. “**얼마나 잘 동작하는지**”, “**어떤 데이터로 학습했는지**”, “**어디에 배포됐는지**”는 AI 관제 패널이 담당. 룰 관리와 관제는 **데이터·UI 모두 분리**하는 것이 바람직함. |

이렇게 **룰 관리 ↔ Nexus Map ↔ AI 관제 패널**을 구분해 두면, 1차(ai)·1차 확장(전 도메인)·2차 확장(IoT 엣지) 시 각각의 책임 범위가 명확해진다.

## 3. 핵심 개념 제안

### 3.1 룰 세트 (Rule Set) / 프롬프트 템플릿 (Prompt Template)

- **룰 세트**: 하나의 “지침 문서” 단위. 예: “채팅 기본 품질 룰”, “오케스트레이터 라우팅 룰”, “Nexus 노드 설명 생성 룰”, “문서 메타데이터 추출 룰”.
- **내용**: 마크다운 또는 평문. 필요 시 **플레이스홀더**(`{{model}}`, `{{context}}` 등)를 넣어, 호출 시점에 치환할 수 있게 하면 “프롬프트 템플릿”이 됨.
- **속성**: 이름, 설명, 스코프(아래), 적용 대상(Consumer·모델·프로젝트), 버전(선택), 활성/비활성.

### 3.2 스코프 (Scope) — “어디에 쓰이는가”

| 스코프            | 설명                                                                  | 예시                                                  |
| ----------------- | --------------------------------------------------------------------- | ----------------------------------------------------- |
| **시스템**        | 전역 기본. 모든 Consumer에 공통으로 깔 수 있음.                       | “출력은 마크다운만”, “HTML 금지”                      |
| **Consumer**      | 사용처 단위. 채팅 / 오케스트레이터 / Nexus / 메타추출 / …             | “채팅은 2문장 이내 요약”, “오케스트레이터는 라우팅만” |
| **채널·프로젝트** | 채널 또는 프로젝트 단위. 같은 Consumer라도 채널/프로젝트마다 다른 룰. | “A 프로젝트: 코드 스타일 가이드”, “B 채널: 영어만”    |
| **세션·채팅**     | 가장 좁은 범위. 특정 대화·세션에만.                                   | 현재 “이 대화에만 적용되는 지침”에 해당               |
| **모델**          | 특정 모델에만 적용. (같은 Consumer라도 모델별 다른 룰)                | “llama는 JSON 강조”, “llava는 이미지 설명만”          |
| **태스크**        | Consumer 내부의 세부 태스크.                                          | “제목 생성”, “요약”, “코드 설명”                      |

- **계층 결합**: 호출 시 “시스템 → Consumer → 채널/프로젝트 → 세션” 순으로 **겹쳐서** 최종 문자열을 만드는 방식은 유지할 수 있음. “통합 관리”는 **각 층의 내용을 중앙에서 편집·버전 관리**하는 쪽에 초점.

### 3.3 Consumer (사용처) — “누가 쓰는가”

| Consumer 예시       | 필요한 룰의 성격                                            |
| ------------------- | ----------------------------------------------------------- |
| **기본 채팅**       | 대화 품질, 출력 형식, 금지 사항                             |
| **오케스트레이터**  | 라우팅 규칙, 어떤 입력을 어떤 모델/스킬로 보낼지            |
| **Nexus Map**       | 노드 설명 생성, 연결 규칙, 페르소나/스킬 설명               |
| **메타데이터 추출** | 형식별(문서/이미지/코드) “이 JSON 스키마만 출력하라”는 지침 |
| **시스템 보조**     | 배치·알림·에러 해석 등 백그라운드 태스크용 지침             |
| **파일/탐색기**     | (앞으로) 검색 힌트, 요약 표시용 짧은 룰                     |

- 각 Consumer는 **“나에게 필요한 룰 세트 키”**를 알고 있고, **Resolution API**(아래)에 “Consumer + 컨텍스트(채널, 프로젝트, 모델, 태스크)”를 넘겨 **최종 결합된 룰 문자열**을 받는다.

### 3.4 해석 순서 (Resolution) — “어떤 룰을 어떻게 합칠까”

1. **키 기반 조회**: Consumer 이름(또는 태스크 키) + 스코프(시스템 / Consumer / 채널 / 프로젝트 / 모델 / 세션)별로 “활성”인 룰 세트 목록을 가져온다.
2. **우선순위**: 시스템(가장 아래) → Consumer 기본 → 채널/프로젝트 → 모델 오버라이드 → 세션(가장 위). 위일수록 기존 내용을 **덮어쓰거나 뒤에 붙이는** 정책(append vs override)을 하나 정한다.
3. **결과**: 하나의 문자열(또는 메시지 배열)로 합쳐서 반환. 호출부(채팅, 오케스트레이터 등)는 이 결과만 `systemInstruction` 등에 넣어 쓰면 됨.

## 3.5 룰 항목 통일 — 가능 여부와 방향

**질문**: 도메인별·프로젝트별·용도별로 룰을 다르게 두면 사용자는 “여기는 채팅용, 여기는 Nexus용”처럼 이해하기는 쉽겠지만, 전체 시스템에서는 **일관성이 떨어지고 복잡도**가 올라가지 않을까? **룰 항목(구조)을 통일**할 수 있을까?

**답**: **가능하고, 통일하는 편이 좋다.**  
“통일”은 **룰 하나의 데이터 구조와 해석 방식**을 도메인·프로젝트·용도와 관계없이 **같게** 두는 것이다. **내용(content)** 과 **적용 대상(어디에 쓰이느냐)** 만 다르게 두면 된다.

| 통일하는 것                     | 설명                                                                                                                                                                                    |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **룰 항목 스키마**              | 모든 룰이 같은 필드(id, key, name, content, scope, consumer, …)를 가진 **한 가지 엔티티**. “채팅 전용 테이블”, “Nexus 전용 테이블”을 나누지 않고, **테이블/저장소는 하나**.             |
| **해석(Resolution) 파이프라인** | 스코프 순서(시스템 → Consumer → 채널/프로젝트 → 세션), 결합 규칙(append/override)을 **한 가지**로 고정. Consumer가 달라도 “키와 적용 대상만 넣으면 결합 문자열이 나온다”는 동작은 동일. |
| **형식**                        | 본문은 예를 들어 **마크다운 문자열 하나**로 통일. (필요 시 플레이스홀더만 추가.) “채팅용은 JSON, Nexus용은 YAML”처럼 용도별로 형식을 나누지 않음.                                       |

| 통일하지 않는 것 (그래도 괜찮은 것) | 설명                                                                                                                                                                                                         |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **내용**                            | 채팅용 룰과 오케스트레이터용 룰의 **문구**는 당연히 다름. 같은 구조에 **다른 content**만 넣으면 됨.                                                                                                          |
| **적용 대상**                       | 어떤 룰을 어떤 Consumer/채널/프로젝트에 쓸지는 **연결(Assignment)** 로만 구분. 스키마는 같고, `consumer`·`channel_id` 등 필드 값만 다름.                                                                     |
| **UI에서의 보이기**                 | 사용자에게 “채팅용”, “Nexus용”처럼 보이게 하려면, **목록/필터**에서 `consumer`·스코프로 걸러서 보여 주거나, **레이블(태그)** 만 붙이면 됨. “데이터 구조를 나누는 것”이 아니라 **보기만 용도별로** 나누면 됨. |

**정리**

- **룰 항목은 하나의 구조로 통일**하고, **저장소·Resolution API·UI(폼/목록)** 도 그 구조 하나만 다루면, 전체 시스템 **복잡도는 낮고 일관성은 높다**.
- 도메인/프로젝트/용도별로 “다르게” 보이는 부분은 **같은 엔티티**에 `consumer`, `scope`, `channel_id` 등을 넣어 구분하고, UI에서 필터·레이블로만 “채팅용만 보기”, “Nexus용만 보기”처럼 나누면 된다.
- 즉, **“통일된 룰 항목 + 적용 대상(스코프·Consumer)으로만 차이”** 로 가져가면, 사용자 이해도(용도별로 구분해서 보기)와 시스템 일관성(구조·파이프라인 하나)을 동시에 잡을 수 있다.

### 3.6 페르소나 + 스킬 ⇒ 테스크 추출 (룰 적용의 개념 모델)

룰을 "누가, 어떤 능력으로, 어떤 일을 할지"에 따라 쓰이게 하려면, **페르소나(Persona) + 스킬(Skill) ⇒ 테스크(Task) 추출**이라는 관점을 도입하는 것이 좋다.

| 개념         | 역할                                                                                                                                                                      |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **페르소나** | AI의 **역할·성향·말투**. "기술 문서 전문가", "요약 담당", "코드 리뷰어" 등. **누가(Who)** 에 해당.                                                                        |
| **스킬**     | AI가 가진 **기능·할 수 있는 일**. "요약", "라우팅", "JSON 추출", "노드 설명 생성" 등. **무엇을 할 수 있는가(What)** 에 해당.                                              |
| **테스크**   | 실제로 **지금 수행할 작업**. "이 대화에서 요약만 해라", "이 입력을 오케스트레이터가 라우팅해라" 등. **구체적인 일(Task)** 은 **페르소나와 스킬의 조합**에서 **추출**된다. |

**로직**:

- **페르소나**가 "어떤 맥락·역할로 말할지"를 정하고, **스킬**이 "어떤 능력을 쓸지"를 정한다.
- 그 둘이 결합되면 **"지금 이 요청에 대한 테스크"**가 정해진다. 예: 페르소나="기술 문서 전문가", 스킬="요약" ⇒ 테스크="기술 문서 요약".
- **룰 Resolution** 시에는 "지금 컨텍스트의 **테스크**"를 알면, 그 테스크에 맞는 룰 세트를 가져오면 된다.
- 따라서 **테스크**는 "Consumer + (선택) 페르소나 + (선택) 스킬"에서 **유도된 값**으로 두고, Resolution API에 **consumer**, **task**(또는 persona_id + skill_id)를 넘기면, 그에 맞는 룰만 조회·결합할 수 있다.

**현재 스키마와의 대응**

- **Consumer** = 사용처(채팅, 오케스트레이터, Nexus 등). 넓은 의미의 "어떤 종류의 일".
- **테스크** = Consumer 내부의 세부 작업. `rule_assignments`에 **task** 컬럼(또는 `task_key`)을 두면 "이 룰은 이 테스크에만 적용"으로 좁힐 수 있음.
- **페르소나·스킬** = 확장 시 `rule_assignments`에 `persona_id`, `skill_id`(또는 키)를 두고, "이 페르소나 + 이 스킬 조합일 때만 이 룰 적용"으로 매핑 가능.
- 정리하면, **"페르소나 + 스킬 ⇒ 테스크"** 로 "지금 할 일"을 정하고, 그 **테스크**(및 선택적으로 persona/skill)를 Resolution 조건에 넣어 **해당 룰만** 가져오는 흐름으로, 본 문서의 룰 통합 관리와 기존 기획서의 페르소나·스킬·테스크 체계를 맞출 수 있다.

## 4. 데이터·저장 초안

**스키마 관리**: DDL/SQL 파일은 별도로 두지 않는다. 테이블은 **Workbench에서 직접 생성·관리**하며, 아래 속성 정의를 참고한다.

### 4.1 테이블 구성 (2테이블)

- **rule_sets**: 룰 **본문과 식별 정보**. 하나의 “룰 내용”을 여러 곳에 재사용할 수 있도록 본문만 저장.
- **rule_assignments**: 그 룰을 **어디에 적용할지**(스코프, Consumer, 채널, 프로젝트, 모델). Resolution 시 이 테이블로 “지금 컨텍스트에 맞는 룰”을 찾고 `rule_sets`와 조인해 `content`를 결합.

### 4.2 rule_sets 테이블 속성

| 컬럼        | 타입                    | 필수 | 설명                                                                       |
| ----------- | ----------------------- | ---- | -------------------------------------------------------------------------- |
| id          | INT, PK, AUTO_INCREMENT | O    | 기본 키                                                                    |
| key         | VARCHAR(120), UNIQUE    | O    | 고유 식별자. 예: `chat.default`, `orchestrator.routing`, `nexus.node_desc` |
| name        | VARCHAR(255)            | O    | 표시 이름 (UI 목록·폼용)                                                   |
| description | VARCHAR(500)            | -    | 설명(용도, 사용처 등)                                                      |
| content     | MEDIUMTEXT              | O    | 룰 본문. 마크다운 또는 평문. `{{placeholder}}` 가능                        |
| is_active   | TINYINT(1), DEFAULT 1   | O    | 1=활성, 0=비활성(Resolution에서 제외)                                      |
| version     | INT, DEFAULT 1          | -    | 버전. 변경 이력·롤백 시 활용(선택)                                         |
| created_at  | DATETIME                | O    | 생성 시각                                                                  |
| updated_at  | DATETIME                | O    | 수정 시각                                                                  |
| created_by  | VARCHAR(100)            | -    | 생성자 식별(선택)                                                          |

- **인덱스**: `uk_key`, `idx_active`, `idx_updated`.

### 4.3 rule_assignments 테이블 속성

| 컬럼        | 타입                    | 필수 | 설명                                                                                                            |
| ----------- | ----------------------- | ---- | --------------------------------------------------------------------------------------------------------------- |
| id          | INT, PK, AUTO_INCREMENT | O    | 기본 키                                                                                                         |
| rule_set_id | INT, FK → rule_sets.id  | O    | 적용할 룰 세트. CASCADE DELETE                                                                                  |
| scope       | VARCHAR(30)             | O    | `system` \| `consumer` \| `channel` \| `project` \| `model` \| `session`. 결합 시 정렬 순서(낮은 스코프가 먼저) |
| consumer    | VARCHAR(60)             | O    | 사용처. `chat`, `orchestrator`, `nexus`, `metadata_extract`, `system` 등                                        |
| channel_id  | VARCHAR(80)             | -    | 채널 ID. NULL이면 해당 Consumer 전역                                                                            |
| project_id  | VARCHAR(100)            | -    | 프로젝트 ID. NULL이면 프로젝트 무관                                                                             |
| model       | VARCHAR(120)            | -    | 모델 이름. NULL이면 모델 무관                                                                                   |
| session_id  | VARCHAR(80)             | -    | 세션/채팅 ID 등 가장 좁은 범위                                                                                  |
| sort_order  | SMALLINT, DEFAULT 0     | -    | 같은 스코프 내 결합 순서. 작을수록 앞                                                                           |
| is_active   | TINYINT(1), DEFAULT 1   | O    | 1=활성                                                                                                          |
| created_at  | DATETIME                | O    | 생성 시각                                                                                                       |
| updated_at  | DATETIME                | O    | 수정 시각                                                                                                       |

- **인덱스**: Resolution 조회용 `idx_resolution(consumer, scope, is_active)`, `idx_channel(consumer, channel_id)`, `idx_project(consumer, project_id)`, `idx_model(consumer, model)`, `idx_rule_set(rule_set_id)`.

### 4.4 Resolution 조회 예시

- “채팅, 채널 A, 현재 세션”에 적용되는 룰을 가져오려면:  
  `rule_assignments`에서 `consumer='chat'`, `channel_id IN (NULL, 'A')`, `session_id IN (NULL, current_session_id)`, `is_active=1` 인 행을 `scope`·`sort_order` 순으로 조회 → `rule_set_id`로 `rule_sets` 조인 → `content`를 스코프 순으로 결합.

- **1단계**: 위 스키마로 DB에 저장. **2단계**: UI에서 rule_sets CRUD + rule_assignments로 “어떤 Consumer/채널/프로젝트에 연결할지” 지정.

- **기존 채팅 instruction** 과의 관계:
  - **마이그레이션**: 현재 시스템/채널/채팅 instruction을 “룰 세트”로 옮기고, 스코프만 매핑.
  - **채팅**은 당분간 기존처럼 localStorage로 쓰다가, Resolution API가 준비되면 “채팅 Consumer + 현재 채널/채팅 ID”로 조회해 치환할 수 있음.

## 5. UI — “한 군데서 관리”하는 화면

### 5.1 테이블 기반 (기본안)

- **룰·프롬프트 관리 전용 화면** 하나를 둔다.
  - **목록**: 룰 세트 목록. 필터: Consumer, 스코프, 채널/프로젝트, 활성 여부.
  - **생성/수정**: 이름, key, 본문(content), 스코프, 적용 대상(Consumer, 모델, 채널/프로젝트 선택), 활성/비활성.
  - **미리보기**: 선택한 룰(또는 여러 개 결합)이 최종 문자열로 어떻게 붙는지 미리보기.
  - **적용 테스트**: “채팅 Consumer + 채널 A”로 Resolution 호출한 결과를 보여 주거나, 실제로 짧은 채팅 한 번 돌려 보기.
- **적용(Apply)**: “이 룰 세트를 채널 B의 채팅에 적용”처럼 **연결(Assignment)** 만 저장하면, 해당 Consumer가 그 컨텍스트에서 Resolution 할 때 자동으로 포함된다.  
  즉, “생성·수정”은 룰 내용 편집, “적용”은 “어디에 쓰일지” 연결하는 것.

- **위치**: AI 도메인 설정 패널 안에 “룰·프롬프트” 탭으로 두거나, Nexus/시스템 설정과 함께 두는 **공통 설정** 영역으로 둘 수 있음.  
  사용처가 많아지면 **독립 메뉴**(예: “Rule Manager”)로 빼도 됨.

### 5.2 그래프 기반 UI 제안 (D3 등 노드·라인) — 구현 가능

기존 **테이블/폼** 틀을 넘어서, **노드(Node)와 라인(Edge)** 으로 룰·페르소나·스킬·테스크를 시각화하고, **선택·연결·노드 추가·믹싱 → 테스크 추출 → 과제 부여 → 시뮬레이션**까지 한 흐름으로 다루는 UI는 **구현 가능**하다.

| 항목 | 설명 |
|------|------|
| **구현 수단** | **D3.js**, 또는 Vue/React 생태계의 **Vue Flow**·**React Flow**, **Cytoscape.js**, **vis-network** 등으로 노드·엣지 캔버스를 구현할 수 있음. NEXA에 Nexus Map이 이미 노드/엣지 UX를 계획하고 있다면, 같은 라이브러리나 패턴을 재사용하면 일관성과 개발 부담 절감에 유리함. |
| **노드** | **룰 세트**, **페르소나**, **스킬**, **테스크** 등을 각각 노드로 표시. 노드 타입별로 아이콘·색·모양을 구분. 드래그로 배치, 더블클릭 또는 패널에서 본문(content) 편집. |
| **라인(엣지)** | 노드 간 **연결** = “이 룰을 이 스킬에 적용”, “이 페르소나 + 이 스킬 ⇒ 이 테스크”, “이 테스크는 이 Consumer에 할당” 등. 라인을 그으면 곧 **rule_assignments** 또는 페르소나·스킬·테스크 관계로 저장 가능. |
| **선택·연결·노드 추가** | 노드를 선택하고, “연결할 노드”를 선택하거나, 새 노드를 추가한 뒤 라인으로 이어서 **믹싱**(어떤 룰이 어떤 페르소나/스킬과 묶이는지)을 시각적으로 구성. |
| **테스크 추출** | “페르소나 + 스킬 ⇒ 테스크”(§3.6)에 따라, **연결된 페르소나·스킬 노드**에서 **테스크 노드**를 자동 생성하거나, 사용자가 “이 조합으로 테스크 만들기”를 실행하면 테스크가 추출·등록됨. |
| **과제 부여** | 특정 **테스크** 노드에 “과제”(예: 샘플 입력, 기대 출력)를 붙이거나, “이 경로로 Resolution 실행” 대상을 지정. |
| **시뮬레이션** | 선택한 **경로**(시작 노드 → 룰/페르소나/스킬을 거쳐 테스크까지) 또는 **선택한 노드들**에 대해, **Resolution API**를 호출해 “이 조합일 때 결합되는 최종 프롬프트”를 미리보기하거나, **실제로 한 번 호출**(드라이 런 또는 테스트 채팅)해 결과를 확인. “시뮬레이션” = 구성한 그래프가 실제 동작과 맞는지 검증하는 단계로 둘 수 있음. |

- **정리**: 테이블만으로도 CRUD와 적용은 가능하지만, **노드·라인 기반 UI**로 가면 “어떤 룰이 어디에 어떻게 엮이는지”가 한눈에 들어오고, **페르소나 + 스킬 ⇒ 테스크** 추출·과제 부여·시뮬레이션까지 같은 캔버스에서 처리할 수 있다. **구현 가능**하고, 단계적으로는 Phase 3에서 테이블 UI를 먼저 넣은 뒤, Phase 4 또는 별도 Phase에서 **그래프 뷰**를 추가하는 식으로 도입할 수 있다.

## 6. 단계적 접근 (막막함 줄이기)

| 단계               | 목표                                  | 할 일                                                                                                                                                                                                                                                                |
| ------------------ | ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Phase 0 (현재)** | 채팅만, 시스템/채널/채팅 instruction. | 유지.                                                                                                                                                                                                                                                                |
| **Phase 1**        | **중앙 저장소** 도입.                 | (1) 룰 세트를 파일 또는 DB에 정의. (2) **Resolution API** 한 개 구현(키/Consumer/스코프 입력 → 결합 문자열 출력). (3) 채팅은 “가능하면” 이 API를 쓰도록 전환(또는 기존 localStorage + 하드코딩 룰을 “시스템 스코프 1개 + 채널/채팅 2개”로 매핑해 Resolution에 넣음). |
| **Phase 2**        | **다른 Consumer** 연결.               | 오케스트레이터, 메타데이터 추출, Nexus 등에서 “자기 Consumer 키”로 Resolution API 호출하도록 연결. 각 사용처별 **기본 룰 세트**를 1~2개씩 등록.                                                                                                                      |
| **Phase 3**        | **관리 UI**.                          | 룰 세트 목록/생성/수정 화면. 필터, 적용 대상 지정, 미리보기.                                                                                                                                                                                                         |
| **Phase 4**        | **고급**.                             | 버전 관리, 플레이스홀더(템플릿), 모델별/프로젝트별 오버라이드, A/B 테스트. **그래프 기반 UI**(§5.2): D3 등 노드·라인으로 룰/페르소나/스킬/테스크 선택·연결·믹싱, 테스크 추출, 과제 부여, **시뮬레이션**(Resolution 미리보기·테스트 호출).                                                                                                                                     |

- 먼저 **Phase 1**만 정하면 “한 군데서 정의하고, 한 API로 조회”가 가능해진다. UI는 Phase 3에서 해도 되고, 그 전에는 설정 파일/DB 직접 편집으로도 운영 가능하다.

## 7. 정리

- **룰 항목 통일** = 도메인·프로젝트·용도와 관계없이 **같은 스키마·같은 Resolution** 하나. 내용과 적용 대상만 다르게 두고, “다르게 보이기”는 UI 필터·레이블로 처리 → 일관성 확보, 복잡도 억제.
- **한 군데서 관리** = 룰 세트를 **엔티티**로 두고, **스코프·Consumer·적용 대상**으로 연결한 뒤, **Resolution API** 한 곳에서 “누가, 어떤 컨텍스트에서 쓰는지”에 따라 **결합된 룰 문자열**을 내려주는 구조.
- **생성·수정·적용** = (1) 룰 세트 내용 편집, (2) “이 룰을 어떤 Consumer/채널/프로젝트/모델에 쓸지” 연결. UI에서는 목록 + 폼 + 적용 대상 선택으로 처리.
- **많은 모델·많은 룰** = “모델별 룰”, “프로젝트별 룰”을 **스코프와 적용 대상**으로만 추가하면 되고, Resolution 순서만 정해 두면 코드는 “Resolution API 호출” 한 번으로 유지된다.
- **막막할 때**: Phase 1(저장소 + Resolution API)만 먼저 정하고, 기존 채팅 instruction을 그 API로 이어 붙인 다음, 새 Consumer를 하나씩 붙여 나가면 된다.  
  이 문서는 그때까지의 **지도**로 두고, 세부 스키마·API 시그니처·UI 와이어프레임은 구현 단계에서 구체화하면 된다.
